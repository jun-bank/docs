# UC-15. 실패한 정산을 강제 재개한다

- 작성일: 2026-08-05
- 상태: **검토대기 (계약 블록 완결)**
- 액터: **운영자 2인** — 요청 = 담당자(maker) · 승인 = 책임자(checker) (BR-55 · 같은 사람 불가)
- 권한 요건: **BR-56 ④** (책임자 승인 조작) · 스코프 = ★ **전사 스코프만** (BR-55 특칙 — 대상이 영업일이라 고객·조직 귀속 축이 없다)
- 트랜잭션 경계: ★ **E1~E5 아님 — 자금 무이동** (커밋은 둘: ① C8 `consume` + 재개 지시 이벤트 outbox INSERT가 같은 커밋 ② C4 수신측 `resumeByOperator` 커밋 — **R15**, 원자적으로 묶이지 않는다)
- 관련 규칙: BR-37·52·53·54·55·56·57·58 · Settlement INV-4 · 정산 SM S6·SF1·SF6·SF8·SF10 · ApprovalRequest INV-1~4·A1~A5 · ADR-014 O-13·O-16 · ADR-017 AD-2·5·6·8 (참조만 — F-24)

## 1. 목표 (한 문장)

자동 재시도가 소진되어 `FAILED`로 굳은 영업일의 정산을 **2인 승인을 거쳐 재개**해, 그날 순액이 확정될 수 있게 한다.

## 2. 사전 조건 / 사후 조건

- 사전: 대상 정산이 `FAILED` **이고** `retryCount ≥ 임계`다 (S6 사전조건 — 임계 미만이면 SF10). 요청자가 **전사 스코프** 담당자다. 임계값은 **[미확정]**(BR-37 — 미확정 수치 표).
- 사후(성공): 승인 `CONSUMED` + 지시 이벤트 발행(**같은 커밋** — R15) → C4 수신 → `retryCount = 0` · 상태 `CALCULATING` · **사유 기록 필수** · `SettlementResumedByOperator` 발행 · 감사 기록. ★ **이 UC의 목표는 재개까지다** — 그 뒤 `calculate` 성공 여부는 정산 배치 경로(운영 절차)에 속한다.
- 사후(거절/만료): 정산 상태 **무변화**. 요청이 `REJECTED`/`EXPIRED`(종료 — 재사용 불가), 사유가 감사에 남는다.
- 사후(승인은 됐으나 지시가 정체): 승인은 이미 `CONSUMED`인데 재개는 일어나지 않았다 — ★ **유실이 아니라 정체**(M17)다. **새 승인 없이 재투입**이 경로이고(UC-19), 이중 실행은 **지시 ID 멱등**이 막는다.
- 사후(수신측 거절 — 대상 상태가 바뀌었다): 정산 무변화 + 거절 사실이 감사에 남는다(§4-H).

## 3. 주요 성공 시나리오

1. 담당자 A가 `escalate`로 운영자 목록에 오른 미결 정산을 확인한다 [S5 · BR-53 ④ 통지]
2. A → C8 `request(정산 강제 재개, **지시 ID** · businessDate · 사유)` — ★ 지시 ID는 maker가 생성해 요청 인자에 싣는다(UC-16과 통일 — INV-3 검사 대상이 되고, EXPIRED 후 재요청은 새 ID) — `PENDING` [A1 · 감사 직접 append]
3. 책임자 B → C8 `approve(B)` — **B ≠ A** 검사 → `APPROVED` [A2 · INV-1]
4. ★ 승인 시점에 C8이 **`consume` + 재개 지시 이벤트 outbox INSERT를 같은 커밋**으로 수행 [A4 ④ 경로 · **R15** · AD-6] — **실행 엔드포인트는 없다**
5. 릴레이가 지시 이벤트를 C4로 전달 — 계좌ID 없는 이벤트라 **파티션 0** [ADR-014 O-6·O-8]
6. C4 수신 — **지시 ID 멱등** 검사 후 `resumeByOperator(operator, reason)` 호출. 기술 실행자는 수신 시스템이고 **업무 귀속 = maker**(지시 이벤트에 maker·checker가 실린다) [A4 · settlement.md §4]
7. `retryCount = 0` · `CALCULATING` · `SettlementResumedByOperator` 발행 · 감사 outbox (커밋 내 — AD-2) [S6]
8. 이후 정산 배치가 `calculate`로 `COMPLETED`에 도달한다 — **이 UC 밖**(운영 절차)

## 5. 대체 시나리오

- **임계 도달 전 자동 재시도**(S4 `retry`) — 목표(순액 확정)는 같고 주체가 시스템이다. 임계 안에서 성공하면 이 UC는 발생하지 않는다. 임계를 넘으면 자동 경로는 닫히고 **이 UC가 `FAILED`의 유일한 탈출구**가 된다(SF6 주석).

## 6. 인가·감사 ★

- 주체 판정 순서: ★ **① 단계(담당자/책임자) + 전사 스코프 — 둘 다 요청자의 자기 속성이라 대상 조회 전에 판정**(FORBIDDEN_LEVEL이 대상 존재 탐색 채널이 되지 않는다 — UC-02 선례) → **② 대상 정산 존재** → **③ 상태·`retryCount`**(SF8·SF10).
- L7: ★ **존재 비노출의 대상이 아니다** — 대상 식별자가 **영업일**이라 추측 가능한 공개 축이고 고객·조직 귀속이 없다(BR-58의 소유 축이 성립하지 않는다). 대신 **거절 시도는 기록**한다(독립 커밋 — AD-2). *(U-6 근거)*
- 감사 경로: 요청·승인·거절·만료 = **C8 직접 append**(AD-5) / C4 재개 실행 = **커밋 내 outbox**(AD-2 · R13) / 거절·실패 = **독립 커밋**(AD-2) / 목록 조회 = 비동기(AD-4).
- 항목: AD-8 — 주체·시각·대상(영업일)·스코프·종류·결과 + **사유·요청자·승인자**(BR-56 조작).

## 7. 계약 (계약 블록)

> **공통 승인 계약의 정본 = UC-02 §7** (`POST /ops/approval-requests` · `/{id}/approve` · `/reject` · `GET /ops/approval-requests`) — 복사하지 않고 참조한다(U-7 · F-24). 이 UC가 정의하는 것은 **④의 조작별 인자**와 ★ **R15 지시 이벤트**다.
> ★ **실행 엔드포인트가 없다**(R15) — 승인 커밋이 `consume` + 지시 이벤트 outbox INSERT를 함께 수행하고(A4 ④), **실행 1회는 수신측 지시 ID 멱등**이 보장한다.
> 오류 코드 3계층 = K-1 ⑴ 공통 4종(`FORBIDDEN_LEVEL`·`NOT_FOUND`·`INVALID_STATE`·`ARG_MISMATCH`) / ⑵ ★ **정산 SM 금지 표의 응답 열이 정본**(SF1·SF8·SF10 — 계약이 재발명하지 않는다) / ⑶ ★ **이 UC에서 처음 만드는 코드는 없다** — 쓰는 코드는 전부 **신설 코드 대장**(색인 §5 K-1)에 이미 등재된 것들이다: `DUPLICATE_INSTRUCTION`(④⑤ 지시 ID — **대장 신설분**이며 정본 착지는 UC-02 §7) · `ALREADY_APPROVED/REJECTED/CONSUMED/EXPIRED`(승인요청 종료 재호출 — 대장 신설분). *"고유 신설 없음"* 은 **대장 밖 코드를 만들지 않았다**는 뜻이지 이 UC가 대장에 아무것도 얹지 않았다는 뜻이 아니다.
> 운영자 화면 전환도는 공통이다 — **UC-02 §7 참조**(승인 대기 목록 → 요청 상세 → 승인/거절). ★ 단 ④에는 *"실행 확인"* 화면이 없다(실행 엔드포인트 부재).

> ★ **확정 (D-㉡) — 요청 시점에 대상 정산의 존재·상태(`FAILED`·`retryCount ≥ 임계`)를 검사하지 않는다. 권위는 수신측(C4) 단독이다.**
> C4는 **별도 배포**이고 R15가 존재하는 이유가 *"배포 경계를 넘는 동기 호출·원자 커밋을 만들지 않는다"*(ADR-010)이다 — 따라서 C8은 요청 시점에 정산 상태를 **볼 수 없다**. SF8·SF10 거절은 전부 **승인 이후 수신측**에서 일어나고(§4-C·D·H), 거절은 **감사 독립 커밋으로 관측**된다(★ 새 M을 적재하지 않는다 — 아래 (수신) 블록 감사 칸의 확정).
> ⚠️ **승인 낭비를 감수한다** — 2인 승인을 다 받은 요청이 수신 시점에 거절될 수 있다. **그 종결 처리는 아래 (수신) 블록에서 확정됐다**(감사 독립 커밋 · 새 M 없음 — §9 UC15-2 닫힘).
> ★ **화면이 무엇을 정산 상태 소스로 쓰는가는 후속이다**(D-㉡ — `escalate` 목록(§3-1)의 소스가 구독 복제인지 조회인지. **참고 표시일 뿐 권위가 아니므로** 이 계약은 그것에 의존하지 않는다. C8→C4 관계 신설은 이 패스에서 하지 않는다 — 신설된 관계는 R17·R18 둘뿐이다).

#### (수신) C4 `resumeByOperator` — 지시 이벤트 처리 계약 ★ **엔드포인트가 아니다**

| 항목 | 내용 |
|---|---|
| 주체 | **시스템**(릴레이 경로 — 경로 식별자 필수 · C-1 · BR-54 ③). ★ 업무 귀속 = payload의 `maker`(A4 ④) |
| 요청 | 지시 이벤트 payload 그대로. **다른 호출 표면이 없다**(§4-B — 운영자용 재개 엔드포인트 부재) |
| 응답(성공) | ★ **응답 상대가 없다**(비동기). 사후 = `retryCount = 0` · `CALCULATING`(S6) · `instructionId`·사유 저장 · `SettlementResumedByOperator` 발행 · 감사 outbox — **한 커밋** |
| 오류 표 ★ | ★ 아래는 응답 코드가 아니라 **감사(독립 커밋)에 남는 거절 사유 값**이다 — 새 불일치(M)를 만들지 않는다(아래 감사 칸 확정). **정산 SM 금지 표의 응답 열이 정본**(K-1 ⑵): `SETTLEMENT_NOT_FAILED`(**SF8** — `PENDING`·`CALCULATING`·`COMPLETED`. §4-C · 승인~수신 간극의 §4-H) · `SETTLEMENT_RETRY_REMAINING`(**SF10** — 임계 미만. §4-D) · 대상 영업일 부재 = `NOT_FOUND`(★ L7 ✕ — 축이 없어 **부재만** 있다) · ★ **중복 `instructionId`는 오류가 아니라 무연산**(§4-F) |
| 멱등 | ★ **`instructionId` 유일 — 무연산**(원장 INV-9와 같은 형태). 두 번 재개되면 `retryCount`가 또 0으로 밀려 SF6 임계가 무의미해진다(§4-F) |
| 예산 | 실시간 아님 — 비동기 릴레이. 전달 지연·재시도·DLQ 상한은 **ADR-014 소관**(O-10·O-11) |
| 감사 | 성공 = **커밋 내 outbox**(AD-2 · R13) — 주체 = 경로 식별자 **+ 업무 귀속 `maker`**(두 주체) · 대상 = `businessDate` · **스코프 = `전사`**(K-4) · 결과 + 사유·요청자·승인자(BR-56 조작). **거절(SF8·SF10) = 독립 커밋**(AD-2) · ★ **확정 (2026-08-06 듀얼 리뷰 F-03/c-F03) — 수신 거절의 관측 계약**: **거절은 새 M을 적재하지 않는다** — 거절 사실은 **감사 독립 커밋**으로 남고(AD-2), 재개가 계속 필요한 상태라면 **기존 감시가 잡는다**(드레인 미완 = M16 적재 경로 · 정산 방치 = BR-53 통지 — ★ 재점검 정정: SF8이 모든 상태에서 M16 선행을 보장하지는 않는다). 지시는 그 자리에서 종결이며 재개하려면 **새 2인 승인**이다(승인 낭비 — 위 D-㉡). **§9 UC15-2 닫힘** |

#### 이벤트 `SettlementResumedByOperator` (기존 — **정본 = settlement.md §4.1**. 계약 확인 블록)
