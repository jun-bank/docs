# UC-04. 카드 분실을 신고한다

- 작성일: 2026-08-05
- 상태: **확정** (정본 판정 2건 반영 — 2026-08-05)
- 액터: **고객(소지자) ∪ 운영자 담당자** — ★ 두 주체가 같은 전이를 공유하는 유일한 조작 (카드 SM C1)
- 권한 요건: 고객 = 자기 카드만 / 운영자 = **담당자** 단계 + 스코프 안 (BR-55 배정 표)
- 트랜잭션 경계: **없음 — 단일 애그리게이트 상태 전이** (카드 `suspend` — 자금 무이동)
- 관련 규칙: BR-15·35·54·55·57·58 · 카드 SM C1·C2 (참조만)

> 이 문서를 다 읽으면 **분실 카드가 어떻게 즉시 정지되는지, 고객과 운영자 두 주체가 같은 전이를 어떻게 공유하고 감사가 그 둘을 어떻게 구분하는지**를 설명할 수 있어야 한다.

## 1. 목표

분실·도난이 의심되는 카드를 **즉시 정지**해 신규 승인을 막는다.\
기존 매입 반영은 계속된다(BR-35).

## 2. 사전·사후 조건

시작 조건은 하나다.\
카드가 해지 상태가 아니다(C1 조건).

끝 상태는 둘로 갈린다.

- **성공** — `status = 정지`로 서고, **신규 승인만 차단**된다(BR-15).\
  홀딩·한도 사용액은 불변이다.\
  매입·환불은 계속 반영된다(BR-35).\
  신고 주체가 감사에 남는다.
- **거절** — 상태는 변하지 않고, 시도가 기록된다.

### 동작 구조

두 주체(고객/운영자)가 경로만 다르게 같은 정지 전이를 공유하는 구조를 보여준다.

```
[고객(본인 카드)]       ──POST /me/cards/{id}/suspension──┐
[운영자 담당자(스코프)]  ──POST /ops/cards/{id}/suspension─┤
                                                           ▼
                                          [정지 UC — 카드 SM C1]
                                                   │
                                                   ▼
                                    [카드] suspend: NORMAL → SUSPENDED
                                                   │       (홀딩·한도 불변)
                                     ┌─────────────┴─────────────┐
                                     ▼                           ▼
                          [CardSuspended 발행]            [감사 outbox]
                          (행위자 비포함 AD-7②)       주체 유형·개인 (AD-8)
```

## 3. 주요 성공 시나리오

1. 신고 접수 — 주체 판정 (고객 본인 카드 / 운영자 스코프 안) [BR-54·55]
2. `suspend(requester)` — `NORMAL → SUSPENDED` [카드 SM C1]
3. `CardSuspended` 발행 (운영자 전용 이벤트 아님·자금 이벤트 아님 — payload에 **신고 주체 유형** 포함 여부는 §9) 
4. 감사 기록 — **누가**(소지자인지 운영자인지) 정지시켰는가 [BR-57 · CDS1이 예고한 신호]

### 흐름도

정지 성공 흐름에 스코프·상태 분기(§4 A~D)와 정지 후 사건(§4 E~G, §5)을 얹었다.

```
[시작: 분실·도난 신고 접수]
   │  주체 판정 (고객 본인 / 운영자 스코프 · 운영자 대행 §5)
   ▼
⟨주체 스코프 안 & 카드 존재?⟩ ──아니오──▶ [NOT_FOUND — 부재 동일] (§4-A·B)
   │ 예
   ▼
⟨카드 상태?⟩ ──TERMINATED──▶ [거절: 전이 없음] (§4-C)
   │ NORMAL     └─SUSPENDED──▶ [거절: ALREADY_SUSPENDED (CF9)] (§4-D)
   ▼
[suspend: NORMAL → SUSPENDED]  (신규 승인만 차단 BR-15 · 홀딩·한도 불변)
   │
   ▼
[CardSuspended 발행 + 감사(주체 유형·개인)] ──▶ (끝)

[정지 후]
 · 승인 전문 도착 → 거절 CARD_SUSPENDED (CF4, §4-E)
 · 매입 파일 도착 → 반영됨 (외부 확정 사실 BR-35, §4-F)
 · 오신고(카드 찾음) → resume: SUSPENDED → NORMAL (정지와 대칭, §4-G)
```

## 4. 예외 시나리오 ★

정지는 신규 승인만 막는 조작이라, 어디서 갈라져 무슨 코드로 끝나는지가 성공 경로만큼 중요하다.\
아래 표는 트리거와 응답 코드의 대응이다 — 코드는 §7 계약의 정본과 같다.

| # | 트리거 | 응답 코드 → 종결 | 근거 |
|---|---|---|---|
| A | 타인 카드 지목(고객) | `NOT_FOUND` — 부재와 동일 형태 + 시도 기록 | BR-58 (L7) |
| B | 운영자 스코프 밖 카드 | `NOT_FOUND` — 부재와 동일 형태 | BR-58 · IS-4 |
| C | 해지된 카드 | 거절 — `TERMINATED`에서 전이 없음 | 카드 SM C1 조건 |
| D | 이미 정지된 카드 재신고 | `ALREADY_SUSPENDED` — 명시 거절 | 카드 SM CF9 |
| E | 정지 직후 승인 전문 도착 | `CARD_SUSPENDED` — 거절 | BR-15 · 카드 SM CF4 · UC-01 §4-C·§7 |
| F | 정지 중 매입 파일 도착 | 반영된다(거절 아님) | BR-35 |
| G | 오신고 — 카드를 찾음 | `resume` 해제 | 카드 SM C2 |

네 갈래는 표 한 줄에 담기지 않는 사정이 있다.

- **재신고 거절(D)** — `ALREADY_SUSPENDED`는 **정본 변경**의 결과다.\
  구 매트릭스의 ◎를 사용자 재확인으로 뒤집어 명시 거절로 확정했다(카드 SM CF9).
- **정지 후 승인 거절(E)** — 카드 사용 불가는 뭉뚱그리지 않고 **SM 응답 열 3코드**로 갈린다.\
  `CARD_SUSPENDED`(CF4)·`CARD_EXPIRED`(CF6)·`CARD_TERMINATED`(CF3)이며, 이는 구 단일 `DECLINED_CARD` 표기를 **대체**한 것이지 신설이 아니다(UC-01 §7 v0.6 · 색인 §5 K-1 코드 대장 v0.13 확정).
- **정지 중 매입 반영(F)** — 반직관이지만 정상이다.\
  매입은 외부에서 확정된 사실이라 정지가 막지 않는다(BR-35).
- **오신고 해제(G)** — 카드를 찾으면 `resume(requester)`로 해제한다.\
  주체는 소지자 또는 담당자로, 정지와 대칭이다(카드 SM C2).

## 5. 대체 시나리오

**운영자 대행 신고** — 고객이 전화로 신고하면 운영자(담당자)가 대행한다.\
같은 목표·같은 전이이며, **주체 기록만 다르다** — 감사가 그것을 구분한다(CDS1: "운영자가 정지된 카드를 만지고 있다는 신호").

## 6. 인가·감사 ★

주체 판정은 진입 1회다 — 고객(본인 카드) 또는 운영자(담당자·스코프).\
**두 주체의 스코프 판정이 다르다**: 고객 = 소유, 운영자 = 조직.

L7은 §4-A·B에서 선다 — 두 주체 모두 범위 밖이면 부재와 동일 응답이다.

감사는 정지·해제 각각에 **주체 유형·개인 식별**을 포함한다(AD-8).\
이것이 상태 머신 CDS1이 예고한 "감사 로그 설계"의 착지다.

## 7. 계약 (계약 블록)

아래는 정지·해제 두 조작과 `CardSuspended` 이벤트의 계약 블록이다.

#### `POST /me/cards/{cardId}/suspension` (고객) · `POST /ops/cards/{cardId}/suspension` (운영자)

| 항목 | 내용 |
|---|---|
| 주체 | 고객(본인) / 운영자 담당자(스코프 안) — 경로 분리로 주체 계약을 가른다 |
| 요청 | 사유 코드(분실/도난/기타 — [미정: 코드 체계]) |
| 응답(성공) | `SUSPENDED` + 효과 고지(신규 승인 차단 · **기존 매입은 계속** — BR-35를 사용자에게도 고지) |
| 오류 표 ★ | `NOT_FOUND`(부재·타인·스코프 밖 동일 — L7) · `TERMINATED`(§4-C) · `ALREADY_SUSPENDED`(§4-D — **확정** · CF9) |
| 멱등 | **비멱등 — 재신고는 명시 거절**(CF9. 거절이 멱등 경계 역할) |
| 예산 | 실시간 — 분실 신고는 지연이 곧 위험. 목표치 [미검증] |
| 감사 | 주체 유형·개인·카드·사유 (AD-8 — 경로: 성공 = 커밋 내 outbox · 거절 = 독립 커밋, AD-2 규칙) |

#### `DELETE /me/cards/{cardId}/suspension` (고객) · `DELETE /ops/cards/{cardId}/suspension` (운영자) — 해제

| 항목 | 내용 |
|---|---|
| 주체 | 고객(본인) / 운영자 담당자(스코프 안) — 정지와 대칭 (SM C2 확정) |
| 요청 | 해제 사유 코드([미정 — 정지와 같은 체계]) |
| 응답(성공) | `NORMAL` — 신규 승인 재개 고지 |
| 오류 표 ★ | `NOT_FOUND`(부재·타인·스코프 밖 동일 — L7) · `ALREADY_NORMAL`(§4-D와 대칭 — CF10) · `TERMINATED`(CF1) |
| 멱등 | **비멱등 — 재해제는 명시 거절**(`ALREADY_NORMAL` CF10. 거절이 멱등 경계 역할) |
| 예산 | 실시간 아님 (신고와 달리 지연이 위험이 아니다) |
| 감사 | 주체 유형·개인·카드·사유 (AD-8 — 경로: 성공 = 커밋 내 outbox · 거절 = 독립 커밋, AD-2 규칙) |

해제의 오류 코드 하나는 표기가 바뀐 내력이 있다.\
`ALREADY_NORMAL`은 정지 상태가 아닌 카드의 재해제를 명시 거절하며, 신고(CF9)·재해지(CF8)와 같은 판정이다(**CF10** — 2026-08-06 CDS3 통일).\
구 표기 `NOT_SUSPENDED`는 정본에 없던 코드라 CF10 정본 코드로 교체했다.

#### 이벤트 `CardSuspended` (기존 — card.md가 정본. 계약 확인 블록)

| 항목 | 내용 |
|---|---|
| payload | `cardId` — ★ **행위자 비포함 확정**(AD-7 ② 확장) |
| 구독 | — (구독자 정의는 card.md 정본 확인 필요 — Phase 4 계약 전수) |
| 멱등 키 | 상태 전이가 경계 — 재신고는 **명시 거절**(CF9 확정) |
| 스키마 버전 | ★ **`schemaVersion: 1`** (K-3 — 2026-08-06 계약 전수) |

payload가 행위자를 싣지 않는 것은 **주체 혼합 이벤트**이기 때문이다(AD-7 ② 확장).\
행위자는 이벤트가 아니라 감사가 나른다.
