# UC-07. 타행 이체로 입금받는다

- 작성일: 2026-08-05
- 상태: **검토대기 (계약 블록 완결)**
- 액터: **외부 입금원(시스템 주체 — 고객 대리)** — 목표의 주인은 계좌 소유 고객, 요청의 주체는 모의 외부 입금원 (UC-01의 대리 구도 선례)
- 권한 요건: 시스템 주체 — **경로 식별자 필수**(BR-54 ③ · AU-2). BR-54 예외 목록 **밖**(횡단 아님 — 단건 계좌 지목, UC-01 선례). 고객·운영자 단계 무관
- 트랜잭션 경계: **E3** (계좌 · 회수 대상 미수들 · 입금 수신 — 한 커밋)
- 관련 규칙: BR-02·07·08·14·20·28·29·34·40·41·45·54·57·58 · DepositReceipt INV-1·2·3 · Receivable INV-1·4·5 · 계좌 POST-1·RC-2·RC-4·RC-5 (참조만 — F-24)

> 이 문서를 다 읽으면 **타행 입금이 어떻게 정확히 한 번만 반영되어 오래된 미수부터 회수되고 남은 만큼만 잔액이 느는지, 그리고 재수신·충돌·부재 계좌가 어떻게 갈리는지**를 설명할 수 있어야 한다.

## 1. 목표

고객이 타행에서 보낸 이체가 **정확히 한 번만** 반영되어, 회수 가능한 미수를 오래된 것부터 갚고 **남은 만큼만** 계좌 잔액이 는다.

## 2. 사전·사후 조건

시작 조건은 둘이다.\
대상 계좌가 존재하고,\
`depositId`는 외부 입금원이 생성한다(DepositReceipt 키 출처 표 — 정정의 `reversalId`와 출처가 다르다).

끝 상태는 넷으로 갈린다.

- **성공** — 전부 한 커밋(E3)으로 끝난다.\
  ★ `(기관, depositId, 입금)` 수신 기록이 남고, 회수 대상 미수들의 `recoveredAmount`가 오르고, **잔여분만** `balance`가 늘고, 이동 행이 갱신되며(`netAmount`·`receivableDelta`), 미수가 전부 종결되면 `receivableBlockLifted`로 복귀한다.\
  원장 기표는 비동기다(R6 — `차) 예치금 / 대) 미수금·고객예금`).
- **재수신** — 무변화, 최초 결과 반환(DepositReceipt INV-1·INV-2).
- **커밋 실패** — 전부 롤백된다.\
  수신 기록도 남지 않으므로 재전송이 정상 처리된다 — 반영 후 기록 전 종료가 없다는 것이 E3의 존재 이유다.
- **부족분이라는 결말은 없다** — ★ 회수액 = `min(유입액, Σ 회수 가능 미수)` 이므로 유입보다 많이 회수되지 않고, 잔액은 줄지 않는다.\
  미수가 남은 채 끝나는 것이 정상 결과다(POST-1).\
  매입(BR-20)·입금 정정(BR-38)과 달리 이 경로는 채권을 만들지 않는다.

기관 축은 이 UC 전체를 관통한다.\
`depositId`는 외부 입금원이 채번하므로 유일성 스코프는 발신 기관이다(R-06).\
기관 = ACL이 인증한 발신 기관이며, 전문 본문 X-6 기관 코드와 일치 검증한다.

### 동작 구조

외부 입금원 전문이 어떤 저장소를 거쳐 E3 한 커밋으로 회수·입금·수신 기록을 끝내는지 보여준다.

```
[외부 입금원]
   │ DEPOSIT-ADV 전문  (depositId = 입금원이 채번)
   ▼
[입금원 경로 ACL]  (경로 식별자 · 발신 기관 인증 X-6)
   │
   ▼
[코어: 입금 UC]
   ├─멱등 조회──▶ [DepositReceipt] find(기관, depositId, 입금)
   ├─회수 대상 선정──▶ [미수들] FIFO(발생일, 미수ID) · frozen 제외
   ├─배분 recover──▶ [계좌] 잔여만 balance 증가 (POST-1 · RC-2)
   └─이동 행 갱신──▶ [AccountDailyMovement]  (귀속 영업일 BR-14)
   │  E3 — 계좌·미수들·수신 기록·감사를 한 커밋
   ▼
[감사 outbox] (AD-2 · 경로 귀속)
   ├─Deposited──▶ [원장] 차)예치금 대)미수금·고객예금 (3분해)
   ├─ReceivableRecovered──▶ (원장 아님 — 유입 이벤트가 회수 분개를 소유)
   └─DepositConflict──▶ [대사] M13  (같은 키·다른 지문일 때)
```

## 3. 주요 성공 시나리오

1. 입금 전문 수신 — 시스템 주체 + **경로 식별자** 부여, 도메인 언어로 번역 [BR-54 ③ · AU-2·3]
2. `find(기관, depositId, 입금)` — 기존 결과가 있으면 §4-A로. ★ **기관 = ACL이 인증한 발신 기관**(X-6 일치 검증 — 불일치 = `ARG_MISMATCH`) · **기관이 다르면 "없음"** [DepositReceipt INV-1·2 · **R-06** · BR-29·02]
3. `assertSameRequest(fingerprint)` — 지문이 다르면 §4-B로 [INV-3 · BR-02]
4. **회수 대상 선정** — 그 계좌의 미결 ∧ `frozen = false` 미수, 정렬 `(발생 영업일, 미수 식별자)` **전순서** [BR-34·28 · Receivable INV-5 · 미수 SM VF3]
5. `deposit(depositId, amount, recoverable)` — 회수액 = `min(유입, Σ outstanding)` → FIFO 배분 `recover()` → **잔여만** `balance` 증가 [BR-34 · POST-1 · 미수 SM V2·V3 · RC-2]
6. 이동 행 갱신 — 귀속 영업일(BR-14) 행에 `netAmount`·`receivableDelta -= 회수분` 더하기 [DC-006 · RC-4·RC-5] (피연산자 = **balance 변화량** — DC-006 §3. ~~정본 충돌~~은 정정 완료 `1dff628`)
7. 미수가 전부 종결되면 **계좌가 자기 `receivableBlockLifted`를 재평가** [계좌 INV-3 · BR-45 · 미수 SM V3]
8. `record(기관, depositId, 입금, …)` 수신 기록 — **같은 커밋** [E3 · INV-1 · **R-06**]
9. `Deposited` 발행 — `receivedAmount = recoveredAmount + creditedAmount` **3분해**가 예치금 차변 이중 계상을 막는다 [BR-29·08 · account.md §5 "이벤트 금액을 셋으로 나눈 이유"] · `ReceivableRecovered` 발행(**원장 아님** — 회수 분개는 유입 이벤트가 소유)

### 흐름도

X-10 판정 순서(① 인자 → ② 멱등 단락 → ③ 대상 존재 → ④ 상태)에 §4의 분기를 얹었다. 멱등 단락이 계좌 조회보다 앞서야 재수신이 최초 결과를 낸다.

```
[입금 전문]
   │
   ▼
⟨amount > 0?⟩ ──아니오──▶ [거절: ARG_MISMATCH] (§4-G · X-10 ①)
   │예
   ▼
⟨재수신(같은 기관·depositId)?⟩ ──아니오──▶ (계속)
   │예
   ▼
⟨요청 지문 동일?⟩ ──예──▶ [최초 결과 반환 · 무변화] (§4-A)
   │아니오
   ▼
[IDEMPOTENCY_CONFLICT · DepositConflict 발행 → M13] (§4-B)  ──▶ (끝)

(계속)
   ▼
⟨대상 계좌 존재?⟩ ──아니오──▶ [거절: ACCOUNT_NOT_FOUND · 사유 구분] (§4-H)
   │예
   ▼
[회수 대상 선정 — FIFO · frozen 제외]
   ▼
[배분 recover — min(유입, Σ미결)] ──배분 실패(VF1·VF4)──▶ [E3 전체 롤백] (§4-E)
   │
   ▼
[잔여만 balance 증가] ──▶ [수신 기록 · 이동 행] ──▶ [Deposited·
   ReceivableRecovered 발행] ──▶ (끝)
```

## 4. 예외 시나리오 ★

아래 표는 입금 경로의 열세 갈래와 그 종결을 정리한다.\
재수신·충돌·배분·부재가 각각 어떻게 갈리는지 보여주고, 응답 코드는 §7 계약·미수 SM의 정본과 같다.

| # | 트리거 | 응답 → 종결 | 근거 |
|---|---|---|---|
| A | ★ 같은 기관의 같은 `depositId` 재수신 | 무변화 — 최초 결과 반환 | DepositReceipt INV-1·2 · BR-29 |
| B | 같은 키 · **다른 요청 지문** | `IDEMPOTENCY_CONFLICT` + `DepositConflict` 발행 → M13 | INV-3 · BR-02·09 |
| C | 회수 가능액 ≥ 유입액 | 잔액 증가 0, 미수만 감소 — 정상 | BR-34 검증① · POST-1 |
| D | **보류 미수만 있는 계좌** | 보류분 선정 제외 → 미수 남은 채 잔액 증가(정상) | BR-28 · BR-34 검증⑤ · 미수 SM **VF3** |
| E | 배분 중 어느 미수가 이미 종결·초과 | `RECEIVABLE_CLOSED`/`RECOVER_EXCEEDS_OUTSTANDING` → E3 전체 롤백 | 미수 SM **VF1·VF4** · INV-1·4 |
| F | 회수액 ≠ 배분 합계 | 커밋 안 검사 실패 — 구조적으로 차단 | 계좌 **RC-2** · BR-34 |
| G | `amount ≤ 0` | `ARG_MISMATCH` — 거절 | `deposit()` 사전조건 |
| H | **존재하지 않는 계좌 지목** | `ACCOUNT_NOT_FOUND` — 사유 구분 거절 | **§9 UC7-3**(닫힘) · BR-36 계열 |
| I | 보관 기간 경과 후 재수신 | ★ 중복 반영 — 잔액 2배 | DepositReceipt **DR1** (보관 기간 미확정) |
| J | 입금과 매입의 동시 도착 | 순서 무관 — 교환적 · 새 미수는 다음 회수 대상 | account.md §8 · receivable §8 |
| K | 회수 대상 미수가 많음 | E3 락 보유 시간 증가 — 대상 수 상한 미확정 | **RV3** |
| L | 감사 적재 실패 | 성공 = 조작과 함께 롤백 / 거절 기록 실패 = M18 | AD-2 · R16 |
| M | 원장 기표 지연·유실 | 정상 — 내부 대사가 잡음 | BR-40·41 · BR-52 드레인 |

여러 갈래는 표 한 줄로는 부족하다.

- **재수신(A)** — 무변화로 최초 결과를 반환한다(전문 2회 배달이 정상 전제다).\
  ★ 기관이 다르면 재수신이 아니라 별건으로 처리한다(R-06).
- **다른 지문 충돌(B)** — 충돌을 거절하고 `DepositConflict`를 발행한다.\
  ★ M13은 대사 배치가 아니라 이 이벤트가 적재한다.
- **보류 미수만 있는 계좌(D)** — 보류분은 회수 대상 선정에서 제외된다.\
  미수가 남은 채 잔액이 느는 것은 오류가 아니다(미수 SM VF3).
- **배분 실패(E)** — 어느 미수가 이미 종결·초과면 거절하고 E3 전체를 롤백한다.\
  부분 배분이 남지 않는다(VF1·VF4 · INV-1·4).
- **합계 불일치(F)** — 회수액 ≠ 배분 합계면 커밋 안 검사가 실패한다.\
  ★ *대상 먼저 → 합 나중* 순서가 이것을 구조적으로 막는다(RC-2).
- **비양수 금액(G)** — `amount ≤ 0`은 거절이다.\
  `refund(0)`은 정상이지만 입금은 아니다 — 사전조건이 다르다(`deposit()` 사전조건).
- **부재 계좌(H)** — 존재하지 않거나 범위 밖 계좌를 지목한 입금은 `ACCOUNT_NOT_FOUND`로 사유를 구분해 거절한다(UC7-3 닫힘).\
  시스템 채널이라 C-2 채널 조항(사람 주체) 밖이고 사유 구분을 요구하는 정본(BR-15·36 같은 것)도 입금에 따로 있지 않지만, 입금원이 재전송 여부를 판단할 수 있어야 하므로 사유를 구분한다(BR-36 계열).
- **보관 기간 만료(I)** — ★ 멱등 레코드가 만료된 뒤 재수신되면 중복 반영되어 잔액이 2배가 된다(DR1 — 보관 기간 미확정).
- **원장 기표 지연·유실(M)** — 정상이다.\
  자금 이동과 기표는 분리돼 있고(BR-40), 내부 대사(M12·M14)가 잡는다(BR-41 · BR-52 드레인).

## 5. 대체 시나리오

대체 경로는 없다 — 입금의 정식 경로는 외부 입금원 전문 하나다.\
입금 취소는 범위 밖이고(BR-29 예외 — 모의 입금원은 취소 전문을 보내지 않는다),\
잘못 반영된 입금의 정정은 운영자 역분개(UC-02 · BR-38)로 액터·목표가 다른 유스케이스다 *(U-6 근거)*.

## 6. 인가·감사 ★

주체는 전문 수신 ACL 진입 시 **1회** 판정한다(AU-3·4) — 시스템 주체 + 경로 식별자.\
소유자 필터는 없다(AU-2).\
계좌를 단건으로 지목하므로 횡단 접근이 아니고, 따라서 BR-54 예외 목록 대상이 아니다(UC-01 §6과 같은 판정).

L7은 대상이 아니다 ✕ — 사람 주체 채널이 아니다(C-2 채널 조항).\
다만 §4-H의 거절 응답 형태는 미판정이었고(UC7-3), "✕"가 곧 "사유를 다 알려도 된다"는 뜻은 아니다.

감사는 경로에 따라 커밋이 다르다.\
성공은 E3 커밋 내 outbox(AD-2) — 주체(경로)·계좌·금액·회수분/증가분·결과.\
거절(§4-B·G·H)은 독립 커밋(AD-2)이다.\
조회가 아니므로 AD-4는 비적용이다.

★ 이 UC의 감사에는 **개인 행위자가 없다**.\
BR-57의 *"공용·시스템 계정의 행위도 개인 또는 정의된 경로 단위로 귀속"* 조항이 근거이며, 귀속 단위는 **경로 식별자**다.

| 오류 표 ★ | **X-10 판정 순서**: 경로 인가 `FORBIDDEN_LEVEL` → ① `ARG_MISMATCH` → ② `IDEMPOTENCY_CONFLICT`(→ M13) → ③ `ACCOUNT_NOT_FOUND` → ④ `RECEIVABLE_CLOSED`(VF1)/`RECOVER_EXCEEDS_OUTSTANDING`(VF4) → E3 롤백 · VF3은 오류 아님 — 상세는 아래 산문 |
| 멱등 | ★ **`(기관, depositId, 입금)`**(R-06 · DepositReceipt INV-1·2) · 시스템 채널 재수신 = 최초 결과 재반환(K-1) · 만료 후 재수신 = 중복 반영(DR1 · §4-I) — 상세는 아래 산문 |
| 예산 | 동기 전문이나 외부 응답 SLA 정본 없음 · 내부 deadline 전파(T-11~T-13) 적용 · 값 ⚠️ **[미확정 — 입금원 SLA 가정 필요]** — 상세는 아래 산문 |
| 감사 | AD-2 경로: 성공 = E3 커밋 내 outbox / 거절(§4-B·G·H) = 독립 커밋(실패는 M18) · 항목 = AD-8 · 스코프 = 대상 소유 축(A-6·B-5) — 상세는 아래 산문 |

전문 계약의 여러 칸은 판단 근거가 길어 표 밖에서 풀어 읽는다.

**요청** — `depositId`는 외부 입금원이 자기 체계로 채번하므로 유일성 스코프는 발신 기관이다(DepositReceipt 키 출처 표 · INV-1 · R-06) — 정정의 `reversalId`와 출처가 다르다.\
귀속 영업일 판정 입력은 우리 수신 시각이다(BR-14 — 2026-08-06 R-02 명확화: 별도 필드가 없다).\
외부가 만든 전송일시는 발신측 시계에 의존해 신뢰할 수 없으므로 판정에 쓰지 않는다 — 참고값이다.\
1회 입금 상한은 미확정이다(BR-29 · UC7-4).

**응답** — 외부 응답은 `receivedAmount`(수납 총액)과 귀속 영업일 둘뿐이다(2026-08-06 R-10 — 사용자 판정).\
**3분해**(`receivedAmount = recoveredAmount + creditedAmount`)와 잔여 미수 상태 Y/N은 내부 반환값이며 이 계약의 외부 응답 표면이 아니다.\
그것은 원장 번역 입력(`Deposited` payload · account.md §5 — 합치면 예치금 차변이 두 번 잡힌다)과 내부 판정이 소비하고, 등식 자체는 그대로 유지된다.\
강등 근거는 존재·신용 비노출 원칙의 통일이다 — 회수분·잔액 증가분·잔여 미수는 그 계좌 소유자의 신용 상태이고, 입금원이 재전송 판단에 필요한 것은 오류 사유와 수납 총액이며 그 둘은 남는다(`REVERSAL-RES`가 원승인 존재조차 구별하지 않는 것과 같은 갈래).\
재수신은 최초 결과를 그대로 재반환한다(K-1 시스템 채널 · DepositReceipt INV-1·2 — §4-A).\
L7은 비적용이다 — 사람 주체 채널이 아니다(C-2 채널 경계).

**오류 표(X-10 판정 순서)** — 판정 순서는 X-10이 정본이다(시스템 채널 — `interfaces/README.md`: ① 인자 형식 → ② 멱등 단락 → ③ 대상 존재 → ④ 상태).\
이 순서가 구 *"K-1 순서(단계 → 스코프·존재 → 상태·인자)"* 문면을 대체한다 — 멱등 단락이 계좌 조회보다 앞서야 재수신이 최초 결과를 반환한다.\
**채널** — 경로 인가 `FORBIDDEN_LEVEL`(경로 식별자 부재·미인가 — 전문 처리 이전의 ACL 판정이라 ① 앞에 선다).\
**① 인자 형식** — `ARG_MISMATCH`(`amount ≤ 0` — `deposit()` 사전조건, §4-G).\
**② 멱등 단락** — `IDEMPOTENCY_CONFLICT`(같은 키 · 다른 지문 — BR-02 · INV-3. `DepositConflict` 발행 → M13, §4-B. `DepositReceipt`에는 상태 머신이 없어 응답 열 정본이 없으므로 UC-01 §7과 같은 코드를 쓴다 — K-1 ⑶ 신설 최소화).\
**③ 대상 존재** — `ACCOUNT_NOT_FOUND`(대상 계좌 부재·범위 밖 — 2026-08-06 U-2 확정 **A-4**(UC7-3, 사용자 판정): ★ 사유를 구분한다. 기관 채널이라 C-2(부재·타인 동일 형태)의 적용 대상이 아니고 BR-36 계열의 사유 구분을 따른다 — 입금원이 재전송 여부를 판단할 수 있어야 한다. L7 비적용 · 신설 코드 대장 등재 = 색인 §5 K-1. ★ ①·②가 앞서므로 열거 오라클이 답하는 입력 범위가 좁아진다).\
**④ 상태** — 배분 단계는 미수 SM 응답 열 그대로다: `RECEIVABLE_CLOSED`(**VF1**) · `RECOVER_EXCEEDS_OUTSTANDING`(**VF4**) → E3 전체 롤백(§4-E — 부분 배분이 남지 않는다).\
★ 보류 미수(**VF3**)는 오류가 아니다 — 회수 대상 선정에서 제외된다(§4-D).\
거절도 전부 감사에 남는다(BR-57).

**멱등** — 멱등 키는 **`(기관, depositId, 입금)`**이다.\
`depositId`는 외부 입금원이 자기 체계로 채번하므로 유일성 스코프는 발신 기관이다(2026-08-06 R-06 · DepositReceipt **INV-1**).\
기관 = ACL이 인증한 발신 기관이며, 전문 본문 X-6 기관 코드와 일치 검증한다(불일치 = `ARG_MISMATCH`) · **INV-2**(결과 불변).\
시스템 채널 재수신은 최초 결과를 재반환한다(K-1).\
수신 기록은 자금 반영과 **같은 커밋**이다(E3 — 갈리면 반영 후 기록 전 종료가 재반영을 만든다).\
⚠️ 보관 기간 경과 후 재수신은 중복 반영이다(**DR1** — 보관 기간 **[미확정]**, §4-I).

**예산** — 동기 전문이지만 외부 응답 SLA의 정본이 없다(BR-01 3초는 승인 경로 값이다).\
내부 deadline 전파(T-11~T-13)는 적용되고 T-14가 E3에도 예산을 요구하나, T-14가 지목한 상한 출처(*배치 슬롯 예산*)는 *"전문 응답이 아니다"* 를 전제한다 — 이 경로는 전문 응답이라 그 전제가 성립하지 않는다.\
★ 2026-08-06 U-2 확정 — **A-5**: T-14의 배치 슬롯 예산 전제는 이 경로에 적용하지 않는다(명시).\
상한은 입금원 타임아웃 SLA 가정을 세운 뒤 확정한다 — 값 ⚠️ **[미확정 — 입금원 SLA 가정 필요]**(미확정 수치 표 소관).

**감사** — AD-2 경로로, 성공은 E3 커밋 내 outbox, 거절(§4-B·G·H)은 독립 커밋이다(적재 실패는 **M18** — §4-L · R16).\
항목은 AD-8이다(`sourceRef` · **주체 = 경로 식별자** — ★ 개인 행위자가 없다(BR-57 공용·시스템 계정의 경로 단위 귀속, §6) · 시각 · 대상 `accountId` · ★ **스코프 = 대상 계좌의 소유 축(`ownerId`)** · 종류 · 결과) + 금액 · 회수분/증가분.\
조회가 아니므로 AD-4는 비적용이다.\
★ 2026-08-06 U-2 확정 — **A-6·B-5**: 시스템 채널은 판정에 쓰인 스코프 값이 없으므로(AU-2 소유자 필터 없음) AD-8 스코프 칸에 대상의 소유 축을 기록한다(IS-2 형태 — K-4 보정. 재현 가능성 기준).

#### 이벤트 `Deposited` (기존 — account.md §6이 정본. 계약 블록)

| 항목 | 내용 |
|---|---|
| payload | `accountId` · ★ **3분해 유지**(`receivedAmount`·`recoveredAmount`·`creditedAmount`) · 입금 식별자 · 영업일 · **행위자 비포함**(자금 이벤트 — AD-7 ②) · `ownerId` 없음(U-2 A-2·3) — 상세는 아래 산문 |
| 구독 | **C5 원장**(R6 ACL 번역 — `차) 예치금 / 대) 미수금·고객예금`) · 감사 수집은 구독이 아니라 감사 전용 outbox(AD-2) |
| 멱등 키 | 수신측 = 전표 **INV-8**(같은 `sourceEvent`로 두 번 기표하지 않는다) — outbox at-least-once 전제 |
| 스키마 버전 | **`schemaVersion: 1`** (K-3) · 의미 필드 추가 = **새 이벤트 타입**(S-6a) |

`Deposited` payload는 3분해를 유지한다 — 합치면 원장에서 예치금 차변이 두 번 잡힌다(account.md §5).\
축은 기존 파티션 축 `accountId`를 유지하되 `ownerId`는 없다(2026-08-06 U-2 확정 — A-2·3: 이벤트 payload 전면 비포함).\
`Deposited`는 **원장 번역 입력**이라 IS-5의 원장 언어 순수성이 그대로 서고, IS-1 6종은 저장 모델 대상이었다.

#### 이벤트 `ReceivableRecovered` (기존 — receivable.md §6이 정본. 계약 블록)

| 항목 | 내용 |
|---|---|
| payload | 미수ID · `accountId` · 회수액 · 잔여(receivable.md §6) · **행위자 비포함 확정**(색인 §3 · AD-7 ②) · `ownerId` 없음(U-2 A-2·3) |
| 구독 | ⚠️ **원장 아님** — 회수 분개는 유입 이벤트(`Deposited`)가 소유(receivable.md §6 · journal-entry ACL 소유 규칙) · 현재 구독자 없음 |
| 멱등 키 | 수신측 없음 — **E3 커밋 원자성**이 담보 · 구독자가 생기면 `sourceEventId` 유일 제약(AD-3 형태) |
| 스키마 버전 | **`schemaVersion: 1`** (K-3) · 의미 필드 추가 = **새 이벤트 타입**(S-6a) |

#### 이벤트 `DepositConflict` (기존 — deposit-receipt.md §6이 정본. 계약 블록 · §4-B)

| 항목 | 내용 |
|---|---|
| payload | ★ **`institution`**(발신 기관 — R-06. M13 `subject` 축) · `key`(= `depositId`) · `operation`(= 입금) · **두 지문**(deposit-receipt.md §6) · **행위자 비포함**(시스템 적재 — 색인 §3 · AD-7 ②) · `ownerId` 없음(U-2 A-2·3) — 상세는 아래 산문 |
| 구독 | **C6 대사** — 적재 유형 **M13**(BR-09) · ★ 적재 주체가 대사 배치가 아니라 이 이벤트다(discrepancy.md §3 M13 행) |
| 멱등 키 | 수신측 = 불일치 **INV-2** 유일성 `(type, scope, subject)` — M13의 `subject` = ★ **`(기관, key, operation)`**(R-06) — 상세는 아래 산문 |
| 스키마 버전 | **`schemaVersion: 1`** (K-3) · 의미 필드 추가 = **새 이벤트 타입**(S-6a) |

`DepositConflict`는 `institution`(발신 기관)을 payload에 싣는다 — R-06으로 M13의 `subject` 축이 기관을 포함하므로 payload가 그것을 날라야 한다.\
축은 기존 payload 축을 유지하되 `ownerId`는 없다(2026-08-06 U-2 확정 — A-2·3 전면 비포함) — `DepositReceipt`가 그 컬럼을 드는 것은 **저장 모델** 쪽이다(IS-1).\
M13의 `subject`는 **`(기관, key, operation)`**이다(R-06 — 키가 기관 스코프이므로 충돌도 기관 스코프다).\
기관을 빼면 다른 입금원의 같은 `depositId` 충돌이 한 건으로 뭉쳐 한쪽이 조용히 사라진다.\
재전달은 `recordOrTouch`가 흡수한다(같은 영업일이면 `detectionCount`도 오르지 않는다 — DC3).
