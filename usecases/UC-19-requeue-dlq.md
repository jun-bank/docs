# UC-19. DLQ 이벤트를 재투입한다

- 작성일: 2026-08-05
- 상태: **검토대기 (계약 블록 완결)**
- 액터: **운영자 담당자** — ★ 재투입은 **사람의 조작**이다(ADR-014 O-14: 자동 재투입은 무한 루프가 된다)
- 권한 요건: **담당자** 단계 (BR-55 배정 표 — *DLQ(M17) 재투입 = 담당자, 정체 해소 · 기표는 멱등이 막는다*) · 스코프 = ★ **전사 스코프만**(BR-55 특칙) · **2인 승인 대상 아님**(BR-56 목록 5개 밖)
- 트랜잭션 경계: **없음 — 자금 무이동**. outbox 레코드의 상태 전이(`DLQ_UNRESOLVED` → 재전달 → `RESOLVED_BY_REPLAY`)이고, 반영 커밋은 **각 수신측**이 자기 멱등으로 소유한다
- 관련 규칙: BR-09·52·53·54·55·57·58 · ADR-014 **O-10~O-16 · B-6~B-10** · M16·M17 · JournalEntry INV-8·INV-9 · ADR-017 AD-2·3·8 (참조만 — F-24)

## 1. 목표 (한 문장)

재시도 상한을 넘어 **격리(DLQ)된 outbox 이벤트**를 원인 조치 후 다시 전달해 **정체를 해소**하고, 그 영업일의 드레인·대사가 다시 성립하게 한다.

## 2. 사전 조건 / 사후 조건

- 사전: 대상 outbox 레코드가 `DLQ_UNRESOLVED`이고 **M17이 적재**돼 있다. ★ **원인이 조사·조치되었다** — 사람이 원인을 봐야 한다는 것이 자동 재투입을 기각한 이유다. 요청자 = **전사 담당자**.
- 사전(★ 유실이 아니다): outbox 레코드는 **물리적으로 남아 있다**(O-12 — 물리 이동은 잔량 0으로 드레인 완료를 위조한다). 재투입할 대상이 존재한다는 것 자체가 이 UC의 성립 근거다.
- 사후(성공): 재전달 성공 → 레코드 **`RESOLVED_BY_REPLAY`**(O-15) · 수신측 멱등이 **이중 반영을 막는다** · 재투입 주체가 감사에 남는다.
- 사후(성공, 파급) ★ 그 영업일 `DLQ_UNRESOLVED`가 **0이 되면** 드레인 완료 판정이 성립하고(O-16 · BR-52 ②), **그 영업일 대사가 재실행**되며 성공 시 **M16이 닫힌다**(BR-42).
- 사후(재실패): 다시 `DLQ_UNRESOLVED` · M17 유지(같은 영업일이면 `detectionCount`는 오르지 않는다 — BR-48).
- 사후(재투입으로 못 고치는 경우): 수신 계약 자체가 어긋난 것이면 재전달은 영구 실패다 — **정정으로 닫는다**(`RESOLVED_BY_CORRECTION` — §5).

## 3. 주요 성공 시나리오

1. **M17 통지**(1건이라도 통지 — BR-53 ②) → 담당자가 목록을 연다. `subject` = **(영업일, 계좌ID, 이벤트 타입, outbox 순번)**, 계좌ID 없는 이벤트는 **"파티션 0"** [ADR-014 O-13]
2. 원인 조사·조치(수신측 스키마 등) — **이 UC 밖**(조치 대상 컨텍스트의 문제다)
3. 담당자가 대상 레코드로 **재투입 요청** — 단계·전사 스코프 판정 [BR-55 · O-14]
4. 릴레이가 그 레코드를 다시 전달 — **파티션 소유**(O-7)·**순번 순서**(O-8) 규칙은 그대로, **fencing token** 동반 [B-6·B-7]
5. 수신측 멱등 판정 — 원장 `sourceEvent`(**INV-8**) / 정정 지시 `instructionId`(**INV-9**) / 정산 `sourceEventId` / C3 `markSettled` 무연산 / C6 `sourceEventId` [ADR-014 §2.4 · AD-3]
6. 레코드 **`RESOLVED_BY_REPLAY`** 표시 [O-15]
7. 그 영업일 `DLQ_UNRESOLVED` = 0 → 드레인 완료 → 대사 재실행 → **M16 닫힘** [O-16 · BR-52 · BR-42]
8. 감사 — 재투입 주체·대상 레코드·결과 (AD-2·AD-8)

## 5. 대체 시나리오

- ★ **정정으로 해소한다**(`RESOLVED_BY_CORRECTION` — O-15). 수신 계약 자체가 어긋나 재전달이 영구 실패하는 경우, 목표(정체 해소)는 같지만 경로가 다르다 — 수신측을 고치거나(스키마 진화 — ADR-015) 이미 어긋난 기록을 정정한다(원장이면 **UC-16 역분개**). ★ 이 경우 **레코드는 여전히 남고** 상태만 `RESOLVED_BY_CORRECTION`이 된다.

## 6. 인가·감사 ★

- 주체 판정 순서: **① 단계(담당자) + 전사 스코프 — 요청자 자기 속성** → **② 레코드 존재** → **③ 상태**(`DLQ_UNRESOLVED`인가 — §4-E).
- L7: ★ **존재 비노출의 대상이 아니다** — outbox 레코드는 전사 조작의 대상이고 소유 축이 성립하지 않는다(IS-2의 "축이 없는 것"과 같은 성격). 거절 시도는 기록한다(독립 커밋 — AD-2). ⚠️ **단 목록 응답 본문에는 계좌·고객 식별자가 실릴 수 있다** — 노출 범위는 §9 UC19-3.
- 감사: 재투입 = 커밋 내 outbox(AD-2 · R13) / 거절 = 독립 커밋 / 목록 조회 = 비동기(AD-4). 항목 = AD-8(주체·시각·대상 레코드·스코프·종류·결과). **2인 승인 조작이 아니므로 사유·승인자 칸은 비운다**(BR-56 목록 밖 — 과잉 배정 금지). ⚠️ 감사 outbox 자신이 DLQ에 갇히면 그 사실은 M17로 잡히고, **감사 적재 실패(비-outbox 경로)는 M18**로 갈린다(AD-4 · R16).

## 7. 계약 (계약 블록)

> ★ **2인 승인 계약이 아니다** — BR-56 목록 5개 밖이므로 승인 경로를 타지 않고 **감사의 사유·승인자 칸도 비운다**(과잉 배정 금지 — §6). *기표는 멱등이 막는다*(BR-55 배정 표)가 담당자 단독의 근거다.
> ★ **L7 ✕** — outbox 레코드는 전사 조작의 대상이고 **소유 축이 성립하지 않는다**(§6 · IS-2의 *"축이 없는 것"*). `NOT_FOUND`는 **부재만** 뜻한다(§4-L). ⚠️ **단 응답 본문에는 계좌·고객 식별자가 실릴 수 있다** — ★ **확정(D-UC19): 메타데이터만 노출하고, `partition` = 계좌ID라는 사실을 계약에 명시한다**(아래).
> ★ **이 UC의 안전은 발신이 아니라 수신측 멱등이 준다**(§4-B) — 재투입 API는 **비멱등**이어도 된다.
> 오류 코드 3계층 = K-1 ⑴ 공통 4종 / ⑵ **outbox 레코드에는 상태 머신 문서가 없다** — 상태값 정본은 ADR-014 O-12·O-15(`DLQ_UNRESOLVED`·`DELIVERED`·`RESOLVED_BY_REPLAY`·`RESOLVED_BY_CORRECTION`) / ⑶ ★ **이 계약이 쓰는 고유 코드 2종은 신설 코드 대장**(색인 §5 K-1)에 등재돼 있다 — **`ALREADY_DELIVERED`·`ALREADY_RESOLVED`**(종료 상태 재투입의 명시 거절. K-1 CDS3 유도로 **이 UC에서 신설해 같은 커밋으로 대장에 얹은 것**이다 — *"고유 신설 없음"* 은 잘못된 회계였다. 2026-08-06 리뷰 **F-09**). 대장 밖 코드는 만들지 않는다.

#### `GET /ops/dlq?businessDate=&partition=&type=&cursor=&size=` — DLQ 목록 (= M17 대상)

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **조회** 단계 이상 · ★ **전사 스코프**(BR-55 특칙 — 계좌ID가 실린 이벤트라도 조직 축으로 판정하지 않는다, §4-I) |
| 요청 | 필터 = `businessDate` · `partition`(★ 계좌ID 없는 이벤트는 **"파티션 0"** — O-13) · `type`(이벤트 타입) · 상태 · 커서 · `size`(상한 **[미정]** — 강제) |
| 응답(성공) | 레코드 목록 — `outboxRecordId` · `businessDate` · `partition` · 이벤트 타입 · **outbox 순번**(O-8) · 상태 · 재시도 횟수 · 최종 실패 사유 · 최초/최종 시도 시각 · 다음 커서. ★ **`subject` 4요소**(영업일, 계좌ID, 이벤트 타입, 순번)가 M17의 축과 일치해야 조사가 이어진다(§3-1) · ★ **payload 본문은 싣지 않는다 — 메타데이터만**(확정 **D-UC19** · 아래) |
| 오류 표 ★ | ① `FORBIDDEN_LEVEL` — 단계 미달 **및 전사 스코프 미보유**(§4-I. 자기 속성 · L7 축이 없어 코드를 가르지 않는다 — ★ 확정 **P-6**: `FORBIDDEN_SCOPE` 신설 없음, **UC-14·15·18과 통일**) → ② 목록이므로 대상 판정 없음 → ③ `INVALID_CURSOR`(만료 커서 — 재발급) · `ARG_MISMATCH`(필터 형식 · `size` 상한 초과는 **상한 강제**) |
| 멱등 | 조회 — 자연 멱등 (커서 = offset 아님) |
| 예산 | 실시간 아님 — 목표치 **[미검증]** |
| 감사 | ★ **조회도 남는다**(BR-57) · **비동기 적재**(AD-4) · 적재 실패는 조회를 막지 않고 **M18**(R16) · AD-8 + **조회 범위(필터)** · ★ **스코프 = `전사`**(K-4) · 사유·승인자 칸은 비운다 |

> ★ **확정 (D-UC19) — DLQ 목록은 메타데이터만 노출한다. payload 본문은 싣지 않는다.** (§9 UC19-3 닫힘)
> 전사 담당자는 **전 계좌의 레코드를 보게 된다** — BR-58의 축 판정이 성립하지 않는 표면이라 **계약이 유일한 통제**다. 노출 = 위 응답 필드 + 실패 사유까지이며, **재투입 결정에 본문이 필요 없다**(원인 조사는 *"이 UC 밖"* — §3-2). 메타+식별자·전체 payload는 채택하지 않는다.
> ★ **명시 (D-UC19의 절반)**: 메타만이어도 **`partition`이 곧 계좌ID**라 **축 자체는 이미 노출된다** — 이 사실을 계약에 못박아야 검증이 *"안 새는가"* 를 물을 수 있다(BR-58 전수 시험의 대상 밖임을 숨기지 않는다).
> ⚠️ 본문이 필요해지면 **별도 표면 신설 = 같은 커밋으로 색인 등재**(C-6) — 이 패스는 신설하지 않는다.

| 오류 표 ★ | **K-1 판정 순서** ① `FORBIDDEN_LEVEL`(단계 미달 **및 전사 스코프 미보유** — §4-I · P-6) → ② `NOT_FOUND` — ★ **레코드 부재만**(순번 오기 · §4-L. L7 축 없음) → ③ 상태: ★ **`ALREADY_DELIVERED` · `ALREADY_RESOLVED`**(`RESOLVED_BY_REPLAY`·`RESOLVED_BY_CORRECTION`) — **명시 거절이지 무연산이 아니다**(K-1 CDS3 일반화: *사람 채널의 상태 전이 재요청은 전부 명시 거절 — 무음 무시는 상태 오인을 만든다*). ★ **확정 — K-1 유도로 UC19-4가 닫혔고, 두 코드 모두 신설 코드 대장에 등재됐다** |
| 멱등 | ★ **발신은 비멱등이고 그래도 안전하다** — 같은 레코드를 두 번 재투입해도 **수신측 멱등이 이중 반영을 막는다**(§4-B): 원장 `sourceEvent`(**INV-8**) · 정정 지시 `instructionId`(**INV-9**) · 정산 `sourceEventId` · C3 `markSettled` 무연산 · C6 `sourceEventId`. ★ **멱등은 중복만 막고 순서는 막지 않는다**(§4-D · §9 UC19-2) |
| 예산 | 실시간 아님 — 접수만 동기. 백오프·상한(**1s→2s→4s→8s ±30% · 5회** — O-10·O-11 확정 수치)은 릴레이 소관 |
| 감사 | 성공 = **커밋 내 outbox**(AD-2 · R13) — 주체(재투입 담당자) · 시각 · 대상(`outboxRecordId` + `subject` 4요소) · ★ **스코프 = `전사`**(K-4) · 결과. **거절 = 독립 커밋**(AD-2) · **사유·승인자 칸은 비운다**. ⚠️ 감사 outbox 자신이 갇히면 **M17**, 비-outbox 감사 적재 실패는 **M18**로 갈린다(§6 · AD-4 · R16) |

> ★ **확정 (D-UC19) — 재투입 단위 = 레코드 1건.** (§9 UC19-1 닫힘)
> 위 계약이 가정한 형태 그대로다 — `POST …/{outboxRecordId}/replay`는 **색인 등재된 표면**이고 **부분 실패가 없다**. `(영업일, 파티션)` 일괄은 채택하지 않는다: **순번 오름차순 보장(O-8)과 부분 실패 처리**를 새로 정해야 하고 **새 엔드포인트라 색인 등재 대상**(C-6)이 된다.
> ⚠️ **남는 부담**: 드레인 완료 판정이 **`DLQ_UNRESOLVED` = 0**(O-16)이라, 1건 단위로는 남은 1건이 그 영업일 대사를 계속 막는다(UC-18 `DRAIN_INCOMPLETE`). 일괄 표면의 실질 수요는 여기서 나오며, 필요해지면 **신설 + 같은 커밋 색인 등재**로 다룬다.

#### (수신) 각 컨텍스트의 멱등 키 — ★ **이 UC의 안전을 소유하는 곳**(계약 확인 블록)

| 수신 | 멱등 키 | 재수신 동작 | 정본 |
|---|---|---|---|
| **C5 원장** (정상 기표) | `sourceEvent` 유일 | 아무 일도 하지 않고 **기존 전표 반환** | JournalEntry **INV-8** · `post()` |
| **C5 원장** (R15 정정 지시) | **`instructionId`** 유일 | **무연산** — 이중 역분개 차단(§4-G) | JournalEntry **INV-9** · `reverse()` |
| **C4 정산** | `sourceEventId` | 무연산 — ★ R15 재개 지시는 **지시 ID**(settlement `resumeByOperator`) | ADR-014 §2.4 · settlement.md §4 |
| **C3 결제** | `markSettled` **사전조건 무연산** | 이미 같은 영업일로 정산완료면 아무것도 안 한다 | authorization.md |
| **C6 대사** | `sourceEventId` | 무연산 | ADR-014 §2.4 |

> ★ **at-least-once 위에서 비멱등 수신측은 재전달이 곧 영구 실패**다(AD-3 형태). 위 표가 비면 이 UC 자체가 성립하지 않는다.
> ★ **fencing token**(B-6~B-10)은 멱등과 다른 층이다 — 좀비 인스턴스의 쓰기를 **저장소와 수신측 양쪽이 거부**하고, 거부 사실이 적재된다(§4-F).

#### 불일치 M17의 **조사·처리**(`investigate`·`resolve`) — ★ **UC-17 소관**(U-7)

★ **재투입 성공이 M17을 닫지 않는다**(§4-K) — M17은 대사가 재발견하지 않으면 갱신되지 않고, 닫는 주체는 **운영자의 `resolve`**이며 `resolution` 없이는 닫히지 않는다(Discrepancy INV-3 · SM D3).
