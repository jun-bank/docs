# UC-12. 조사 대상을 보류/해제한다

- 작성일: 2026-08-05
- 상태: **검토대기 (계약 블록 완결)**
- 액터: **운영자 담당자** (BR-54 ② 운영자 주체)
- 권한 요건: **담당자** 단계 (BR-55 배정 표 — 승인 보류/해제 · 미수 보류/해제 2행) · 스코프 = 대상의 계좌 개설 조직 (IS-4). **BR-56 대상 아님** — 가역이고 자금 간접이다
- 트랜잭션 경계: **없음 — 단일 애그리게이트 플래그 전이** (조작 대장에서 `freeze`·`unfreeze` 4건 모두 경계 `—`. 자금 무이동)
- 관련 규칙: BR-28·34·50·54·55·57·58 · 승인 SM T15·F9·F17 · 미수 SM V6·VF3·VF7 · `Receivable` INV-5 · `Authorization`·`Receivable` 조작 사전조건 (참조만 — F-24)

> 이 문서를 다 읽으면 **조사 중 자동 처리를 멈추는 보류가 승인과 미수 두 대상으로 어떻게 갈리는지, 보류가 무엇을 막고 무엇을 막지 않는지, 그리고 해제가 왜 기한을 연장하지 않아 즉시 만료로 이어질 수 있는지**를 설명할 수 있어야 한다.

## 1. 목표

운영자가 조사가 필요한 **승인 또는 미수**를 자동 처리(만료·매입 반영·회수)에서 빼 두었다가, 조사가 끝나면 되돌린다.

> **왜 한 유스케이스인가 (U-1)**: 목표는 *"조사 동안 자동 처리를 멈춘다"* 하나이고, 대상이 둘(승인·미수)로 갈린 것은 BR-28이 **보류 대상을 둘로 나눈 결과**다. 다만 그 둘이 운영 화면에서 섞이면 운영자가 잘못된 쪽을 푼다 — 미수 SM **RCS1**이 열어 둔 의문이며 §9에 인용한다.

## 2. 사전·사후 조건

시작 조건은 조작에 따라 갈린다.

- **승인 보류** — 대상 승인이 **종료 상태가 아니다**(`Authorization.freeze` 사전조건 · F9).\
  `REQUESTED`는 트랜잭션 안에만 있어 운영자가 손댈 수 없다(매트릭스 `-`).
- **미수 보류** — 대상 미수가 **미결(`OPEN`)** 이다(`Receivable.freeze` 사전조건 · VF7).
- **해제 공통** — 대상이 **이미 보류 중**이다(`unfreeze` 사전조건 `frozen = true`).

끝 상태는 셋으로 갈린다.

- **보류 성공** — `frozen = true`이며 **상태는 바뀌지 않는다**(T15 · V6 — 보류는 직교 플래그).\
  효과는 §3의 세 갈래(만료 제외·매입 격리·회수 제외)이며, 행위자가 감사에 남는다(BR-57).
- **해제 성공** — `frozen = false`다.\
  ★ **기한은 연장되지 않았다** — 해제 시점에 홀딩 기한이 이미 지났다면 **다음 만료 배치에서 즉시 만료**된다(BR-28).\
  보류 중 격리된 매입 레코드는 자동 반영되지 않는다 — **UC-14**(2인 승인)를 거친다.
- **거절** — 플래그 무변화 + 거절 시도 기록(독립 커밋 — AD-2).

### 동작 구조

운영자 담당자가 승인 또는 미수 애그리게이트의 `frozen` 플래그만 토글한다(자금 무이동) — 대상이 둘로 갈린다.

```
운영자 담당자
   │ 보류/해제 요청 (담당자 단계 · 계좌 개설 조직 스코프)
   ▼
[운영 API]  ── 단일 애그리게이트 플래그 전이 (자금 무이동) ──
   ├─▶ [승인 freeze/unfreeze] frozen 토글
   │        ├ 만료 배치 제외 · 매입 도착 시 격리(F17)
   │        └ 정산은 안 막음
   │        └─▶ 이벤트 [Frozen · Unfrozen]
   ├─▶ [미수 freeze/unfreeze] frozen 토글
   │        └ 회수 대상 제외(INV-5) · writeOff는 안 막음
   │        └─▶ 이벤트 [ReceivableFrozen · ReceivableUnfrozen]
   └─▶ 이벤트 ─▶ 운영(C8) · 감사 outbox(AD-2, 행위자 포함)
```

## 3. 주요 성공 시나리오

성공 경로는 일곱 단계이며, 승인 보류(②)와 미수 보류(③)가 각각 무엇을 막고 막지 않는지가 이 UC의 축이다.

1. 조사 필요 인지 — 대상 선택(승인 / 미수). 주체 판정: 담당자 단계 · 계좌 개설 조직 스코프 [BR-54·55 · IS-4]
2. **승인 보류** `Authorization.freeze(operator)` — `frozen = true`, 상태 불변 [승인 SM **T15**]
   - 효과 ①: 만료 배치가 이 건을 건너뛴다 — `expire`의 조건이 `frozen = false`다 [T7 · BR-28]
   - 효과 ②: 매입 레코드가 도착하면 **반영하지 않고 격리**된다 [**F17** · BR-50]. ★ 이 격리는 **불일치를 만들지 않고 M1(미매입)으로도 잡히지 않는다** — 의도된 지연이다
   - 효과 ③(비효과): **정산은 막지 않는다** — BR-28의 제외 목록에 정산이 없다 [`markSettled` 열 · T15]
3. **미수 보류** `Receivable.freeze(operator)` — `frozen = true`, 상태 불변 [미수 SM **V6**]
   - 효과: 회수 **대상 선정에서 빠진다**(`recoverable` 목록에 안 들어간다) [`Receivable` **INV-5** · BR-34 예외 ① · VF3]
   - 비효과: `writeOff`(환불에 의한 소멸)는 **막지 않는다** — 우리 조사와 무관한 외부 사실이다 [V4·V5]
4. 조사 수행 (불일치 건이면 **UC-17**과 짝을 이룬다 — 다만 보류 격리는 불일치가 아니다)
5. **해제** `unfreeze(operator)` — 승인은 **종료 상태에서도 허용**(T15 · F9 주석), 미수는 `CLOSED`에서도 허용(V6 · 매트릭스 `CLOSED` 행)
6. 해제 후 자동 처리 복귀 — ★ **만료 기한이 지났으면 다음 배치에서 즉시 만료**(BR-28) · 회수 대상 복귀(BR-34) · **격리 매입은 자동 복귀하지 않는다**(→ UC-14)
7. 보류·해제 각각이 행위자와 함께 감사에 남는다 [BR-57 · AD-8]

### 흐름도

대상(승인/미수)과 조작(보류/해제)에 따른 분기와 §4 거절을 함께 본다.

```
[시작] ─▶ ⟨단계·스코프 통과?⟩ ─아니오─▶ [FORBIDDEN_LEVEL / NOT_FOUND] ─▶ (끝)
             │예
             ▼
        ⟨조작 종류?⟩
        ├ 승인 보류 ─▶ ⟨종료 상태?⟩ ─예─▶ [AUTH_TERMINAL §4-A] ─▶ (끝)
        │                 │아니오
        │                 ▼
        │            [frozen=true] 만료 제외·매입 격리·정산 안 막음
        ├ 미수 보류 ─▶ ⟨CLOSED?⟩ ─예─▶ [RECEIVABLE_CLOSED §4-C] ─▶ (끝)
        │                 │아니오
        │                 ▼
        │            [frozen=true] 회수 대상 제외
        └ 해제(unfreeze) ─▶ ⟨frozen=true?⟩ ─아니오─▶ [ALREADY_UNFROZEN §4-D]
                                 │예
                                 ▼
                            [frozen=false]
                                 ▼
                            ⟨홀딩 기한 지남?⟩ ─예─▶ [다음 배치 즉시 만료 §4-K]
                                 │아니오
                                 ▼
                            [자동 처리 복귀 (격리 매입은 UC-14)]
                                 │
        (성공 공통) frozen 전이 ─▶ 이벤트 발행 + 감사(행위자) ─▶ (끝)
```

## 4. 예외 — 열네 갈래 ★

보류는 무엇을 막고 무엇을 막지 않는지가 예외의 핵심이라, "통과한다"가 오류가 아닌 갈래가 여럿이다.\
아래 표는 트리거와 종결의 대응이며, 거절 코드는 §7 계약의 정본(승인 SM F9 · 미수 SM VF7 응답 열)과 같다.

| # | 트리거 | 종결 | 근거 |
|---|---|---|---|
| A | **종료 상태 승인에 `freeze`** (`DECLINED`·`VOIDED`·`REFUNDED`·`SETTLED`) | 거절 `AUTH_TERMINAL` — 조사할 진행 처리 없음 | 승인 SM **F9** |
| B | `REQUESTED` 승인에 `freeze`·`unfreeze` | 경로 부재 — 트랜잭션 안에만 존재, 지목 불가 | 매트릭스 `REQUESTED` 행 `-` |
| C | **종결(`CLOSED`) 미수에 `freeze`** | 거절 `RECEIVABLE_CLOSED` — 진행 회수 없음 | 미수 SM **VF7** |
| D | **보류가 아닌 대상에 `unfreeze`** | 거절 — `frozen = true`가 사전조건이자 멱등 경계 | `Authorization.unfreeze`·`Receivable.unfreeze` 사전조건 |
| E | **보류 중 승인에 매입 레코드 도착** | 반영 안 함 → 격리. 불일치 아님 · M1도 아님 | **F17** · BR-50 · `CaptureBatch` 격리 사유 표 |
| F | **보류 중 승인에 망취소·승인취소 도착** | ★ 통과한다 — 보류는 `expire`·`capture`만 막는다 | T4·T13 · F9 주석 |
| G | F의 뒤처리 — 종료 상태에 남은 보류 | `unfreeze`가 종료 상태에서도 허용 — 목록에서 내림 | T15 · F9 주석(비대칭의 이유) |
| H | 보류 중 미수가 환불로 `CLOSED` 도달 | 정상 — `CLOSED`에서 `unfreeze`만 열려 있다 | V4·V5 · 미수 매트릭스 `CLOSED` 행 |
| I | **보류 전환과 매입 반영의 경합** | 승인 락에서 하나만 성공 — 매입 승리면 "이미 매입됨" 고지 | 승인 SM §6 동시성 |
| J | **보류와 회수의 경합** | 보류가 미수 락을 잡음 — 회수 승리분은 유효 | 미수 SM §6 동시성 |
| K | 해제 시점에 홀딩 기한이 이미 지남 | ★ 다음 만료 배치에서 즉시 만료 — 기한 미연장 | **BR-28** (검증 방법 ②) |
| L | 보류가 무기한으로 길어짐 | 상한 = `operation.freeze.max-duration` — 수치 미확정 | BR-28 수치 · BR-50 예외 |
| M | 스코프 밖·부재 대상 지목 | 거절 — 응답이 "없음"과 구별 안 됨 + 시도 기록 | BR-58 (L7) · IS-4 |
| N | 승인 보류와 미수 보류를 **혼동해 반대쪽을 해제** | ★ 시스템이 막지 못한다 — 화면 구분이 유일 방어선 | BR-28 · 미수 SM **RCS1** (§9) |

여섯 갈래는 표 한 줄로 담기지 않는 사정이 있다.

- **`unfreeze` 사전조건 위반(D)** — 이 거절이 멱등 경계다.\
  ⚠️ 리뷰 정정: 처음 인용한 "UC-04 `NOT_SUSPENDED`"는 실재하지 않는 코드였다.\
  카드의 대응 칸(`NORMAL × resume`)은 당시 ◎ 무시였으나 **2026-08-06 CDS3 통일로 X `ALREADY_NORMAL`(CF10)** 이 되어 이 거절과 같은 판정이 됐다.\
  ⚠️ 상태 매트릭스는 `frozen` 축을 세지 않으므로 이 거절은 매트릭스에 안 보인다 — 애그리게이트 사전조건이 정본이다.
- **보류 중 매입 도착(E)** — 반영하지 않고 격리하되 **불일치 아님 · M1도 아님**이다(의도된 지연 — F17 · BR-50 · `CaptureBatch` 격리 사유 표).
- **보류 중 망취소·승인취소(F)** — ★ **통과한다** — 보류는 `expire`·`capture`만 막는다.\
  `frozen = true`인 채 `VOIDED`에 도달한다(T4·T13 · F9 주석).
- **종료 상태의 잔여 보류(G)** — `unfreeze`가 종료 상태에서도 허용되어 목록에서 내릴 수 있다(T15 · F9 주석 — 비대칭의 이유).
- **보류 중 미수의 환불 종결(H)** — `writeOff`는 보류가 막지 않는다.\
  `frozen = true`인 채 `CLOSED`가 되므로 **`CLOSED`에서 `unfreeze`만 열려 있다**(V4·V5 · 미수 매트릭스 `CLOSED` 행).
- **경합(I·J)** — 승인 락에서 매입이 이겼으면 운영자에게 *"이미 매입됨"* 을 알린다(승인 SM §6).\
  미수 보류는 락을 잡지만, 회수가 이겼다면 그 회수는 유효하다 — 보류 이전에 들어온 자금이기 때문이다(미수 SM §6).
- **반대쪽 해제 혼동(N)** — ★ **시스템이 막지 못한다** — 둘은 별개 조작이고 각각 유효하다.\
  화면 구분이 유일한 방어선이다(RCS1 · BR-28 — §9).

## 5. 대체 시나리오

목표 달성 경로는 §3 하나지만, 대상이 둘인 것 자체가 대체 경로다.

- **승인 축과 미수 축** — 같은 목표(조사 중 자동 처리 정지)를 **승인 축**(만료·매입을 멈춘다)과 **미수 축**(회수를 멈춘다)으로 각각 이룬다.\
  하나로 묶으면 *"승인은 정상인데 그 미수만 조사"* 를 표현할 수 없다(BR-28 주석).\
  승인과 그 승인에서 발생한 미수를 **둘 다** 보류해야 하는 경우 두 조작을 각각 호출한다.
- 그 밖의 대체 경로는 없다 — 자동 처리를 멈추는 다른 수단이 설계에 없다(BR-28이 분쟁·차지백의 최소 대체물이다 · U-6 근거).

## 6. 인가·감사 ★

판정 순서는 UC-02 §7 선례를 따른다.\
① **단계**(담당자 미달 → `FORBIDDEN_LEVEL` — 자기 속성이라 대상 조회 전에 판정한다) → ② **스코프·존재**(`NOT_FOUND` — 부재·스코프 밖 동일, L7) → ③ **상태·플래그**(§4-A·C·D).\
대상을 본 뒤 단계를 판정하면 단계 오류가 존재 탐색 채널이 된다.\
판정 시점은 운영자 API 진입 시 **1회**(AU-4 — 트랜잭션 안에서 재판정하지 않는다).

L7은 §4-M이다 — 스코프 밖 승인·미수는 부재와 같은 응답이다.\
스코프 축 = 대상의 **계좌 개설 조직**(IS-4 — 승인·미수 둘 다 계좌 귀속이 있으므로 전사 특칙 대상이 아니다).

감사는 AD-2 경로 규칙을 따른다.\
**성공 = 조작 커밋 내 감사 outbox** · **거절 = 독립 커밋**(거절되면 조작 트랜잭션이 롤백되므로) · 유실 시 **M18**(R16).\
항목(AD-8) = 주체·시각·대상(승인ID/미수ID)·**스코프(계좌 소유 축)**·종류(보류/해제)·결과·사유.

이벤트에 행위자를 **싣는다** — `Frozen`·`Unfrozen`·`ReceivableFrozen`·`ReceivableUnfrozen`은 구독이 운영인 **운영자 전용 이벤트**다(AD-7 ①. 자금 이벤트·주체 혼합 이벤트와 다르다).\
승인 흐름은 **해당 없음**이다 — BR-56 5조작 목록에 보류/해제가 없다(가역·자금 간접이라 담당자 단독. BR-55 배정 표 · U-6 근거).

## 7. 계약 (계약 블록)

> 승인 흐름 없음(§6) — BR-56 5조작 목록 밖이므로 담당자 단독 조작 4건이다.
> 경로를 승인/미수로 **분리**하는 것이 RCS1(두 보류의 혼동)에 대한 계약 층 방어선이다 — 한 엔드포인트에 `targetType`을 받으면 오지목이 조용히 성공한다.

네 API 블록의 오류 표는 공통 판정 순서를 쓴다.\
① `FORBIDDEN_LEVEL`(담당자 미달 — 자기 속성이라 **대상 조회 전**) → ② `NOT_FOUND`(부재 · 스코프 밖 · `REQUESTED` 승인 **전부 동일 형태**, L7) → ③ 상태·플래그 거절(아래 각 블록) — **K-1 판정 순서 고정**이다.

#### 이벤트 `Frozen` · `Unfrozen` — 승인 보류/해제 성공 시

기존 이벤트이며 `authorization.md` §6이 정본이다(축·버전은 이 계약이 최초 설계).

| 항목 | 내용 |
|---|---|
| payload | `authorizationId` · ★ 운영자(행위자 포함) — 운영자 전용 이벤트(AD-7 ①) · 축 = `accountId`(K-4) · `ownerId` 비포함 — 아래 산문 |
| 구독 | **운영(C8)**. ★ 감사 수집은 이 구독이 아니라 **감사 전용 outbox 레코드**가 나른다(AD-2) |
| 멱등 키 | 수신측 유일 제약 = **`sourceRef` = `sourceEventId`**(AD-3 — outbox는 at-least-once) |
| 스키마 버전 | **`schemaVersion: 1`**(K-3). ★ 의미 필드 추가는 버전 올림이 아니라 **새 이벤트 타입**이다(S-6a) |

payload는 `authorizationId`와 ★ **운영자(행위자 포함)** 를 싣는다 — 구독이 운영인 **운영자 전용 이벤트**(AD-7 ① · 색인 §3 *포함 ✓* 확정)이며 정본 payload와 일치한다.\
축 = `accountId`(K-4 — 기존 파티션 축 유지. 이 시점이 최초 설계다 — IS-5) · ★ **`ownerId` 비포함**(K-4 보정 확정 — **이벤트 payload에 `ownerId`를 얹지 않는다(전면 비포함)**. IS-1 선반영 6종은 **저장 모델** 대상이고, 운영 이벤트의 스코프는 **소비 시점에 판정**한다).

기존 이벤트이며 `receivable.md` §6이 정본이다.

| 멱등 키 | `sourceRef` = `sourceEventId`(AD-3) |
| 스키마 버전 | **`schemaVersion: 1`**(K-3) |

payload는 `receivableId` · **`accountId`**(정본 이미 포함 — 축 = `accountId`, K-4) · ★ **운영자(행위자 포함)** 를 싣는다 — 운영자 전용 이벤트(AD-7 ① — ★ 이 이벤트가 그 선의 **기존 선례**다) · ★ **`ownerId` 비포함**(K-4 보정 확정 — 전면 비포함. IS-1 6종은 저장 모델 대상).
