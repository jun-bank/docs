# UC-02. 잘못 반영된 입금을 정정한다

- 작성일: 2026-08-05
- 상태: **확정** (파일럿 — 듀얼 1패스 반영, 2026-08-05)
- 액터: **운영자 2인** — 요청·실행 = 담당자(maker) · 승인 = 책임자(checker) (BR-55, ★ 같은 사람 불가)
- 권한 요건: **BR-56 ①** (책임자 승인 조작) · 스코프 = 대상 계좌의 개설 조직 안 (IS-4 — 전사 특칙 대상 아님: 계좌 귀속이 있다)
- 트랜잭션 경계: **E5** (계좌 · 미수 · 입금수신 — 한 커밋. ★ C8 `consume`이 같은 트랜잭션에 참여 — 자금 무이동 참여자, R14)
- 관련 규칙: BR-38·47·54·55·56·57 · DepositReceipt INV-1·4·5 · ApprovalRequest INV-1~3 (참조만)

> 이 문서를 다 읽으면 **잘못 반영된 입금이 2인 승인(담당자·책임자)을 거쳐 어떻게 역분개로 정정되는지, 그리고 승인·실행 두 관문에서 무엇이 왜 거절되는지**를 설명할 수 있어야 한다.

## 1. 목표

운영자가 잘못 반영된 입금을 **2인 승인 절차를 거쳐** 역분개로 정정한다.\
이미 사용된 부족분은 미수로 전환한다.

## 2. 사전·사후 조건

시작 조건은 둘이다.\
원입금 레코드가 존재한다 — 근거 없는 정정이 고객 자금을 줄이면 안 되기 때문이다(INV-4).\
대상은 요청자 스코프 안의 계좌다.

끝 상태는 넷으로 갈린다.

- **성공** — `balance`가 줄고, 부족분이 `Receivable(origin=DEPOSIT_REVERSAL)`로 서고, `(기관, reversalId, 정정)` 수신 기록이 남고, 이동 행이 갱신되고, 승인이 `CONSUMED`가 되고, 감사 outbox 행이 선다.\
  이 전부가 **한 커밋(E5)**이다.\
  `reversalId`는 **우리 채번**이라 기관 = **자행 고정**이다(R-06).\
  원장 `DepositReversed` 기표는 비동기다(R6).
- **거절/만료** — 자금은 변하지 않는다.\
  승인 요청이 `REJECTED`/`EXPIRED`로 종료되고(재사용 불가), 사유가 감사에 남는다.
- **실행 커밋 실패** — 승인이 **미소비**로 남는다.\
  `consume`이 같은 트랜잭션이라 재실행할 수 있고, 이중 실행은 멱등이 막는다.

### 동작 구조

2인 승인(담당자 maker → 책임자 checker)이 C8을 거쳐 실행 커밋(E5)으로 끝나는 경로다.

```
[담당자 A (maker)]                       [책임자 B (checker)]
   │ ① request(reversalId·원입금·금액)      │ ② approve  (B ≠ A 검사, INV-1)
   ▼                                        ▼
[C8 ApprovalRequest]  PENDING ─────────────▶ APPROVED
   │
   │ ③ A가 실행: reverseDeposit(A)
   ▼
[C1 역분개 UC] ──④ consume(A)──▶ [C8]  (executor=maker · 인자 일치 INV-3)
   │
   │ ⑤ E5 — 한 커밋
   ├──▶ [계좌] balance 감소
   ├──▶ [미수 원장] Receivable(origin=DEPOSIT_REVERSAL)
   ├──▶ [입금수신 기록] (기관, reversalId, 정정)
   └──▶ [감사 outbox] (AD-2)
   │
   │ ⑥ DepositReversed 발행 (비동기)
   ▼
[릴레이] ──▶ [C5 원장] 역분개 기표  (귀속 영업일=정정 시점 BR-47)
```

## 3. 주요 성공 시나리오

1. 담당자 A → C8 `request(입금 역분개, reversalId·원입금·금액)` — `PENDING` [ApprovalRequest A1 · 감사 append]
2. 책임자 B → C8 `approve(B)` — **B ≠ A** 검사 → `APPROVED` [A2 · INV-1 · 감사 append]
3. A → C1 `reverseDeposit(reversalId, 원입금, 금액, A)` 실행
4. C1 → C8 `consume(A)` 동기 호출 — 실행 인자 = 요청 인자(INV-3) · executor = maker(A4) [R14]
5. [E5 커밋] 수신 기록 · `balance` 감소 · 부족분 `incur` · 이동 행 · 감사 outbox · `CONSUMED`
6. 릴레이 → C5: `DepositReversed` 번역 기표 — 귀속 영업일 = **정정 시점**(BR-47) [R6]

### 흐름도

승인 게이트와 실행 게이트 두 관문의 분기(§4 A~K)를 거절 코드와 함께 얹었다.

```
[시작: 담당자 A 역분개 요청]
   │  (스코프 밖·부재 계좌 = NOT_FOUND 동일 형태, §4-K)
   ▼
[C8 request → PENDING]
   │
   ▼
⟨책임자 B 승인?⟩ ──B=A?──▶ [거절: SELF_APPROVAL] (§4-A)
   │ 승인(B≠A)   ├─거절──▶ [REJECTED + 사유 필수] ──▶ (끝) (§4-H)
   │             └─상한 경과──▶ [EXPIRED — 재요청] ──▶ (끝) (§4-G)
   ▼
[APPROVED]   (승인 전 실행은 경로 부재 — 구조적 차단, §4-B)
   │
   ▼
⟨A가 실행 (executor=maker)?⟩ ──A≠maker──▶ [거절: NOT_MAKER] (§4-I)
   │ 예                    └─인자 변경──▶ [거절: ARG_MISMATCH] (§4-F)
   ▼
⟨원입금 존재 & Σ정정 ≤ 원입금?⟩ ──부재──▶ [거절: NO_ORIGINAL] (§4-C)
   │ 예                       └─초과──▶ [거절: EXCEEDS_ORIGINAL] (§4-D)
   ▼
⟨같은 reversalId 재실행?⟩ ──예──▶ [무변화·최초 결과 (E5 멱등)] ──▶ (끝) (§4-E)
   │ 아니오
   ▼
[E5 커밋: balance 감소·미수 전환·수신 기록·consume·감사]
   │  (커밋 실패 → 전체 롤백, 승인 미소비·재실행 가능, §4-J)
   ▼
[DepositReversed 발행 → C5 원장 기표] ──▶ (끝)
```

## 4. 예외 시나리오 ★

정정은 승인 게이트와 실행 게이트 두 관문을 거치므로, 예외도 그 둘로 갈린다.\
각 갈래는 사유를 구분해 응답한다.

아래 표는 트리거와 응답 코드의 대응이다. 코드는 §7 계약의 정본과 같다.

| # | 트리거 | 응답 → 종결 | 근거 |
|---|---|---|---|
| A | A가 자기 요청을 승인 | `SELF_APPROVAL` — 거절 | ApprovalRequest INV-1 · AF7 |
| B | 승인 전 실행 시도 | 경로 부재 — `PENDING`에서 `consume` 불가 | AF1 |
| C | 원입금 레코드 없음 | `NO_ORIGINAL` — 실행 거절 | DepositReceipt INV-4 |
| D | Σ(정정) > 원입금 | `EXCEEDS_ORIGINAL` — 실행 거절 | DepositReceipt INV-5 |
| E | 같은 `reversalId` 재실행 | 무변화 — 최초 결과(E5 멱등) | DepositReceipt INV-1 · BR-38 |
| F | 승인 후 인자 변경 실행 | `ARG_MISMATCH` — `consume` 거절 | INV-3 |
| G | 승인 대기 상한 경과 | `EXPIRED` — 재요청 | A5 |
| H | 책임자 거절 | `REJECTED` — 사유 필수 | A3 |
| I | 실행자 ≠ 요청자 | `NOT_MAKER` — `consume` 거절 | A4 |
| J | E5 커밋 실패 | 전체 롤백 — 승인 미소비 | A4 |
| K | 스코프 밖 계좌 지목 | `NOT_FOUND` — 부재와 동일 | BR-58 (L7) |

몇 갈래는 표의 한 줄에 담기지 않는 사정이 있다.

- **자기 승인·승인 전 실행(A·B)** — A는 상태와 무관한 조건 위반이라 어느 상태에서도 거절된다(INV-1).\
  B는 오류 코드가 아니라 경로 자체가 없다 — `PENDING` 승인에서는 `consume`이 호출되지 않는다(AF1 구조적 강제).
- **근거·한도 위반(C·D·F)** — C는 근거 없는 잔액 감소를 막고(원입금이 없으면 고객 자금을 줄일 수 없다), D는 받은 것보다 많이 되돌릴 수 없다는 제약이다.\
  F는 승인 후 인자 바꿔치기를 막는다 — 실행 인자 ≠ 요청 인자면 `consume`이 거절한다(INV-3).
- **대기·거절의 종결(G·H)** — G의 승인 대기 상한은 **수치 미확정**이다(BR-56).\
  H의 책임자 거절은 사유가 필수이며 감사에 남는다(A3).
- **커밋 실패(J)** — E5가 실패하면 전체가 롤백되고, 승인은 미소비로 남아 재실행할 수 있다(A4 — 같은 트랜잭션).
- **스코프 밖 계좌(K)** — 거절 응답이 "없는 계좌"와 구별되지 않는다(존재 비노출, BR-58 L7).\
  거절 시도도 감사에 남는다.

## 5. 대체 시나리오

없다.\
입금 정정의 정식 경로는 이것 하나다 — BR-38이 "취소 기능이 아니라 운영자의 역분개"라 정한다(U-6 근거).

## 6. 인가·감사 ★

주체는 운영자 API 진입 시 한 번 판정한다.\
단계(담당자/책임자)와 스코프(소속 조직 × 계좌 개설 조직 — IS-4)를 본다.

L7이 응답 형태를 통일한다.\
스코프 밖 계좌와 부재 계좌는 **동일 응답**이다(§4-K).\
거절 시도도 기록된다(독립 커밋 — AD-2).

감사는 경로에 따라 커밋이 다르다.\
요청·승인·거절·만료는 C8이 직접 append 하고(AD-5), 실행은 E5 커밋 내 outbox다(AD-2).\
**다섯 사건 전부에 행위자가 남는다**(AD-8: 주체·대상·스코프·사유·요청자·승인자).

## 7. 계약 (계약 블록)

### `POST /ops/approval-requests` — 승인 요청 생성

이 블록이 **BR-56 6조작 공통 계약의 정본이다** — 다른 조작 UC는 복사하지 않고 여기를 참조한다(F-24).\
조작별 인자 스키마만 각 UC가 정의한다.\
★ **⑥(권한 부여·회수)의 인자 스키마와 UC는 명시 이월** — C7 관리 API 패스에서 정의한다(L1-15).

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **담당자** 이상 · 스코프 = 대상 식별자의 귀속 |
| 요청 | 대상 조작(BR-56 **①~⑥**) · 조작별 인자 · 사유 |
| 응답(성공) | 요청 ID · `PENDING` |
| 오류 표 ★ | ① `FORBIDDEN_LEVEL` → ② `NOT_FOUND` → ③ `INVALID_OPERATION` · `DUPLICATE_INSTRUCTION` |
| 멱등 | 비멱등 — 중복 요청은 각각 `PENDING` |
| 예산 | 실시간 아님 (관리 조작) |
| 감사 | 요청자·대상·스코프·인자 (AD-5 직접 append) |

주체·스코프에는 전사 특칙이 붙는다.\
스코프 판정은 대상 식별자의 귀속으로 하되, 전사 조작이면 전사 스코프다(BR-55 특칙).

요청 칸의 대상 조작 목록에는 세 가지 단서가 있다.\
목록 밖 조작은 거절한다.\
★ **⑥은 책임자·AUDITOR 단계의 권한 부여·수동 회수**다(2026-08-06 C7 D-7 — L1-06). 실행 컨텍스트는 **C7**이며(R14), **유일 예외는 break-glass**인데 그것은 승인 요청 자체를 만들지 않는다(BR-61).\
조작별 인자의 스키마는 각 조작 UC가 정의한다 — **①은 본 UC**로 `reversalId`·원입금·금액이다.\
★ **④⑤는 `instructionId`(maker 생성 — R15)를 요청 단계에서 유일하게 포함**한다 — 없으면 두 번째 승인이 수신측 무연산으로 조용히 사라진다(2026-08-06 계약 전수 D 확정).

오류 표의 판정 순서는 **재점검 정정**을 거쳤다 — ① 단계 → ② 스코프·존재 → ③ 상태·목록이다.\
① 단계(`FORBIDDEN_LEVEL`)는 자기 속성이라 대상 조회 없이 판정한다 — 단계 미달자는 대상 존재를 영원히 모른다.\
② 스코프·존재(`NOT_FOUND`)는 부재·스코프 밖을 동일하게 응답한다(L7).\
③ 상태·목록(`INVALID_OPERATION`)과 ★ **`DUPLICATE_INSTRUCTION`**(④⑤ — 같은 `instructionId`의 요청 존재. 요청 칸의 유일 제약이 여기서 거절된다 — 리뷰 F6 보강)이 마지막이다.\
대상을 본 뒤 단계를 판정하면 `FORBIDDEN_LEVEL`이 존재 탐색 채널이 된다.

멱등은 비멱등이다 — 중복 요청은 각각 `PENDING`으로 남고 방치 통지(BR-53 계열)가 잡는다. *(리뷰 확인 요청 — 멱등 필요?)*

### `POST /ops/approval-requests/{id}/approve` · `/reject` — 승인/거절

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **책임자** · `checker ≠ maker` (INV-1) |
| 요청 | reject는 사유 필수 (A3) |
| 응답(성공) | 요청 ID · 전이된 상태(`APPROVED`/`REJECTED`) |
| 오류 표 ★ | ① `FORBIDDEN_LEVEL` → ② `NOT_FOUND` → ③ `SELF_APPROVAL` · `ALREADY_*` |
| 멱등 | 상태 전이가 멱등 경계 — 종료 상태 재호출은 `ALREADY_*` |
| 예산 | 실시간 아님 |
| 감사 | 승인자/거절자·사유 (AD-5 — C8 자기 조작 직접 append) |

오류 표의 판정 순서는 **K-1**이다.\
① **책임자 단계 미달 = `FORBIDDEN_LEVEL`**은 자기 속성이라 대상 조회 전에 판정한다(2026-08-06 리뷰 F-01 보강).\
② **스코프·존재 = `NOT_FOUND`**는 부재·스코프 밖을 동일하게 응답한다(L7).\
③ `SELF_APPROVAL`(INV-1)은 스코프 안 ID에만 반환되므로 탐색 채널이 아니다(리뷰 Q-2 해소).\
★ 종료 상태 재호출은 `ALREADY_APPROVED`·`ALREADY_REJECTED`·`ALREADY_CONSUMED`·`ALREADY_EXPIRED`로 응답한다 — 구 `INVALID_STATE` 단일 코드를 대체한다(2026-08-06 CDS3 소급: 무엇이었는지가 응답에 보여야 상태 오인이 없다. approval-request SM 주석이 짝이다).\
멱등도 같은 경계다 — 종료 상태 재호출은 **`ALREADY_*` 명시 거절**이다(CDS3 소급).

### `POST /ops/accounts/{accountId}/deposit-reversals` — 역분개 실행

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **담당자** · `executor = maker` (A4) · 스코프 안 |
| 요청 | `reversalId` · 원입금 ID · 금액 · 승인 요청 ID |
| 응답(성공) | 정정 결과 — `DepositReversed` payload와 동형 |
| 오류 표 ★ | `NOT_FOUND` · `NO_APPROVAL` · `NOT_MAKER` · `ARG_MISMATCH` · `NO_ORIGINAL` · `EXCEEDS_ORIGINAL` · `DUPLICATE` |
| 멱등 | `(기관, reversalId, 정정)` — DepositReceipt INV-1 (R-06) |
| 예산 | 실시간 아님 (사람 조작 — 단 E5 커밋은 락 순서 준수) |
| 감사 | E5 커밋 내 outbox (AD-2) — 주체·계좌·금액·승인 참조 |

응답의 정정 결과는 잔액 회수분과 미수 전환분이며 `DepositReversed` payload와 같은 모양이다.

오류 코드의 근거는 다음과 같다.\
`NOT_FOUND`는 계좌 부재·스코프 밖을 동일하게 응답한다(L7).\
`NO_APPROVAL`은 승인이 없는 실행이다(AF1).\
★ **`NOT_MAKER`**는 실행자 ≠ maker다(A4) — `FORBIDDEN_LEVEL`과 판정 위치가 다르다: 단계는 대상 조회 전, 이것은 승인요청을 본 뒤다(BR-56 ①~③ 실행 공통 — 2026-08-06 확정).\
`ARG_MISMATCH`(INV-3) · `NO_ORIGINAL`(INV-4) · `EXCEEDS_ORIGINAL`(INV-5) · `DUPLICATE`(E5 멱등 — 최초 결과 반환)가 나머지다.

멱등 키의 기관 축은 자행 고정이다.\
키는 **`(기관, reversalId, 정정)`**이며(DepositReceipt INV-1 · 2026-08-06 **R-06**: 채널 키의 유일성 스코프는 발신 기관이다).\
★ `reversalId`는 우리가 채번하므로(운영자 지시 — 외부 전문이 아니다) 기관 = **자행 고정**이고 스코프가 자명하다 — 입금(`depositId` = 입금원 채번)과 갈리는 지점이다.

### 이벤트 `DepositReversed` (기존 — account.md §6이 정본. 계약 확인 블록)

| 항목 | 내용 |
|---|---|
| payload | accountId · amount · recoveredFromBalance · receivableIncurred · sourceRef · 사유 — **행위자 없음**(자금 이벤트 — AD-7 ②) |
| 구독 | C5 원장 (R6 ACL 번역) |
| 멱등 키 | 수신측 = 전표 INV-8(`sourceEvent`) |
| 스키마 버전 | **`schemaVersion: 1`** (K-3 — 2026-08-06 계약 전수. 의미 필드 추가 = 새 타입, S-6a) |

payload에 행위자가 없는 것은 자금 이벤트이기 때문이다(AD-7 ②).\
행위자는 E5 커밋의 감사 outbox가 나른다 — 정본과 일치한다.
