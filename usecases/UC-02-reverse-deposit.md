# UC-02. 잘못 반영된 입금을 정정한다

- 작성일: 2026-08-05
- 상태: **확정** (파일럿 — 듀얼 1패스 반영, 2026-08-05)
- 액터: **운영자 2인** — 요청·실행 = 담당자(maker) · 승인 = 책임자(checker) (BR-55, ★ 같은 사람 불가)
- 권한 요건: **BR-56 ①** (책임자 승인 조작) · 스코프 = 대상 계좌의 개설 조직 안 (IS-4 — 전사 특칙 대상 아님: 계좌 귀속이 있다)
- 트랜잭션 경계: **E5** (계좌 · 미수 · 입금수신 — 한 커밋. ★ C8 `consume`이 같은 트랜잭션에 참여 — 자금 무이동 참여자, R14)
- 관련 규칙: BR-38·47·54·55·56·57 · DepositReceipt INV-1·4·5 · ApprovalRequest INV-1~3 (참조만)

## 1. 목표 (한 문장)

운영자가 잘못 반영된 입금을 **2인 승인 절차를 거쳐** 역분개로 정정하고, 이미 사용된 부족분은 미수로 전환한다.

## 2. 사전 조건 / 사후 조건

- 사전: 원입금 레코드가 존재한다(INV-4 — 근거 없는 정정이 고객 자금을 줄이면 안 된다). 요청자 스코프 안의 계좌다.
- 사후(성공): `balance` 감소 · 부족분 `Receivable(origin=DEPOSIT_REVERSAL)` · `(reversalId, 정정)` 수신 기록 · 이동 행 갱신 · 승인 `CONSUMED` · 감사 outbox — **전부 한 커밋**(E5). 원장 `DepositReversed` 기표는 비동기(R6).
- 사후(거절/만료): 자금 무변화 · 승인 요청 `REJECTED`/`EXPIRED`(종료 — 재사용 불가) · 사유가 감사에 남는다.
- 사후(실행 커밋 실패): 승인 **미소비**(consume이 같은 트랜잭션 — 재실행 가능, 이중 실행은 멱등이 막는다).

## 3. 주요 성공 시나리오

1. 담당자 A → C8 `request(입금 역분개, reversalId·원입금·금액)` — `PENDING` [ApprovalRequest A1 · 감사 append]
2. 책임자 B → C8 `approve(B)` — **B ≠ A** 검사 → `APPROVED` [A2 · INV-1 · 감사 append]
3. A → C1 `reverseDeposit(reversalId, 원입금, 금액, A)` 실행
4. C1 → C8 `consume(A)` 동기 호출 — 실행 인자 = 요청 인자(INV-3) · executor = maker(A4) [R14]
5. [E5 커밋] 수신 기록 · `balance` 감소 · 부족분 `incur` · 이동 행 · 감사 outbox · `CONSUMED`
6. 릴레이 → C5: `DepositReversed` 번역 기표 — 귀속 영업일 = **정정 시점**(BR-47) [R6]

## 4. 예외 시나리오 ★

| # | 트리거 | 시스템 반응 → 종결 | 근거 |
|---|---|---|---|
| A | **A가 자기 요청을 승인** | 거절 — 상태 무관 조건 위반 | ApprovalRequest INV-1 · AF7 |
| B | **승인 전 실행 시도** | 경로 부재 — `PENDING`에서 `consume` 불가 | AF1 (구조적 강제) |
| C | 원입금 레코드 없음 | 실행 거절 — 근거 없는 잔액 감소 차단 | DepositReceipt INV-4 |
| D | Σ(정정) > 원입금 | 실행 거절 — 받은 것보다 많이 되돌릴 수 없다 | DepositReceipt INV-5 |
| E | 같은 `reversalId` 재실행 | 무변화 — 최초 결과 (E5 멱등) | DepositReceipt INV-1 · BR-38 |
| F | **승인 후 인자 변경 실행** | `consume` 거절 — 실행 인자 ≠ 요청 인자 | INV-3 (바꿔치기 방지) |
| G | 승인 대기 상한 경과 | `EXPIRED` — 재요청 필요 (수치 미확정 — BR-56) | A5 |
| H | 책임자 거절 | `REJECTED` + **사유 필수** — 감사에 남는다 | A3 |
| I | 실행자 ≠ 요청자 | `consume(executor)` 거절 | A4 (`executor = maker`) |
| J | E5 커밋 실패 | 전체 롤백 — 승인 미소비, 재실행 가능 | A4 (같은 트랜잭션) |
| K | 스코프 밖 계좌 지목 | 거절 — ★ 응답이 "없는 계좌"와 구별되지 않는다 | BR-58 (L7) · 시도 감사 기록 |

## 5. 대체 시나리오

- 없음 — 입금 정정의 정식 경로는 이것 하나다(BR-38: "취소 기능이 아니라 운영자의 역분개"). *(U-6 근거)*

## 6. 인가·감사 ★

- 주체 판정: 운영자 API 진입 시 1회 — 단계(담당자/책임자)·스코프(소속 조직 × 계좌 개설 조직 — IS-4).
- L7: 스코프 밖·부재 계좌 = **동일 응답**(§4-K). 거절 시도도 기록(독립 커밋 — AD-2).
- 감사: 요청·승인·거절·만료 = C8 직접 append(AD-5) / 실행 = E5 커밋 내 outbox(AD-2). **다섯 사건 전부에 행위자**(AD-8: 주체·대상·스코프·사유·요청자·승인자).

## 7. 계약 (계약 블록)

#### `POST /ops/approval-requests` — 승인 요청 생성 (★ **이 블록이 BR-56 5조작 공통 계약의 정본이다** — 다른 조작 UC는 복사하지 않고 여기를 참조한다(F-24). 조작별 인자 스키마만 각 UC가 정의)

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **담당자** 이상 · 스코프 판정 = 대상 식별자의 귀속 (전사 조작이면 전사 스코프 — BR-55 특칙) |
| 요청 | 대상 조작(BR-56 ①~⑤ 목록 안 — 밖이면 거절) · **조작별 인자(스키마는 각 조작 UC가 정의 — ①은 본 UC: reversalId·원입금·금액)** · 사유 |
| 응답(성공) | 요청 ID · `PENDING` |
| 오류 표 ★ | ★ **판정 순서 = 스코프·존재 먼저**(밖이면 무조건 `NOT_FOUND` — 그 뒤에만 상태·단계 판정. 리뷰 Q-2: 순서가 없으면 상태 오류가 ID 탐색 채널이 된다) → `NOT_FOUND`(대상 부재·스코프 밖 동일, L7) · `INVALID_OPERATION`(목록 밖) · `FORBIDDEN_LEVEL`(단계 미달 — 자기 단계는 자기가 알므로 비노출 아님) |
| 멱등 | 비멱등 — 중복 요청은 각각 `PENDING`으로 남고 방치 통지(BR-53 계열)가 잡는다. *(리뷰 확인 요청 — 멱등 필요?)* |
| 예산 | 실시간 아님 (관리 조작) |
| 감사 | 요청자·대상·스코프·인자 (AD-5 직접 append) |

#### `POST /ops/approval-requests/{id}/approve` · `/reject` — 승인/거절

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **책임자** · ★ `checker ≠ maker` (INV-1) |
| 요청 | (reject는 사유 필수 — A3) |
| 응답(성공) | 요청 ID · 전이된 상태(`APPROVED`/`REJECTED`) |
| 오류 표 ★ | ★ **판정 순서 = 스코프·존재 먼저** → `NOT_FOUND`(부재·스코프 밖 동일 — L7) → `SELF_APPROVAL`(INV-1 — 스코프 안 ID에만 반환되므로 탐색 채널이 아니다, 리뷰 Q-2 해소) · `INVALID_STATE`(AF2~AF6) |
| 멱등 | 상태 전이가 멱등 경계 — 종료 상태 재호출은 `INVALID_STATE` |
| 예산 | 실시간 아님 |
| 감사 | 승인자/거절자·사유 (AD-5 — C8 자기 조작 직접 append) |

#### `POST /ops/accounts/{accountId}/deposit-reversals` — 역분개 실행

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **담당자** · ★ `executor = maker` (A4) · 스코프 안 |
| 요청 | `reversalId` · 원입금 ID · 금액 · 승인 요청 ID |
| 응답(성공) | 정정 결과(잔액 회수분 · 미수 전환분 — `DepositReversed` payload와 동형) |
| 오류 표 ★ | `NOT_FOUND`(계좌 부재·스코프 밖 동일 — L7) · `NO_APPROVAL`(AF1) · `ARG_MISMATCH`(INV-3) · `NO_ORIGINAL`(INV-4) · `EXCEEDS_ORIGINAL`(INV-5) · `DUPLICATE`(E5 멱등 — 최초 결과 반환) |
| 멱등 | `(reversalId, 정정)` — DepositReceipt INV-1 |
| 예산 | 실시간 아님 (사람 조작 — 단 E5 커밋은 락 순서 준수) |
| 감사 | E5 커밋 내 outbox (AD-2) — 주체·계좌·금액·승인 참조 |

#### 이벤트 `DepositReversed` (기존 — account.md §6이 정본. 계약 확인 블록)

| 항목 | 내용 |
|---|---|
| payload | accountId · amount · recoveredFromBalance · receivableIncurred · sourceRef · 사유 — ★ **행위자 없음(자금 이벤트 — AD-7 ②)**. 행위자는 E5 커밋의 감사 outbox가 나른다 ✓ 정본과 일치 |
| 구독 | C5 원장 (R6 ACL 번역) |
| 멱등 키 | 수신측 = 전표 INV-8(`sourceEvent`) |
| 스키마 버전 | Phase 4 계약 전수 시 S-9 일괄 부여 — **[미정]** (파일럿 범위 밖 — 근거: 색인의 이벤트 표가 전수 시점의 입력) |

#### 화면 전환도 (운영자 — 유일한 실질 UI)
