# UC-13. 미수 계좌의 승인 차단을 해제한다

- 작성일: 2026-08-05
- 상태: **검토대기 (계약 블록 완결)**
- 액터: **운영자 2인** — 요청·실행 = 담당자(maker) · 승인 = 책임자(checker) (BR-55, 같은 사람 불가)
- 권한 요건: **BR-56 ②** (책임자 승인 조작) · 스코프 = 대상 계좌의 개설 조직 (IS-4 — 계좌 귀속이 있으므로 전사 특칙 대상이 아니다)
- 트랜잭션 경계: **없음 — 계좌 단일 애그리게이트**(조작 대장 `liftReceivableBlock` = `—`). ★ **C8 `consume`이 같은 트랜잭션에 참여**한다 — 자금 무이동 참여자이며 E 표 밖의 의식적 예외(R14 · AD-2)
- 관련 규칙: BR-34·45·54·55·56·57·58 · `Account` INV-3·PRE-2 · `ApprovalRequest` INV-1~3 · 미수 SM V3·V5 (참조만 — F-24)

## 1. 목표 (한 문장)

운영자가 미수 때문에 승인이 거절되는 계좌의 차단을 **2인 승인 절차를 거쳐** 풀어, 미수가 남은 상태에서도 결제가 되게 한다.

## 2. 사전 조건 / 사후 조건

- 사전: 대상 계좌에 **미결 미수가 존재한다**(`liftReceivableBlock` 사전조건 — 미수가 없으면 차단 자체가 없다). 요청자 스코프 안의 계좌다.
- 사전: ★ **승인된 요청이 존재한다**(BR-56 ② — C8 동기 확인, R14). 승인 전에는 실행 경로가 없다(AF1).
- 사후(성공): `receivableBlockLifted = true` · `ReceivableBlockLifted` 발행(payload = `accountId`·**운영자** — AD-7 ①) · 승인 요청 `CONSUMED` · 감사 outbox — **한 커밋**. 이후 `hold()`의 미수 조건이 통과한다(PRE-2).
- 사후(거절/만료): 차단 유지 · 승인 요청 `REJECTED`/`EXPIRED`(종료 — 재사용 불가) · 사유가 감사에 남는다.
- 사후(실행 커밋 실패): 승인 **미소비** — `consume`이 같은 트랜잭션이므로 재실행 가능(A4·J).
- 사후(자동 해제): ★ **미결 미수가 전부 없어지면 `receivableBlockLifted`는 자동으로 `false`로 돌아간다**(`Account` **INV-3**) — 운영자 조작이 아니라 계좌가 **E3·E4 커밋 후 자기 필드를 재평가**한 결과다(미수 SM V3·V5). 이 UC의 효과는 **그 시점에 끝난다**.

## 3. 주요 성공 시나리오

1. 담당자 A → C8 `request(미수 차단 해제, accountId)` — `PENDING` [ApprovalRequest **A1** · 감사 직접 append(AD-5)]
2. 책임자 B → C8 `approve(B)` — **B ≠ A** 검사 → `APPROVED` [**A2** · **INV-1**]
3. A → `Account.liftReceivableBlock(operator = A)` 실행 요청 — 사전조건 검사: **미결 미수 존재** · **승인된 요청 존재**
4. 계좌 → C8 `consume(A)` 동기 호출 — 실행 인자 = 요청 인자(**INV-3**) · `executor = maker`(**A4**) [**R14** — 같은 트랜잭션]
5. [커밋] `receivableBlockLifted = true` · `ReceivableBlockLifted` · 감사 outbox · 승인 `CONSUMED`
6. 이후 신규 승인에서 미수 조건이 통과한다 — `hold()`의 **PRE-2**(미결 미수 없음 **또는** `receivableBlockLifted = true`) [BR-45]
7. (자동 종료) 유입 자금이 미수를 전액 회수하면 계좌가 자기 플래그를 재평가해 **차단이 자동 복원**된다 [**INV-3** · BR-34·45 · V3·V5]

## 5. 대체 시나리오

- **기다린다(무조작).** 미수가 전액 상계되면 차단은 자동으로 풀린다(BR-45 · INV-3) — 같은 결말("이 계좌에서 다시 결제가 된다")에 도달하는 유일한 다른 경로이며, **채권을 키우지 않는다**. 운영자 해제는 그 대기를 앞당기는 예외 경로다.
- 건별 승인은 **불가능하다** — 승인은 실시간 경로라 사람이 개입할 수 없어 **계좌 단위 차단 해제**로 설계됐다(BR-45 주석). 따라서 "이 결제만 통과시킨다"는 대체 경로는 존재하지 않는다.

## 6. 인가·감사 ★

- **판정 순서** (UC-02 §7 선례): ① **단계**(요청 = 담당자 / 승인 = 책임자 — `FORBIDDEN_LEVEL`, 대상 조회 전) → ② **스코프·존재**(`NOT_FOUND` — 부재·스코프 밖 동일, L7) → ③ **상태·사전조건**(§4-B·C·I).
- 판정 시점: 요청·승인·실행 **각 API 진입 시 1회**(AU-4). 트랜잭션 안에서 재판정하지 않는다.
- L7: §4-M — 스코프 밖 계좌는 부재와 같은 응답. `SELF_APPROVAL`(INV-1)은 스코프 안 승인요청 ID에만 반환되므로 탐색 채널이 아니다(UC-02 UC2-2 판정 승계).
- 감사(AD-2 경로 규칙): **요청·승인·거절·만료 = C8 자기 조작이므로 자기 저장소에 직접 append**(AD-5·AD-6) / **실행 성공 = 커밋 내 outbox** / **거절·실패 = 독립 커밋** / 유실 = **M18**(R16).
- 감사 항목(AD-8): 주체·시각·대상(계좌)·스코프·종류·결과 + **사유·요청자·승인자**(BR-56 조작 필수 3항).
- 승인 흐름: **요청·승인·소비**가 UC-02 §7의 **공통 승인 계약(U-7 정본)** 을 그대로 탄다 — 이 UC는 조작별 인자만 정의한다(§7).

| 응답(성공) | `accountId` · `receivableBlockLifted: false` · 효과 고지: 신규 승인이 다시 **PRE-2**에 걸린다 · ★ **다시 풀려면 새 2인 승인**(BR-56 ②)이 필요하다 |
| 오류 표 ★ | ① `FORBIDDEN_LEVEL` → ② `NOT_FOUND`(부재·스코프 밖 동일 — L7) → ③ **`ALREADY_BLOCKED`**(`reimposeReceivableBlock` 사전조건 **`receivableBlockLifted = true`** 위반 — ★ **정본이 이미 거절을 명시**한다(*"아니면 거절 — 되돌릴 해제가 없다"*, account.md §5)이므로 K-1 CDS3와 충돌 없이 유도된다. **코드명만 신설** — CF10 `ALREADY_NORMAL` 패턴 = `ALREADY_<현재 상태>`). ★ **원인이 구별되지 않는다**: 운영자가 이미 재부과한 계좌와 **미수 전액 회수로 자동 복원된 계좌**(INV-3 · §4-J)가 **같은 코드**로 거절된다 — 구별은 감사 기록과 `ReceivableBlockLifted`/`Reimposed` 이벤트 이력이 나른다 |
| 멱등 | **비멱등 — 재요청은 명시 거절**(`ALREADY_BLOCKED`). 거절이 멱등 경계다(K-1 CDS3) |
| 예산 | 실시간 아님 — **계좌 단일 애그리게이트**(C8 참여 없음 — 아래 비대칭 표) |
| 감사 | 경로(AD-2) = 성공 → 커밋 내 outbox · 거절 → 독립 커밋 · 유실 = M18. 항목(AD-8) = `sourceRef` · 주체 · 시각 · 대상(`accountId`) · 스코프(판정에 쓰인 개설 조직 — K-4) · 종류(재부과) · 결과 + **사유**. ★ **요청자·승인자 칸이 없다** — BR-56 조작이 아니므로 3항 중 사유만 남는다(비대칭이 감사 항목에도 그대로 드러난다) |

#### ★ 해제와 재부과의 계약 비대칭 (한 화면에 나란히 서는 두 조작이므로 명시한다)

| 축 | 해제 `receivable-block-lifts` | 재부과 `receivable-block-reimpositions` |
|---|---|---|
| 위험 방향 | **확대** — 미수가 남은 채 결제가 다시 나간다(§4-K: 시스템이 채권 증가를 막지 않는다) | **축소** — 신규 승인을 다시 막는다(안전 방향) |

| 트랜잭션 참여자 | 계좌 + **C8 승인 요청**(자금 무이동 참여자 — E 표 밖 의식적 예외) | **계좌 단독** |
