# UC-13. 미수 계좌의 승인 차단을 해제한다

- 작성일: 2026-08-05
- 상태: **초안 (계약 블록 후속)**
- 액터: **운영자 2인** — 요청·실행 = 담당자(maker) · 승인 = 책임자(checker) (BR-55, 같은 사람 불가)
- 권한 요건: **BR-56 ②** (책임자 승인 조작) · 스코프 = 대상 계좌의 개설 조직 (IS-4 — 계좌 귀속이 있으므로 전사 특칙 대상이 아니다)
- 트랜잭션 경계: **없음 — 계좌 단일 애그리게이트**(조작 대장 `liftReceivableBlock` = `—`). ★ **C8 `consume`이 같은 트랜잭션에 참여**한다 — 자금 무이동 참여자이며 E 표 밖의 의식적 예외(R14 · AD-2)
- 관련 규칙: BR-34·45·54·55·56·57·58 · `Account` INV-3·PRE-2 · `ApprovalRequest` INV-1~3 · 미수 SM V3·V5 (참조만 — F-24)

## 1. 목표 (한 문장)

운영자가 미수 때문에 승인이 거절되는 계좌의 차단을 **2인 승인 절차를 거쳐** 풀어, 미수가 남은 상태에서도 결제가 되게 한다.

## 2. 사전 조건 / 사후 조건

- 사전: 대상 계좌에 **미결 미수가 존재한다**(`liftReceivableBlock` 사전조건 — 미수가 없으면 차단 자체가 없다). 요청자 스코프 안의 계좌다.
- 사전: ★ **승인된 요청이 존재한다**(BR-56 ② — C8 동기 확인, R14). 승인 전에는 실행 경로가 없다(AF1).
- 사후(성공): `receivableBlockLifted = true` · `ReceivableBlockLifted` 발행(payload = `accountId`·**운영자** — AD-7 ①) · 승인 요청 `CONSUMED` · 감사 outbox — **한 커밋**. 이후 `hold()`의 미수 조건이 통과한다(PRE-2).
- 사후(거절/만료): 차단 유지 · 승인 요청 `REJECTED`/`EXPIRED`(종료 — 재사용 불가) · 사유가 감사에 남는다.
- 사후(실행 커밋 실패): 승인 **미소비** — `consume`이 같은 트랜잭션이므로 재실행 가능(A4·J).
- 사후(자동 해제): ★ **미결 미수가 전부 없어지면 `receivableBlockLifted`는 자동으로 `false`로 돌아간다**(`Account` **INV-3**) — 운영자 조작이 아니라 계좌가 **E3·E4 커밋 후 자기 필드를 재평가**한 결과다(미수 SM V3·V5). 이 UC의 효과는 **그 시점에 끝난다**.

## 3. 주요 성공 시나리오

1. 담당자 A → C8 `request(미수 차단 해제, accountId)` — `PENDING` [ApprovalRequest **A1** · 감사 직접 append(AD-5)]
2. 책임자 B → C8 `approve(B)` — **B ≠ A** 검사 → `APPROVED` [**A2** · **INV-1**]
3. A → `Account.liftReceivableBlock(operator = A)` 실행 요청 — 사전조건 검사: **미결 미수 존재** · **승인된 요청 존재**
4. 계좌 → C8 `consume(A)` 동기 호출 — 실행 인자 = 요청 인자(**INV-3**) · `executor = maker`(**A4**) [**R14** — 같은 트랜잭션]
5. [커밋] `receivableBlockLifted = true` · `ReceivableBlockLifted` · 감사 outbox · 승인 `CONSUMED`
6. 이후 신규 승인에서 미수 조건이 통과한다 — `hold()`의 **PRE-2**(미결 미수 없음 **또는** `receivableBlockLifted = true`) [BR-45]
7. (자동 종료) 유입 자금이 미수를 전액 회수하면 계좌가 자기 플래그를 재평가해 **차단이 자동 복원**된다 [**INV-3** · BR-34·45 · V3·V5]

## 4. 예외 시나리오 ★

| # | 트리거 | 시스템 반응 → 종결 | 근거 |
|---|---|---|---|
| A | **A가 자기 요청을 승인** | 거절 — 상태 무관 조건 위반 | `ApprovalRequest` **INV-1** · **AF7** |
| B | **승인 전 실행 시도** | 경로 부재 — `PENDING`에서 `consume` 불가 | **AF1** (구조적 강제) |
| C | **미결 미수가 없는 계좌에 실행** | 거절 — 사전조건 위반. 차단이 없는데 해제 플래그만 남으면 **INV-3 위반 상태**가 된다 | `liftReceivableBlock` 사전조건 · `Account` **INV-3** |
| D | 승인 후 **인자 변경 실행**(다른 계좌) | `consume` 거절 — 실행 인자 ≠ 요청 인자 | **INV-3**(바꿔치기 방지) |
| E | 실행자 ≠ 요청자 | `consume(executor)` 거절 | **A4** (`executor = maker`) |
| F | 승인 대기 상한 경과 | `EXPIRED` — 재요청 필요 (상한 **수치 미확정** — BR-56) | **A5** |
| G | 책임자 거절 | `REJECTED` + **사유 필수** — 감사에 남는다 | **A3** |
| H | 커밋 실패 | 전체 롤백 — 승인 **미소비**, 재실행 가능 | **A4**(같은 트랜잭션) · R14 |
| I | **이미 해제된 계좌에 재실행** | 승인 요청은 종료 상태 재사용이 막히므로(INV-2) **새 승인이 필요**하고, 계좌 플래그는 이미 `true`다 — 응답 형태는 `ALREADY_LIFTED` 명시 거절을 제안 **[판정 대기 — §9 UC13-2]** | `ApprovalRequest` **INV-2**·**AF5** |
| J | 해제 후 **미수가 전액 회수됨** | 차단 **자동 복원**(플래그 `false`) — 운영자 조작 없이 이 UC의 효과가 끝난다. 다시 풀려면 **새 2인 승인**이 필요하다 | `Account` **INV-3** · BR-45 · V3·V5 |
| K | 해제 후 **결제가 계속되어 채권이 더 쌓임** | ★ **시스템이 막지 않는다** — 이것이 이 조작의 위험 그 자체다(BR-45 근거: 회수 전 추가 결제는 채권을 계속 키운다). 방어선은 **2인 승인과 감사뿐**이고, 재차단 경로는 정본에 없다(§9 UC13-1) | BR-45 · BR-56 ② |
| L | 해제된 계좌에서 매입 시 잔액 부족 | 정상 경로 — 부족분이 **새 미수**가 된다(`Receivable.incur(CAPTURE, …)`, E2) | BR-20 · E2 |
| M | 스코프 밖·부재 계좌 지목 | 거절 — 응답이 **"없음"과 구별되지 않는다** + 시도 기록 | BR-58 (L7) · IS-4 |
| N | 미수가 **보류 중**이라 회수가 안 되는 계좌 | 정상 — 보류 미수는 회수 대상이 아니므로(UC-12) **자동 해제(§3-7)가 오지 않는다**. 차단 해제의 효과가 사실상 무기한 지속될 수 있다 | BR-28·34 · `Receivable` INV-5 |

## 5. 대체 시나리오

- **기다린다(무조작).** 미수가 전액 상계되면 차단은 자동으로 풀린다(BR-45 · INV-3) — 같은 결말("이 계좌에서 다시 결제가 된다")에 도달하는 유일한 다른 경로이며, **채권을 키우지 않는다**. 운영자 해제는 그 대기를 앞당기는 예외 경로다.
- 건별 승인은 **불가능하다** — 승인은 실시간 경로라 사람이 개입할 수 없어 **계좌 단위 차단 해제**로 설계됐다(BR-45 주석). 따라서 "이 결제만 통과시킨다"는 대체 경로는 존재하지 않는다.

## 6. 인가·감사 ★

- **판정 순서** (UC-02 §7 선례): ① **단계**(요청 = 담당자 / 승인 = 책임자 — `FORBIDDEN_LEVEL`, 대상 조회 전) → ② **스코프·존재**(`NOT_FOUND` — 부재·스코프 밖 동일, L7) → ③ **상태·사전조건**(§4-B·C·I).
- 판정 시점: 요청·승인·실행 **각 API 진입 시 1회**(AU-4). 트랜잭션 안에서 재판정하지 않는다.
- L7: §4-M — 스코프 밖 계좌는 부재와 같은 응답. `SELF_APPROVAL`(INV-1)은 스코프 안 승인요청 ID에만 반환되므로 탐색 채널이 아니다(UC-02 UC2-2 판정 승계).
- 감사(AD-2 경로 규칙): **요청·승인·거절·만료 = C8 자기 조작이므로 자기 저장소에 직접 append**(AD-5·AD-6) / **실행 성공 = 커밋 내 outbox** / **거절·실패 = 독립 커밋** / 유실 = **M18**(R16).
- 감사 항목(AD-8): 주체·시각·대상(계좌)·스코프·종류·결과 + **사유·요청자·승인자**(BR-56 조작 필수 3항).
- 승인 흐름: **요청·승인·소비**가 UC-02 §7의 **공통 승인 계약(U-7 정본)** 을 그대로 탄다 — 이 UC는 조작별 인자만 정의한다(§7).

## 7. 계약 (요약 — 상세 블록은 **계약 전수 패스로 이월**)

> **공통 승인 계약(`POST /ops/approval-requests` · `/approve` · `/reject`)의 정본은 UC-02 §7이다**(U-7). 여기서는 복사하지 않고 **이 조작의 인자와 실행 엔드포인트만** 적는다.

| 인터페이스 | 조작 | 주체 (유형·단계·스코프) | L7 대상 |
|---|---|---|---|
| (공통) `POST /ops/approval-requests` — **대상 조작 = BR-56 ②** · 인자 = `accountId` · 사유 | `ApprovalRequest.request` | 운영자 · **담당자** · 계좌 개설 조직 | ✅ (정본 = UC-02 §7) |
| (공통) `POST /ops/approval-requests/{id}/approve`·`reject` | `approve`·`reject` | 운영자 · **책임자** · `checker ≠ maker` | ✅ (정본 = UC-02 §7) |
| `POST /ops/accounts/{accountId}/receivable-block-lifts` | `Account.liftReceivableBlock(operator)` + C8 `consume`(R14, 같은 트랜잭션) | 운영자 · **담당자**(= maker) · 계좌 개설 조직 | ✅ 계좌 부재·스코프 밖 동일 |
| 이벤트 `ReceivableBlockLifted` | 〃 | 발행자 = C1 뱅킹 · 구독 = 운영 | — (**운영자 전용 이벤트 — 행위자 포함**, AD-7 ①. payload = `accountId`·운영자) |

- 실행 인자: `accountId` · 승인 요청 ID. **금액 인자가 없다** — 계좌 단위 플래그이므로 INV-3(인자 일치) 검사가 계좌 식별자 하나에 걸린다.
- 오류 표·멱등(§4-I)·예산·감사 상세 블록 · 스키마 버전(S-9): **[미정 — 계약 전수 패스]**.
- ★ 차단을 **다시 거는** 엔드포인트는 없다 — 정본에 그 조작이 없기 때문이다(§9 UC13-1).

## 9. 열린 의문

| # | 의문 |
|---|---|
| UC13-1 | ★ **재차단 경로가 없다.** `Account` 조작 표에 차단을 되거는 조작이 없고, `receivableBlockLifted`는 **미수가 전부 종결될 때만**(INV-3) `false`로 돌아간다. 오판으로 해제했거나 §4-K(채권 증가)가 관측돼도 **되돌릴 수단이 없다** — BR-45가 자동 해제만 규정하고 수동 재차단을 안 정한 공백. 정본(BR-45 · `account.md` §5) 판정 필요 |
| UC13-2 | 재실행(§4-I)의 계약 — 이미 `true`인 계좌에 대한 응답이 **명시 거절(`ALREADY_LIFTED`)** 인가 멱등 no-op인가. UC-04가 같은 형태를 **명시 거절**로 판정한 선례(CF9)가 있으나 이 조작에는 정본 칸이 없다 |
| UC13-3 | §4-N — **보류 미수만 남은 계좌**에서 차단을 해제하면 자동 복원(§3-7)이 영원히 오지 않는다. BR-28의 보류 상한(미확정)이 이 결합의 실질 상한이므로, UC12-2와 같은 수치에 묶인다 |
| UC13-4 | 승인 대기 상한(A5·AR1) · `APPROVED` 상태의 유효 기간(**AR2** — 만료가 `PENDING`에만 있다) — 승인만 받아 두고 오래 뒤에 실행하면 그 사이 계좌 상태가 달라진다. UC-02와 공유하는 의문 |
