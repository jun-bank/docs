# UC-14. 보류 격리 매입을 재처리로 승격한다

- 작성일: 2026-08-05
- 상태: **검토대기 (계약 블록 완결)**
- 액터: **운영자 2인** — 요청·실행 = 담당자(maker) · 승인 = 책임자(checker) (BR-55, 같은 사람 불가)
- 권한 요건: **BR-56 ③** (책임자 승인 조작) · ★ **전사 스코프 운영자만** — 매입 배치는 고객·조직 귀속이 없어 지점 스코프로는 판정할 축이 없다 (BR-55 스코프 특칙)
- 트랜잭션 경계: **E2** (승인 · 계좌 · 카드 · 매입 배치 · 부족 시 미수 — 한 커밋). ★ **C8 `consume`이 같은 트랜잭션에 참여**(R14 · AD-2의 E 표 밖 의식적 예외)
- 관련 규칙: BR-16·20·23·24·28·50·54·55·56·57·58 · `CaptureBatch` INV-2·3·4·**5** · 매입 배치 SM **B8**·**BF11**·**BF12** · 승인 SM F17 (참조만 — F-24)

> 이 문서를 다 읽으면 **보류로 격리됐던 매입 한 건이 2인 승인을 거쳐 어떻게 반영·승격되는지, 그리고 왜 이 조작이 전사 스코프에 묶이고 반영·승격·소비가 한 커밋이어야 하는지**를 설명할 수 있어야 한다.

## 1. 목표 (한 문장)

보류 때문에 반영되지 않고 격리돼 있던 매입 레코드를, 보류가 풀린 뒤 **2인 승인을 거쳐** 실제로 반영하고 격리 → 처리로 승격시킨다.

## 2. 사전 조건 / 사후 조건

시작 조건은 넷을 모두 만족해야 한다.

- 대상 레코드가 원 배치의 **격리 목록에 있다**(= 아직 미반영).\
  원 배치는 **`COMPLETED`** 다(**BF11** — 진행 중 배치에서는 격리가 아직 확정이 아니다).
- 격리 **사유 = 보류(BR-50)** 다(**INV-5**).
- 원승인의 **보류가 해제됐다**(UC-12 §3-5).
- ★ **승인된 요청이 존재한다**(BR-56 ③ — C8 동기 확인, R14).

끝 상태는 성공·거절·커밋 실패로 갈린다.

성공하면 다음이 **전부 한 커밋(E2)**으로 성립한다.

- 계좌에서 **즉시 출금** · 승인 `CAPTURED` · 카드·계좌 한도 복원(기준일 조건 — BR-24).
- 부족분은 **새 미수**(BR-20).
- 레코드가 **격리 → 처리로 원자 이동**(B8, 사유는 이력 보존) · 승인 요청 `CONSUMED` · 감사 outbox.
- 원 배치는 `COMPLETED` 그대로이며 **다시 열리지 않는다**(INV-4 · BF3).

성공의 불변식은 하나다.\
`|처리| + |격리|`가 **변하지 않으므로** 완료 판정(**INV-3**)이 그대로 성립한다 — 승격은 추가가 아니라 **이동**이다.

거절·만료면 자금은 변하지 않는다.\
레코드는 격리에 남고(= 미반영) · 승인 요청은 `REJECTED`/`EXPIRED`가 된다.

커밋 실패면 전체 롤백이며 승인은 **미소비**로 남는다.\
★ ②(반영)와 ③(승격)이 갈리면 *"출금은 됐는데 배치는 미반영"* 이 되어 **재시도가 같은 레코드를 또 출금**하고 **어떤 대사도 잡지 못한다**(매입 배치 SM §5 재처리 절차).

### 동작 구조

2인 승인 뒤, 격리 레코드의 반영·승격·소비가 한 커밋(E2)에 묶여 실행된다.

```
담당자 A(maker) ──request(기관·fileId·recordId, 사유)──▶ [C8 승인요청] PENDING
책임자 B ──approve(B≠A)──▶ [C8] APPROVED
담당자 A ──재처리 지시──▶  ─── E2 한 커밋 ───
   │ [Account.capture 출금] · [Authorization.capture]
   │ [한도 복원 BR-24] · [부족분 Receivable.incur BR-20]
   │ [CaptureBatch.promoteIsolated: 격리→처리 원자 이동 B8]
   │ [C8 consume(A) 동기 R14]
   │ 이벤트
   ├─▶ [IsolatedRecordPromoted] ─▶ 운영(C8)
   ├─▶ [Withdrawn] ─▶ C5 원장
   └─▶ [Captured] ─▶ C4 정산
   원 배치 COMPLETED 유지 · |처리|+|격리| 불변(INV-3)
```

## 3. 주요 성공 시나리오

승인 두 단계를 거친 뒤 담당자가 재처리 배치를 지시하고, 레코드마다 판정·반영·승격이 한 커밋에 묶인다.

1. 보류 해제 확인 — 대상 승인의 `frozen = false` (**UC-12** §3-5)
2. 담당자 A → C8 `request(격리 매입 재처리 승격, fileId·recordId)` — `PENDING` [ApprovalRequest **A1** · 감사 직접 append(AD-5)]
3. 책임자 B → C8 `approve(B)` — **B ≠ A** → `APPROVED` [**A2** · **INV-1**]
4. A가 재처리 배치를 지시 — 레코드마다:
   - ① **원 배치의 격리 목록에 있는가?** 없으면 이미 반영된 것이므로 **건너뛴다** [매입 배치 SM §5 · BR-50 멱등]
   - ② 반영 — `Account.capture(...)` · `Authorization.capture(...)` (부분 매입이면 `Card.restoreLimit`·`Account.restoreAccountLimit` — BR-24, 기준일이 다르면 복원 없음)
   - ③ `CaptureBatch.promoteIsolated(recordId, operator)` — 격리 → 처리 **원자 이동** [**B8**]
   - ④ C8 `consume(A)` 동기 호출 — 인자 일치(INV-3) · `executor = maker`(A4) [**R14**]
5. [E2 커밋] ②③④ + 부족분 `Receivable.incur(CAPTURE, …)` + 감사 outbox + 승인 `CONSUMED` — **같은 커밋**
6. 원 배치는 `COMPLETED` 유지 · 멱등 키는 원 ★ **`(기관, fileId, recordId)`** 승계 [BR-23 · **R-06**]
7. 대사에서 정상화 — 보류 격리는 원래 M1(미매입)으로 잡히지 않았으므로 새로 닫을 불일치가 없다 [BR-50]

### 흐름도

재처리 실행의 판정 순서와 §4 거절/건너뜀 분기를 함께 본다.

```
[시작]
   ▼
[담당자 A request] ─▶ [책임자 B approve]
   ▼
⟨책임자 = 요청자?⟩ ─예─▶ [SELF_APPROVAL §4-H]
   │아니오(B≠A) → APPROVED → [재처리 실행]
   ▼
⟨원 배치 COMPLETED?⟩ ─아니오─▶ [BATCH_NOT_COMPLETED §4-B]
   │예
   ▼
⟨격리 목록에 있음?⟩ ─아니오─▶ [건너뜀(재지시=ALREADY_PROMOTED §4-C)]
   │예
   ▼
⟨격리 사유 = 보류?⟩ ─아니오─▶ [PROMOTE_NOT_ALLOWED §4-A]
   │예
   ▼
⟨원승인 보류 해제됨?⟩ ─아니오─▶ [INVALID_STATE §4-E]
   │예
   ▼
⟨실행자=maker · 인자 일치?⟩ ─아니오─▶ [NOT_MAKER / ARG_MISMATCH]
   │예
   ▼
[반영: capture 출금 · 한도 복원 · 부족분 미수]
   ▼
[promoteIsolated 격리→처리 · consume]  ── E2 한 커밋
   ▼
[Withdrawn→C5 · Captured→C4 · IsolatedRecordPromoted→C8]
   ▼
(끝) 원 배치 COMPLETED 유지
```

## 4. 예외 시나리오 ★

아래 표는 트리거와 종결 코드의 대응이다. 코드는 §7 계약의 정본과 같다.

| # | 트리거 | 종결 코드 | 근거 |
|---|---|---|---|
| A | 보류 외 사유 격리를 승격 시도(M2 미승인·M4 초과·M7 후속·M8 무효·**M19 기한 초과**) | `PROMOTE_NOT_ALLOWED` | **BF12** · `CaptureBatch` **INV-5** |
| B | 원 배치가 `COMPLETED`가 아님 | `BATCH_NOT_COMPLETED` | **BF11** |
| C | 이미 승격된 레코드에 재지시 | 건너뜀(재지시 = `ALREADY_PROMOTED`) | BR-50 주석 · **INV-2** · 매입 배치 SM §5 |
| D | 매입사가 같은 파일을 재전송 | 먼저 커밋한 쪽만 반영 | BR-23 · 매입 배치 SM §6 동시성 |
| E | 원승인의 보류가 아직 안 풀렸다 | 거절 (`INVALID_STATE`) | **B8** 조건 · 승인 SM **F17** · BR-50 |
| F | 보류 중 원승인이 종료 상태로 갔다(망취소 → `VOIDED` 등) | M8 자동 재분류 후 **BF12**(`PROMOTE_NOT_ALLOWED`) | `reclassifyIsolated`(B9) · 승인 SM **F12** · BR-49·50·51 |
| G | E2 커밋 실패(②만 반영된 채 갈림) | 전체 롤백 — 승인 미소비 | E2 · 매입 배치 SM §5 |
| H | A가 자기 요청을 승인 | 거절 — 상태 무관 조건 위반 | `ApprovalRequest` **INV-1** · **AF7** |
| I | 승인 전 실행 시도 | 경로 부재 — `PENDING`에서 `consume` 불가 | **AF1** |
| J | 승인 후 인자 변경 실행(다른 recordId) | `consume` 거절 — 실행 인자 ≠ 요청 인자 | **INV-3**(바꿔치기 방지) |
| K | 실행자 ≠ 요청자 / 책임자 거절 / 대기 상한 경과 | `consume` 거절(**A4**) / `REJECTED`+사유 필수(**A3**) / `EXPIRED`(**A5**, 수치 미확정) | ApprovalRequest SM |
| L | 반영 시 잔액 부족 | 정상 — 부족분이 **새 미수**(같은 커밋) | BR-20 · E2 |
| M | 승격 후 원 배치에 레코드 추가 시도(`markProcessed`·`isolate`) | `BATCH_COMPLETED` — 승격(이동)만 예외이고 추가는 금지 | **BF2** · **INV-4** |
| N | 보류가 무기한 길어져 격리가 오래 남음 | 상한 = BR-28의 보류 최대 기간(**수치 미확정**) | BR-50 예외 · BR-28 수치 |
| O | 단계 미달·전사 스코프 아님 | 거절 — 지점 스코프 운영자는 판정 축이 없어 수행 불가 | BR-55 스코프 특칙 |
| P | 부재 `fileId`·`recordId` 지목 | `NOT_FOUND` | BR-58 (L7 축 없음) |

다섯 갈래는 표에 담기지 않는 사정이 있다.

- **보류 외 사유 승격(A)** — 허용하면 **반영 안 된 레코드가 "처리됨"으로 표시**되고 건수 판정(INV-3)은 통과한다.\
  격리 사유·이력이 소멸하고 **대사는 불일치라 말하는데 배치는 처리됐다고 말한다** — 그래서 명시 거절한다.
- **이미 승격된 레코드에 재지시(C)** — ①에서 걸러진다, 격리 목록에 없으므로 **건너뛴다**(오류 아님).\
  *격리에 있다 = 미반영 · 처리에 있다 = 반영됨* 이 멱등 경계다(운영자 API 재지시는 §7의 `ALREADY_PROMOTED` 명시 거절로 간다).
- **매입사 재전송(D)** — 원 **`(기관, fileId, recordId)`** 멱등 집합을 공유하므로 **먼저 커밋한 쪽만 반영**된다.\
  같은 기관의 같은 파일일 때만 같은 집합이다(R-06).
- **보류 중 원승인 종료(F)** — 매입 배치가 사유를 **M8로 자동 재분류**하고 불일치로 적재한다(`reclassifyIsolated` — 이력 보존, UC14-2 확정).\
  이후 승격 시도는 **BF12(`PROMOTE_NOT_ALLOWED`)** 로 거절 — 반복 실패 대신 명시 거절 + 불일치 경로로 간다.
- **E2 커밋 실패(G)** — 전체 롤백, 승인 미소비.\
  ★ ②만 반영된 채 갈리면 **이중 출금 창구**가 되므로 ②③이 같은 커밋인 것이 방어선이다.

## 5. 대체 시나리오

**없음 — 격리된 보류 매입을 반영하는 정식 경로는 이것 하나다.**\
원 배치를 다시 여는 경로(`COMPLETED → PROCESSING`)는 **의도적으로 막혀 있다**(BF3 · INV-4) — 열면 이미 마감·정산된 영업일의 배치가 되살아난다.\
매입사 재전송도 대체가 되지 못한다(§4-D 멱등에서 걸러진다). *(U-6 근거)*

## 6. 인가·감사 ★

판정 순서는 UC-02 §7 선례를 따른다.\
① **단계**(요청 = 담당자 / 승인 = 책임자 — `FORBIDDEN_LEVEL`) → ② **스코프**(★ **전사 스코프 보유 여부** — 지점 스코프면 여기서 거절, BR-55 특칙) → ③ **존재**(`NOT_FOUND`) → ④ **상태·사유**(§4-A·B·E).

★ L7의 성질이 다르다.\
대상(매입 배치·레코드)에 **고객·조직 귀속이 없어** "남의 것"이라는 축 자체가 없다.\
따라서 이 UC의 `NOT_FOUND`는 **부재만** 뜻하고, 존재 비노출은 **전사 스코프 단계 판정**이 대신 담당한다(단계 미달자는 대상을 조회할 수 없다).

판정 시점은 요청·승인·실행 각 진입 1회다(AU-4).

감사 경로는 AD-2 규칙을 따른다.\
요청·승인·거절·만료 = **C8 직접 append**(AD-5·6) / 실행 성공 = **E2 커밋 내 outbox** / 거절·실패 = **독립 커밋** / 유실 = **M18**(R16).

감사 항목은 AD-8이다.\
주체·시각·대상(`fileId`·`recordId`)·스코프(전사)·종류·결과 + **사유·요청자·승인자**.\
★ `promoteIsolated`는 5조작 중 **마지막까지 `operator` 인자가 없던 조작**이었고(멀티테넌시 루프 2 F-07) 지금은 시그니처가 행위자를 받는다 — 감사가 실을 것이 있다.

승인 흐름은 UC-02 §7의 **공통 승인 계약(U-7 정본)** 을 그대로 탄다.

## 7. 계약 (계약 블록)

> **공통 승인 계약(`POST /ops/approval-requests` · `/approve` · `/reject`)의 정본은 UC-02 §7**(U-7) — **복사하지 않는다.** 여기서는 이 조작의 **인자**와 **실행 엔드포인트**만 완결한다.

#### (참조) 공통 승인 계약에 넘기는 이 조작의 인자 — 블록 본문은 **UC-02 §7**

| 항목 | 내용 |
|---|---|
| 대상 조작 | **BR-56 ③** 격리 매입 재처리 승격 지시 |
| 조작별 인자 | **`fileId`·`recordId`** · 사유 · ★ **승인 단위 = 레코드 1건 확정**(판정 **P-5** — UC14-4 닫힘) |
| 스코프 | ★ **전사**(BR-55 특칙) · `request`(담당자) · `approve`·`reject`(책임자 · `checker ≠ maker`) |
| 나머지 전 칸 | UC-02 §7 정본 그대로 — 단 **L7은 §6의 변형**을 탄다 |

승인 단위를 레코드 1건으로 확정한 근거는 커밋 경계다(UC14-4 닫힘 · P-5).\
**E2가 레코드 단위 커밋**(capture-batch §6)이고 **INV-3의 요청 인자가 단일**이라야 *"어디까지 소비됐나"* 를 승인 요청 1건이 표현한다.\
묶음 `(fileId, recordId[])`이면 인자가 집합이 되어 부분 실행·부분 실패의 정의가 새로 필요해진다.

스코프가 전사인 이유는 매입 배치에 고객·조직 귀속이 없기 때문이다(BR-55 특칙).\
그래서 나머지 칸은 UC-02 §7 정본을 그대로 쓰되 **L7만 §6의 변형**을 탄다 — 스코프 축이 없으므로 존재 비노출을 **전사 스코프 판정**이 대신한다.

#### `POST /ops/capture-batches/{fileId}/isolated-records/{recordId}/promotion` — 격리 승격 실행 (반영 + 이동 + `consume`, 한 커밋 E2)

| 항목 | 내용 |
|---|---|
| 주체 | 운영자 **담당자** · ★ **`executor = maker`**(A4 · BR-55) · ★ **전사 스코프 보유자만**(BR-55 특칙, §4-O) · 판정 시점 = 진입 1회(AU-4) |
| 요청 | 경로 ★ **`기관`·`fileId`·`recordId`**(R-06) · **승인 요청 ID** |
| 응답(성공) | 출금액 · 승인 `CAPTURED` · 복원된 한도(BR-24) · 부족분 미수(BR-20, 있으면) · 레코드 격리 → 처리 이동 · 승인 요청 `CONSUMED` · 원 배치 `COMPLETED` 유지 |
| 오류 표 ★ | **K-1 판정 순서 + §6의 4단계 변형** — 아래 산문에 전개 |
| 멱등 | ★ **승격이 곧 멱등 장치** — 원 **`(기관, fileId, recordId)`** 승계(새 키 발급 금지) |
| 예산 | 실시간 아님(관리 조작) — **E2 커밋**의 락 순서 준수(C8 `consume`은 ⑤군) |
| 감사 | 경로 = AD-2 · 항목 = AD-8 — 아래 산문에 전개 |

요청 경로에 `기관`을 함께 받는 이유는 레코드 키가 `(기관, fileId, recordId)`이기 때문이다(R-06).\
`fileId`만으로는 배치가 지목되지 않는다.\
사람 채널이라 X-6 일치 검증 대상이 아니고 **운영자가 대상 배치를 지목하는 축**이다.

성공 응답이 담는 반영 결과는 이렇게 갈린다.\
**출금액**(`Account.capture` — 계좌에서 실제 나간 돈) · 승인 `CAPTURED` · **복원된 한도**(BR-24 — ★ `at`의 영업일 ≠ `limitBasisDate`면 **복원 없음**) · **부족분 미수**(BR-20, 있으면).\
레코드는 **격리 → 처리로 이동**하고 격리 사유는 **이력 보존**되며, 승인 요청은 `CONSUMED`가 된다.\
★ **원 배치는 `COMPLETED` 그대로이고 `|처리| + |격리|`가 불변**이므로 완료 판정(INV-3)이 그대로 성립한다(승격은 추가가 아니라 이동이다).

⚠️ **BR-58 반환 범위의 특이점**: 스코프 축이 없는 조작인데 **응답은 특정 고객 계좌의 자금 결과**를 담는다.\
§9 **UC14-1**(스코프 축 어긋남) 확정 지점이다.\
**전사 유지 + 보상통제**(checker에 대상 지점 노출 · 감사 필수 기록)로 닫혔다.

**오류 표(★ K-1 판정 순서 + §6의 4단계 변형)** 는 네 단계로 흐른다.

- ① `FORBIDDEN_LEVEL`(담당자 미달).
- ② **전사 스코프 미보유**(§4-O — 지점 스코프면 여기서 거절). ★ **확정: `FORBIDDEN_LEVEL`로 접는다**(판정 **P-6** — 신설 없음).\
  단계와 전사 보유는 **둘 다 자기 속성이라 대상 조회 전에 판정**되므로 L7 누설이 없고 K-1 ⑶(신설 최소화)에 부합한다 — ★ **UC-15·18·19(전사 특칙 3조작)와 통일된 판정이다**.
- ③ `NOT_FOUND`(★ **`기관`·`fileId`·`recordId` 부재만** — §4-P · R-06. 스코프 밖이라는 경우가 존재하지 않는다).
- ④ 상태·사유 코드들:
  - `BATCH_NOT_COMPLETED`(**BF11 응답 열 정본** — 완료 전 배치에서는 격리가 확정이 아니다).
  - `PROMOTE_NOT_ALLOWED`(**BF12 응답 열 정본** — 보류 외 사유 M2·M4·M7·M8·**M19**. ★ 보류 중 원승인이 종료돼 **M8로 자동 재분류**된 건도 여기로 온다, §4-F · B9).
  - `INVALID_STATE`(★ 원승인의 **보류 미해제** — §4-E). **B8 조건**(*보류 해제됨*) 위반인데 금지 표에 응답 열이 없어 **K-1 ⑴ 공통 4종으로 접었다** — 반영을 강행해도 `capture`가 **F17**에 막힌다.
  - `NO_APPROVAL`(**AF1**).
  - `ARG_MISMATCH`(**INV-3** — 승인 후 다른 `recordId`로 실행, §4-J).
  - 승인 요청 종료 상태(**AF4·AF5·AF6** → ★ **`ALREADY_REJECTED`·`ALREADY_CONSUMED`·`ALREADY_EXPIRED`** — 통합1 원칙의 실행 시점 동일 적용, UC-13과 한 판정).
  - ★ **`NOT_MAKER`**(§4-K · A4 실행자 ≠ maker. **확정: 통합2 — 신설**. 정본 착지 = **UC-02 §7 실행 블록**(BR-56 ①~③ 공통 — 여기서는 인용만) · UC-13과 한 판정).
  - ★ **`ALREADY_PROMOTED`**(§4-C — 이미 승격된 레코드에 재지시. **확정: 통합1(CDS3 소급) — 명시 거절**) — 아래에 따로 전개.

`ALREADY_PROMOTED`가 무음 성공(no-op)이 아니라 **명시 거절**인 이유는 채널이 판정을 가르기 때문이다.\
✓ **정본 반영됨** — capture-batch SM **v0.6 B8 채널 주석**: *BF8의 무음 건너뜀은 **배치 재개 전용**이고, 운영자 API 재지시는 명시 거절*(같은 판정을 채널이 가른다 — C-2 경계와 같은 갈림).\
no-op 성공이면 운영자가 *"내 지시로 방금 반영됐다"* 고 오인하고(CF9 논거) 승인 요청 소비 여부도 갈린다.\
⚠️ **멱등 장치 자체는 그대로다** — 반영이 두 번 일어나지 않는 것은 격리/처리 집합의 원자 이동이 보장한다.\
⚠️ **거절이므로 승인 요청은 소비되지 않는다** — 트랜잭션이 롤백되고 `APPROVED`가 잔존한다(**UC-13 `ALREADY_LIFTED`와 동일**한 귀결이며, 그 `APPROVED`의 재사용 여부는 AR2 = UC13-4에 묶인다).

멱등의 정본은 이렇다.\
★ **승격이 곧 멱등 장치다** — 키는 원 ★ **`(기관, fileId, recordId)`**(R-06 — `fileId`는 매입사가 채번하므로 유일성 스코프는 **발신 기관**이다. 배치 INV-1) 를 **승계**한다(**새 키 발급 금지 — 이중 출금**).\
경계 = *격리에 있다 = 미반영 · 처리에 있다 = 반영됨*(B8의 원자 이동이 그 경계를 넘긴다).\
매입사 재전송도 **같은 멱등 집합**을 보므로 먼저 커밋한 쪽만 반영된다(§4-D).\
승인 요청 쪽 멱등은 별개다 — **1건 1회 소비**(INV-2).

예산은 실시간이 아니지만 락 순서를 지킨다.\
**E2 커밋**(승인·계좌·카드·매입 배치·부족 시 미수 + C8 승인 요청)의 **락 순서**를 지킨다(C8 `consume`은 ⑤군).\
★ ②(반영)와 ③(승격)이 **갈리면 이중 출금 창구**가 되므로 같은 커밋인 것이 방어선이다(§4-G).

감사 경로(AD-2)는 이렇게 갈린다.\
**실행 성공 → E2 커밋 내 outbox** · **거절·실패 → 독립 커밋** · **요청·승인·거절·만료 → C8 직접 append**(AD-5·AD-6) · 조회 아님(AD-4 해당 없음) · 유실 = **M18**(R16).\
항목(AD-8) = `sourceRef`(AD-3) · 주체 · 시각 · 대상(★ **`기관`·`fileId`·`recordId`** — R-06) · ★ **스코프 = 판정에 실제 쓰인 값 = 전사**(K-4 — 조직 축 값이 아니라 *전사*가 판정에 쓰인 값이다) · 종류 · 결과 + **사유·요청자·승인자**(BR-56 3항).\
★ `promoteIsolated`는 5조작 중 **마지막까지 `operator` 인자가 없던 조작**이었고(루프 2 F-07) 지금은 시그니처가 행위자를 받는다 — 감사가 실을 것이 있다.

#### 이벤트 `IsolatedRecordPromoted` — `promoteIsolated()` 성공 시 (기존 — `capture-batch.md` §4가 정본. 축·버전은 이 계약이 최초 설계)

| 항목 | 내용 |
|---|---|
| payload | `fileId` · `recordId` · **원승인 ID** · **이전 격리 사유 = 보류**(이력 보존) · ★ **운영자(행위자 포함)** · **축 = `accountId`** · ★ **`ownerId` 비포함** |
| 구독 | **운영(C8)** — 감사 수집은 **감사 전용 outbox**(AD-2) · ★ **원장(C5) 구독이 아니다** |
| 멱등 키 | 수신측 유일 제약 = **`sourceRef` = `sourceEventId`**(AD-3 — at-least-once) |
| 스키마 버전 | **`schemaVersion: 1`**(K-3) · 의미 필드 추가 = 새 타입(S-6a) |

payload 필드 넷은 근거가 각각 다르다.\
**원승인 ID** — 격리 레코드가 isolate 매칭 시점부터 보유한다(capture-batch §4 B9 주석).\
**운영자(행위자 포함)** — 구독이 운영인 **운영자 전용 이벤트**(AD-7 ① · 색인 §3 *포함 ✓* 확정).\
**축 = `accountId`** — 기존 파티션 축 유지(K-4). 매입 배치 자체에는 계좌 귀속이 없지만 **같은 E2 커밋의 `Account.capture`가 그 값을 안다**(이 시점이 최초 설계 — IS-5).\
★ **`ownerId` 비포함** — K-4 보정 확정, **이벤트 payload 전면 비포함**(매입 배치가 IS-1 6종이 아니라는 이유에 더해, IS-1 6종 자체가 **저장 모델** 대상이다).

구독은 운영(C8) 하나이고 자금 기표는 다른 이벤트가 나른다.\
자금 기표는 **`Withdrawn`(→ C5 원장)** 이 나르고, **`Captured`는 C4 정산**으로 간다(F-04 정정).

#### 이벤트 `Captured` · `Withdrawn` — 반영 단계 ②에서 발행 (기존 — `authorization.md`·`account.md`가 정본. **계약 확인 블록**)

| 항목 | 내용 |
|---|---|
| payload | `Withdrawn` = `accountId` · **`withdrawnAmount`**(계좌에서 실제 나간 돈 — 매입액이 아니다) · 영업일 / `Captured` = 승인 정본. ★ **행위자 비포함** · 축 = `accountId` · ★ **`ownerId` 비포함** |
| 구독 | ★ **둘의 구독자가 갈린다** — **`Withdrawn` = C5 원장**(R6) · **`Captured` = C4 정산**(**R8**) |
| 멱등 키 | C5(`Withdrawn`) = **전표 INV-8(`sourceEvent`)** · C4(`Captured`) = **`sourceEventId`**(ADR-014 §2.4) |
| 스키마 버전 | **`schemaVersion: 1`**(K-3) — 계약 정본 소관은 **UC-10** |

payload가 행위자를 비포함하는 이유는 원장이 자금 언어이기 때문이다.\
★ **행위자 비포함**(자금 이벤트 — AD-7 ② · 색인 §3 *비포함 확정*) — **원장은 자금 언어다**. 행위자는 E2 커밋의 **감사 outbox**가 나른다.\
✓ 정본과 일치 · 축 = `accountId` · ★ **`ownerId` 비포함**(K-4 보정 확정 — 전면 비포함. 자금 이벤트는 **원장 언어**다 — IS-5).

구독자가 둘로 갈리는 것은 정본대로다(2026-08-06 리뷰 **F-04** 정정: 이전 판은 둘 다 C5로 적었다).\
**`Withdrawn` = C5 원장**(R6 ACL 번역 — 계좌에서 실제 나간 자금의 기표를 소유한다).\
**`Captured` = C4 정산**(**R8** — *정산이 매입 결과를 집계한다*). 승인 `Captured`는 상태 변화를 알릴 뿐 **자금 분개를 소유하지 않으므로** 원장 번역 입력이 아니다(컨텍스트 맵 §8 주석).

멱등 키는 수신측마다 형태가 다르다.\
수신측 C5(`Withdrawn`) = **전표 INV-8(`sourceEvent`)** — UC-02 `DepositReversed`와 같은 형태.\
수신측 C4(`Captured`) = **`sourceEventId`**(ADR-014 §2.4 — UC-11 `Refunded`의 두 수신측 표기와 같은 형태).\
★ 이 두 이벤트의 계약 정본 소관은 **UC-10**(매입 파일 청산)이며 이 블록은 **승격 경로에서 같은 이벤트가 나온다는 확인**이다 — 승격은 새 이벤트 타입을 만들지 않는다.
