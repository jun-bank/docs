# UC-01. 카드 결제를 승인받는다

- 작성일: 2026-08-05 · 상태: **확정**(파일럿 — 듀얼 1패스 반영)
- 액터: **매입사/VAN** — 시스템 주체(R1 전문 경로). 카드소지자의 결제를 대리한다 — 목표의 주인은 소지자, 요청의 주체는 매입사다.
- 트랜잭션 경계: **E1** — 승인·계좌·카드·멱등·취소예약이 한 커밋.
- 권한: 시스템 주체(BR-54 예외 목록 밖 — 단건 카드 지목이라 횡단이 아니다). 운영자·고객 단계와 무관.
- 관련 규칙: BR-01·02·04·05·13·15·17·22·36·44·45·54 (참조만).

> 이 문서를 다 읽으면 **승인 한 건이 어떤 검증을 거쳐 성립하거나 거절되는지, 그리고 각 거절이 왜 사유를 구분하는지**를 설명할 수 있어야 한다.

## 1. 목표

매입사가 카드 결제 요청 전문에 대해 **p99 3초 안에 승인번호 또는 사유가 구분된 거절**을 받는다.

## 2. 사전·사후 조건

시작 조건은 하나다.\
전문이 R1 ACL 검증(포맷·상관 식별자 존재 — BR-17)을 통과했다.

끝 상태는 셋으로 갈린다.

- **성공** — 승인이 `AUTHORIZED`로 서고, 홀딩이 잡히고, 카드·계좌 두 층의 한도 사용액이 오르고, 승인번호가 발번된다.\
  이 전부가 **한 커밋(E1)**이며, 감사 outbox 행도 같은 커밋에 있다(AD-2).
- **거절** — 자금 상태는 **변하지 않는다**.\
  사유 코드를 응답하고, 거절 사실은 감사에 남는다(BR-57 — 독립 커밋).
- **실패(응답 유실 포함)** — 성립했으면 성립한 대로 남는다.\
  매입사의 망취소(BR-13·22)가 정합을 회복한다(이 UC 범위 밖 — §4-G).

### 동작 구조

누가 요청을 보내고, 코어 승인 UC가 어떤 저장소를 거쳐 한 커밋(E1)으로 끝내는지 보여준다.

```
[매입사/VAN]
   │ AUTH-REQ 전문
   ▼
[R1 ACL 어댑터]  (경로 식별자 부여 · 포맷 검증 BR-17)
   │
   ▼
[코어: 승인 UC]
   ├─멱등 검사──▶ [멱등 원장] find/record (BR-02)
   ├─취소예약 조회──▶ [취소예약 원장] consume (BR-22)
   ├─카드 확인──▶ [카드] assertUsable (BR-15)
   └─홀딩·한도──▶ [계좌 원장] hold·useLimit (BR-04·05·44)
   │
   │ E1 — 승인·홀딩·한도·멱등·감사를 한 커밋
   ▼
[감사 outbox] (AD-2)   ──응답──▶ [매입사]  (승인번호 / 거절 사유)
```

## 3. 주요 성공 시나리오

1. 전문 수신 → R1 ACL이 도메인 언어로 번역 + **경로 식별자 부여** [BR-54 시스템 주체]
2. 멱등 조회 `find(correlationId, 승인)` — 기존 결과 있으면 §4-A로 [BR-02]
3. 유효한 취소 예약 조회 — 있으면 §4-B로 [BR-22]
4. 카드 `assertUsable(now)` — 상태·유효기간·정지 [BR-15]
5. 가용잔액(BR-04) · 카드 1회/1일 한도(BR-05) · 계좌 한도(BR-44) · 미수 차단(BR-45) 판정
6. `authorize` — 홀딩 생성 · 두 층 한도 사용 · 승인번호 발번 · 멱등 기록 [승인 T1 · E1 같은 커밋]
7. 승인 응답 송신 (내부 deadline 2.5초 — 0.5초는 응답 예약분) [ADR-013 T-11]

### 흐름도

주요 성공 흐름(§3)에 예외(§4 A~H) 분기와 그 거절 코드를 얹었다.

```
[시작: AUTH-REQ 수신]
   │
   ▼
⟨멱등키 기존 결과?⟩ ──있음(지문 동일)──▶ [최초 결과 재반환] ──▶ (끝)
   │ 없음          └─지문 상이──▶ [거절: IDEMPOTENCY_CONFLICT] (§4-A)
   ▼
⟨유효한 취소 예약?⟩ ──있음──▶ [VOIDED 생성 → VOIDED_BY_RESERVATION] (§4-B)
   │ 없음
   ▼
⟨카드 사용 가능?⟩ ──아니오──▶ [거절: CARD_SUSPENDED/EXPIRED/TERMINATED] (§4-C)
   │ 예          └─미등록──▶ [거절: DECLINED_UNREGISTERED] (§4-D)
   ▼
⟨가용잔액·한도 충분?⟩ ──아니오──▶ [거절: DECLINED_FUNDS / DECLINED_LIMIT] (§4-E)
   │ 예              └─미수 차단──▶ [거절: DECLINED_RECEIVABLE_BLOCK] (§4-F)
   ▼
[authorize: 홀딩·한도 사용·승인번호·멱등 기록 — E1 한 커밋]
   │
   ▼
[승인 응답 송신 (내부 deadline 2.5초)] ──▶ (끝)

[락 충돌·deadline 초과] → 3회 재시도 후 [거절: TIMEOUT_RETRYABLE] (§4-H)
[응답 유실(성립 후)] → 매입사 망취소 수신 → 성립분 복원 (§4-G, UC 범위 밖)
```

## 4. 예외 — 여덟 갈래 ★

승인은 "자금이 움직이는 조작은 기본이 거절"이라, 예외가 성공 경로만큼 중요하다.\
각 갈래는 사유를 구분해 응답한다 — 뭉뚱그리면 운영자가 원인을 못 찾기 때문이다(BR-36·15).

아래 표는 트리거와 응답 코드의 대응이다. 코드는 §7 계약의 정본과 같다.

| 갈래 | 트리거 | 응답 코드 | 근거 |
|---|---|---|---|
| A | 같은 멱등키 · 지문 동일 | (최초 결과 재반환 — 무변화) | BR-02 · 멱등 INV-2 |
| A | 같은 멱등키 · 지문 상이 | `IDEMPOTENCY_CONFLICT` | BR-02 |
| B | 유효한 취소 예약 존재 | `VOIDED_BY_RESERVATION` | BR-22 · 승인 T3 |
| C | 카드 사용 불가 | `CARD_SUSPENDED / _EXPIRED / _TERMINATED` | BR-15 · 승인 T2 |
| D | 미등록 카드번호 | `DECLINED_UNREGISTERED` | BR-36 |
| E | 가용잔액·한도 부족 | `DECLINED_FUNDS / _LIMIT` | BR-04·05·44 |
| F | 미결 미수 계좌 | `DECLINED_RECEIVABLE_BLOCK` | BR-45 |
| H | 락 충돌·내부 deadline 초과 | `TIMEOUT_RETRYABLE` (3회 재시도 후) | ADR-012 W-10 · ADR-013 T-11 |

세 갈래는 표에 담기지 않는 사정이 있다.

- **취소 예약 선도착(B)** — `createVoidedByTombstone`이 홀딩·한도를 **건드리지 않고** `VOIDED` 승인을 만들고 예약을 소비한다.\
  성립한 자금이 없다(승인 T3).
- **미수 차단(F)** — 미결 미수가 있는 계좌는 거절하되, **운영자가 차단을 해제한 계좌는 통과**한다.\
  해제는 UC-02 계열 승인 조작이다(BR-56 ②).
- **응답 유실(G)** — 성립 후 응답이 유실되면 매입사가 타임아웃으로 망취소를 보낸다.\
  성립분이 복원되거나 취소 예약이 된다(BR-13·22 — 이 UC 범위 밖).

## 5. 대체 시나리오

없다.\
승인의 목표 달성 경로는 §3 하나뿐이고, 부분 승인·할부는 제품 정의 범위 밖이다(U-6 근거).

## 6. 인가·감사 ★

주체는 R1 ACL 진입 시 한 번 판정한다(AU-3·AU-4) — 시스템 주체에 경로 식별자를 붙인다.\
소유자 필터는 없다(시스템 주체 — AU-2).\
카드→계좌 결합은 IDOR 표면이 아니다 — 전문은 카드번호만 지목하고, 계좌는 시스템이 카드 참조로 유도한다(Card.AccountId — CM1).

거절 사유 구분은 해석 예외가 아니라 정본이다.\
BR-36·BR-15가 "뭉뚱그리면 운영자가 원인을 알 수 없다"며 사유 구분을 명시 요구한다.\
BR-58의 L7(존재 비노출)은 사람 주체 채널(고객·운영자 API)을 대상으로 하므로, 매입사 전문 채널과는 역할이 갈린다(02 양식 C-2 조항).

감사는 경로에 따라 커밋이 다르다.\
성공은 E1 커밋 안의 감사 outbox(AD-2 — 주체·경로·대상 카드/계좌·결과).\
거절은 독립 커밋이다 — 롤백에 쓸리지 않게 한다.\
조작 감사 유실은 outbox 멱등이, 거절 기록 유실은 M18이 지킨다.

## 7. 계약

> 물리 규격(고정길이 레이아웃)은 [`interfaces/auth-message.md`](../interfaces/auth-message.md)에 있다.\
> 이 §7이 **의미의 정본**, 규격은 표면이다(2026-08-06 신설).

**전문 `AUTH-REQ`** — API가 아니라 R1 ACL 인터페이스이나, 블록 형식은 같게 적용한다.

| 항목 | 내용 |
|---|---|
| 주체 | 시스템 — 매입사 전문 경로(ACL이 경로 식별자 부여) |
| 요청 | 카드번호 · 금액(BR-07) · 가맹점 ID · 상관 식별자(매입사 생성 — BR-17) |
| 응답(성공) | 승인번호 · 승인 금액 |
| 멱등 키 | `(기관, 상관 식별자, 승인)` — 최초 결과 반환(BR-02) |
| 예산 | 외부 p99 3초 · 내부 deadline 2.5초(T-11) |
| 감사 | 주체(경로) · 카드/계좌 · 결과 · 거절 사유(AD-8) |

오류 코드는 §4 표가 정본이다. 두 가지만 표 밖에서 따로 설명한다.

- **제3형태 `VOIDED_BY_RESERVATION`** — 승인도 일반 거절도 아니다.\
  응답은 **응답 코드 + 승인번호 발번 + 금액 0**이다(규격 §2와 동형).\
  승인 레코드가 `VOIDED` 상태로 실재하므로, 매입사가 대사·조회로 그 건을 지목할 연결 고리(BR-17 ②)가 필요하다.\
  홀딩이 잡히지 않아 성립한 자금은 없다.
- **멱등의 기관 축** — 상관 식별자는 매입사가 채번하므로 유일성 스코프는 **발신 기관**이다(R-06 · 멱등 INV-1).\
  기관은 ACL이 인증한 발신 기관이며, 전문 본문의 X-6 기관 코드와 일치해야 한다(불일치 = `ARG_MISMATCH`).

**이벤트 `HoldPlaced`** — 정본은 account.md §6, 여기선 계약 확인만.

| 항목 | 내용 |
|---|---|
| payload | accountId · 금액 — 행위자 없음(자금 이벤트 AD-7) |
| 구독 | 없음(같은 트랜잭션) |
| 멱등 | E1 커밋 원자성이 담보 |
| 스키마 | `schemaVersion: 1`(K-3) |

축 필드는 판정하지 않는다.\
같은 트랜잭션 내부 이벤트라 구독자가 없어 계약 발행 대상이 아니다(발행되는 자금 이벤트의 축은 Phase 4 계약 전수 IS-5에서).
