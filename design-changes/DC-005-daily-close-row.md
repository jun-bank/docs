# DC-005. 마감 잔액을 **필드가 아니라 행**으로

- 일자: 2026-08-05
- 발동: **Phase 3 마감 듀얼 리뷰** — Opus C-1 · C-2 (치명)
- 상태: **반영 완료**
- 관련: **ADR-011**(lazy close) · **M12 · M14** · `account.md` · `receivable.md` · **DC-001**

---

## 1. 무엇이 깨졌나

### C-1 — `closedBalance`가 하루 어긋난다

```
D-1 마감   balance 100,000 · closedBalance 100,000 · lastClosed D-1

D일 첫 거래 (귀속 D)
  D > D-1 ?  참
  closedBalance ← balance = 100,000      ← D-1 마감 잔액. 맞다
  lastClosedBusinessDate ← D             ← ★ 여기

  lastClosed 는 D 인데 closedBalance 는 D-1 것이다
```

**필드 정의**(*"그 영업일 마감 시점 잔액"*)와 **알고리즘**(직전 영업일을 확정)이 **정확히 하루 어긋난다.**

D일 마감 후 대사(M12):

| 계좌 | `lastClosed < D` | 무엇을 쓰나 | 결과 |
|---|---|---|---|
| ★ **그날 거래한 계좌** | `D < D` 거짓 | `closedBalance` = **D-1 잔액** | ❌ **허위 불일치** |
| 거래 없던 계좌 | `D-1 < D` 참 | `balance` | ✅ |

> ★ **T2를 고치려다 범위를 키웠다.** T2는 마감 후 **20분 창**(96,000건)이었는데
> 이것은 **그날 거래한 전 계좌**다.

### C-2 — M14에는 T2가 그대로 남았다

ADR-011 §5가 미수 대사를 *"실시간 값으로"* 처리하며 근거를 이렇게 적었다:

> *"미수는 `incurredBusinessDate`를 이미 든다"*

**그 문장이 틀렸다.** `incurredBusinessDate`는 **생긴 날**만 고정하고,
`recoveredAmount`·`writtenOffAmount`는 **그 뒤로도 변한다**(INV-3).

```
D  14:00  미수 R1 발생 20,000 (incurred = D)
          전표 차) 미수금 20,000 / 대) 매입사 미지급금 20,000
D  23:00  마감 — 미수금 보조부(D일) = 20,000
D+1 00:10 입금 20,000 → FIFO 회수 → outstanding() = 0
D+1 00:20 ★ D일 대사 (QS-04 마감 후 1시간 이내)
          좌변 Σ outstanding(incurred ≤ D) = 0
          우변 미수금 보조부 D일           = 20,000
          → M14 허위 불일치 20,000
```

## 2. 진짜 원인 — 단일 필드는 **하루만** 든다

★ **lazy close의 통찰은 옳았다.** *"마감을 시각이 아니라 사건으로"* — 그래서 확정이
자금 조작과 **같은 트랜잭션** 안에서 일어나고, T2(마감 후 20분 창)가 사라진다.

**틀린 것은 그것을 담는 그릇이다.**

```
closedBalance 는 값을 하나만 든다
  → D일 마감값을 쓰면 D-1 것이 사라진다
  → D일 마감값은 D+1 첫 거래가 와야 확정된다
  → 그런데 대사는 D일 마감 직후 돈다
  → ★ 구조적으로 못 맞춘다
```

**판정을 `<` → `≤` 로 바꿔도 안 된다** — 그러면 D+1 거래가 섞인 `balance`를 쓰게 돼
**원래 T2로 돌아간다.**

> ★ **같은 형태를 이번 리뷰에서만 세 번 봤다.**
>
> | 무엇 | 답 |
> |---|---|
> | `CaptureBatch` 처리 집합 | **W-14** — `(fileId, recordSeq)` 별도 행 |
> | outbox 완료 여부 | **O-15** — 상태 4종 |
> | ★ `closedBalance` | **이 문서** — 영업일별 행 |
>
> 그리고 **DC-001이 같은 결론**이었다 — *합계를 애그리게이트가 들지 마라.*
> **네 번째다.**

## 3. 결정 — `AccountDailyClose` 행

```
AccountDailyClose            Account 애그리게이트 안의 엔티티 (C1 소유)
  accountId
  businessDate               ← 키
  closingBalance             ★ 그 영업일 종료 시점 잔액
  closingReceivable          ★ 그 영업일 종료 시점 미수 잔여 합계
```

### 언제 갱신하나

**자금을 바꾸는 모든 조작이 같은 트랜잭션에서** 그 거래의 **귀속 영업일 행**을 upsert 한다.

```
거래 귀속 영업일 = B (BR-14)
  행(accountId, B) 이 없으면
      가장 최근 (businessDate ≤ B) 행의 값으로 만들고 (없으면 0)
  조작 반영 후
      closingBalance    ← balance
      closingReceivable ← closingReceivable + Δ(발생 +amount · 회수 −recovered · 소멸 −writtenOff)
```

### 대사는 무엇을 읽나

```
M12 좌변  = 가장 최근 (businessDate ≤ 대상 영업일) 행의 closingBalance
M14 좌변  = 〃                                          closingReceivable
행이 없으면 = 0  (그 영업일까지 거래가 없었다)
```

### 왜 이것인가

| 근거 | |
|---|---|
| ★ **ADR-011의 통찰을 유지**한다 — 확정이 자금 조작과 같은 트랜잭션 안에서 일어난다 |
| ★ **D일 행과 D+1 행이 따로 선다** — D+1 거래가 D일 값을 덮지 않는다 |
| **거래 없던 계좌**는 행이 없고, 대사가 *"가장 최근 ≤ D"* 를 읽으므로 자동으로 맞는다 |
| **DS2가 유지된다** — 기준점이 자기 자신을 검증하지 못하는 문제는 *같은 트랜잭션 확정*이 없앤다 |
| **C-2도 같이 닫힌다** — 미수도 같은 행에 산다 |

### 왜 `DailySnapshot` 부활이 아닌가

| | 폐기된 `DailySnapshot` | ★ `AccountDailyClose` |
|---|---|---|
| 언제 만드나 | **마감 시각에 배치로** | **자금 조작과 같은 트랜잭션** |
| 무엇이 문제였나 | ★ **T2 — 20분 창에 D+1 거래가 섞인다** | 섞일 창이 없다 |
| 무엇을 검증하나 | 자기 자신 (DS2) | 조작이 확정 |

**폐기 이유였던 T2·DS2가 되살아나지 않는다.**

### ③ 의식적 예외 4칸 (DC-001)

| 칸 | |
|---|---|
| **등식** | `closingBalance[B]` = 귀속 영업일 ≤ B 인 마지막 조작 직후의 `balance` |
| **정본** | 자금 조작 자체 (`Account.balance` · `Receivable.outstanding()`) |
| **경계** | ★ **E1~E5와 같은 트랜잭션** — 조작과 갱신이 갈릴 수 없다 |
| **탐지** | ★ **M12 · M14** — 이 값이 틀리면 원장과 어긋난다 |

## 5. 이 판단이 틀리면

| 신호 | 무엇을 뜻하나 | 그때 |
|---|---|---|
| 행 갱신이 **계좌 경합을 키운다** | 같은 계좌의 같은 날 행이 직렬화 지점 | 계좌 행과 **같은 락**이므로 추가 경합은 없어야 한다 — 실측으로 확인 |
| 행이 **너무 많이 쌓인다** | 계좌 × 영업일 | 보존 기간을 정한다(원장 보조부와 같은 기간) |
| **M12·M14가 여전히 허위**를 낸다 | 원인이 다른 데 있다 | 대사 시점·귀속 영업일 규칙(BR-14)부터 다시 본다 |
