# DC-006. 마감 잔액을 **스냅샷이 아니라 증분**으로

- 일자: 2026-08-05
- 발동: ★ **정지 규칙**(core §3) — 같은 자리가 **세 번** 깨졌다
- 상태: **반영 완료**
- 대체: **DC-005**(부분 — 행으로 나눈 판단은 유지, 담는 값이 바뀐다)
- 관련: **ADR-011** · **M12 · M14** · `account.md` · `receivable.md` · **DC-001** · **ADR-003**

---

## 1. 왜 토대를 바꾸나 — 세 번 깨졌다

| # | 시도 | 어떻게 깨졌나 | 언제 |
|---|---|---|---|
| ① | **`DailySnapshot`** — 마감 시각에 배치로 뜬다 | **T2** — 마감 후 20분 창에 D+1 거래가 섞인다 (80 TPS × 20분 = **96,000건 허위**) | Phase 3 리뷰 |
| ② | **`closedBalance`** — 계좌가 단일 필드로 든다 | **정확히 하루 어긋난다** — 그날 거래한 **전 계좌**가 허위 | Phase 3 마감 리뷰 C-1 |
| ③ | **`AccountDailyClose`** — 영업일별 행 + `← balance` 절대값 복사 | ★ **역순 귀속에서 깨진다** — 아래 | Phase 3 마감 재리뷰 |

```
D1 마감 100
D2 입금 +20            → D2 행 120
D3 에 늦은 D1 매입 −30 도착   (BR-06: 매입 파일은 D+1 09:00 처리 — 정상 경로다)

closingBalance ← balance  →  D1 행에 현재 잔액 90 을 복사
  올바른 값   D1 = 70 · D2 = 90
  실제 값     D1 = 90 · D2 = 120
  → D1 은 +20, D2 는 +30 틀린다
```

> ★ **소급 보정(`businessDate > B` 인 행에 Δ 전파)도 패치다.**
> **네 번째 패치를 하지 않는다** — core §3: *"같은 결함을 2회+ 고쳐도 또 깨지면
> **틀린 토대를 다듬는 중**이다. polish 말고 설계를 되돌려 재슬라이스하라."*

---

## 2. 진짜 원인

```
balance 는 시간축이 없다.
  → 시간축 있는 것으로 만들려는 모든 시도가
    "현재값을 어느 시점에 복사할 것인가"에서 깨진다
```

**세 번 다 같은 자리에서 깨졌다** — ①은 *복사 시각*, ②는 *복사 대상 날짜*, ③은 *복사 시점의 값*.
**복사가 있는 한 네 번째가 온다.**

### 원장은 왜 안 깨지나

**전표가 append-only이고 각 전표에 귀속 영업일이 있다.**

```
D일 보조부 잔액 = Σ(전표[귀속 영업일 ≤ D])
```

★ **구성적**이다. 복사 시점이라는 개념 자체가 없다.
**ADR-003이 원장만 append-only로 둔 것이 여기서 값을 한다** — 그리고 계좌가 그 성질을 못 받아 세 번 깨졌다.

---

## 3. 결정 — 계좌도 **이동을 적는다**

```
AccountDailyMovement            Account 애그리게이트 안의 엔티티 (C1 소유)
  accountId
  businessDate                  ← 키 (거래의 귀속 영업일 · BR-14)
  netAmount                     ★ 그 영업일 자금 이동의 부호 있는 합
  receivableDelta               ★ 그 영업일 미수 증감의 합
```

### 언제 갱신하나

**자금을 바꾸는 모든 조작이 같은 트랜잭션에서** 그 거래의 **귀속 영업일 행에 더한다.**

```
거래 귀속 영업일 = B (BR-14)
  netAmount[B]      += 조작 금액 (입금 +, 출금 −)
  receivableDelta[B] += 발생 +amount · 회수 −recovered · 소멸 −writtenOff
```

★ **더하기뿐이다.** 읽고-판단하고-복사하는 단계가 없다.

### 대사는 무엇을 읽나

```
M12 좌변 = anchor.balance              + Σ(netAmount      [anchor < bd ≤ D])
M14 좌변 = anchor.receivableOutstanding + Σ(receivableDelta[anchor < bd ≤ D])
```

### ★ 세 번 깨진 것이 전부 사라진다

| 깨졌던 것 | 증분이면 |
|---|---|
| **T2** 마감 창에 D+1 이 섞인다 | 귀속일로 갈리므로 ★ **섞일 수 없다** |
| **하루 어긋남** | ★ **복사가 없다** |
| **역순 귀속** | ★ **더하기는 순서가 무관**하다(교환법칙). 소급 보정 불필요 |
| 플래그 off 구간 누락 | 나중에 그 행에 더하면 **복구된다** |
| **DS2** 기준점이 자기 자신을 검증 못 한다 | 기준점이 **없어도 계산된다**(아래) |

> ★ **M12가 좌우변을 같은 방식으로 계산하게 된다** — 둘 다 `Σ(이동[귀속일 ≤ D])`.
> **그런데 경로는 다르다** — 계좌 쪽은 **조작이 직접 쓰고**, 원장 쪽은 **outbox 이벤트로 생성**된다.
> **대사의 독립성은 유지된다.**

### 기준점(anchor)은 성능 최적화일 뿐이다 ★

```
AccountBalanceAnchor(accountId, businessDate, balance, receivableOutstanding)
```

| # | 규칙 | 왜 |
|---|---|---|
| **A-1** | anchor는 ★ **늦은 거래 상한(BR-06 D+1)을 훨씬 넘긴 과거 구간**에만 만든다 (예: 전월 말을 이번 달 중순에) | 그 구간에는 새 거래가 안 온다 |
| **A-2** | ★ **anchor 없이도 계산할 수 있다** — 처음부터 Σ 하면 된다 | 그래서 **T2·DS2가 구조적으로 못 생긴다** |
| **A-3** | anchor 검증 = `anchor.balance == Σ(처음부터 anchor일까지)` | **자기 자신이 아니라 이동이 검증한다** |
| **A-4** | anchor가 틀려도 **Σ가 정본**이다 | anchor는 **캐시**이지 사실이 아니다 |

> ★ **A-2가 이 설계의 핵심이다.** ①~③이 깨진 이유는 **기준점이 없으면 계산이 불가능**했기 때문이고,
> 그래서 기준점을 어떻게든 만들려다 매번 다른 데서 깨졌다.
> **기준점이 선택적이면 그 실패 모드가 통째로 사라진다.**

### ③ 의식적 예외 4칸 (DC-001)

| 칸 | |
|---|---|
| **등식** | `netAmount[B]` = Σ(귀속 영업일 = B 인 이 계좌 자금 조작의 부호 있는 금액)<br/>`receivableDelta[B]` = 〃 미수 증감 |
| **정본** | ★ **자금 조작 자체.** 계좌에 조작 이력이 없으므로 이 행이 **그 이력을 대신한다** |
| **경계** | ★ **E1~E5와 같은 트랜잭션** — 조작과 기록이 갈릴 수 없다 |
| **탐지** | ★ **M12 · M14** — 이 값이 틀리면 원장과 어긋난다 |

> ⚠️ **이것도 합계 필드다.** 그런데 **원장 보조부가 정확히 같은 형태**이고,
> DC-001이 허용한 ③ 의식적 예외의 조건(등식·정본·경계·탐지)을 **네 칸 다 채운다.**
> 차이는 **누적값이 아니라 이동값**이라는 것이다 — ★ **이동은 나중에 더해도 맞다.**

## 5. 이 판단이 틀리면

| 신호 | 무엇을 뜻하나 | 그때 |
|---|---|---|
| **Σ 범위가 커져 대사가 QS-04(1시간)를 못 지킨다** | anchor 주기가 길다 | anchor를 자주 만든다 — **A-4로 안전하다** |
| 같은 계좌·같은 날 행에 **경합이 몰린다** | += 가 직렬화 지점 | 계좌 행과 **같은 락**이다(ADR-012 W-17). 실측 확인 |
| ★ **M12·M14가 또 허위를 낸다** | ★ **네 번째다 — 이 문서도 틀렸다** | **패치하지 말고** 대사 시점·BR-14를 다시 본다 |
