# 도메인 용어사전 (Ubiquitous Language) — 초안 v0.1

- 작성일: 2026-08-02
- 상태: **초안 — 사용자 검토 대기**
- **이 문서가 용어의 정본이다.** 다른 문서·코드·API·이벤트명은 여기 정의된 용어만 쓴다. 새 용어가 필요하면 여기에 먼저 추가한다.

> **왜 용어사전이 먼저인가**
> 현재 코드베이스에서 `Money` 값 객체가 account / card / payment / ledger / transaction / transfer **6곳에 각각 복붙**되어 있다. 금액이라는 하나의 개념에 6개의 정의가 있다는 뜻이다. 이는 코드 문제가 아니라 **용어가 합의되지 않은 채 구현이 시작된 결과**다.

## 1. 참여자

| 용어 | 코드명 | 정의 |
|---|---|---|
| **카드소지자** | `Cardholder` | jun-bank가 발급한 카드를 보유한 고객. 시스템 내 `User`와 동일 인물이지만 **결제 맥락에서의 역할명**이다 |
| **가맹점** | `Merchant` | 카드를 결제수단으로 받는 상점. jun-bank와 직접 계약 관계가 **없다** (매입사와 계약) |
| **발급사** | `Issuer` | 카드를 발급하고 **승인 여부를 판단**하며 고객에게 대금을 청구하는 주체. **= jun-bank (우리)** |
| **매입사** | `Acquirer` | 가맹점과 계약해 거래를 매입하고 가맹점에 대금을 지급하는 주체. **모의 서비스로 구축** |
| **VAN** | `Van` | 가맹점 단말과 카드사 사이의 전문 중계망. 본 프로젝트에서는 **매입사에 통합**한다 |
| **카드망/브랜드사** | — | VISA·Mastercard 등 국제 브랜드. **범위 밖** |

> **결정 필요 #G1**: 매입사와 VAN을 하나의 모의 서비스로 합칠지, 두 서비스로 나눌지. 합치면 단순하고, 나누면 "중계 구간이 하나 더 있어서 타임아웃 지점이 늘어나는" 현실이 재현된다.

## 2. 거래 라이프사이클 ⚠️

결제는 **한 번에 끝나지 않는다.** 이 순서를 이해하는 것이 결제 도메인의 출발점이다.

```
 승인(Authorization)  →  매입(Capture)  →  정산(Settlement)  →  대사(Reconciliation)
   실시간, 초 단위        D+0~D+1, 파일        D+1~D+2, 자금이동      D+1~, 대조
   돈 안 움직임          금액 확정            실제 돈 이동           맞는지 확인
```

| 용어 | 코드명 | 정의 |
|---|---|---|
| **승인** 🔒 | `Authorization` | 카드소지자의 지불 능력을 확인하고 **해당 금액을 점유**하는 절차. **이 시점에 돈은 움직이지 않는다.** 승인 성공 = 지불 약속이지 지불이 아니다 |
| **홀딩(한도 점유)** 🔒 | `Hold` | 승인으로 인해 가용잔액에서 차감된 금액. 매입되면 확정 거래로 전환되고, 만료되면 해제된다 |
| **매입** ⚠️ | `Capture` | 가맹점이 실제 대금을 청구하는 절차. 승인건이 **확정 거래**가 되는 시점. 승인 없이는 발생할 수 없다 |
| **정산** ⚠️ | `Settlement` | 발급사 → 매입사 → 가맹점으로 **실제 자금이 이동**하는 절차 |
| **대사** 🔒 | `Reconciliation` | 우리 원장과 상대방(매입사) 기록을 대조해 **불일치를 찾는** 절차. 자동 정정하지 않고 적재한다 |
| **청구** | `Billing` | 신용카드에서 월 단위로 고객에게 대금을 청구하는 절차. **체크카드에는 없다** |

> ⚠️ **가장 흔한 오해**: "승인 = 결제 완료". 아니다. 승인만 되고 매입되지 않은 거래는 며칠 뒤 자동 소멸한다(홀딩 만료). 고객 화면에서 "결제 예정"과 "결제 완료"를 다르게 보여줘야 하는 이유다.

## 3. 거래 정정 🔒

| 용어 | 코드명 | 시점 | 정의 |
|---|---|---|---|
| **승인취소** | `AuthorizationVoid` | **매입 전** | 승인을 무효화하고 홀딩을 해제한다. 원장에 확정 거래가 없으므로 **역분개도 없다** |
| **매입취소 / 환불** | `Refund` | **매입 후** | 이미 확정된 거래를 되돌린다. **역분개 전표가 생성**되며 자금이 반환된다 |
| **부분취소** | `PartialCancellation` | 양쪽 | 원거래의 **일부 금액만** 취소. 원거래 금액을 넘을 수 없고, 누적 취소액도 원거래 금액을 넘을 수 없다 🔒 |
| **망취소** ⚠️🔒 | `Reversal` | 승인 직후 | **통신 장애·타임아웃으로 승인 응답을 받지 못했을 때**, 요청자가 보내는 강제 취소 전문 |

### 망취소가 이 프로젝트의 핵심인 이유

승인 요청을 보낸 매입사가 응답을 받지 못했다. 이때 매입사가 아는 것은:

- 승인이 성공했을 수도 있다 (응답만 유실)
- 승인이 실패했을 수도 있다
- **어느 쪽인지 알 방법이 없다**

이것이 분산 시스템의 **두 장군 문제**이며, 결제 도메인에서는 **실제 고객 자금의 오차**로 나타난다. 해법이 망취소다 — "성공했다면 취소하고, 실패했다면 아무 일도 하지 마라"를 **멱등하게** 요청하는 것. 그래서 망취소 처리는 반드시 멱등해야 한다 🔒.

## 4. 금액과 잔액 ⚠️🔒

**잔액은 하나가 아니다.** 결제 도메인 초심자가 가장 많이 틀리는 지점이다.

| 용어 | 코드명 | 정의 |
|---|---|---|
| **원장잔액** | `LedgerBalance` | **확정된 거래만** 반영한 잔액. 회계적으로 참인 값 |
| **가용잔액** 🔒 | `AvailableBalance` | 지금 쓸 수 있는 금액 = **원장잔액 − 홀딩 합계 − 지급정지액** |
| **금액** 🔒 | `Money` | 통화 + 최소단위 정수. **부동소수 금지.** KRW의 최소단위는 1원 |
| **통화** | `Currency` | 다통화는 범위 밖이지만 **필드는 처음부터 둔다** (나중에 넣으면 전 테이블 마이그레이션) |
| **한도** | `Limit` | 1회 / 1일 / 월 단위로 카드에 부여되는 결제 상한 |

> 🔒 **불변식**: 승인 판단은 **가용잔액** 기준이다. 원장잔액 기준으로 판단하면 동시 결제 시 한도 초과 승인이 난다.

> **결정 필요 #G2**: `Money`를 common-lib에 둘 것인가, 각 서비스가 자기 것을 가질 것인가. 공유하면 서비스 간 결합이 생기고, 나누면 지금처럼 6벌이 갈라진다. **ADR 대상.**

## 5. 원장 (복식부기) 🔒

| 용어 | 코드명 | 정의 |
|---|---|---|
| **복식부기** | — | 모든 거래를 **차변과 대변 양쪽에** 기록하는 방식. 은행 원장의 기본 |
| **차변** | `Debit` | 자산의 증가 / 부채의 감소 |
| **대변** | `Credit` | 자산의 감소 / 부채의 증가 |
| **전표(분개)** 🔒 | `JournalEntry` | 하나의 거래를 표현하는 기록 단위. **차변 합계 = 대변 합계**여야 한다 |
| **계정과목** | `LedgerAccount` | 전표가 기록되는 대상 (예: 고객예금, 미결제매입금, 수수료수익) |
| **역분개** | `ReversingEntry` | 기존 전표를 되돌리는 전표. **기존 전표를 수정·삭제하지 않는다** 🔒 |
| **시산** | `TrialBalance` | 전체 차변 합 = 전체 대변 합인지 검증하는 절차 |

> 🔒 **원장의 제1원칙**: 기록은 **추가만 한다(append-only)**. 잘못된 전표는 수정하지 않고 역분개로 상쇄한다. 이것이 감사 가능성의 근거다.

> ⚠️ 현재 `ledger-service`에는 `EntryType` enum만 있고 복식부기 구조가 없다. **원장 모델 설계가 이 프로젝트의 최대 난이도 구간**이다.

## 6. 식별자

| 용어 | 코드명 | 정의 |
|---|---|---|
| **승인번호** | `ApprovalNumber` | 승인 성공 시 발급사가 부여하는 번호. 취소 시 원거래를 지목하는 데 쓴다 |
| **거래고유번호** 🔒 | `TransactionId` | 시스템 내에서 거래를 식별하는 유일 키 |
| **멱등키** 🔒 | `IdempotencyKey` | **요청자가 생성**해 보내는 키. 같은 키의 요청은 **최초 결과를 그대로 반환**하며 재처리하지 않는다 |
| **원거래 참조** 🔒 | `OriginalTransactionRef` | 취소·환불이 어떤 거래를 되돌리는지 가리키는 참조. **없는 취소는 존재할 수 없다** |
| **가맹점번호** | `MerchantId` | 가맹점 식별자 |
| **카드번호 / 토큰** | `Pan` / `CardToken` | 실제 카드번호(PAN)는 저장하지 않고 **토큰으로 대체**한다 |

> ⚠️ **멱등키와 거래고유번호는 다르다.** 거래고유번호는 우리가 만들고, 멱등키는 상대가 만든다. 재시도를 판별할 수 있는 건 **상대가 만든 키**뿐이다.

## 7. 시간과 주기 ⚠️

| 용어 | 코드명 | 정의 |
|---|---|---|
| **거래일시** | `TransactionAt` | 거래가 실제 발생한 시각 (타임존 명시 필수 🔒) |
| **영업일** ⚠️ | `BusinessDate` | 회계상 귀속되는 날짜. **거래일시와 다를 수 있다** — 마감 이후 거래는 다음 영업일에 귀속 |
| **마감(컷오프)** | `CutOff` | 하루치 거래를 확정하는 시각. 이후 거래는 다음 영업일 몫 |
| **D+n** | — | 거래일 기준 n 영업일 후. 매입은 D+0~D+1, 정산은 D+1~D+2 |

> 🔒 **불변식**: 원장 기록의 기준은 **영업일**이지 거래일시가 아니다. 이 둘을 혼용하면 일 마감 금액이 맞지 않는다.

## 8. 아직 정의하지 않은 용어

아래는 **구현 전에 반드시 정의해야 하나 아직 합의되지 않은** 용어다. 임의로 코드에 등장시키지 않는다.

- 지급정지 / 거래정지의 정확한 구분
- 신용카드 도입 시: 여신한도, 결제일, 청구주기, 이월
- 수수료 체계 (가맹점 수수료, 정산 수수료)
- 가맹점 등급·업종 분류
