# 애그리게이트: 불일치

- 작성일: 2026-08-03
- 상태: 검토대기
- 소속 컨텍스트: **C6 대사**
- 코드명: `Discrepancy`

---

## 1. 책임

> **대사에서 발견된 어긋남을 유형별로 적재하고, 운영자가 처리할 때까지 추적한다.**

**대사는 아무것도 고치지 않는다.** 대사 컨텍스트는 상류에 대해 **순응자(Conformist)** 이며 읽기 전용이다(컨텍스트 맵 R9). 불일치는 대사가 소유하는 **유일한 데이터**다.

---

## 2. 구성

| 필드 | 타입 | 뜻 |
|---|---|---|
| `type` | `DiscrepancyType` | M1·M2·M4~**M17** (BR-09) |
| `scope` | `ReconciliationScope` | **외부 대사**(BR-30) / **내부 대사**(BR-41) |
| `subject` | `SubjectRef` | 대상 (상관 식별자 · 파일·레코드 ID · 계정과목 등) |
| `firstDetectedOn` | `BusinessDate` | **최초** 발견 영업일 |
| `lastDetectedOn` | `BusinessDate` | **최근** 발견 영업일 |
| `detectionCount` | `int` | 누적 발견 횟수 — **영업일당 최대 1회 증가**(BR-48) |
| `expected` · `actual` | `Money?` | 금액 불일치인 경우 |
| `status` | `DiscrepancyStatus` | 미처리 / 조사중 / 처리완료 |
| `resolution` | `String?` | 운영자가 남긴 처리 결과 |

## 3. 불변식

| # | 불변식 | 근거 | 위반 시 |
|---|---|---|---|
| **INV-1** | **자동 정정이 일어나지 않는다** — 이 애그리게이트는 상류 데이터를 바꾸는 조작을 갖지 않는다 | BR-09 | 틀린 값으로 덮어쓰기 |
| **INV-2** | 같은 `(type, scope, subject)`은 **하나만** 존재한다. 재발견 시 새로 만들지 않고 `lastDetectedOn`을 갱신하며, **`lastDetectedOn`이 이미 그 영업일이면 `detectionCount`는 올리지 않는다** | BR-48 | 같은 불일치가 매 대사마다 쌓여 목록이 노이즈가 된다 |
| **INV-3** | `status = 처리완료` 이면 `resolution ≠ null` | — | 처리했는데 근거가 없음 |
| **INV-4** | **`status = 처리완료` 인 건이 재발견되면 `미처리`로 되돌아간다** | BR-48 | "고쳤다는데 또 나온다"는 신호가 사라져 잘못된 처리가 은폐된다 |

> ⚠️ **INV-1이 이 애그리게이트의 존재 이유다.** BR-09("자동 정정하지 않는다")가 **조작 목록의 부재**로 강제된다 — 고칠 방법이 아예 없다.

## 4. 불일치 유형 (BR-09)

| 유형 | 범위 | 뜻 |
|---|---|---|
| **M1** 미매입 | 외부 | 승인·홀딩은 있는데 매입 레코드가 없다 |
| **M2** 미승인 매입 | 외부 | 매입은 있는데 매칭되는 승인이 없다 (BR-27) |
| **M4** 금액 초과 매입 | 외부 | 매입액이 `승인액 − 취소액`을 초과 (BR-16 ③) |
| **M5** 취소 불일치 | 외부 | 취소가 원거래와 맞지 않거나 누적 취소액 초과 |
| **M6** 귀속일 상이 | 외부 | 매입 레코드 영업일 ≠ 우리 원장 귀속 영업일 |
| **M7** 후속 매입 | 외부 | 이미 매입된 승인에 매입이 또 도착 (BR-32) |
| **M8** 무효 승인 매입 | 외부 | 승인은 **찾았으나** `DECLINED`·`VOIDED`·`REFUNDED` (BR-51) |
| **M9** 홀딩 정합 상이 | **내부** | 계좌 `holdTotal` ≠ Σ(승인 `heldAmount`) — `subject` = 계좌ID (BR-04·41) |
| **M10** 카드 한도 정합 상이 | **내부** | 카드 `usage` ≠ Σ(승인 `limitContribution`) — `subject` = (카드ID, 기준일) (BR-05·41) |
| **M11** 계좌 한도 정합 상이 | **내부** | 계좌 `dailyUsage` ≠ Σ(승인 `limitContribution`) — `subject` = (계좌ID, 기준일) (BR-44·41) |
| **M12** 잔액-원장 상이 | **내부** | ★ 계좌 **`anchor.balance` + Σ(`netAmount`[`anchor < businessDate ≤` 대상 영업일]) · DC-006** ≠ 그 계좌의 **고객예금 보조부 잔액** — `subject` = (계좌ID, 영업일) (BR-41·52 · ADR-011) |

| **M13** 입금 멱등 충돌 | **내부** | 같은 `(key, operation)`에 다른 요청 지문 — `subject` = (key, operation). ★ **적재 주체가 대사 배치가 아니라 `DepositConflict` 이벤트다** (BR-29·38) |
| **M14** 미수-원장 상이 | **내부** | ★ 계좌 **`anchor.receivableOutstanding` + Σ(`receivableDelta`[〃]) · DC-006** ≠ 미수금 보조부 잔액 — `subject` = (계좌ID, 영업일) (BR-41·52) |
| **M15** 정산 합계 상이 | **내부** | 정산 합계 ≠ Σ(그 영업일 `settledBusinessDate` 승인들) — `subject` = 영업일 (BR-21·41) |

> ★ **M15에 누락 축이 하나 더 있다** (Phase 3 마감 리뷰 M-8): 좌변(정산 합계)과 우변의 선택 키(`settledBusinessDate`)가 **둘 다 C3의 같은 집계 패스에서 나온다** — BR-21이 *정산은 개별 매입을 안 읽는다*고 정했기 때문이다. 그래서 **C3가 승인 한 건을 빠뜨리면 좌·우변에서 동시에 빠져 통과**한다. **AND 조건을 하나 더 둔다**: ★ *그 영업일에 매입 반영된 승인 중 `settledBusinessDate = null` 인 건수 = 0*. 이 좌변은 **E2 커밋이 직접 쓴 사실**이라 집계 패스를 안 거친다.
| **M16** 드레인 미완 | **내부** | 커트오프 상한 내 Outbox 전달 미완 **또는 `DLQ_UNRESOLVED` 잔존** — `subject` = 영업일 (BR-52 · ADR-014 O-16). ★ **대사를 실행하지 못했다는 사실**이 적재된다 |
| **M17** 이벤트 전달 실패 | **내부** | 릴레이 재시도 상한 초과로 DLQ 격리 — `subject` = **(영업일, 계좌ID, 이벤트 타입, outbox 순번)** — 계좌ID 없는 이벤트는 **"파티션 0"** (ADR-014 O-13). ⚠️ **순번만으로는 무엇이 안 갔는지 역추적이 안 된다.** ★ **유실이 아니라 정체**다 |
| ★ **M18** 감사 기록 유실 | **내부** | 조회 감사의 비동기 적재 실패 — `subject` = **(영업일, 실패 경로)** (BR-57 · ADR-017 AD-4 · R16). 무음 유실 금지의 착지점 |

> ★ **M14가 없으면 `subjectId`를 들기만 하고 안 쓴다** — 비용은 치르고 보호는 없는 상태다.
> 잡는 것: 미수 **발생·회수·소멸 중 하나만 기표**된 경우 · **회수 이중 기표**(R9 T3 유형) ·
> 소멸과 반환의 **배분 오류**.

> ★ **`DepositConflict`가 구독자만 있고 적재할 유형이 없었다** (R9 H5) — BR-41이 명문으로
> 경고한 실패다. 이벤트를 C6으로 보내면서 **받아 적을 곳을 안 만들었다.**

> ★ **M12는 계좌 단위다.** 계정과목 합계로 대조하면 **상계가 은폐한다** — 한 계좌가 +7,
> 다른 계좌가 −7 어긋나면 합계는 맞는다. 그래서 전표 항목이 `subjectId`를 든다 (`journal-entry.md` INV-7).

> M3는 **폐기된 번호**다 (M4와 범위가 같았다). 재사용하지 않는다.
>
> **M2와 M8을 혼동하지 않는다.** M2 = 승인 레코드를 **못 찾았다**(매입사 오발송·우리 유실 의심) · M8 = **찾았는데 유효하지 않다**(매입사가 우리 거절·취소 응답을 못 받았을 가능성 → 전문 로그 대조). **조치가 다르므로 유형이 다르다.**
>
> **보류 격리는 불일치가 아니다.** 보류(BR-50)로 격리된 매입은 우리가 의도한 지연이므로 여기에 적재하지 않으며, **M1(미매입)으로도 잡지 않는다.**

## 5. 조작

| 조작 | 코드명 | 사전조건 | 사후조건 | 이벤트 |
|---|---|---|---|---|
| **적재 또는 갱신** | `recordOrTouch(type, scope, subject, on, expected, actual)` | — (**호출 주체 = 대사 배치 탐지 또는 매입 배치 격리**) | 없으면 생성. 있으면 `lastDetectedOn` 갱신하고 **그 값이 바뀐 경우에만 `detectionCount` +1**. **처리완료였다면 미처리로 복귀** (INV-4) | `DiscrepancyRecorded` 또는 `DiscrepancyRedetected` |
| **조사 시작** | `investigate(operator)` | 상태 = 미처리 | 상태 = 조사중 | `DiscrepancyInvestigating` |
| **처리 완료** | `resolve(operator, resolution)` | `resolution` 있음 (INV-3) | 상태 = 처리완료 | `DiscrepancyResolved` |

### 누가 부르는가

| 호출 주체 | 언제 | 비고 |
|---|---|---|
| **매입 배치** | `isolate()` 시점 — **즉시** | 격리 즉시 운영자 화면에 보인다. **보류 격리(BR-50)는 제외** |
| **대사 배치** | 3자 비교에서 탐지 시 (BR-30·41) | 이미 적재된 건은 재발견 갱신 |
| ★ **C8 운영** | 조회 감사 적재 실패 감지 시 — **즉시** (M18) | R16 — outbox 경유(매입 배치 격리 적재와 같은 형태). 감사 저장이 죽어도 **불일치 적재는 별도 테이블·outbox라 부분 실패에서 살아남는다** |

> **격리를 즉시 적재하지 않으면 묻힌다.** 대사는 정산 완료에 딸려 시작되므로(BR-42), 정산이 실패·지연되면 격리 건이 `isolatedRecords` 안에만 남아 **아무도 못 본다.**
>
> **대신 같은 건을 대사가 또 탐지한다.** 그래서 `detectionCount`는 **영업일당 1회만** 오른다(BR-48) — 매입 격리와 대사가 같은 날 둘 다 탐지해도 1이고, 배치를 세 번 재실행해도 1이다. **`발견 횟수 ≈ 미해결 영업일 수`** 가 성립한다.

### 지속 지표

`firstDetectedOn`과 `detectionCount`가 있으면 **"며칠째 미해결인가"** 가 자연히 드러난다. 오래 지속되는 불일치가 목록에서 눈에 띄고, 이는 운영자가 우선순위를 잡는 근거가 된다.

> **상류를 고치는 조작이 없다.** 운영자가 상류를 고쳐야 한다면 **해당 컨텍스트의 관리 오퍼레이션**을 호출한다(컨텍스트 맵 §8).

## 5.1 발행 이벤트

| 이벤트 | 코드명 | 발생 | 담는 것 | 구독 |
|---|---|---|---|---|
| 불일치 적재됨 | `DiscrepancyRecorded` | `recordOrTouch()` — 최초 생성 | `(type, scope, subject)`, `firstDetectedOn`, `expected` · `actual` | 운영자 |
| 불일치 재발견됨 | `DiscrepancyRedetected` | `recordOrTouch()` — 기존 건 갱신 | `(type, scope, subject)`, `lastDetectedOn`, `detectionCount`, **처리완료→미처리 복귀 여부**(INV-4) | 운영자 |
| 조사 시작됨 | `DiscrepancyInvestigating` | `investigate()` | `(type, scope, subject)`, **담당 운영자** | 운영자 |
| 처리 완료됨 | `DiscrepancyResolved` | `resolve()` | `(type, scope, subject)`, **운영자**, `resolution` | 운영자 |

> 조작 표의 이벤트 열에 이름만 있고 payload가 없었다 — 정산 §4.1이 고친 것(R10 ⑮)과 같은 결함.
> BR-53의 **통지는 적재와 별개의 경로**이므로 이 표의 구독이 통지를 대신하지 않는다.

## 6. 경계 근거

| 질문 | 답 |
|---|---|
| **왜 이 범위인가** | 하나의 불일치가 발견부터 처리까지 추적된다. 중복 적재 방지(INV-2)가 이 안에서 성립 |
| **왜 더 크지 않은가** | 대사 실행 전체를 묶으면 개별 불일치의 처리 상태를 추적할 수 없다 |
| **왜 더 작지 않은가** | `status`·`resolution`을 빼면 "발견했으나 아무도 안 봤다"를 구분할 수 없다 |
| **트랜잭션 단위인가** | 예 — 불일치 하나가 한 트랜잭션 |

## 7. 의문

### 닫힌 의문

#### ~~DC1~~ 반복 발견되는 불일치 → **하나로 유지하고 재발견을 추적** (BR-48 · INV-2·INV-4)

**문제 상황**: 대사는 아무것도 고치지 않는다(INV-1). 상류가 그대로면 **같은 불일치가 매일 다시 잡힌다.**

| 선택지 | 내용 | 결과 |
|---|---|---|
| (a) | 발견일이 다르면 **새 건**으로 적재 | ❌ 기각 |
| (b) | **처리완료된 건은 다음 대사에서 제외** | ❌ 기각 (치명적) |
| **(c)** | **하나로 유지 + 재발견 추적** (최초/최근 발견일 · 발견 횟수) | ✅ **채택** |

**(a)를 기각한 이유 — 목록이 노이즈가 된다**

한 건의 미해결 불일치가 30일이면 30건이 된다. 운영자 화면에서 **"새로 생긴 것"과 "여전히 안 고쳐진 것"이 구분되지 않는다.** 목록이 신호를 잃으면 아무도 보지 않고, 그러면 대사 자체가 무의미해진다.

**(b)를 기각한 이유 — 잘못된 처리가 은폐된다** ★

이것이 가장 위험하다. **"처리했다고 기록했는데 사실 안 고쳐진 것"을 영원히 못 본다.** 운영자가 한 번 잘못 판단하는 순간, 그 불일치는 다시는 화면에 나타나지 않는다.

BR-09가 자동 정정을 금지한 이유는 **사람이 실제로 판단하게 하려는 것**이다. (b)는 사람의 판단을 검증 불가능하게 만들어 그 취지를 정면으로 뒤집는다. 자동 정정을 막아 놓고 "사람이 처리완료를 눌렀다"는 사실만으로 추적을 끊으면, 결국 조용한 은폐라는 같은 결과에 도달한다.

**(c)를 채택한 이유**

- **한 건 = 한 문제.** 목록 길이가 미해결 문제 수와 일치한다.
- **처리완료 후 재발견 시 `미처리`로 복귀**(INV-4) — "고쳤다는데 또 나온다"가 **눈에 보이는 신호**로 남는다. (b)가 지우려던 바로 그 정보다.
- **`firstDetectedOn` + `detectionCount`로 지속 기간이 드러난다.** 오래된 불일치가 자연히 위로 올라오고, 이것이 운영자의 우선순위 근거가 된다.

#### ~~DC3~~ `detectionCount`의 계수 단위 → **영업일당 1회** (BR-48 · INV-2)

매입 배치 격리가 즉시 적재하고(BR-51) 대사가 같은 건을 또 탐지하므로 **하루에 2회 이상 오를 수 있었다.** 그러면 지표가 *"며칠째 미해결인가"* 가 아니라 *"배치를 몇 번 돌렸나"* 가 되고, **배치 재실행이 멱등하지 않게 된다.**

`lastDetectedOn`이 바뀔 때만 `detectionCount`를 올리면 **`발견 횟수 ≈ 미해결 영업일 수`** 가 성립한다.
