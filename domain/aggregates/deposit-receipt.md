# 애그리게이트: 입금 수신

- 작성일: 2026-08-04
- 상태: 검토대기 — **R8 S5·S7로 신설 · R9로 키 설계 정정**
- 소속 컨텍스트: C1 뱅킹
- 코드명: `DepositReceipt`

> 이 문서를 다 읽으면 입금 수신이 **무엇을 소유하고**(입금·정정 지시의 멱등 레코드) **무엇을 통제하는지**(같은 입금·정정이 한 번만 반영되게) 설명할 수 있어야 한다.

---

## 1. 책임

이 애그리게이트가 지는 책임은 한 문장이다.

> **계좌 자금을 움직이는 입금·정정 지시가 한 번만 반영되게 만든다.**

입금은 **외부 입금원의 전문**이고, 정정은 **운영자의 역분개 지시**다 (BR-29 · BR-38).

이 애그리게이트가 왜 새로 필요했는지 밝혀 둔다.

BR-29가 *"입금은 입금 식별자 기준으로 멱등"* 이라고 선언했는데 **그것을 소유하는 곳이 없었다.**\
계좌 `deposit()`에는 식별자 인자조차 없었고, `IdempotencyRecord`는 C3(결제)의 것이며 그 키는 매입사가 생성하고 `operation`에 입금이 없다.

★ **계좌가 처리한 식별자 집합을 들면 안 된다.**\
무한히 증가하는 집합을 애그리게이트가 드는 것이고, `04-aggregate-format.md` §4 합계 필드 판정이 **②(별도 애그리게이트로 분리)** 를 지시하는 형태다 — DC-001에서 미수에 대해 내린 결론과 같다.

---

## 2. 구성

### 애그리게이트 루트

루트는 하나이며, 식별자가 이 애그리게이트의 핵심 설계 결정이다.

`DepositReceipt` — 식별자 ★ **`(발신 기관, key, operation)`**(2026-08-06 개정 R-06 — 구 `(key, operation)` 대체)

### 상태 필드

레코드가 드는 필드는 아래와 같다.

| 필드 | 타입 | 뜻 |
|---|---|---|
| `institution` | `InstitutionCode` | 발신 기관 — 키의 스코프 축 (R-06) |
| `key` | `ReceiptKey` | 멱등 키 — `operation`마다 출처가 다르다 (아래 표) |
| `operation` | `DepositOperation` | 입금 / 정정 |
| `originalDepositId` | `DepositId?` | **정정일 때만** — 되돌릴 원입금 (BR-38) |
| `accountId` | `AccountId` | 대상 계좌 (ID 참조) |
| `ownerId` | `CustomerId` | 소유 축 (ADR-018 IS-1). 조회 격리(BR-58)의 축 |
| `amount` | `Money` | 전문 금액 |
| `requestFingerprint` | `Fingerprint` | 전문 본문의 해시 |
| `result` | `StoredResult` | 최초 처리 결과 |
| `receivedAt` | `Instant` | 수신 시각 (주입받는다) |

기관 축을 표 밖에 풀어 둔다.

`institution`은 **ACL이 인증한 발신 기관**이며, 전문 본문의 X-6 기관 코드와 일치하는지 검증한다 — 불일치는 `ARG_MISMATCH`다 (2026-08-06 R-06).\
단 **정정은 우리가 채번**하므로(운영자 지시) 기관은 자행으로 고정되고 스코프가 자명하다.\
입금의 `depositId`는 입금원이 자기 체계로 채번하므로 그 자체로는 전역 유일이 아니다.

#### 키의 출처가 다르다 ★ (R9 H3·H4)

`operation`에 따라 키를 누가 만드는지가 갈린다.

| `operation` | 키 | 누가 생성하나 | 근거 |
|---|---|---|---|
| **입금** | `DepositId` | 외부 입금원(타행) | BR-29 |
| **정정** | `ReversalId` | 운영자의 정정 지시 | BR-38 |

정정 키를 왜 정정 지시에 거는지, 그것이 무엇을 가능하게 하는지 밝힌다.

정정은 외부 전문이 아니라 운영자의 역분개다 (BR-38).\
BR-29도 *"모의 입금원은 취소 전문을 보내지 않는다"* 고 예외를 명시하므로, 정정의 멱등은 입금 식별자가 아니라 정정 지시에 걸린다.

★ **이것이 부분 정정 2회를 가능하게 한다.**\
키를 `depositId`로 두면 같은 입금을 3만·4만으로 나눠 정정할 때 둘째가 자기 키에 막힌다.\
원입금과의 연결은 `originalDepositId`가 맡는다.

### 다른 애그리게이트 참조

`accountId`만 ID로 든다.\
계좌 객체를 들지 않는다.

입금 수신이 소유하는 것은 **입금·정정 지시의 멱등 레코드**이고, 계좌 자금 반영을 같은 커밋으로 보증하며 충돌을 대사로 내보낸다.

### 협력·소유 구조

아래 그림은 이 레코드가 누구와 협력하고 무엇을 소유하는지 한 장으로 보여준다.

```
                      소속: C1 뱅킹
  ┌────────────────── DepositReceipt ──────────────────┐
  │ 소유: institution · key · operation(입금/정정)     │
  │       originalDepositId · accountId · ownerId      │
  │       amount · requestFingerprint · result         │
  │ 식별자: (institution, key, operation) 유일 (INV-1) │
  └─┬─────────────────────┬───────────────┬────────────┘
    │ [C1 계좌]           │ 키 채번       │ [C7 인증]
    │ deposit E3          │ 입금=외부     │ 회원 ownerId
    │ reverseDeposit E5   │ 입금원        │
    ▼ 멱등 보증           ▼ 정정=운영자   ▼ 참조만
    기록과 자금           (자행 고정)     소유축
    반영 한 커밋

  발행:
   DepositConflict ───▶ C6 대사 (M13 적재)
   ─▶ 정상 경로는 무발행 (막는 게 일이지 알리는 게 아니다)
```

## 3. 불변식 (INV)

레코드가 지키는 명제는 다섯이다.

| # | 불변식 | 근거 규칙 | 위반 시 | 검증 위치 |
|---|---|---|---|---|
| **INV-1** | `(발신 기관, key, operation)`은 유일하다 | BR-29 · BR-38 | 같은 전문·지시가 두 번 반영 | `record()` |
| **INV-2** | `result`는 한 번 설정되면 바뀌지 않는다 | BR-29 · BR-02 | 재수신마다 다른 결과 | 모든 조작 후 |
| **INV-3** | `requestFingerprint`가 다르면 같은 키로 저장할 수 없다 | BR-02 | 다른 거래의 결과를 반환 | `record()` |
| **INV-4** | `operation = 정정` 이면 `originalDepositId`의 입금 레코드가 존재한다 | BR-38 | 원입금 없는 정정이 고객 자금을 줄인다 | `record()` |
| **INV-5** | `Σ(같은 `originalDepositId`를 가진 정정들의 `amount`) ≤ 그 입금의 `amount`` | BR-38 | 받은 것보다 많이 되돌린다 | `record()` |

INV-1과 INV-5는 표 한 줄로 담기지 않는 사정이 있어 아래에 풀어 둔다.

INV-1의 외부 채널 키(`depositId`) 유일성 스코프는 **발신 기관**이다 (2026-08-06 개정 R-06).\
입금원이 자기 체계로 채번하며, 운영자 지시가 만드는 `reversalId`는 우리 채번이라 스코프가 자명하다.\
전역 유일을 가정하면 다른 입금원의 같은 `depositId`가 남의 결과를 반환하고 그 입금이 조용히 사라진다.

INV-5를 어기면 받은 것보다 많이 되돌린다 — 입금 10에 6을 두 번 정정하면 채권 12가 생기고 원장도 12로 기표돼 M14가 못 잡는다.

#### INV-5의 좌변은 **저장하지 않는다** ★ (R10 치명4)

좌변은 매번 계산한다.

```
누적 정정액 = Σ(originalDepositId = D 인 정정 레코드들의 amount)   ← 매번 계산
```

합계 필드 판정(`04-aggregate-format.md` §4)에서 **①(파생값)** 을 고른 근거는 셋이다.

| 왜 ①인가 | |
|---|---|
| 한 입금당 정정 건수가 **적다** | 조회 비용이 문제되지 않는다 |
| 그 값에 **상태·수명·개별 규칙이 없다** | ②(분리)의 근거가 없다 |
| E5가 이미 `DepositReceipt` 참여자다 | 같은 커밋 안에서 읽는다 |

★ **저장하면 그것이 다시 합계 필드가 되어 정정 레코드들과 어긋난다.**\
승인 `refundedTotal`이 세 라운드에 걸쳐 고쳐진 것이 정확히 이 자리였다 — *"상한을 적었는데 좌변(누계)이 어디에도 없다"*.\
여기서는 좌변을 파생으로 두어 어긋날 수 없게 한다.

★ **INV-1이 이 애그리게이트의 존재 이유다.**\
이것이 없으면 아래 세 경우가 일어난다.

| 없으면 | 실제로 일어나는 일 |
|---|---|
| 입금 전문 2회 배달 | 잔액 2배. 근거 없는 고객예금·예치금이 원장에 생긴다 |
| 같은 정정 지시 2회 | 잔액 20에 정정 10을 두 번 → 20이 사라진다. 부족분 미수의 유일성은 잔액이 부족할 때만 작동하므로 막지 못한다 |
| 다른 정정 지시로 초과 정정 | INV-5가 막는다 — 입금 10에 6+6은 둘째가 거절된다 |

## 4. 상태

**상태가 없다.**\
존재 자체가 *"이미 처리됨"* 이고, 되돌아가는 전이가 없다.\
보관 기간이 지나면 만료된다.

## 5. 조작

레코드가 제공하는 조작은 넷이다.

| 조작 | 코드명 | 사전조건 | 사후조건 | 발행 이벤트 |
|---|---|---|---|---|
| **조회** | `find(institution, key, operation)` | — | 있으면 `result` 반환 (기관이 다르면 "없음" — R-06) | — |
| **기록** | `record(institution, key, operation, accountId, amount, fingerprint, result, at, originalDepositId?)` | INV-1 · INV-3 · **INV-4** | 레코드 생성 | — |
| **충돌 판정** | `assertSameRequest(institution, fingerprint)` | — | 다르면 충돌 오류 (BR-02) | `DepositConflict` |
| **만료 정리** | `expire(now)` | 보관 기간 경과 | 삭제 대상 | — |

두 조작에서 기관 축과 커밋 경계를 밝혀 둔다.

`find`는 **기관이 다르면 "없음"으로 답한다** — 같은 `depositId`라도 남의 결과를 보지 않는다 (R-06).\
`assertSameRequest`에서 기관은 **판정 대상 레코드를 지목하는 축**이며, 키의 일부다.

⚠️ **기록은 자금 반영과 같은 커밋이다** — 입금은 E3, 정정은 E5.\
갈리면 반영 후 기록 전 종료 시 재수신이 또 반영된다.

## 6. 발행 이벤트

이 애그리게이트가 내는 이벤트는 하나뿐이며, 정상 경로는 무발행이다.

| 이벤트 | 코드명 | 발생 | 담는 것 | 구독 |
|---|---|---|---|---|
| 입금 충돌 | `DepositConflict` | `assertSameRequest()` 실패 | `institution`(R-06), `key`, `operation`, 두 지문 | C6 대사 — M13 적재 |

M13 적재와 스키마 판정을 밝혀 둔다.

이 충돌은 대사에서 적재 유형 **M13**으로 잡힌다 (BR-09).\
`subject`가 `(기관, key, operation)`이므로 payload가 기관을 실어야 한다.\
S-6a 판정으로 **계약 발행 전**(Phase 5 전 설계 단계)이라 필드 추가는 새 타입이 아니며, `schemaVersion: 1`을 유지한다.

> **정상 경로는 이벤트를 내지 않는다.** 자금 이동은 계좌가 알린다(`Deposited`·`DepositReversed`).
> 이 애그리게이트는 **막는 것이 일이지 알리는 것이 일이 아니다.**

## 7. 경계 근거

이 애그리게이트를 왜 이 크기로 그었는지에 대한 답이다.

| 질문 | 답 |
|---|---|
| **왜 이 범위인가** | INV-1(키 유일성)이 이 안에서만 검증된다. 계좌를 읽을 필요가 없다 |
| **왜 더 크지 않은가** | 계좌와 합치면 계좌가 **무한 증가 집합**을 들게 된다 — DC-001이 미수에서 내린 결론과 같은 이유로 분리한다 |
| **왜 더 작지 않은가** | `operation`을 떼면 키 공간이 섞인다 — 입금 식별자와 정정 지시 ID가 같은 값일 수 있다 |
| **트랜잭션 단위인가** | 아니다 — **E3·E5의 참여자**다. 기록과 자금 반영이 갈리면 멱등이 무의미해진다 |

### `IdempotencyRecord`와 왜 합치지 않았나 (R8 S5·S7)

두 애그리게이트는 컨텍스트·키 생성 주체·작업이 모두 다르다.

| | `IdempotencyRecord` | `DepositReceipt` |
|---|---|---|
| 컨텍스트 | C3 결제 | C1 뱅킹 |
| 키 생성 주체 | 매입사 (BR-17 ①) | 외부 입금원(입금) · 운영자(정정) |
| 작업 | 승인 · 망취소 · 취소 | 입금 · 정정 |

합쳤을 때의 비용과, 그럼에도 분리한 이유를 밝힌다.

합치면 C1 조작이 C3 애그리게이트를 같은 커밋에서 바꾼다 — 컨텍스트 맵 소유권 표와 충돌하고, 키 생성 주체가 둘로 갈라진 하나의 애그리게이트가 된다.

★ **대가는 인정한다** — 멱등 메커니즘이 둘이 되고 애그리게이트가 11종이 됐다.\
그러나 키의 출처가 다른 것을 한 애그리게이트로 묶는 것이 더 큰 비용이다.

## 8. 동시성

동시 수신과 프로세스 종료를 아래처럼 처리한다.

| 상황 | 처리 |
|---|---|
| 같은 `(발신 기관, key, operation)` 동시 2회 | INV-1의 유일 제약이 하나를 거절 → 거절된 쪽은 `find()`로 최초 결과 반환 |
| 기록 후 프로세스 종료 | 자금 반영과 같은 커밋이므로 둘 다 없거나 둘 다 있다 |
