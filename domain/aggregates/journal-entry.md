# 애그리게이트: 전표

- 작성일: 2026-08-03
- 상태: 검토대기
- 소속 컨텍스트: **C5 원장**
- 코드명: `JournalEntry`

---

## 1. 책임

> **하나의 자금 이동을 복식부기로 기록하고, 그 기록이 절대 바뀌지 않게 한다.**

원장은 **감사 가능성의 근거**다. "지금 얼마인가"는 계좌(C1)가 답하고, 원장은 **"무슨 일이 있었는가"** 를 답한다.

**책임지지 않는 것**:
- 계좌 잔액 — C1 뱅킹이 독립 보유 (BR-04). **원장은 잔액의 출처가 아니다**
- 홀딩 — 자금 이동이 아니므로 **기표하지 않는다** (BR-39)
- 고객 조회 — 원장은 고객 화면 소스가 아니다 (RM4)

#### `EntryLine.subjectId` — 보조 차원 ★ (R8 S9)

| 필드 | 타입 | 뜻 |
|---|---|---|
| `account` | `AccountTitle` | 계정과목 (고객예금 · 예치금 · 미수금 · 매입사 미지급금 …) |
| `amount` · `direction` | `Money` · `차/대` | 금액과 방향 |
| **`subjectId`** | `SubjectId?` | ★ **보조부 차원** — 고객예금·미수금은 **누구의 것인지**까지 든다 |

> **왜 필요한가**: 대사를 계정과목 합계로만 하면 **상계가 은폐한다** —
> 한 계좌가 +7 어긋나고 다른 계좌가 −7 어긋나면 합계는 맞는다. R8 S6이 만든 7만 갭이
> 정확히 계좌 단위였고, 합계만 봐서는 **어느 계좌인지 조사할 수단이 없다.**
>
> ⚠️ **대가**: 원장이 계정과목 장부에서 **보조부를 가진 장부**가 된다. Phase 3 저장 설계에
> 선행 제약이 걸린다 — 계정과목만 알면 되던 것이 아니게 된다. **의식적으로 진 비용이다.**

| 필드 | 타입 | 뜻 |
|---|---|---|
| `lines` | `List<EntryLine>` | 차변·대변 항목 (계정과목 + 금액 + 방향 + **`subjectId`**) |
| `businessDate` | `BusinessDate` | **귀속 영업일** (BR-14) — 거래일시가 아니다 |
| `sourceEvent` | `SourceRef` | 어느 이벤트에서 번역됐는가 (ACL 추적) |
| `reversalOf` | `JournalEntryId?` | 역분개인 경우 원전표 |

## 3. 불변식 ★

| # | 불변식 | 근거 | 위반 시 |
|---|---|---|---|
| **INV-1** | **차변 합계 = 대변 합계** | BR-08 | 원장 전체를 신뢰할 수 없음 |
| **INV-2** | **기존 전표는 수정·삭제되지 않는다** | BR-10 | 감사 불가 |
| **INV-3** | `lines`가 비어 있지 않다 | BR-08 | 빈 전표 |
| **INV-4** | 모든 항목의 통화가 같다 | BR-07 | 통화 혼재 균형은 무의미 |
| **INV-5** | `reversalOf`가 있으면 원전표와 **차대가 반대**이고 금액이 같다 | BR-10 | 역분개가 상쇄하지 못함 |
| **INV-6** | **역분개의 `businessDate`는 정정 시점의 영업일**이며, 원전표의 영업일을 따르지 않는다 | BR-47 | 마감된 영업일의 순액이 바뀐다 |
| **INV-7** | **고객예금·미수금 항목은 `subjectId`가 반드시 있다** | BR-41 | 계좌별 대사(**M12**·**M14**)가 불가능해지고 **상계가 불일치를 은폐**한다 |
| **INV-8** | ★ **같은 `sourceEvent`로 두 번 기표하지 않는다** (유일) | BR-40 · ADR-005 O-2 | ★ **중복 전달이 그대로 이중 기표**가 된다. Outbox는 **at-least-once**(O-1)이므로 재전달이 정상 동작인데, 이 불변식이 없으면 `Withdrawn(40,000)` 재전달 시 고객예금 −40,000·미지급금 +40,000이 **더 생기고 미지급금 과다는 어떤 M 유형도 안 잡는다** | `post()` |
| **INV-9** | ★ **같은 정정 지시 ID로 두 번 역분개하지 않는다** (유일) | BR-56 ⑤ · R15 | ★ R15도 at-least-once다 — 이 불변식이 없으면 지시 재전달·DLQ 재투입이 **역분개를 두 번 기표**하고, 되돌리는 유일한 수단이 또 다른 역분개(=또 2인 승인)다. approval-request가 선언한 *"지시 ID 멱등"* 의 **소유 구현이 이 행이다**(루프 3 R3-04) | `reverse()` |

### ACL — 상류 언어를 전표로 번역 (컨텍스트 맵 R5~R7)

| 상류 이벤트 | 전표 |
|---|---|
| `Deposited` (C1) | 차) 예치금 `receivedAmount` / 대) 미수금 `recoveredAmount` · 고객예금 `creditedAmount` — **한 전표로 분할 기표**한다 |
| `Withdrawn` (C1, 매입) | 차) 고객예금 `withdrawnAmount` / 대) 매입사 미지급금 `withdrawnAmount` — ★ **출금액이지 매입액이 아니다.** 부족분은 `ReceivableIncurred(CAPTURE)`가 소유한다 |
| `ReceivableIncurred` (C1, `origin = CAPTURE`) | 차) 미수금 / 대) 매입사 미지급금 |
| `ReceivableIncurred` (C1, **`origin = DEPOSIT_REVERSAL`**) | 차) 미수금 / 대) **예치금** — 착오 입금분을 되돌린 것이라 매입사와 무관하다 (BR-38) |
| **`DepositReversed`** (C1) | 차) 고객예금 `recoveredFromBalance` / 대) 예치금 `recoveredFromBalance` — **잔액에서 실제로 회수한 몫만.** 부족분은 위 `ReceivableIncurred`가 소유한다 |
| `ReceivableRecovered` (C1) | ⚠️ **원장 기표 없음** — 회수는 **언제나** 자금이 들어온 이벤트(`Deposited`·`Refunded`)의 전표 안에 이미 있다 |

> ★ **회수(`recover`)를 부르는 경로는 둘뿐이고 둘 다 자금 유입 이벤트를 낸다** — `Account.deposit`(E3 → `Deposited`)와 `Account.refund`(E4 → `Refunded`). 그래서 `ReceivableRecovered`는 **한 번도 단독 기표되지 않는다.** 따로 기표하면 그 재원이 두 번 잡힌다.
>
> ⚠️ **이 규칙은 R7 U4에서 `Deposited`에만 적용했다가 R8 S2에서 `Refunded` 쪽이 빠진 것이 드러났다** — *"별도 기표는 환불 반환액이 다른 미수를 회수하는 경우에만"* 이라고 적었는데, 그 경우가 바로 `Refunded` 전표가 덮는 경우였다. **한쪽만 고쳤다.**

### ACL 소유 규칙 — 이벤트는 **자기가 단독 소유한 줄만** 쓴다 ★ (R8 S6)

한 트랜잭션에서 이벤트가 여럿 나온다. 전표를 누가 쓰는지 정하지 않으면
**같은 금액이 두 번 잡히거나(R7 U4) 아무도 안 쓴다(R8 S6).**

```
규칙   이벤트는 자기가 단독 소유한 분개만 쓴다
검산   Σ 예치금 변동 = 실제 자금 이동액
```

| 트랜잭션 | 이벤트 | 그 이벤트가 소유한 줄 |
|---|---|---|
| **E1 승인** | — | **없다** — 홀딩·한도는 자금 이동이 아니다 |
| **E2 매입** | `Withdrawn` (C1) | 출금분 `withdrawnAmount` |
| | `ReceivableIncurred(CAPTURE)` | 부족분 |
| | `Captured` (C3) | **없음** — 상태 변화만 알린다 |
| **E3 입금** | `Deposited` | 유입 전액 — 회수분·잔액증가분으로 **분할** |
| | `ReceivableRecovered` | **없음** (위가 덮는다) |
| **E4 환불** | `Refunded` | 반환분 |
| | `ReceivableWrittenOff` | 소멸분 |
| **E5 입금 정정** | `DepositReversed` | 잔액 회수분 |
| | `ReceivableIncurred(DEPOSIT_REVERSAL)` | 부족분 |

> ★ **이 표는 E1~E5를 전부 덮어야 한다.** 초판(R8 S6)은 **E3·E4·E5만 적었고**,
> 그래서 `Captured`가 소유 판정 없이 남아 `Withdrawn`과 **이중 기표**될 수 있었다 (R9 T1).
> **규칙을 세우면서 적용 범위를 절반만 적으면 안 쓴 범위가 옛 규칙으로 남는다.**
>
> ⚠️ **E3만 "한 이벤트가 분할"이고 나머지는 "이벤트마다 자기 몫"이다.**
> 다르게 보이지만 규칙은 하나다 — **회수는 유입 이벤트 없이 일어나지 않으므로**
> `ReceivableRecovered`에는 단독 소유분이 아예 없다.

#### 입금 정정에서 실제로 무슨 일이 있었나 (R8 S6)

`DepositReversed`가 ACL에 **아예 없었다.** 계좌는 줄었는데 원장은 그것을 몰랐다:

```
10만 입금 → 3만 사용 → 잔액 7만 → 10만 전액 정정

  차) 예치금 10 / 대) 고객예금 10      최초 입금
  차) 고객예금 3 / 대) 미지급금 3      사용
  차) 미수금 3   / 대) 예치금 3        정정 부족분
  ─────────────────────────────
  계좌 잔액 0  ↔  원장 고객예금 7 · 예치금 7     ← 7만이 통째로 뜬다
```

고친 뒤:

```
  차) 고객예금 7 / 대) 예치금 7        DepositReversed        ← 신규
  차) 미수금 3   / 대) 예치금 3        ReceivableIncurred     ← 기존
  ─────────────────────────────
  예치금   −10 = 원입금 전액  ✅
  고객예금 − 7 = 잔액 0       ✅
  미수금   + 3 = 부족분       ✅
```

### 환불을 역분개로 번역하지 않는 이유 ★ (R8 S2)

세 규칙이 서로 모순이었다:

```
INV-5    역분개는 원전표와 금액이 같다        → 부분 환불 불가
ACL      Refunded → 원 매입 전표의 반대       → "원 매입 전표"가 둘이다
BR-43 ①  4만 환불 = 매입사 미지급금 4만 감소
```

매입 10 · 출금 7 · 미수 3 에서 **4만 환불**:

| 길 | 결과 |
|---|---|
| 출금 전표(7) 전액 역분개 | 고객예금 +7 인데 실제 반환은 1 — **6 어긋남**. 미지급금 0 인데 잔여 채무는 6 |
| 두 전표(7+3) 다 역분개 | 미지급금 **−3** (음수) |
| 1만 부분 역분개 | **INV-5 위반** |

**세 길 모두 규칙 하나가 반드시 깨진다.** 환불은 *"원거래를 지운다"* 가 아니라
*"거래를 얼마로 줄이는가"* 이므로(BR-43 ①), **역분개가 애초에 맞는 도구가 아니다.**

```
ReceivableWrittenOff(3)   차) 매입사 미지급금 3 / 대) 미수금 3      ← 소멸분 (기존 규칙)
Refunded(returned=1)      차) 매입사 미지급금 1 / 대) 고객예금 1    ← 반환분 (신규)
                          ─────────────────────────────────
                          미지급금 −4 = 거래 축소액 ✅
                          미수금   −3                ✅
                          고객예금 +1 = 반환액       ✅
                          예치금    0  ← 자금 유입이 없다 ✅
```

> ★ **반환액이 다른 미수를 회수하면** 대변이 고객예금이 아니라 **미수금**이 된다
> (`recoveredAmount`). 예치금을 건드리지 않는 것이 핵심 — 외부 유입이 0이기 때문이다.
>
> **검산**: `Σ(환불로 인한 매입사 미지급금 감소) = Σ(reductionAmount)`.
> `writtenOffAmount + returnedAmount = reductionAmount` 가 이벤트 안에서 성립한다.

> **`reverse()`는 남는다.** 오기표 정정(BR-10·47)이 그 조작의 용도다 — 환불은 오기표가 아니다.

| 상류 이벤트 | 전표 |
|---|---|
| **`ReceivableWrittenOff`** (C1) | 차) 매입사 미지급금 / 대) 미수금 — **받을 권리를 버렸다.** 자금 이동 없음 (BR-43 ①) |
| **`Refunded`** (C3) | 차) 매입사 미지급금 `returnedAmount` / 대) 미수금 `recoveredAmount` · 고객예금 `creditedAmount` — **한 전표로 분할 기표**. **역분개가 아니다** |
| `SettlementCompleted` (C4) | 차) 매입사 미지급금 / 대) 예치금 |

> ⚠️ **원장은 "승인·매입·정산"을 모른다.** 번역이 원장 쪽 ACL에서 일어나므로, **상류가 늘어나도 원장은 바뀌지 않는다** — 번역 규칙만 추가된다.
>
> ★ **미수 이벤트 3종은 전표가 각각 다르다.** 발생·회수·소멸을 한 이벤트로 합치면 원장이 구분할 수 없다 (`receivable.md` §6). 그리고 `origin`에 따라 **발생 전표의 대변이 갈린다** — 매입 부족분은 매입사 미지급금, 입금 정정분은 예치금이다.

> ⚠️ **계정과목 체계는 아직 잠정이다** (`glossary.md` §5). Phase 2-5 이후 확정 대상.

## 5. 파생 — 원장 계정 잔액

| 이름 | 계산 |
|---|---|

## 6. 경계 근거

| 질문 | 답 |
|---|---|
| **왜 이 범위인가** | 차대 균형(INV-1)이 **한 전표 안에서** 성립해야 한다 |
| **왜 더 크지 않은가** | 여러 전표를 묶으면 개별 균형을 검증할 수 없다 |
| **왜 더 작지 않은가** | 항목(`EntryLine`) 하나만으로는 균형이 성립하지 않는다 |
| **트랜잭션 단위인가** | 예 — 전표 하나가 한 트랜잭션. **자금 이동과는 별도 트랜잭션** (BR-40) |

| (c) | 마감 전이면 원전표 날짜, 마감 후면 정정 시점 (분기) | ❌ 기각 |

**(a)를 기각한 이유 — 세 가지가 동시에 깨진다**

1. **BR-21 INV-4가 깨진다.** "정산 완료 후 `netAmount`는 바뀌지 않는다"고 정해 놓고, 역분개가 마감된 날짜로 들어가면 그날 순액이 사후에 움직인다.
2. **BR-10의 정신이 깨진다.** 전표는 물리적으로 추가만 되지만, 귀속일이 과거면 **논리적으로는 과거를 수정한 것**이다. append-only가 형식만 남는다.
3. **회계 원칙에 어긋난다.** 마감된 기간은 바뀌지 않는다. 바꿔야 한다면 그것은 정정이 아니라 재마감이며, 우리 범위 밖이다.

그리고 BR-43이 이미 같은 논리를 채택했다 — *"정산 완료 후 환불은 다음 영업일 차감분"*. 여기서 (a)를 고르면 같은 상황에 두 규칙이 서로 다른 답을 준다.

**(c)를 기각한 이유 — 분기가 필요 없다**

(b)를 한 문장으로 쓰면 (c)의 두 갈래가 **결과로서** 자연히 나온다.

```
규칙: 역분개는 정정 시점의 영업일에 귀속한다.

  마감 전 정정 → 결과적으로 원전표와 같은 날이 된다 (아직 순액 미산출이라 문제없다)
  마감 후 정정 → 자연히 다음 영업일이 된다
```

분기를 규칙으로 적어 두면 **마감 시각 경계에서 "어느 쪽인가"를 판정해야 하고**, 그 판정 자체가 경합 지점이 된다. 단일 규칙에는 그 경합이 없다.
