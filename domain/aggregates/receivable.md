# 애그리게이트: 미수

- 작성일: 2026-08-04
- 상태: 검토대기
- 소속 컨텍스트: **C1 뱅킹**
- 코드명: `Receivable`
- 근거: **DC-001** (합계 필드의 소유와 검증)

---

## 1. 책임

> **매입 시 회수하지 못한 금액을 채권 한 건으로 보유하고, 그 회수·소멸을 스스로 통제한다.**

미수는 **계좌의 숫자가 아니라 채권이다.** 언제 생겼는지(회수 순서) · 조사 중인지(보류) · 얼마나 갚혔는지(진행도)를 스스로 안다.

**책임지지 않는 것**:
- 계좌 잔액 — C1 계좌. 미수 회수는 **잔액을 늘리지 않는다**(유입 자금이 잔액 대신 채권으로 갔을 뿐)
- 거래의 상태·금액 — C3 승인. 미수는 **원거래를 참조만** 한다
- 전표 — C5 원장

## 2. 구성

### 애그리게이트 루트

| 이름 | 코드명 | 식별자 |
|---|---|---|
| 미수 | `Receivable` | `ReceivableId` |

### 상태 필드

| 필드 | 타입 | 뜻 |
|---|---|---|
| `amount` | `Money` | **발생액** — 매입 시 확정 후 **불변** |
| `recoveredAmount` | `Money` | 자금 유입으로 회수한 누계 (BR-34) |
| `writtenOffAmount` | `Money` | 환불로 채무가 줄어 **소멸**한 누계 (BR-43 ①) |
| `incurredBusinessDate` | `BusinessDate` | **발생 영업일** — FIFO 정렬의 1차 키 (BR-34) |
| `frozen` | `boolean` | 보류 — 회수 대상에서 제외 (BR-28) |
| **`origin`** | `ReceivableOrigin` | **`CAPTURE`**(매입 부족분) 또는 **`DEPOSIT_REVERSAL`**(입금 정정 — BR-38) |
| **`sourceRef`** | `SourceRef` | 발생 출처. `CAPTURE`면 `AuthorizationId`, `DEPOSIT_REVERSAL`이면 **입금 식별자** |

### 파생 값

| 이름 | 계산 |
|---|---|
| **잔여 미수** `outstanding()` | `amount − recoveredAmount − writtenOffAmount` |
| **종결 여부** | `outstanding() == 0` |

> **잔여를 저장하지 않는다.** 저장하면 세 값과 어긋날 수 있다 — DC-001이 없앤 바로 그 구조를 다시 만드는 셈이다.

### 다른 애그리게이트 참조

| 참조 대상 | 참조 방식 | 왜 참조하는가 |
|---|---|---|
| 승인 | `AuthorizationId` (**`origin = CAPTURE`일 때만**) | 어느 거래에서 생겼는가 — 환불 시 소멸 대상을 찾는 키 |
| 계좌 | `AccountId` | 어느 계좌의 채권인가 — 회수 대상 조회 키 |

## 3. 불변식 (INV) ★

| # | 불변식 | 근거 | 위반 시 | 검증 위치 |
|---|---|---|---|---|
| **INV-1** | `recoveredAmount + writtenOffAmount ≤ amount` | BR-20·34·43 | **없는 채권을 회수·소멸** — 발생액보다 많이 갚혔다는 상태 | 모든 조작 후 |
| **INV-2** | `amount`는 **발생 후 불변** | BR-20 | 채권액이 사후에 바뀌면 감사 불가 | 모든 조작 후 |
| **INV-3** | `recoveredAmount`·`writtenOffAmount`는 **단조 증가** | BR-34·43 | 회수 이력이 사라진다 | 모든 조작 후 |
| **INV-4** | `outstanding() == 0` 이면 **더 이상 회수·소멸되지 않는다** | BR-43 | ★ **소멸한 채권을 계속 회수** — 4차 Q3이 정확히 이것이었다 | `recover()` · `writeOff()` |
| **INV-5** | `frozen = true` 이면 **회수 대상으로 선정되지 않는다** | BR-28 | 조사 중 자동 회수 — 되돌리기 어렵다 | 회수 대상 조회 |
| **INV-6** | 같은 `(origin, sourceRef)`의 미수는 **하나만** 존재한다 | BR-20·38 | 같은 부족분이 두 채권이 되어 **이중 청구** | `incur()` |

> ★ **INV-1과 INV-4가 이 애그리게이트의 존재 이유다.** 이전에는 이 두 명제를 **계좌 합계와 승인 필드에 걸쳐** 지켜야 했고, 그래서 네 라운드 연속으로 깨졌다(DC-001 §2). 이제 **한 애그리게이트 안에서 검증된다.**

## 4. 상태

> 전이와 금지는 별도 문서 → `domain/state-machines/receivable.md`

| 상태 | 코드명 | 뜻 | 종료 |
|---|---|---|---|
| 미결 | `OPEN` | 잔여가 남아 있다 | ✕ |
| 종결 | `CLOSED` | `outstanding() == 0` — 회수·소멸·둘의 조합으로 | **✓** |

> **상태가 둘뿐이다.** "미결 / 부분회수"를 나누지 않은 이유는 **두 상태에서 허용되는 조작이 같기** 때문이다(양식 §4 — 허용 조작이 같으면 나눌 이유가 없다). 진행 정도는 `recoveredAmount`가 말한다.
>
> **종결 사유를 상태로 나누지 않는다.** 전액 회수·전액 소멸·둘의 조합이 모두 가능한데, 사유는 두 금액 필드에 이미 드러난다. 상태로 나누면 조합에서 답이 없어진다.
>
> **보류는 상태가 아니라 직교 플래그다.** `recover` 하나만 막는다 — 상태로 올리면 2종이 4종이 되고 얻는 것이 없다 (상태 머신 README ⑥).

## 5. 조작

| 조작 | 코드명 | 사전조건 | 사후조건 | 발행 이벤트 |
|---|---|---|---|---|
| **발생** | `incur(origin, sourceRef, accountId, amount, businessDate)` | `amount > 0`, **같은 `(origin, sourceRef)` 없음** | 생성, 상태 = 미결 | `ReceivableIncurred` |
| **회수** | `recover(amount)` | 상태 = 미결 · **`frozen = false`** · `amount ≤ outstanding()` (INV-1·4·5) | `recoveredAmount` 증가. 잔여 0이면 종결 | `ReceivableRecovered` |
| **소멸** | `writeOff(amount)` | 상태 = 미결 · `amount > 0` · `amount ≤ outstanding()` (INV-1·4) | `writtenOffAmount` 증가. 잔여 0이면 종결 | `ReceivableWrittenOff` |
| **보류** | `freeze(operator)` | 상태 = 미결 | `frozen = true` | `ReceivableFrozen` |
| **보류 해제** | `unfreeze(operator)` | `frozen = true` | `frozen = false` | `ReceivableUnfrozen` |

> **`recover()`와 `writeOff()`를 나눈 이유가 다르다.**
>
> | | 무엇인가 | 자금이 움직이나 | 보류가 막나 |
> |---|---|---|---|
> | `recover` | 고객이 **갚았다** | ✅ 유입 자금이 채권으로 | ✅ (BR-28) |
> | `writeOff` | 매입사 환불로 **채무가 줄었다** | ❌ 자금 이동 없음 | ❌ — 우리 조사와 무관한 외부 사실 |
>
> 하나로 합치면 **보류 중인 미수가 환불로도 안 줄어들어**, 조사가 끝날 때까지 이미 없어진 채무가 남는다.

### 조작 상세 — `writeOff()` 는 자금을 움직이지 않는다 (BR-43 ①)

```
매입 10만 · 출금 7만 → 미수 3만 (amount=3만)
4만 환불 → 잔여 채무 6만 < 회수액 7만 → 미수 전액 소멸

  writeOff(3만)          receivable: outstanding 3 → 0, 상태 = 종결
  계좌 잔액              변하지 않는다  ← 채권 감소이지 자금 이동이 아니다
  고객 반환 1만          별도 — 승인의 반환액 산식이 정한다
```

> ⚠️ **소멸을 "고객에게 돈을 준다"로 착각하면 이중 지급이 된다.** 소멸은 *받을 권리를 버리는 것*이고, 반환은 *이미 받은 것을 돌려주는 것*이다. 둘은 금액도 시점도 다르다.

### 조작 상세 — 회수 대상 선정 (BR-34)

**미수 자신이 아니라 회수 절차가 대상을 고른다.** 조건과 순서:

```
대상 = { r : r.accountId = 이 계좌 AND r.상태 = 미결 AND r.frozen = false }
정렬 = (incurredBusinessDate, receivableId)          ← 전순서
상계액 = min(유입액, Σ 대상.outstanding())            ← 대상을 먼저 정하고 합을 낸다
```

> ★ **상계액을 계좌 합계에서 먼저 정하면 안 된다.** 보류분을 뺄 수 없어 상계액과 실제 회수 합계가 어긋난다 — 4차 Q4가 이것이었다.
>
> ★ **정렬 2차 키가 필요하다.** 같은 영업일에 발생한 미수들의 순서가 미정이면 **어느 채권이 먼저 갚혔는지가 실행마다 달라져** 대사에서 재현할 수 없다.

## 6. 발행 이벤트

| 이벤트 | 코드명 | 언제 | 담는 정보 | 구독자 |
|---|---|---|---|---|
| 미수 발생 | `ReceivableIncurred` | `incur()` | 미수ID, **`origin`·`sourceRef`**, 계좌ID, 금액, 영업일 | **C5 원장** · 운영자 |
| 미수 회수 | `ReceivableRecovered` | `recover()` | 미수ID, 회수액, 잔여 | ⚠️ **원장 아님** — 회수 분개는 유입 이벤트가 소유한다 (ACL 소유 규칙) |
| **미수 소멸** | `ReceivableWrittenOff` | `writeOff()` | 미수ID, 소멸액, 잔여, **원인 = 환불** | **C5 원장** |
| 보류 / 해제 | `ReceivableFrozen` · `ReceivableUnfrozen` | | 미수ID, 운영자 | 운영자 |

> **회수와 소멸은 전표가 다르다.** 회수는 `차) 예치금 / 대) 미수금`(자금이 들어왔다), 소멸은 `차) 매입사 미지급금 / 대) 미수금`(받을 권리를 버렸다). **한 이벤트로 합치면 원장이 구분할 수 없다.**

## 7. 경계 근거

| 질문 | 답 |
|---|---|
| **왜 이 범위인가** | INV-1(회수+소멸 ≤ 발생액)과 INV-4(종결 후 불변)가 **한 채권 안에서** 성립해야 한다. 그 둘을 계좌 합계와 승인 필드에 걸쳐 지키려다 네 라운드 연속 실패했다 (DC-001) |
| **왜 더 크지 않은가** | 계좌에 합치면 **회수 순서·보류·진행도를 담을 자리가 없다** — 그것이 원래 구조였고 실패했다. 승인에 합치면 정산완료(`SETTLED`)된 거래의 채권이 승인 종료와 함께 접근 불가가 된다 |
| **왜 더 작지 않은가** | `recoveredAmount`·`writtenOffAmount`를 빼면 INV-1·INV-4를 지킬 수 없다. `incurredBusinessDate`를 빼면 FIFO가 성립하지 않는다 |
| **트랜잭션 단위인가** | 원칙상 예. **회수는 계좌·미수들과**(E3), **소멸은 승인·미수·계좌와**(E4) 한 트랜잭션 — E4에 계좌가 있어야 반환액 입금과 `receivableBlockLifted` 갱신이 함께 성립한다 |

### 합계 필드 판정 (양식 §4)

**이 애그리게이트는 다른 애그리게이트들의 합을 필드로 들지 않는다.** `amount`·`recoveredAmount`·`writtenOffAmount`는 전부 **자기 채권 한 건**의 값이다.

> 계좌에 있던 `receivable` 합계가 **판정 ②(별도 애그리게이트로 분리)** 로 처리된 결과가 이 문서다.

## 8. 동시성

| 상황 | 처리 |
|---|---|
| **같은 계좌에 입금과 매입이 동시** | 회수 대상 조회와 회수가 **한 트랜잭션**(E3). 매입이 새 미수를 만들면 다음 회수 대상에 포함 |
| **회수와 소멸의 경합** | 미수 단위 락. 둘 다 `outstanding()`을 줄이므로 **INV-1이 나중 것을 막는다** |
| **보류와 회수의 경합** | 보류가 미수 락을 잡는다 — 회수가 이겼다면 그 회수는 유효(보류 이전 자금이므로) |
| **여러 미수에 걸친 배분 중 일부 실패** | E3가 한 커밋이므로 **전부 반영되거나 전부 롤백**. 부분 배분이 남지 않는다 |
| 배분 대상 미수가 많을 때 | 락 보유 시간이 길어진다 → 대상 수 상한 필요 (RV3) |

## 9. 의문

> **의문 ID는 `RV`다.** `RC-n`은 **대사 불변식**(7개 문서에서 쓰인다)이므로 접두사를 갈랐다 — 같은 글자가 두 의미로 쓰이면 참조 무결성 검사(⑨)가 둘을 구분하지 못한다 (R8 S14).

### 열린 의문

| # | 의문 | 영향 |
|---|---|---|
| **RV1** | **미수의 보류는 승인 보류와 별개인가.** BR-28은 "거래를 보류한다"고만 하는데, 미수가 독립 채권이 된 지금 **미수만 보류**하는 것이 가능해졌다. 운영자 화면에서 둘을 어떻게 보이나 | BR-28 범위 · 운영 화면 |
| **RV2** | **미수에도 소멸 시효가 있는가.** 영원히 회수되지 않는 채권이 `미결`로 쌓인다. 대손 처리 개념이 현 범위에 없다 | 제품 범위 · 원장 계정 |
| **RV3** | 한 계좌의 미수가 많을 때 **배분 대상 수 상한** | 미확정 수치 · E3 락 시간 |
| **RV4** | **`DEPOSIT_REVERSAL` 미수는 환불로 소멸하지 않는다** — 원거래 승인이 없으므로 `writeOff` 경로가 없다. 회수 외에 종결되는 길이 있는가 | BR-38 · **RV2**와 같은 계열 |
