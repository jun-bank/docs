# B. 결제 승인 (S4) ★

**도메인 설명**: 승인은 "돈을 옮기는 것"이 아니라 **"지불 능력을 확인하고 금액을 점유하는 것"** 이다. 아래 검증이 순서대로 통과해야 승인이 성립한다.

| # | 🟧 이벤트 | 🟦 커맨드 | 🟨 액터 | 도메인 설명 |
|---|---|---|---|---|
| B1 | 승인이 요청되었다 | 승인을 요청한다 | 매입사 | 상관 식별자를 실어 보낸다 (BR-17) |
| B2 | **중복 승인 요청이 식별되었다** | 〃 | 시스템 | 같은 상관 식별자 재수신 → 최초 결과 반환 (BR-02) |
| B3 | **카드 검증이 실패했다** | 〃 | 시스템 | 상태·유효기간·정지 (BR-15) |
| B4 | **한도가 초과되었다** | 〃 | 시스템 | 1회 또는 1일 (BR-05) |
| B5 | **가용잔액이 부족했다** | 〃 | 시스템 | 계좌잔액 − 홀딩 (BR-04) |
| B6 | 승인이 거절되었다 | 〃 | 시스템 | B3~B5 중 하나라도 실패 |
| B7 | 홀딩이 생성되었다 | 〃 | 시스템 | 가용잔액 점유. **계좌 잔액은 그대로** |
| B8 | 승인번호가 발번되었다 | 〃 | 시스템 | 발급사가 생성 (BR-17 ②) |
| B9 | 한도 사용액이 증가했다 | 〃 | 시스템 | 달력일 기준 누적 (BR-05) |
| B10 | **승인이 성립했다** | 〃 | 시스템 | B7~B9가 **원자적으로** 확정된 시점 |
| B11 | 승인 응답이 전송되었다 | 〃 | 시스템 | **반드시 B10 이후** (S4 순서 규칙) |

> ⚠️ **B10 → B11 순서가 규칙이다.** 응답을 먼저 보내고 홀딩을 만들면, 홀딩 실패 시 매입사는 정상 승인으로 알고 우리 가용잔액은 줄지 않아 **초과 승인**이 난다.

# C. 망취소 (S5) ★

**도메인 설명**: 매입사가 승인 응답을 못 받았다. 성공인지 실패인지 **알 수 없으므로** 강제 취소 전문을 보낸다. 이 전문은 **중복되거나 원 승인보다 먼저 도착할 수 있다.**

| # | 🟧 이벤트 | 🟦 커맨드 | 🟨 액터 | 도메인 설명 |
|---|---|---|---|---|
| C1 | 승인 응답이 유실되었다 | — (외부 사건) | 네트워크 | 우리는 이 사실을 모른다 |
| C2 | 망취소가 수신되었다 | 망취소한다 | 매입사 | 상관 식별자로만 식별 (BR-17) |
| C3 | 원승인이 매칭되었다 | 〃 | 시스템 | 정상 경로 |
| C4 | 홀딩이 해제되었다 (망취소) | 〃 | 시스템 | |
| C5 | 승인이 무효화되었다 | 〃 | 시스템 | |
| C6 | 한도 사용액이 복원되었다 | 〃 | 시스템 | BR-24 |
| C7 | **중복 망취소가 무시되었다** | 〃 | 시스템 | 이미 무효화됨 (BR-13) |
| C8 | **원승인을 찾을 수 없었다** | 〃 | 시스템 | **선도착** 또는 승인 미도달 |
| C9 | **취소 예약이 기록되었다** | 〃 | 시스템 | tombstone (BR-22) |
| C10 | **예약된 승인이 즉시 무효화되었다** | 승인을 요청한다 | 매입사 | 뒤늦게 도착한 원승인. **홀딩을 만들지 않는다** |

> ⚠️ **C8~C10이 두 장군 문제의 실체다.** C9가 없으면 뒤늦게 도착한 승인이 그대로 성립해 **취소되었어야 할 홀딩이 되살아난다.**

# D. 매입 / 청산 (S6)

**도메인 설명**: 매입은 승인건을 **확정 거래로 전환**하는 절차다. 여기서 **비로소 고객 계좌에서 돈이 빠진다.** 파일 단위 배치이므로 부분 실패와 재처리가 상시 발생한다.

| D3 | 매입 레코드가 파싱되었다 | 〃 | 시스템 | |

| D5 | 원승인이 매칭되었다 | 〃 | 시스템 | 상관 식별자 + 승인번호 (BR-17) |

| D8 | **매입액이 승인액을 초과했다** | 〃 | 시스템 | → 불일치 (BR-16 ③) |

| D14 | 매입 전표가 기록되었다 | 〃 | 시스템 | 고객예금 감소 / 매입사 미지급금 증가 |
| D15 | **매입 처리가 중단되었다** | — (장애) | 시스템 | 부분 실패 |

## 정책에서 드러난 것

**동기가 압도적으로 많다.** 이유는 **자금 정합성** 때문이다 — 홀딩·출금·전표가 따로 놀면 잔액이 틀어진다.

> ⚠️ **P3이 이 시스템에서 가장 어려운 트랜잭션이다.** 홀딩 생성 + 승인번호 발번 + 한도 증가가 **원자적**이어야 하는데, 이 셋이 서로 다른 저장소에 있을 가능성이 높다(계좌·승인·카드). Phase 3의 핵심 설계 대상.

# ⑦ 애그리게이트

## 먼저 — 확정된 설계 원칙

> ✅ **확정 (2026-08-03)**: **한 요청이 여러 트랜잭션 경계를 넘지 않게 한다.**
> 경계를 넘는 분산은 **시간축이 다른 곳**(실시간 ↔ 배치)에서 자연히 생기게 둔다.

**왜 "분산을 넣지 않는다"가 아니라 "경계를 넘지 않게"인가**

실제 카드사·결제사는 승인 경로도 분산 시스템이다. 규모상 그럴 수밖에 없다. 그런데 **분산돼 있어도 승인 한 건은 보통 한 곳에서 끝난다** — 그렇게 만드는 기법이 있기 때문이다.

```
분산 시스템이다  ≠  한 요청이 여러 노드를 왕복한다
```

따라서 진짜 지표는 "분산이냐 아니냐"가 아니라 **"한 요청이 몇 개 경계를 넘느냐"** 다. 이 문장이 같은 판단을 낳으면서, 규모가 커져도 깨지지 않는다.

**경계를 넘을 때 늘어나는 것은 지연이 아니라 실패 모드다.** 3초 안에 응답은 할 수 있어도, 계좌는 성공하고 카드는 타임아웃이면 홀딩만 잡힌 채 한도는 안 잡힌 상태가 남는다. 보상이 필요하고, 보상도 실패하면 미결 상태가 잔류한다.

**근거**:

1. **락 경합이 실제로 없다.** "한 트랜잭션 = 한 애그리게이트"를 어기는 대가는 락 범위 증가인데, 여기서 부딪히는 건 **같은 계좌·같은 카드의 동시 결제**뿐이다. 한 사람이 같은 순간에 여러 곳에서 결제하는 빈도는 극히 낮다.
2. **승인 경로를 쪼개서 얻는 게 없다.** 확장성은 불필요하고(1인·로컬), 분산처리 학습은 **다른 축에서 이미 넘친다** — 승인↔매입(시간축), 매입↔정산(단위), 자금이동↔원장기표(BR-40), 대사, 망취소 순서 역전.
3. **승인은 SLA가 걸린 유일한 경로다**(QS-01 p99 3초). 나머지는 전부 배치라 느려도 된다. 여기에 분산을 넣으면 **잃는 것만 있다** — SLA 위협, 실패 모드 증가, 보상 경로 필요.

> **검토했으나 채택하지 않은 대안**: 계좌·카드를 분리하고 **선반영 후 확정(reserve-then-confirm)** 으로 메시징 조율.
> 기각 이유 — ① 확정까지 기다리면 메시지 왕복이 승인 응답 경로에 들어가 QS-01 위협 ② 확정 전에 응답하면 **S4 순서 규칙 위반**(응답 후 실패 = 초과 승인) ③ 확정 신호 미수신 시 선반영이 잔류해 **2PC와 같은 문제**가 재현된다(ADR-0001에서 2PC를 배제한 이유).
> 다만 **이 패턴 자체는 유효하며, 위치가 다를 뿐이다** — 자금이동↔원장기표(BR-40), 정산↔대사(BR-42)가 정확히 그 구조다. 그리고 **홀딩→매입이 이미 선반영 후 확정**이다. 주기가 메시지 왕복이 아니라 D+1일 뿐.

## 참고 — 규모가 커졌을 때 경계를 늘리지 않고 확장하는 기법

우리 규모에서는 필요 없으나, 원칙이 왜 확장 가능한지 보여주므로 기록한다.

| 기법 | 원리 | 우리에게 |
|---|---|---|
| **계정 단위 샤딩 + 데이터 지역성** | 같은 카드·계좌의 데이터를 같은 샤드에 모아, 시스템은 분산이되 **요청당 경계는 1개** | 규모 불필요. 다만 **원리는 이미 채택** — 승인 데이터를 한 곳에 모은 것이 축소판 |
| **인메모리 + 이벤트 로그** (LMAX 스타일) | 상태를 메모리에 두고 단일 스레드 순차 처리, 디스크는 append만. 락 경합 자체가 없다 | 과함 |
| **예약 토큰 (분산 총량 관리)** | 중앙 총량을 노드가 청크 단위로 미리 예약하고, 청크 안에서는 로컬 판단 | **후속 선택지** — 한도를 별도 서비스로 뗄 때 쓸 수 있음 |
| **응답 시간 예산 배분** | 각 홉에 시간 예산을 나누고 초과 시 조기 실패 | **QS-01 검증에 활용 가능** |
| **판단용 복제본 + 점유만 중앙** | 읽기는 복제본, 쓰기(점유)만 원자적으로 | 부분 채택 — 카드 정보는 복제본 방향 |

> ⚠️ **이 기법들은 지연을 줄이지 실패 모드를 줄이지 않는다.** 경계를 넘는 비용의 본질은 속도가 아니라 **부분 실패의 조합 수**다.

## 애그리게이트 목록

### 실시간 경계 (승인 경로 — 한 트랜잭션)

| 애그리게이트 | 구성 | 🔒 불변식 | 확신도 |
|---|---|---|---|
| **계좌** `Account` | 계좌잔액 · 홀딩합계 · 미수 | ① 가용잔액(= 계좌잔액 − 홀딩합계) ≥ 0 ② 계좌잔액 ≥ 0 (BR-20) ③ 미수 ≥ 0 | **높음** |
| **카드** `Card` | 상태 · 유효기간 · 한도(1회·1일) · 한도사용액(달력일별) · 계좌 참조 | ① 한도사용액 ≤ 1일한도 ② 1회 승인액 ≤ 1회한도 (BR-05) | **높음** |

## 애그리게이트 경계 근거

| 애그리게이트 | 왜 이 범위인가 | 왜 더 크지 않은가 | 왜 더 작지 않은가 |
|---|---|---|---|
| **계좌** | 가용잔액 불변식이 **계좌잔액과 홀딩합계를 함께** 요구한다 | 카드 한도까지 넣으면 **한 계좌에 카드가 여러 장(1:N 확정)** 일 때 카드별 한도를 계좌가 떠안게 된다 | 홀딩합계를 빼면 가용잔액을 계좌 안에서 판단할 수 없다 |
| **카드** | 한도 불변식이 **한도와 한도사용액을 함께** 요구한다 | 계좌잔액까지 넣으면 계좌:카드가 1:N일 때 중복 소유가 된다 | 한도사용액을 빼면 한도 검사를 카드 안에서 못 한다 |
| **승인** | 취소·매입 불변식이 **승인액·누적취소액·매입여부를 함께** 요구한다 | 홀딩 금액까지 들면 계좌와 중복 소유 | 매입여부를 빼면 BR-16 ②(매입 1회)를 지킬 수 없다 |
| **전표** | 차대 균형이 **한 전표 안에서** 성립해야 한다 | 여러 전표를 묶으면 개별 균형을 못 본다 | 항목 하나만으로는 균형이 성립하지 않는다 |

## 홀딩을 어디에 두는가 — 나눠 가진다

| 무엇 | 어디에 | 이유 |
|---|---|---|
| **홀딩 금액의 합계** | **계좌** | 가용잔액 판단에 필요 |
| **이 승인이 홀딩을 잡고 있는가** | **승인** | 이중 해제를 막는 상태 |

> 계좌는 "얼마가 묶여 있나"만 알고, 승인은 "내가 묶었나"만 안다. **한 트랜잭션 경계에 있으므로 원자적으로 함께 갱신**된다.
> 이렇게 나누지 않으면 계좌가 홀딩 목록 전체를 들어야 하고, 그러면 계좌 애그리게이트가 승인 수만큼 커진다.

# ⑧ 바운디드 컨텍스트

## 핵심 통찰 — 컨텍스트와 트랜잭션 경계는 다른 축이다

애그리게이트를 **한 트랜잭션 경계**에 넣기로 했다고 해서 **한 컨텍스트**인 것은 아니다.

```
컨텍스트     = 언어가 같은 범위        (도메인 기준)
트랜잭션 경계 = 함께 원자적으로 변하는 범위 (정합성 기준)
서비스       = 함께 배포되는 범위      (Phase 3에서 결정)
```

**셋은 다른 축이다.** 승인 경로의 다섯 애그리게이트는 **한 트랜잭션 경계**에 있지만 **언어는 셋으로 갈린다**.

## 컨텍스트 후보 (언어 기준)

| # | 컨텍스트 | 고유 언어 | 포함 애그리게이트 | 시간축 |
|---|---|---|---|---|
| **C1** | **뱅킹** | 계좌 · 잔액 · 입금 · 출금 | 계좌 | 실시간 |
| **C2** | **카드** | 발급 · 정지 · 해지 · 한도 | 카드 | 실시간 |
| **C3** | **결제** | 승인 · 홀딩 · 망취소 · 매입 · 취소 | 승인 · 취소예약 · 멱등 · 매입배치 | **실시간 + 배치** |
| **C4** | **정산** | 순액 · 미지급금 · 영업일 · 마감 | 정산 | 배치 |
| **C5** | **원장** | 전표 · 차변 · 대변 · 계정과목 · 역분개 | 전표 | 배치 |
| **C6** | **대사** | 불일치 · 3자 비교 · 내부/외부 대사 | 불일치 | 배치 |
| **C7** | **인증** | 회원 · 자격증명 · 세션 · 토큰 | 회원 · 자격증명 | 실시간 |

> ⚠️ **인증(C7)은 Phase 2-3 작성 중 발견해 추가했다.** 최초 ⑧에서 누락되어 있었다 — 제품 정의서 §3.1에 "고객·인증"이 범위 안이고 이벤트 A1(회원이 가입되었다)이 있는데도 컨텍스트로 잡지 않았다. **이벤트에서 컨텍스트를 도출할 때 A그룹 앞부분을 흘려본 결과다.**

## 경계 근거

| 경계 | 왜 나누는가 | **왜 합치지 않는가** |
|---|---|---|
| **뱅킹 ↔ 카드** | 계좌는 자금, 카드는 결제 수단. 한 계좌에 카드가 여러 장일 수 있다 | 합치면 카드 발급·정지가 계좌 잔액과 같은 생명주기에 묶인다 |
| **결제 ↔ 뱅킹** | 결제는 "승인·매입"을 말하고, 뱅킹은 "입금·출금"을 말한다 | 합치면 승인 상태 전이가 계좌 애그리게이트를 비대하게 만든다 |
| **결제 ↔ 정산** | 결제는 **건별**, 정산은 **영업일 순액** | 합치면 "청산 성공 + 정산 미결" 상태를 표현할 수 없다 (§2.2) |
| **정산 ↔ 원장** | 정산은 지급 의무 산출, 원장은 기록 | 합치면 BR-40(자금 이동과 기표 분리)이 불가능해진다 |
| **원장 ↔ 대사** | 원장은 기록, 대사는 **대조** | 대사가 원장 안에 있으면 원장이 자기를 검증하게 된다 |
| **운영 ↔ 나머지** | 운영은 **다른 컨텍스트를 조작**하는 관점 | 각 컨텍스트에 운영 기능을 흩으면 보류·조사 절차가 일관되지 않는다 |

## 결제 컨텍스트가 시간축을 걸친다

**C3(결제)만 실시간과 배치에 모두 걸쳐 있다.** 승인(실시간)과 매입(배치)이 **같은 언어**를 쓰기 때문이다 — 둘 다 "승인·홀딩·매입"으로 말한다.

이건 이상한 게 아니라 **컨텍스트(언어)와 서비스(배포)가 다른 축이라는 증거**다. Phase 3에서 C3을 한 서비스로 둘지 실시간/배치로 나눌지는 **별도 판단**이다.

## 아직 정하지 않은 것

- **컨텍스트 간 관계 유형**(파트너십·고객공급자·ACL 등) → Phase 2-3 컨텍스트 맵
- **데이터 소유권** → Phase 2-3. 특히 **계좌잔액의 소유자**(뱅킹)와 **홀딩합계의 소유자**(뱅킹)가 같은지
- **서비스 분할** → Phase 3 ADR-0003. **컨텍스트 7개가 서비스 7개를 뜻하지 않는다**
