# 상태 머신 — 승인 요청 `ApprovalRequest` (C8 운영)

- 일자: 2026-08-05 (멀티테넌시 설계 변경 — 리뷰 루프 1 L-08로 신설)
- 정본 관계: **BR-56**(2인 승인)의 상태·전이 계약. 소유 = **C8 운영** (context-map §8 CM4 · ADR-017 AD-6)
- ⚠️ **애그리게이트 상세 명세는 Phase 4** (C7 회원·자격증명·세션과 함께 — 백로그). 이 문서가 그때까지 상태·불변식의 정본이다.

---

## 1. 상태 (5)

| 상태 | 코드 | 뜻 | 종료? |
|---|---|---|---|
| 대기 | `PENDING` | maker가 요청했고 checker의 판정을 기다린다. **이 상태에서 대상 조작은 실행되지 않는다**(BR-56) | |
| 승인됨 | `APPROVED` | checker가 승인했다 — 대상 조작이 실행될 수 있다 | |
| 거절됨 | `REJECTED` | checker가 사유와 함께 거절했다 | ✅ |
| 소비됨 | `CONSUMED` | 대상 조작이 실행되며 이 승인을 **1회 소비**했다 | ✅ |
| 만료됨 | `EXPIRED` | 대기 상한(BR-56 수치 — 미확정) 경과 | ✅ |

## 2. 전이 표

| # | 현재 | 전이(조작) | 다음 | 조건 | 부수 효과 |
|---|---|---|---|---|---|
| A1 | (생성) | `request(maker, 대상 조작, 인자)` | `PENDING` | maker 단계 ≥ **담당자**(BR-55) · 대상 = BR-56 ★ **①~⑥** 목록 안(2026-08-06 L1-06 — ⑥ 권한 부여·수동 회수 추가. ⑥의 maker는 **책임자**다: 권한 조작 자체가 책임자 단계이기 때문) | 요청이 감사 기록에 남는다(AD-5 — 직접 append) · 방치 통지 타이머(BR-53 계열) |
| A2 | `PENDING` | `approve(checker)` | `APPROVED` | ★ **`checker ≠ maker`** (INV-1) · checker 단계 = **책임자** | 승인이 감사 기록에 남는다 |
| A3 | `PENDING` | `reject(checker, reason)` | `REJECTED` | 〃 · **`reason` 필수** | 거절·사유가 감사 기록에 남는다 |
| A4 | `APPROVED` | `consume(executor)` | `CONSUMED` | ★ **실행 인자 = 요청 인자** (INV-3) · ★ **①~③·⑥: `executor = maker` 강제**(BR-55 — 인자로 받으므로 검사 가능, 재점검 지적. ⑥은 코어 안 C7 조작이라 ①~③과 같은 형태다 — L1-06) · ④·⑤: 기술 실행자는 수신 시스템이고 **업무 귀속 = maker**(지시 이벤트에 maker·checker가 실린다) | ★ **코어 안 ①~③·⑥**(⑥ = C7 `RoleGrant.issue`·`revoke` — R14): 실행 컨텍스트가 C8의 이 조작을 **동기 호출**하고 실행 커밋과 **같은 트랜잭션**에 참여한다(R14 — C8이 자기 상태를 바꾼다: 운영자 `freeze()` 명령·R2 같은 트랜잭션 선례. **타 컨텍스트의 직접 테이블 쓰기가 아니다** — ADR-017 기각안 C와 다름) · ★ **코어 밖 ④·⑤**: C8이 승인 시점에 consume + **지시 이벤트 outbox INSERT를 같은 커밋**(R15). INV-2가 보장하는 것은 **발행 1회**이고, **실행 1회는 지시 ID 멱등**이 보장한다 |
| A5 | `PENDING` | `expire()` | `EXPIRED` | 대기 상한 경과 (배치) | 만료가 감사 기록에 남는다 |

## 3. 불변식

| # | 불변식 | 근거 | 깨지면 |
|---|---|---|---|
| **INV-1** | `approvedBy ≠ requestedBy` — 같은 사람이 요청과 승인을 다 할 수 없다 | BR-56 · 감독규정 제28조 | 직무 분리 무력화 — 셀프 승인 |
| **INV-1b** | ★ **⑥(권한 부여·회수) 한정**: `approvedBy ≠ 수혜자(대상 operatorId)` — maker≠checker만으로는 A가 요청하고 **수혜자 B가 자기 권한을 승인**하는 경로가 남는다(2026-08-06 재점검 R3 · role-grant INV-G8) | BR-56 ⑥ | 권한 상승 우회 |
| **INV-2** | 종료 상태(`REJECTED`·`CONSUMED`·`EXPIRED`) 이후 **불변** — 같은 승인이 두 번 소비되지 않는다 | BR-56 | ★ **승인 1건으로 위험 조작이 반복 실행**된다 (취소예약 `consume` INV-3과 같은 형태) |
| **INV-3** | **소비 시점의 실행 인자 = 요청 시점의 인자** | BR-56 | ★ 승인 후 **인자 바꿔치기** — 100원 정정을 승인받아 100만원을 정정한다 |
| **INV-4** | 모든 전이가 행위자와 함께 감사 기록에 남는다 | BR-57 · AD-5 | 승인 이력이 없는 승인 — 감사 불능 |

## 4. 금지된 전이

| # | 현재 | 시도 | 왜 금지인가 |
|---|---|---|---|
| AF1 | `PENDING` | `consume` | ★ **승인 전 실행 경로가 존재하지 않는다** — BR-56 검증 ②의 구조적 강제 |
| AF2 | `APPROVED` | `approve` | 재승인 — 승인 횟수가 의미를 가지면 안 된다 |
| AF3 | `APPROVED` | `reject` | 승인 뒤집기는 거절이 아니라 **새 요청**이다 (이력이 갈린다) |
| AF4 | `REJECTED` | `approve` · `consume` | 종료 상태 (INV-2) |
| AF5 | `CONSUMED` | `approve` · `consume` | 종료 상태 — **재사용 금지** (INV-2) |
| AF6 | `EXPIRED` | `approve` · `consume` | 종료 상태 — 만료된 승인의 부활 금지 |
| AF7 | 모든 상태 | `approve(maker 본인)` | INV-1 — 조건 위반은 상태와 무관하게 거절 |

## 5. 의문

| # | 의문 | 상태 |
|---|---|---|
| AR1 | 대기 상한·방치 통지 임계 값 | **미확정** (BR-56 — 미확정 수치 표) |
| AR2 | `APPROVED` 상태의 유효 기간(승인 후 미실행 방치) — 만료가 `PENDING`에만 있는 것이 맞나 | **열림** — Phase 4 계약에서 판정 |

> **④·⑤의 지시 이벤트가 DLQ(M17)에 갇히면?** 승인은 이미 `CONSUMED`지만 M17은 *유실이 아니라 정체*다 —
> **재투입이 경로**이고(새 승인 불요) **지시 ID 멱등이 이중 실행을 막는다.** 재투입은 담당자 조작(BR-55)이다.

> ★ **종료 상태 재호출의 응답 코드** (2026-08-06 CDS3 소급 — 계약 정본 = UC-02 §7): `approve`·`reject`·`consume`을 종료 상태에 재호출하면 **명시 거절** — `ALREADY_APPROVED` · `ALREADY_REJECTED` · `ALREADY_CONSUMED` · `ALREADY_EXPIRED`(구 `INVALID_STATE` 단일 코드를 대체 — 무엇이었는지가 응답에 보여야 상태 오인이 없다).
