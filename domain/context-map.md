## 1. 컨텍스트 목록

이벤트 스토밍 ⑧의 후보에서 **인증을 추가하고 운영을 제외**해 7종으로 확정했다. 인증은 제품 정의서 §3.1에 "고객·인증"이 범위 안이고 이벤트 A1(회원이 가입되었다)이 있는데 ⑧에서 누락되어 있었다.

| # | 컨텍스트 | 책임 (한 문장) | 핵심 애그리게이트 | 주 액터 | 시간축 |
|---|---|---|---|---|---|
| **C1** | **뱅킹** | 고객의 자금을 보관하고 잔액을 정확히 유지한다 | 계좌 | 카드소지자 · 모의 입금원 | 실시간 |
| **C2** | **카드** | 결제 수단을 발급·관리하고 한도를 통제한다 | 카드 | 카드소지자 | 실시간 |
| **C3** | **결제** | 승인 여부를 판단하고 결제 라이프사이클을 관리한다 | 승인 · 취소예약 · 멱등 · 매입배치 | 매입사 | **실시간 + 배치** |
| **C4** | **정산** | 영업일 단위 자금 의무를 순액으로 확정한다 | 정산 | 정산 배치 | 배치 |
| **C5** | **원장** | 자금 이동을 복식부기로 기록하고 감사 가능하게 한다 | 전표 | (이벤트 구독) | 배치 |
| **C6** | **대사** | 기록 간 어긋남을 찾아 적재한다 | 불일치 | 대사 배치 | 배치 |
| **C7** | **인증** | 누가 요청했는지 확인한다 | 회원 · 자격증명 · 세션 | 카드소지자 | 실시간 |

> **운영은 컨텍스트가 아니다 (결정 2026-08-03).** 자기 모델이 없기 때문이다 — 승인 보류는 C3, **미수 보류는 C1**, 불일치는 C6, 운영자 계정은 C7이 소유한다.
> **운영자는 액터**이고, 보류·조사·처리는 **각 컨텍스트의 관리 오퍼레이션**이다. 상세는 §8 참조.

## 2. 컨텍스트 맵

```
                        [매입사 / VAN]  (외부 · 모의)
                               │
                        ═══ ACL ═══        ← 외부 모델이 침투하지 못하게 번역
                               │
    [C7 인증] ──고객-공급자──▶ │
        │                      ▼
        │                 ┌─────────────────────────────┐
        │                 │        C3 결제               │
        │                 │  승인 · 망취소 · 매입 · 취소   │
        │                 └──┬────────────┬─────────────┘
        │       고객-공급자 │            │ 고객-공급자
        │                    ▼            ▼
        └──────────────▶ [C1 뱅킹]   [C2 카드]
                             │            │
                             └──이벤트────┴──────┐
                                                 ▼
   [C4 정산] ──이벤트──────────────────────▶ [C5 원장]
        ▲                                        ▲   ═══ ACL ═══
        └──이벤트── [C3 결제]                     │   (각 상류 언어 → 전표로 번역)
                                                 │
   [C6 대사] ──읽기 전용──▶ C1 · C2 · C3 · C4 · C5

   ※ 운영자(액터)는 각 컨텍스트의 관리 오퍼레이션을 호출한다 — 별도 컨텍스트 아님
```

> **범례**: 실선 화살표 = **의존 방향**(하류 → 상류). 데이터 흐름과 반대일 수 있다.
> `ACL` = 부패 방지 계층. `이벤트` = 비동기 통합.

## 3. 관계 정의

| # | 상류 (Upstream) | 하류 (Downstream) | 관계 유형 | 통합 방식 | 근거 |
|---|---|---|---|---|---|
| **R1** | 매입사 (외부) | C3 결제 | **부패 방지 계층 (ACL)** | 동기 전문 + 파일 | 외부 모델을 우리가 못 바꾼다. 전문 포맷이 도메인에 침투하면 안 된다 |
| **R2** | C1 뱅킹 | C3 결제 | **고객-공급자** | 동기 호출 (같은 트랜잭션) | 결제가 잔액·홀딩을 필요로 하고, 필요한 조작(hold)을 요구할 수 있다 |
| **R3** | C2 카드 | C3 결제 | **고객-공급자** | 동기 호출 (같은 트랜잭션) | 결제가 카드 유효성·한도를 필요로 한다 |
| **R4** | C7 인증 | C1 뱅킹 · C3 결제 | **공개 호스트 서비스 (OHS)** | 동기 (요청 컨텍스트 전파) | 여러 컨텍스트가 같은 인증 결과를 소비한다 |
| **R5** | C3 결제 | C5 원장 | **부패 방지 계층 (ACL)** | **이벤트 (비동기)** | 원장이 결제 언어(승인·매입)를 전표 언어(차변·대변)로 **번역**한다 |
| **R6** | C1 뱅킹 | C5 원장 | **부패 방지 계층 (ACL)** | **이벤트 (비동기)** | 〃 (입금·출금 → 전표) |
| **R7** | C4 정산 | C5 원장 | **부패 방지 계층 (ACL)** | **이벤트 (비동기)** | 〃 (순액·미지급금 → 전표) |
| **R8** | C3 결제 | C4 정산 | **고객-공급자** | 이벤트 (비동기) | 정산이 매입 결과를 집계한다 |
| **R9** | C1·C2·C3·C4·C5 | C6 대사 | **순응자 (Conformist)** | **읽기 전용** | 대사는 상류를 바꿀 수 없고 있는 그대로 대조한다 |
| **R10** | (없음) | — | — | — | **운영은 컨텍스트가 아니므로 관계도 없다.** 운영자가 각 컨텍스트의 관리 오퍼레이션을 호출한다 |

### R1 상세 — 매입사 ACL (가장 중요)

| 항목 | 내용 |
|---|---|
| **전달되는 것** | 승인 요청 전문 · 망취소 전문 · 취소 요청(실시간) · 매입 파일(매입·취소 레코드 혼재) |
| **하류가 상류에 요구할 수 있는가** | **아니오.** 모의 서비스지만 **실제 매입사를 흉내내야** 학습 가치가 있으므로, 우리 편의로 포맷을 바꾸지 않는다 |
| **상류 변경 시 하류는** | ACL만 고친다. 도메인은 건드리지 않는다 |
| **번역 계층 필요 여부** | **필수.** 전문 필드명·코드 체계·날짜 포맷이 도메인에 들어오면 안 된다 |

> 이것이 지금 코드베이스가 갖지 못한 것이다. 외부 포맷이 도메인에 스며들면 나중에 분리할 수 없다.

### R5~R7 상세 — 원장 ACL

**원장은 세 컨텍스트에서 이벤트를 받는다.** 각각 다른 언어로 말한다:

| 상류 | 상류의 말 | 원장의 번역 |
|---|---|---|
| C1 뱅킹 | "매입 출금이 반영되었다" (`Withdrawn`) | 차) 고객예금 / 대) 매입사 미지급금 |
| C1 뱅킹 | "입금이 반영되었다" (`Deposited`) | 차) 예치금 / 대) 미수금 · 고객예금 |
| C3 결제 | "환불이 확정되었다" (`Refunded`) | 차) 매입사 미지급금 / 대) 미수금 · 고객예금 |
| C4 정산 | "정산이 완료되었다" | 차) 매입사 미지급금 / 대) 예치금 |

> ★ **매입은 C3가 아니라 C1이 알린다.** 승인 `Captured`는 상태 변화를 알릴 뿐 **자금 분개를 소유하지 않는다** —
> 계좌 `Withdrawn`이 소유한다. 둘 다 기표하면 **매입사 미지급금이 두 배**가 된다 (R9 T1).
> 정본은 `journal-entry.md` ACL 표이며, 이 표는 **요약이다.**
>
> **원장이 상류 언어를 그대로 받으면 안 된다.** 원장은 "승인·매입·정산"을 모르고 **"차변·대변·계정과목"만 안다.** 번역이 원장 쪽 ACL에서 일어난다.
>
> 이 구조 덕분에 **상류가 늘어나도 원장은 안 바뀐다** — 번역 규칙만 추가된다.

## 4. 데이터 소유권 ★

**모든 데이터에 소유 컨텍스트가 정확히 하나여야 한다.**

> ★ **합계 필드는 소유가 하나여도 안전하지 않다** (DC-001). `홀딩 합계`·`한도 사용액`은 C1·C2가 소유하지만 **값의 구성 요소는 C3의 승인들**이다. 소유만으로는 등식이 지켜지지 않으므로, 둘 다 **의식적 예외 ③** 으로 등재하고 등식·트랜잭션 경계·탐지(BR-41)를 명시했다.
>
> 미수는 같은 이유로 **합계에서 채권 한 건씩으로 분리**됐다 — 회수 순서·보류·진행도가 합계에 담기지 않기 때문이다.

| **고객 식별자** | **C7 인증** | C1·C3 (참조용 ID만) | — | C7 |
| 계좌 · **계좌잔액** | **C1 뱅킹** | 없음 | — | C1 |
| **홀딩 합계** | **C1 뱅킹** | 없음 | — | C1 |
| **미수 (채권 한 건)** | **C1 뱅킹** — `Receivable` | 없음 | — | C1 |

### 소유권에서 명시적으로 정한 것

**① 홀딩은 두 컨텍스트가 나눠 가진다 — 중복이 아니다**

```
C1 뱅킹:  홀딩 "합계"          → 가용잔액 판단에 필요
C3 결제:  "이 승인이 잡았나"    → 이중 해제를 막는 상태
```

**서로 다른 것을 소유한다.** 같은 데이터의 복제가 아니다. 한 트랜잭션 경계에 있으므로 원자적으로 함께 갱신된다.

**② 보류 상태는 결제가 소유하고 운영이 명령한다**

운영자가 상태를 직접 쓰지 않는다. `freeze()` 명령을 보내면 결제가 자기 상태를 바꾼다. 이래야 BR-28의 불변식(보류 중 자동 처리 제외)이 결제 안에서 지켜진다.

**③ 대사는 아무것도 소유하지 않고 불일치만 소유한다**

대사는 순응자(Conformist)다. 상류 데이터를 **읽기만** 하고 절대 고치지 않는다. BR-09("자동 정정하지 않는다")가 관계 유형으로 표현된 것이다.

**④ 카드 정보에 복제본을 두지 않는다**

⑦에서 "카드 정보는 복제본으로 충분하다"고 분석했으나, **승인 경로를 한 트랜잭션 경계로 확정하면서 복제가 불필요해졌다.** 같은 경계 안이므로 직접 조회한다.

> 다만 **컨텍스트 경계는 지킨다** — 결제가 카드 테이블을 직접 읽지 않고 **카드 컨텍스트의 인터페이스를 통해** 조회한다. 같은 서비스라도 이 규칙을 어기면 나중에 나눌 수 없다.

**⑤ 고객 식별자만 공유하고 나머지는 인증이 소유한다**

기존 코드베이스는 `email`을 `user_db`와 `auth_db` **양쪽에 저장**해 정합성 소유자가 없었다. 여기서는 **인증(C7)이 자격증명 일체를 소유**하고, 다른 컨텍스트는 **고객 식별자만** 참조한다.

## 5. 경계 근거

| 경계 | 왜 나누는가 | **왜 합치지 않는가** |
|---|---|---|
| C1 뱅킹 ↔ C2 카드 | 계좌는 자금, 카드는 결제 수단. **한 계좌에 카드가 여러 장**일 수 있다 | 합치면 카드 발급·정지가 계좌 잔액과 같은 생명주기에 묶인다 |
| C3 결제 ↔ C1 뱅킹 | 결제는 "승인·매입", 뱅킹은 "입금·출금" — 다른 언어 | 합치면 승인 상태 전이가 계좌 애그리게이트를 비대하게 만든다 |
| C3 결제 ↔ C4 정산 | 결제는 **건별**, 정산은 **영업일 순액** | 합치면 "청산 성공 + 정산 미결" 상태를 표현할 수 없다 |
| C4 정산 ↔ C5 원장 | 정산은 의무 산출, 원장은 기록 | 합치면 BR-40(자금 이동과 기표 분리)이 불가능해진다 |
| C5 원장 ↔ C6 대사 | 원장은 기록, 대사는 **대조** | 대사가 원장 안에 있으면 **원장이 자기를 검증**하게 된다 |
| C7 인증 ↔ C1 뱅킹 | 인증은 "누구인가", 뱅킹은 "얼마인가" | **합쳤다가 갈라진 것이 기존 코드베이스의 `email` 이중 저장이다** |

## 6. 컨텍스트 ≠ 서비스

**이 문서는 논리 경계만 정한다.** 배포 단위는 Phase 3에서 정한다.

현재 확정된 방향(Phase 3 백로그): **승인 경로(C1·C2·C3 실시간 부분·C7)를 한 서비스로 묶고 내부를 모듈러 모놀리스로 구성**한다. 컨텍스트 7개가 서비스 7개를 뜻하지 않는다.

> **그래도 소유권을 지금 정한 이유**: 소유권이 명확하면 나중에 묶든 나누든 자유롭다. **반대는 안 된다** — 뭉뚱그린 채 묶으면 나중에 나눌 수 없다.

## 8. 🟥 결정 필요 — 운영(C7)은 컨텍스트인가

**컨텍스트가 되려면 자기 모델이 있어야 한다.** 운영에 자기 모델이 있는지 점검했다.

| 운영이 다루는 것 | 실제 소유자 |
|---|---|
| 보류 상태 | **C3 결제** (§4에서 확정) |
| 불일치 목록 | **C6 대사** |
| 미수 `Receivable` | **C1 뱅킹** |
| 입금 수신 `DepositReceipt` | **C1 뱅킹** |
| 마감 스냅샷 `DailySnapshot` | **C1 뱅킹** |
| 운영자 계정·권한 | **C7 인증** |

**운영 고유 데이터가 하나도 없다.** 전부 다른 컨텍스트가 소유하고, 운영은 **명령만** 한다.

| | 별도 컨텍스트로 둔다 | 각 컨텍스트의 관리 오퍼레이션으로 둔다 |
|---|---|---|
| 근거 | 운영자라는 고유 액터가 있고, 조사·처리 절차의 일관성이 필요 | **자기 모델이 없으면 컨텍스트가 아니다.** 절차 일관성은 UI·애플리케이션 계층의 문제 |
| 대가 | 데이터를 안 가진 빈 컨텍스트가 생긴다 | 운영 기능이 여러 컨텍스트에 흩어진다 |
| 나중에 | 운영 고유 데이터(작업 이력·승인 워크플로)가 생기면 자연스러워진다 | 그때 컨텍스트로 승격하면 된다 |
