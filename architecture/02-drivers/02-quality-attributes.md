## 왜 우선순위가 핵심인가

품질 속성은 **전부 높이는 것이 불가능하다.** 서로 당기기 때문이다.

- 신뢰성을 높이려 재시도를 넣으면 → **중복 처리 위험**(기능 정확성 저하)
- 성능을 높이려 캐시를 넣으면 → **정합성 저하**
- 유지보수성을 위해 추상화를 늘리면 → **성능·분석성 저하**

따라서 이 문서의 실질은 8개 특성의 나열이 아니라 **"충돌할 때 무엇을 버릴 것인가"의 순위**다.

## 1. 8개 품질 특성과 jun-bank 적용

### ① 기능 적합성 (Functional Suitability)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 기능 완전성 | 결제 라이프사이클(승인→매입→정산→대사)이 끊기지 않고 이어지는가 | 높음 |
| **기능 정확성** | **금액·잔액·원장이 정확한가.** 1원도 틀리면 안 된다 | **최상** |
| 기능 적절성 | 도메인 규칙이 실제 결제 업무와 부합하는가 | 높음 |

> **기능 정확성이 이 시스템의 존재 이유다.** 결제 시스템에서 "대체로 맞는 잔액"은 틀린 잔액이다.

### ② 성능 효율성 (Performance Efficiency)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 시간 반응성 | **승인 응답 시간** — 매입사가 타임아웃으로 간주하기 전에 답해야 한다 | 높음 (승인 경로 한정) |
| 자원 활용률 | 로컬 단일 머신에서 전 서비스 구동 가능한가 (제약 TC-5) | 중간 |
| 용량 | 동시 승인 처리량 | 낮음 |

> 성능이 중요한 곳은 **승인 경로 하나뿐**이다. 조회·배치는 느려도 된다. 이 비대칭이 아키텍처를 가른다.

### ③ 호환성 (Compatibility)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 공존성 | 서비스들이 한 머신에서 자원 경합 없이 함께 도는가 | 중간 |
| **상호운용성** | **모의 매입사/VAN과의 전문 규약**, 서비스 간 계약(API·이벤트) | 높음 |

### ④ 사용성 (Usability)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 전반 | API만 제공하며 UI가 없다 (범위 밖) | **낮음** |
| (예외) 오류 메시지 명확성 | 실패 원인을 코드·메시지로 구분 가능한가 | 중간 |

> ISO 25010의 8개 특성 중 **사용성만 의도적으로 낮게 둔다.** 프런트엔드가 범위 밖이기 때문이며, 이는 태만이 아니라 선택이다.

### ⑤ 신뢰성 (Reliability)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 성숙성 | 정상 조건에서 실패하지 않는가 | 높음 |
| 가용성 | 서비스 다운타임 | **낮음** (학습 프로젝트 — 제약 BC-1) |
| **결함 허용성** | **일부 서비스 장애·네트워크 단절 시에도 데이터가 틀어지지 않는가** | **최상** |
| **복구성** | **부분 실패 후 정확한 상태로 되돌아오는가** (보상·망취소·재처리) | **최상** |

> **가용성은 낮고 결함 허용성·복구성은 최상**이라는 조합이 이 프로젝트의 특징이다. "죽어도 된다, 단 틀리면 안 된다."

### ⑥ 보안성 (Security)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 기밀성 | 카드번호 토큰화, 비밀번호 암호화 | 높음 |
| **무결성** | **원장이 append-only이며 변조 불가한가** | **최상** |
| 부인 방지 | 거래 요청의 출처를 부인할 수 없는가 | 중간 |
| **책임 추적성** | **모든 자금 이동에 감사 로그가 남는가** | 높음 |
| 인증성 | 인증·인가 | 높음 |

### ⑦ 유지보수성 (Maintainability)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 모듈성 | 서비스·모듈 경계가 명확한가 | 높음 |
| 재사용성 | `common-lib` 범위 — **과하면 배포 결합**(제약 TC-3) | 중간 |
| 분석성 | 장애 시 원인 추적 가능한가 (분산 추적) | 높음 |
| 수정성 | 요구 변경 시 영향 범위가 좁은가 | 높음 |
| **시험성** | **학습 프로젝트이므로 실험을 반복한다. 검증이 쉬워야 한다** | **높음** |

### ⑧ 이식성 (Portability)

| 부특성 | jun-bank에서의 의미 | 중요도 |
|---|---|---|
| 적응성 | 다른 환경(클라우드)으로 옮길 수 있는가 | 낮음 |
| **설치 용이성** | **`docker compose up` 한 번으로 전체가 뜨는가** (제약 BC-3) | 높음 |
| 대체 가능성 | 구성요소 교체 가능성 | 낮음 |

## 2. 우선순위 (제안)

충돌 시 **위가 아래를 이긴다.**

| 순위 | 품질 속성 | 한 줄 근거 |
|---|---|---|
| **1** | **기능 정확성** (①) | 금액이 틀리면 이 시스템은 존재 의미가 없다 |
| **2** | **결함 허용성 · 복구성** (⑤) | 분산 환경에서 부분 실패는 정상 상태다. 틀어지지 않는 것이 목표 |
| **3** | **무결성 · 책임 추적성** (⑥) | 원장은 append-only. 무슨 일이 있었는지 항상 설명 가능해야 한다 |
| **4** | **시험성 · 분석성** (⑦) | 학습 프로젝트의 실질 = 실험과 관찰. 검증·추적이 안 되면 배울 수 없다 |
| **5** | **시간 반응성** (②) | 단 **승인 경로에 한정**. 조회·배치는 느려도 된다 |
| **6** | **상호운용성** (③) | 계약이 명확해야 모의 카드사와 맞물린다 |
| **7** | **설치 용이성** (⑧) | 로컬에서 전부 떠야 한다 |
| **8** | **가용성** (⑤) · **사용성** (④) | 의도적으로 버린다 |

### 이 순위가 만드는 판단

| 상황 | 이 순위가 내리는 답 |
|---|---|
| 승인 속도를 위해 잔액을 캐시할까? | **안 된다** (1위 > 5위). 캐시하려면 정확성을 보장하는 구조가 먼저 |
| 서비스 하나 죽었을 때 계속 받을까 거절할까? | **거절한다** (2위 > 8위). 틀린 승인보다 거절이 낫다 |
| 재시도로 신뢰성을 높일까? | **멱등성이 보장된 뒤에만** (1위 > 2위) |
| 로그를 줄여 성능을 높일까? | **안 된다** (3·4위 > 5위) |
