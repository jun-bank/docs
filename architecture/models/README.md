# 아키텍처 모델

> 추상화 레벨: ① 아키텍처 설계
> 책 대응: 3.6.2 아키텍처 모델 (154쪽)

**아키텍처는 하나의 그림으로 표현할 수 없다.** 보는 사람에 따라 알고 싶은 것이 다르기 때문이다. 그래서 **뷰(View)** 라는 개념이 필요하다.

---

## 왜 뷰가 여러 개인가

| 묻는 사람 | 알고 싶은 것 | 필요한 뷰 |
|---|---|---|
| 도메인을 이해하려는 사람 | 어떤 개념들이 어떻게 관계 맺는가 | **논리 뷰** |
| 코드를 고치려는 사람 | 어느 저장소·모듈을 열어야 하는가 | **개발 뷰** |
| 장애를 조사하는 사람 | 런타임에 무엇이 무엇을 호출하는가 | **프로세스 뷰** |
| 배포·운영하는 사람 | 무엇이 어디에 떠 있는가 | **물리 뷰** |
| 위 넷을 연결하려는 사람 | 실제 요구가 어떻게 흐르는가 | **시나리오 뷰** |

한 장에 다 그리면 **아무도 못 읽는 그림**이 된다.

---

## 이 프로젝트에서 쓰는 두 모델

| 모델 | 성격 | 문서 |
|---|---|---|
| **4+1 뷰** | **무엇을 그릴 것인가** — 관점의 분류 | [4plus1-views.md](4plus1-views.md) |
| **C4 모델** | **얼마나 확대해서 그릴 것인가** — 줌 레벨 | [c4-model.md](c4-model.md) |

### 두 모델은 경쟁 관계가 아니다

축이 다르다. **4+1은 "어떤 관점"**, **C4는 "어떤 배율"** 이다. 교차해서 쓸 수 있다.

```
            C4 배율 →
        컨텍스트  컨테이너  컴포넌트   코드
      ┌─────────┬─────────┬─────────┬──────┐
논리  │         │         │    ★    │      │   ★ = 주로 그리게 되는 칸
개발  │         │    ★    │    ★    │      │
프로세스│    ★    │    ★    │         │      │
물리  │         │    ★    │         │      │
시나리오│   ★     │    ★    │         │      │
      └─────────┴─────────┴─────────┴──────┘
```

실무적으로는 **모든 칸을 채우지 않는다.** 필요한 칸만 그린다.

---

## 그리기 규칙

1. **모든 다이어그램에 범례(legend)를 넣는다.** 화살표가 호출인지 데이터 흐름인지 의존인지 명시한다. 이게 없으면 그림은 추측의 대상이 된다.
2. **텍스트로 관리한다.** Mermaid 또는 PlantUML을 쓴다. 이미지 파일은 diff가 안 되고 결국 낡는다.
3. **뷰마다 파일을 나눈다.** 한 그림에 관점을 섞지 않는다.
4. **낡은 그림은 지운다.** 틀린 그림은 없는 그림보다 나쁘다.
5. **다이어그램 아래에 항상 설명을 쓴다.** 그림만으로 전달되는 것은 생각보다 적다.

---

## 현재 상태

| 뷰 | 상태 |
|---|---|
| 논리 뷰 | 미착수 — 도메인 모델 확정 후 |
| 개발 뷰 | 미착수 — 서비스 분할 재검토(ADR-0003) 후 |
| 프로세스 뷰 | 미착수 — 트랜잭션 설계 확정 후 |
| 물리 뷰 | 미착수 — `infrastructure` 저장소의 docker-compose 기반으로 작성 가능 |
| 시나리오 뷰 | 미착수 — S3(결제 승인) 우선 |

> **그리는 순서 권고**: 시나리오 뷰(S3 결제 승인) → 프로세스 뷰 → 논리 뷰 → 개발 뷰 → 물리 뷰.
> 시나리오부터 그리는 이유는, 하나의 구체적 흐름을 끝까지 따라가 보면 **나머지 뷰에 무엇이 필요한지가 드러나기 때문**이다.
