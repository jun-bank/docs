# 03. 트랜잭션 경계와 흐름 설계

> 추상화 레벨: ① 아키텍처 설계 (일부 ② 모듈)
> 관련: ADR-0001(MSA 채택) · `study/06-orchestration-vs-choreography/` · 품질 시나리오 QS-03·QS-05·QS-09
> 상태: **초안 v0.1 — 규약 확정 필요**

## 0. 이 문서가 필요한 이유

ADR-0001에서 마이크로서비스를 채택한 순간, **트랜잭션은 더 이상 `@Transactional` 하나로 끝나지 않는다.** 그런데 현재 코드베이스는 서비스마다 다른 방식을 쓰고 있다.

| 흐름 | 현재 방식 | 문제 |
|---|---|---|
| 회원가입 (`user-service`) | `@Transactional` 안에서 **Feign 동기 호출** | 분산 트랜잭션을 로컬처럼 다룸. 보상 없음 |
| 계좌 이체 (`transfer-service`) | `SagaStatus` + `OutboxEvent` | 방향은 맞음 |
| 이벤트 발행 (`user-service`) | try-catch 삼킴 + `FailedEventEntity` 자체 재시도 | **QS-05 통과 불가** (유실 가능) |
| 이벤트 발행 (`transfer-service`) | Outbox | 정상 |

**같은 문제에 두 개의 답이 공존한다.** 이 문서의 목적은 하나의 규약으로 통일하는 것이다.

## 1. 트랜잭션 경계 — 계층별 규칙

### 1.1 어느 계층이 트랜잭션을 여는가

```
presentation/     ❌ 트랜잭션을 열지 않는다
      │
      ▼
application/      ✅ ★ 여기가 유일한 트랜잭션 경계 ★
   service/          @Transactional 은 여기에만 붙인다
      │
      ▼
domain/           ❌ 트랜잭션을 모른다 (인프라 개념이므로)
      ▲
      │
infrastructure/   ❌ 스스로 열지 않는다 (애플리케이션이 연 것에 참여만)
```

**왜 애플리케이션 계층인가**: 트랜잭션 경계는 **유스케이스의 경계**와 같아야 한다. "결제를 승인한다"가 하나의 유스케이스이면 그것이 하나의 트랜잭션이다. 도메인은 트랜잭션을 몰라야 순수성이 유지되고(study/03), 프레젠테이션은 HTTP 관심사만 다뤄야 한다.

### 1.2 규칙

| # | 규칙 | 이유 |
|---|---|---|
| **TX-1** | `@Transactional`은 **애플리케이션 서비스에만** 붙인다 | 경계를 한 곳에 모은다 |
| **TX-2** | **트랜잭션 안에서 외부 네트워크 호출을 하지 않는다** | DB 커넥션을 쥔 채 대기 → 풀 고갈. 외부 성공 + 로컬 실패 시 고아 데이터 |
| **TX-3** | 하나의 트랜잭션은 **하나의 애그리게이트만** 변경한다 | 애그리게이트 = 정합성 단위 |
| **TX-4** | 조회 전용은 `@Transactional(readOnly = true)` | 플러시 생략, 슬레이브 라우팅 여지 |
| **TX-5** | 이벤트 발행은 **Outbox를 통한다** | 커밋과 발행의 원자성 (QS-05) |
| **TX-6** | 트랜잭션 커밋 후 작업은 `AFTER_COMMIT` | 롤백됐는데 알림 나가는 사고 방지 |

> **TX-2가 현재 가장 크게 위반되고 있다.** `CreateUserService`가 `@Transactional` 안에서 `authServicePort.createAuthUser()`를 호출한다.

### 1.3 TX-2 위반의 구체적 결과

```java
@Transactional                                    // ① 트랜잭션 시작 (DB 커넥션 점유)
public UserResult createUser(CreateUserCommand command) {
    User savedUser = userRepository.save(user);   // ② 로컬 INSERT (아직 커밋 전)
    createAuthUser(userId, email, password);      // ③ ★ 네트워크 호출 — 여기서 수 초 대기 가능
    publishCreateEventSafely(savedUser);          // ④ 이벤트 (try-catch로 삼킴)
    return ...;
}                                                  // ⑤ 커밋
```

| 실패 지점 | 결과 |
|---|---|
| ③이 느림 | **DB 커넥션을 쥔 채 대기.** 동시 요청이 늘면 커넥션 풀 고갈 → 전체 장애 |
| ③ 성공 후 ⑤ 실패 | auth_db에 **고아 AuthUser**. user_db엔 없음 → 영구 불일치 |
| ③ 타임아웃 (상태 불명) | 성공했는지 실패했는지 모름. 롤백해도 상대는 남을 수 있음 |
| 재시도 | 멱등키가 없어 **중복 생성** |

## 2. 분산 트랜잭션 전략

### 2.1 채택: Saga (보상 기반), 2PC 미사용

**2PC를 쓰지 않는 이유** (study/06 §1):
- 준비~커밋 사이 내내 락 유지 → 처리량 급락
- 조율자 장애 시 참여자 영구 대기
- Kafka·외부 API가 지원하지 않음

### 2.2 오케스트레이션 vs 코레오그래피 — 흐름별 선택

**하나로 통일하지 않는다.** 흐름의 성격에 따라 고른다.

| 판단 기준 | 선택 |
|---|---|
| 결과를 **즉시 응답**해야 하는가 | 오케스트레이션 |
| 실패 시 **정확히 되돌려야** 하는가 | 오케스트레이션 |
| 흐름이 **3단계 이상**인가 | 오케스트레이션 |
| **부수적**이고 순서가 중요하지 않은가 | 코레오그래피 |
| 구독자가 **늘어날 예정**인가 | 코레오그래피 |

### 2.3 흐름별 배정 (제안)

| 흐름 | 방식 | 조율자 | 근거 |
|---|---|---|---|
| **결제 승인** (S3) | **오케스트레이션** | card-service | 즉시 응답 필수(QS-01), 실패 시 정확한 보상 필요 |
| **망취소** (S4) | **오케스트레이션** | card-service | 상태 불명을 확정으로 수렴시켜야 함 |
| **계좌 이체** | **오케스트레이션** | transfer-service | 현행 유지 (이미 Saga 구조) |
| **회원가입** (S1) | **오케스트레이션** | user-service | **현재 방식에서 변경 필요** — TX-2 위반 해소 |
| 매입·정산 (S5) | 배치 + 코레오그래피 | — | 파일 단위 처리, 후속은 이벤트 |
| 결제 완료 후 알림·집계 | **코레오그래피** | — | 부수적, 구독자 증가 예정 |
| 회원 탈퇴 후 정리 | **코레오그래피** | — | 현행 유지 |

> **결정 필요 #T1**: 위 배정에 동의하는가? 특히 결제 승인을 오케스트레이션으로 두는 것.
> **결정 필요 #T2**: 조율자를 **전용 서비스**로 뺄 것인가, **시작 서비스가 겸할** 것인가. 위 표는 후자를 가정했다.

## 3. 결제 승인 Saga (설계 초안)

### 3.1 흐름

```
매입사 ──승인요청──▶ [card-service = 조율자]
                          │
                    ① 카드 유효성·한도 점유 (로컬)
                          │
                    ② ──▶ [account-service] 가용잔액 확인 + 홀딩 생성
                          │
                    ③ ──▶ [ledger-service] 홀딩 전표 기록
                          │
                    ④ 승인 확정 ★ 피벗 ★
                          │
                    ⑤ ──event──▶ 알림·집계 (코레오그래피, 실패해도 승인은 유지)
                          │
                          ▼
                    승인 응답 반환
```

### 3.2 피벗 트랜잭션

**④ 승인 확정이 피벗이다.**

| 구간 | 실패 시 |
|---|---|
| ①~③ (피벗 이전) | **전체 보상** — 역순으로 홀딩 해제, 한도 반환, 역분개 |
| ④ (피벗) | 이 지점을 넘으면 되돌리지 않는다 |
| ⑤ (피벗 이후) | **보상하지 않고 재시도.** 알림이 실패했다고 승인을 취소하지 않는다 |

### 3.3 보상 정의

| 단계 | 정방향 | 보상 | 비고 |
|---|---|---|---|
| ① | 카드 한도 점유 | 한도 반환 | 멱등 |
| ② | 계좌 잔액 홀딩 | 홀딩 해제 | 멱등 |
| ③ | 원장 홀딩 전표 | **역분개** (삭제 아님) | append-only 원칙 |

> ⚠️ **원장은 절대 삭제·수정하지 않는다.** 보상도 새 전표를 추가하는 방식이다 (QS-07).

### 3.4 각 단계의 트랜잭션 경계

```
① card-service   [ TX ]                          ← 로컬 트랜잭션 1
② account-service        [ TX ]                  ← 로컬 트랜잭션 2 (별도 서비스, 별도 DB)
③ ledger-service                [ TX ]           ← 로컬 트랜잭션 3
```

**각각 즉시 커밋된다.** ②가 커밋된 뒤 ③이 실패하면 ②는 이미 확정되어 있으므로 **보상 호출**로 되돌린다.

## 4. 시스템 전역 규약

### 4.1 멱등성 규약

| # | 규칙 |
|---|---|
| **ID-1** | **모든 상태 변경 API는 멱등키를 받는다** (`Idempotency-Key` 헤더 또는 요청 본문) |
| **ID-2** | 멱등키는 **요청자가 생성**한다. 우리가 만든 거래고유번호로 대체할 수 없다 |
| **ID-3** | 같은 키의 재요청은 **최초 결과를 그대로 반환**한다. 재처리하지 않는다 |
| **ID-4** | 멱등키 저장소에 **유니크 제약**을 건다 (동시 요청 방어) |
| **ID-5** | 멱등키 저장과 실제 처리는 **같은 트랜잭션**이어야 한다 |
| **ID-6** | 보관 기간을 정한다 (제안: 30일) |
| **ID-7** | **보상 호출도 멱등해야 한다** — 보상이 두 번 실행되면 이중 환입이 난다 |

> **ID-7이 자주 빠진다.** 정방향만 멱등하게 만들고 보상을 놓치면, 재시도 시 홀딩이 두 번 해제된다.

### 4.2 이벤트 발행 규약 (Outbox)

| # | 규칙 |
|---|---|
| **EV-1** | 이벤트는 **상태 변경과 같은 DB 트랜잭션**으로 outbox 테이블에 기록한다 |
| **EV-2** | 별도 발행기(스케줄러 또는 CDC)가 outbox를 읽어 브로커에 발행한다 |
| **EV-3** | 발행은 **at-least-once**다. 중복이 전제이므로 **소비 측이 멱등**해야 한다 |
| **EV-4** | 소비 측은 **처리한 이벤트 ID를 기록**해 중복을 걸러낸다 |
| **EV-5** | 발행 실패는 삼키지 않는다. outbox에 남아 재시도된다 |
| **EV-6** | outbox 적체는 **모니터링 대상**이다 (미발행 건수·최고 지연) |

> **현재 `user-service`의 `FailedEventEntity` + `EventRetryService`는 EV-1을 만족하지 않는다.** 발행을 먼저 시도하고 실패한 것만 저장하는 구조라, **발행 시도 자체를 못 한 경우**(프로세스 강제 종료)에 유실된다. Outbox로 교체 대상.

### 4.3 재시도·타임아웃 규약

| # | 규칙 |
|---|---|
| **RT-1** | 모든 서비스 간 호출에 **타임아웃을 명시**한다. 무한 대기 금지 |
| **RT-2** | 재시도는 **지수 백오프 + 지터**를 쓴다 (동시 재시도 폭주 방지) |
| **RT-3** | **멱등하지 않은 작업은 재시도하지 않는다** |
| **RT-4** | 서킷 브레이커를 적용한다 (Resilience4j — 이미 의존성에 있음) |
| **RT-5** | **타임아웃 = 실패가 아니라 "상태 불명"** 이다. 실패로 단정하고 보상하면 위험하다 |

> **RT-5가 결제 도메인의 핵심이다.** 승인 요청이 타임아웃되면 상대는 승인이 됐는지 모른다. 이때 필요한 것이 **망취소**이고, 망취소는 반드시 멱등해야 한다(ID-7).

### 4.4 Saga 상태 관리 규약

| # | 규칙 |
|---|---|
| **SG-1** | Saga 상태를 **DB에 영속화**한다. 메모리에만 두면 프로세스 재시작 시 유실 |
| **SG-2** | 각 단계 완료 시 **즉시 상태를 갱신**한다 (도중에 죽어도 어디까지 갔는지 알 수 있게) |
| **SG-3** | 보상은 **완료된 단계만 역순으로** 수행한다 |
| **SG-4** | 미완결 Saga를 **주기적으로 스캔**해 복구한다 (조율자가 죽은 경우) |
| **SG-5** | Saga 타임아웃을 정의한다. 무한정 `IN_PROGRESS`로 남지 않게 |

## 5. 현재 코드와의 격차

| 항목 | 현재 | 목표 | 우선순위 |
|---|---|---|---|
| 회원가입 트랜잭션 내 Feign 호출 | 위반 (TX-2) | Saga로 전환 | **높음** |
| 멱등키 | `transaction-service`에 `IdempotencyKey` 도메인만 존재 | 전 상태변경 API 적용 | **높음** |
| Outbox | `transfer-service`만 | 전 서비스 표준 | **높음** |
| 이벤트 소비 멱등성 | 미확인 | 처리 이벤트 ID 기록 | 높음 |
| 서킷 브레이커 | 의존성만 추가됨 | 실제 적용·설정 | 중간 |
| Saga 복구 스캐너 | 없음 | SG-4 구현 | 중간 |
| 원장 append-only | 원장 미구현 | 설계 시 강제 | **높음** |
