# ADR-014. Outbox 릴레이 운영 — 순서·재시도·독약 격리·소유권

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: `study/11-failure-modes` **F-12 · F-13 · F-14 · F-09**
- 관련: **ADR-005**(Outbox) · **ADR-008**(파티션) · **ADR-009**(계좌ID 키)

---

## 1. 맥락 — ADR-005가 선언만 한 것들

ADR-005는 Outbox로 **유실**을 막았다. 그런데 나머지는 **계약 문장**으로 남았다.

| ADR-005가 적은 것 | 장치가 있나 |
|---|---|
| **O-1** at-least-once | ✅ 구조상 그렇다 |
| **O-2** 수신측 멱등 | ⚠️ 원장은 INV-8로 해결. **정산은 없다** |
| **O-4** *"순서는 같은 파티션 키 안에서만"* | ❌ ★ **선언뿐** |
| *"재시도가 자연스럽다"*(§3) | ❌ ★ **백오프·상한·독약 격리가 한 줄도 없다** |
| **ADR-008 B-3** lease | ❌ ★ **좀비 쓰기를 못 막는다** |

> ★ **"보장한다"고 적은 것과 "보장하는 장치"는 다르다.**
> `study/11` B그룹 §정리 ③이 이 프로젝트에서 **가장 많이 걸린 유형**으로 지목한 것이다.

---

## 2. 결정

### 2.1 순서 — 소유권으로 만든다 (F-12)

**릴레이가 여러 인스턴스면 같은 계좌의 이벤트를 병렬로 집을 수 있다.**

```
릴레이 인스턴스 A → outbox 레코드 5 (계좌 X, 입금 100)
릴레이 인스턴스 B → outbox 레코드 6 (계좌 X, 출금 30)
                    ★ B가 먼저 도착하면 순서가 뒤집힌다
```

**답: 파티션을 소유한 인스턴스만 그 파티션을 전달한다.**

| # | 규칙 | 왜 |
|---|---|---|
| **O-6** | outbox 레코드에 ★ **파티션 키(계좌ID 해시)** 를 저장한다 | 조인 없이 소유 판정 |
| **O-7** | ★ **한 파티션은 한 인스턴스만 전달**한다. ⚠️ **ADR-008의 배정 테이블을 재사용하지 않는다** — 별도 `relay_partition_lease(partitionId, generation, holder, expiresAt)` | 아래 |
| **O-8** | 파티션 안에서는 ★ **outbox 순번(단조 증가) 오름차순**으로 전달한다 | 순서 보장의 실체 |
| **O-9** | 순서 검증을 **검증 항목에 넣는다** | ADR-005 검증표는 중복만 쟀다 |

> ★ **우아한형제들이 같은 답을 냈다** — *커넥터 단일 태스크 + 키→테이블 고정*.
> **"한 키는 항상 한 소비자"** 라는 소유권 구조다.
>
> ⚠️ **계좌ID가 없는 이벤트가 있다** — `SettlementCompleted`(영업일 단위) 등.
> 그것은 **전용 파티션(0번)** 에 넣어 단일 소비자가 처리한다.
>
> ⚠️ **배치와 릴레이는 파티션 모델이 다르다** (Phase 3 마감 리뷰 결함8):
>
> | | 배치(ADR-008) | 릴레이 |
> |---|---|---|
> | 수명 | **유한** — 범위를 끝내면 `COMPLETED` | ★ **영구** — outbox가 0건이어도 안 끝난다 |
> | 키 | `(runId, partitionId)` | `(partitionId)` |
> | 완료 | 있다 | ★ **없다** |
>
> **재사용하는 것은 "조건부 갱신으로 소유권을 잡는다"는 기법이지 테이블이 아니다.**

### 2.2 재시도와 독약 격리 (F-09 · F-13)

**순서대로 훑는 구조(O-8)라 한 건이 막히면 뒤가 전부 멈춘다.**

```
레코드 5 가 영구 실패 (수신측 스키마 불일치 등)
  → 재시도 → 또 실패 → 무한
  → ★ 6 이후가 영원히 안 나간다
  → 유실이 아니라 정체라 대사는 "아직 안 왔다"로만 본다
```

| # | 규칙 | 값 |
|---|---|---|
| **O-10** | 지수 백오프 **+ 지터** | 1s → 2s → 4s → 8s (±30% 지터) |
| **O-11** | 재시도 **상한** | **5회** |
| **O-12** | ★ **상한 초과는 DLQ로 옮기고 다음으로 진행**한다 | 버리지 않는다 |
| **O-13** | ★ **DLQ 적재는 불일치 유형으로 올린다** (**M17**) | 사람이 봐야 한다 |
| **O-15** | ★ **outbox 레코드 상태를 넷으로 구분**한다 — `DELIVERED` · `DLQ_UNRESOLVED` · `RESOLVED_BY_REPLAY` · `RESOLVED_BY_CORRECTION` | 아래 |
| **O-16** | ★ **`DLQ_UNRESOLVED`는 "드레인 완료"로 세지 않는다** (BR-52) | 사실이 원장에 안 갔는데 완료로 세면 **대사가 그 위에서 돈다** |
| **O-14** | DLQ 재투입은 **운영자 조작**이다 | 자동 재투입은 무한 루프가 된다 |

> ★ **O-12가 F-13의 답이다.** 상한만 두고 DLQ가 없으면 **그것이 유실**이다.
> **빼되 버리지 않는 곳**이 필요하다.
>
> ⚠️ **DLQ로 옮기면 그 파티션의 순서가 깨진다.** 그것을 감수하는 이유는
> **정체가 순서 위반보다 나쁘기 때문**이다 — 뒤의 전부가 안 나가면 대사가 매일 허위를 쏟는다.
> **M17이 그 사실을 사람에게 알린다.**
>
> ★ **그러나 "다음으로 진행"이 "드레인 완료"를 뜻하면 안 된다** (Phase 3 마감 리뷰 치명2).
>
> ```
> 매입 100 = 출금 70 + 미수 30
>   Withdrawn(70)          → ★ DLQ
>   ReceivableIncurred(30) → 전달됨
>   후속 환불 20            → 전달됨
>
> 코어    출금 70 · 미수 10
> 원장    출금 0  · 미수 30 · 환불 20   ← 70이 없다
> → 드레인을 "완료"로 세면 대사가 이 상태를 정상 기준으로 삼는다
> ```
>
> **`DLQ_UNRESOLVED`가 하나라도 있으면 그 영업일의 드레인은 미완이다**(O-16).
> 대사는 실행되지 않고 **M16 + M17**이 함께 적재된다.

### 2.3 좀비 — fencing token (F-14)

**lease 만료는 "가져가는 것"을 조정할 뿐 "쓰는 것"을 막지 않는다.**

```
A  파티션 3 임차 (만료 30s)
   ★ GC 정지 40초
B  만료 감지 → 파티션 3 임차 → 전달 시작
A  깨어남. 자기가 소유자인 줄 안다 → 전달
   → 둘이 같은 파티션을 전달한다 (순서·중복 둘 다 깨진다)
```

| # | 규칙 |
|---|---|
| **B-6** | ★ 파티션 임차마다 **단조 증가하는 fencing token**을 발급한다 |
| **B-7** | 전달 완료 표시·상태 갱신에 **token을 함께 쓴다** |
| **B-8** | ★ **저장소가 "지금까지 본 것보다 작은 token"을 거부**한다 | 
| **B-9** | 거부된 쓰기는 **적재**한다 — 좀비가 있었다는 사실이 남아야 한다 |

| **B-10** | ★ **수신측(C4·C5)이 `(partitionId, fencingToken)` 최대값을 보관하고 더 작은 token의 이벤트를 거부**한다 | 아래 |

> ⚠️ **B-6~B-9만으로는 부족하다** (Phase 3 마감 리뷰 결함6): **거부되는 것은 우리 쪽 완료 표시뿐**이고
> **전달은 이미 나갔다.**
>
> ```
> A(token 17)  정지
> B(token 18)  이벤트 6 을 원장에 기표
> A            깨어나 이벤트 5 를 전달  → ★ 원장은 6 → 5 순서로 append
>              A 의 완료 표시만 거부된다 (B-8)
> ```
>
> **원장은 append-only라 재정렬이 불가능하다**(§3). 그러므로 **수신측이 거부해야** 한다.

> ★ **B-1(할당의 원자성)·B-2(멱등)·B-3(lease)·B-5(runId) 넷 다 이것을 못 막는다.**
> B-1은 *가져가는 것*, B-2는 *순차 재실행 가정*, B-5는 *실행 간 구분*이다.
> **소유권 세대(generation)를 표현하는 것은 fencing token뿐이다.**

### 2.4 수신측 멱등 — 정산도 (O-2 보강)

| 수신측 | 멱등 키 | 상태 |
|---|---|---|
| **원장** | `sourceEvent` | ✅ **INV-8** 유일 제약 |
| **정산** | ★ `sourceEventId` | ★ **신설** — `Settlement`에 처리한 이벤트 ID 집합 |

> ⚠️ **집합을 애그리게이트가 들면 합계 필드 문제가 된다**(DC-001).
> **별도 테이블 + 유니크 제약**으로 둔다 — `DepositReceipt`와 같은 형태다.

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 |
|---|---|
| **전역 단일 릴레이** | 순서는 완벽하나 **처리량이 릴레이 하나로 제한**되고 단일 장애점이 된다 |
| **순서 포기 + 수신측 정렬** | 수신측이 버퍼를 들어야 하고, **얼마나 기다릴지**를 또 정해야 한다. 그리고 원장은 append-only라 **재정렬이 불가능**하다 |
| **DLQ 없이 무한 재시도** | ★ **F-13 그대로** — 한 건이 전체를 막는다 |
| **DLQ 자동 재투입** | 영구 실패면 **무한 루프**가 된다. 사람이 원인을 봐야 한다 |
| **lease 시간을 늘린다** | GC 정지 시간을 **예측할 수 없다.** 늘려도 더 긴 정지가 있으면 같다 |

## 4. 결과

| | |
|---|---|
| **얻는 것** | 순서가 **장치로** 보장 · 정체가 전체를 안 막는다 · 좀비 쓰기 차단 |
| **내주는 것** | outbox에 파티션 키 컬럼 · DLQ 운영 · token 관리 |
| **새로 생기는 일** | ★ **M17**(DLQ 적재) · DLQ 재투입 절차 · **파티션 0번**(계좌 없는 이벤트) |

## 5. 되돌리는 조건

| # | 관찰되면 | 그때 할 일 |
|---|---|---|
| **R1** | DLQ 적재가 **주 1회 이상** | 수신측 계약 문제 — 스키마 진화 규칙 재검토(ADR-015) |
| **R2** | fencing token 거부가 **발생한다** (B-9 적재) | 좀비가 실재한다 — lease 시간·GC 튜닝 |
| **R3** | 파티션 0번(계좌 없는 이벤트)이 **병목이 된다** | 그 이벤트군을 별도 축으로 파티션 |
| **R4** | 순서 보장 비용이 **QS-04(1시간)를 침해**한다 | 순서가 꼭 필요한 이벤트만 O-8 적용, 나머지는 병렬 |

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | ★ **순서 시험** | 같은 계좌에 입금→출금 연속 발행 → 수신측이 **그 순서로** 받는다 |
| Phase 5 | ★ **독약 주입** | 영구 실패 이벤트 1건 → **5회 후 DLQ · 뒤 이벤트는 정상 전달** · M17 적재 |
| Phase 5 | ★ **좀비 시험** | 릴레이에 `SIGSTOP` → lease 만료 → 다른 인스턴스 인수 → `SIGCONT` → **옛 인스턴스의 쓰기가 거부**된다 |
| Phase 5 | 정산 멱등 | 같은 `sourceEventId` 재전달 → **집계가 변하지 않는다** |

> ★ **세 번째가 B-6~B-9 전용이다.** `SIGSTOP`/`SIGCONT`로 GC 정지를 흉내 낸다 —
> 리서치의 실험 시나리오 X-8이 같은 방법을 제안했다.
