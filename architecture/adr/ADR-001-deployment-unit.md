# ADR-001. 배포 단위는 **단일 모듈러 모놀리스**로 한다

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 관련: 제약 **C-01·C-02·C-03·C-04** · 품질 속성 **정합성(1)·가용성(2)·단순함** · 시나리오 **QS-01·QS-02·QS-07**

---

## 1. 맥락

Phase 2가 **바운디드 컨텍스트 6개**(C1 뱅킹 · C2 카드 · C3 결제 · C4 정산 · C5 원장 · C6 대사)를
확정했다. 이제 그것을 **몇 개의 배포 단위**로 실행할지 정해야 한다.

**지금 정해야 하는 이유**: 배포 단위는 나중에 바꾸는 비용이 가장 큰 결정 중 하나다.
데이터 이관·계약 변경·운영 절차가 전부 딸려 온다.

### 가장 무거운 입력 — 트랜잭션 경계

Phase 2가 **의식적 예외 5건**(E1~E5)을 확정했고, 각각의 참여자는 다음과 같다.

| 경계 | 참여 애그리게이트 | 걸치는 컨텍스트 |
|---|---|---|
| **E1** 승인 성립·해제·복원 | 승인 · 계좌 · 카드 · 멱등 · 취소예약 | **C1 · C2 · C3** |
| **E2** 매입 반영 | 승인 · 계좌 · 카드 · 배치 · 미수 | **C1 · C2 · C3** |
| **E3** 미수 회수 | 계좌 · 미수 · 입금수신 | C1 |
| **E4** 환불 | 승인 · 계좌 · 미수 · 배치 | **C1 · C3** |
| **E5** 입금 정정 | 계좌 · 미수 · 입금수신 | C1 |

> ★ **E1·E2가 세 컨텍스트를 한 커밋으로 묶는다.** 이것이 이 결정의 핵심 제약이다.
> 품질 속성 상충표가 *"트랜잭션 경계 안은 강한 일관성"* 으로 이미 판정했고,
> 그것은 곧 **E1·E2의 참여자가 같은 트랜잭션 자원 안에 있어야 한다**는 뜻이다.

## 2. 고려한 안

| # | 안 | 장점 | 단점 | 어느 품질을 얻고 잃나 |
|---|---|---|---|---|
| **A** | **단일 모듈러 모놀리스** — 컨텍스트를 모듈로 분리, 배포는 하나 | E1~E5가 **로컬 트랜잭션**으로 성립 · 운영 단위 1개 · 컨텍스트 경계는 코드로 유지 | 모듈 경계가 **코드 규율에 의존** · 한 모듈 장애가 전체에 영향 | 얻음: 정합성·단순함 / 잃음: 장애 격리 |
| **B** | **컨텍스트별 6개 서비스** | 컨텍스트 = 배포 단위로 경계가 **물리적으로 강제** · 개별 확장 | ★ **E1·E2가 분산 트랜잭션이 된다** · 운영 단위 6배(C-02 위반) · 2주 내 불가(C-03) | 얻음: 격리 / **잃음: 정합성(치명)** |
| **C** | **2분할** — 실시간(C1·C2·C3) / 배치(C4·C5·C6) | E1~E5가 실시간 쪽에 **온전히 들어간다** · 배치가 실시간을 방해하지 않음 | 운영 단위 2배 · 원장 기표가 프로세스를 넘음(이미 비동기라 부담은 작다) · 배포·스키마 관리 이중화 | 얻음: 배치 격리 / 잃음: 단순함 |
| **D** | **현행 유지** | — | 현행이 없다 (첫 결정) | — |

## 3. 결정

### **A. 단일 모듈러 모놀리스**

컨텍스트 6개를 **모듈 6개**로 두되, **배포 단위는 하나**로 한다.

### 왜 이것인가 — 반증 가능한 근거

| 근거 | 어디에 걸리나 |
|---|---|
| E1·E2가 **C1·C2·C3를 한 커밋**으로 요구한다. 분할하면 분산 트랜잭션이거나 보상 트랜잭션이며, 둘 다 **정합성 1순위를 내주는 것**이다 | Phase 2 E1·E2 · 품질 속성 §3 상충 2행 |
| 운영 단위가 늘면 배포·모니터링·장애 대응이 **단위 수만큼 곱해진다** | **C-02** (운영 인력 1명) |
| 관리형 인프라 없이 다중 서비스를 돌릴 수 없다 | **C-04** (예산 0) |
| 예상 부하가 **단일 인스턴스 범위**다 | **QS-01** 80 TPS · **QS-02** 400 TPS. 카카오페이 실측이 단일 서비스에서 400 TPS를 처리한다 |
| 분할이 필요해지면 **컨텍스트 경계가 이미 분할선을 갖고 있다** | Phase 2 컨텍스트 맵 |

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **B** 6개 서비스 | ★ **E1·E2가 분산 트랜잭션이 된다.** 그것은 Phase 2가 열 라운드에 걸쳐 막은 사고(이중 출금·초과 승인)를 **아키텍처가 되살리는 것**이다. 게다가 C-02·C-03을 동시에 위반한다 | E1·E2의 참여자가 줄어 한 컨텍스트에 들어오게 되면. **그러나 그것은 도메인 변경이지 아키텍처 판단이 아니다** |
| **C** 2분할 | E1~E5는 실시간 쪽에 온전히 들어가므로 **정합성은 지켜진다.** 그럼에도 기각하는 이유는 **C-02**다 — 운영 단위 2개는 배포·스키마 마이그레이션·장애 대응을 두 벌로 만든다. 그리고 배치와 실시간이 **같은 DB를 공유**하므로 격리 효과도 제한적이다 | 배치가 실시간 응답시간(QS-01)을 **실측으로** 침해할 때. 그때는 C가 첫 후보다 |
| **D** 현행 유지 | 현행이 없다 | — |

> ★ **C를 "나쁘다"고 기각한 것이 아니다.** C는 **다음 단계**이며, 되돌리는 조건 R2가 그것을 가리킨다.

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | E1~E5가 **로컬 트랜잭션**으로 성립 · 운영 단위 1개 · 배포·롤백이 한 번 |
| **내주는 것** | **장애 격리 없음** — 한 모듈의 문제가 전체에 영향 · 모듈별 개별 확장 불가 |
| **새로 생기는 일** | ★ **모듈 경계를 코드로 지키는 일.** 물리적으로 강제되지 않으므로 **아키텍처 테스트가 필요하다**(ADR-002에서 다룬다) |

### 모듈 구조

```
C1 뱅킹    Account · Receivable · DepositReceipt
C2 카드    Card
C3 결제    Authorization · ReversalTombstone · IdempotencyRecord · CaptureBatch
C4 정산    Settlement
C5 원장    JournalEntry
C6 대사    Discrepancy
```

> ⚠️ **모듈 간 직접 참조를 허용하지 않는다.** 컨텍스트 맵의 관계 유형(R1~R7)이 허용한 방향으로만
> 의존한다. 이것을 **코드 규율이 아니라 검사로** 강제하는 것이 ADR-002의 과제다.

## 5. 되돌리는 조건 ★

| # | 관찰되면 | 무엇을 뜻하나 | 그때 할 일 |
|---|---|---|---|
| **R1** | 단일 인스턴스에서 **QS-02(400 TPS)를 p99 3초로 못 지킨다** | 수직 확장 한계 | 먼저 **인스턴스 수평 증설**(HA-1~HA-5가 이미 허용) → 그래도 안 되면 분할 |
| **R2** | **배치 실행 중 실시간 응답시간이 QS-01을 침해**한다 (실측) | 배치·실시간 자원 경합 | **안 C(2분할)** 로 간다 |
| **R3** | 한 모듈의 장애가 **자금 경로 전체를 멈춘 사례**가 발생 | 장애 격리 부재의 대가가 현실화 | 해당 모듈만 분리 |
| **R4** | 모듈 간 **금지된 의존이 검사에서 반복 검출**된다 | 코드 규율로는 경계가 안 지켜진다 | 물리 분할로 강제 |

> ★ **R1의 순서가 중요하다.** 부하가 부족하면 **분할이 아니라 증설**이 먼저다.
> 분할은 정합성을 내주는 결정이고, 증설은 그렇지 않다.

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | QS-01 부하 시험 | 80 TPS에서 p99 ≤ 3초 |
| Phase 5 | QS-02 부하 시험 | 400 TPS에서 p99 ≤ 3초 · **M9~M15 불일치 0건** |
| Phase 5 | E1~E5 통합 테스트 | 각 경계가 **한 트랜잭션**으로 커밋·롤백됨 |
| Phase 6 | 아키텍처 테스트 | 모듈 간 금지된 의존 **0건** |
