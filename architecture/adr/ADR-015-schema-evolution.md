# ADR-015. 스키마·계약 진화 — expand-contract를 절차로

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: `study/11-failure-modes` **F-06 · F-17 · F-08**
- 관련: **HA-5**(expand-contract) · **ADR-011**(lazy close) · **ADR-014**(이벤트 계약)

---

## 1. 맥락 — HA-5는 선언이었다

`quality-attributes.md` **HA-5**: *스키마 변경은 expand-contract (구/신 버전 동시 가동 가능)*.

**그런데 절차를 소유한 문서가 없다.** 무엇을 어떤 순서로 하는지, **누가 "다음 단계로 가도 된다"를 판정하는지**가 없다.

### 무엇이 걸려 있나

| 대상 | 왜 |
|---|---|
| **DB 스키마** | 컬럼 드롭이 **배포 안 된 인스턴스를 죽인다**(F-06 GitHub 2025-08) |
| **이벤트 계약** | 구 버전이 새 필드를 못 읽는다 — ★ **유실이 아니라 오해라 대사가 못 잡는다** |
| ★ **동작 규칙** | 구/신이 **다른 판단**을 한다 — Knight Capital(F-17) |

### 우리에게 가장 구체적인 노출

**ADR-011 lazy close**:

```
"자금 조작이 그 거래의 귀속 영업일 마감 행을 갱신한다" (DC-005)
  → ★ 어느 버전의 거래가 행을 만드는가?
  → 구 버전은 안 만들고 신 버전은 만든다
  → 계좌마다 그날 마감 행이 있거나 없다
  → ADR-011이 없앴다고 선언한 T2 가 배포 경로로 부활한다
```

## 2. 결정

### 2.1 DB 스키마 — 5단계 + 대기 판정

```
① expand    새 컬럼 추가 (nullable · 기본값 있음). 구 버전은 모른 채 동작
   ─ 대기 ─  ★ 전 인스턴스가 ①을 본다 (마이그레이션 완료 확인)
② 이중 쓰기  신 버전이 구·신 둘 다 쓴다. 읽기는 구
   ─ 대기 ─  ★ 전 인스턴스가 ②를 배포받는다
③ 백필      과거 데이터를 신 컬럼으로. ★ 배치로 나눠서
   ─ 대기 ─  백필 완료 + 검증
④ 읽기 전환  신 버전이 신 컬럼을 읽는다. 쓰기는 여전히 둘 다
   ─ 대기 ─  일정 기간 관측 (되돌릴 수 있는 마지막 지점)
⑤ contract  구 컬럼 제거 · 이중 쓰기 중단
```

| # | 규칙 | 왜 |
|---|---|---|
| **S-1** | 각 단계 사이에 ★ **"전 인스턴스가 이전 단계를 반영했다"** 를 확인한다 | 확인 없이 넘어가면 F-17 |
| **S-2** | ★ **④까지는 되돌릴 수 있다.** ⑤는 되돌릴 수 없다 | 되돌릴 수 없는 단계를 아는 것이 중요하다 |
| **S-3** | 컬럼 **드롭·이름 변경·타입 축소**는 항상 5단계를 거친다 | ORM이 컬럼 이름을 나열한다(F-06) |
| **S-4** | 백필은 **배치로 나눈다.** 한 트랜잭션으로 하지 않는다 | 롱 트랜잭션(F-05) |
| **S-5** | DDL은 **복제 지연을 계산**하고 실행한다 | INPLACE는 복제본에서 논블로킹이 아니다(F-06 PlanetScale) |

> ★ **S-1의 "확인"이 실제로 무엇인가**: 배포 도구의 **롤아웃 완료** + 옛 버전 인스턴스 **0대**.
> *"배포했으니 됐겠지"* 가 Knight Capital의 8대 중 1대다.

### 2.2 이벤트 계약 — 더 엄격하다

**이벤트는 저장된다.** 스키마와 달리 **과거 이벤트가 남아 있고** 그것을 나중에 읽는다.

| # | 규칙 | 왜 |
|---|---|---|
| **S-6** | ★ **선택적·비의미적 필드만 추가 가능.** 삭제·이름 변경·의미 변경 금지 | 구 버전이 못 읽는다 |
| **S-6a** | ★ **분개 계정·금액 산식·멱등 키·파티션 키·귀속일에 영향을 주는 필드는 추가도 금지** — **새 이벤트 타입**을 만든다 | 아래 |
| **S-7** | **알 수 없는 필드는 무시**한다 (수신측) | 신 버전이 보낸 것을 구 버전이 받아도 죽지 않는다 |
| **S-8** | ★ **의미를 바꿔야 하면 새 이벤트 타입**을 만든다 | ⚠️ **재사용된 플래그가 Knight Capital의 직접 원인**이다 |
| **S-9** | 이벤트에 **스키마 버전**을 싣는다 | 나중에 구분할 수 있어야 한다 |

> ★ **S-6a가 왜 필요한가** (Phase 3 마감 리뷰 치명3): *"필드 추가 + 구 버전은 무시"* 는
> **문법적으로는 안전하지만 회계적으로는 아니다.**
>
> ```
> ReceivableIncurred 에 origin 이 없던 시절 → 원장은 "매입 부족분"으로 가정
>   차) 미수금 / 대) 매입사 미지급금
>
> origin 필드 추가 (DEPOSIT_REVERSAL)
>   신 버전 원장:  차) 미수금 / 대) 예치금       ← 맞다
>   구 버전 원장:  origin 을 무시 → 대) 매입사 미지급금   ★ 틀린 계정
>
> 파싱은 성공하고 차대도 균형이다. → 대사가 못 잡는다
> ```
>
> **의미를 결정하는 필드는 "추가"가 아니라 "새 타입"이다.**

> ★ **S-8이 이 절의 핵심이다.** *"이 필드 이제 다른 뜻으로 쓰자"* 가 가장 싸 보이는데
> **가장 비싸다** — 구 버전이 옛 의미로 해석하고, **그것이 유실이 아니라 오해라 대사가 못 잡는다.**

### 2.3 동작 규칙 변경 — 플래그로 가른다

★ **ADR-011 lazy close 같은 "판단이 바뀌는 변경"이 가장 위험하다.**

```
❌ 그냥 배포     구 버전은 안 닫고 신 버전은 닫는다 → 데이터가 갈린다
✅ 플래그        신 코드를 배포하되 꺼둔다 → 전 인스턴스 배포 확인 → 켠다
```

| # | 규칙 |
|---|---|
| **S-10** | ★ **자금·상태 판단이 바뀌는 변경은 플래그 뒤에** 둔다 |
| **S-11** | 플래그 전환은 **전 인스턴스 배포 확인 후** 한다 (S-1) |
| **S-12** | 플래그는 **한 곳에서** 읽는다. 인스턴스마다 다른 값을 보면 안 된다. ★ **자금 경로(E1~E5)에서 판정하는 플래그는 런타임 조회가 아니라 *전환 임계값 T*로 표현**한다 — ⚠️ **판정 기준은 `처리 영업일`(또는 배포 활성화 epoch)이지 `귀속 영업일`이 아니다** |
| **S-20** | ★ **플래그 판정일과 행 키를 분리**한다 — 판정 = **처리 시점** · `AccountDailyClose` 행 키 = **귀속 영업일**(BR-14) |

> ⚠️ **S-20이 없으면 늦게 도착한 과거 거래가 영원히 구 동작을 탄다** (Phase 3 마감 재리뷰 치명2):
>
> ```
> T = D3 · 전 인스턴스 신 버전
> D4 에 D2 귀속 매입 40 도착
>   귀속 영업일 D2 < T  →  구 동작 선택
>   ★ 그런데 구 동작이던 DailySnapshot 은 폐기됐다 → 마감 행이 안 생긴다
>   원장에는 D2 출금 40 이 기표되는데 M12 좌변은 과거 값 또는 0
> ```
>
> ★ **배포가 100% 끝난 뒤에도 과거 파일은 계속 off 경로로 간다.**
> 판정은 *"지금 이 코드가 신 버전인가"* 이지 *"이 거래가 언제 것인가"* 가 아니다.

> ★ **왜 임계값인가** (Phase 3 마감 리뷰 H-7): *"한 곳"* 을 안 정하면 셋 다 막힌다.
>
> | 읽는 위치 | 무엇에 걸리나 |
> |---|---|
> | 인스턴스 기동 시 캐시 | **S-12 위반** + **HA-1**(인스턴스 로컬 상태로 자금 판단 금지) — 마감 행 생성은 **자금 판단**이다 |
> | 외부 설정 서비스 호출 | 자금 트랜잭션 안에 **네트워크 호출** — 느려지면 **계좌 락을 쥔 채 대기**(F-16 그 자체). ADR-013 §2.2가 이 대상에 브레이커를 안 정했다 |
> | 자금 DB 설정 테이블 | W-1·T-10은 만족하나 **자금 조작마다 핫 로우 읽기 1회** |
>
> **T는 배포 설정에 실려 오므로 자금 트랜잭션 안에서 추가 조회·추가 커넥션이 없다**
> (ADR-007 W-1 · ADR-013 T-10·T-11 무영향).
> 전환 확정 = S-11(전 인스턴스 배포 확인) 뒤에 **다음 영업일을 T로 잡는 것**이며,
> ★ **이것이 S-18(영업일 경계 전환)을 절차가 아니라 자료구조로 강제**한다.
>
> 부수 효과로 **S-13의 함정도 한 값으로 드러난다** — T를 미래로 미루는 것은 안전하고,
> **이미 지난 T를 되돌리는 것만이 위험하다.**
| **S-13** | ★ **전환 후 되돌릴 수 있는지를 미리 판정**한다 — 되돌릴 수 없으면 그것을 적는다 |
| **S-18** | ★ **마감 행 전환은 영업일 경계에서만** 한다. 켜기 전 전 계좌의 **마지막 마감 행이 기준 시점에 정렬돼 있는지 확인**한다 |
| **S-19** | ★ **마감 행 플래그가 off인 동안 M12·M14를 실행하지 않는다.** 좌변이 **없는** 것이지 **옛 좌변이 있는** 것이 아니다 — **M16과 같은 취급**(기준 부재를 불일치로 적재) |

> ⚠️ **S-19가 필요한 이유 — off가 안전 상태가 아니다** (Phase 3 마감 리뷰 H-6):
> §2.3의 플래그 모델은 *구 동작 ↔ 신 동작*을 전제하는데, **마감 행의 구 동작이던 `DailySnapshot`은
> ADR-011 Q-3로 폐기됐다.** 그래서 **off = 옛 동작이 아니라 좌변 생성 자체가 없음**이다.
>
> DC-005의 대사 규칙(*행이 없으면 = 0*)과 합치면 — **플래그를 끈 채 배포한 첫 영업일 대사는
> 전 계좌의 M12 좌변을 0으로 읽는다.** 원장 보조부에는 실잔액이 있으므로 **전 계좌 허위 불일치**다.
>
> ★ **"플래그는 꺼두면 안전하다"가 여기서 거짓이다.** S-13의 짝이다.
### 2.4 채번 (F-08)

| # | 규칙 | 왜 |
|---|---|---|
| **S-14** | 승인번호·전표번호는 ★ **블록 할당** 방식으로 한다 (인스턴스가 N개씩 미리 받는다) | 중앙 시퀀스는 **한 행이 직렬화 지점**이 된다 |
| **S-15** | ★ **채번이 별도 커넥션을 잡지 않는다** | F-03 우아한형제들 — 한 작업이 커넥션 둘이면 풀 데드락 |
| **S-16** | 번호는 **시간순 대략 증가**해야 한다 (인덱스 단편화 방지) | UUID v4는 삽입이 흩어진다 |
| **S-17** | 블록 미사용분은 **버린다** (재사용하지 않는다) | 재사용은 순서 가정을 깬다 |

> ⚠️ **형식(자릿수·구성)은 Phase 4 계약 설계에서 정한다.** 여기서는 **방식**만 정한다.

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 |
|---|---|
| **점검 시간(downtime) 배포** | 가용성 2순위 포기. 그리고 *"점검 창이 있으니 괜찮다"* 가 **절차를 안 만드는 핑계**가 된다 |
| **블루-그린으로 스키마도 전환** | DB는 공유되므로 **스키마는 블루-그린이 안 된다.** 앱만 가능하다 |
| **이벤트 스키마에 upcasting** | 과거 이벤트를 변환하는 계층을 **영구히** 안고 간다. **S-6(추가만)** 으로 애초에 필요 없게 만드는 것이 싸다 |
| **채번을 UUID로** | 병목은 없지만 **인덱스 단편화**와 **순서 부재**의 대가가 크다(ADR-014 O-8이 순번을 요구한다) |

## 5. 되돌리는 조건

| # | 관찰되면 | 그때 할 일 |
|---|---|---|
| **R1** | 5단계가 **너무 느려 변경이 밀린다** | 변경 유형별로 단계를 줄인다 (컬럼 **추가만**은 ①만으로 충분) |
| **R2** | 플래그가 **10개를 넘어 조합을 못 센다** | 전환 완료된 플래그를 **정리하는 절차**를 만든다 |
| **R3** | 이벤트에 **필드 추가만으로 표현 못 하는** 변경이 반복된다 | 이벤트 설계 재검토 — S-8(새 타입)이 답인지 본다 |
| **R4** | 블록 채번의 **미사용분 낭비가 문제**가 된다 | 블록 크기 축소 |

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | ★ **구/신 동시 기동** | 구·신 버전을 동시에 띄우고 자금 경로 실행 → **데이터 갈림 0건** |
| Phase 5 | 컬럼 드롭 시나리오 | 5단계로 진행 → 각 단계에서 **구 버전이 죽지 않는다** |
| Phase 5 | ★ **플래그 전환** | 끈 상태 → 전 인스턴스 배포 → 켬 → **마감 행이 일관되게 생성** |
| Phase 5 | ★ **off 상태 대사** | 플래그 off로 대사 실행 → **M12·M14 미실행 + 기준 부재 적재**(S-19). ⚠️ **허위 불일치 0건**이 통과 기준 |
| Phase 5 | 이벤트 필드 추가 | 신 버전이 필드 추가 → **구 버전이 무시하고 정상 처리**(S-7) |
| Phase 5 | 채번 | 다중 인스턴스에서 **중복 0 · 시간순 대략 증가**(S-14·S-16) |

> ★ **첫 항목이 F-17 전용이다.** 리서치의 실험 시나리오 X-14가 같은 방법을 제안했다.
