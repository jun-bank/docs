# ADR-029. 컴포넌트별 내부 아키텍처 — **바깥 경계는 정본을 따르고, 안쪽은 도메인 깊이 × 언어 관용구에 맞춘다**

- 일자: 2026-08-07
- 상태: **채택**
- 결정자: 사용자 · AI 페어 (2026-08-07 대화 — "파이프라인·레이어드·클린·모듈리스를 컴포넌트마다 다르게 가는 게 맞나")
- 근거: 사용자 발의 · ADR-002(모듈 그래프·헥사고날) · ADR-010(배포 3단위) · ADR-028(언어 — 서비스=Kotlin·인프라=Go) · C-08(도구·구조 최소주의) · usecases K-1(판정 순서 파이프라인)
- 관련: 각 리포 구현이 이 문서를 내부 구조의 근거로 삼는다

---

## 1. 맥락 — "어느 아키텍처가 최선인가"는 틀린 물음이다

구현을 앞두고 내부 구조를 정해야 한다. 유혹은 하나의 아키텍처(예: 클린 아키텍처)를 전 컴포넌트에 균일하게 바르는 것이다. 그러나 우리 컴포넌트는 **도메인 깊이**와 **언어 관용구**가 서로 다르다. 은행 코어는 여섯 컨텍스트(C1 뱅킹·C2 카드·C3 결제·C6 대사·C7 인증·C8 운영 — ADR-010)에 애그리게이트 15종·조작 80·상태 기계 11종의 깊은 도메인이고, 인프라 dispatcher는 고정 인자를 받아 명령을 실행하는 도메인이 거의 없는 도구다. 같은 옷을 입히면 한쪽은 과설계, 다른 쪽은 과소설계가 된다.

바깥 경계는 이미 정본이 정했다 — 헥사고날 포트-어댑터(ADR-002)·모듈리스 배포 3단위(ADR-010)·언어 2체제(ADR-028). 이 문서가 정하는 것은 **그 경계 안쪽의 내부 구조**이며, 원칙은 하나다: **도메인 깊이 × 언어 관용구에 맞춘다.**

## 2. 결정

**IA-1. 서비스 레이어(Kotlin 코어·정산·원장) = 헥사고날 + 유스케이스 파사드 + 파이프라인 모양의 내부 오케스트레이션.** 바깥은 ADR-002 포트-어댑터. 유스케이스(애플리케이션 서비스)가 파사드가 되고, 그 내부는 도메인 조작을 순서대로 부르는 **명시적 스테이지 파이프라인**이다. 근거: **순서가 정본으로 확정된 유스케이스**가 판정 순서 파이프라인으로 문서화되어 있다(예: UC-01 = 멱등→예약→카드→자금→authorize의 고유 실행 순서, 실패 시 조기 이탈 = Cockburn 확장 1:1). ⚠️ 이 파이프라인 모양은 **그런 유스케이스에 한한다** — K-1은 채널별 오류 판정 순서 규약(사람 3단·시스템 X-10 4단)이지 전 서비스의 공통 구조가 아니다. 순서가 확정되지 않은 조회·집계 유스케이스는 파이프라인을 강제하지 않는다.

**IA-2. 파이프라인은 모양이지 프레임워크가 아니다.** 범용 Stage 추상·체인 빌더를 도입하지 않는다. 스테이지는 한 트랜잭션·한 컨텍스트를 공유하고 분기가 복잡해 무거운 파이프라인 추상이 도메인과 싸운다. 가치는 "스테이지가 코드에 순서대로 보인다"까지다. ★ **판정 기준(리뷰어용)**: 허용 = 유스케이스 함수가 도메인 조작을 순서대로 호출하는 명시 코드 · 금지 = 범용 `Stage`/`Filter` 인터페이스, 단계 등록·조립 runner/DSL, DI로 스테이지 집합을 주입해 순서를 런타임에 정하는 것(= 사내 프레임워크). 판정 단위는 유스케이스 하나이고 검증은 리뷰가 한다. 클린/레이어드는 "도메인이 중심" 방향으로만 지키고 4겹 폴더 의식은 하지 않는다.

**IA-3. 코어는 모듈리스다.** 코어 여섯 컨텍스트(C1 뱅킹·C2 카드·C3 결제·C6 대사·C7 인증·C8 운영 — ADR-010)가 한 배포물 안 모듈로 산다. 모듈 경계의 주 강제는 **port 빌드 모듈 분리**(ADR-002 — 컴파일이 역방향 의존을 막는다)이고, ArchUnit이 컴파일 밖(리플렉션·모듈 내 레이어·shared 침투)을 보완한다. ⚠️ ArchUnit은 도구만 확정(1.5)됐고 규칙 이식 전이라 현재 실행 규칙 0건이다(dev-conventions §7.1) — 규칙 이식이 이 모듈리스의 미완 선행이다.

**IA-4. 인프라(Go)는 컴포넌트마다 다른 모양이고, Go 관용구를 따른다.**
- **agent** = 두 층으로 나눈다. ⑴ **HTTP 진입 미들웨어**(auth → validate → 멱등 단락) = Go `http.Handler` 체인. ⑵ **배포 오케스트레이션**(requestId 선점·모드 버전 검증과 락 획득의 원자 경계·단계별 내구 상태·UNKNOWN 조회 전이·이력 기록과 락 해제의 트랜잭션 — ADR-027 DO-10·16·17) = 상태를 가진 오케스트레이터. ⚠️ 미들웨어의 선형성이 이 상태·트랜잭션 경계를 가리지 않도록 둘을 분리한다.
- **dispatcher** = 평평한 명령 실행기. 고정 열거 인자 스위치. 도메인이 없으므로 레이어·클린 도입은 과설계 — 평평하게 둔다.
- **watchdog** = 제어 루프 + 작은 상태 기계(폴링 → 판정 → 조치). 파이프라인도 클린도 아니다.

**IA-5. Go에 Kotlin/Spring 클린 아키텍처를 이식하지 않는다.** `domain/application/infrastructure` 4겹 폴더·클린 의식은 Go 관용구(평평한 패키지·package-by-feature·소비 지점 인터페이스)에 반한다. 이식하면 Go를 고른 이유(작은 코드 표면·감사 용이 — ADR-028)를 스스로 버린다. 인프라 도구는 Go답게 짠다. ★ **최소 구조 계약(도구 즉시 지목은 아님, 요구·검사 책임만)**: 패키지 경계·의존 방향은 `internal/` 배치 + `go vet`·`go list`(의존 그래프) + 리뷰가 본다(Go엔 ArchUnit이 없으므로 이 셋이 대체). dispatcher의 허용 import는 닫힌 목록으로 리뷰가 지킨다. watchdog의 상태 전이 완결성은 테스트가 본다. 검사 도구 확정은 [구현 검증].

## 3. 기각한 대안

- **A. 전 컴포넌트 클린 아키텍처 균일 적용** — dispatcher처럼 도메인 없는 도구에 4겹을 바르면 순수 과설계이고, Go 관용구에도 반한다(IA-5). 균일함은 일관성이 아니라 부적합이다.
- **B. 서비스 레이어에 범용 파이프라인 프레임워크** — 추상 Stage·체인 DSL. 우리 스테이지의 공유 트랜잭션·복잡 분기와 싸운다(IA-2). 모양만 취하고 프레임워크는 버린다.
- **C. 코어를 마이크로서비스로 분해** — ADR-010이 이미 배포 3단위로 기각. 모듈리스가 경계는 지키면서 분산 비용은 피한다.
- **D. 인프라를 서비스 레이어와 같은 구조로** — 도메인 깊이가 달라 부적합(IA-4). 세 도구가 서로도 다르다.

## 4. 결과

- 좋은 것: 각 컴포넌트가 자기 모양에 맞는 최소 구조 · Go·Kotlin 각 관용구 존중(언어 선택의 이유를 코드가 배신하지 않는다) · 유스케이스 파이프라인이 문서(K-1)와 코드가 같은 모양.
- 나쁜 것(감수): "하나의 아키텍처"가 아니라 컴포넌트마다 판단이 필요하다 — 신규 컴포넌트는 이 문서의 원칙(도메인 깊이 × 언어 관용구)으로 그때 판정한다. 균일 규칙보다 판단 비용이 있으나, 그 판단 기준을 이 문서가 고정한다.
- 되돌리는 조건: **R1** 서비스 레이어 스테이지의 재사용·조합 요구가 실증되면 **IA-2를 재검한다**(재사용 요구만으로 프레임워크를 도입하지 않는다 — C-08: 조합 계약·명시 코드로 불가하다는 증거·후보 적합성 판정이 뒤따라야 도입) **R2** 인프라 도구가 도메인 판정을 담기 시작하면(ADR-028 R1과 같은 신호 — 그 부분은 서비스 레이어로).
