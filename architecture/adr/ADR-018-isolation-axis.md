# ADR-018. 격리 축 — "지금 안 하면 못 하는 것"만 선반영한다

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: **BR-54·58** · RQ-5(테넌트 일반화 대비 — 인터뷰 확정) · 멀티테넌시 전수 스캔
- 관련: **ADR-009**(K-1 — 같은 형태의 선례) · **ADR-012**(인덱스 계약) · **ADR-015**(S-6a) · **ADR-016**

---

## 1. 맥락 — 격리 축과 파티션 축은 다르다

`study/09`는 *"격리 축과 파티션 축이 일치한다"* 고 적었지만 **부정확하다** — ADR-009 전문에
"고객"은 0회 등장하고, E1 참여자 유도는 전부 **계좌ID**다. 실제 소유 축 현황(전수 스캔):

| 사실 | |
|---|---|
| `CustomerId`를 든 애그리게이트 = **2종뿐** (계좌·카드) | 승인은 계좌ID 경유로만 소유를 안다 |
| 격리 축이 전무한 4종 = 멱등·취소예약·매입배치·정산 | 키가 전부 **외부(매입사) 생성·시간·파일** |
| 조직/지점 축 = 문서 전체 **0회** | `Customer` 애그리게이트 자체가 없다 |
| 캐시 키 규정 = 아키텍처에 **없음** (도입 조건만 2곳) | L6 누수의 자리가 비어 있다 |

### 시점 제약 — 왜 지금인가

- **ADR-009 §1의 논증이 그대로 적용된다**: 축 컬럼·조회 계약 형태는 *"나중에 정하면 전부 다시 짜야 한다."* K-1(*"유도 가능해도 저장한다"*)이 정확히 같은 형태의 선례다.
- **ADR-015 S-6a**: 의미 필드는 기존 이벤트에 추가 금지 — 이벤트 계약이 굳는 **Phase 4가 유일한 창**이다.
- 반대 방향의 제약: **ADR-012가 인덱스 선두를 계약으로 못박았다** — 축 컬럼이 그것을 건드리면 갭 락이 전 계좌로 번진다.

## 2. 결정

| # | 규칙 | 왜 |
|---|---|---|
| **IS-1** | **고객 소유가 성립하는 저장물은 소유 축 컬럼(`ownerId` = 고객ID)을 갖는다 — 유도 가능해도 저장한다.** 대상: 계좌 · 카드 · 승인 · 미수 · 입금수신 · 이동 행(`AccountDailyMovement`). ★ K-1과 같은 형태·같은 이유. ★ **이름 계약: 저장 컬럼명 = `ownerId`, 값 = `CustomerId`** — 문서 참조 표의 "회원 `CustomerId`"와 같은 것이다(리뷰 R19 — 두 이름이 각각 굳는 것을 막는다) | 조회 경로(BR-58)가 축을 따라간다 — 나중에 넣으면 전 테이블 재작성(study/09 §6 *"지금 안 하면 못 하는 것"*) |
| **IS-2** | ★ **축이 없는 4종(멱등·취소예약·매입배치·정산)에는 넣지 않는다** — 키의 본질이 외부 식별자·파일·영업일이다. 파일 단위 집합이 계좌로 안 나뉘는 것(O-3)과 같은 이유로 **고객으로도 안 나뉜다**. ★ **잔여 저장물 판정(전수 — 루프 3 R3-07·재점검 정밀화)**: 전표 = `subjectId`(계좌 등 **보조부 식별자** — 소유 축과 **동형이되 값이 다르다**: 고객은 계좌 경유 유도, INV-7) · 불일치 = `subject` 다형(유형별 축) · **승인 요청 = 대상 조작 인자 속 대상 식별자**가 스코프 판정 축 · **감사 기록 = AD-8의 스코프 필드**(대상의 `ownerId`/조직)가 축(BR-58 운영자 스코프 조회의 대상) | 본질이 아닌 축을 강제하면 O-3와 같은 미해결이 하나 더 생길 뿐이다. 이 4종의 격리는 **접근 경로(ADR-016)가 지킨다** |
| **IS-3** | **유일성 키·인덱스 선두·파티션 판정 축은 불변이다** — 축 컬럼은 보조 필터·보조 인덱스로만 쓴다. ADR-012의 `(accountId, incurredBusinessDate, receivableId)` 계약을 건드리지 않는다 | 선두가 바뀌면 갭 락이 전 계좌로 번진다(ADR-012). 파티션은 여전히 계좌ID다(ADR-009) |
| **IS-4** | 조직·지점 스코프 축은 **운영자 쪽에 둔다** — 운영자 계정의 소속(C7)과 계좌의 개설 조직(C1 참조 컬럼)만. 거래·이벤트에는 싣지 않는다 | 스코프 판정은 "운영자가 어디 소속인가 × 대상이 어디 것인가"로 충분하다 — 전 저장물에 3축을 다 넣는 것은 요구 없는 확장 |
| **IS-5** | **격리 축 필드는 Phase 4 이벤트 계약 최초 설계에 포함한다** — 문서 모델의 **자금 이벤트에도 지금 얹지 않는다**(원장 언어 순수성 — ADR-017 AD-7의 선). 계약 발행 후의 추가는 S-6a(새 이벤트 타입) | ADR-015 자기 규칙 준수 + 행위자 선(AD-7)과 일관. 계약이 굳기 전 = "추가"가 아니라 "최초 설계" |
| **IS-6** | ★ **캐시가 도입되는 시점에 캐시 키에는 주체 범위가 반드시 들어간다** — 도입 조건(ADR-011 R1 · DC-001)이 발화할 때의 의무를 지금 규정한다 | L6(캐시 키 누수)는 도입 순간에 안 넣으면 그대로 남의 결과가 반환된다. 자리가 비어 있는 지금이 규정을 심을 유일한 시점 |
| **IS-7** | **테넌트 축은 지금 만들지 않는다.** 일반화는 형태로 보장한다 — 소유 축 컬럼(IS-1)과 주체 인자 계약(AU-1)이 *"축이 하나 더 늘 수 있는"* 자리다. 격리 등급 승격(DB·스키마 분리)도 하지 않는다(D-01) | 요구 없는 축은 근거 없는 큰 수와 같다(D-03의 판단). 컬럼 추가는 expand-contract(ADR-015)로 나중에 가능 — **계약 형태만이 "지금 안 하면 못 하는 것"** 이다 |

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **A. `tenantId`를 지금 전 테이블에** | 테넌트 요구가 아직 없다 — 요구 없는 축은 오버엔지니어링(constraints §0의 금지선) | 실제 테넌트(기관·브랜드) 요구가 오면 IS-1의 자리에 expand-contract로 |
| **B. DB·스키마 분리로 격리** | D-01(수평 분할 포기)과 같은 선 — 마이그레이션 N회·부분 적용 문제(study/09 §4). 인터뷰에서 명시 배제 | 대형 테넌트 요구 + 운영 인력 |
| **C. 전 저장물에 3축(고객·조직·테넌트) 완비** | IS-2·IS-4의 반대 방향 — 본질이 아닌 축이 4종에서 O-3형 미해결을 양산한다 | — |

## 4. 결과

- Phase 4 계약·Phase 5 스키마의 **선행 제약**: IS-1 대상 6종의 축 컬럼, 이벤트 계약의 축·행위자 필드, 캐시 키 규정.
- 데이터 뷰 §1의 "소유자"(컨텍스트)와 이 문서의 "소유 축"(고객)은 **다른 개념**이다 — 용어 충돌을 B-5에서 명시한다.

## 5. 되돌리는 조건

| 신호 | 그때 |
|---|---|
| IS-2의 4종에서 격리 사고 경로가 실제로 발견된다 | 접근 경로 통제(ADR-016)가 뚫린 것 — 축 추가가 아니라 **경로부터** 재점검 |
| 한 고객의 계좌 수가 커져 고객 단위 대사·조회가 필요해진다 | 고객 단위 RC(대사 불변식) 신설 검토 — 지금은 계좌·카드 단위뿐 |
| 테넌트 요구 수신 | IS-7 해제 — D-04 재작성본의 되돌리는 조건(B-5)을 따른다 |

## 6. 검증

- ① IS-1 대상 표 ↔ 애그리게이트 명세의 양방향 대응 (소유 축이 있어야 할 곳에 다 있고, IS-2 4종에는 없다)
- ② ADR-012 인덱스 계약 문자열이 변경되지 않았는지 (diff 0)
- ③ Phase 4 이벤트 계약 설계 시 이 ADR의 IS-5가 입력으로 인용되는지
