# ADR-013. 타임아웃 계층과 자원 격리

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: `study/11-failure-modes` **F-09 · F-16 · F-03**
- 관련: **BR-01**(p99 3초) · **ADR-012**(재시도) · 품질 속성 **가용성(2)** · 시나리오 **QS-01·QS-06**

---

## 1. 맥락

**BR-01은 목표값이지 장치가 아니다.** *"p99 3초"* 를 적어도 **3초에 무엇이 일어나는지**가 없다.

### 무엇이 문제인가 (F-16)

```
승인이 3초에 포기하고 거절 응답
  → ★ DB 트랜잭션이 안 죽으면 계좌 로우가 계속 잠겨 있다
  → 다음 승인이 그 락을 기다린다 → 줄줄이 느려진다
  → 매입사 타임아웃 → 망취소 → 그 망취소도 같은 락을 원한다
```

**바깥 값은 리서치가 확보했는데 안쪽 계층이 없다.**

| 계층 | 값 | 출처 |
|---|---|---|
| 매입사 규약 | **25초 권장** | [1차] Worldpay ISO 8583 Ref Guide V2.63 |
| Mastercard 프로세서 | **7초** (초과 시 STIP) | [2차] Mastercard Developers |
| 우리 목표 | **p99 3초** | BR-01 (자체 가정) |
| **DB 쿼리** | ❓ | **없다** |
| **락 대기** | ❓ | **없다** |

---

## 2. 결정

### 2.1 타임아웃 계층 — 안으로 갈수록 짧다

```
매입사 규약        25초   (상대가 정한다)
  └ 우리 응답      3초    BR-01 · QS-06
      └ 애플리케이션 트랜잭션  2.5초
          └ DB 쿼리          1초
              └ 락 대기       0.5초
```

| # | 규칙 | 왜 |
|---|---|---|
| **T-1** | **하위 타임아웃 < 상위 타임아웃.** 예외 없다 | 역전되면 상위가 포기해도 **하위가 자원을 계속 잡는다** |
| **T-2** | ★ **상위가 포기하면 하위를 실제로 취소**한다 | 전파가 없으면 T-1이 무의미하다 |
| **T-3** | 락 대기 타임아웃을 **명시**한다 (`innodb_lock_wait_timeout` 기본 50초는 **너무 길다**) | 기본값은 3초 목표의 16배다 |
| **T-4** | 타임아웃 값은 **설정**이며 코드에 박지 않는다 | 실측 후 조정한다 |

> ★ **T-3이 가장 자주 빠진다.** 기본값 50초는 *"배치용"* 이고, 실시간 승인 경로에서는
> **그 자체가 장애**다. 락을 50초 기다리는 요청이 스레드를 50초 묶는다.

### 2.2 서킷 브레이커 — 대기 자체를 없앤다

**재시도만으로는 F-09를 못 막는다.** 느린 대상을 계속 부르는 것이 문제다.

| 대상 | 브레이커 | 열리면 |
|---|---|---|
| **매입사 게이트웨이** (아웃바운드) | ✅ | 즉시 실패 → 망취소 예약 경로로 |
| **DB** | ❌ | 브레이커를 열면 **전부 실패**한다. 대신 **풀·타임아웃**으로 다룬다 |
| **Outbox 릴레이 → 위성** | ✅ | 전달 중단, outbox에 쌓임 (유실 없음) |

| # | 규칙 |
|---|---|
| **T-5** | 브레이커는 **아웃바운드에만** 둔다. DB에는 두지 않는다 |
| **T-6** | 임계·반열림 시간은 **설정**이며 **실측 후** 정한다 (초기값은 가정임을 명시) |
| **T-7** | 브레이커가 열린 것을 **적재**한다 — 조용히 거절하지 않는다 |

> ★ **T-5가 중요하다.** *"의존 대상이니 브레이커"* 라고 DB에 붙이면,
> 열리는 순간 **전 요청이 실패**한다. DB는 **분리와 상한**으로 다루는 것이다.

### 2.3 자원 격리 — 풀을 나눈다 (F-03)

**배치와 실시간이 같은 DB를 친다**(ADR-010). 풀을 공유하면 배치가 실시간을 먹는다.

| 풀 | 용도 | 크기 근거 |
|---|---|---|
| **자금 경로** | E1~E5 | QS-02 400 TPS × 평균 보유 시간 |
| **조회 전용** | 조회 API | 별도 — 자금 경로를 침해하지 않는다 |
| **배치** | 대사·정산·만료 | ★ **작게** — 배치는 느려도 되지만 실시간을 막으면 안 된다 |

| # | 규칙 |
|---|---|
| **T-8** | 세 풀을 **분리**한다. 총합이 DB `max_connections`를 넘지 않는다 |
| **T-9** | ★ **총 커넥션 = 인스턴스 수 × 풀 합계** 를 계산해 상한을 검증한다 |
| **T-10** | 한 작업이 **커넥션을 둘 이상 잡지 않는다** (F-03 우아한형제들) |

> ★ **T-9가 HA-1~HA-5와 맞물린다.** 인스턴스를 늘리면 커넥션도 배로 는다 —
> **증설이 DB를 죽이는 경로**이고, `study/10` §4가 말한 *"상태 있는 것은 늘려도 안 된다"* 다.

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 |
|---|---|
| **타임아웃을 한 값으로 통일** | 계층이 없으면 F-16이 그대로 난다 |
| **DB에도 브레이커** | 열리는 순간 전 요청 실패 (§2.2) |
| **풀 공유 + 우선순위 큐** | 우선순위는 **대기 순서**를 정할 뿐 **점유**를 못 막는다. 배치가 이미 잡은 커넥션은 안 뺏긴다 |
| **타임아웃 없이 큐잉** | 대기가 쌓이면 **응답이 무의미해진 요청**을 처리하게 된다 |

## 4. 결과

| | |
|---|---|
| **얻는 것** | 포기가 **자원 해제로 이어진다** · 배치가 실시간을 못 먹는다 · 느린 대상이 전체를 안 물린다 |
| **내주는 것** | 설정 항목이 는다 · 풀을 나누면 **총 커넥션 여유가 준다** |
| **새로 생기는 일** | ★ **실측 후 조정** — 초기값은 전부 가정이다 |

### 초기값 (전부 [미검증] 가정)

| 항목 | 초기값 | 근거 |
|---|---|---|
| 우리 응답 | 3초 | BR-01 |
| 앱 트랜잭션 | 2.5초 | [유도] 응답의 83% |
| DB 쿼리 | 1초 | [미검증] |
| 락 대기 | 0.5초 | [미검증] |
| 브레이커 임계 | 실패율 50% / 10초 창 | [미검증] |

> ⚠️ **다섯 개 중 셋이 [미검증]이다.** QS-01·QS-02 실측 후 조정하며,
> **그때까지 이 값을 근거로 다른 결정을 하지 않는다.**

## 5. 되돌리는 조건

| # | 관찰되면 | 그때 할 일 |
|---|---|---|
| **R1** | 락 대기 타임아웃(0.5초)으로 인한 **거절이 1%를 넘는다** | 값 상향 → 그래도 안 되면 락 경합 자체를 본다(ADR-012 R1) |
| **R2** | 브레이커가 **하루 10회 이상** 열린다 | 매입사 응답 특성 재측정 · 임계 조정 |
| **R3** | 배치 풀이 작아 **QS-04(1시간)를 못 지킨다** | 배치 풀 확대 → 그래도 안 되면 배치 전용 읽기 경로 |
| **R4** | **총 커넥션이 `max_connections`의 80%를 넘는다** | 풀 축소 또는 DB 상한 조정 |

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | ★ **타임아웃 계층 시험** | 매입사 무응답 주입 → 우리 응답 **3초 이내** · **락이 3초 안에 해제**된다 |
| Phase 5 | 브레이커 | 매입사 실패율 주입 → 브레이커 열림 → **스레드 점유 0** |
| Phase 5 | 풀 격리 | 배치 실행 중 **자금 경로 풀 사용률이 안 오른다** |
| Phase 5 | ★ **커넥션 상한** | 인스턴스 N대에서 총 커넥션 = N × 풀 합계 **< max_connections** |

> ★ **첫 항목의 두 번째 조건이 F-16 전용이다.** *"응답이 3초"* 만 재면 락이 남는 것을 놓친다.
