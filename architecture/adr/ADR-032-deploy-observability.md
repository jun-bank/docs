# ADR-032. 배포 관제·플로우 트레이싱 — **배포를 실시간으로 보고, 요청은 트레이싱으로 따라간다**

- 일자: 2026-08-12
- 상태: **채택** (구조 확정 · 관제 UI·트레이싱 도구는 `[구현 검증]`)
- 결정자: 사용자 · AI 페어 (2026-08-12 대화 — "각 서버 배포를 실시간 시각화·모니터링, 요청이 어디까지 왔나")
- 근거: **ADR-027 DO-6**(관제 v1 — 이력·가동 태그·락·모드) · **DO-12**(관제 LAN 전용) · **IN-7**(관제 UI 미구현) · **ADR-023**(관측 — OB-1 독립성 · OB-2 노출 규약 · OB-7 범주 구분) · **ADR-031**(블루-그린 — 관제가 시각화할 상태 · 큐를 트레이싱으로 대체) · **C-08**(도구 최소주의)
- 관련: **ADR-027**(DO-6 · DO-12 · IN-7) · **ADR-023**(관측 축) · **ADR-031**(블루-그린 상태) · **ADR-017**(감사 — 배포 이력과 다른 축) · 후속(관제 UI 구현 · 트레이싱 도구 선정)
- 규칙 ID 접두어: **`DV-`** (deploy visibility)

---

## 1. 맥락 — 배포 이력은 있는데, 보이지 않는다

ADR-027 DO-6이 관제 v1을 정했다 — 대상별 현재/직전 가동 버전·마지막 배포 이력·배포 창 락 점유·모드를 보여주는 최소 페이지. 그러나 IN-7이 *"미구현"* 으로 남겨 두었고, ADR-031이 블루-그린 전환을 확정하면서 **볼 것이 하나 늘었다**: 전환이 실시간으로 어디까지 왔는가 — green이 떴나, 라우트가 옮겨갔나, blue가 드레인 중인가.

여기에 두 요구가 붙는다. 하나는 **배포 플로우의 실시간 시각화**(서버별 블루-그린 진행). 다른 하나는 **요청이 어디서 어디까지 진행 중인가** — ADR-031이 큐를 기각하면서 그 가시성의 자리를 트레이싱에 넘겼다(BG-3의 짝).

핵심은 **축을 섞지 않는 것**이다(ADR-023 OB-7). 배포 관제, 호스트·컨테이너 헬스, 애플리케이션 관측은 서로 다른 것을 보는 서로 다른 도구다 — 한 화면에 놓는 것과 한 수집기로 걷는 것은 다른 결정이다.

## 2. 결정 — 세 축을 나누고, 배포 관제와 트레이싱을 세운다

| # | 규칙 | 왜 |
|---|---|---|
| **DV-1** | **배포 관제 v1 = DO-6 넷 + 블루-그린 상태다.** 보여주는 것 — 대상별 현재/직전 가동 버전 · 마지막 배포 이력(요청자·커밋·각 단계 결과·거절 사유) · 배포 창 락 점유 · 모드 + **(신규) 블루-그린 상태**(어느 인스턴스가 떴나 · green 헬스 · 라우트 전환 진행 · blue 드레인 진행 — ADR-031). 후보 = **Next.js BFF**(대시보드 제품을 도입하지 않는다 — C-08 · IN-7). ★ **기능·인증 계약(문서 결정)**: ⑴ **기능 범위 = 조회 + 모드 토글**이다 — 모드 토글은 DO-5가 관제에 준 소유이므로 관제는 읽기 전용이 아니라 **변경 표면을 하나 가진 UI**다(그 외 조작 없음 — 배포 방아쇠·롤백은 관제 밖) ⑵ **조회·변경 모두 인증 필수**(주체 = 운영자) · **변경(모드 토글)은 CSRF 방어 필수** · ⚠️ **LAN 전용(DO-12)은 노출 축소막이지 인증의 대체가 아니다** — 인증 형식·세션·CSRF 구현은 `[구현 검증]`(IV-38). ★ **상태 진실성 계약**: ⑶ 화면 상태는 **2층을 구별해 표시**한다 — **보고 상태**(실행 주체가 기록한 단계 — 정본 = 배포 이력 DB·DO-17, `requestId`에 귀속) vs **관측 상태**(라우트의 실제 target — 정본 = SCG 설정(BG-1 ⑵) · 인스턴스 생존). 이력은 실행자가 적은 것일 뿐 실제와 어긋날 수 있다 — **어긋나거나 관측이 닿지 않으면 `STALE/UNKNOWN`으로 표시**하고 최종 갱신 시각을 함께 적는다 ⑷ **단계 전이는 단조**다 — 역행 표시가 관측되면 정상 진행이 아니라 이상으로 표시한다. 실시간 전송 방식(polling/SSE)·갱신 간격은 `[구현 검증]` | *"무엇이 돌고 있는지 아무도 모른다"* 가 RL-7이 막으려던 상태다(실측으로 한 번 일어난 사건). 이력이 **있는 것**과 **보이는 것**은 다르다. 블루-그린은 진행 중 상태(전환·드레인)가 중요한데, ⚠️ **오래된 `DRAINING` 표시는 실제 드레인과 관제 단절을 구별하지 못한다** — 보고/관측 2층과 STALE 표시가 없으면 관제의 핵심 성질(*"멈춘 것"* 과 *"진행 중"* 의 구별)이 성립하지 않는다. 모드 토글이라는 변경 표면이 있는 한 인증·CSRF는 신뢰경계이지 구현 세부가 아니다 |
| **DV-2** | **플로우 가시성 = 2층 계약이다 — 요청 ID 상관(전 요청) + span 트레이싱(샘플+강제 추적).** ⑴ **요청 ID 상관**: 게이트웨이가 요청 ID를 부여·전파하고 각 서비스가 **구조화 로그에 그 ID를 싣는다**(ADR-023 OB-2의 연장) — **모든 요청**에 적용되며, 로그를 ID로 이으면 경로가 재구성된다 ⑵ **span 트레이싱**: 서비스별 span(부모-자식·시작·종료·오류)에 **필수 속성 — service · instance/slot(blue|green) · version** 을 싣는다 — 적용 범위는 **샘플링 + 특정 요청 강제 추적**(전 요청 span이 아니다). *"이 요청이 blue인가 green인가"* 는 ⑵의 slot 속성이 준다. ⚠️ ★ **성립 선행조건 = 수집·조회 경로**다 — span을 만들어도 export·저장·조회가 없으면 *"진행 위치가 보인다"* 는 성립하지 않는다. **그 수집기 도입은 ADR-023 소유**이며 도입 전까지 ⑵는 **계약만 고정된 미성립 상태**다(⑴은 로그 축이라 수집기 없이도 선다). ★ **이것이 ADR-031이 큐를 기각한 근거의 짝**이다. 도구·전파 표준·샘플링 수치는 `[구현 검증]`(IV-54) | 큐를 관측 목적으로 요청 경로에 넣으면 상시 지연을 지운다(ADR-031 큐 기각 ⑶). 트레이싱은 **요청 경로에 동기 홉을 더하지 않는다**(수집 비용·오버헤드는 IV-54 실측 — "비용 없음"이 아니다). 요청 ID만으로는 span·계층·처리 인스턴스가 생기지 않으므로 — ID 상관을 전 요청의 바닥으로 깔고, 그 위에 샘플·강제 추적 span을 얹는 2층이어야 **문면의 보장과 실제 가시성이 일치**한다 |
| **DV-3** | **호스트·컨테이너 헬스 감시는 이미 있다 — 다시 만들지 않는다.** 각 호스트의 **수집 에이전트**가 컨테이너 헬스·자원을 걷어 임계 초과 시 경보한다. 우리 서비스도 **컨테이너로 올리고 `healthcheck`를 정의하면 그 감시망에 자동 편입**된다. 관제는 이 축을 **인용만** 하고 재구축하지 않는다 | 가동 여부 감시를 관제가 다시 만들면 도구가 둘이 된다(C-08 — 도구 하나 = 운영 대상 하나). 호스트 축 경보는 이미 서 있으므로, 관제가 새로 소유하는 것은 **배포 이력·플로우**뿐이다(ADR-027 DO-6 · 기각 E와 같은 축) |
| **DV-4** | **세 축을 섞지 않는다(ADR-023 OB-7).** ⑴ **배포 관제** = 배포 이력·플로우·블루-그린 상태(관제가 신규 소유) ⑵ **호스트 축** = 컨테이너 헬스·자원(수집 에이전트 — 기존) ⑶ **애플리케이션 관측** = 구조화 로그·메트릭(ADR-023 OB-2), **트레이싱은 ⑶의 연장**이다. 한 화면에 얹는 것과 한 수집기로 걷는 것은 다른 결정이며, 소유가 갈린다 | 축을 섞으면 *"배포가 실패한 건가, 호스트가 부하인 건가, 앱이 느린 건가"* 가 한 지표에 뭉쳐 진단이 흐려진다. OB-7의 범주 구분이 그것을 막는다. 배포 관제가 자원 경보까지 삼키기 시작하면 §3의 로드맵(대시보드 제품)으로 번진다 |
| **DV-5** | **관제가 소유하지 않는 것을 명시한다.** ⑴ 가동 여부 감시·자원 경보 = 수집 에이전트(DV-3) ⑵ **감사 기록** = ADR-017(배포 이력은 감사가 아니다 — 범주가 다르다) ⑶ 애플리케이션 메트릭 정본 = ADR-023 OB-2. 관제는 이 셋을 인용하되 소유하지 않는다 | 배포 이력을 감사로 쓰거나 관제에 앱 메트릭을 얹으면 소유가 흐려지고, 그 흐림이 곧 *"어디를 봐야 하나"* 의 혼란이 된다 |

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 | 도입 조건 |
|---|---|---|
| **관측 대시보드 제품 도입**(수집·시각화 스택) | ⑴ 가동 감시는 이미 있다(DV-3) ⑵ 관제가 새로 소유하는 것은 배포 이력·플로우·블루-그린 상태뿐이라 제품을 들일 규모가 아니다(C-08) ⑶ 트레이싱은 애플리케이션 관측(ADR-023)의 연장이지 관제의 소유가 아니다 | 배포 대상·이력·트레이스의 양이 최소 페이지로 읽히지 않을 때, 또는 ADR-023의 수집기가 도입되어 같은 화면에 얹는 것이 더 싸질 때 |
| **큐로 플로우를 관리·가시화**(사용자 초기 아이디어) | ADR-031이 이미 기각 — 요청 경로에 상시 지연. 플로우 가시성은 트레이싱(DV-2)이 큐 없이 준다 | ADR-031 §3의 도입 조건(비동기·백프레셔·부하 격리)과 동일 |

## 4. 결과

- **배포가 보인다** — 이력·락·모드 + 블루-그린 진행이 한 화면에(DV-1). *"전환이 멈춤"* 과 *"드레인 중"* 이 구별된다.
- **요청 플로우가 트레이싱으로 따라진다** — 큐 없이(DV-2). 블루-그린에서 요청이 blue인가 green인가가 트레이스로 드러난다.
- **도구가 늘지 않는다** — 호스트 헬스는 기존 수집 에이전트(DV-3), 관제는 배포 이력·플로우만 새로 소유(C-08).
- **축이 갈려 진단이 명료하다**(DV-4·DV-5) — 배포/호스트/앱 관측이 섞이지 않는다.
- **내주는 것(감수)**: ⑴ 관제 UI·BFF는 미구현(IN-7) — **인증 필수·CSRF 방어 필수·기능 범위는 DV-1이 결정했고**, 남는 것은 형식·구현뿐(`[구현 검증]` — IV-38) ⑵ 트레이싱 도구·전파 표준·샘플링 수치 미정(DV-2 · IV-54) — ★ **span 층은 ADR-023 수집기 도입 전까지 계약만 고정된 미성립 상태**다(ID 상관 층은 로그 축이라 먼저 선다) ⑶ 관제는 LAN 전용이라 외부에서 보려면 VPN 경유(DO-12) ⑷ 관제의 보고/관측 2층 표시(DV-1 ⑶)는 관측 경로 구현 전까지 보고 층만 선다 — 그동안 관측 칸은 `UNKNOWN`이 정직한 표시다.

## 5. 되돌리는 조건

- **배포·이력·트레이스의 양이 최소 페이지·경량 트레이싱으로 감당되지 않으면** 수집·시각화 스택 도입을 재검한다(§3).
- **축 분리(DV-4)가 실무에서 오히려 세 화면을 오가게 만들면** 통합 화면을 별도 결정으로 판단한다(단 한 수집기로 걷는 것과는 다른 결정).

## 6. 이 ADR이 닫지 않는 것

- **관제 UI 구현**(DV-1 · IN-7 · `[구현 검증]`) — Next.js BFF의 형태·인증 형식·CSRF 구현·세션 수명·실시간 전송 방식(polling/SSE)·갱신 간격은 구현 접촉에서(IV-38). ⚠️ **인증 필수·CSRF 방어 필수·기능 범위(조회+모드 토글)·보고/관측 2층·STALE 표시는 DV-1이 이미 결정했다** — 여기 남는 것은 형식이지 여부가 아니다.
- **트레이싱 도구·전파 표준·샘플링 수치**(DV-2 · `[구현 검증]` · IV-54) — 무엇으로 트레이스를 잇고 얼마나 샘플링하나. 계약(2층 — 전 요청 ID 상관 + 샘플·강제추적 span과 필수 속성)은 고정, 도구는 실물에서. **span 층의 성립은 ADR-023 수집기 도입이 선행조건**이다.
- **애플리케이션 관측 수집기**(ADR-023 소유) — 트레이싱은 그 축의 연장이며, 수집기 도입 자체는 ADR-023의 자리다.
