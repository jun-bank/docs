# ADR-021. 이벤트 전송 — **브로커를 두지 않는다. 릴레이가 직접 전달한다**

- 일자: 2026-08-06
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: Phase 5 진입 아키텍처 스케치 v4(미니멀) · 선검증 F-08~F-11·F-14·F-22 · 사용자 확정(*"도구 싹 빼고 미니멀"*)
- 관련: **ADR-005**(Outbox 계약 O-1~O-5·O-17·O-18) · **ADR-014**(릴레이 운영 O-6~O-16·B-6~B-10) · **ADR-017**(감사 수집 AD-2·AD-3) · **ADR-010**(배포 3) · context-map **R5~R8·R11~R13·R15~R17·R19** · **BR-40·BR-52**

---

## 1. 맥락 — ADR-005가 열어둔 문을 지금 열 것인가

ADR-005는 브로커 직접 발행(안 B)을 기각하면서 **문을 닫지 않았다**:

> *"B를 기각한 것이 '브로커를 안 쓴다'는 뜻은 아니다. 지금은 릴레이가 직접 전달할 뿐이고,
> 브로커가 필요해지면 **릴레이의 전달 대상만 바뀐다**."* (ADR-005 §3)

Phase 5 진입 스케치가 그 문을 열어 **Kafka 도입**을 후보로 올렸고, 선검증이 **파생 결함 6건**을 냈다.

| # | 브로커를 넣으면 새로 생기던 문제 | 성격 |
|---|---|---|
| 1 | **드레인 완료의 축이 갈라진다** — `broker-published ≠ consumer-applied`. BR-52 ②·④의 *"전달 완료"* 가 더 이상 `DELIVERED` 하나로 안 정해진다 | ★ 커트오프 정본 침범 |
| 2 | **파티션 0의 의미가 뒤집힌다** — 정본(O-8)은 *고정 배정*인데 브로커에서 "키 없음"은 **라운드로빈**이다 | 무음 순서 붕괴 |
| 3 | **"파티션"이 두 개념 한 이름이 된다** — outbox 파티션(해시 저장·재분배 가능) ≠ 토픽 파티션(증설 시 매핑 변경) | 용어 충돌 |
| 4 | **fencing token이 브로커를 건너야 한다** — 경유 홉이 늘어 역순 도달 위험이 커진다(B-10) | 기존 방어선 약화 |
| 5 | **컨슈머 적용 watermark**를 새로 만들어야 한다 | 신규 장치 |
| 6 | **INBOX_DLQ**를 신설해야 한다 — OUTBOX_DLQ(M17)와 **별도 상태·별도 소유자**, 둘 다 커트오프를 차단 | 신규 상태 |

### 무엇이 브로커를 요구하는가 — 세어 보면 없다

| 브로커가 실제로 주는 것 | 지금 요구가 있나 |
|---|---|
| **소비자 다변화**(한 이벤트를 여러 독립 소비자가) | ❌ R5~R8·R11·R12·R15·R19 전부 **수신자가 1이거나 명시된 소수**다 |
| **리플레이**(과거 이벤트 재소비) | ❌ 재전달의 정본은 **outbox 레코드 상태**(O-15)이고 DLQ 재투입은 운영자 조작(O-14) |
| **발행/소비 시간 분리(버퍼)** | ⚠️ outbox 테이블이 이미 그 버퍼다 — 릴레이가 못 보내면 **레코드가 남는다** |
| **순서 보장** | ⚠️ 이미 **소유권으로** 보장한다(O-6~O-8). 브로커를 쓰면 그 위에 두 번째 순서 축이 생긴다 |

> ★ **6건의 파생 결함이 전부 "브로커를 넣었기 때문에" 생긴 것**이고,
> 그것이 푸는 요구는 **하나도 실증되지 않았다.** 이 비대칭이 결정이다.

## 2. 결정

| # | 규칙 | 왜 |
|---|---|---|
| **ET-1** | ★ **메시지 브로커를 도입하지 않는다.** 컨텍스트 간 전달은 **outbox → 릴레이 직접 전달**이다 — **ADR-005·ADR-014가 현 정본 그대로 유지된다** | 요구가 없다. 파생 결함 6건이 **전부 소멸**한다 |
| **ET-2** | ★ **`DELIVERED`의 의미는 "수신측이 반영했다"** 이다 — 변하지 않는다. 릴레이는 수신측 응답이 **성공일 때만** 완료 표시한다 | BR-52 ②·④의 드레인 완료가 이 의미 위에 서 있다. 이 의미가 흔들리면 커트오프가 흔들린다 |
| **ET-3** | **배포 경계를 넘는 전달 = 수신 배포의 `inbox` API 직접 호출**(내부 mTLS). 릴레이가 호출하고, 수신측이 **자기 트랜잭션에서 멱등 판정 + 반영 + 커밋**한 뒤 응답한다. ★ **"배포 경계를 넘는 동기 호출 금지"(ADR-010)의 정의 = 배포 경계를 넘는 요청이 발신측 자금 트랜잭션에 참여하는 것**이며, **inbox 전달은 자금 커밋 뒤 릴레이가 별도로 하는 호출이므로 예외 ①(릴레이 전달)** 이다(예외 ② = 읽기 전용 R9·R18 — ADR-020 §1) | 홉이 하나다. 실패는 릴레이의 재시도·DLQ(O-10~O-13)가 그대로 흡수한다. ★ 정의를 안 적으면 *"inbox 호출도 동기 아닌가"* 로 읽혀 이 ADR이 ADR-010과 모순돼 보인다 — 금지의 축은 **동기/비동기가 아니라 자금 트랜잭션 참여 여부**다 |
| **ET-4** | ★ **봉투(envelope)의 필수 항목 8** — `eventId` · `type` · `schemaVersion` · `partitionKey` · ★ **`partitionId`** · **`fencingToken`** · `occurredAt` · ★ **`traceparent`**. ⚠️ **B-10(수신측이 `(partitionId, fencingToken)` 최대값보다 작은 것을 거부)은 브로커 유무와 무관한 정본**이므로 **B-10이 쓰는 `partitionId`가 봉투에 실려야** 한다. ★ **`traceparent`는 소급이 불가**하다(ADR-023 OB-3·OB-4 — 이 항목의 단일 주체는 ET-4다) | 봉투는 전송 수단의 속성이 아니라 **계약**이다. 나중에 전송 수단이 바뀌어도 이 여덟은 그대로 간다. ★ `partitionId`가 빠지면 수신측이 **무엇의 최대값과 비교할지**를 모르고, `traceparent`가 빠진 기간의 레코드는 **영원히 문맥이 없다** |
| **ET-5** | **payload는 발행 컨텍스트가 소유**하고 수신측이 ACL로 번역한다(R5~R7). **공통 층은 봉투만 소유**한다 | payload를 공용화하면 발행·수신이 **lockstep 배포**로 묶인다(S-6a가 막는 형태) |
| **ET-6** | ★ **배포를 넘지 않는 이벤트는 인프로세스로 전달**한다 — R16·R17·R19와 **R13의 코어 구간**이 그렇다. outbox INSERT(같은 커밋)는 유지하되, 릴레이는 **같은 프로세스 안에서 핸들러를 호출**한다. **네트워크 왕복을 만들지 않는다** | 유실 방지는 outbox가 하고, 전달 거리는 짧을수록 좋다. 코어 안에서 HTTP를 도는 것은 비용만이다 |
| **ET-7** | ★ ★ **위성(C4·C5)의 감사 기록도 C8으로 간다** — **경로 신설**: 위성의 **감사 outbox** → 위성 릴레이 → **코어 C8의 감사 inbox**. 멱등은 `sourceRef` 유일(ADR-017 AD-3), 번역은 C8의 ACL(R13). ⚠️ **R13은 문면상 이미 "C1~C7 전 컨텍스트 → C8"** 인데 **C4·C5의 경로만 규정돼 있지 않았다** — 이 규칙이 그 공백을 닫는다. ★ **덮는 범위는 감사 3경로 전부다**: ⑴ 성공한 조작(자금 커밋과 같은 트랜잭션의 outbox) ⑵ ★ **거절·실패**(BR-57 — 자금 트랜잭션이 롤백돼도 남아야 하므로 **독립 커밋**으로 감사 outbox에 쓴다) ⑶ ★ **조회 감사**(비동기 적재). **코어에서는 ⑵⑶이 outbox 밖(C8 직접 append)이지만, 위성에서는 배포 경계를 넘어야 하므로 셋 다 위성 감사 outbox의 감사 레코드를 경유**한다. ⚠️ **감사 누락의 감시 축은 M18** 이며, 위성 경로의 미전달·DLQ도 **M18이 보는 대상**이다 | 정산 `resumeByOperator`·원장 `reverse`는 **운영자 조작**이다. 경로가 없으면 **위성의 행위자 기록만 통째로 비고**, BR-57이 배포 경계에서 조용히 끊긴다. ★ 거절·조회까지 적지 않으면 *"성공한 것만 남는 감사"* 가 되고, 그것은 **거절 반복 탐지(BR-58 · AU-5)를 위성에서만 잃는** 형태다 |
| **ET-8** | **DLQ의 정본은 outbox 레코드 상태다**(O-15) — 별도 DLQ 저장소를 만들지 않는다. 드레인 완료 축은 **outbox 잔량 + `DLQ_UNRESOLVED`** 둘뿐이고(BR-52 · O-16), ★ **컨슈머 lag·watermark 축은 존재하지 않는다** | 브로커가 없으므로 "발행됐지만 아직 소비 안 됨" 상태 자체가 없다. 축이 하나면 커트오프 판정이 하나다 |
| **ET-9** | ★ **브로커 도입 조건 — 셋 중 하나가 실증될 때만**: ⑴ **소비자 다변화** — 같은 이벤트를 **3 이상의 독립 소비자**가 소비해야 한다 ⑵ **리플레이 요구** — 과거 이벤트 재소비가 운영 절차로 필요하다 ⑶ ★ **드레인 미완으로 커트오프 지연이 반복 실측된다** — 수신 배포 정지·지연으로 **드레인이 끝나지 않아 `M16`이 적재되고 커트오프가 지연된 영업일**이 **2회 이상**(M16 적재 이력으로 판정). 그때 꺼낼 설계는 **§7(예약된 설계)** 에 이미 적혀 있다 | *"나중에 필요하면"* 은 판정 불가다. **조건을 지금 적어두는 것**이 도구 최소주의의 실행 형태다(C-08) |

### 전달 경로 (한 장)

```
코어 트랜잭션 ─┬─ 사실 갱신
               └─ outbox INSERT            ← 같은 커밋 (BR-40 · 유실 불가)

코어 릴레이 ─┬─ 코어 안 수신자(C6·C8 …)     ← ★ 인프로세스 호출 (ET-6)
             └─ 배포 밖 수신자(C4·C5)        ← inbox API · 내부 mTLS (ET-3)
                     └ 수신측 멱등 판정 + 반영 + 커밋 → 응답 → DELIVERED (ET-2)

정산 릴레이 ─┬─ C3(R11) · C6(R12)           ← inbox API
             └─ ★ C8 감사 inbox (ET-7 신설 — 성공 · ★거절/실패(독립 커밋) · ★조회 감사)
원장 릴레이 ──── ★ C8 감사 inbox (ET-7 신설 — 같은 3경로 · 미전달 감시 = M18)
```

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 (도입 조건) |
|---|---|---|
| **A. Kafka(브로커) 지금 도입** | 요구 셋(다변화·리플레이·버퍼)이 **하나도 실증되지 않았고**, 넣는 순간 §1의 파생 결함 6건이 **전부 우리 문제가 된다** — 그중 1·2·6은 **커트오프·순서라는 이 프로젝트의 최상위 불변식**을 건드린다 | ★ **ET-9의 셋 중 하나** — 그때 §7의 예약된 설계를 꺼낸다 |
| **B. Outbox + CDC** | ADR-005 안 C를 그대로 유지한다 — **CDC 파이프라인과 브로커를 동시에** 운영해야 한다 | ADR-005 **R2 그대로** — 폴링 지연이 업무 요구를 못 맞출 때 |
| **C. 배포 간 동기 쓰기 호출**(이벤트 대신) | ADR-010의 금지선이고, ADR-005 안 D의 기각 이유(*"원장 장애가 자금 경로를 멈춘다"*)가 그대로 산다 | — (구조적) |
| **D. 공유 DB 테이블을 통한 전달**(수신측이 발신 outbox를 직접 폴링) | 수신측이 **발신측 스키마에 결합**된다. ADR-022가 스키마·계정을 가른 목적(소유권)을 정면으로 깬다 | — |
| **E. 릴레이가 파일·큐 파일로 전달** | 내구성은 얻지만 **순서·fencing·멱등을 전부 다시** 만들어야 한다. outbox가 이미 그 자리다 | — |

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | ★ **현 정본이 그대로 산다** — ADR-005·014·BR-52·M16·M17의 의미가 하나도 안 바뀐다 · 운영 대상 0 증가 · 파생 결함 6건 소멸 |
| **내주는 것** | **수신 배포가 죽어 있으면 그동안 전달이 안 된다**(outbox에 쌓인다 — 유실은 아니다) · 소비자가 늘면 릴레이가 그만큼 호출한다 |
| **새로 생기는 일** | ★ **수신 배포의 `inbox` API 계약**(Phase 4) · 내부 mTLS · ★ **위성 감사 outbox와 C8 감사 inbox**(ET-7) |

## 5. 되돌리는 조건

| # | 관찰되면 | 그때 할 일 |
|---|---|---|
| **R1** | ★ **ET-9의 도입 조건 중 하나가 실증된다** | §7의 예약된 설계로 브로커 도입 — **설계를 처음부터 다시 하지 않는다** |
| **R2** | 수신 배포 정지가 **발신 배포의 자금 경로 지연**을 만든다 | 릴레이 전달을 자금 트랜잭션에서 더 떼어낸다 → 그래도 안 되면 ET-9 ⑶(**M16 적재 영업일 2회 이상**) |
| **R3** | 한 이벤트의 **수신자가 계속 는다**(핸들러 추가가 릴레이 변경을 부른다) | ET-9 ⑴에 접근 중 — 수신자 수를 지표로 관찰한다 |
| **R4** | ★ **관측형** — 위성 릴레이의 **DLQ 적재(M17)가 주 1회 이상**(ADR-014 R1과 같은 축)이고, 그중 ★ **감사 이벤트가 차지하는 비율**(M17 적재 건의 이벤트 유형 분류)이 **2주 연속 상위**로 관측된다 | ADR-017 §5 그대로 — **감사 전용 릴레이 분리**(자금 이벤트와 큐를 가른다) |
| **R5** | inbox API 호출이 **릴레이 처리량의 병목**이 된다 | 배치 전달(한 호출에 여러 이벤트 — 순서·멱등 계약 유지)을 먼저 검토 |

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | ★ **완료 표시의 의미** | 수신측 커밋 **직전** 강제 종료 → 릴레이는 완료 표시하지 않고 **재전달**한다(ET-2) |
| Phase 5 | 중복 전달 | 수신측 커밋 **직후·응답 전** 종료 → 재전달되나 **결과 동일**(O-2 · AD-3) |
| Phase 5 | 순서 | 같은 계좌 입금→출금 연속 발행 → 수신측이 **그 순서로** 받는다(O-8) |
| Phase 5 | fencing | 좀비 릴레이의 늦은 이벤트 → **수신측이 거부**(B-10) |
| Phase 5 | ★ **위성 감사 경로** | 정산 `resumeByOperator` 실행 → **C8 감사 기록에 행위자가 남는다**(ET-7). 같은 이벤트 재전달 → 적재 1건 |
| Phase 5 | ★ **위성 거절 감사** | 위성 조작을 **권한 없이 시도**(거절) → 자금 사실은 안 바뀌는데 **거절 감사가 독립 커밋으로 감사 outbox에 남고 C8에 도달**한다(ET-7 ⑵ · BR-57). 전달이 막히면 **M18에 잡힌다** |
| Phase 5 | ★ **봉투 8항목** | 전달 봉투에 `partitionId`·`traceparent`가 **실려 있고**(ET-4), 수신측 B-10 판정이 **봉투의 `partitionId`** 를 쓴다 |
| Phase 5 | 드레인 | `DLQ_UNRESOLVED` 1건 주입 → **대사 미실행 + M16·M17 적재**(BR-52 · O-16) |
| Phase 5 | 인프로세스 | 코어 안 이벤트(R16·R17·R19) 전달에 **네트워크 홉이 없다**(ET-6) |

## 7. 부록 — 예약된 설계 (브로커를 도입한다면) ★

> **지금 쓰지 않는다.** ET-9의 조건이 실증되는 날 **이 절을 그대로 꺼낸다** —
> 선검증에서 이미 설계·검증한 것을 버리면 그날 같은 6건을 다시 겪는다.

| 항목 | 그때의 설계 |
|---|---|
| **토픽 경계** | 컨텍스트 경계 단위(코어 / 정산 / 원장 / C8 지시) — 배포 경계를 넘는 흐름만 태운다. **코어 내부 이벤트는 그때도 인프로세스**(ET-6 유지) |
| **파티션 매핑** | ★ **outbox `partitionId`를 메시지 키로** 쓴다 — 토픽 파티션을 증설해도 `partitionId → 파티션` 함수만 바뀌고 **순서 축의 소유자는 `partitionId`** 로 남는다. 두 개념(저장 파티션 ≠ 토픽 파티션)을 **이름으로 가른다** |
| **키 없는 이벤트** | ⚠️ **"키 없음"을 쓰지 않는다** — 라운드로빈이 되어 O-8의 고정 배정이 깨진다. **고정 키(`partition-0`)로 단일 파티션 강제** |
| **드레인 완료** | ★ **컨슈머 축을 추가**한다 — BR-52 ②·④의 완료 = outbox 잔량 0 **AND 컨슈머 적용 watermark 도달**. `broker-published ≠ consumer-applied` 를 커트오프가 구분해야 한다 |
| **소비 실패** | ★ **`INBOX_DLQ` 신설** — `OUTBOX_DLQ`(M17)와 **별도 상태·별도 소유자**이며, **둘 다** 해당 영업일 커트오프를 차단한다 |
| **봉투** | ET-4 그대로(+ `outboxSequence`) — 브로커 경유로 역순 도달 위험이 커지므로 **B-10 거부가 더 중요해진다** |
| **파티션 증설 절차** | **[구현 검증]** — 매핑 변경 중 순서 보장 방법은 실물 없이 판정 불가 |
