# ADR-031. 블루-그린 전환 수단 — **게이트웨이가 라우트를 바꾸고, 구 인스턴스는 드레인으로 접는다**

- 일자: 2026-08-12
- 상태: **채택** (전환 수단 확정 · 전환 실행 ③~⑤는 미구현 — 후속)
- 결정자: 사용자 · AI 페어 (2026-08-12 대화 — "green 뜨면 라우팅 전환, blue는 처리 끝나면 종료")
- 근거: **ADR-027 잔여-6 / DO-20 ⑶**(허브 안쪽 전환 수단 미정 — 이 ADR이 닫는다) · **ADR-024 §2.1 · RL-2**(블루-그린 · RL-5 롤백 로컬) · **ADR-027 CD-4 ⑤~⑨**(전환 순서) · **CD-1**(전환 판정) · **CD-2**(드레인 상한) · **ADR-019 · ADR-020**(채널 진입 · 정적 라우팅 — SCG 내부 게이트웨이의 자리) · **C-08**(도구 최소주의)
- 관련: **ADR-027**(DO-20 ⑶ · 잔여-6 · CD-4 · DO-6) · **ADR-024 §2.1** · **ADR-030**(배포물) · **ADR-032**(이 전환을 시각화하는 관제·트레이싱) · 후속 이슈(전환 실행 구현 · SCG 동적 라우트 갱신 방식)
- 규칙 ID 접두어: **`BG-`** (blue-green)

---

## 1. 맥락 — 전환 "수단"만 비어 있었다

ADR-024 §2.1이 사람 채널의 무중단 배포를 **블루-그린**으로 정했다 — 신 버전을 다른 포트로 띄우고, 헬스체크를 통과하면 라우팅을 옮기고, 구 버전을 드레인 후 종료한다. 순서(CD-4 ①~⑩)도 서 있다. 그런데 그 ⑤ "전환"이 **무엇을 조작하는가**는 미정으로 남았다 — ADR-027 DO-20 ⑶과 §7 잔여-6이 *"엣지 nginx 설정 교체 + reload인가, compose 포트 스왑인가"* 를 열어 둔 자리다.

그 사이 내부 라우팅의 정본이 바뀌었다. 채널 진입은 여전히 엣지 nginx가 외부에서 받지만(ADR-019 CH-1), **서비스로의 내부 라우팅은 Spring Cloud Gateway(SCG)** 가 맡는 것으로 정해졌다(사용자 결정 — 추후 모바일/웹 채널별 라우팅·권한을 담을 내부 API 게이트웨이). 그러면 블루-그린 전환의 자연스러운 자리도 정해진다: **어느 인스턴스로 보내는가를 이미 결정하는 그곳**, 곧 SCG의 라우트다.

핵심 제약은 둘이다. 첫째, 전환은 **한 서비스의 blue를 green으로 바꾸는 내부 조작**이지 엣지(공유 인스턴스)를 건드리는 일이 아니어야 한다 — 엣지 설정 사고는 남의 프로젝트까지 죽인다(ADR-027 §4 ⑶). 둘째, blue를 즉시 끄면 진행 중이던 요청이 끊긴다 — 구 인스턴스가 **처리 중인 요청은 마저 끝내고** 접혀야 한다.

## 2. 결정 — SCG 라우트 전환 + 드레인

블루-그린 전환의 수단은 **Spring Cloud Gateway의 라우트 전환**이고, 구 인스턴스는 **연결 드레인**으로 접는다. 아래 표가 그 불변식이다.

| # | 규칙 | 왜 |
|---|---|---|
| **BG-1** | **전환 수단 = SCG의 라우트 전환이다.** 한 서비스(예: `/core`)의 라우트 대상을 blue 인스턴스에서 green 인스턴스로 바꾸는 **동적 라우트 갱신**이 전환이다. ⚠️ ADR-024 RL-2의 *"nginx upstream 전환"* 을 **내부 라우팅으로 정밀화**한 것이지 재판정이 아니다 — **엣지 nginx는 외부 진입(TLS 종단·프록시) 그대로**이고, **서비스 간 blue↔green 전환은 내부 게이트웨이(SCG)** 가 소유한다(ADR-019/020과 정합). 이로써 ADR-027 잔여-6 / DO-20 ⑶이 닫힌다 | 전환은 *"어느 인스턴스로 보내나"* 를 바꾸는 일이고, 그 결정은 **이미 SCG가 라우트로 내리고 있다**. 별도 스왑 기구(엣지 reload·포트 재바인딩)를 새로 만들면 도구가 늘고(C-08 위반), 엣지를 건드리면 공유 인스턴스의 반경이 커진다. 전환을 라우트 갱신 하나로 두면 조작이 **한 곳·한 종류**로 닫힌다 |
| **BG-2** | **전환 판정 = CD-1 헬스다(정본 그대로).** green을 다른 포트/컨테이너로 띄우고(현 dispatch #15의 pull→up까지), **CD-1 준비성 판정을 통과한 뒤에만** 라우트를 green으로 바꾼다. green 헬스 실패 = **미전환**(blue 유지·green 종료 — CD-4 ④, 롤백이 아니라 전환하지 않음) | 라우팅을 옮기는 순간 사용자 트래픽이 green으로 간다 — green이 실제로 요청을 처리할 수 있음을 CD-1이 증명하기 전에 옮기면 첫 요청에서 죽는다. compose 내장 healthcheck가 아니라 CD-1이 전환 판정의 정본이다(ADR-024 §2.1) |
| **BG-3** | **드레인 = 새 요청은 green으로만, blue는 in-flight만 마저 처리 후 종료.** 라우트 전환 뒤 blue는 **신규 수신을 받지 않고** 이미 받은 요청을 끝낸다. in-flight가 소진되면 `compose down`(이미지는 남긴다 — RL-5). 즉 *"blue가 처리 중이면 즉시 끄지 않고, green이 뜨면 라우팅을 green으로, blue가 끝나면 종료"* 가 성립한다 | 즉시 종료는 진행 중 요청을 끊는다. 드레인은 큐 같은 별도 기구 없이 **게이트웨이가 새 요청 방향을 바꾸는 것만으로** 성립한다 — 구 인스턴스로 가는 새 요청이 0이 되면 자연히 비워진다. 드레인 상한(ADR-027 CD-2)과 강제 종료의 불가역 턱(진행 중이 자금 조작이면 운영자 확인 — CD-2 ⒝)은 정본을 그대로 인용한다 |
| **BG-4** | **전환은 배포 창 락을 보유한 채의 단계다(CD-4 ⑤~⑨의 실행 형태).** 라우트 전환·드레인·blue 종료는 배포 시퀀스의 뒷부분이며, 각 단계 직전 **락 보유를 재확인**한다(CD-3 fencing). 전환 이후의 부분 실패(라우트는 바뀌었는데 blue 종료 실패 등)는 **락을 유지한 채 사람에게** 올린다(CD-4 부분 실패 전이) | 전환은 상태를 바꾸는 불가역 구간이다 — 락 없이 두 배포가 겹치면 라우트가 엇갈린다. 정본의 락·이력·부분 실패 계약을 이 ADR이 다시 정하지 않고 그대로 탄다 |
| **BG-5** | **SCG 동적 라우트 갱신의 구체 방식은 `[구현 검증]`이다.** actuator refresh·게이트웨이 라우트 관리 API·설정 리로드 중 무엇으로 라우트를 blue→green으로 원자적으로 바꾸는가, 그 갱신이 진행 중 요청을 끊지 않는가는 실물 접촉에서 판정한다. **계약은 고정**이다(검증된 green으로 원자 전환 → blue 드레인 → 종료) — 수단만 미정 | *"라우트를 바꾼다"* 까지가 결정으로 적을 수 있는 한계다. SCG가 그 원자 전환을 어떤 API로, 무중단으로 해내는지는 걸어 봐야 안다(ADR-030 CP-1의 태도와 같은 축) |

전환 실행(라우트 전환·드레인·종료 = CD-4 ⑤~⑨)은 **아직 미구현**이다 — 현 dispatch(#15)는 pull→up→CD-1 헬스(②③④)까지이고, 그 자리가 곧 잔여-6이 열어 두었던 곳이다. 이 ADR은 **수단을 확정**하며, 구현은 후속으로 남긴다(§6).

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 | 도입 조건 |
|---|---|---|
| **큐 기반 라우팅** (사용자 제안) — 각 서버로 가는 요청을 큐에 담아 처리하고, 전환 때 큐의 라우팅을 제어한다 | ⑴ **큐를 요청 경로에 넣으면 모든 요청에 큐 홉 지연이 붙는다** — 핫패스에 상시 비용을 지운다(사용자도 *"속도가 느려지려나"* 로 짚은 자리) ⑵ **전환 제어는 큐 없이 드레인으로 성립한다** — 큐가 주려는 세밀한 전환 제어(구 인스턴스로의 요청을 끊고 신 인스턴스로)를 **게이트웨이 라우트 전환 + 드레인**이 더 싸게 준다(BG-1·BG-3) ⑶ **"요청이 어디까지 왔나"의 가시성은 큐가 아니라 분산 트레이싱이 준다**(ADR-032 DV-2) — 큐를 그 목적으로 쓰면 관측 수단을 실행 경로에 박는 셈이다. 즉 블루-그린 전환을 위해 큐를 도입할 근거가 서지 않는다 | ★ **블루-그린이 아니라 다른 요구가 실증되면** — 비동기 처리 · 백프레셔(부하 급증 시 요청 완충) · 부하 격리가 실제로 필요해지면 그때 큐를 **별도 결정**으로 판단한다(C-08 — 요구 → 계약 → 도구 순서). 그 판단은 이 전환 결정과 독립이다 |
| **엣지 nginx upstream 전환** (RL-2 문면의 직역) | 내부 서비스의 blue↔green 전환을 위해 **공유 엣지**를 매 배포마다 건드리는 것은 반경이 크다(설정 오류 = 남의 도메인까지 죽는다 — ADR-027 §4 ⑶). 엣지는 외부 진입만 소유하고 내부 전환은 SCG가 맡는 것이 경계상 옳다 | 내부 게이트웨이(SCG)가 없거나 그 라우트 전환이 무중단으로 성립하지 않을 때(BG-5의 [구현 검증] 결과가 부정적일 때) |
| **compose 포트 스왑** (호스트에서 직접 포트 재바인딩) | 포트를 스왑하는 순간의 원자성·무중단 보장이 게이트웨이 라우트 갱신보다 약하고, 라우팅 결정을 두 곳(게이트웨이 + 포트)으로 흩는다 | — (구조적 — SCG가 라우트를 소유하는 한 열리지 않는다) |

## 4. 결과

- **전환 수단이 한 곳·한 종류로 닫힌다** — 라우트 갱신 하나. 엣지를 건드리지 않아 공유 인스턴스의 반경이 늘지 않고(BG-1), 별도 스왑 기구가 생기지 않는다(C-08).
- **무중단이 드레인으로 성립한다** — green이 헬스를 통과한 뒤에만 라우트가 옮겨가고(BG-2), blue는 in-flight를 마저 처리하고 접힌다(BG-3). 큐 같은 상시 비용 기구가 없다.
- **정본과 정합** — 전환은 배포 창 락·이력·부분 실패 계약을 그대로 탄다(BG-4). 롤백도 이 전환의 역방향으로 성립한다(ADR-024 §4 코어 롤백 ⒝).
- **내주는 것(감수)**: ⑴ SCG의 동적 라우트 갱신이 무중단으로 서는지는 [구현 검증](BG-5) ⑵ 전환 실행(③~⑤)은 아직 미구현이라 첫 배포는 green 기동까지만 검증된다 ⑶ 드레인 상한을 넘는 장기 요청은 강제 종료의 불가역 턱에 걸린다(CD-2 ⒝ — 자금 조작이면 운영자 확인).

## 5. 되돌리는 조건

- **SCG 라우트 전환이 무중단으로 성립하지 않으면**(전환 순간 요청이 끊긴다) BG-5를 재검한다 — 그때 엣지 전환·포트 스왑의 도입 조건이 관찰된 것이다.
- **비동기·백프레셔·부하 격리가 실증되면** 큐를 별도 결정으로 판단한다(전환과 독립 — §3 도입 조건).

## 6. 이 ADR이 닫지 않는 것

- **전환 실행 구현**(CD-4 ⑤~⑨ — 라우트 전환·드레인·blue 종료) — 현 dispatch(#15)는 green 기동·CD-1 헬스까지다. 그 뒤 전환을 이 ADR의 수단(BG-1·BG-3)으로 구현하는 것은 후속이다.
- **SCG 동적 라우트 갱신 방식**(BG-5 · `[구현 검증]`) — actuator refresh vs 라우트 관리 API vs 설정 리로드. 계약은 고정, 수단은 실물에서.
- **드레인 상한·강제 종료 임계값**(ADR-027 CD-2 · `[구현 검증]`) — in-flight를 얼마나 기다리나. 이 ADR은 드레인의 형태만 정한다.
