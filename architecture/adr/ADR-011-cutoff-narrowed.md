# ADR-011. 커트오프 축소 — **원장 대사에만 · 마감 잔액은 계좌가 든다**

- 일자: 2026-08-05
- 상태: **채택** — **ADR-006을 대체한다**
- 결정자: 사용자 · AI 페어
- 근거: **DC-004** · **ADR-010**(배포 3) · Phase 3 리뷰 **T2**
- 관련: **BR-14**(귀속 영업일) · **BR-52**(커트오프) · 시나리오 **QS-04**

---

## 1. 맥락 — 무엇이 바뀌었나

ADR-010이 **대사를 코어로** 되돌렸다. ADR-006의 전제가 절반 사라졌다.

| 대사 유형 | ADR-011 (배포 4) | 지금 (배포 3) |
|---|---|---|
| **M9·M10·M11** | 커트오프 필요 | ★ **불필요** — 코어 안, 한 읽기 트랜잭션 |
| **M15** 정산 합계 | 커트오프 필요 | ★ **불필요** — 승인은 코어 안. 단 `settledBusinessDate`가 채워져야 한다(N-1·N-2) |
| **M12·M14** 원장 대사 | 커트오프 필요 | ⚠️ **여전히 필요** — 원장은 밖이다 |
| **M1~M8** 매입 대사 | 커트오프 필요 | ⚠️ 원장을 보는 부분만 |

> ★ **범위가 4개에서 1개(계좌 잔액·미수)로 줄었다.**

### 그런데 T2는 안 풀렸다

Phase 3 리뷰 **T2**: *"드레인은 이벤트를 멈추지 코어 쓰기를 안 멈춘다."*

```
23:00      마감. 잔액 100, 원장 보조부 100
23:00:01   D+1 귀속 입금 7 반영 → 현재 잔액 107
23:20      D일 스냅샷 → balance = 107        ← D+1이 섞였다
           → M12가 7을 탐지. 실제 유실 0
```

**대사를 코어로 옮겨도 이 문제는 그대로다** — 원장이 밖이고, `balance`가 **귀속 영업일을 구분하지 않는 누적 현재값**이기 때문이다.

## 3. 결정

### **A. 계좌가 마감 잔액을 든다 — lazy close**

```
Account
  balance                  현재 잔액 (지금과 동일)
  AccountDailyMovement 행  ★ 신설 — 영업일별 이동 (DC-006)
                             (accountId, businessDate, netAmount, receivableDelta)

규칙
  자금을 바꾸는 조작이 들어올 때, 그 거래의 귀속 영업일(BR-14) 행을
    → 없으면 가장 최근 (businessDate ≤ B) 행의 값으로 만들고
    → 조작 반영 후 netAmount·receivableDelta 에 더하기   ← 같은 트랜잭션
  (같은 트랜잭션 안에서)
```

### 왜 이것인가

| 근거 | |
|---|---|
| **거래가 스스로 마감을 트리거**하므로 별도 배치가 필요 없다 | 전 계좌 UPDATE 배치가 사라진다 |
| 확정이 **자금 조작과 같은 트랜잭션**이라 시점이 정확하다 | E1~E5 안에서 일어난다 |
| **거래가 없는 계좌는 행이 안 생긴다** — 대사가 *"가장 최근 ≤ 대상 영업일"* 을 읽어 자동으로 맞는다 | 계좌 수와 무관한 비용 |
| **BR-14가 이미 귀속 영업일을 정하고 있다** — 새 개념이 아니다 | BR-14 |

> ★ **T2의 원인은 "마감 시각과 스냅샷 시각이 다르다"였다.**
> lazy close는 **마감을 시각이 아니라 사건으로** 바꾼다 — *"D+1 첫 거래가 D를 닫는다."*

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **B** write barrier | 쓰기를 멈추는 것은 **가용성 2순위 침해**다. 그리고 멈춘 사이 들어온 요청을 어떻게 할지 또 정해야 한다 | — |
| **C** 한 읽기 트랜잭션 | 계좌 수만큼 긴 트랜잭션이 되고 **파티션 병렬(ADR-008)이 불가능**해진다. 그리고 트랜잭션 시작 시점 자체가 마감 시각이 아니다 | 계좌 수가 아주 적을 때 |
| **D** 원장을 코어에 맞춤 | 원장은 **감사 정본**이다. 그것을 코어 시점에 맞추면 append-only·귀속 영업일(BR-14·47)이 무너진다 | — |

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | T2 소멸 · 마감 배치 불필요 · 시점이 트랜잭션으로 보장 |
| **내주는 것** | 계좌에 **영업일별 마감 행** · 자금 조작마다 **행 upsert 1회** |
| **새로 생기는 일** | `DailySnapshot` **폐기** (§5) · 마감 행 보존 기간 |

### 축소된 커트오프 절차

```
① 영업일 마감 (BR-06)
② Outbox 드레인            ← 원장·정산이 D일 사실을 전부 받는다
③ 정산 산출 → settledBusinessDate 반영 (R11)
④ 두 번째 드레인            ← ★ N-2. 정산이 만든 이벤트를 전달
⑤ 대사
     M9·M10·M11·M15   코어 안 — 실시간 값으로 계산
     M12·M14          AccountDailyMovement 행 ↔ 원장 D일 보조부
     M1~M8            승인·매입은 코어, 원장 부분만 D일 기준
```

> ★ **③④가 N-1·N-2다.** ADR-006에는 정산 이후 게이트가 없어 M15가 매일 허위로 떴다(T1).

## 5. `DailySnapshot`은 어떻게 되나

**폐기한다.** 계좌가 **영업일별 마감 행**을 직접 들면 별도 애그리게이트가 필요 없다(DC-005).

| ADR-006의 스냅샷 | 지금 |
|---|---|
| `balance` | → ★ **anchor + Σ `netAmount`**(DC-005) |
| `receivableOutstanding` | → ★ **anchor + Σ `receivableDelta`**(DC-005). ⚠️ **초안은 *"실시간 값으로 한다"* 였고 근거를 *"미수는 `incurredBusinessDate`를 이미 든다"* 로 적었는데 — 그 문장이 틀렸다.** `incurredBusinessDate`는 **생긴 날**만 고정하고 `recoveredAmount`·`writtenOffAmount`는 그 뒤로도 변한다(INV-3). **T2가 미수 쪽에 그대로 남아 있었다**(C-2) |
| `holdTotal`·`dailyUsage` | → **불필요** (M9·M11이 코어 안) |

> ★ **DS2(기준점은 자기 자신을 검증하지 못한다)가 사라진다.** 마감 행은
> **자금 조작과 같은 트랜잭션에서 확정**되므로 별도 검증 대상이 아니다.
