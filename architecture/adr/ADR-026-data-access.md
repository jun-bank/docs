# ADR-026. 데이터 접근 — **Spring Data JDBC를 쓴다. JPA는 도입 조건과 함께 불도입한다**

- 일자: 2026-08-07
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: 사용자 결정(2026-08-07 — *"JPA를 안 쓰는 이유와 DB 정책으로 막는 구조를 명시한 의사결정 문서"*) · C-08(도구 최소주의) · 애그리게이트 정본 15종
- 관련: **ADR-002**(domain/adapter 분리 — 영속성은 port 뒤) · **ADR-012**(인덱스·잠금) · **E2 test-strategy**(하한 L1 — 경계·원자성은 실 MySQL · DB-X1~X8 잠금 실험) · **BR-07**(부동소수 금지 — Money) · **dev-conventions KO-4·MO 규칙**

---

## 1. 맥락 — 이 도메인의 쓰기는 "객체 그래프 저장"이 아니라 "조건부 상태 전이"다

정본이 요구하는 쓰기 경로의 모양을 보면 결정이 반쯤 정해져 있다. 멱등 판정("이미 처리했으면 그 결과를 반환"), 배포 창 락("점유자가 없을 때만 내 식별자로 바꾼다 — 영향 행 1 = 획득"), fencing token(B-10 — 최대값 미만 거부), 원장 전표의 한 커밋 원자성(E1~E5) — 전부 **조건부 UPDATE와 행 잠금으로 표현되는 상태 전이**이고, "언제 어떤 SQL이 실행되는가"가 불변식의 일부다. E2의 잠금 실험(DB-X1~X8 — gap lock·데드락·insert intention waiting)도 정확한 SQL 통제를 전제한다.

JPA(Hibernate)의 가치는 반대 지점에 있다: 복잡한 객체 그래프의 자동 영속(더티체킹·지연로딩·영속성 컨텍스트). 그 대가로 **flush 타이밍·쿼리 생성·캐시라는 숨은 동작**이 생기는데, 이 프로젝트의 실측 최다 사고 유형이 silent failure다 — 숨은 동작은 그 축을 늘린다.

도메인 엔티티와 영속 엔티티는 분리한다(ADR-002 — 영속성은 adapter, 사용자 확인 2026-08-07). 이 분리가 결정의 성격을 바꾼다: ⑴ 도메인 오염 걱정은 사라지고 ⑵ 포트 뒤라 **되돌림 비용이 낮아지며** ⑶ 분리 구조에서는 더티체킹을 쓸 수 없어(도메인 변경을 영속 엔티티로 복사해 명시 save) **JPA를 골라도 사실상 Data JDBC의 사용 패턴이 된다** — 무거운 런타임만 얹은 채로.

## 2. 결정

**D1. 쓰기 = Spring Data JDBC.** 애그리게이트 단위 영속(정본의 애그리게이트 15종과 1:1 — 애그리게이트 경계 = 저장 경계), 명시 `save()`, 숨은 동작 없음. 조건부 상태 전이는 `@Modifying` 명시 쿼리로 쓴다 — 쿼리가 코드에 보이는 것이 결함이 아니라 요구사항이다.

**D2. 조회 = 명시 쿼리(JdbcClient/JdbcTemplate).** 처음부터. 목록·집계·커서(UC3-1 전순서 커서)는 애그리게이트 재구성이 아니라 조회 전용 모델로 — "성능 문제가 생기면 JDBC로 내려간다"가 아니라 **조회는 시작부터 그 층이다.**

**D3. 무결성·안정성의 방어선은 3층이며 영속성 프레임워크가 아니다.** ⑴ **컴파일** — 값 타입(Money·BusinessDate, KO-4)이 타입 안정성을 막는다 ⑵ **테스트** — 계약·불변식 검증(E2)이 의미를 막는다 ⑶ **DB** — 제약(유니크·FK)·조건부 UPDATE·행 잠금이 동시성과 최종 무결성을 막는다. "JPA가 검증·안정성을 준다"는 전제는 이 3층 어디에도 해당하지 않아 기각했다.

**D4. JPA(Hibernate)는 불도입 — 도입 조건과 함께 잠근다.** 조건: **복잡한 객체 그래프의 자동 영속이 실증적으로 필요해질 때**(한 애그리게이트의 매핑·저장 코드가 반복적으로 결함을 내거나, 그래프 깊이가 명시 저장으로 감당되지 않음이 2회 이상 실측). 그때도 전면 교체가 아니라 **해당 애그리게이트의 adapter만** 교체한다(포트 뒤 — 되돌리는 조건이 곧 도입 단위다).

## 3. 기각한 대안

- **A. JPA 전면 채택("검증·안정성")** — 전제가 성립하지 않는다(D3). 분리 구조에서는 장점(더티체킹·매핑 편의)이 변환 계층에 상쇄되고 숨은 동작만 남는다.
- **B. JPA 쓰기 + 성능 문제 시 조회 JDBC(하이브리드·단계 도입)** — 단계적 사고 자체는 C-08과 정합해 진지하게 검토했다. 기각 이유: 이 도메인의 조회(커서·집계·대사)는 성능 문제가 "생기는" 것이 아니라 시작부터 조회 전용 층이 필요한 형태이고(D2), 쓰기 경로의 조건부 전이는 JPA 장점이 소멸하는 지점이다(§1). 하이브리드의 좋은 부분(단계 도입)은 D4의 도입 조건으로 보존했다.
- **C. 순수 JdbcTemplate 전면(매핑도 수동)** — 애그리게이트 저장의 반복 코드를 전부 손으로 쓰게 된다. Data JDBC가 그 반복만 걷어내고 숨은 동작은 더하지 않으므로, C를 고를 실익이 없다.

## 4. 결과

- **좋은 것**: SQL이 코드에 보인다(실험 재현·리뷰 가능) · 애그리게이트 정본과 도구 모델 일치 · silent failure 표면 축소 · 의존 최소(Spring 계열 내 — 새 라이브러리 0).
- **나쁜 것(감수)**: 조회 전용 모델·매핑 코드를 직접 쓴다(초기 비용) · JPA 생태계의 편의(스키마 자동 생성 등)를 안 쓴다 — 스키마는 어차피 Flyway가 정본이다 · 학습 축에서 실무 표준 JPA 경험은 이 프로젝트 밖으로 미뤄진다(사용자 인지 후 결정).
- **되돌리는 조건**: D4의 도입 조건 = 되돌림 트리거. 관측 대장은 dev-conventions §9.
