# ADR-007. 읽기/쓰기 분리 — **자금 판단 조회는 쓰기 경로와 같은 곳에서 읽는다**

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 관련: **ADR-002**(모듈 구조) · 품질 속성 **정합성(1)·가용성(2)** · **HA-1** · 시나리오 **QS-01·QS-02**

---

## 1. 맥락

승인 경로(E1)는 **가용잔액 = 계좌잔액 − 홀딩 합계**로 판단한다(BR-04).
그 값을 **어디서 읽는가**가 정합성을 정한다.

### 두 개의 함정이 같은 뿌리를 갖는다

```
① 같은 트랜잭션 안에서 ORM 쓰기 + JDBC 직접 조회
     영속성 컨텍스트가 flush되기 전에 JDBC가 DB를 직접 읽는다
     JPQL은 실행 전 자동 flush되지만 JdbcTemplate은 그 흐름 밖이다
     → 변경 전 데이터를 읽는다

② 읽기 복제본에서 자금 판단
     복제 지연만큼 오래된 값을 읽는다
     → 방금 쓴 홀딩이 안 보인다
```

**둘 다 "오래된 값으로 자금을 판단한다"** 이고, 그것은 **초과 승인**이다 —
Phase 2가 열 라운드에 걸쳐 막은 사고다.

> ★ **`HA-1`이 이미 이것을 금지하고 있다** — *"인스턴스 로컬 상태로 자금 판단을 하지 않는다"*.
> 복제본과 미flush 상태는 **인스턴스 로컬 캐시와 같은 범주**다. 셋 다 *"진짜가 아닌 값"* 이다.

## 3. 결정

### **A. 자금 경로는 단일 경로로만 읽는다**

**"자금 경로"의 정의**: 트랜잭션 경계 **E1~E5 안에서 일어나는 모든 조회**.

| 경로 | 읽기 방식 | 복제본 |
|---|---|---|
| **자금 경로 (E1~E5)** | ★ **쓰기와 같은 영속성 컨텍스트.** 다른 접근 수단을 쓰지 않는다 | ❌ **금지** |
| 조회 전용 (거래 내역·잔액 조회 API) | 자유 — 성능에 맞는 수단 | ✅ 허용 |
| 배치 집계 (정산·대사) | 자유 | ⚠️ 커트오프 기준(ADR-011) |

### 왜 이것인가

| 근거 | 어디에 걸리나 |
|---|---|
| **혼용을 금지하면 flush 타이밍 문제가 발생할 수 없다** — 규약이 아니라 구조다 | ① |
| 자금 판단에 복제본을 안 쓰면 **복제 지연이 정합성에 닿지 않는다** | ② · **HA-1** |
| 조회 API·배치는 자금 판단이 아니므로 **자유롭게 최적화**할 수 있다 | 품질 속성 D-01 |
| E1~E5는 **이미 명확히 식별돼 있다** — 어디에 적용할지 모호하지 않다 | Phase 2 조작 대장 |

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **B** 혼용 + flush 강제 | ★ **개발자 재량에 맡기면 반드시 사고가 난다.** 이 프로젝트의 실측 결론이 *"주의력에 의존하는 규칙은 지켜지지 않는다"* 이고, 검산 스크립트 18종·변이 20건이 그 결론에서 나왔다. **flush를 한 번 빠뜨리면 초과 승인**이며, 그것은 리뷰로 막을 수 있는 종류가 아니다 | — (이 이유는 안 바뀐다) |
| **C** 전면 CQRS | 자금 경로 문제는 해결하지만 **읽기 모델 동기화라는 새 정합성 문제**를 만든다. 그리고 지금 조회 요구가 그것을 요구하지 않는다 | 조회 부하가 쓰기 경로를 침해할 때(R2) |

> ★ **A는 CQRS를 배제하지 않는다.** 조회 전용 경로는 이미 자유이고, 필요해지면 **거기서만** CQRS로 간다.
> **자금 경로는 어떤 경우에도 단일 경로**다.

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | flush 타이밍 사고 **구조적 불가** · 복제 지연이 정합성에 안 닿음 |
| **내주는 것** | 자금 경로에서 **네이티브 쿼리 최적화를 못 쓴다** · 복잡한 조회를 자금 경로에 넣을 수 없다 |
| **새로 생기는 일** | ★ **"자금 경로"를 코드에서 식별할 수 있어야 한다** — 아니면 규칙을 강제할 수 없다 |

### 규칙

| # | 규칙 | 왜 |
|---|---|---|
| **W-1** | E1~E5 트랜잭션 안에서 **ORM 외의 DB 접근을 하지 않는다** | flush 타이밍 |
| **W-2** | 자금 판단 조회는 **쓰기 데이터소스**에서만 한다 | 복제 지연 |
| **W-3** | 조회 전용 트랜잭션은 **읽기 전용으로 명시**하고 자금 경로와 **분리**한다 | 경계를 섞지 않는다 |
| **W-4** | 조회 전용 경로가 **자금 판단 결과를 반환하지 않는다** — 표시용과 판단용을 가른다 | 표시용 값이 판단에 쓰이면 W-2가 무의미해진다 |

> ★ **W-4가 가장 자주 무너지는 자리다.** *"잔액 조회 API가 이미 있으니 승인에서도 쓰자"* 가
> 자연스러운 유혹이고, 그 순간 복제본 값이 자금 판단에 들어온다.

### 무엇이 이것을 강제하나

| 수단 | 무엇을 막나 |
|---|---|
| **모듈 분리** (ADR-002) | 자금 경로가 사는 모듈에 **JDBC 접근 수단을 아예 두지 않는다** — 컴파일 단계 |
| **아키텍처 테스트** | `application/`에서 JDBC 타입 참조 **0건** |
| **데이터소스 분리** | 자금 경로 모듈이 **읽기 복제 데이터소스를 주입받지 않는다** |

> ⚠️ **셋 다 "쓸 수 없게 만드는" 방식이다.** *"쓰지 마라"* 라고 적는 방식이 아니다.
> ADR-002 §5와 같은 원리다.

## 5. 되돌리는 조건

| # | 관찰되면 | 무엇을 뜻하나 | 그때 할 일 |
|---|---|---|---|
| **R1** | 자금 경로에서 **ORM으로는 감당 못 하는 조회**가 반복해서 필요해진다 | 경계가 잘못 그어졌거나 모델이 조회에 부적합 | 그 조회가 **정말 자금 판단인지** 먼저 본다 → 아니면 조회 전용으로 이관 |
| **R2** | 조회 부하가 **쓰기 경로를 침해**한다 (QS-01 침해) | 읽기/쓰기가 같은 자원을 경합 | 조회 전용을 **복제본으로** — 자금 경로는 그대로 |
| **R3** | W-4 위반이 **검사에서 반복 검출**된다 | 표시용과 판단용의 구분이 코드에 안 드러난다 | 반환 타입을 갈라 **컴파일이 막게** 한다 |
