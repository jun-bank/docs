# ADR-020. 라우팅 — **정적 설정. 서비스 디스커버리를 두지 않는다**

- 일자: 2026-08-06
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: Phase 5 진입 아키텍처 스케치 v4(미니멀) · 사용자 확정(*"도구는 실제 필요할 때 추가"*)
- 관련: **ADR-010**(배포 3 — 재개 조건의 출처) · **ADR-019**(진입점) · 품질 속성 **HA-4**(스티키 금지) · ★ **ADR-031**(블루-그린 전환 — **내부 blue↔green 전환 라우트는 SCG가 소유**(BG-1 ⑵): RT-4의 외부 라우팅=nginx는 불변, 전환 라우트의 정본 = SCG 설정 한 곳(RT-1 "설정 한 곳 정본" 원칙의 적용이지 위반이 아니다 — 동적 *갱신*이지 정본의 *분산*이 아님))

---

## 1. 맥락 — 배포 수가 고정이면 디스커버리는 답이 없는 문제의 답이다

서비스 디스커버리(레지스트리 + 클라이언트 조회)가 푸는 문제는 **"대상이 몇 개이고 어디에 있는지 미리 모른다"** 이다.

| 우리 상황 | |
|---|---|
| 배포 단위 수 | ★ **3으로 고정**(ADR-010 — 되돌리기 난이도 "높음") |
| 배포 간 호출 | ★ **쓰기·조작은 금지**(ADR-010 — 금지의 정의는 **ADR-021 ET-3**: *발신측 자금 트랜잭션에 참여하는 것*). ★ **예외는 둘뿐이다 — ① 릴레이 전달**(ADR-021 ET-3) **② 읽기 전용 R9·R18** |
| 인스턴스 증감 | 앱 계층 수평 확장은 허용(HA-1·HA-4) — 그러나 **주소를 아는 주체는 LB**다 |

> ★ **"대상이 몇 개인지 모른다"가 성립하지 않는다.** 그 전제가 없으면 레지스트리는
> **운영 대상 하나가 늘고 장애 지점 하나가 느는 것** 외에 아무것도 하지 않는다.

## 2. 결정

| # | 규칙 | 왜 |
|---|---|---|
| **RT-1** | 배포 간 대상 주소는 ★ **설정 기반 정적 라우팅**이다 — 환경별 설정 한 곳이 정본이고, **코드에 주소를 적지 않는다** | 3개 고정. 주소가 코드에 흩어지면 환경 전환이 배포가 된다 |
| **RT-2** | 수평 확장은 ★ **LB 뒤 인스턴스 추가**로 한다. **애플리케이션은 인스턴스 목록을 모른다** — 아는 주체는 LB 하나다 | HA-4(스티키·세션 의존 금지)와 같은 요구다. 앱이 인스턴스를 알면 그 순간 앱이 상태를 든다 |
| **RT-3** | ★ **레지스트리(Eureka·Consul 계열)를 도입하지 않는다.** 재개 조건은 §3에 명시한다 | 요구가 없다. 도구는 요구 → 계약 → 도구 순서로만 들어온다(C-08) |
| **RT-4** | 사람 채널의 외부 라우팅은 **진입점(nginx) 설정**이 소유한다(ADR-019 CH-1) — 애플리케이션 안에 두 번째 라우팅 표를 만들지 않는다 | 같은 규칙이 두 곳에 있으면 갈라진다 |
| **RT-5** | 대상이 응답하지 않을 때의 처리는 **라우팅이 아니라 호출자의 계약**이다 — 릴레이는 재시도·DLQ(ADR-014 O-10~O-14), 동기 읽기는 타임아웃 계층(ADR-013) | 라우팅 계층에 재시도를 넣으면 **같은 재시도가 두 층에서** 돌아 상한이 곱해진다 |

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 (재개 조건) |
|---|---|---|
| **A. 레지스트리 기반 디스커버리**(Eureka·Consul 계열) | 대상 수가 **고정이고 아는 값**이라 푸는 문제가 없다. 레지스트리 자체가 운영 대상이고, 등록 지연·스플릿 상황에서 **틀린 주소를 자신 있게 알려주는** 장애 유형이 새로 생긴다 | ★ **ADR-010이 개정되어 배포 단위가 동적으로 늘어날 때** — 그 결정이 이 ADR의 유일한 재개 트리거다 |
| **B. DNS(SRV) 기반 동적 조회** | 레지스트리보다 가볍지만 **TTL·캐시 계층이 또 하나** 생기고, 장애 시 "어느 캐시의 값을 보고 있나"가 불투명해진다. 얻는 것이 정적 설정 대비 없다 | 배포가 컨테이너 오케스트레이터 위로 갈 때 — 그때는 플랫폼이 이미 제공한다 |
| **C. 클라이언트 사이드 로드밸런싱** | 앱이 인스턴스 목록을 들면 **HA-4의 취지(앱이 위치를 모른다)** 가 깨지고, 목록 갱신이 또 하나의 분산 상태가 된다 | LB가 병목으로 실측될 때 |
| **D. 라우팅 계층에서 재시도·서킷브레이킹** | 호출자 계약과 **중복**된다 — 릴레이 재시도 상한 5회(O-11)가 라우팅 재시도와 곱해지면 수신측이 보는 중복이 배수로 는다 | — (RT-5가 이것의 답이다) |

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | 운영 대상 0 증가 · 장애 지점 0 증가 · 주소 정본이 설정 한 곳 |
| **내주는 것** | 배포 대상이 늘면 **설정 변경 + 재적용**이 필요하다(자동 등록이 없다) |
| **새로 생기는 일** | 환경별 설정의 형상 관리 · 설정 변경의 무중단 적용 절차 |

## 5. 되돌리는 조건

| # | 관찰되면 | 그때 할 일 |
|---|---|---|
| **R1** | ★ **ADR-010이 개정되어 배포 단위가 늘거나 동적으로 변한다** | 안 A 재검토 — 이것이 이 결정의 **명시된 재개 조건**이다 |
| **R2** | 인스턴스가 **자동 스케일**로 뜨고 죽는다(주소가 사전에 없다) | LB가 흡수하는 범위인지 먼저 판정 → 넘으면 안 B·A |
| **R3** | 설정 변경이 **무중단으로 안 된다**(적용마다 재기동) | 설정 재로딩 경로를 만든다 — 도구 도입은 그 뒤 |
| **R4** | 같은 주소가 **두 곳 이상의 설정**에 나타난다 | RT-1 위반 — 정본을 하나로 되돌린다 |

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | 설정 전환 | 대상 주소를 환경 설정만 바꿔 전환 → **코드 변경 0** |
| Phase 5 | 인스턴스 증설 | 코어 인스턴스를 늘려도 **호출자 설정이 안 바뀐다**(LB가 흡수) |
| Phase 5 | 인스턴스 종료 | 인스턴스 1대 강제 종료 → 진행 중 요청 외에는 영향 없음(HA-4) |
| Phase 5 | 재시도 중복 부재 | 수신측이 본 중복 수 = 릴레이 재시도 수 (라우팅 계층이 더하지 않는다 — RT-5) |
