# ADR-005. 컨텍스트 간 통신 — **DB Outbox + 폴링 릴레이**

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 관련: **ADR-010**(배포 단위) · **BR-40**(별도 논리 단위) · 컨텍스트 맵 **R5~R12** · 품질 속성 **감사가능성(3)·복구가능성(5)** · 시나리오 **QS-05**

---

## 1. 맥락

ADR-004가 코어와 위성 3개를 갈랐다. 이제 **경계를 넘는 사실 전달**을 어떻게 할지 정해야 한다.

```
R5  C3 결제 → C5 원장    이벤트 (비동기 · ACL)
R6  C1 뱅킹 → C5 원장    이벤트 (비동기 · ACL)
R7  C4 정산 → C5 원장    이벤트 (비동기 · ACL)
R8  C3 결제 → C4 정산    이벤트 (비동기)
R9  C1~C5 → C6 대사      읽기 전용 (순응자)
```

### 요구는 이미 정해져 있다

**BR-40**: 자금 이동과 원장 기표는 **별도 논리 단위**다. 다만 **전표는 반드시 기록된다.**

> ★ *"별도인데 반드시"* — 이 두 조건이 이 ADR의 전부다.
> 같은 트랜잭션이 아니면서 유실되지 않아야 한다.

### 무엇이 유실되면 무슨 일이 일어나나

| 유실 | 결과 |
|---|---|
| `Withdrawn` 전표 | 계좌는 줄었는데 원장에 없다 → **M12가 매일 갭을 적재** |
| `ReceivableIncurred` | 채권이 원장에 없다 → **M14** |
| `Captured` → 정산 | 그 영업일 순액이 **매입액만큼 적다** → **M15** |

**대사가 전부 잡는다.** 즉 유실을 **탐지는** 한다. 문제는 **복구**다.

## 3. 결정

### **A. DB Outbox + 폴링 릴레이**

```
E2 매입 반영 (코어 트랜잭션)
  ├ 승인 · 계좌 · 카드 · 배치 · 미수 갱신
  └ outbox INSERT  (Withdrawn · ReceivableIncurred · Captured)
     ────────────── 여기까지 한 커밋 ──────────────

릴레이 (별도 프로세스)
  → outbox 폴링 → 위성으로 전달 → 성공 시 발행 완료 표시
```

### 왜 이것인가

| 근거 | 어디에 걸리나 |
|---|---|
| **사실과 이벤트가 같은 트랜잭션에 기록**된다 — 둘 다 있거나 둘 다 없다. **유실이 원천적으로 불가능**하다 | **BR-40** *"반드시 기록된다"* |
| **C-04(예산 0)에서 실행 가능**하다 — 브로커 없이 MySQL만으로 된다 | C-04 |
| ADR-010 실행 순서의 **단계 2를 가장 작게** 만든다 — 비동기 경계를 도입하되 새 미들웨어는 없다 | ADR-010 §7 |
| 재시도가 **자연스럽다** — 발행 완료 표시 전까지 계속 남아 있다 | QS-05 복구가능성 |

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **B** 브로커 직접 발행 | ★ **커밋 후 발행 전 종료 시 유실**된다. 그것은 정확히 **QS-05가 재는 시나리오**이고, Phase 2 변이 검사가 20건이나 쌓아둔 결함 유형이다. 브로커를 쓰더라도 **Outbox 없이는 안 된다** | — (이 이유는 안 바뀐다) |
| **C** Outbox + CDC | 유실은 막지만 **CDC 파이프라인과 브로커를 동시에 운영**해야 한다. 단계 2에서 도입할 것이 너무 많다 | ★ **폴링 지연이 문제가 될 때**(R2) — 그때는 A에서 C로 가는 것이 자연스럽다. **Outbox 테이블은 그대로 쓴다** |
| **D** 동기 호출 | R5~R8이 전부 **비동기 ACL**로 정해져 있다. 동기로 바꾸면 원장 장애가 **자금 경로를 멈춘다** — 가용성 2순위 위반 | 원장이 코어로 되돌아올 때 (ADR-003 R3) |

> ★ **B를 기각한 것이 "브로커를 안 쓴다"는 뜻은 아니다.** Outbox는 브로커와 **함께 쓰는 것**이고,
> 지금은 릴레이가 직접 전달할 뿐이다. 브로커가 필요해지면 **릴레이의 전달 대상만 바뀐다.**

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | 유실 0 · 브로커 없이 시작 · 재시도가 공짜 |
| **내주는 것** | **폴링 지연**(전달이 즉시가 아니다) · outbox 테이블이 코어 DB에 부하를 더한다 |
| **새로 생기는 일** | ★ **중복 전달을 수신측이 흡수**해야 한다 · 발행 완료 레코드 정리(purge) · 릴레이 자체의 단일 실행 보장 |

### 계약 — at-least-once

| # | 규칙 | 왜 |
|---|---|---|
| **O-1** | 릴레이는 **최소 한 번** 전달한다. 정확히 한 번은 보장하지 않는다 | 전달 후 완료 표시 전 종료가 가능하다 |
| **O-2** | **수신측이 멱등해야 한다** — 같은 이벤트를 두 번 받아도 결과가 같다 | O-1의 필연적 대가 |
| **O-3** | 이벤트에 **고유 식별자**를 싣는다 (`sourceEventId`) | 수신측 멱등의 키 |
| **O-4** | 순서는 **같은 파티션 키 안에서만** 보장한다 | 전역 순서는 처리량을 죽인다 |
| **O-5** | outbox 레코드는 **발행 완료 후에도 일정 기간 보관**한다 | 중복 판정·감사 |
| ★ **O-17** | **역방향(R11·R12)도 같은 계약**이다 — `calculate()`·`fail()`과 **같은 커밋**에 ★ **정산 outbox**(배포 2)로 INSERT되고 릴레이가 전달한다 | 아래 |
| ★ **O-18** | **payload에 하루치 집합을 싣지 않는다** — 원장용은 `SettlementCompleted(영업일, 순액)`, C3용 승인 반영은 ★ **파티션 단위로 쪼갠 별도 이벤트**로 나눈다 | 아래 |

> ⚠️ **O-18이 없으면 집합을 되살린다** (Phase 3 마감 재리뷰 #5): 초안의 `settledAuthorizationIds`는
> **그 영업일 승인 전체**(예: 1,200,000건)다. 이 프로젝트가 **다섯 번 걷어낸 형태**
> (DC-001 · W-14 · O-15 · DC-005 · 여기)이고, 실제로 **C-5의 부분 적용 문제를 만든 원인**이다.
> 파티션 단위로 쪼개면 실패 단위가 작아지고 **재전달이 그 파티션만** 다시 돈다.

> ★ **O-17이 없으면 유실 경로가 열린다** (Phase 3 마감 리뷰 H-5):
>
> ```
> D일 23:40  Settlement.calculate() 커밋 — netAmount 확정 · status = 완료 (INV-4로 이후 불변)
> D일 23:40  ★ 발행 전 프로세스 종료 → SettlementCompleted 소실
> ```
>
> ⚠️ **재발행 경로가 하나도 없다** — `calculate`·`retry`·`fail`·`resumeByOperator`의
> 사전조건이 전부 `status = 완료`를 배제한다. **운영자 탈출구도 없다.**
>
> | 하류 | |
> |---|---|
> | 승인 | `settledBusinessDate` = null **영구** (예: 1,200,000건) |
> | M15 | 우변 = 0 → **그날 순액 전액이 불일치** |
> | 원장 | 매입사 미지급금 그날치 **영구 잔류 · 매일 누적** |
> | 커트오프 | ④ 두 번째 드레인이 M15를 기다린다 → ⑤ **대사 미진입** |
> | ★ **탐지** | **M16도 M17도 안 뜬다** — 둘 다 **코어 outbox 기준**이다 |
>
> ★ **하루치 대사 전체가 무음으로 정지한다.**
> **DC-004 T1의 피해가 "매일 M15 1건"이었는데, ADR-010 N-1이 "경로"만 만들고
> "유실되지 않는 경로"를 안 만들어 대사 전체 정지로 커졌다.**

> ★ **O-2는 새로운 부담이 아니다.** ISO 8583의 망취소가 이미 *"몇 번 오는지 모른다"* 를 전제하고
> (`quality-scenarios.md` QS-03), Phase 2가 멱등 애그리게이트 셋을 그래서 만들었다.
> **at-least-once는 이 도메인의 기본 전제이지 Outbox가 새로 만든 조건이 아니다.**

### 원장의 멱등 — 이미 준비돼 있다

`JournalEntry`는 **`sourceEvent`(ACL 추적)** 필드를 이미 갖고 있다.
같은 `sourceEventId`로 두 번 기표하지 않으면 O-2가 충족된다.

## 5. 되돌리는 조건

| # | 관찰되면 | 무엇을 뜻하나 | 그때 할 일 |
|---|---|---|---|
| **R1** | outbox 폴링이 **코어 DB 부하를 유의미하게** 올린다 | 폴링 비용이 과했다 | 폴링 주기·배치 크기 조정 → 그래도 안 되면 **안 C(CDC)** |
| **R2** | **전달 지연이 업무 요구를 못 맞춘다** (예: 정산 마감 전에 매입 집계가 안 옴) | 폴링 모델의 한계 | **안 C(CDC)** 로. Outbox 테이블은 그대로 |
| **R3** | 중복 전달이 **자금 사고로 이어진다** | O-2(수신측 멱등)가 실제로는 없다 | 수신측 멱등을 구조로 강제 (테스트·제약조건) |
| **R4** | outbox 테이블이 **비대해져 코어 쿼리를 방해**한다 | purge 정책 실패 | 파티셔닝 또는 별도 스키마 분리 |

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | QS-05 복구 | outbox INSERT **직후** 강제 종료 → 재시작 시 **전달됨** |
| Phase 5 | QS-05 복구 | 전달 **직후·완료 표시 전** 강제 종료 → 재시작 시 **중복 전달되나 결과 동일** |
| Phase 5 | QS-04 대사 | 정상 상태에서 **M12·M14·M15 불일치 0건** |
| Phase 5 | 릴레이 다중 인스턴스 | **같은 레코드를 둘이 전달하지 않는다** (HA-2) |

> ★ **두 번째 항목이 이 ADR의 진짜 시험이다.** 유실은 Outbox가 막지만 **중복은 안 막는다.**
> O-2가 실제로 구현됐는지를 여기서 잰다.
