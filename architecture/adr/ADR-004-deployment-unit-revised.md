# ADR-004. 배포 단위 재결정 — **실시간 코어 + 위성 3개**

- 일자: 2026-08-05
- 상태: **채택** — **ADR-001을 대체한다**
- 결정자: 사용자 · AI 페어
- 관련: 제약 **§0 프로젝트 목적** · **C-04** · 품질 속성 **정합성(1)·가용성(2)·탐지가능성(4)** · 시나리오 **QS-01·QS-02·QS-04·QS-07**

---

## 1. 맥락 — 왜 다시 여는가

ADR-001은 **단일 모듈러 모놀리스**를 채택했다. 그 근거의 절반이 조직 제약이었다.

| ADR-001의 근거 | 지금 |
|---|---|
| E1·E2가 C1·C2·C3를 **한 커밋**으로 요구한다 | ✅ **그대로** — 도메인 사실 |
| 운영 단위가 늘면 부담이 곱해진다 (**C-02**) | ❌ **철회됨** |
| 2주 안에 불가 (**C-03**) | ❌ **철회됨** |
| 관리형 인프라 없이 다중 서비스 불가 (**C-04**) | ⚠️ **실행 제한으로 좁혀짐** — 설계를 막지 않는다 |

**세 근거 중 둘이 사라졌다.** 그리고 프로젝트 목적이 명시됐다(`constraints.md` §0):

> *"최대한 크게 하되, 이 큰 걸 아주 작은 단위로 끊어보는 연습."*
> *"오버엔지니어링보단 실제 은행 서비스를 기준으로."*

**"최대한 크게"는 구조를, "작게 끊는다"는 일정을 가리킨다.** 둘을 섞으면 안 된다.

> ★ **ADR-001을 수정하지 않는다.** 그때의 판단과 근거가 사라지면 *"왜 처음엔 그렇게 봤나"* 를
> 재구성할 수 없다. 원장의 역분개와 같은 원리다 (ADR 양식 §4).

## 3. 결정

### **E. 실시간 코어 + 위성 3개 (배포 단위 4)**

### 왜 이것인가

| 근거 | 어디에 걸리나 |
|---|---|
| E1~E5가 **코어 안에 온전히** 들어간다 — 분산 트랜잭션이 생기지 않는다 | Phase 2 E1~E5 · 품질 속성 §3 상충 2행 |
| 위성 셋은 **이미 이벤트 단방향**이다. R5·R6·R7(→원장)·R8(→정산)이 전부 비동기 ACL이고, R9(대사)는 **읽기 전용 순응자**다 | 컨텍스트 맵 R5~R9 |
| BR-40이 이미 **원장 기표를 별도 논리 단위**로 정했다 — 프로세스를 넘는 것이 새 부담이 아니다 | BR-40 |
| **실제 은행 구조에 가깝다** — 계정계(실시간)와 정보계(배치·원장·대사)의 분리 | §0 *"실제 은행 서비스를 기준으로"* |
| 배치가 실시간 자원을 **직접 경합하지 않는다** | QS-01·QS-02 |

> ★ **"컨텍스트 경계를 그대로 배포 단위로"가 아니다.** C1·C2·C3는 **묶어야만** 한다 —
> 트랜잭션이 그것을 요구한다. 나머지는 **이미 비동기**라 뗄 수 있다.
> **분할선은 컨텍스트가 아니라 동기 결합이 정한다.**

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **A** 단일 모놀리스 | 정합성은 지켜지지만 **§0의 목적을 덜 만족한다** — 이벤트 계약·Outbox·커트오프·복제 지연을 실제로 다루지 않게 된다. 그리고 배치와 실시간이 **같은 자원을 경합**한다 | 위성 분리의 운영 비용이 학습 가치를 넘어설 때 |
| **B** 6분할 | ★ **E1·E2·E4가 분산 트랜잭션이 된다.** 인원이 늘어도 안 바뀐다 — **정합성은 인원으로 살 수 없다** | E1·E2의 참여자가 한 컨텍스트로 줄면. **그것은 도메인 변경이지 아키텍처 판단이 아니다** |
| **C** 2분할 | E와 방향이 같으나 **정산·원장·대사를 한 덩어리로 묶는다.** 셋은 성격이 다르다 — 정산은 집계, 원장은 append-only 수신, 대사는 읽기 전용. 묶을 이유가 없다 | 위성 셋의 개별 운영이 과하다고 판명될 때 |

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | 배치·실시간 자원 분리 · 원장의 독립적 감사 경계 · **이벤트 계약을 실제로 설계하게 된다** |
| **내주는 것** | 배포·스키마 4벌 · **결과적 일관성 구간이 늘어난다** · 장애 조합이 복잡해진다 |
| **새로 생기는 일** | ★ **Outbox**(유실 없는 이벤트 전달) · ★ **대사 커트오프 스냅샷** · 이벤트 스키마 버전 관리 · 4개 단위의 배포 순서 |

### ★ 대사 커트오프 — 이 결정이 만든 가장 큰 숙제

대사는 다섯 컨텍스트의 값을 **같은 시점 기준으로** 봐야 한다.

```
M12  계좌 balance ≟ 원장 고객예금 보조부
     → 읽는 사이에 잔액이 변하면 어긋난 게 아닌데 어긋나 보인다 (허위 불일치)
```

단일 DB라면 한 스냅샷 트랜잭션으로 끝나지만, **분리하면 시점을 맞출 장치가 필요하다.**

| 후보 | |
|---|---|
| **영업일 커트오프 스냅샷** | 마감 시점의 잔액·미수를 명시적으로 확정한다. 실제 은행의 EOD 방식 |
| 이벤트 재구성 | 대사가 자기 사본을 갖게 된다 — **그 사본이 맞는지를 또 대사해야 한다** ❌ |
| API 조회 | 조회 시점이 달라 허위 불일치 ❌ |

> ⚠️ **이것은 이 ADR이 정하지 않는다.** 별도 ADR로 다룬다 — 커트오프는 **도메인 개념**을
> 추가하는 일이고(마감 시점 잔액), Phase 2 산출물에 영향을 준다.

## 5. 되돌리는 조건 ★

| # | 관찰되면 | 무엇을 뜻하나 | 그때 할 일 |
|---|---|---|---|
| **R1** | 코어가 **QS-02(400 TPS)를 p99 3초로 못 지킨다** | 수직 한계 | ① 인스턴스 증설 → ② 계좌 샤딩 + 해시 라우팅. **분할이 아니다** |
| **R2** | **허위 불일치가 M9~M15에서 상시 발생**한다 | 커트오프 설계가 실패했다 | 위성을 코어로 되돌린다 (안 A·C) |
| **R3** | Outbox 유실·중복이 **자금 사고로 이어진다** | 비동기 경계의 대가가 감당 범위를 넘었다 | 원장 기표를 코어 트랜잭션에 편입 (BR-40 재검토) |
| **R4** | 이벤트 스키마 변경이 **4개 단위 배포 순서 문제**를 반복해서 만든다 | 분할 비용이 학습 가치를 넘었다 | 안 C로 축소 |

> ★ **R1의 순서는 ADR-001에서 그대로 가져온다.** 부하가 부족하면 **분할이 아니라 증설**이 먼저다.
> 분할은 정합성을 내주는 결정이고 증설은 그렇지 않다.

## 7. 실행 순서 — 구조는 크게, 작업은 작게

§0의 *"작은 단위로 끊는 연습"* 을 여기에 적용한다. **4개를 처음부터 다 띄우지 않는다.**

| 단계 | 무엇 | 왜 이 순서 |
|---|---|---|
| **1** | 코어 안에서 E1 승인 한 줄기 | 뼈대. 이벤트 없이 |
| **2** | 원장(C5) 분리 + **Outbox** | 비동기 경계를 **하나만** 먼저 다룬다 |
| **3** | 정산(C4) 분리 | 같은 패턴 반복 — 계약만 다르다 |
| **4** | 대사(C6) 분리 + **커트오프** | 가장 어렵다. 앞의 셋이 안정된 뒤 |
| **5** | 나머지 경계·규칙을 붙인다 | *"기본 파이프라인에 조건 붙이기"* |

> ⚠️ **단계 2가 진짜 시험대다.** Outbox가 되면 3은 반복이고, 안 되면 4는 시작도 못 한다.
