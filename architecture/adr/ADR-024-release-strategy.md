## 1. 맥락 — "무중단 배포"는 한 문장으로 못 적는다

ADR-019가 채널을 셋으로 갈랐다. **그 셋은 배포 중에 멈췄을 때의 대가가 서로 다르다.**

| 채널 | 배포 중 멈추면 | 흡수 장치가 있나 |
|---|---|---|
| **사람 채널**(고객 조회·운영자) | 요청이 **그 자리에서 실패**한다 — 재시도 주체가 사람이다 | ❌ 없다 |
| **대외계 전문**(승인·취소·망취소·입금통지) | 기관이 **재전송**한다 | ✅ **재전송 규약 + 재수신 멱등**(X-10 ②) |
| **배치·커트오프**(매입·대사·마감) | 실행 중 프로세스가 죽으면 **그 영업일 판정이 깨진다** | ⚠️ 재실행은 되지만 **BR-52 순서**가 걸린다 |

> ★ **하나의 배포 전략으로 셋을 덮으려 하면 가장 약한 채널에 맞춰진다.**
> 사람 채널을 무중단으로 만들자고 전문 채널까지 무중단을 요구하면 **연결·프레이밍 계층(CH-7 [미확정])** 을
> 모르는 채로 설계해야 하고, 배치까지 무중단을 요구하면 **커트오프 도중 코드가 바뀐다.**

### 하나 더 — 전문 어댑터는 코어 안에 있다

CH-4가 **전문 어댑터를 코어 프로세스 안**에 두었다. 그래서 **코어를 배포하면 전문 수신도 같이 끊긴다** —
사람 채널의 무중단과 전문 채널의 수신 정지 창이 **같은 배포 한 번에 동시에 일어난다.** 이 ADR은 그 사실을 감추지 않는다.

## 2. 결정

| # | 규칙 | 왜 |
|---|---|---|
| **RL-1** | ★ **배포 가용성은 채널별로 따로 정의한다** — 하나의 "무중단" 선언을 만들지 않는다. 채널별 규칙은 RL-2~RL-4다 | 대가가 다른 것을 같은 규칙으로 덮으면 **가장 비싼 요구가 전부에 전파**된다 |
| **RL-2** | **사람 채널 = ★ 블루-그린 포트 스왑**. 같은 호스트에 **신 버전을 다른 포트로 띄우고** → 헬스체크 통과 확인 → ★ **nginx upstream 전환**(RT-1의 설정 정본을 바꾼다) → 구 버전 **드레인 후 종료**. 컨테이너 오케스트레이터를 도입하지 않는다. ★ **2026-08-07 개정 — 배포물이 컨테이너 이미지 + compose로 바뀌었다**(전환 구조는 그대로 · 재판정 근거·새 문면 = **§2.1**) | 진입점이 이미 nginx다(CH-1). **전환 지점이 하나**이므로 무중단이 설정 한 줄로 표현된다 — 새 도구가 필요 없다(C-08) |
| **RL-3** | **대외계 전문 = ★ 수신 정지 창(drain)**. ⑴ 어댑터가 **신규 수신을 거절**하고 ⑵ **진행 중 전문의 응답을 끝낸 뒤** ⑶ 프로세스를 교체한다. 정지 동안의 요청은 **기관의 재전송과 재수신 멱등(X-10 ②)이 흡수**한다. ⚠️ ★ **이 규칙은 CH-7([미확정] 전송 프로토콜 계층) 확정 전의 정의**이며, **확정 시 재판정한다**(R1) | 상시 연결인지 요청당 연결인지에 따라 *"수신을 어떻게 끊는가"* 가 통째로 달라진다. **모르는 것 위에 무중단을 설계하면 그 설계가 근거를 잃는다**(CH-7이 이미 같은 이유로 어댑터 상세를 이연했다) |
| **RL-4** | **배치·커트오프 = ★ 배포 창 락**. **배치·커트오프 실행 중에는 그 배포에 배포하지 않는다** — 실행 여부를 배포 절차가 **먼저 확인하고**, 실행 중이면 **배포가 거절**된다(사람의 주의가 아니라 절차가 막는다). ★ **2026-08-07 개정 — 예외 1건이 붙었다**(**§2.4** — **긴급 롤백에 한한 override**. ⚠️ **전진 배포에는 예외가 없다**) | BR-52는 **순서가 있는 절차**다. 도중에 코드가 바뀌면 앞 단계와 뒤 단계가 **다른 버전의 판정**을 하고, 그것은 재실행으로도 복구되지 않는다 |
| **RL-5** | ★ **롤백은 "직전 가동 버전으로의 스왑"** 이다 — deploy-agent가 **직전 버전 산출물을 대상 호스트에 보관**하고, 되돌릴 때 **재빌드하지 않는다**. 되돌릴 수 없는 것은 **DB 마이그레이션뿐**이고 그 답은 RL-6이다. ★ **2026-08-07 개정 — 이미지 태그 롤백**(§2.1의 귀결): 되돌림의 단위는 ★ **직전 가동 이미지 태그**이고 롤백 = ★ **그 태그로 compose 재기동**이다 — **재빌드도 레지스트리 재조회도 하지 않고 호스트 로컬 이미지를 쓴다**. 보관 = **직전 가동 이미지 N개를 호스트에 남긴다**(N·정리 정책 = `operations/cicd.md` **CD-5** · 수치는 **CDV-5**). ⚠️ ★ **불변 태그일 때만 성립한다** — 같은 태그를 다시 밀면(이동 태그·`latest` 류) *"직전 가동 버전으로 되돌렸다"* 가 **다른 이미지로 되돌린 것**이 된다(CD-5 불변 식별자 규칙의 이미지 판) | 장애 중에 빌드를 기다리는 것이 곧 장애 시간이다. 배포 산출물이 남아 있으면 롤백이 **스왑 한 번**이다 |
| **RL-6** | ★ **DB 마이그레이션은 expand-contract**다(**ADR-015** 그대로) — 스키마 변경과 코드 배포를 **같은 창에 묶지 않는다**. ⑴ 확장(구·신 버전이 함께 읽힌다) → ⑵ 코드 배포 → ⑶ 백필 → ⑷ 전환 → ⑸ 축소. **⑸ 이전까지만 롤백이 성립**한다(S-2) | 롤백이 "코드만"이면 **스키마가 신 버전인 채로 구 코드가 돈다**. expand-contract는 그 구간을 **설계로 만든** 것이다 |
| **RL-7** | ★ **배포 실행 주체는 `deploy-agent` 하나**다 — CI(GitHub Actions)가 빌드·테스트·아티팩트까지 하고, **VPN 안의 배포 API를 호출**하면(오라클 프록시 → `.9` → agent) agent가 대상 서버에 적용한다. 사람이 서버에 들어가 손으로 바꾸지 않는다 | 배포 경로가 둘이면 **무엇이 돌고 있는지**를 아무도 모른다(상태 오인). 경로가 하나면 배포 이력이 곧 사실이다 |
| **RL-8** | ★ **배포 요청은 인증키로 검증한다** — **HMAC 서명 + GitHub OIDC/서명 검증**으로 *"깃 배포에 의한 요청인가"* 를 판정하고, 실패하면 **적용하지 않는다**. 키의 발급·보관·교체(병행 검증 창)는 **IV-14** | 배포 API는 **인터넷에서 도달 가능한 원격 코드 실행**이다. 여기를 못 막으면 앞의 모든 경계가 의미를 잃는다 |
| **RL-9** | ★ **세부 절차는 이 ADR이 정하지 않는다** — 헬스체크 판정 기준·드레인 대기 상한·배포 창 정의·agent 구현·아티팩트 보관 개수는 **Phase 5 진입 절차 `E4`(구성 관리·CI/CD 문서)** 로 이월한다. 이 ADR은 **"어느 채널이 어떤 방식으로 멈추는가"** 만 고정한다 | 결정과 절차를 한 문서에 섞으면 절차가 바뀔 때마다 **결정이 다시 열린 것처럼 보인다** |
| **RL-10** | ★ **자동 배포를 두지 않는다**(2026-08-06 개정 — 승격) — ★ **2026-08-07 개정: 「모드」 조항이 붙었다**(사용자 승인 — 아래 ★ 모드 절). main 머지가 곧 배포가 되지 않는다. 파이프라인은 **아티팩트 생성까지 자동**이고 ★ **배포 방아쇠는 사람의 지시**다(E4 §1.1 P3·P4). ⚠️ ★ **RL-7과 다른 축이다** — RL-7이 정한 것은 *"누가 **적용**하나"*(실행 주체 = agent 하나)이고, 이 규칙은 *"누가 **방아쇠**를 당기나"* 다. RL-9의 5항목에 그 자리가 없었으므로 **세부 절차가 아니라 새 결정**이다. ★ **2026-08-06 사용자 승인으로 승격** — 문면·근거의 출처는 `operations/cicd.md` **§1.2**(E4 잠정 판정) | ★ **근거는 둘이고 둘 다 silent failure다.** ⑴ ★ **무음 미배포** — 배포 창 락(RL-4 · 절차 = E4 `CD-3`)은 **거절만 하고 자동 재시도를 두지 않는다**. main 머지가 곧 배포면 **배치 창과 겹친 머지는 거절로 끝나고**, 파이프라인은 초록인데 **배포는 일어나지 않은 상태**가 남는다 — 그 상태는 장애로 보이지 않는다. ⑵ ★ **사람이 모르는 정지 창** — 락을 통과한 경우에도 코어 배포는 **전문 수신 정지 창(RL-3)을 연다**. 그 창은 **기관 재전송에 의존하는 구간**이라, 여는 시각을 아무도 모른 채 열리면 **R2**(*"재전송으로 회수되지 않은 사건"*)가 났을 때 **언제 열렸는지조차 재구성되지 않는다** |
| **RL-11** | ★ **자동 롤백을 두지 않는다 — 되돌림 판정 주체는 사람이다**(2026-08-06 개정 — 승격). ★ **2026-08-07 개정 — 명시 예외 1건이 붙었다**(**§2.3** — deploy-agent **자기 교체 직후 스모크 실패 시 1회 자동 복원**. ⚠️ **경계를 벗어나면 예외가 아니다**). 헬스체크 실패는 **전환 전**이라 롤백이 아니라 **미전환**이고(E4 `CD-1`), 전환 후의 자동 되돌림은 **플랩**(전환 ↔ 되돌림 반복)을 만든다 — 그 사이 사람 채널은 **두 버전을 오간다**. ★ **도입 조건**(C-08 형식 — *"조건 없는 부정은 조건 없는 도입과 같은 결함"*): ⓐ **되돌림 판정이 기계로 표현 가능해지고**(= 전환 후 실패의 판정 기준이 `CD-1`처럼 **연속 N회·상한 D**로 적힐 때) **동시에** ⓑ ★ **플랩 방지 장치**(같은 버전의 자동 되돌림 **1회 제한** — 2회째는 사람)가 함께 설 때. ⚠️ **ⓐ만으로는 안 된다** — 플랩은 판정 정확도가 아니라 **반복 허용**에서 난다. ★ **2026-08-06 사용자 승인으로 승격** — 출처는 `operations/cicd.md` **§4**(E4 잠정 판정) | RL-5가 롤백을 **스왑 한 번**으로 만들었지만, *"언제 되돌리나"* 는 스왑의 비용이 아니라 **판정의 문제**다. 기준 없는 자동 되돌림은 **반복**되고, 그 반복이 곧 사람 채널이 두 버전을 오가는 상태다 — 되돌림을 싸게 만든 것이 되돌림을 **자동으로 해도 된다**는 뜻은 아니다 |

### 2.1 ★ 2026-08-07 개정 — RL-2 배포물 재판정 (컨테이너 이미지 + compose)

> ★ **이 절은 문면 교체가 아니다.** 이전 결정과 그 근거를 **지우지 않고 남기고**, *"무엇이 관찰되어 다시 열렸나"* 와 새 결정을 아래에 잇는다 — 그것이 없으면 다음 사람이 **왜 바뀌었는지 모른 채** 되돌린다.

| | 내용 |
|---|---|
| **이전 결정**(v0.1~v0.2) | 사람 채널 = **블루-그린 포트 스왑** + nginx 전환. ★ 배포물의 형태는 **RL-2가 직접 정하지 않았고**, `operations/cicd.md` **§6.3**이 *"v1 배포물을 비컨테이너(프로세스 교체)로 둔다"* 로 **잠정 판정**하고 있었다 |
| **그 근거**(그대로 유효한 부분) | ⑴ 포트 스왑·재빌드 없는 되돌림이 **프로세스 교체로 이미 성립**한다 ⑵ **레지스트리가 풀 문제가 없었다**(C-08 — 요구 → 계약 → 도구). ⚠️ *"오케스트레이터 불도입 ⇒ 비컨테이너"* 는 **귀결이 아니었다**(§6.3이 이미 정정 — 컨테이너는 오케스트레이터 없이 쓴다) |
| ★ **재판정 사유 — 실측 3건**(2026-08-07 홈랩 실측) | ⑴ ★ **sudo 암호 장벽** — 집 서버 3대의 배포 계정은 **sudo에 암호가 걸려 있고 무암호 드롭인이 없다**. 즉 **systemd 유닛 설치·서비스 재시작이 대화형 사람 개입을 요구**한다 — 비컨테이너 프로세스 교체를 agent가 자동으로 하려면 그 장벽을 **먼저 낮춰야** 하고, 그것은 *"배포를 위해 호스트의 권한 경계를 여는"* 순서다. 반면 **docker·compose는 그 계정이 무암호로 쓴다** ⑵ ★ **기존 모니터링이 컨테이너를 자동으로 걷는다** — 각 호스트의 수집 에이전트가 **컨테이너 헬스·재시작 정책을 걷어 임계 초과 시 경보**한다. 컨테이너로 올리면 **관측이 공짜로 편입**되고, 비컨테이너로 두면 감시를 systemd 유닛 목록에 등록해야 하는데 그 경로가 다시 ⑴의 장벽에 걸린다(ADR-023 OB-1의 독립성과 충돌하지 않는다 — 이것은 **호스트 축 경보**다) ⑶ ★ **홈랩 운영 관습** — 3대 전부 docker·compose가 이미 서 있고 **가동 중인 서비스가 전부 컨테이너**다. 비컨테이너 프로세스 교체는 **이 호스트들에서 유일한 예외**가 되고, 예외는 절차가 아니라 사람의 기억으로 유지된다 |
| ★ **새 결정 (RL-2 배포물)** | ★ **배포물 = 컨테이너 이미지 · 기동 단위 = docker compose**. 블루-그린 전환 구조는 **바뀌지 않는다** — 신 버전을 **다른 포트의 컨테이너로 띄우고** → 헬스체크(**CD-1**) → **nginx upstream 전환**(RT-1) → 구 버전 컨테이너 **드레인 후 종료**. ★ **오케스트레이터는 계속 도입하지 않는다**(§3 기각 B 그대로 — 컨테이너 ≠ 오케스트레이터) |
| ★ **무엇이 바뀌지 않나** | RL-1·RL-3·RL-4·RL-6·RL-7·RL-8·RL-9·RL-11 **전부 불변**. 채널별 가용성 정의(RL-1)·전환 지점 하나(RT-1)·배포 실행 주체 하나(RL-7)·서명 검증(RL-8)은 배포물의 형태와 **독립**이다 |
| ★ **무엇이 바뀌나** | ⑴ **RL-5의 되돌림 단위** = 직전 가동 **이미지 태그**(RL-5 개정 조항) ⑵ **아티팩트의 실체** = 이미지이고 보관은 **레지스트리 태그 + 호스트 로컬 이미지**(CD-5) ⑶ **컨테이너 레지스트리가 도입된다** — `operations/cicd.md` **§6.3의 「불도입」 판정이 뒤집힌다**(그 문서가 도입 판정을 기록한다) ⑷ 각 단계의 **실행 형태**(회수 = 이미지 pull · 기동 = compose up · 종료 = compose down) — 순서 ①~⑩은 그대로다 |
| ⚠️ ★ **새로 생기는 실패 축** | ⑴ **레지스트리가 배포 경로의 의존이 된다** — pull이 실패하면 배포가 서지 않는다(롤백은 호스트 로컬 이미지를 쓰므로 **롤백은 레지스트리에 걸리지 않는다** — 그것이 RL-5 개정 조항이 로컬 이미지를 못박는 이유다) ⑵ **이미지가 호스트 디스크를 먹는다** — 보관 개수 N이 디스크 제약과 만난다(위성 한 대는 디스크 여유가 가장 작다 — 실측) ⑶ ★ **compose 헬스체크와 CD-1이 다른 판정**이다(아래) |
| ⚠️ ★ **compose 헬스체크 ≠ CD-1**(혼동 금지) | **CD-1이 배포 전환의 정본**이고(DB 커넥션·권한·expand 단계·서명 자료를 본다), compose의 `healthcheck`는 **호스트 경보·재시작 정책의 입력**이다. 두 판정이 어긋나면 **CD-1이 이긴다**. ⚠️ ★ **재시작 정책이 판정을 감출 수 있다** — green 컨테이너가 헬스 대기 구간에서 죽었다가 자동 재기동하면 *"연속 N회"* 가 **다른 프로세스의 성공을 이어붙인 것**이 된다. 그래서 agent는 **컨테이너 재시작 횟수를 CD-1 판정 입력에 포함**한다(CD-1 ⑶ 플랩 기록과 같은 축). 실효성 = `[구현 검증]` |

### 2.2 ★ RL-10 모드 조항 (2026-08-07 개정 — 사용자 승인)

### 2.3 ★ RL-11 개정 — 자동 복원의 명시 예외 1건 (2026-08-07 · agent 자기 교체 한정)

> ★ **이 절은 충돌을 해소하는 절이지 문면을 지우는 절이 아니다.** `ADR-027` **DO-8 ⑸**(자기 교체 후 스모크 실패 시 **같은 세션이 직전 버전으로 재기동**)는 ★ **기계가 실패를 판정해 자동으로 이전 버전으로 되돌리는 것**이므로 **RL-11과 정면으로 만난다**. ADR-027 v0.1은 *"RL-7의 예외가 아니다"*(실행 주체 축)만 적고 **RL-11 축(판정 주체)의 충돌은 적지 않았다** — ⚠️ ★ **그것을 조용히 넘기지 않고 여기서 개정으로 처리한다.**

| | 내용 |
|---|---|
| ★ **결정** | **deploy-agent 자기 교체 직후의 스모크 실패에 한해, 직전 가동 버전으로의 자동 복원 1회를 허용한다** — **RL-11의 명시 예외**다. 실행 형태 = **ADR-027 DO-8 ⑸**(같은 SSH 세션) · 세션이 죽는 가지 = **DO-19**(호스트 상주 watchdog) |
| ★ **왜 예외가 서나 — 도입 조건 ⓐⓑ가 이 한 자리에서 이미 충족된다** | RL-11의 도입 조건은 *"ⓐ 되돌림 판정이 **기계로 표현 가능**하고 **동시에** ⓑ **플랩 방지 장치**(1회 제한)가 함께 설 때"* 였다. ⑴ ★ **ⓐ 충족** — 여기서의 판정은 **스모크 한 종류**이고(임의 배포 요청 1건이 정상 거절/수락되는지) **이진**이며 **판정 시점이 교체 직후로 고정**돼 있다. *"전환 후에 무엇이 실패인가"* 라는 열린 문제가 **이 자리에는 없다** ⑵ ★ **ⓑ 충족** — **1회 제한**을 규칙에 못박는다(아래 경계). ⑶ ★ **게다가 이 대상에는 사람이 되돌릴 경로가 애초에 없다** — 되돌릴 주체가 교체 중이라 존재하지 않는다는 것이 **CDT-2가 열려 있던 이유**다. **RL-11을 문자 그대로 적용하면 이 자리는 영원히 닫히지 않는다** |
| ★ **예외의 경계**(넘으면 예외가 아니라 자동 롤백이다) | ⑴ ★ **대상 = deploy-agent 자신뿐**. **코어·위성의 전환 후 실패에는 적용하지 않는다**(거기서는 사람이 판정한다 — RL-11 본문 그대로) ⑵ ★ **판정 = 스모크 실패 한 종류**. 헬스 플랩·간헐 오류·응답 지연으로 **확장하지 않는다** ⑶ ★ **횟수 = 1회**. 복원 후 스모크가 또 실패하면 **자동 조작을 멈추고 사람**에게 간다 ⑷ **되돌림 대상 = 직전 가동 버전**(RL-5 · 교체 전에 이미 기록된 값이다 — 그 자리에서 고르지 않는다) ⑸ ★ **자동 복원은 이력에 별도 사건으로 남는다** — *"성공한 배포"* 로 접지 않는다 |
| ⚠️ ★ **무엇이 바뀌지 않나** | **RL-11 본문은 그대로다** — 코어·위성 배포에 **자동 롤백은 없고 판정 주체는 사람**이다. ★ **RL-7도 그대로다**(되돌리는 것은 사람이 아니라 배포 경로가 낸 명령) · **RL-4·RL-5·RL-8·CD-4 순서**도 무관하다. ⚠️ ★ **이 예외는 「도입 조건 ⓐⓑ가 충족된 첫 자리」이지 도입 조건의 철회가 아니다** — 다른 자리에서 자동 롤백을 열려면 **그 자리에서 다시 ⓐⓑ를 충족**해야 한다 |
| ★ **되돌리는 조건** | **R8**(아래) — 예외의 경계가 지켜지지 않은 사건 1회면 **예외를 철회**한다(**ADR-027 R8**과 같은 관측 대상) |

### 2.4 ★ RL-4 재판정 — 긴급 롤백 override 1건 (2026-08-07 · 배치·커트오프 점유 중 한정)

> ★ **이 절은 RL-4를 철회하지 않는다 — 「롤백」이라는 한 방향에만 문을 낸다.** `operations/cicd.md` **§4**는 *"배치가 걸린 채 즉시 롤백이 필요한 장애에서 **현행 절차는 실행 불가**"* 를 적어 두고 그 자리를 **CDT-7**로 이월했다(= **ADR-027 §7 잔여-3**). 그 이월의 소유자가 이 ADR이므로, 여기서 판정한다.
> ⚠️ ★ **한 번 열렸다가 닫혔던 자리라는 사실을 먼저 적는다.** `cicd.md` **v1.2**(2026-08-06 재점검)가 *"롤백 override 철회 — **RL-4 우회 권한 없음** → CDT-7"* 로 **스스로 되돌렸다**. ★ **그 철회는 옳았다** — 그때 override를 적고 있던 것은 **절차 문서**였고, *"커트오프를 열린 상태로 표시한다"* 는 **상위 결정의 변경이지 절차가 아니다**(CF-1). ★ **지금 다르게 여는 것은 문 자체가 아니라 여는 주체다** — 그때는 **절차 문서가 몰래** 열었고, 지금은 **상위 정본이 재판정으로** 연다. 문면·경계·관측이 **RL-4 옆에** 서고, 발동이 **되돌리는 조건에 걸린다**.

| | 내용 |
|---|---|
| ★ **재판정 사유** | ⑴ ★ **RL-4는 「배포를 미룬다」의 대가만 계산했다** — 배포는 미뤄도 되지만 **장애 중의 롤백은 미룰수록 손실이 커진다**. 커트오프 절차는 **BR-52 ①~⑤ 한 점유**(`cicd.md` CD-3)라 **두 드레인과 단계 사이 대기까지 포함한 긴 창**이고, 그 창 전체에서 **되돌릴 방법이 하나도 없다** ⑵ ★ **대기가 유일 경로라는 것이 「안전」이 아니다** — 깨진 버전이 커트오프 절차 자체를 돌리고 있을 수 있다. 그때 대기는 **깨진 코드로 그 영업일 판정을 끝까지 밀어붙이는 것**이다 ⑶ ⚠️ ★ **코어 다운 축과 혼동하지 않는다** — 코어가 죽어 락을 못 잡는 문제는 **ADR-022 §2.1**(배포 스키마·agent 계정)이 닫았다. **이 절이 여는 것은 「락은 잡히는데 배치가 점유 중」인 자리**다 |
| ★ **결정** | **배치·커트오프 점유 중이라도, ⑴ 롤백에 한해 ⑵ 사람의 2단 확인을 거쳐 ⑶ 그 영업일 커트오프 판정을 「열림」으로 표시하고 ⑷ 발동 사실을 관측 대상으로 남기는 조건에서 배포 창 락의 override를 허용한다.** ★ **RL-4의 명시 예외 1건**이며 그 밖의 모든 경우에 RL-4 본문은 그대로다 |

| ★ **경계 ⑸ — 발동은 관측 대상이다** | ★ **override 발동 2회 = RL-4 재판정**(**R9**). ⚠️ ★ **예외가 상시 경로가 되는 것이 이 문의 유일한 실패 모드**다 — *"장애니까"* 가 두 번 성립하면 그것은 **예외가 아니라 배포 절차가 배치 일정과 맞지 않는다는 신호**이고, 그때 볼 것은 override의 조건이 아니라 **배치 시간대·배포 창의 배치**다(**R3**과 같은 축) |
| ★ **경계 ⑹ — 긴급 권한은 정상 배포 권한과 다른 capability다**(2026-08-07 재검 신설 — `EMERGENCY_ROLLBACK`) | ★ **override는 「정상 배포 요청에 확인 두 칸을 채운 것」으로 서지 않는다.** ⑴ ★ **별도 증거** — 정상 배포의 서명·신원(**RL-8** · **ADR-027 DO-10·DO-11**)만으로는 override가 **서지 않는다**. override 요청은 ★ **정상 배포와 다른 발급 경로로 발급된 증거**(`EMERGENCY_ROLLBACK` capability)를 함께 싣고 **agent가 그것을 따로 검증**한다 — ★ **이 경계의 유일한 목적은 「정상 배포 signer나 침해된 파이프라인이 긴급 권한까지 행사하지 못하게」** 하는 것이다 ⑵ ★ **일회성 소비** — 증거는 **`requestId` 하나에 결박**되고 **부작용 전에 선점·소비**된다(DO-10 ⑶의 `requestId`·`jti` 선점과 **같은 축·같은 저장** — 배포 스키마). ★ **소비된 증거의 재사용 = 거절·기록** ⑶ ★ **결박 대상 넷** — `requestId` · **대상 배포** · 되돌릴 **직전 가동 manifest 식별**(DO-18) · **영업일**. 하나라도 요청과 어긋나면 **override가 서지 않고**, ⚠️ ★ **정상 배포로 강등되지도 않는다**(거절·기록 — 전진 배포는 경계 ⑴이 이미 막는다) ⑷ ★ **2단 확인은 그대로 남는다** — capability는 *"권한이 있나"*, 2단 확인은 *"지금 그것을 쓰는 것을 인지했나"* 로 **다른 것을 본다**. ⚠️ ★ **capability는 역할 분리가 아니라 결박**이다 — 경계 ⑵의 한계(같은 사람이 둘 다 해도 성립)는 **그대로 남고 감추지 않는다** ⑸ **발급·보관·교체 = IV-14 축**이며 이 ADR은 값·경로를 갖지 않는다. ⚠️ ★ **플랫폼에서 실제로 서는지는 `[구현 검증]`**(`cicd.md` **CDV-20**) — **DO-11 ⑵의 운영 승인 결박(ADR-027 §7 잔여-5)과 같은 축이되 대상이 다르다**(그쪽은 *정상 배포의 승인*, 이쪽은 *긴급 권한 자체*). ★ **판정 전까지 「capability 없이는 override가 서지 않는다」는 절차로 지키고 그 한계를 이력에 남긴다**(자기 신고 한계와 같은 강도로 읽는다) |
| ⚠️ ★ **무엇이 바뀌지 않나** | **RL-4 본문**(배치·커트오프 중 **배포**는 거절 — 방향이 전진이면 예외 없음) · **RL-11**(★ **override는 자동이 아니다** — 사람이 판정하고 사람이 두 번 확인한다. §2.3의 예외와 **다른 축**이며 서로를 넓히지 않는다) · **RL-5**(되돌림 단위 · 호스트 로컬 이미지) · **RL-7**(실행 주체 = agent — ★ **사람이 서버에 들어가는 경로를 열지 않았다**) · **RL-8**(서명 검증) · **CD-4 적용 순서·부분 실패 전이** · **RL-10 모드**(override는 모드와 무관하다). ★ **BR-52의 순서도 바뀌지 않는다** — 바뀌는 것은 *"그 순서가 완주하지 못한 영업일이 어떻게 표시되는가"* 이고, 그 표시는 BR-52가 **이미 갖고 있는 형태**다. ★ **2026-08-07 재검 추가** — **ADR-014 B-6~B-10**(릴레이 파티션 fencing) · **ADR-008 B-4**(모든 파티션 완료 전에는 완료가 아니다) · **CD-3 원자 계약**도 **재판정하지 않는다**: 핸드셰이크는 **그 계약들 위에 인계 순서 하나를 얹은 확장**이고, capability는 **RL-8을 대체하지 않고 그 위에 한 겹 더 요구**하는 것이다 |
| ★ **되돌리는 조건** | **R9**(아래) — 발동 2회면 **RL-4를 다시 연다**. ⚠️ 그때의 물음은 *"override를 더 쉽게 할까"* 가 **아니다** |

### 배포 한 번이 채널에 미치는 것 (한 장)

```
[코어 배포]  신 이미지 pull ─▶ green 컨테이너 기동(다른 포트) ─▶ 헬스체크 ─▶ nginx upstream 전환 ─▶ blue 드레인·종료
   ├─ 사람 채널      : 무중단              (RL-2)
   ├─ 전문 어댑터    : ★ 수신 정지 창       (RL-3 — 재전송·멱등이 흡수. CH-7 확정 시 재판정)
   └─ 배치·커트오프  : ★ 실행 중이면 배포 거절 (RL-4)

[정산 .158 / 원장 .164 배포]  사람 채널 진입 없음(CH-2 ⑶) ─▶ 릴레이 전달이 재시도로 흡수(ET-3 · O-10~O-13)
   └─ 단, 커트오프 절차 진행 중이면 배포 창 락 (RL-4)

[롤백]  직전 가동 이미지 태그로 compose 재기동  (RL-5 — 재빌드·재pull 없음)
                                          ‖   [스키마]  expand-contract 5단계 (RL-6 · ADR-015)
```

> ★ **위성 배포가 가장 싸다.** 사람 채널 진입이 없고(CH-2 ⑶) 유입이 릴레이 전달뿐이라
> **outbox에 쌓였다가 재시도로 흘러간다** — ADR-021이 *"수신 배포가 죽어 있으면 쌓인다(유실은 아니다)"* 로
> 이미 적어 둔 성질이 **배포 창의 가용성**으로 그대로 쓰인다.

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 (도입 조건) |
|---|---|---|
| **A. 전 채널 무중단**(전문 채널까지 연결 인계) | **CH-7이 [미확정]** 이다 — 상시 연결의 인계는 프레이밍·재연결 규약을 모르면 설계가 성립하지 않는다. 게다가 **흡수 장치(재전송·멱등)가 이미 있는 채널**에 가장 비싼 방식을 쓰는 것이다 | ★ **CH-7 확정 후** — RL-3의 재판정 시점(R1) |
| **B. 컨테이너 오케스트레이터(K8s 계열) 도입으로 롤링 배포** | 얻는 것(롤링·헬스체크·롤백)이 **RL-2·RL-5로 이미 덮인다**. 서버 3대에 오케스트레이터를 올리면 **운영 대상이 클러스터 하나 늘고**(C-02 운영 1명) 배포보다 플랫폼이 더 큰 문제가 된다. ⚠️ ★ **2026-08-07 재확인 — §2.1의 컨테이너 채택이 이 기각을 열지 않는다**: 바뀐 것은 **배포물의 포장**이고, 이 행이 기각한 것은 **클러스터라는 운영 대상**이다(컨테이너 ≠ 오케스트레이터 — 도입 조건은 아래 그대로) | 배포 대상 호스트가 늘어 **수작업 스왑이 안 될 때**(ADR-020 R1과 같은 축) |
| **C. 배치도 무중단으로**(실행 중 교체) | 커트오프는 **순서 있는 절차**(BR-52)라 도중 교체가 앞·뒤 단계의 버전 스큐를 만든다. ADR-015 S-11이 *"전 인스턴스 배포 확인 후 전환"* 을 요구하는 것과 같은 이유다 | — (구조적) |
| **D. CI가 서버에 직접 SSH로 배포** | 배포 경로가 **CI의 자격증명 유출 = 서버 전면 장악**이 된다. VPN 안의 좁은 API + 서명 검증(RL-7·RL-8)이 노출면을 **엔드포인트 하나**로 줄인다 | — |
| **E. 롤백을 "이전 커밋 재배포"로** | 재빌드 시간이 장애 시간에 들어가고, **빌드가 재현되지 않으면 롤백 자체가 실패**한다. 아티팩트 보관이 그 답이다(RL-5) | — |
| ★ **F. 배포물을 비컨테이너 프로세스로 유지**(이전 판) | **§2.1 실측 3건** — ⑴ 자동 교체가 **sudo 암호 장벽**에 걸려 *"배포를 위해 호스트 권한 경계를 먼저 여는"* 순서가 된다 ⑵ **기존 컨테이너 경보에 편입되지 않는다** ⑶ 그 호스트들에서 **유일한 예외 운영 형태**가 된다 | ★ **컨테이너 런타임이 배포 경로의 장애 원인이 되는 사건 2회**(R6) — 그때는 배포물 형태를 다시 연다. ⚠️ *"sudo 무암호 드롭인을 깔면 되지 않나"* 는 도입 조건이 **아니다** — 그것은 배포 편의를 위해 **호스트 권한 경계를 낮추는 것**이라 방향이 반대다 |

## 5. 되돌리는 조건

| # | 관찰되면 | 그때 할 일 |
|---|---|---|
| **R1** | ★ **CH-7(전송 프로토콜 계층)이 확정된다** | **RL-3을 재판정**한다 — 연결 인계가 가능한 형태면 안 A를 다시 본다. 이 ADR은 그 재판정을 **예약해 둔 것**이다 |
| **R2** | 전문 채널의 **정지 창에 유입된 전문이 재전송으로 회수되지 않은 사건**이 **1회라도** 실측된다(기관 재전송 이력 대조) | 흡수 전제가 깨졌다 — RL-3을 **수신 큐 앞단 분리**로 되돌리거나 배포 창을 대외계 협의 창으로 옮긴다 |
| **R3** | **배포 창 락으로 배포가 막히는 일이 2회 이상** 반복된다(배치 창이 사실상 상시) | 배치 시간대를 먼저 재배치 → 그래도 안 되면 **배치를 별도 프로세스로** 떼어 배포 단위를 가른다(ADR-010 재검토 신호) |
| **R4** | **롤백이 스왑으로 안 된다**(스키마 때문에 되돌릴 수 없다) | RL-6 위반이다 — expand-contract 단계를 건너뛴 배포가 있었는지 절차부터 점검한다(ADR-015 S-1·S-2) |
| **R5** | 배포 API가 **서명 없이 도달 가능한 경로**가 하나라도 발견된다 | 즉시 차단 — RL-8은 예외를 두지 않는다 |
| ★ **R6**(2026-08-07 신설) | **컨테이너 런타임·레지스트리가 배포 경로의 장애 원인**이 되는 사건이 **2회** 실측된다(pull 실패로 배포 불성립 · 런타임 문제로 green이 서지 않음 · 이미지 보관이 호스트 디스크를 채움) | ★ **§2.1의 배포물 판정을 다시 연다**(기각 F의 도입 조건). ⚠️ 되돌림의 방향은 *"sudo 경계를 낮춘다"* 가 **아니다** — 그것은 §2.1 재판정 사유 ⑴을 뒤집어 쓰는 것이다 |
| ★ **R7**(2026-08-07 신설) | **dev 모드의 자동 배포가 운영 모드 판정 기준(ⓐⓑⓒ)을 통과한 대상에서 실행된 사건**이 **1회라도** 관측된다 | 모드 조항의 전제가 깨졌다 — **토글 권한을 분리**하거나 **dev 모드를 철회**한다(ADR-027 R5와 같은 관측 대상) |
| ★ **R8**(2026-08-07 신설 — §2.3의 예외에 붙는다) | ★ **자동 복원이 ⑴ 같은 교체에서 2회 이상 실행되거나 ⑵ agent 자기 교체 밖(코어·위성)에서 실행되거나 ⑶ 스모크 실패가 아닌 판정으로 발동한 사건**이 **1회라도** 관측된다 | ★ **§2.3의 명시 예외를 철회**한다 — 경계가 지켜지지 않는 예외는 **예외가 아니라 자동 롤백**이고, 그러면 RL-11의 근거(플랩)가 그대로 돌아온다. **ADR-027 R8과 같은 관측 대상** |
| ★ **R9**(2026-08-07 신설 — §2.4의 예외에 붙는다) | ★ **긴급 롤백 override가 2회 발동**한다. ★ **또는 경계 위반이 1회라도 관측된다** — ⑴ **override로 전진 배포가 실행**됐다 ⑵ **2단 확인 중 하나가 기록 없이 지나갔다** ⑶ ★ **커트오프 판정이 열림으로 표시되지 않았다**(★ **2026-08-07 — 「열림 미적재 채무」가 미해소인 채 그 영업일이 닫힌 것도 여기다**) ★ **2026-08-07 재검 신설** — ⑷ ★ **핸드셰이크 없이 인계됐다**(PREEMPT 기록·ACK·lease 만료 중 어느 것도 없이 소유자가 바뀐 사건) ⑸ ★ **`EMERGENCY_ROLLBACK` capability 없이 override가 섰다**, 또는 **소비된 증거가 두 번 통과**했다 | ★ **발동 2회 = RL-4를 다시 연다** — 예외가 상시 경로가 됐다는 뜻이고, 그때 볼 것은 override의 조건이 아니라 **배치 시간대·배포 창의 배치**다(**R3**과 같은 축 — 배치를 별도 프로세스로 떼는 판단이 여기서 만난다). ★ **경계 위반 1회 = §2.4의 예외를 철회**한다(**R8과 같은 무관용 형태** — 경계가 지켜지지 않는 예외는 **예외가 아니라 RL-4의 철회**다). ⚠️ ★ **⑶은 특히 무겁다** — 표시가 빠지면 *"커트오프가 정상 완료된 영업일"* 과 **구별되지 않고**, 그것이 BR-52가 막으려던 형태다 |
| ★ **R10**(2026-08-07 재검 신설 — §2.4 경계 ⑶ 부속 ⓑ에 붙는다) | ★ **「PREEMPT 미응답」으로 구 버전 강제 정지 경로를 탄 사건이 1회라도** 관측된다(= 스케줄러가 살아서 lease를 갱신하는데 기한 안에 **안전 경계에 닿지 않았다**) | ⚠️ ★ **이것은 경계 위반이 아니라 예정된 가지다 — 그래서 예외를 철회하지 않는다.** 볼 것은 override의 조건이 아니라 ★ **BR-52 단계 경계의 간격**이다: 한 단계(⑤ 대사·드레인)가 너무 길면 *"안전 경계가 사실상 없다"* 는 뜻이고, 그때는 **단계 경계를 더 잘게 두는 쪽**이 답이지 **핸드셰이크를 건너뛰는 쪽이 아니다**. ⚠️ **2회 누적이면 CDV-18의 기한이 아니라 BR-52 절차 배치를 다시 본다**(**R3**과 같은 축) |
