# ADR-024. 릴리스·배포 — **채널마다 "멈춰도 되는 것"이 다르다**

- 일자: 2026-08-06
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 근거: Phase 5 진입 아키텍처 스케치 v2(CI/CD 절)·v4(미니멀) · **E1 리뷰 N5** · 실서버 3대(`.9`·`.158`·`.164`) + 오라클 리버스 프록시
- 관련: **ADR-019**(채널 진입 CH-1·CH-4·CH-5·**CH-7**) · **ADR-020**(정적 라우팅 RT-1) · **ADR-021**(릴레이 전달 ET-2·ET-3) · **ADR-015**(expand-contract) · **ADR-022**(DB 토폴로지) · **BR-52**(커트오프) · `interfaces/README.md` **X-10 ②**

---

## 1. 맥락 — "무중단 배포"는 한 문장으로 못 적는다

ADR-019가 채널을 셋으로 갈랐다. **그 셋은 배포 중에 멈췄을 때의 대가가 서로 다르다.**

| 채널 | 배포 중 멈추면 | 흡수 장치가 있나 |
|---|---|---|
| **사람 채널**(고객 조회·운영자) | 요청이 **그 자리에서 실패**한다 — 재시도 주체가 사람이다 | ❌ 없다 |
| **대외계 전문**(승인·취소·망취소·입금통지) | 기관이 **재전송**한다 | ✅ **재전송 규약 + 재수신 멱등**(X-10 ②) |
| **배치·커트오프**(매입·대사·마감) | 실행 중 프로세스가 죽으면 **그 영업일 판정이 깨진다** | ⚠️ 재실행은 되지만 **BR-52 순서**가 걸린다 |

> ★ **하나의 배포 전략으로 셋을 덮으려 하면 가장 약한 채널에 맞춰진다.**
> 사람 채널을 무중단으로 만들자고 전문 채널까지 무중단을 요구하면 **연결·프레이밍 계층(CH-7 [미확정])** 을
> 모르는 채로 설계해야 하고, 배치까지 무중단을 요구하면 **커트오프 도중 코드가 바뀐다.**

### 하나 더 — 전문 어댑터는 코어 안에 있다

CH-4가 **전문 어댑터를 코어 프로세스 안**에 두었다. 그래서 **코어를 배포하면 전문 수신도 같이 끊긴다** —
사람 채널의 무중단과 전문 채널의 수신 정지 창이 **같은 배포 한 번에 동시에 일어난다.** 이 ADR은 그 사실을 감추지 않는다.

## 2. 결정

| # | 규칙 | 왜 |
|---|---|---|
| **RL-1** | ★ **배포 가용성은 채널별로 따로 정의한다** — 하나의 "무중단" 선언을 만들지 않는다. 채널별 규칙은 RL-2~RL-4다 | 대가가 다른 것을 같은 규칙으로 덮으면 **가장 비싼 요구가 전부에 전파**된다 |
| **RL-2** | **사람 채널 = ★ 블루-그린 포트 스왑**. 같은 호스트에 **신 버전을 다른 포트로 띄우고** → 헬스체크 통과 확인 → ★ **nginx upstream 전환**(RT-1의 설정 정본을 바꾼다) → 구 버전 **드레인 후 종료**. 컨테이너 오케스트레이터를 도입하지 않는다 | 진입점이 이미 nginx다(CH-1). **전환 지점이 하나**이므로 무중단이 설정 한 줄로 표현된다 — 새 도구가 필요 없다(C-08) |
| **RL-3** | **대외계 전문 = ★ 수신 정지 창(drain)**. ⑴ 어댑터가 **신규 수신을 거절**하고 ⑵ **진행 중 전문의 응답을 끝낸 뒤** ⑶ 프로세스를 교체한다. 정지 동안의 요청은 **기관의 재전송과 재수신 멱등(X-10 ②)이 흡수**한다. ⚠️ ★ **이 규칙은 CH-7([미확정] 전송 프로토콜 계층) 확정 전의 정의**이며, **확정 시 재판정한다**(R1) | 상시 연결인지 요청당 연결인지에 따라 *"수신을 어떻게 끊는가"* 가 통째로 달라진다. **모르는 것 위에 무중단을 설계하면 그 설계가 근거를 잃는다**(CH-7이 이미 같은 이유로 어댑터 상세를 이연했다) |
| **RL-4** | **배치·커트오프 = ★ 배포 창 락**. **배치·커트오프 실행 중에는 그 배포에 배포하지 않는다** — 실행 여부를 배포 절차가 **먼저 확인하고**, 실행 중이면 **배포가 거절**된다(사람의 주의가 아니라 절차가 막는다) | BR-52는 **순서가 있는 절차**다. 도중에 코드가 바뀌면 앞 단계와 뒤 단계가 **다른 버전의 판정**을 하고, 그것은 재실행으로도 복구되지 않는다 |
| **RL-5** | ★ **롤백은 "직전 아티팩트로의 포트 스왑"** 이다 — deploy-agent가 **직전 버전 아티팩트를 보관**하고, 되돌릴 때 **재빌드하지 않는다**. 되돌릴 수 없는 것은 **DB 마이그레이션뿐**이고 그 답은 RL-6이다 | 장애 중에 빌드를 기다리는 것이 곧 장애 시간이다. 배포 산출물이 남아 있으면 롤백이 **스왑 한 번**이다 |
| **RL-6** | ★ **DB 마이그레이션은 expand-contract**다(**ADR-015** 그대로) — 스키마 변경과 코드 배포를 **같은 창에 묶지 않는다**. ⑴ 확장(구·신 버전이 함께 읽힌다) → ⑵ 코드 배포 → ⑶ 백필 → ⑷ 전환 → ⑸ 축소. **⑸ 이전까지만 롤백이 성립**한다(S-2) | 롤백이 "코드만"이면 **스키마가 신 버전인 채로 구 코드가 돈다**. expand-contract는 그 구간을 **설계로 만든** 것이다 |
| **RL-7** | ★ **배포 실행 주체는 `deploy-agent` 하나**다 — CI(GitHub Actions)가 빌드·테스트·아티팩트까지 하고, **VPN 안의 배포 API를 호출**하면(오라클 프록시 → `.9` → agent) agent가 대상 서버에 적용한다. 사람이 서버에 들어가 손으로 바꾸지 않는다 | 배포 경로가 둘이면 **무엇이 돌고 있는지**를 아무도 모른다(상태 오인). 경로가 하나면 배포 이력이 곧 사실이다 |
| **RL-8** | ★ **배포 요청은 인증키로 검증한다** — **HMAC 서명 + GitHub OIDC/서명 검증**으로 *"깃 배포에 의한 요청인가"* 를 판정하고, 실패하면 **적용하지 않는다**. 키의 발급·보관·교체(병행 검증 창)는 **IV-14** | 배포 API는 **인터넷에서 도달 가능한 원격 코드 실행**이다. 여기를 못 막으면 앞의 모든 경계가 의미를 잃는다 |
| **RL-9** | ★ **세부 절차는 이 ADR이 정하지 않는다** — 헬스체크 판정 기준·드레인 대기 상한·배포 창 정의·agent 구현·아티팩트 보관 개수는 **Phase 5 진입 절차 `E4`(구성 관리·CI/CD 문서)** 로 이월한다. 이 ADR은 **"어느 채널이 어떤 방식으로 멈추는가"** 만 고정한다 | 결정과 절차를 한 문서에 섞으면 절차가 바뀔 때마다 **결정이 다시 열린 것처럼 보인다** |

### 배포 한 번이 채널에 미치는 것 (한 장)

```
[코어 배포]  신 버전 :8081 기동 ─▶ 헬스체크 ─▶ nginx upstream 8080→8081 ─▶ 구 버전 드레인·종료
   ├─ 사람 채널      : 무중단              (RL-2)
   ├─ 전문 어댑터    : ★ 수신 정지 창       (RL-3 — 재전송·멱등이 흡수. CH-7 확정 시 재판정)
   └─ 배치·커트오프  : ★ 실행 중이면 배포 거절 (RL-4)

[정산 .158 / 원장 .164 배포]  사람 채널 진입 없음(CH-2 ⑶) ─▶ 릴레이 전달이 재시도로 흡수(ET-3 · O-10~O-13)
   └─ 단, 커트오프 절차 진행 중이면 배포 창 락 (RL-4)

[롤백]  직전 아티팩트 포트 스왑  (RL-5)   ‖   [스키마]  expand-contract 5단계 (RL-6 · ADR-015)
```

> ★ **위성 배포가 가장 싸다.** 사람 채널 진입이 없고(CH-2 ⑶) 유입이 릴레이 전달뿐이라
> **outbox에 쌓였다가 재시도로 흘러간다** — ADR-021이 *"수신 배포가 죽어 있으면 쌓인다(유실은 아니다)"* 로
> 이미 적어 둔 성질이 **배포 창의 가용성**으로 그대로 쓰인다.

## 3. 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 (도입 조건) |
|---|---|---|
| **A. 전 채널 무중단**(전문 채널까지 연결 인계) | **CH-7이 [미확정]** 이다 — 상시 연결의 인계는 프레이밍·재연결 규약을 모르면 설계가 성립하지 않는다. 게다가 **흡수 장치(재전송·멱등)가 이미 있는 채널**에 가장 비싼 방식을 쓰는 것이다 | ★ **CH-7 확정 후** — RL-3의 재판정 시점(R1) |
| **B. 컨테이너 오케스트레이터(K8s 계열) 도입으로 롤링 배포** | 얻는 것(롤링·헬스체크·롤백)이 **RL-2·RL-5로 이미 덮인다**. 서버 3대에 오케스트레이터를 올리면 **운영 대상이 클러스터 하나 늘고**(C-02 운영 1명) 배포보다 플랫폼이 더 큰 문제가 된다 | 배포 대상 호스트가 늘어 **수작업 스왑이 안 될 때**(ADR-020 R1과 같은 축) |
| **C. 배치도 무중단으로**(실행 중 교체) | 커트오프는 **순서 있는 절차**(BR-52)라 도중 교체가 앞·뒤 단계의 버전 스큐를 만든다. ADR-015 S-11이 *"전 인스턴스 배포 확인 후 전환"* 을 요구하는 것과 같은 이유다 | — (구조적) |
| **D. CI가 서버에 직접 SSH로 배포** | 배포 경로가 **CI의 자격증명 유출 = 서버 전면 장악**이 된다. VPN 안의 좁은 API + 서명 검증(RL-7·RL-8)이 노출면을 **엔드포인트 하나**로 줄인다 | — |
| **E. 롤백을 "이전 커밋 재배포"로** | 재빌드 시간이 장애 시간에 들어가고, **빌드가 재현되지 않으면 롤백 자체가 실패**한다. 아티팩트 보관이 그 답이다(RL-5) | — |

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | 채널별 가용성이 **문서로 판정 가능**해진다 · 롤백이 스왑 한 번 · 배포 경로가 하나(RL-7)라 **무엇이 돌고 있는지**가 사실로 남는다 |
| **내주는 것** | ★ **전문 채널에 수신 정지 창이 생긴다**(기관 재전송에 의존) · 배포가 **배치 일정에 종속**된다(RL-4) · 블루-그린이 호스트 자원을 **일시적으로 두 배** 쓴다(`.9` 공존 제약 — ADR-019 CH-1) |
| **새로 생기는 일** | deploy-agent · 아티팩트 보관·회수 · **배포 키 관리(IV-14)** · 배치 실행 상태를 배포 절차가 조회하는 경로(RL-4) · `E4` 문서 |

## 5. 되돌리는 조건

| # | 관찰되면 | 그때 할 일 |
|---|---|---|
| **R1** | ★ **CH-7(전송 프로토콜 계층)이 확정된다** | **RL-3을 재판정**한다 — 연결 인계가 가능한 형태면 안 A를 다시 본다. 이 ADR은 그 재판정을 **예약해 둔 것**이다 |
| **R2** | 전문 채널의 **정지 창에 유입된 전문이 재전송으로 회수되지 않은 사건**이 **1회라도** 실측된다(기관 재전송 이력 대조) | 흡수 전제가 깨졌다 — RL-3을 **수신 큐 앞단 분리**로 되돌리거나 배포 창을 대외계 협의 창으로 옮긴다 |
| **R3** | **배포 창 락으로 배포가 막히는 일이 2회 이상** 반복된다(배치 창이 사실상 상시) | 배치 시간대를 먼저 재배치 → 그래도 안 되면 **배치를 별도 프로세스로** 떼어 배포 단위를 가른다(ADR-010 재검토 신호) |
| **R4** | **롤백이 스왑으로 안 된다**(스키마 때문에 되돌릴 수 없다) | RL-6 위반이다 — expand-contract 단계를 건너뛴 배포가 있었는지 절차부터 점검한다(ADR-015 S-1·S-2) |
| **R5** | 배포 API가 **서명 없이 도달 가능한 경로**가 하나라도 발견된다 | 즉시 차단 — RL-8은 예외를 두지 않는다 |

## 6. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | ★ **사람 채널 무중단** | 배포 중 조회 요청을 지속 발생 → **실패 0**(포트 스왑 · RL-2) |
| Phase 5 | ★ **전문 정지 창 흡수** | 배포 창에 전문을 보낸다 → 거절 후 **기관 재전송 → 결과가 최초 처리와 동일**(멱등 · X-10 ②) |
| Phase 5 | ★ **배포 창 락** | 배치 실행 중 배포를 시도한다 → **배포가 거절된다**(사람이 막는 것이 아니다 — RL-4) |
| Phase 5 | 롤백 | 신 버전 배포 후 롤백 → **직전 아티팩트로 스왑**, 재빌드 없음 · 소요 시간 기록(RL-5) |
| Phase 5 | 스키마 | expand 단계만 적용한 상태에서 **구 버전과 신 버전이 동시에 정상 동작**(RL-6 · ADR-015) |
| Phase 5 | ★ **배포 인증** | 서명 없는·변조된 배포 요청 → **적용되지 않고 거절 기록**(RL-8) |
