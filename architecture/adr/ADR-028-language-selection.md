# ADR-028. 언어 선택 — **서비스 레이어는 Kotlin/JVM + Spring, 인프라 레이어는 Go**

- 일자: 2026-08-07
- 상태: **채택**
- 결정자: 사용자 · AI 페어 (2026-08-07 대화 — "은행이 왜 JVM인가·인프라가 왜 Go인가"를 정면으로 따진 결과의 정본화)
- 근거: C-05(Kotlin/JVM — E1 사용자 확정)·infrastructure.md §4(Go — 사용자 확정)의 **상위 근거를 이 문서가 소유**한다. 언어별 동작 방식·장단점의 학습 정본 = `study/tech/languages/`(java-jvm·kotlin·go·rust·c-cpp-csharp)
- 관련: **ADR-013**(시간 예산 — CPU 집약 전제의 반박 근거) · **ADR-026**(방어선 3층) · **ADR-027**(인프라 도구 3종) · **C-08**(도구 최소주의) · dev-conventions **KO 규칙**

## 1. 맥락 — "어느 언어가 좋은가"는 틀린 물음이다

이 시스템에는 성격이 다른 두 층이 있다. **서비스 레이어**(은행 코어·정산·원장)는 돈의 사실을 다루는 장기 실행 트랜잭션 프로세스이고, **인프라 레이어**(deploy-agent·dispatcher·watchdog·콜렉터)는 인터넷 입력을 받고 호스트를 조작하는 작은 상주 데몬이다. 두 층의 지배 요구가 다르므로 물음은 "어느 언어가 좋은가"가 아니라 **"각 층의 실패 모드를 무엇이 막는가"** 다.

전제 교정 하나가 결정의 절반이다: **은행 코어는 CPU 집약이 아니다.** ADR-013 예산에서 응답 3초의 지배 항은 쿼리 1초·락 대기 0.5초 — 즉 **경합·I/O 집약**이다. 배치(정산·대사)도 지배 항은 DB 왕복이다. 따라서 "CPU 성능이 좋은 언어"는 이 결정의 축이 아니며, 축은 세 가지다: ⑴ 실패 모드(무엇이 조용히 틀리게 하나) ⑵ 생태계 성숙(밟아본 지뢰의 지도가 있나) ⑶ 운영 관측(새벽 3시에 열어볼 수 있나).

## 2. 결정

**L-1. 서비스 레이어 = Kotlin/JVM + Spring Boot.** 은행 도메인 코드(코어·정산·원장·common 라이브러리)는 전부 Kotlin이다. C-05의 상위 근거가 이 조항이다.

**L-2. 인프라 레이어 = Go.** deploy-agent·dispatcher·watchdog·(후속) 콜렉터는 Go 단일 바이너리다. 경계는 "도구가 도메인 판정을 담기 시작하는 순간"이며, 그때가 이 결정의 되돌림 신호다(infrastructure §4).

**L-3. 관제 UI = Next.js**(BFF — IN-7). 이 문서는 확정하지 않고 인용만 한다.

## 3. 왜 서비스 레이어는 JVM인가 — "빨라서"도 "안전해서"도 아니다

**⑴ 메모리 안전이 은행의 최악 실패 모드를 계급째 제거한다.** 은행에서 가장 무서운 것은 크래시가 아니라 **조용히 틀린 값으로 계속 도는 것**인데, C/C++의 메모리 오류(use-after-free·버퍼 오버플로)가 만드는 것이 정확히 그것이다 — 죽지 않고 오염된 상태로 진행하는 프로세스. GC 언어에는 이 실패 계급 자체가 없다. 이 프로젝트의 실측 최다 사고 유형이 silent failure라는 사실과 같은 축이다.

**⑵ 안정성의 실체는 런타임이 아니라 지뢰 지도다.** JDBC·트랜잭션 매니저·커넥션 풀·TLS 스택이 이 도메인에서 25년간 두들겨 맞으며 실패 모드가 전부 문서화되어 있다. "JVM이 안정적"의 정직한 번역은 "**터지는 방식이 예측 가능하고, 터졌을 때 열어볼 도구(스레드 덤프·힙 덤프·JFR)가 업계 최강**"이다.

**⑶ JIT는 장기 실행 서버에서 비용을 상각한다.** JVM의 실비용은 기동(수백 ms~수 초)과 상주 메모리인데, 코어는 한 번 떠서 몇 주를 도는 프로세스라 기동이 상각되고 JIT가 뜨거운 경로를 네이티브 1~2배 안까지 만든다. GC 일시정지 반론은 현대 컬렉터(ZGC — 서브 ms)에서 소멸했고 p99 3초 예산에서 잡음이다. JVM이 정말 틀린 자리는 반대편 — 기동이 잦은 짧은 프로세스와 메모리가 귀한 데몬 — 이고, 그것이 L-2의 이유가 된다.

### 3.1 왜 Spring인가

⑴ **트랜잭션 경계의 선언적 관리** — 우리 불변식의 다수가 "한 커밋"(E1~E5)이고, Spring의 트랜잭션 추상화는 그 경계를 코드 구조로 드러낸다. ⑵ **DI가 ADR-002의 포트 구조를 실행한다** — 어댑터 교체(모의 매입사·실 MySQL)가 조립 문제가 된다. ⑶ **이 도메인에서 가장 두들겨 맞은 프레임워크** — 문제를 만나면 이미 누군가 만났던 문제다. ⑷ 학습 축 — 실무 표준이라는 것 자체가 이 프로젝트의 목적(학습)에서 가치다. 비용(추상화 뒤 숨은 동작·기동 무게)은 인지하고 수용한다 — 마법 배제 규칙은 dev-conventions가 소유한다.

### 3.2 왜 Java가 아니라 Kotlin인가 — 간결함 너머의 실질

간결·유지보수는 부수 효과다. 결정적인 것은 **컴파일러가 우리 정본의 방어를 몇 개나 대신 서주는가**다.

- **null 안전이 타입 시스템에 있다** — "경계에서 검증해 non-null 도메인 타입으로"(KO-3)가 Java에서는 규율이고 Kotlin에서는 **타입 검사**다. 방어선 3층(ADR-026)의 컴파일 층이 실제로 두꺼워진다.
- **sealed + when 완결성 검사** — 상태 기계 11종의 분기에서 상태가 추가되면 **처리 안 한 분기가 컴파일 오류**가 된다. Java의 switch는 (최근 개선에도) 이 강제가 우리 SM 표현 방식에서 약하다. 은행 코드에서 "빠뜨린 상태 분기"는 silent failure의 전형적 입구다.
- **불변이 기본형이다** — val·읽기전용 컬렉션·data class copy. "행위자와 가변성을 명시한다"가 언어 관습이다(KO-2와 정합).
- **값 타입 표현** — data class·value class가 Money·BusinessDate 같은 도메인 값(BR-07)을 상용구 없이 불변·동등성까지 정확하게 표현한다.
- **코루틴** — 필요해질 때 경량 동시성이 언어에 있다(도입은 필요 실증 후 — C-08).
- **Java 100% 상호운용** — 위를 전부 얻으면서 JVM 생태계(⑵항)를 하나도 잃지 않는다.
- 정직한 비용: 컴파일 시간, `@JvmStatic` 류 상호운용 마찰(TL-1 스파이크가 실측 — 우회 존재), 검사 예외 폐지는 찬반이 있는 트레이드(우리는 오류 모델을 코드 대장·타입으로 관리하므로 이득 쪽).

## 4. 왜 인프라 레이어는 Go인가 — 소거법 + 적극 근거

인프라 도구의 일: HTTP 수신·서명 검증·SSH/docker 실행·SQLite 기록·상주. 지배 요구 = 배포 단순성·작은 상주 비용·보안 표면 최소·기동 속도(dispatcher는 호출마다 뜨므로 기동이 곧 배포 소요).

- **C/C++ 배제** — 인터넷 입력을 파싱하고 SSH 키를 쥐는 프로세스를 메모리 비안전 언어로 짜면, 파서 결함 하나가 서버 3대 장악이 된다. 수용 불가.
- **Rust 배제** — 안전성 최강이나 그 보증의 대가(소유권과 싸우는 개발 비용)는 공유 상태 동시성·지연 보증에서 회수되는데, 우리 도구에는 그 자리가 없다.
- **C# 배제** — 기술적으로 가능하나 Go 대비 이 용도의 우위가 없이 세 번째 런타임을 살림에 추가한다(C-08).
- **Kotlin/JVM 배제** — L-1의 강점이 여기서 전부 뒤집힌다: 기동 무게(dispatcher 치명)·상주 메모리(허브 혼잡)·배포 복잡성(JVM 설치). 도구가 셋이라 "하나면 스택 단일성이 이긴다"는 조건도 불성립.
- **Go 채택** — 이 틈새를 위해 설계된 언어다: 정적 단일 바이너리·크로스컴파일(3서버 배포 = scp 한 번), 기동 수 ms, 작은 힙에서 GC 무비용, 고루틴으로 동시 SSH, 표준 라이브러리에 http/crypto. 그리고 **언어의 단순함이 보안 자산이다** — 감사할 코드 표면이 작다. 업계 실측: docker·kubernetes·prometheus·terraform — 인프라 층 전체가 Go로 수렴했고, 우리가 할 일의 선례가 전부 거기 있다.

## 5. 관통 원리 — 안전은 층마다 다른 것을 뜻한다

**도메인 정확성**(돈 계산이 맞는가)의 방어 = 타입 시스템 + 3층 방어선(ADR-026) → Kotlin이 최강. **인프라 보안**(침해되면 호스트 장악)의 방어 = 메모리 안전 + 작은 코드 표면 → Go/Rust의 자리, 비용까지 계산하면 Go. **운영 안정성**(열어볼 수 있는가)의 방어 = 생태계·관측 도구 → JVM 최강. 층별로 다른 언어가 정답인 것이지 어느 쪽이 좋은 언어인 것이 아니다 — 이것이 두 언어 체제의 근거이고, 경계는 권한으로 강제된다(DO-4·DT-10: 인프라 도구는 업무 스키마에 한 칸도 없다).

## 6. 기각한 대안

- **A. Java 단일** — ⑵⑶은 동일하나 3.2의 컴파일 층 방어(null·완결성·불변 기본)를 포기한다. E1에서 사용자가 Kotlin을 확정한 결정의 상위 근거가 3.2다.
- **B. 전층 Kotlin 단일 스택** — §4의 Kotlin 배제 근거. 스택 단일성(C-08)은 도구가 하나일 때의 논리다.
- **C. 전층 Go** — 도메인 모델링 표현력(sealed·값 타입·불변식 표현)이 얕아 서비스 레이어의 컴파일 층 방어가 사라진다.
- **D. 진짜 CPU 집약이 생기면?** — 그때가 네이티브/Rust의 도입 조건 관찰 시점이다(예: 리스크 시뮬레이션). 지금 열지 않는다.

## 7. 결과

- 좋은 것: 층별 실패 모드에 최적 방어 · 인프라 도구의 배포·상주 비용 최소 · 학습 폭(두 생태계).
- 나쁜 것(감수): 언어 2개 유지(툴체인·규약·CI 2벌 — 단 인프라 층은 GC 규약 별도 최소셋) · Kotlin 컴파일 시간 · JVM 상주 메모리.
- 되돌리는 조건: **R1** 인프라 도구가 도메인 판정을 담기 시작(→ 그 부분을 서비스 레이어로 이관) **R2** 서비스 레이어에 진짜 CPU 집약 코어 실증(→ 그 모듈만 네이티브 검토 — 전면 교체 아님).
