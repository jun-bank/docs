# ADR-002. 모듈 구조 — **진입 컨텍스트가 조율한다**

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 관련: ★ **ADR-010**(배포 단위 — ADR-004를 대체) · 컨텍스트 맵 **R2·R3·R9** · 품질 속성 **정합성(1)**

---

## 1. 맥락

★ **ADR-010**이 **실시간 코어**(C1 뱅킹 · C2 카드 · C3 결제 · **C6 대사** · **C7 인증**)를 한 배포 단위로 묶었다.
그 안에서 **애그리게이트 8종과 트랜잭션 경계 E1~E5를 어떻게 배치할 것인가**를 정해야 한다.

### 진입점이 이미 갈려 있다

| 경계 | 무엇으로 시작하나 | 진입 컨텍스트 |
|---|---|---|
| **E1** 승인 · **E2** 매입 · **E4** 환불 | 승인 전문 · 매입 파일 · 취소 레코드 | **C3 결제** |
| **E3** 미수 회수 · **E5** 입금 정정 | 입금 전문 · 운영자 지시 | **C1 뱅킹** |

### 컨텍스트 맵이 이미 방향을 정했다

```
R2  C1 뱅킹 → C3 결제   고객-공급자 · 동기 호출 (같은 트랜잭션)
R3  C2 카드 → C3 결제   고객-공급자 · 동기 호출 (같은 트랜잭션)
```

**C3가 고객이고 C1·C2가 공급자다.** 즉 **C3가 C1·C2를 호출한다.**

---

## 2. 고려한 안

| # | 안 | 조율 위치 | 컨텍스트간 의존 |
|---|---|---|---|
| **A** | **진입 컨텍스트가 조율** | C3(E1·E2·E4) · C1(E3·E5) | C3 → C1 · C3 → C2 (단방향) |
| **B** | 별도 응용 모듈이 전부 조율 | `application/` 하나 | 컨텍스트간 **의존 0**, application → 전부 |
| **C** | 트랜잭션 경계를 1급 모듈로 | `flow/authorize` 등 5개 | flow → 도메인 전부 |

## 3. 결정

### **A. 진입 컨텍스트가 조율한다**

```
core/                                   ← ADR-004의 실시간 코어 (배포 단위 1)
  banking/                    C1
    domain/       Account · Receivable · DepositReceipt
    application/  ★ E3 미수 회수 · E5 입금 정정
    port/         공개 인터페이스 (C3가 호출)
    adapter/      영속성 · 전문 수신
  card/                       C2
    domain/       Card
    port/         공개 인터페이스
    adapter/
  payment/                    C3
    domain/       Authorization · ReversalTombstone · IdempotencyRecord · CaptureBatch
    application/  ★ E1 승인 · E2 매입 · E4 환불
                  └ banking.port · card.port 를 호출
    port/
    adapter/      매입사 ACL(R1) · 파일 수신
  shared/                     Money · BusinessDate 등 값 타입

  reconciliation/             C6  ★ 코어 안 (ADR-010) — 다섯 컨텍스트를 읽어야 한다
    domain/       Discrepancy
    application/  M9~M17 계산
  auth/                       C7  ★ 코어 안 (ADR-010) — R4가 동기다
  ops/                        C8  ★ 코어 안 (ADR-010 v0.2) — R14 동기 · 감사 수집(R13) · 승인 워크플로
                              (인가 계약 타입(주체·단계·스코프)은 shared/ — 전 컨텍스트 하향 의존, 새 상향·순환 없음: ADR-016 AU-6)

settlement/  ledger/          ← 위성 2 (배포 2·3)
```

### 왜 이것인가

| 근거 | 어디에 걸리나 |
|---|---|
| **컨텍스트 맵과 코드가 1:1로 대응**한다. R2·R3의 고객-공급자 방향이 그대로 의존 방향이 된다 | 컨텍스트 맵 R2·R3 |
| 의존이 **단방향**(C3 → C1, C3 → C2)이라 순환이 없다. C1 → C2 의존도 없다 | — |
| 조율이 **진입점 옆에** 있다 — 승인 전문을 받는 곳에서 승인 조율을 읽는다 | — |
| E3·E5는 **C1 안에서 끝난다** — 밖으로 꺼낼 이유가 없다 | Phase 2 E3·E5 참여자 |

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **B** 별도 응용 모듈 | 컨텍스트간 의존이 0이 되는 것은 장점이나, **R2·R3의 고객-공급자 관계가 코드에서 사라진다.** 그리고 트랜잭션 경계가 도메인 밖에 있으면 *"이건 어느 컨텍스트의 규칙인가"* 가 흐려진다 — Phase 2가 **소유권을 하나로 정하는 데** 열 라운드를 썼는데 그것을 코드에서 잃는다 | 조율이 **세 컨텍스트 이상**을 대등하게 엮게 될 때. 지금은 C3가 명확한 고객이다 |
| **C** 경계를 1급 모듈로 | E1~E5가 코드에 직접 드러나는 것은 매력적이나, **조회 경로와 배치가 flow에 안 들어간다.** 경계 5개에 모듈 5개는 구조가 아니라 나열이 된다 | 경계가 15개쯤으로 늘어 그 자체가 지도가 필요해질 때 |

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | 문서와 코드가 대응 · 의존 단방향 · 조율이 진입점 옆에 |
| **내주는 것** | **조율이 두 곳(C1·C3)에 나뉜다** — E1~E5를 한눈에 보려면 두 군데를 봐야 한다 |
| **새로 생기는 일** | ★ **모듈 경계를 무엇으로 강제할 것인가** (§5) |

### 규칙

| # | 규칙 | 왜 |
|---|---|---|
| **M-1** | 다른 컨텍스트의 `domain/`을 **직접 참조하지 않는다.** `port/`만 호출한다 | 경계가 무너지면 ADR-004의 전제가 무너진다 |
| **M-2** | `port/`는 **도메인 타입을 노출하지 않는다.** 값 타입(`shared/`)과 ID만 | 애그리게이트가 밖으로 새면 소유권이 흐려진다 |
| **M-3** | 의존 방향은 **C3 → C1 · C3 → C2** 뿐. **역방향·순환 금지** | R2·R3 |
| **M-4** | C1 → C2 의존도 **없다** | 컨텍스트 맵에 그 관계가 없다 |
| **M-5** | 위성(**C4·C5**)은 코어를 **동기 호출하지 않는다.** 이벤트로만 오간다(R5~R8·R11·R12) | R5~R12 |
| **M-6** | ★ **C6 대사는 코어 안에서 다른 컨텍스트를 읽는다.** 쓰지 않는다(R9 순응자) | ADR-010 |

## 5. 경계를 무엇으로 강제하나 ★★

**규칙을 문서로만 두면 사문화된다.** 이 프로젝트의 실측 결론이다
(`study/project-workflow/verification-by-construction.md`).

| 수단 | 강제력 | 대가 |
|---|---|---|
| **패키지 규약만** | ❌ 없음 — 주의력에 의존 | 0 |
| **아키텍처 테스트** | ⚠️ 빌드 시점에 검출 | 테스트 유지 |
| ★ **빌드 모듈 분리** | ✅ **컴파일이 거부** | 빌드 설정 복잡도 |

### 결정: **빌드 모듈 분리 + 아키텍처 테스트**

```
core:banking      → core:shared 만 의존
core:card         → core:shared 만 의존
core:payment      → core:shared · core:banking(port) · core:card(port)
core:auth         → core:shared · core:banking(port) · core:payment(port)      C7 (R4 동기)
core:reconciliation → core:shared · 위 전부의 (port)  ★ 읽기만 — 쓰기 의존 없음  C6 (M-6)
```

**`port/`를 별도 빌드 모듈로 뺀다.** 그러면 `core:payment`가 `core:banking:port`에는 의존하되
`core:banking:domain`에는 **컴파일 단계에서 의존할 수 없다.** M-1·M-2가 구조로 강제된다.

> ★ **M-3·M-4(방향·순환)도 빌드 그래프가 막는다.** 순환 의존은 빌드 도구가 거부한다.
>
> ⚠️ **아키텍처 테스트가 여전히 필요하다** — 빌드 모듈이 못 막는 것이 있다:
> 리플렉션 접근 · 같은 모듈 안의 레이어 위반 · `shared/`에 도메인 타입이 스며드는 것.

### 라이브러리는 정하지 않는다

`constraints.md` §3 — **프로세스별 필요한 능력을 먼저 적고 Phase 5에서 고른다.**
여기서 정한 것은 *"빌드 모듈로 나눈다"* 이지 *"어떤 도구로"* 가 아니다.

## 6. 되돌리는 조건

| # | 관찰되면 | 무엇을 뜻하나 | 그때 할 일 |
|---|---|---|---|
| **R1** | `port/`가 도메인 타입을 노출해야만 하는 사례가 반복된다 | 경계가 잘못 그어졌다 | 해당 컨텍스트의 책임 재검토 (Phase 2로) |
| **R2** | C1이 C3를 호출해야 하는 사례가 나온다 | R2·R3의 방향이 틀렸다 | 컨텍스트 맵 재검토 |
| **R3** | 조율이 두 곳에 나뉜 것이 **실제로 혼란을 만든다** | 안 B가 옳았다 | `application/` 모듈로 통합 |
| **R4** | 빌드 모듈 분리가 **개발 속도를 유의미하게 떨어뜨린다** | 강제 수단이 과했다 | 단일 모듈 + 아키텍처 테스트로 완화 |
