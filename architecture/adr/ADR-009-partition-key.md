# ADR-009. 파티션 키는 **계좌ID**로 한다 — 지금 나누지 않되 나눌 수 있게

- 일자: 2026-08-05
- 상태: **채택**
- 결정자: 사용자 · AI 페어
- 관련: **ADR-004**(배포 단위) · **ADR-008**(배치 파티션) · **HA-5**(expand-contract) · 품질 속성 **D-01**(데이터 계층 수평 분할 포기) · 시나리오 **QS-02**

---

## 1. 맥락 — 지금 안 나누는데 왜 정하나

**D-01**은 데이터 계층 수평 분할(샤딩)을 **포기**했다. 예상 부하가 단일 DB 범위이기 때문이다.
그런데 **파티션 키는 지금 정해야 한다.**

| 무엇 | 언제 필요한가 |
|---|---|
| **ADR-008 배치 파티션** | ★ **지금 필요하다** — 대사를 병렬로 돌려야 한다 |
| DB 샤딩 | 나중 (ADR-004 R1) |

> ★ **그리고 나중에 정할 수 없는 종류다.** `HA-5`(expand-contract)와 같은 성격이다 —
> 테이블 설계·인덱스·조회 경로가 파티션 키를 따라가므로, **나중에 정하면 전부 다시 짜야 한다.**

---

## 2. 후보

| # | 키 | E1 참여자가 같은 파티션에 들어가나 | 배치가 나뉘나 |
|---|---|---|---|
| **A** | **계좌ID** | ✅ (아래 §3) | ✅ 대사·정산 대부분 |
| **B** | 카드ID | ⚠️ 한 계좌에 카드 여러 장(CM1) → **계좌가 쪼개진다** | ⚠️ |
| **C** | 승인ID | ❌ 계좌·카드가 매번 다른 파티션 | ❌ |
| **D** | 가맹점ID | ❌ 자금 경로와 무관한 축 | ⚠️ 정산에만 유리 |

---

## 3. 결정

### **A. 계좌ID**

### E1 참여자가 전부 계좌ID로 유도되는지 확인했다

| 참여자 | 계좌ID로 유도되나 | 근거 |
|---|---|---|
| **계좌** | ✅ 자기 자신 | — |
| **카드** | ✅ 카드는 계좌에 속한다 | **CM1** |
| **승인** | ✅ 카드번호 → 카드 → 계좌 | BR-17 |
| **미수** | ✅ `accountId`를 든다 | `receivable.md` |
| **입금 수신** | ✅ `accountId`를 든다 | `deposit-receipt.md` |
| **멱등 레코드** | ⚠️ 키는 `correlationId`(매입사 생성)이지만 **전문에 카드번호가 있어 라우팅 가능** · 레코드를 그 계좌 파티션에 둔다 | BR-17 ① |
| **취소 예약** | ⚠️ 위와 같다. 망취소 전문(0400)에도 PAN이 있다 | BR-22 |

> ★ **E1·E3·E5가 계좌ID 파티션 안에서 닫힌다.**
>
> ⚠️ **E4(환불)는 안 닫힌다** (Phase 3 리뷰 D6이 정정). E4 참여자에 **`CaptureBatch`가 있다** —
> 매입 파일의 취소 레코드로 들어온 환불이 `markProcessed()`를 같은 커밋에 요구하기 때문이다
> (R7 U2). **E2와 같은 이유로 파일 단위 집합이 계좌로 안 나뉜다** → §4의 미해결에 함께 든다.

### 왜 이것인가

| 근거 | 어디에 걸리나 |
|---|---|
| **자금의 소유 축**이다 — 잔액·미수·한도가 전부 계좌에 걸린다 | Phase 2 소유권 표 |
| 대사 M9·M11·M12·M14가 **계좌별 등식**이다 | BR-41 |
| E1~E5 중 **셋(E1·E3·E5)이 이 축에서 닫힌다** | Phase 2 경계 |
| 나중에 샤딩할 때 **같은 키를 그대로 쓴다** — 배치 파티션과 샤드가 일치 | ADR-004 R1 |

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **B** 카드ID | 한 계좌에 카드가 여러 장이므로(**CM1**) **계좌가 여러 파티션으로 쪼개진다.** 계좌 잔액 등식(M9·M12)이 파티션을 넘는다 | 계좌:카드가 1:1이 되면 |
| **C** 승인ID | 승인마다 계좌·카드가 **다른 파티션**에 있게 되어 E1이 매번 파티션을 넘는다 | — |
| **D** 가맹점ID | 자금 경로와 무관한 축이다. 정산 집계에는 유리하나 **E1~E5가 전부 깨진다** | 정산 전용 파티션이 별도로 필요해질 때 (그때는 축을 두 개 쓴다) |

---

## 4. ★ E2·E4가 이 축에서 깨진다 — 미해결로 남긴다

```
E2 매입 반영 = 승인 · 계좌 · 카드 · 매입 배치 · 미수
                                  ↑
                        파일 단위 집합 — 여러 계좌에 걸친다
```

`CaptureBatch`는 `processedRecords`·`isolatedRecords`를 **파일 단위**로 든다.
계좌 파티션에 넣을 수 없다.

**그리고 그 집합이 멱등 장치다** — *"격리에 있다 = 미반영, 처리에 있다 = 반영됨"*.
샤드를 넘으면 **이중 출금 방어선이 깨진다**(Phase 2 R8 S1이 `promoteIsolated`를 E2로 올린 이유).

| 지금 | 영향 없음 — 단일 DB이므로 E2가 한 트랜잭션으로 성립한다 |
|---|---|
| **배치 파티션(ADR-008)** | ⚠️ 매입 배치를 계좌로 나누면 파일 단위 집합이 파티션을 넘는다 |
| **샤딩할 때(ADR-004 R1)** | ❌ **별도 설계 필요** |

### 지금 하는 것 / 안 하는 것

| | |
|---|---|
| **한다** | 매입 배치는 **파일 단위로 파티션**한다 (계좌가 아니라). 파일이 여럿이면 병렬이 된다 |
| **안 한다** | 파일 단위 집합을 계좌 축으로 재설계하는 것 |

> ★ **400 TPS에서 필요 없는 설계를 미리 하지 않는다.** 그것은 *"근거 없는 큰 수"* 와 같은 문제다
> (품질 속성 **D-03**). 대신 **미해결로 명시**해 나중에 잊지 않게 한다.

## 5. 결과

| | 내용 |
|---|---|
| **얻는 것** | 배치 병렬(ADR-008)이 지금 가능 · 샤딩 경로가 **열린 채로** 남는다 |
| **내주는 것** | 테이블·인덱스가 계좌ID를 **선행 키로** 갖게 된다 (조회 패턴 제약) |
| **새로 생기는 일** | ★ **모든 자금 테이블이 계좌ID를 갖고 있어야 한다** — 없으면 파티션 불가 |

### 규칙

| # | 규칙 | 왜 |
|---|---|---|
| **K-1** | 자금 관련 테이블은 **계좌ID를 컬럼으로 갖는다** (유도 가능해도 저장한다) | 조인 없이 파티션 판정 |
| **K-2** | 파티션 판정은 **계좌ID 해시**로 한다. 계좌ID 자체의 순서에 의존하지 않는다 | 편향 방지 |
| **K-3** | 파티션 수는 **설정값**이며 코드에 박지 않는다 | 재분배 |
| **K-4** | 계좌를 넘는 집계(M15 등)는 **파티션 완료 후 단일 단계**로 한다 | ADR-008 §4 |

> ★ **K-1이 지금 안 하면 나중에 못 하는 것이다.** 승인 테이블에 계좌ID가 없으면
> 파티션 판정에 매번 카드 조인이 필요하고, 샤딩 시에는 **아예 불가능**하다.

## 6. 되돌리는 조건

| # | 관찰되면 | 무엇을 뜻하나 | 그때 할 일 |
|---|---|---|---|
| **R1** | 파티션을 넘는 처리가 **M15·매입 배치 말고도 계속 늘어난다** | 계좌가 잘못된 축이다 | 축 재검토 — 그러나 **자금의 소유 축이 계좌라는 것은 도메인 사실**이므로 도메인부터 본다 |
| **R2** | 계좌별 **부하 편차가 심하다** (핫 계좌) | 해시로 안 풀리는 편중 | 핫 계좌 전용 처리 — 파티션 키는 유지 |
| **R3** | 매입 배치 파일 파티션이 **병렬이 안 된다** (파일이 항상 1개) | 파일 단위 축의 한계 | 파일 내부를 계좌로 재분할 — §4의 미해결을 그때 푼다 |
