# ADR-006. 대사 커트오프 — **마감 스냅샷 + Outbox 드레인**

> ⚠️ **이 결정은 [ADR-011](ADR-011-cutoff-narrowed.md)로 대체됐다.**
> 아래는 **당시의 판단 그대로**이며 수정되지 않았다.

- 일자: 2026-08-05
- 상태: ★ **대체됨 (ADR-011)** — 2026-08-05. ADR-010이 대사를 코어로 되돌려 범위가 4개에서 1개로 축소됐고, 남은 T2는 **lazy close**로 해소했다. **이 문서는 수정하지 않는다**
- 결정자: 사용자 · AI 페어
- 관련: **ADR-004**(배포 단위) · **ADR-005**(Outbox) · **BR-06**(마감) · **BR-41**(대사) · 품질 속성 **탐지가능성(4)** · 시나리오 **QS-04**
- ⚠️ **이 결정은 Phase 2 산출물을 변경한다** (§6)

## 1. 맥락 — ADR-004가 만든 숙제

대사(C6)가 별도 배포 단위가 되면서 **다섯 컨텍스트의 값을 같은 시점 기준으로 볼 수단이 없어졌다.**

### 어느 대사가 실제로 시점 문제를 겪나

| 유형 | 비교 대상 | 프로세스를 넘나 |
|---|---|---|
| **M9** 홀딩 정합 | 계좌 `holdTotal` ↔ 승인 `heldAmount` | ❌ **코어 안** — 같은 DB 스냅샷으로 끝 |
| **M10·M11** 한도 정합 | 카드·계좌 ↔ 승인 | ❌ 코어 안 |
| **M12** 잔액-원장 | 계좌 `balance` ↔ 원장 보조부 | ★ **넘는다** |
| **M14** 미수-원장 | 미수 ↔ 원장 보조부 | ★ **넘는다** |
| **M15** 정산 합계 | 정산 ↔ 승인 | ★ **넘는다** |
| **M1~M8** 매입 대사 | 승인 ↔ 매입 레코드 ↔ 원장 | ★ **넘는다** |

> ★ **크로스 대사는 전부 원장(C5) 또는 정산(C4)이 상대다.** 그리고 **그 둘은 Outbox로 코어의 사실을 받는다**(ADR-005).
> 즉 **시점 문제의 정체는 "원장이 아직 못 받은 이벤트"** 다.

```
코어    잔액 = 100  (매입 20 반영 완료)
원장    고객예금 = 120  (매입 20 이벤트를 아직 못 받음)
대사    "20 어긋났다"  ← 어긋난 게 아니다. 아직 도착 안 했을 뿐
```

**이것이 허위 불일치다.** 하루 수백 건씩 쌓이면 대사 자체가 무의미해진다 —
*"어차피 매일 뜨는 것"* 이 되어 **진짜 불일치가 묻힌다.**

| # | 안 | 시점을 어떻게 맞추나 | 새 개념 |
|---|---|---|---|

## 3. 결정

### **A. 마감 스냅샷 + Outbox 드레인**

```
① 영업일 마감 (BR-06)
      ↓
② Outbox 드레인 — 커트오프 이전 이벤트를 전부 전달 완료
      ↓
③ 코어: 계좌별 마감 스냅샷 확정  (한 트랜잭션 · 스냅샷 읽기)
      balance · Σ 미수 outstanding · holdTotal · dailyUsage
      ↓
④ 원장: 그 영업일까지의 보조부 잔액 집계
      ↓
⑤ 대사: ③과 ④를 비교  →  M12 · M14 · M15 · M1~M8
```

### 왜 이것인가

| 근거 | 어디에 걸리나 |
|---|---|
| ②가 **허위 불일치의 원인 자체를 제거**한다 — 비교 시점에 양쪽이 같은 사실 집합을 갖는다 | ADR-005 O-1 |
| ③이 **한 트랜잭션의 스냅샷 읽기**이므로 그 순간의 정확성은 **DB가 보장**한다 | — |
| **실제 은행의 EOD 방식**과 같다 | `constraints.md` §0 *"실제 은행 서비스를 기준으로"* |
| BR-42가 이미 *"정산 완료 시 자동 시작"* 이라 **순서가 맞는다** — 정산도 커트오프 후다 | **BR-42** |

### 왜 나머지를 기각했나

| 안 | 기각 이유 | 이 이유가 바뀌면 |
|---|---|---|
| **B** 워터마크 재구성 | ★ **우리는 상태를 저장하지 사건을 저장하지 않는다**(ADR-003). 과거 시점 상태를 재구성할 수단이 없다. 하려면 이벤트 소싱으로 가야 하고, 그것은 ADR-003이 기각했다 | ADR-003 R1이 발동해 부분 이벤트 소싱으로 갈 때 |
| **C** 허용 오차 | ★ **탐지가능성을 포기하는 것이다.** 임계 이하의 진짜 사고가 영원히 안 잡힌다. 그리고 임계값에 **근거가 없다** — `quality-scenarios.md`가 배제한 형태 | — (이 이유는 안 바뀐다) |
| **D** 대사를 코어로 | 시점 문제는 사라지지만 ADR-004를 되돌리는 것이다. **먼저 A를 시도하고 실패하면 그때** | ★ **R2** — 드레인이 실용적으로 안 될 때 |

## 4. 결과

| | 내용 |
|---|---|
| **얻는 것** | 허위 불일치 0 · 대사 결과를 신뢰할 수 있다 |
| **내주는 것** | **대사가 실시간이 아니다**(이미 D-05로 포기했다) · 마감 후 처리 시간이 길어진다 |
| **새로 생기는 일** | ★ **드레인 대기와 그 실패 처리** · 마감 스냅샷 저장 · 스냅샷 보관 기간 |

### 드레인이 안 끝나면 ★

무한정 기다릴 수 없다. **기다림에 상한이 있어야 하고, 초과 시 무엇을 할지 정해야 한다.**

| 상황 | 처리 |
|---|---|
| 드레인 완료 | 정상 — ③으로 |
| **상한 내 미완** | ★ **대사를 실행하지 않는다.** *"드레인 미완"* 을 **불일치로 적재**한다 |
| 반복 미완 | 릴레이 장애 — 운영 통지 |

> ★ **대사를 강행하지 않는 것이 핵심이다.** 미완 상태로 돌리면 **허위 불일치가 쏟아지고**,
> 그것이 정확히 이 ADR이 막으려는 것이다. **"대사를 못 했다"가 "틀린 대사 결과"보다 낫다.**
>
#### ★ BR-42와의 충돌 — 확인했고 해소한다 (P-3)

**BR-42**: *"대사는 정산 완료 시 자동 시작된다. 정산 미결이 임계를 넘으면 **정산 완료 없이도 강제 실행**된다."*
근거는 *"대사를 정산에만 의존시키면 정산 실패 시 **진단 수단이 막힌다**"* 였다.

**겹치는 구간에서 정면으로 부딪힌다:**

```
정산 미결 + 드레인 미완
  BR-42     강제 실행하라   (진단이 막히면 안 되니까)
  ADR-006   실행하지 마라   (허위 불일치가 쏟아지니까)
```

**해소: 트리거와 전제조건을 가른다.**

| | 무엇 | 값 |
|---|---|---|
| **트리거** | 언제 시작하는가 | 정산 완료 · 운영자 수동 · **정산 미결 임계 초과** (BR-42 그대로) |
| **전제조건** | 시작해도 되는가 | ★ **드레인 완료** (신설) |

**전제조건이 미충족이면 트리거가 무엇이든 실행하지 않고 M16을 적재한다.**

> ★ **이 해소가 BR-42의 의도를 해치지 않는다.** BR-42가 걱정한 것은 *"진단 수단이 막히는 것"* 인데,
> 드레인 미완 상태로 대사를 돌리면 **허위 불일치가 쏟아져 진단으로도 쓸모가 없다.**
> 대신 **M16(드레인 미완) 자체가 진단 정보다** — *"릴레이가 밀려 있다"* 를 정확히 알려준다.
>
> ⚠️ **각각은 맞는데 합치면 깨지는 형태**였다. DC-003에서 겪은 것과 같다
> (R8 S8과 R9 H1이 각각은 옳았는데 합쳐서 깨졌다). **적용 전에 확인해서 다행이다.**

### 마감 스냅샷은 합계 필드인가

**아니다.** `04-aggregate-format.md` §4 판정을 적용하면:

| 질문 | 답 |
|---|---|
| 저장 대신 매번 계산하면 무엇이 안 되나 | **시점이 흐른다** — 대사의 목적 자체가 사라진다 |
| 구성 요소와 어긋날 수 있나 | ❌ **한 트랜잭션의 스냅샷 읽기로 뜨므로 그 순간 정확하다** |
| 이후에 바뀌나 | ❌ **마감 후 불변** |

> ★ **합계 필드의 위험은 "저장한 값과 실제가 시간에 따라 벌어지는 것"이다.**
> 마감 스냅샷은 **시간이 흐르지 않는 값**이므로 그 위험이 없다.
> 정산 `captureTotal`이 ③인 것과 대비된다 — 그건 **누적되는 값**이다.

## 5. 되돌리는 조건

| # | 관찰되면 | 무엇을 뜻하나 | 그때 할 일 |
|---|---|---|---|
| **R1** | 드레인 대기가 **마감 후 처리 시간(QS-04 1시간)을 잡아먹는다** | 릴레이 처리량 부족 | 릴레이 병렬화 → **ADR-005 R2(CDC)** |
| **R2** | 드레인이 **상시 미완**이라 대사가 자주 못 돈다 | 비동기 경계의 대가가 감당 범위를 넘었다 | ★ **안 D — 대사를 코어로** (ADR-004 R2와 같은 신호) |
| **R3** | 마감 스냅샷 저장량이 **부담**이 된다 | 보관 정책 실패 | 보관 기간 단축 · 집계 후 원본 삭제 |
| **R4** | 커트오프 경계에서 **귀속 영업일 판정이 흔들린다** | 마감 시각 경계 경합 | BR-14·BR-47 재검토 (Phase 2로) |

## 6. ★ Phase 2에 미치는 영향

**이 ADR은 도메인 개념을 추가한다.** 아키텍처 결정이 앞 Phase를 바꾸는 정당한 경로이며,
`project-workflow/README.md`가 정한 *"순서를 벗어나는 경로"* 에 해당한다.

| # | 무엇 | 어디 |
|---|---|---|
| **P-1** | **마감 스냅샷** 개념 신설 — 계좌별 (영업일, balance, 미수 합계, holdTotal, dailyUsage) | `domain/aggregates/` · 용어사전 |
| **P-2** | **커트오프 절차** 규칙 신설 — 마감 → 드레인 → 스냅샷 → 정산 → 대사 순서 | `product/01-business-rules.md` |
| **P-3** | ✅ **확인 완료 — 충돌했고 해소했다** (§4). BR-42는 **트리거**, 드레인은 **전제조건**으로 가른다. 규칙 본문에 반영 필요 | **BR-42** |

> ★ **P-3은 실제로 충돌했고 §4에서 해소했다.** 나머지 넷은 적용 대상이다.

## 7. 검증

| 언제 | 무엇으로 | 통과 기준 |
|---|---|---|
| Phase 5 | QS-04 대사 | **정상 상태에서 M1~M15 불일치 0건** — 허위 불일치가 없다 |
| Phase 5 | 드레인 미완 주입 | 대사가 **실행되지 않고** M16이 적재된다 |
| Phase 5 | 커트오프 직전·직후 거래 주입 | 귀속 영업일이 **BR-14대로** 갈린다 |
| Phase 5 | 진짜 불일치 주입 | 스냅샷 기준으로 **정확히 탐지**된다 |

> ★ **첫 번째 항목이 이 ADR의 존재 이유다.** *"정상인데 아무것도 안 잡힌다"* 를 통과 기준으로
> 두는 검증은 드물지만, **허위 불일치가 대사를 죽이는 방식**이기 때문에 필요하다.
