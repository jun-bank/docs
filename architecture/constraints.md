## 0. 이 프로젝트의 목적 ★★

**설계 경험을 쌓는 것이다.** 사용자 진술(2026-08-05):

> *"최대한 크게 하되, 이때 이 큰 걸 **아주 작은 단위로 끊어보는 연습**을 하려는 것."*

이 목적이 **제약 판단의 기준 자체를 바꾼다.**

**산출물이 둘이다.**

| # | 산출물 | 어디 |
|---|---|---|
| ① | **결제 시스템** | `product/` `domain/` `architecture/` … |
| ② | ★ **설계 워크플로우 자체** | `study/project-workflow/` |

> 사용자 진술: *"설계 워크플로우를 만들면서 흐름을 보고 이를 바탕으로 설계 역량을 키우고,
> 이 경험을 바탕으로 나중에 실무에서는 **필요한 부분만 부분적으로 활용**해서 응용 가능하다."*
>
> ★ **②가 ①보다 오래 산다.** 결제 시스템은 이 프로젝트로 끝나지만 워크플로우는 다음 일에 쓰인다.
> 그래서 **워크플로우 문서는 "부분 채택 가능"해야 한다** — 전부 따라야만 쓸모 있는 절차는
> 실무에서 안 쓰인다.

| | 보통의 프로젝트 | 이 프로젝트 |
|---|---|---|
| 운영 인력·개발 인력 | 고정된 자원 → **선택지를 지운다** | ★ **필요한 만큼 늘어난다고 가정** |
| 좋은 결정의 기준 | 운영 편의 · 납기 | **설계의 정확성** · 끊는 연습의 학습 가치 |
| 복잡도 | 줄이는 것이 미덕 | **실제 은행이 하는 만큼**은 감당한다 |

> ⚠️ **"최대한 크게"가 오버엔지니어링의 허가는 아니다.** 사용자가 같은 대화에서
> *"오버엔지니어링보단 실제 은행 서비스를 기준으로"* 라고 못박았다.
> **기준선은 실제 은행이고, 그 이상은 하지 않는다** — 품질 속성 **D-03(과잉 처리량)** 과 같은 판단이다.

> ★ **"작은 단위로 끊는다"가 일정 방식도 정한다.** 사용자 진술: *"애자일 형태로 기본 파이프라인을
> 만들고 거기에 여러 조건들을 붙이는 방향."* 이것은 **범위를 줄이는 것이 아니라 순서를 정하는 것**이다
> — 전부 만들되 뼈대부터. Walking Skeleton의 원래 뜻과 같다.

### 1.1 조직 제약 철회가 무엇을 바꾸고 무엇을 안 바꾸나 ★★

C-01·C-02·C-03이 철회됐다. **설계 공간이 실제로 넓어진다** — 그 셋이 지우던 것들:

| 지워졌던 것 | 지금 |
|---|---|
| 다중 배포 단위 | **후보로 복원** — ADR-001 재검토 대상 |
| 브로커 상시 운영 | **후보로 복원** |
| 분산 추적·중앙 로그 수집 | **후보로 복원** |
| 전 유스케이스 구현 | **한다** |

**그러나 다음은 조직 제약과 무관하므로 그대로다.**

| 남는 것 | 왜 |
|---|---|
| ★ **E1·E2·E4가 C1·C2·C3를 한 커밋으로 요구한다** | **도메인 사실**이다. 인원이 늘어도 안 바뀐다 |
| ★ **대사(C6)는 다섯 컨텍스트의 "진짜 값"을 봐야 한다** | R9 순응자·읽기 전용. **사본을 보면 감사가 아니다** |
| **C-04 예산 0** | 실행 환경 제한 |
| **C-05~07** 기술 스택 | |

> ★ **정합성은 인원으로 살 수 없다.** 사람을 늘려도 분산 트랜잭션은 분산 트랜잭션이다.
> 그래서 **ADR-001의 안 B 기각은 유지되고, 안 C·E는 재검토 대상**이 된다.

### 1.2 C-04와 설계의 관계 — 실행과 설계를 가른다

예산 0은 **지금 무엇을 띄울 수 있는가**만 제한한다. **설계가 그것을 전제하면 안 된다** —
품질 속성 §2.1이 고가용성에서 내린 판단과 같다.

```
설계    다중 인스턴스·브로커·복제를 전제할 수 있다
실행    지금은 로컬 단일 구성으로 돌린다
```

### 1.3 (참고) 철회 전 판단 — C-01이 절반만 완화되던 이유

사용자 판단: *"제약은 괜찮아, 너랑 구현하잖아."*

**맞다. 다만 무엇이 완화되고 무엇이 안 되는지를 가른다.**

| | 완화되나 | 실측 근거 |
|---|---|---|
| **코드 작성 속도** | ✅ **크게 완화** | Phase 2에서 문서 11종·상태 머신 8종·규칙 51개를 3일에 작성 |
| **검증 부담** | ❌ **오히려 는다** | 그 산출물에 **치명 36건**이 있었다. 리뷰어 둘 × **10라운드**가 필요했다 |
| **운영 대응** | ❌ **전혀 완화 안 됨** | 장애는 사람이 받는다. AI는 호출돼야 움직인다 (C-02) |

> ★ **생산량이 늘면 검증 부담도 같이 는다.** 이것이 이 프로젝트의 가장 큰 실측이다
> (`study/project-workflow/docs-only-limits.md`). 빨리 만드는 것은 해결된 문제이고,
> **빨리 만든 것이 맞는지 아는 것**이 남은 문제다.
>
> **그래서 C-01 완화가 설계 공간을 넓히지 않는다** — 지우는 주체는 C-02이기 때문이다.

### 1.4 (참고) 철회 전 판단 — C-02가 가장 많은 것을 지우던 이유

운영 인력이 **개발자 본인 1명**이라는 것은 *"운영 복잡도가 곧 개발 시간을 먹는다"* 는 뜻이다.

| 지워지는 것 | 왜 |
|---|---|
| **다중 배포 단위(MSA)** | 배포·모니터링·장애 대응이 단위 수만큼 곱해진다 |
| **메시지 브로커 상시 운영** | Kafka·RabbitMQ는 그 자체가 운영 대상이다 (C-04와 겹침) |
| **분산 추적·중앙 로그 수집 스택** | 운영할 사람이 없다 |
| **수동 개입 전제 복구 절차** | 새벽에 깨어 있을 사람이 없다 → **자동 재시도 + 실패 시 적재**로 간다 |

> ★ **이것이 이 프로젝트에서 가장 중요한 제약이다.** Phase 2가 만든 도메인은 컨텍스트 6개이지만,
> **컨텍스트 ≠ 서비스**다. 배포 단위 수는 **C-02가 정한다** — C-01이 완화돼도 이 제약은 남는다.

### 1.5 (참고) 철회 전 판단 — C-03이 범위를 줄이던 이유

2주는 **"전부 만든다"가 불가능한 기간**이다. 양식(`01` §4)이 정한 대로 일정 제약은
**범위 축소의 근거**로 쓴다 — 품질을 낮추는 근거가 아니다.

```
줄이는 것    유스케이스 수 · 외부 연동 실체 · 운영 도구
줄이지 않는 것  자금 보존 · 대사 · 감사가능성   ← 도메인이 요구하는 것
```

> ⚠️ **load-bearing 가정**: 2주는 **Phase 3~5(아키텍처 + 샘플 유스케이스 E2E)** 의 기간으로 본다.
> Phase 6~9까지 포함이면 범위를 더 줄여야 한다 — **확인 필요**(§4 R1).

## 2. 제약이 아닌 것 (확인함)

| 후보 | 왜 제약이 아닌가 |
|---|---|
| **MSA로 만든다** | 사용자가 *"MSA 구조라면"* 이라고 조건부로 언급했다. **아직 정해진 것이 아니고**, **C-02**가 이 안을 강하게 제한한다 → **ADR에서 판정** |
| **게이트웨이를 둔다** | 위와 같다. 배포 단위가 하나면 필요 없다 → **ADR에서 판정** |
| **특정 라이브러리 채택** | 사용자가 *"기능별로 필요한 것을 정리·분리하는 게 맞다"* 고 명시했다. **구조 확정 후 Phase 5에서 고른다** |
| **성능이 좋아야 한다** | 어기면 *"느려진다"* 이므로 품질 속성이다 → `quality-attributes.md` |
| **정합성이 중요하다** | 위와 같다. 품질 속성이며, 이 프로젝트에서 **1순위 후보**다 |

> ★ **"MSA"와 "게이트웨이"를 제약에서 뺀 것이 이 문서의 판정 중 가장 중요하다.**
> 사용자도 *"우선 전체 구조부터 정하는 게 맞다"* 고 했다 — **구조는 제약이 아니라 결정**이고,
> 결정은 근거(제약 + 품질 시나리오)를 갖춰야 한다.

## 3. 라이브러리·알고리즘은 여기서 정하지 않는다

사용자 방침: *"바로 이거 이거 쓰기보단 각 프로세스별 필요한 라이브러리나 알고리즘을 정리·분리하는 게 맞다."*

| 시점 | 정하는 것 |
|---|---|
| **Phase 3 (지금)** | 배포 단위 수 · 통신 방식 · 일관성 모델 · 데이터 저장 위치 |
| **Phase 4** | 계약(API·이벤트 스키마) |
| **Phase 5** | ★ **프로세스별로 필요한 능력을 먼저 적고**, 그 능력을 채우는 라이브러리를 고른다 |

```
Phase 5에서 쓰는 순서
  ① 이 프로세스가 필요로 하는 능력      "멱등 저장", "영업일 배치 스케줄", "재시도 백오프"
  ② 그 능력의 판단 기준                  C-02(운영 1명)에 걸리는가
  ③ 후보와 기각 이유                     ADR 또는 기반 결정서
```

> ⚠️ **미정을 미정으로 남기는 것이 이 절의 목적이다.** 지금 라이브러리를 정하면
> **구조가 라이브러리에 끌려간다** — Phase 2에서 *"저장 구조가 도메인을 지배한다"* 를
> 흔한 실수로 등재한 것과 같은 형태다.

## 5. 이 제약이 남기는 설계 공간

**지워지고 남은 것**을 적어둔다 — ADR이 여기서 출발한다.

| 결정할 것 | 제약이 남긴 후보 |
|---|---|
| **배포 단위 수** | 단일 배포(모듈러 모놀리스) / 2~3개 분할 — **6개 분할은 C-02가 지웠다** (C-01 완화와 무관) |
| **컨텍스트 간 통신** | 인-프로세스 이벤트 / DB 기반 Outbox — **브로커 상시 운영은 C-02·C-04가 지웠다** |
| **일관성 모델** | 트랜잭션 경계(E1~E5) 안은 **강한 일관성**(MySQL 트랜잭션), 밖은 **최종 일관성 + 대사** |
| **배치 실행** | 앱 내 스케줄러 / 외부 크론 — **오케스트레이터는 C-02가 지웠다** |
| **저장소 분리** | 단일 스키마 / 스키마 분리 — 소유권(Phase 2)을 지키는 선에서 |

> ★ **트랜잭션 경계 E1~E5가 분할의 하한이다.** E2(매입 반영)는 승인·계좌·카드·배치·미수가
> **한 커밋**이어야 하므로, 이 다섯이 서로 다른 서비스에 있으면 **분산 트랜잭션이 된다.**
> Phase 2가 열 라운드에 걸쳐 막은 사고가 아키텍처에서 되살아나는 경로다.
