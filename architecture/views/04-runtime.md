# 런타임 뷰 — 자금이 움직이는 흐름

- 작성일: 2026-08-05
- 독자: 개발자 · 장애 대응
- 답하는 질문: **한 요청이 어떤 순서로 흐르나** · ★ **어디까지가 한 트랜잭션인가**
- 답하지 않는 질문: 배포 단위(→ 컨테이너 뷰) · 소유(→ 데이터 뷰)

> ★ **커밋 경계를 그림에 표시한다.** 분산 트랜잭션이 있으면 여기서 보여야 한다.

---

## 1. E1 승인 성립

```
매입사 ──승인 전문──▶ C3
                      │
        ┌─────────────┴──────────── 한 트랜잭션 (코어) ───────────┐
        │ ① 멱등 조회 — 이미 처리했나        (IdempotencyRecord) │
        │ ② 취소 예약 조회 — 망취소가 먼저 왔나 (ReversalTombstone)│
        │ ③ 카드 사용 가능 판정               (Card)              │
        │ ④ 가용잔액 = balance − holdTotal    (Account) ★ 쓰기 DS │
        │ ⑤ 한도 검사 (카드·계좌 두 층)                           │
        │ ⑥ 홀딩·한도 점유 · 승인 생성 · 멱등 기록                │
        │    heldAmount · limitContribution · limitBasisDate      │
        └────────────────────── COMMIT ──────────────────────────┘
                      │
                      ▼ 승인/거절 응답 (목표 p99 3초 · BR-01)
```

| 항목 | |
|---|---|
| **격리 수준** | READ COMMITTED (ADR-012 §2.2) |
| **락** | 낙관적 (W-5). 쓰기 순서 = 승인 → 계좌 → 카드 |
| **타임아웃** | ★ **내부 deadline 2.5초** > 쿼리 1초 > 락 0.5초 (ADR-013 T-11~T-13). 나머지 0.5초는 응답 예약분 |
| **실패하면** | 롤백. 부분 반영 없음 → 매입사가 재시도하면 ①이 흡수 |
| **원장** | ❌ **전표 없음** — 홀딩은 자금 이동이 아니다(BR-39) |
| ★ **이동 행** | ❌ **갱신 없음** — 홀딩은 `balance`를 안 바꾼다. ⚠️ *"모든 조작이 갱신"* 을 E1에도 적용하려는 오독을 막는다 |

## 2. E2 매입 반영

```
매입 파일 ──▶ CaptureBatch (레코드 순번 범위로 파티션 · ADR-009 R3)
                │
    ┌───────────┴─────────── 한 트랜잭션 (레코드 하나) ──────────┐
    │ ① 원승인 매칭 — 없으면 M2 / 무효면 M8 격리                 │
    │ ② 승인 상태 전이 (CAPTURED)                                │
    │ ③ 홀딩 전액 해제 · 부분 매입이면 한도 복원                  │
    │    ★ at.영업일 == limitBasisDate 일 때만 (DC-003)          │
    │ ④ 계좌 출금 — 부족분은 Receivable.incur                    │
    │ ⑤ CaptureBatch.markProcessed / promoteIsolated             │
    │ ⑤'★ AccountDailyMovement(귀속 영업일) upsert (DC-005)         │
    │ ⑥ outbox INSERT — Withdrawn · ReceivableIncurred · Captured│
    └────────────────────── COMMIT ─────────────────────────────┘
                │
                ▼ 릴레이 (파티션 소유 · 순번 오름차순 · ADR-014)
           원장 · 정산
```

> ★ **⑤가 멱등 장치다.** *"격리에 있다 = 미반영, 처리에 있다 = 반영됨"* —
> ④와 ⑤가 갈리면 **재처리가 또 출금**한다(R8 S1).

## 3. E4 환불 (매입 파일의 취소 레코드)

```
    ┌──────────────── 한 트랜잭션 ────────────────┐
    │ ① refundedTotal 증가 (INV-7 상한 검사)      │
    │ ② 반환액·소멸액 파생                        │
    │ ③ ★ 미수 writeOff (소멸 먼저)               │
    │ ④ 계좌 refund — 반환액 입금 + FIFO 회수     │
    │    ★ 반환액 0이어도 부른다 (INV-3 재평가)   │
    │ ⑤ returnedTotal 증가                        │
    │ ⑤'★ AccountDailyMovement upsert (DC-005)       │
    │ ⑥ markProcessed (취소 레코드)               │
    │ ⑦ outbox — Refunded · ReceivableWrittenOff  │
    └──────────────── COMMIT ─────────────────────┘
```

> ★ **③→④ 순서가 규칙이다.** 뒤집으면 회수가 잔여 채무를 줄여 `writeOff`가 거절된다.

## 4. 영업일 커트오프 (BR-52)

```
23:00  마감
  │
  ├─ ① Outbox 드레인 ─────────── 원장·정산이 D일 사실을 전부 받는다
  │      미완이면 → ★ 대사 실행 안 함 · M16 적재 · BR-53 통지
  │
  ├─ ② 정산 산출 → SettlementCompleted (R11) → 승인 markSettled
  │
  ├─ ③ ★ 두 번째 드레인 ──────── 정산이 만든 이벤트를 전달
  │
  └─ ④ 대사 (파티션 병렬 · 코어 안에서 읽기)
         M9·M10·M11        계좌·카드 ↔ 승인      (실시간 값)
         M12·M14           AccountDailyMovement 행 ↔ 원장 보조부
         M15               정산 ↔ 승인
         M1~M8             승인 ↔ 매입 ↔ 원장
         → 불일치 적재. ★ 자동 정정 없음 (BR-09)
```

> ★ **③이 없으면 M15가 매일 허위로 뜬다** — Phase 3 리뷰가 expected 130,000 / actual 0으로 실증했다.

## 5. 실패 경로

| 흐름 | 실패 | 무엇이 일어나나 |
|---|---|---|
| E1 | 응답 유실 | 매입사 → 망취소 → 홀딩·한도 복원(성립했으면) 또는 **취소 예약**(아직이면) |
| E1 | 락 충돌 | 재시도 3회 · ★ **내부 deadline 2.5초를 넘으면 거절**(W-10 · T-11). 3초는 **외부 응답 목표**다 |
| E2 | 커밋 후 종료 | outbox가 남아 있다 → 릴레이가 재전달 |
| E2 | 보류 격리 | 재처리 배치가 `promoteIsolated`로 원자 이동 |
| 릴레이 | 영구 실패 | 5회 후 **DLQ + M17** — 뒤 이벤트는 계속 나간다 |
| 릴레이 | 좀비 | **fencing token**이 늦은 쓰기를 거부(B-8) |
| 커트오프 | 드레인 미완 | **대사 안 함** + M16 + 통지 |

## 6. ★ 책임자 승인 조작 — 입금 역분개 (BR-56 ① · E5 · 2026-08-05 신설)

> 사람이 자극원인 첫 런타임 흐름이다. **코어 안 ①~③은 이 형태**(동기 확인·소비 — R14), **④ 정산 재개·⑤ 원장 역분개는 지시 이벤트**(R15)로 갈린다 — C4·C5가 별도 배포라서다.

```
① 운영자 A(담당자)  → C8: request(입금 역분개, reversalId·원입금·금액)   [PENDING · 감사 append]
② 운영자 B(책임자)  → C8: approve()          [B ≠ A — ApprovalRequest INV-1 · 감사 append]
③ 운영자 A          → C1: reverseDeposit(reversalId, 원입금, 금액, A)
     C1 → C8: consume() 동기 호출 (R14 — ★ C8이 자기 상태를 바꾸는 관리 오퍼레이션.
              타 컨텍스트의 직접 테이블 쓰기가 아니다 — 실행 인자 = 요청 인자, INV-3)
     [E5 트랜잭션] DepositReceipt 기록 · balance 감소 · 부족분 Receivable.incur
                  · AccountDailyMovement 갱신 · ★ 감사 outbox INSERT(AD-2)
                  · ★ C8 consume 참여 — 같은 트랜잭션 (커밋 실패 시 승인도 미소비)
④ 릴레이            → C8: 감사 이벤트 전달 (R13) → C5: DepositReversed 기표 (R6)
```

- **승인 전 실행 경로가 없다** — ③의 사전조건이 구조로 막는다(AF1).
- consume이 실행 커밋과 같은 트랜잭션이므로 **승인 1건 = 실행 1회**(INV-2 — 커밋 실패 시 승인도 소비되지 않는다).
