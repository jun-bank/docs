# ADR-0001: 시스템 아키텍처로 마이크로서비스를 채택한다

- 상태: **제안됨** — 사용자 확정 대기
- 일자: 2026-08-03
- 추상화 레벨: ① 아키텍처 설계
- 관련: `02-drivers/01-constraints.md` · `02-drivers/02-quality-attributes.md` · `study/05-architecture-styles/`

---

## 맥락

jun-bank는 이미 11개 서비스로 분리된 상태로 존재한다. 그러나 **왜 분산형을 택했는지에 대한 기록이 없다.** 서비스 경계는 기술적 직관으로 정해졌고, 그 결과:

- `Money` 값 객체가 6개 서비스에 각각 복붙됨
- `transfer-service`에만 Outbox/Saga가 있고 나머지엔 없음 — 신뢰성 전략이 서비스마다 다름
- `card-service` 안에 `card`와 `payment` 두 도메인이 함께 있음

이 ADR은 **이미 내려진 결정을 사후에 정당화하는 것이 아니라, 원점에서 다시 판단하는 것**이 목적이다. 결론이 "모놀리식으로 되돌린다"여도 무방하다.

> 이 결정은 `01-constraints.md` §2.3에서 **"되돌리기 매우 어려움"**으로 분류된 항목이다. 따라서 ADR이 필수다.

## 검토한 선택지

### 선택지 A: 모놀리식 (레이어드 + 모듈러)

단일 배포 단위 안에서 도메인별 모듈로 분리. 단일 DB, 로컬 트랜잭션.

- **장점**: 트랜잭션이 단순(ACID 하나로 끝남) · 운영 부담 최소 · 정합성 보장이 쉬움 · 기동 빠름 · 디버깅 쉬움
- **단점**: **분산 처리 기법을 배울 기회가 사라진다** · 모듈 경계가 코드로만 강제되어 무너지기 쉬움
- **치명적 문제**: BC-7(학습 목적)을 정면으로 위배. **Saga·Outbox·망취소가 필요 없어진다** — 이 프로젝트의 존재 이유가 사라짐

### 선택지 B: 서비스 기반 아키텍처 (Service-Based)

몇 개의 굵직한 서비스로 나누되 **DB는 공유**.

- **장점**: 배포 분리의 이점은 얻으면서 **트랜잭션은 여전히 단순** · 운영 부담이 MSA보다 훨씬 작음 · MSA로 가는 중간 단계로 적절
- **단점**: DB 공유가 서비스 간 결합을 남김 · **분산 트랜잭션 문제가 발생하지 않아** 학습 목표의 절반이 사라짐
- **평가**: 실무에서는 종종 최선이지만, **본 프로젝트의 학습 목표와 어긋난다**

### 선택지 C: 마이크로서비스 (서비스별 DB 분리)

도메인별 서비스 + 서비스별 DB + 이벤트 기반 통신.

- **장점**: **결제 도메인이 요구하는 분산 처리 기법이 전부 필연이 된다** · 기존 자산 활용 · 바운디드 컨텍스트를 물리적으로 강제
- **단점**: 분산 트랜잭션 · 운영 복잡도 · 로컬 자원 소모 · **1인 개발에 부담**
- **평가**: 대가가 크지만 그 대가 자체가 학습 대상

## 결정 (제안)

**선택지 C — 마이크로서비스를 채택한다.**

근거는 **품질이 아니라 목적**이다. 세 선택지를 품질 속성만으로 비교하면 **A 또는 B가 이긴다.** 기능 정확성(1위)은 단일 트랜잭션이 압도적으로 유리하고, 1인 운영 부담(BC-2)도 A/B가 낫다.

그럼에도 C를 택하는 이유는 **제약 BC-7 때문이다**: 이 프로젝트의 1차 산출물은 동작하는 은행이 아니라 **분산 환경에서 정합성을 지키는 방법에 대한 이해**다. A를 택하면 Saga·Outbox·멱등성·망취소·대사가 전부 불필요해지고, 그러면 배울 것이 남지 않는다.

> **이것은 "MSA가 더 좋아서"가 아니다.** 더 어려운 길을 의도적으로 고른 것이며, 그 어려움이 학습 대상이다. 실무 프로젝트였다면 B를 택했을 것이다.

### 함께 확정하는 것

- 서비스 간 통신: 동기 = OpenFeign, 비동기 = Kafka (제약 TC-1)
- 분산 트랜잭션: **2PC 미사용, 보상 기반(Saga)** → 상세는 `drafts/03-transaction-design.md`
- DB: 서비스별 분리 (제약 TC-2)

### 함께 확정하지 않는 것 (별도 ADR)

- **서비스를 몇 개로, 어떤 경계로 나눌 것인가** → ADR-0003 (예정). 이 ADR은 "분산형으로 간다"까지만 정한다
- 애플리케이션 아키텍처(레이어드/헥사고날) → ADR-0002 (예정)
- 오케스트레이션 vs 코레오그래피 → ADR-0004 (예정)

## 결과

### 좋아지는 것
- 결제 도메인이 요구하는 분산 처리 기법이 **회피 불가능**해진다 (= 학습 목표 달성)
- 바운디드 컨텍스트가 물리적으로 강제되어 경계가 코드로 무너지지 않는다
- 기존 11개 저장소 자산을 버리지 않는다

### 나빠지는 것 / 감수하는 것
- **정합성 보장 비용이 크게 증가**한다 — 품질 1위 항목을 어렵게 만드는 선택임을 인정한다
- 로컬 자원 소모, 기동 시간 증가 (제약 TC-5)
- 1인 운영 부담 (제약 BC-2)
- 디버깅·추적이 어려워진다 → 분산 추적(QS-11)이 **선택이 아니라 필수**가 됨

### 이 결정이 강제하는 후속 작업
1. **서비스 분할 기준 수립 후 현재 경계 재평가** (ADR-0003)
2. **트랜잭션 경계와 보상 전략을 시스템 전역 규약으로 통일** — 현재 서비스마다 다름 (`drafts/03-transaction-design.md`)
3. **멱등성 규약** 수립 — 모든 상태 변경 API에 적용
4. **Outbox 표준화** — 현재 `transfer-service`에만 존재
5. **분산 추적 필수화** (QS-11)
6. `Money` 등 공용 개념의 처리 방침 확정 (ADR-0005 예정)

## 되돌리는 조건

아래 중 **하나라도** 관측되면 이 결정을 재검토한다.

1. **로컬 단일 머신에서 전체 기동이 불가능해질 때** (제약 TC-5 위반, QS-10 실패)
2. **운영 부담 때문에 학습 사이클이 멈출 때** — 한 유스케이스를 도는 데 드는 시간의 절반 이상이 인프라 씨름이면 목적이 전도된 것
3. **정합성 오류를 잡지 못한 채 3회 이상 같은 유형이 재발할 때** — 분산의 대가가 학습 이득을 넘어선 상태
4. 학습 목표가 바뀌어 BC-7이 더 이상 유효하지 않을 때

되돌릴 경우의 경로: **C → B(서비스 기반, DB 통합)** 가 C → A 보다 현실적이다.
