# jun-bank 설계 문서

jun-bank 시스템의 **단일 설계 출처(single source of design truth)**.
각 서비스 저장소의 README는 "그 서비스를 어떻게 돌리나"만 다루고, **"왜 그렇게 설계했나"는 전부 여기**에 있다.

---

## 읽는 순서

문서는 4개 층으로 쌓이며, **위층이 아래층의 입력**이다. 아래층에서 위층의 결정을 임의로 바꾸지 않는다.

```
0. product/       무슨 서비스인가            ← 여기서 시작
      ↓
1. domain/        어떤 개념으로 이루어지나
      ↓
2. architecture/  어떻게 나누고 왜 그렇게 정했나
      ↓
3. backlog/       무엇부터 만드나
```

| 층 | 디렉토리 | 내용 | 상태 |
|---|---|---|---|
| 0 | `product/` | 제품 정의, 범위, 액터, 시나리오, 비즈니스 규칙 | 초안 v0.1 |
| 1 | `domain/` | 용어사전, 이벤트 스토밍, 컨텍스트 맵, 애그리게이트, 상태 머신 | 작성 중 |
| 2 | `drafts/architecture/` | SAD(arc42), ADR(MADR), 품질 속성 | 골격만 |
| 2 | `contracts/` | OpenAPI(동기 계약), 이벤트 카탈로그(비동기 계약) | 미착수 |
| 2 | `drafts/conventions/` | git·버전·커밋·코딩·마이그레이션 규약 | 미착수 |
| 3 | `backlog/` | 에픽, 스프린트, 완료 정의 | 미착수 |

---

## 문서 규칙

1. **결정은 ADR에만.** 다른 문서에 "~하기로 했다"가 있으면 그건 ADR 링크를 달아야 한다. 결정의 근거가 두 곳에 있으면 반드시 갈라진다.
2. **미확정은 숨기지 않는다.** 정해지지 않은 건 `> **결정 필요 #n**:` 블록으로 문서 안에 남긴다. 다음 층으로 임의 추정해서 넘기지 않는다.
3. **용어는 `domain/glossary.md`가 정본.** 다른 문서에서 용어를 새로 정의하지 않는다.
4. **문서도 버전을 갖는다.** 각 문서 하단에 변경 이력. 큰 변경은 PR로.

---

## 이 프로젝트의 목표

기법을 써보기 위해 도메인을 고르는 것이 아니라, **도메인이 기법을 요구하게 만드는 것**.

결제 도메인은 분산 시스템 기법이 "있으면 좋은 것"이 아니라 **없으면 실제로 돈이 틀어지는** 몇 안 되는 영역이다. 멱등성이 없으면 이중 승인이 나고, Outbox가 없으면 D+1 대사에서야 원장 누락이 발견된다. 각 기법이 왜 필요한지는 `product/00-product-definition.md` §7 매핑표에서 시작한다.
