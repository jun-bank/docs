# jun-bank 설계 문서

jun-bank 시스템의 **단일 설계 출처**. 각 서비스 저장소의 README는 "그 서비스를 어떻게 돌리나"만 다루고, **"왜 그렇게 설계했나"는 전부 여기**에 있다.

> ★ **세션 인계·현황의 정본은 `HANDOFF.md`다.** 이 문서는 *무엇이 어디 있나*(지도)를 맡고, `HANDOFF.md`는 *지금 무엇을 하는 중이고 무엇을 되돌리면 안 되나*를 맡는다. 두 문서가 갈리면 **HANDOFF가 이긴다.**

## 문서 규칙

1. **결정은 ADR에만.** 다른 문서에 "~하기로 했다"가 있으면 ADR 링크를 단다. 근거가 두 곳에 있으면 반드시 갈라진다.
2. **미확정은 숨기지 않는다.** 정해지지 않은 것은 문서 안에 `[미확정]`·열린 의문으로 남긴다. **다음 Phase로 추정해서 넘기지 않는다.**
3. **용어는 `domain/glossary.md`가 정본.** 다른 문서에서 용어를 새로 정의하지 않는다.
4. **규칙은 `product/01-business-rules.md`가 정본.** 다른 문서는 `BR-nn`으로 참조만 한다.
5. **순서를 앞지르지 않는다.** 선행 Phase의 산출물이 없으면 그 Phase를 시작하지 않는다.
6. **문서도 버전을 갖는다.** 각 문서 하단에 변경 이력.
7. ★ **"반영 완료"를 적기 전에 본문을 다시 연다.** 이 프로젝트에서 *"고쳤다고 적고 안 고침"* 이 반복 발생한 실측 결함이다(HANDOFF §3).

## 문서 상태 표기

**네 단계만 쓴다.** "초안 v0.1", "골격만", "제안됨" 같은 임의 표현을 섞지 않는다.

| 상태 | 뜻 | 신뢰해도 되나 |
|---|---|---|
| **미착수** | 아직 만들지 않음 | — |
| **작성중** | 쓰는 중. 내용이 바뀔 수 있음 | ❌ 인용 금지 |
| **검토대기** | 다 썼고 확인을 기다림 | △ 참고만 |
| **확정** | 합의됨. 바꾸려면 재합의 필요 | ✅ |

각 문서 상단에 한 줄로 표기한다: `- 상태: 작성중`

## 이 프로젝트의 목표

기법을 써보기 위해 도메인을 고르는 것이 아니라, **도메인이 기법을 요구하게 만드는 것**.

결제 도메인은 분산 시스템 기법이 "있으면 좋은 것"이 아니라 **없으면 실제로 돈이 틀어지는** 몇 안 되는 영역이다. 멱등성이 없으면 이중 승인이 나고, 이벤트 유실 방지가 없으면 정산 대사에서야 원장 누락이 발견된다.

그래서 이 저장소의 1차 산출물은 **동작하는 은행이 아니라 판단의 근거**다. 그리고 **설계 워크플로우 자체가 두 번째 산출물**이며, 그쪽이 더 오래 산다(HANDOFF §1).

## 자주 하는 질문

**Q. `study/`는 설계 문서인가?**
아니다. `study/01~11`은 개인 학습 노트이며 **결정의 근거가 될 수 없다.** 결정은 ADR에만 남긴다.
단 `study/project-workflow/`는 예외로, **문서 작성 순서와 양식의 정본**이다.

**Q. 왜 양식과 내용을 분리하는가?**
특정 프로젝트에 맞춰 미리 써둔 문서는 대부분 읽히지 않고 낡는다. 재사용되는 것은 **양식과 작성법**이다.

**Q. 문서가 코드와 다르면?**
문서를 고친다. 틀린 문서는 없는 문서보다 나쁘다. 고칠 수 없으면 상태를 낮추거나 폐기한다.

**Q. 검산이 통과하면 결함이 없는 것인가?**
아니다. `check_docs.py`가 통과한 상태에서 치명 결함이 나온 적이 있다(HANDOFF §4). 검산은 **과거에 겪은 결함 형태**를 다시 잡아줄 뿐이다.
