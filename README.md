## 읽는 순서

### 처음 온 사람

```
① README.md (이 문서)                    무엇이 어디 있고 지금 어디까지 왔나
② study/project-workflow/README.md        어떤 순서로 만드는가
③ product/00-product-definition.md        이 시스템은 무엇인가
④ domain/glossary.md                      어떤 개념으로 이루어지나
```

### 문서를 쓰려는 사람

```
① study/project-workflow/README.md 에서 현재 Phase 확인
② 그 Phase 폴더의 README.md 로 선행 조건 확인
③ 만들 문서의 *-format.md 를 열고 §3 양식을 복사
④ 정규 위치(product/, domain/ …)에 붙여넣고 채운다
⑤ §6 완료 기준으로 검증
```

## 문서 규칙

1. **결정은 ADR에만.** 다른 문서에 "~하기로 했다"가 있으면 ADR 링크를 단다. 근거가 두 곳에 있으면 반드시 갈라진다.
2. **미확정은 숨기지 않는다.** 정해지지 않은 것은 `> **결정 필요 #n**:` 으로 문서 안에 남긴다. **다음 Phase로 추정해서 넘기지 않는다.**
3. **용어는 `domain/glossary.md`가 정본.** 다른 문서에서 용어를 새로 정의하지 않는다.
4. **규칙은 `product/01-business-rules.md`가 정본.** 다른 문서는 `BR-nn`으로 참조만 한다.
5. **순서를 앞지르지 않는다.** 선행 Phase의 산출물이 없으면 그 Phase를 시작하지 않는다.
6. **문서도 버전을 갖는다.** 각 문서 하단에 변경 이력.

## 문서 상태 표기

**네 단계만 쓴다.** "초안 v0.1", "골격만", "제안됨" 같은 임의 표현을 섞지 않는다.

| 상태 | 뜻 | 신뢰해도 되나 |
|---|---|---|
| **미착수** | 아직 만들지 않음 | — |
| **작성중** | 쓰는 중. 내용이 바뀔 수 있음 | ❌ 인용 금지 |
| **검토대기** | 다 썼고 확인을 기다림 | △ 참고만 |
| **확정** | 합의됨. 바꾸려면 재합의 필요 | ✅ |

각 문서 상단에 한 줄로 표기한다: `- 상태: 작성중`

## 이 프로젝트의 목표

기법을 써보기 위해 도메인을 고르는 것이 아니라, **도메인이 기법을 요구하게 만드는 것**.

결제 도메인은 분산 시스템 기법이 "있으면 좋은 것"이 아니라 **없으면 실제로 돈이 틀어지는** 몇 안 되는 영역이다. 멱등성이 없으면 이중 승인이 나고, 이벤트 유실 방지가 없으면 정산 대사에서야 원장 누락이 발견된다.

그래서 이 저장소의 1차 산출물은 **동작하는 은행이 아니라 판단의 근거**다.

## 자주 하는 질문

**Q. `study/`는 설계 문서인가?**
아니다. `study/01~07`은 개인 학습 노트이며 **결정의 근거가 될 수 없다.** 결정은 ADR에만 남긴다.
단 `study/project-workflow/`는 예외로, **문서 작성 순서와 양식의 정본**이다.

**Q. 왜 양식과 내용을 분리하는가?**
특정 프로젝트에 맞춰 미리 써둔 문서는 대부분 읽히지 않고 낡는다. 재사용되는 것은 **양식과 작성법**이다.

**Q. 문서가 코드와 다르면?**
문서를 고친다. 틀린 문서는 없는 문서보다 나쁘다. 고칠 수 없으면 상태를 낮추거나 폐기한다.
