# 개발 주기 (Development Cycle) — 초안 v0.1

- 작성일: 2026-08-02
- 상태: **초안 — 사용자 검토 대기**
- 근거: `reference/architect-textbook-toc.md` (『아키텍트 첫걸음』 2~4장)

이 문서는 **"무엇을 어떤 순서로 만드는가"**를 정의한다. 책 2~4장의 구조를 jun-bank 맥락으로 번역한 것이며, 각 항목마다 **산출물이 무엇이고 어디에 두는지**를 지정한다.

---

## 0. 전체 흐름

```
 [2장] 설계 기반 정렬        원칙과 어휘를 먼저 맞춘다 (한 번)
      ↓
 [3장] 아키텍처 설계         드라이버 → 선정 → 평가 → 문서화 (한 번, 이후 ADR로 증분)
      ↓
 [4장] 아키텍처 구현         기반 구축 → ★유스케이스 단위 반복★
      ↓                              ↑
      └──────────────────────────────┘
             유스케이스마다 이 루프를 돈다
```

**핵심 구조**: 2장과 3장은 **한 번** 통과하고, 4장의 4.3(유스케이스 중심 구현)이 **반복 단위**가 된다. 애자일 사이클의 한 바퀴 = **유스케이스 1개**다. 스프린트 기간이 아니라 유스케이스가 단위인 이유는, 결제 도메인에서는 "절반만 구현된 승인"이 아무 가치가 없기 때문이다.

### 3.3.4 서비스 분할이 이 프로젝트의 최대 분기점

현재 7개 서비스(user/auth/account/transaction/transfer/card/ledger)는 **명세 없이 기술적 직관으로 나뉜 상태**다. 그 결과:

- `Money`가 6개 서비스에 각각 복붙됨 → 금액 규칙이 6벌
- `transfer-service`에만 Outbox/Saga가 있고 나머지엔 없음 → 신뢰성 전략이 서비스마다 다름
- `card-service` 안에 `card`와 `payment` 두 도메인이 함께 있음 → 경계 근거 불명

책 3.3.4~3.3.5를 근거로 **분할 기준을 먼저 정하고**, 그 기준으로 현재 경계를 평가한 뒤 재분할한다. 결과가 지금과 같아도 좋다 — **근거를 갖는 것**이 목적이다.

### C-2. 유스케이스 반복 (★ 개발 주기의 본체)

**1 사이클 = 유스케이스 1개.** 각 사이클은 아래 7단계를 전부 통과해야 끝난다.

```
① 유스케이스 선정 (4.3.1)
      ↓  선정 기준: 아키텍처 관통도 > 비즈니스 가치 > 난이도
② 기능 명세서 작성 (4.2.2)
      ↓  형식은 conventions 의 표준 명세서 템플릿
③ 설계서 작성 (4.2.3)  — 필요 시 ADR 발행
      ↓
④ 계약 확정 (OpenAPI / 이벤트 스키마)
      ↓  contracts/ 에 먼저 커밋. 구현보다 앞선다
⑤ 구현
      ↓  커밋 단위 = 빌드되는 최소 단위 (파일 단위 커밋 금지)
⑥ 검증  — 단위·통합·시나리오 (5장에서 정교화)
      ↓
⑦ 회고 및 문서 갱신  — 설계와 실제가 갈라진 지점을 문서에 반영
```

**⑦이 빠지면 이 사이클은 그냥 폭포수다.** 구현하며 알게 된 것을 문서로 되돌리는 단계가 애자일의 실질이다.

### 첫 유스케이스 선정 (권고)

책 4.3.1의 기준은 **아키텍처적으로 중요한 유스케이스를 먼저** 구현하는 것이다. jun-bank에서는:

| 후보 | 아키텍처 관통도 | 판단 |
|---|---|---|
| 회원가입 (S1) | 인증·분산 트랜잭션 | 필요하지만 결제 도메인 학습가치 낮음 |
| **결제 승인 (S3)** | **인가·동시성·가용잔액·원장·외부연동·응답 SLA를 전부 통과** | ★ **권고 — walking skeleton** |
| 대사 (S6) | 배치·원장 | 승인이 있어야 대사할 것이 생김 |

> **권고**: 첫 사이클은 **S3 결제 승인**. 단 이를 위해 최소한의 계좌·카드가 필요하므로, 실제로는 `계좌 개설 → 카드 발급 → 결제 승인`을 **하나의 얇은 수직 슬라이스**로 묶는다. 각각을 완성도 높게 만들지 않고, 승인 한 건이 끝까지 흐르는 최소 경로만 뚫는다.
