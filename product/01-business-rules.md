# 2. 식별과 멱등성

## BR-17. 원거래 식별 🔒 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 원거래 식별에는 **두 개의 식별자**가 쓰인다. **① 상관 식별자**는 **매입사가 승인 요청 시점에 생성**해 전문에 실어 보내며, 승인 성립 여부와 무관하게 존재한다. **② 승인번호**는 **승인이 성립할 때 발급사가 발번**한다. **망취소는 ①로만 원거래를 식별**하고, **매입·취소·대사는 ①과 ② 모두**로 식별한다 |
| **분류** | 식별 |
| **근거** | BR-12·BR-16·BR-26·BR-30이 전부 "원승인을 지목한다"는 행위 위에 서 있는데, 지목 수단이 없으면 그 규칙들이 구현·검증 불가능하다. **식별자가 두 개여야 하는 이유**: 승인번호는 우리가 발번하므로 **승인 응답이 유실되거나 망취소가 선도착하면 매입사는 승인번호를 알 수 없다.** 요청자가 만든 상관 식별자가 없으면 BR-22(망취소 선도착)를 구현할 방법이 없다 |
| **수치** | 승인번호 자릿수·상관 식별자 형식 — **미확정** (미확정 수치 표) |
| **설정 키** | `payment.approval-number.format`, `payment.correlation-id.format` |
| **예외** | 없음. **승인 없이 도착한 매입은 BR-27로 격리**되므로 식별 실패가 정상 흐름을 막지 않는다 |
| **적용 범위** | S4, S5, S6, S8, S9 |
| **검증 방법** | ① 승인 → 매입 → 취소 → 대사 전 구간에서 동일 상관 식별자로 원거래를 찾을 수 있는지 ② **승인 응답 유실 상황에서 상관 식별자만으로 망취소가 원거래를 식별하는지** 확인. 식별 실패 0건 |
| **상태** | 확정 |
| **관련** | S4, S5, S6, S8, S9, BR-12, BR-16, BR-22, BR-26, BR-30 |

> **v2.0 재수정**: 최초 v2.0에서는 식별 수단을 `(승인번호, 카드토큰, 승인일시)` 하나로 두었는데, **post-fix 재점검에서 BR-22와 충돌**이 드러났다. 망취소 선도착 시 매입사는 승인번호를 모르므로 tombstone을 후도착 승인과 연결할 수 없다. 요청자가 생성하는 상관 식별자를 분리해 해소했다. 이로써 **OQ3(멱등키를 매입사가 생성하는지)도 함께 닫힌다** — 상관 식별자가 그 역할을 한다.

## BR-02. 멱등 재요청

| 항목 | 내용 |
|---|---|
| **규칙** | 동일한 멱등키의 재요청에 대한 응답은 **최초 처리 결과와 동일**하며, 재처리는 일어나지 않는다. **같은 멱등키로 요청 내용이 다르면 충돌 오류로 거절한다** |
| **분류** | 절차 |
| **근거** | 네트워크 실패 시 요청자는 성공 여부를 알 수 없어 재시도한다. 재처리하면 **이중 승인**이 된다. 한편 키가 같은데 내용이 다르면 키 충돌이거나 호출자 오류이므로, 최초 결과를 돌려주면 **다른 거래의 결과를 반환**하게 된다 |
| **수치** | 보관 기간 **30일** — 근거: **취소·환불이 원거래를 참조할 수 있는 기간(BR-26의 취소 가능 기간)보다 길어야 한다.** 그 기간이 확정되면 재산정한다 |
| **설정 키** | `payment.idempotency.retention` |
| **예외** | 없음. **보상 요청(망취소·취소)에도 동일하게 적용된다** |
| **적용 범위** | 모든 상태 변경 요청. **배치 파일 처리는 BR-23이 담당한다** |
| **검증 방법** | ① 같은 키로 N회 요청 후 최종 상태·응답이 1회 처리와 동일 ② 같은 키 + 다른 payload 요청이 충돌 오류로 거절되는지 확인 |
| **상태** | 확정 |
| **관련** | S4, S5, S9, BR-13, BR-22, BR-23, BR-26 |

## BR-22. 망취소 선도착 🔒 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 원 승인을 찾을 수 없는 망취소는 **취소 예약(tombstone)** 으로 기록된다. 이후 도착한 동일 원승인은 **홀딩을 만들지 않고 즉시 무효 처리**된다 |
| **분류** | 상태전이 |
| **근거** | 망취소가 원 승인보다 먼저 도착하거나, 원 승인이 아직 처리 중일 수 있다. BR-13의 "성립하지 않았다면 변화 없음"으로만 처리하면 **뒤늦게 도착한 승인이 그대로 성립해 취소되었어야 할 홀딩이 되살아난다.** 이것이 S5가 다루려는 두 장군 문제의 가장 어려운 형태다 |
| **수치** | 취소 예약 보관 기간 — **미확정** (미확정 수치 표) |
| **설정 키** | `payment.reversal.tombstone-retention` |
| **예외** | 없음 (확인함) |
| **적용 범위** | S5 |
| **검증 방법** | **망취소 선도착 → 원승인 후도착** 순서를 주입해 홀딩 잔류 0건, 승인 성립 0건 확인 |
| **상태** | 확정 |

# 4. 매입 (청산)

## BR-16. 자동 반영 매입의 조건 🔒

| 항목 | 내용 |
|---|---|
| **규칙** | 자동으로 원장에 반영되는 매입은 아래를 모두 만족하는 매입이다. **① 매칭 가능한 선행 승인을 참조한다 ② 그 승인에 대한 첫 매입이다 ③ 매입액이 승인액을 초과하지 않는다.** 즉 **한 승인에 대한 매입은 한 번만 자동 반영된다** |
| **분류** | 제약 |
| **근거** | 승인 없는 매입은 우리가 판단하지 않은 지급이다. **한 승인에 매입을 한 번만 허용하는 이유**: 매입 파일이 영업일 1회이므로 같은 승인에 대한 복수 매입은 정상 경로가 아니다. 또 복수 매입을 허용하면 잔여 홀딩을 만료까지 유지해야 해 **고객 자금이 최대 7일 묶인다**(BR-18이 즉시 해제하는 이유와 충돌) |
| **수치** | — |
| **설정 키** | — |
| **예외** | 매칭 실패 매입은 **BR-27**로, 두 번째 이후 매입은 **BR-32**로 각각 격리된다 |
| **적용 범위** | S6, S8 |
| **검증 방법** | ① 승인 없는 매입이 BR-27로 격리되는지 ② **같은 승인에 대한 두 번째 매입이 BR-32로 격리되는지** ③ 매입액이 승인액을 초과하는 레코드가 반영되지 않는지 |
| **상태** | 확정 |

# 5. 정산

## BR-21. 정산은 영업일 순액이다 🔒 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 정산은 거래 건별이 아니라 **영업일 단위 순액(net)** 으로 이루어진다. 순액은 **해당 영업일에 반영된 매입액 합계에서, 같은 영업일에 확정된 매입취소·환불액 합계를 뺀 값**이다. 매입 반영(청산) 시점과 정산 지급 시점 사이의 금액은 **매입사 미지급금 계정**으로 유지된다 |
| **분류** | 계산 · 절차 |
| **근거** | 고객 계좌에서만 차감하면 그 돈이 어느 계정으로 갔는지 짝이 없어 **BR-08(차변=대변)을 만족하는 전표를 쓸 수 없다.** 또 청산과 정산을 하나로 취급하면 "고객 기표는 성공했는데 기관 간 정산이 실패한 상태"를 표현할 수 없다. **취소·환불을 차감하는 이유**: 순액은 말 그대로 상계 후 금액이며, 매입만 합산하면 취소가 있는 날 실제 지급액과 어긋난다 |
| **수치** | 정산 주기 = 영업일 1회 (BR-06) |
| **설정 키** | `settlement.net-calculation-at` |
| **예외** | **승인취소는 순액에 영향을 주지 않는다.** 매입되지 않은 거래이므로 애초에 매입 합계에 들어가지 않는다 (BR-26) |
| **적용 범위** | S6, S7, S9 |
| **검증 방법** | ① **매입만 있는 날**: 매입 총액 = 정산 순액 ② **매입 + 매입취소가 있는 날**: (매입 총액 − 취소 총액) = 정산 순액 ③ **매입 + 승인취소가 있는 날**: 승인취소가 순액에 영향을 주지 않는지 ④ 청산 성공 + 정산 미결 상태가 표현·조회 가능한지 ⑤ 미지급금 계정 잔액이 미결 순액과 일치하는지 |
| **상태** | 확정 |
| **관련** | S6, S7, S8, S9, BR-08, BR-26, BR-30 |

> **v2.0 재수정 (post-fix)**: 최초 검증 방법이 "하루치 매입 총액 = 정산 순액"이라 **취소·환불이 있는 날의 순액을 검증하지 못했다.** 순액 산식을 규칙 문장에 명시하고 검증을 3가지 조합으로 나눴다.
