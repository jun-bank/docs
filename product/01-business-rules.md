## BR-04. 가용잔액 기준 승인 🔒

| 항목 | 내용 |
|---|---|
| **규칙** | 승인 판단의 기준은 **가용잔액**이며, 가용잔액은 **계좌잔액에서 홀딩 합계를 뺀 값**이다. **계좌잔액은 계좌가 독립적으로 보유**하며 원장 전표 집계와는 별개다 |
| **분류** | 계산 · 제약 |
| **근거** | 계좌잔액 기준으로만 판단하면 이미 점유된 금액을 다시 승인하게 되어 **동시 결제 시 초과 승인**이 발생한다. **잔액을 원장에서 파생하지 않는 이유**: 파생하면 승인 판단이 원장을 읽어야 해서 원장과 승인이 한 경계에 묶이고, 승인 SLA(QS-01)가 원장 집계 성능에 종속된다 |
| **수치** | — |
| **설정 키** | — |
| **예외** | 없음 (확인함) |
| **적용 범위** | S4 |
| **검증 방법** | 동시 승인 요청 N건 후 **승인된 금액 합계 ≤ 최초 가용잔액** 검산. 초과 승인 0건 |
| **상태** | 확정 |
| **관련** | S4, BR-03, BR-05, BR-18 |

> ★ **`holdTotal`은 합계 필드이며 의식적 예외(③)다** — DC-001. 실시간 승인 경로(QS-01 p99 3초)에서 매번 필요해 저장하지만, 그 대가로 다음 셋을 명시한다:
>
> | | 내용 |
> |---|---|
> | **등식** | `계좌.holdTotal = Σ(그 계좌의 홀딩 점유 중인 승인들의 홀딩액)` — **계좌 RC-1**(대사 불변식)로 등재. 실시간 검증 불가이므로 INV가 아니다 |
> | **트랜잭션 경계** | 승인의 **성립·해제·복원 전부** 계좌·카드와 같은 커밋 (README **E1**) — 망취소·승인취소·만료도 포함한다 |
> | **탐지** | **BR-41 내부 대사에 홀딩 정합 항목을 포함**한다 — 등식이 깨진 계좌를 영업일마다 잡는다 |
>
> **"승인 상태가 막아준다"는 근거가 아니다.** 그렇게 처리했다가 1차 리뷰에서 이중 해제(치명)가 나왔다.

> **v2.0 변경**: 계산식에서 **지급정지액 항을 제거**했다. 지급정지를 만드는 시나리오·액터가 현 범위에 없어 항상 0인 상수가 되기 때문이다(결정 #9). 거래 단위 조사 중단은 BR-28(운영자 보류)이 담당한다.

## BR-05. 결제 한도

| 항목 | 내용 |
|---|---|
| **규칙** | 카드별로 1회 한도와 1일 한도가 있으며, 승인은 두 한도를 모두 만족하는 경우에만 성립한다. **1일 한도의 기준일은 승인일시 기준 달력일이다** |
| **분류** | 제약 |
| **근거** | 도난·부정사용 시 손실 범위를 제한한다. 기준일을 영업일이 아닌 달력일로 두는 이유는, 고객이 체감하는 "오늘"이 영업일이 아니라 달력일이기 때문이다 |
| **수치** | 1회 **100만원** / 1일 **300만원** — 근거: **임시값.** 동시성 테스트에서 경계를 만들 수 있으면 충분 |
| **설정 키** | `card.limit.per-transaction`, `card.limit.daily`, `card.limit.daily-basis`(=CALENDAR_DAY) |
| **예외** | 없음 (확인함) |
| **적용 범위** | S4 |
| **검증 방법** | 한도 경계값(한도−1, 한도, 한도+1) 요청 결과 확인. **마감 시각(23:00) 직후 승인이 같은 달력일 한도에 누적되는지 확인** |
| **상태** | 초안 (수치 미확정) |
| **관련** | S4, BR-04, BR-14, BR-24 |

> ★ **카드 `usage`도 합계 필드이며 의식적 예외(③)다** — DC-001.
>
> | | 내용 |
> |---|---|
> | **등식** | `카드.usage = Σ(그 카드로 그 기준일에 성립해 유효한 승인들의 한도사용액)` — **카드 RC-1**(대사 불변식)로 등재. 실시간 검증 불가이므로 INV가 아니다 |
> | **트랜잭션 경계** | 승인의 성립·해제·복원 **전부** 카드와 같은 커밋 (E1). 복원 조건은 BR-24 |
> | **탐지** | **BR-41 내부 대사에 한도 정합 항목을 포함** |
>
> 복원 책임이 승인 전이(T4·T5·T7·T13)에 흩어져 있어 **이중 복원**이 반복 지적됐다. 등식과 탐지가 그것을 잡는다.
>
> ⚠️ **`limitContribution`이 없으면 등식을 계산할 수 없다.** 정상 매입(`AUTHORIZED → CAPTURED`)과 지연 매입(`EXPIRED → CAPTURED`)은 **최종 상태가 같은데 한도 기여액이 다르다**(전자는 매입액, 후자는 0 — T7이 이미 복원했다). 상태만으로는 구분이 불가능하므로 **승인이 자기 기여액을 직접 든다.**

# 2. 식별과 멱등성

## BR-17. 원거래 식별 🔒 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 원거래 식별에는 **두 개의 식별자**가 쓰인다. **① 상관 식별자**는 **매입사가 승인 요청 시점에 생성**해 전문에 실어 보내며, 승인 성립 여부와 무관하게 존재한다. **② 승인번호**는 **승인이 성립할 때 발급사가 발번**한다. **망취소는 ①로만 원거래를 식별**하고, **매입·취소·대사는 ①과 ② 모두**로 식별한다 |
| **분류** | 식별 |
| **근거** | BR-12·BR-16·BR-26·BR-30이 전부 "원승인을 지목한다"는 행위 위에 서 있는데, 지목 수단이 없으면 그 규칙들이 구현·검증 불가능하다. **식별자가 두 개여야 하는 이유**: 승인번호는 우리가 발번하므로 **승인 응답이 유실되거나 망취소가 선도착하면 매입사는 승인번호를 알 수 없다.** 요청자가 만든 상관 식별자가 없으면 BR-22(망취소 선도착)를 구현할 방법이 없다 |
| **수치** | 승인번호 자릿수·상관 식별자 형식 — **미확정** (미확정 수치 표) |
| **설정 키** | `payment.approval-number.format`, `payment.correlation-id.format` |
| **예외** | 없음. **승인 없이 도착한 매입은 BR-27로 격리**되므로 식별 실패가 정상 흐름을 막지 않는다 |
| **적용 범위** | S4, S5, S6, S8, S9 |
| **검증 방법** | ① 승인 → 매입 → 취소 → 대사 전 구간에서 동일 상관 식별자로 원거래를 찾을 수 있는지 ② **승인 응답 유실 상황에서 상관 식별자만으로 망취소가 원거래를 식별하는지** 확인. 식별 실패 0건 |
| **상태** | 확정 |
| **관련** | S4, S5, S6, S8, S9, BR-12, BR-16, BR-22, BR-26, BR-30 |

> **v2.0 재수정**: 최초 v2.0에서는 식별 수단을 `(승인번호, 카드토큰, 승인일시)` 하나로 두었는데, **post-fix 재점검에서 BR-22와 충돌**이 드러났다. 망취소 선도착 시 매입사는 승인번호를 모르므로 tombstone을 후도착 승인과 연결할 수 없다. 요청자가 생성하는 상관 식별자를 분리해 해소했다. 이로써 **OQ3(멱등키를 매입사가 생성하는지)도 함께 닫힌다** — 상관 식별자가 그 역할을 한다.

## BR-02. 멱등 재요청

| 항목 | 내용 |
|---|---|
| **규칙** | 동일한 멱등키의 재요청에 대한 응답은 **최초 처리 결과와 동일**하며, 재처리는 일어나지 않는다. **같은 멱등키로 요청 내용이 다르면 충돌 오류로 거절한다** |
| **분류** | 절차 |
| **근거** | 네트워크 실패 시 요청자는 성공 여부를 알 수 없어 재시도한다. 재처리하면 **이중 승인**이 된다. 한편 키가 같은데 내용이 다르면 키 충돌이거나 호출자 오류이므로, 최초 결과를 돌려주면 **다른 거래의 결과를 반환**하게 된다 |
| **수치** | 보관 기간 **30일** — 근거: **취소·환불이 원거래를 참조할 수 있는 기간(BR-26의 취소 가능 기간)보다 길어야 한다.** 그 기간이 확정되면 재산정한다 |
| **설정 키** | `payment.idempotency.retention` |
| **예외** | 없음. **보상 요청(망취소·취소)에도 동일하게 적용된다** |
| **적용 범위** | 모든 상태 변경 요청. **배치 파일 처리는 BR-23이 담당한다** |
| **검증 방법** | ① 같은 키로 N회 요청 후 최종 상태·응답이 1회 처리와 동일 ② 같은 키 + 다른 payload 요청이 충돌 오류로 거절되는지 확인 |
| **상태** | 확정 |
| **관련** | S4, S5, S9, BR-13, BR-22, BR-23, BR-26 |

# 3. 망취소

## BR-13. 망취소 멱등 🔒

| 항목 | 내용 |
|---|---|
| **규칙** | 망취소를 1회 받든 여러 번 받든 **최종 상태는 동일**하다. 원 승인이 성립했다면 취소되고, 성립하지 않았다면 상태 변화가 없다 |
| **분류** | 절차 · 상태전이 |
| **근거** | 매입사는 승인 성공 여부를 모르는 상태에서 망취소를 보내며 중복 전송도 가능하다. 멱등하지 않으면 **홀딩이 두 번 해제**된다 |
| **수치** | — |
| **설정 키** | — |
| **예외** | **원 승인을 찾을 수 없는 경우는 BR-22가 담당한다.** 원 승인이 **거절**된 경우는 예외가 아니라 규칙 본문의 *"성립하지 않았다면 상태 변화가 없다"* 에 해당한다 — 오류로 거절하지 않는다 |
| **적용 범위** | S5 |
| **검증 방법** | 응답 유실 주입 후 망취소 N회 전송 → 최종 상태 동일, 홀딩 잔류 0건, 원장 중복 0건. **거절된 승인에 망취소를 보내도 오류가 아니라 무변화**인지 확인 |

## BR-20. 매입 시 잔액 부족 (미수) 🔒 (신설 · **DC-001로 재작성**)

| 항목 | 내용 |
|---|---|
| **규칙** | 매입 반영 시점에 계좌 잔액이 부족하면 **매입은 반영되고 부족분은 미수(미결제)로 적재**된다. 계좌 잔액은 음수가 되지 않는다. **미수는 독립된 채권 단위**로, 어느 승인에서 생겼는지·발생 영업일·회수 진행도·보류 여부를 스스로 보유한다 |
| **분류** | 제약 · 절차 |
| **근거** | 홀딩 해제 후 고객이 그 돈을 다른 결제에 쓰면 매입 시점에 잔액이 없을 수 있다. 매입을 거절할 수 없고(BR-19) 잔액을 음수로 만들 수도 없으므로 **미수 없이는 원장이 닫히지 않는다**. **독립 단위로 두는 이유**: 미수에는 회수 순서(BR-34 FIFO)·보류 제외(BR-28)·회수 진행도가 붙는데, 이것들은 **계좌의 합계 필드에 담을 수 없다**. 계좌 합계로 두고 개별 규칙을 다른 애그리게이트에 흩뿌린 결과가 DC-001의 실패 이력이다 |
| **수치** | — |
| **설정 키** | — |
| **예외** | 없음 (확인함) |
| **적용 범위** | S6, S11 |
| **검증 방법** | 홀딩 만료 → 잔액 소진 → 매입 투입 시나리오에서 ① 계좌 잔액이 음수가 아닌지 ② **미수가 발생 승인·영업일과 함께 적재**되고 운영자 목록에 오르는지 ③ 전표 차변=대변 유지 ④ **같은 계좌에 미수가 둘일 때 각각 독립적으로 회수·보류되는지** |
| **상태** | 확정 |
| **관련** | S6, S11, BR-08, BR-19, BR-28, BR-34, BR-43, BR-45 |

> ★ **미수는 "계좌의 숫자"가 아니라 "채권 한 건"이다.** 계좌가 합계만 들면 *어느 미수를 먼저 갚는가*(FIFO)·*이 미수는 조사 중인가*(보류)·*얼마나 갚았나*(진행도)를 표현할 자리가 없다. 그 셋이 갈 곳을 잃고 승인·계좌·규칙에 흩어진 것이 반복 실패의 원인이었다 (DC-001 §3).
>
> **계좌는 미수 금액을 저장하지 않는다.** 승인 차단(BR-45)에 필요한 것은 *"이 계좌에 미결 미수가 있는가"* 뿐이며, 그것은 존재 여부 조회로 충분하다.

# 5. 정산

## BR-21. 정산은 영업일 순액이다 🔒 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 정산은 거래 건별이 아니라 **영업일 단위 순액(net)** 으로 이루어진다. 순액은 **해당 영업일에 반영된 매입액 합계에서, 같은 영업일에 확정된 매입취소·환불액 합계를 뺀 값**이다. 매입 반영(청산) 시점과 정산 지급 시점 사이의 금액은 **매입사 미지급금 계정**으로 유지된다. **두 합계는 결제 컨텍스트(C3)가 영업일별로 누적해 마감 시 정산(C4)에 전달**하며, 정산은 개별 매입 데이터를 읽지 않는다 |
| **분류** | 계산 · 절차 |
| **근거** | 고객 계좌에서만 차감하면 그 돈이 어느 계정으로 갔는지 짝이 없어 **BR-08(차변=대변)을 만족하는 전표를 쓸 수 없다.** 또 청산과 정산을 하나로 취급하면 "고객 기표는 성공했는데 기관 간 정산이 실패한 상태"를 표현할 수 없다. **취소·환불을 차감하는 이유**: 순액은 말 그대로 상계 후 금액이며, 매입만 합산하면 취소가 있는 날 실제 지급액과 어긋난다 |
| **수치** | 정산 주기 = 영업일 1회 (BR-06) |
| **설정 키** | `settlement.net-calculation-at` |
| **예외** | **승인취소는 순액에 영향을 주지 않는다.** 매입되지 않은 거래이므로 애초에 매입 합계에 들어가지 않는다 (BR-26) |
| **적용 범위** | S6, S7, S9 |
| **검증 방법** | ① **매입만 있는 날**: 매입 총액 = 정산 순액 ② **매입 + 매입취소가 있는 날**: (매입 총액 − 취소 총액) = 정산 순액 ③ **매입 + 승인취소가 있는 날**: 승인취소가 순액에 영향을 주지 않는지 ④ 청산 성공 + 정산 미결 상태가 표현·조회 가능한지 ⑤ 미지급금 계정 잔액이 미결 순액과 일치하는지 |
| **상태** | 확정 |
| **관련** | S6, S7, S8, S9, BR-08, BR-26, BR-30, BR-40 |

> **v2.0 재수정 (post-fix)**: 최초 검증 방법이 "하루치 매입 총액 = 정산 순액"이라 **취소·환불이 있는 날의 순액을 검증하지 못했다.** 순액 산식을 규칙 문장에 명시하고 검증을 3가지 조합으로 나눴다.

## BR-06. 마감과 정산 시각

## BR-28. 운영자 보류 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 운영자는 조사가 필요한 거래를 **보류(freeze)** 상태로 전환할 수 있다. 보류 중인 거래는 **홀딩 만료·자동 정정 대상에서 제외**되고 **매입 레코드도 격리**되며(BR-50), 보류 해제는 운영자만 할 수 있다. **미수의 회수 제외는 미수 자신의 보류**로 표현된다(BR-20 — 미수는 독립 채권이므로 승인과 별개로 보류될 수 있다). **보류가 해제된 시점에 만료 기한이 이미 지났다면 다음 만료 배치에서 즉시 만료 처리**된다 (기한을 연장하지 않는다) |
| **분류** | 상태전이 |
| **근거** | BR-09가 "운영자 확인 대상으로 적재한다"고 하는데, **조사 중 자동 처리를 막는 수단이 없으면 조사 도중 홀딩이 만료되거나 상태가 바뀐다.** 분쟁·차지백은 범위 밖이므로(결정 #6) 그 역할을 최소 형태로 대체한다 |
| **수치** | 보류 최대 기간 — **미확정** (무기한 보류 방지) |
| **설정 키** | `operation.freeze.max-duration` |
| **예외** | 없음 (확인함) |
| **적용 범위** | S11 |
| **검증 방법** | ① 보류 전환 후 만료 배치 실행 → 해당 홀딩 유지 확인 ② **만료 기한이 지난 뒤 보류 해제 → 다음 배치에서 즉시 만료되는지 확인** ③ **보류된 미수가 회수 대상에서 빠지는지** 확인 ④ **승인 보류와 미수 보류가 각각 독립적으로 걸리고 풀리는지** 확인 |
| **상태** | 확정 |
| **관련** | S11, BR-03, BR-09, BR-20, BR-34, BR-50 |

> ★ **미수가 독립 채권이 되면서 보류 대상이 둘로 갈렸다** (DC-001). 승인 보류는 **만료·매입**을 막고, 미수 보류는 **회수**를 막는다. 하나로 묶으면 *"조사 대상은 미수뿐인데 승인의 만료까지 멈추는"* 과잉이 되거나, 반대로 *"승인은 정상인데 그 미수만 조사"* 를 표현할 수 없다.

> **보류는 "시계를 멈추는 것"이 아니라 "자동 처리를 막는 것"이다.** 기한 자체는 계속 흐른다. 보류 기간만큼 기한을 연장하면 시간 계산이 복잡해지고, 조사가 길어질수록 고객 자금이 더 오래 묶인다.

## BR-34. 미수 상계 🔒 (신설 · **DC-001로 재작성**)

| 항목 | 내용 |
|---|---|
| **규칙** | **계좌로 자금이 유입될 때**(입금 · 환불 입금) 그 계좌에 **회수 가능한 미수**가 있으면 미수를 먼저 회수하고, 남은 금액만 계좌 잔액에 반영된다. 회수 대상이 여럿이면 **발생 영업일이 오래된 것부터**(같은 날이면 미수 식별자 순) 채운다. 유입액이 회수 대상보다 적으면 잔액은 증가하지 않는다 |
| **분류** | 계산 · 절차 |
| **근거** | BR-20은 미수를 **적재**하는 것까지만 정했다. **회수 경로가 없으면 미수 계정이 영구히 쌓여 원장이 닫히지 않는다.** 자금 유입 시점이 곧 회수 가능 시점이다. **환불 입금도 포함하는 이유**: 계좌로 들어오는 돈은 출처와 무관하게 채권 회수의 재원이며, 입금과 환불을 다르게 처리하면 규칙이 갈라진다 |
| **수치** | — |
| **설정 키** | — |
| **예외** | ① **보류 중인 미수는 회수 대상이 아니다** (BR-28). 조사 중 자동 회수는 결과를 되돌리기 어렵다 ② **환불 반환액의 회수 대상에서 그 승인 자신의 미수는 제외**한다 — 그 미수는 회수가 아니라 **소멸** 대상이고(BR-43 ①), 소멸이 선행한다 |
| **적용 범위** | S2, S6, S9, S11 |
| **검증 방법** | ① 미수 5만 계좌에 3만 입금 → **미수 2만, 잔액 증가 0** ② 미수 5만에 10만 입금 → **미수 0, 잔액 5만 증가** ③ 환불 입금 10만에 미수 3만 → 미수 0, 잔액 7만 증가 ④ 상계 전표 차변=대변 ⑤ **미수 A(D1 발생, 보류) · B(D3 발생)에 6만 입금 → B만 회수되고 A는 그대로** ⑥ **A(D1) · B(D1) 동점에서 식별자 순으로 결정론적 배분** ⑦ 미수 전액 회수 시 BR-45 차단 자동 해제 |
| **상태** | 확정 |
| **관련** | S2, S6, S11, BR-08, BR-20, BR-28, BR-29, BR-43, BR-45 |

> ★ **"회수 가능한 미수"가 회수액을 정한다.** 계좌 합계에서 먼저 금액을 정하고 나중에 배분하면, **보류분을 뺄 수 없어** 상계액과 배분 합계가 어긋난다. 회수 대상을 먼저 고르고 그 합으로 상계액을 정한다.
>
> **정렬이 전순서여야 한다.** "오래된 순"만으로는 같은 영업일에 발생한 미수들의 순서가 미정이고, 그러면 **어느 미수가 먼저 회수됐는지가 실행마다 달라져** 대사에서 재현할 수 없다. `(발생 영업일, 미수 식별자)`로 못박는다.
>
> **회수는 미수 자신이 한다.** 계좌가 남의 채권 금액을 직접 깎지 않는다 — 그렇게 하면 계좌 합계에서 남의 몫이 깎이는 경로가 다시 열린다 (DC-001 §3).

# 13. 애그리게이트 명세에서 드러난 규칙 (Phase 2-4 반영)

## BR-43. 환불액 산정과 정산 완료 후 환불 🔒 (신설 · **DC-001로 재작성**)

| 항목 | 내용 |
|---|---|
| **규칙** | ① **매입사가 보내는 환불액은 "거래를 얼마로 줄인다"는 뜻**이며 **매입액 기준**이다. 고객에게 반환할 금액은 우리가 계산한다 — `반환액 = max(0, 회수액 − 잔여 채무)`, `잔여 채무 = 매입액 − 누적환불액`, **`회수액 = 매입 시 출금액 + 미수 회수액 − 누적 반환액`**. 회수하지 못한 미수는 잔여 채무가 줄면서 그만큼 **소멸**하며, 소멸은 **미수 자신의 조작**이다 ② **정산이 완료된 건의 환불은 원거래의 순액을 되돌리지 않고**, 매입 파일의 취소 레코드(BR-33)로 접수되어 **다음 영업일 정산의 차감분**으로 반영된다 |
| **분류** | 계산 · 절차 |
| **근거** | ① 카드 부분취소는 **거래 금액을 줄이는 것**이다 — 10만 결제를 4만 취소하면 고객 명세에 6만이 남는다. 반환액을 매입사가 지정하게 두면 **우리가 실제로 회수한 금액과 무관한 값**이 들어와, 미수가 생긴 건에서 받지도 않은 돈을 반환하게 된다. 반대로 상한을 실제 출금액으로 고정하면 **미수를 먼저 갚은 고객이 낸 돈을 못 돌려받는다** ② 정산이 끝났다는 것은 **매입사에 지급 의무가 확정**됐다는 뜻이다. 이미 산출된 순액을 되돌리면 마감된 영업일이 사후에 바뀐다 |
| **수치** | 환불 배치 주기 — **미확정** |
| **설정 키** | `refund.batch.interval` |
| **예외** | 없음 (확인함) |
| **적용 범위** | S6, S7, S9 |
| **검증 방법** | ① 10만 매입·7만 출금·3만 미수 → **4만 환불** → 반환 1만, **미수 소멸**, 잔여 채무 6만 ② 이어서 6만 환불(누계 10만) → 추가 반환 6만(**총 7만 = 실제 출금액**) ③ **고객이 미수 3만을 먼저 입금해 회수된 뒤** 10만 환불 → **반환 10만** ④ 누적환불액이 매입액을 넘는 요청은 격리 ⑤ 정산 완료 건 환불 → **D일 순액 불변**, 다음 영업일에서 차감 ⑥ **미수 소멸 시 계좌 잔액이 변하지 않는지**(소멸은 채권 감소이지 자금 이동이 아니다) |
| **상태** | 확정 |
| **관련** | S6, S7, S9, BR-10, BR-20, BR-21, BR-26, BR-33, BR-34, BR-47, BR-51 |

### 산식과 검산

```
잔여 채무 = 매입액 − 누적환불액
반환액    = max(0, 회수액 − 잔여 채무)      ← 초과 회수분만 돌려준다
회수액   -= 반환액
미수 소멸 = max(0, 기존 미수 − max(0, 잔여 채무 − 회수액))
```

| 시나리오 | 매입 | 회수 | 누적환불 | 잔여 채무 | 반환 | 남은 미수 |
|---|---|---|---|---|---|---|
| 매입 직후 | 10만 | 7만 | 0 | 10만 | — | **3만** |
| 4만 부분 환불 | 〃 | 7 → 6만 | 4만 | 6만 | **1만** | **0** (3만 소멸) |
| 이어서 6만 환불 | 〃 | 6 → 0 | 10만 | 0 | **6만** | 0 |
| 합계 | | | | | **7만 = 실제 출금액** ✅ | |
| **미수를 먼저 갚은 경우** | 10만 | **10만** | 10만 | 0 | **10만** ✅ | 0 |

> ★ **소멸은 미수 애그리게이트의 조작이다.** 계좌 합계에서 금액을 빼는 방식이면 그 사이 다른 경로로 이미 회수된 경우 **남의 채권이 깎인다** — DC-001이 없앤 바로 그 구조다. 미수가 자기 상태를 바꾸고, 계좌는 관여하지 않는다.
>
> ⚠️ **누적환불액의 상한은 매입액이지 출금액이 아니다.** 출금액은 반환액을 제한하는 것이 아니라 **산식에서 자연히 나온다.**
>
> ⚠️ **누적 반환액의 상한도 출금액이 아니다.** 고객이 미수를 갚았으면 **출금액보다 많이 낸 것**이므로 그만큼 더 돌려받아야 한다 — 상한은 `매입 시 출금액 + 미수 회수액`이다. 출금액으로 고정하면 **이 규칙이 기각한 모델로 되돌아간다.**
>
> ⚠️ **②의 "되돌리지 않는다"는 순액에 대한 것이다.** 원거래의 누적환불액 추적까지 막으면 **같은 원거래에 취소 레코드가 두 번 와도 각각만 검사해 상한을 우회**한다. 누계를 어디가 소유하는지는 **DC-002**에서 정한다.

> **정산 완료 건의 환불이 순액을 음수로 만들 수 있다.** 환불이 그날 매입보다 많으면 **매입사가 우리에게 지급**하는 방향이 된다. 정상이며 BR-21이 이미 허용한다.

## BR-48. 불일치의 재발견 추적 🔒 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 같은 `(유형, 범위, 대상)`의 불일치는 **하나만** 유지한다. 또 발견되면 새 건을 만들지 않고 **최근 발견일과 발견 횟수를 갱신**한다. 이때 상태가 `처리완료`였다면 **`미처리`로 되돌린다**. **발견 횟수는 영업일당 최대 1회 증가**한다 — 같은 영업일에 몇 번 탐지되든 한 번만 센다 |
| **분류** | 절차 |
| **근거** | 상류를 고치지 않으면 같은 불일치가 매 대사마다 다시 잡힌다. **영업일당 1회로 제한하는 이유**: 매입 배치의 격리가 즉시 적재하고(BR-51) 대사가 같은 건을 또 탐지하므로 하루에 2회 이상 오를 수 있다. 그러면 지표가 *"며칠째 미해결인가"* 가 아니라 *"배치를 몇 번 돌렸나"* 가 되고, **배치 재실행이 멱등하지 않게 된다**. 매번 새 건으로 쌓으면 목록이 노이즈가 되고, 반대로 처리완료 건을 아예 제외하면 **"처리했다고 기록했지만 실제로는 안 고쳐진 것"을 영원히 볼 수 없다** — 운영자가 잘못 판단한 순간 그 사실이 은폐된다. 이는 BR-09(자동 정정 금지 = 사람이 실제로 판단하게 한다)의 취지에 정면으로 어긋난다 |
| **수치** | — |
| **설정 키** | — |
| **예외** | 없음 (확인함) |
| **적용 범위** | S8 |
| **검증 방법** | ① 같은 불일치를 3영업일 연속 발생시킴 → **건이 1개이고 발견 횟수 = 3** ② 2일차에 `처리완료` 처리 후 3일차 대사 → **상태가 `미처리`로 복귀**하고 발견 횟수 증가 ③ **같은 영업일에 대사를 3번 재실행 → 발견 횟수는 1만 증가**(멱등) ④ 같은 날 매입 격리 적재 + 대사 탐지 → **횟수 1** |
| **상태** | 확정 |
| **관련** | BR-09, BR-30, BR-41, BR-42 |

> **영업일당 1회이므로 `발견 횟수 ≈ 미해결 영업일 수`가 된다.** 최초 발견일과 함께 보면 *"며칠째, 그중 몇 번 잡혔나"* 가 드러난다.
>
> **최초 발견일이 남으므로 "며칠째 미해결인가"가 자연히 드러난다.** 오래 지속되는 불일치가 목록에서 눈에 띄고, 이것이 운영자의 우선순위 근거가 된다.

## BR-49. 만료 후 취소는 채무를 소멸시킨다 🔒 (신설)

| **설정 키** | — |
| **예외** | **한도 사용액을 다시 복원하지 않는다.** 만료 시점에 이미 복원됐으므로(BR-24) 취소 시 또 복원하면 **이중 복원**이 된다 |
| **적용 범위** | S5, S9, S10 |

## BR-50. 보류 중인 승인의 매입 격리 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 보류(`frozen = true`) 중인 승인에 대한 매입 레코드는 **반영하지 않고 격리**한다. 보류가 해제되면 **별도 재처리 배치**가 반영한 뒤 그 레코드를 원 배치에서 **격리 → 처리로 승격**시킨다. 원 배치는 `완료됨` 상태 그대로 두고 다시 열지 않는다. 격리되어 있는 동안 이 건은 대사에서 **M1(미매입)으로 적재하지 않는다** |

| **수치** | — |
| **설정 키** | — |

> **승격이 이 규칙의 멱등 장치다.** *격리 목록에 있다 = 아직 안 반영됨*, *처리 집합에 있다 = 반영됨*이므로, 재처리 배치는 **격리 목록에 있을 때만** 반영하고 성공 즉시 승격시킨다. 두 번 지시하거나 매입사가 파일을 재전송해도 두 번째는 격리 목록에 없어 걸러진다. 합계가 바뀌지 않으므로 완료 판정(BR-23·INV-3)도 그대로 성립한다.

> **격리를 "실패"로 세지 않는다.** 매입 배치의 완료 판정(`처리 + 격리 = 전체`)에서 보류 격리는 **격리 쪽으로 계상**된다. 그러지 않으면 보류 건 하나가 배치 전체를 미완료로 만든다.

## BR-51. 무효 승인에 대한 매입의 격리 🔒 (신설)

| 항목 | 내용 |
|---|---|
| **규칙** | 매입 레코드의 원승인을 **찾았으나 유효한 상태가 아니면**(거절 `DECLINED` · 무효 `VOIDED` · 환불완료 `REFUNDED`) 반영하지 않고 격리하여 **M8 무효 승인 매입**으로 적재한다. **무효가 된 경로는 구분하지 않는다** — 망취소·승인취소·만료 후 취소(BR-49) 전부 M8이다 |
| **분류** | 절차 |
| **근거** | BR-27(M2)은 *"승인 레코드를 못 찾았다"* 를 다루는데, **"찾았는데 유효하지 않다"는 원인도 조치도 다르다.** M2는 매입사 오발송이나 우리 쪽 유실을 의심하지만, M8은 **매입사가 우리 거절·취소 응답을 받지 못했을 가능성**이 높다 — 즉 **응답 유실이라는 확인 가능한 원인**이 있고, 조치는 해당 전문 로그 대조다. 한 유형으로 뭉치면 운영자가 매번 상태를 다시 조회해 원인을 나눠야 한다 |
| **수치** | — |
| **설정 키** | — |
| **예외** | 없음 (확인함) |
| **적용 범위** | S6, S8 |
| **검증 방법** | ① 거절된 승인의 매입 레코드 투입 → **계좌 잔액 불변**, M8로 격리되는지 확인 ② 망취소된 승인의 매입 레코드 투입 → 동일 확인 ③ **승인 레코드가 아예 없는 매입은 여전히 M2**로 분류되는지 확인(M8로 흡수되지 않을 것) |
| **상태** | 확정 |
| **관련** | S6, S8, BR-09, BR-13, BR-16, BR-27, BR-32, BR-49 |

> **M2·M7·M8은 "매입을 반영하지 않는 세 가지 이유"다.** M2는 승인이 없다 · M7은 이미 매입했다 · M8은 승인이 유효하지 않다. 셋 다 **격리가 자동 방어선**이며, 격리가 없으면 승인하지 않은 출금이 그대로 나간다.
