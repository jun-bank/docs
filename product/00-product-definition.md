# jun-bank 제품 정의서 (초안 v0.1)

- 작성일: 2026-08-02
- 상태: **초안 — 사용자 검토 대기**
- 이 문서의 역할: 이후 모든 문서(용어사전 → 이벤트 스토밍 → 컨텍스트 맵 → SAD → ADR → 백로그)의 **기준점**. 여기서 정해지지 않은 것은 아래 계층에서 임의로 정하지 않는다.

---

## 1. 한 줄 정의

> **jun-bank는 고객에게 계좌와 카드를 발급하고, 그 카드로 발생한 결제를 승인·정산·기록하는 리테일 은행이다.**

핵심 문장의 방점은 **"발급하고"** 와 **"승인·정산"** 에 있다. 결제 요청을 만드는 쪽(가맹점·PG)이 아니라, **결제 요청을 받아 판단하고 돈을 움직이는 쪽**이다.

---

## 2. 포지션 — 결제 생태계에서 어디에 서 있는가

```
 [고객]                                                    [가맹점]
    │ 카드 소지                                                │ 카드 제시
    │                                                          ▼
    │                                                    [매입사/VAN]  ← 모의 서비스로 구축
    │                                                          │
    │                                          ① 승인요청(실시간, 인바운드)
    │                                                          │
    ▼                                                          ▼
 ┌──────────────────────────────────────────────────────────────────┐
 │                      jun-bank (발급사 = 우리)                      │
 │                                                                  │
 │   계좌 · 카드 발급   │   승인 판단(한도/잔액)   │   원장 기록      │
 └──────────────────────────────────────────────────────────────────┘
    ▲                                                          ▲
    │                                          ② 매입/정산 파일 (D+1~D+2, 배치)
    │                                                          │
    └──────────────── ③ 대사(reconciliation) ───────────────────┘
```

**이 포지션을 고른 이유** (load-bearing 가정 — 뒤집히면 문서 전체가 바뀜):

1. 기존 저장소가 `account` / `transaction` / `transfer` 로 이미 은행 코어다. 발급사로 두면 이 셋이 **결제의 자금원·정산 대상**으로 자연 편입된다. 버려지는 서비스가 없다.
2. 승인이 **인바운드**여야 타임아웃·상태불명·망취소가 *우리가 처리해야 할 문제*가 된다. 아웃바운드(PG 포지션)면 그건 상대방 문제가 된다.
3. 정산 파일을 **받는** 입장이어야 배치·대사가 필연이 된다.

> **결정 필요 #1**: 이 포지션(발급사)에 동의하는가? 대안은 "jun-bank = PG/매입사" 이며, 그 경우 가맹점 정산이 핵심이 되고 계좌·이체 서비스의 비중이 줄어든다.

## 3. 범위

### 3.1 범위 안 (In Scope)

| 영역 | 내용 |
|---|---|
| 고객·인증 | 회원가입, 로그인, 세션·토큰, 로그인 이력 |
| 계좌 | 개설, 조회, 입출금, 계좌 간 이체 |
| 카드 | 발급, 정지/해지, 재발급, 한도 관리 |
| **결제 승인** | 인바운드 승인 요청 처리, 한도·잔액 검증, 승인/거절 응답, **홀딩(한도 점유)** |
| **결제 정정** | 승인취소, 부분취소, 환불, **망취소(reversal)** |
| **매입·정산** | 매입 파일 수신, 원장 확정 반영, D+n 정산, **대사(reconciliation)** |
| **원장** | 복식부기 기반 거래 기록, 잔액 파생, 감사 로그 |
| 모의 외부 | 매입사/VAN 시뮬레이터 (지연·타임아웃·중복응답 주입 가능) |

### 3.2 범위 밖 (Out of Scope)

- 실제 카드 브랜드망 연동, 실제 ISO 8583 전문 규격 준수 (**개념만 차용**)
- 신용평가·여신 심사 모델, 연체·추심
- 모바일/웹 프론트엔드 (API까지)
- PCI-DSS 실제 준수, 실제 PAN 저장 (**토큰화 개념만 구현**)
- 해외결제·환전·다통화 (**단, 통화 필드는 처음부터 모델에 둔다**)

> **결정 필요 #2**: 카드 종류를 **체크카드만**으로 시작할지, **신용카드**까지 갈지. 체크카드는 "승인 즉시 계좌 출금"이라 단순하고, 신용카드는 여신·청구·결제일이 붙어 원장이 훨씬 깊어진다. 권고는 **체크카드로 시작 → 신용카드를 후속 에픽**.

## 4. 액터

| 액터 | 설명 | 주요 관심사 |
|---|---|---|
| **고객(카드소지자)** | jun-bank 계좌·카드 보유자 | 잔액이 맞는가, 결제가 되는가, 취소가 반영되는가 |
| **가맹점** | 카드를 받는 상점 (우리와 직접 계약 없음) | 승인이 떨어지는가 |
| **매입사/VAN** | 가맹점의 승인 요청을 우리에게 중계, 매입 파일 송부 | 응답이 시간 내 오는가, 정산이 맞는가 |
| **운영자** | jun-bank 내부 운영 | 대사 불일치, 실패 거래, 배치 상태 |
| **정산 배치** | 사람이 아닌 액터 — 마감 시각에 기동 | 파일이 전부 처리됐는가, 원장이 균형인가 |

## 5. 핵심 시나리오

각 시나리오 뒤의 `[ ]` 는 **이 시나리오가 어떤 분산처리 문제를 불러오는지** 표시한다.

### S1. 회원가입 및 계좌 개설
고객이 가입하고 계좌를 개설한다. 인증 정보와 프로필이 분리 저장된다.
`[분산 트랜잭션 / 정합성 소유자 정의]`

### S2. 카드 발급
계좌에 연결된 체크카드를 발급받는다. 카드번호는 토큰화되어 저장된다.
`[민감정보 분리 / 계좌-카드 참조 무결성]`

### S3. 결제 승인 (핵심)
가맹점에서 결제 → 매입사가 승인 요청 → jun-bank가 한도·잔액 검증 후 승인/거절 → **승인 시 홀딩 생성**(실제 출금 아님).
`[동시성 제어 / 응답시간 SLA / 가용잔액 vs 원장잔액]`

### S4. 승인 타임아웃과 망취소 (핵심)
jun-bank가 승인 처리 중 응답이 매입사에 도달하지 못함. 매입사는 **성공인지 실패인지 모른다**. 매입사가 망취소 전문을 보내고, jun-bank는 해당 승인을 **강제 정정**한다.
`[두 장군 문제 / 멱등성 / 상태불명 처리 — 결제 도메인의 심장]`

### S5. 매입 및 정산
D+1에 매입사가 매입 파일 송부 → jun-bank가 파일을 읽어 승인건을 **확정 거래로 전환** → 계좌에서 실제 출금 → 원장 기록.
`[배치 / 대용량 파일 처리 / 부분 실패와 재처리]`

### S6. 대사 (핵심)
우리 원장과 매입사 정산 내역을 대조한다. **불일치 유형**: 우리엔 있는데 파일엔 없음(미매입), 파일엔 있는데 우리엔 없음(미승인 매입), 금액 상이.
`[배치 / 이벤트 유실 탐지 / Outbox가 필요한 진짜 이유]`

### S7. 취소·환불
- **승인취소**: 매입 전. 홀딩 해제.
- **매입취소/환불**: 매입 후. 역분개 전표 생성, 자금 반환.
- **부분취소**: 원거래의 일부 금액만.
`[보상 트랜잭션 / 원거래 참조 무결성 / 금액 정합성]`

### S8. 조회
고객이 거래 내역과 잔액을 조회한다. **승인만 된 건은 "결제 예정"으로, 매입된 건은 "결제 완료"로 다르게 보인다.**
`[읽기 모델 / 두 개의 잔액을 사용자에게 설명하는 문제]`

## 6. 비즈니스 규칙 (초안 — 확정 필요)

| # | 규칙 | 상태 |
|---|---|---|
| BR-01 | 승인 응답은 **5초 이내**. 초과 시 매입사는 타임아웃으로 간주한다 | 초안 |
| BR-02 | 동일 `승인요청 멱등키`로 재요청이 오면 **최초 결과를 그대로 반환**한다 (재처리 금지) | 초안 |
| BR-03 | 홀딩은 승인 후 **7일** 내 매입되지 않으면 자동 해제된다 | 초안 |
| BR-04 | 체크카드 승인은 **가용잔액**(원장잔액 − 홀딩합계) 범위 내에서만 가능하다 | 초안 |
| BR-05 | 1일 결제 한도 / 1회 결제 한도를 카드별로 둔다 | 금액 미정 |
| BR-06 | 매입 파일 마감(cutoff)은 **매일 23:00**, 정산 반영은 **D+1 09:00** | 초안 |
| BR-07 | 모든 금액은 **원(KRW), 정수 최소단위**로 다룬다. 부동소수 금지 | 확정 권고 |
| BR-08 | 원장의 모든 전표는 **차변 합계 = 대변 합계**여야 한다 (불변식) | 확정 권고 |
| BR-09 | 대사 불일치는 자동 정정하지 않는다. **운영자 확인 대상으로 적재**한다 | 초안 |

> **결정 필요 #3**: BR-01/03/05/06의 구체 수치. 학습 목적상 **짧게** 잡는 편이 좋다(예: 홀딩 만료 7일 → 테스트에선 분 단위로 축약 가능하게 설정화).

## 7. 학습 목표와의 매핑

이 프로젝트의 목표는 "분산처리 기법을 써보는 것"이 아니라 **"도메인이 그 기법을 요구하게 만드는 것"** 이다. 각 기법은 아래 시나리오에서 **없으면 돈이 틀어지는** 형태로 등장한다.

| 기법 | 요구하는 시나리오 | 없으면 벌어지는 일 |
|---|---|---|
| 멱등성 | S4 | 재시도가 **이중 승인** → 고객 돈이 두 번 빠짐 |
| 망취소 처리 | S4 | 상태불명 승인이 홀딩으로 영구 잔류 → 가용잔액 잠김 |
| 보상 트랜잭션(Saga) | S1, S7 | 고아 데이터, 취소했는데 돈이 안 돌아옴 |
| Outbox | S5, S6 | 이벤트 유실 → 원장 누락 → **D+1 대사에서야 발견** |
| 배치 | S5, S6 | 정산 파일이 본질적으로 일단위 파일 → 실시간 불가 |
| 동시성 제어 | S3 | 동시 결제로 한도 초과 승인 |
| 캐시/동기화 | S3, S8 | 가용잔액 계산이 승인 SLA를 못 맞춤 |
