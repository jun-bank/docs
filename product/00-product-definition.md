## 1. 한 줄 정의

> **jun-bank는 고객에게 계좌와 체크카드를 발급하고, 그 카드로 발생한 결제를 승인·매입·정산하며 그 결과를 원장에 기록하는 카드 발급사(은행)다.**

가장 중요한 단어는 **"발급"** 과 **"승인"** 이다.

- **발급사**이므로 우리는 결제 요청을 **받는** 쪽이다. 만드는 쪽(가맹점·PG)이 아니다.
- **승인**은 "돈을 옮기는 것"이 아니라 "지불 능력을 확인하고 금액을 점유하는 것"이다. 이 구분이 시스템 전체 구조를 규정한다.

## 2. 포지션 — 결제 생태계에서 어디에 서 있는가

```
 [카드소지자]                                        [가맹점]
      │ 카드 소지                                        │ 카드 제시
      │                                                  ▼
      │                                          [매입사 / VAN]   ← 모의 서비스로 구축
      │                                                  │
      │                              ① 승인 요청 (실시간, 인바운드)
      │                                                  ▼
      ▼                        ┌───────────────────────────────────┐
 계좌 개설 · 카드 발급 ────────▶│      jun-bank  (발급사 = 우리)      │
 결제 내역 조회        ◀────────│  계좌 · 카드 · 승인 판단 · 원장     │
      ▲                        └───────────────────────────────────┘
      │                             ▲          │
 [모의 외부 입금원]                  │          │ 승인/거절 응답
   타행 이체 입금                    │          ▼
                        ② 매입(청산) 파일 ─ 거래 확정 · 고객 계좌 기표
                                     │
                        ③ 정산 ─ 발급사 → 매입사 **순액(net)** 지급
                                     │
                        ④ 대사 ─ 승인·홀딩 ↔ 매입 레코드 ↔ 원장 전표 **3자 비교**
```

**이 포지션을 고른 이유**

1. 승인이 **인바운드**여야 타임아웃·상태불명·망취소가 *우리가 처리해야 할 문제*가 된다.
2. 정산 파일을 **받는** 입장이어야 배치와 대사가 필연이 된다.
3. 기존 계좌·거래 자산이 결제의 **자금원·정산 대상**으로 자연 편입된다.

**이 포지션이 확정하는 경계**

- **가맹점은 우리 고객이 아니다.** 가맹점 계약·가맹점 정산·가맹점 수수료 = 범위 밖
- 우리가 보는 것은 **"매입사가 보내온 승인 요청"까지**다
- **모의 매입사/VAN이 카드망 역할까지 겸한다.** 실제로는 VAN(전문 중계)·매입사(가맹점 계약·매입)·브랜드사(카드망)가 별개 주체지만, 본 프로젝트에서는 **하나의 외부 시스템으로 축약**한다

> ✅ **확정 (2026-08-03)** — 검토한 대안: ① 발급사+매입사 겸업 ② PG/매입사
> **①을 택하지 않은 이유**: 매입사를 겸하면 승인 요청이 내부 호출이 되어 타임아웃·상태불명·망취소가 우리 문제가 아니게 된다.
> **②를 택하지 않은 이유**: 정산 파일을 받는 입장이 아니게 되어 배치·대사의 필연성이 약해진다.

### 2.1 승인 모델 — dual-message 채택

> ✅ **확정 (2026-08-03)**: 본 프로젝트의 체크카드는 **승인·매입 분리(dual-message)** 방식을 쓴다.
> 승인 시점에는 **금액을 점유(홀딩)만** 하고, 실제 계좌 출금은 **매입(청산) 시점**에 일어난다.

**왜 이 결정을 기록하는가**: §2의 포지션에는 선택 근거를 남겼는데 승인 모델에는 근거가 없으면, **"체크카드인데 왜 승인 시 바로 안 빠지지?"** 라는 질문에 문서가 답하지 못한다.

**근거**: 승인–홀딩–매입 분리가 있어야 **홀딩 만료 · 부분 매입 · 가용잔액과 계좌잔액의 이중성 · 대사**가 성립한다. 이 넷이 §7 학습 목표의 핵심이다. 승인 즉시 출금(single-message) 방식을 택하면 넷이 전부 사라진다.

**대가**: 고객 화면에서 "결제 예정"과 "결제 완료"를 구분해 보여줘야 한다(S12).

### 2.2 청산(clearing)과 정산(settlement)은 다른 단계다

| | 청산 (Clearing) | 정산 (Settlement) |
|---|---|---|
| 무엇 | 거래 내역을 확정해 **고객 계좌에 기표** | 발급사 → 매입사로 **자금 이동 의무 확정** |
| 단위 | **거래 건별** | **영업일 단위 순액(net)** |
| 실패 시 | 해당 건만 불일치 | 그날 전체 정산이 미결 |
| 시나리오 | S6 | S7 |

> 이 구분이 없으면 **"고객 기표는 성공했는데 기관 간 정산이 실패한 상태"** 를 표현할 수 없고, 대사(S8)의 비교 단위도 잘못 잡는다.

## 3. 범위

### 3.1 범위 안 (In Scope)

| 영역 | 내용 |
|---|---|
| 고객·인증 | 회원가입, 로그인, 세션·토큰 |
| 계좌 | 개설, 조회 |
| **입금** | **모의 외부 입금원(타행 이체)으로부터의 입금.** 결제 재원 확보 목적 |
| 카드 | **체크카드** 발급, 정지/해지, 한도 관리 |
| **결제 승인** | 인바운드 승인 요청 처리, 카드 유효성·한도·가용잔액 검증, **홀딩과 승인의 원자적 확정**, 승인번호 발번, 승인/거절 응답 |
| **결제 정정** | 승인취소, 부분취소, 환불, **망취소(Reversal)** — 선도착·중복 포함 |
| **매입(청산)** | 매입 파일 수신, 거래 확정, 고객 계좌 기표, **홀딩 정리**(전액·부분) |
| **정산** | 영업일 단위 **순액** 산출 및 지급 의무 기표 |
| **대사** | **외부 대사**(승인·홀딩 ↔ 매입 레코드 ↔ 원장 전표 3자) + **내부 대사**(계좌잔액 ↔ 원장 계정 잔액), 불일치 분류·적재 |
| **운영자 보류** | 조사가 필요한 거래를 **보류(freeze)** 로 전환해 자동 처리에서 제외 |
| **미수 처리** | 매입 시 잔액이 부족한 건을 미수로 적재하고 운영자에게 올림 |
| **원장** | 복식부기 기록, 잔액 파생, append-only, 감사 로그 |
| 모의 외부 | 매입사/VAN 시뮬레이터 — **지연·타임아웃·중복응답·순서 역전을 의도적으로 주입 가능** |

### 3.2 범위 밖 (Out of Scope)

| 제외 항목 | 왜 안 하는가 |
|---|---|
| **신용카드** (여신·청구·결제일·연체) | 분산처리 학습 목표는 체크카드로 전부 커버된다. 신용카드가 더하는 것은 회계 복잡도이지 분산 문제가 아니다 → **후속 단계** |
| **계좌 간 이체** | 이체가 보여주는 Saga·보상은 결제 승인이 이미 같은 것을 보여준다 → **후속 단계** |
| **분쟁·차지백** | 실제 분쟁은 매입 완료 후 제기되는 별도 프로세스이며 매입사와의 분쟁 전문 교환이 필요하다. **조사 중 자동 처리를 막는 기능만 운영자 보류로 대체**한다 |
| **강제매입(force capture)·오프라인 승인** | 승인 없이 자금을 지급하는 경로는 만들지 않는다. 다만 **파일에 들어올 수는 있으며, 반영하지 않고 "미승인 매입" 불일치로 격리**한다 (BR-27) |
| **지급정지·계좌 정지** | 이를 만드는 시나리오·액터가 현 범위에 없어 구현하면 항상 0인 상수가 된다. 거래 단위 조사 중단은 **운영자 보류**가 대체한다 |
| **FDS·이상거래 탐지** | 승인 판단은 **규칙 기반 검증(카드 상태·한도·잔액)까지만**. 스코어링·룰엔진·이상패턴 학습은 밖 |
| 출금 (ATM·현금) | 결제 흐름 검증에 불필요 |
| 가맹점 관리·정산·수수료·**인터체인지** | 발급사 포지션이므로 우리 소관이 아님. 정산 금액은 **매입 총액 순액**으로만 다루고 수수료 배분은 하지 않는다 |
| 실제 카드 브랜드망 연동, ISO 8583 실규격 | 실 연동 불가. **개념만 차용** |
| 신용평가·여신 심사·추심 | 신용카드가 범위 밖이므로 함께 제외 |
| 모바일/웹 프론트엔드 | API까지가 범위 |
| PCI-DSS 실 준수, 실제 PAN 저장 | 실 인증 대상 아님. **토큰화 개념만 구현** |
| 해외결제·환전·다통화 | 단, **통화 필드는 처음부터 모델에 둔다** |

> ⚠️ **"후속 단계"와 "안 함"은 다르다.** 신용카드·계좌이체는 **나중에 할 것**이고, 나머지는 **하지 않을 것**이다.

| **정산 배치** | **시스템(비인간)** | 영업일 순액 산출·기표 | 순액이 개별 거래 합과 맞는가 |
| **대사 배치** | **시스템(비인간)** | 3자 비교, 불일치 적재 | 원장이 균형인가 |
| **만료 처리 배치** | **시스템(비인간)** | 기한이 지난 홀딩을 해제 | 잔류 홀딩이 없는가 |

## 5. 핵심 시나리오

각 시나리오 뒤의 `[ ]` 는 **이 시나리오가 불러오는 기술적 문제**다.

### S1. 회원가입 · 계좌 개설
고객이 가입하고 계좌를 개설한다. 인증 정보와 프로필이 분리 저장된다.
`[분산 트랜잭션 / 정합성 소유자 정의]`

### S2. 입금
모의 외부 입금원이 타행 이체 입금을 보낸다. 계좌 잔액이 증가하고 원장에 전표가 기록된다.
`[외부 이벤트 멱등성 / 복식부기 상대 계정]`

### S3. 카드 발급
계좌에 연결된 체크카드를 발급받는다. 카드번호는 토큰화되어 저장된다.
`[민감정보 분리 / 계좌-카드 참조 무결성]`

### S4. 결제 승인 ★
가맹점 결제 → 매입사가 승인 요청 →
**① 카드 유효성·한도·가용잔액 검증 → ② 승인 상태와 홀딩을 원자적으로 확정 → ③ 승인번호 발번 → ④ 응답 전송**

> ⚠️ **순서가 규칙이다.** 응답을 먼저 보내고 홀딩을 만들면, 홀딩 생성이 실패했을 때 매입사는 정상 승인으로 알고 우리 가용잔액은 줄지 않아 **초과 승인**이 난다.

`[동시성 제어 / 응답시간 SLA / 가용잔액 vs 계좌잔액 / 원자적 확정]`

### S5. 승인 타임아웃과 망취소 ★
승인 응답이 매입사에 도달하지 못한다. 매입사는 **성공인지 실패인지 모른다.** 망취소 전문을 보내며, 이 전문은 **중복 전송되거나 원 승인보다 먼저 도착할 수 있다.**
`[두 장군 문제 / 멱등성 / 순서 역전 / 상태불명 처리 — 결제 도메인의 심장]`

### S6. 매입 (청산)
매입사가 매입 파일을 보낸다. 파일을 읽어 승인건을 **확정 거래로 전환**하고, 고객 계좌에서 실제 출금하며 원장에 기표한다. 전액 매입이면 홀딩을 제거하고, 부분 매입이면 잔여 홀딩을 정리한다.
`[배치 / 대용량 파일 / 부분 실패와 재처리 / 파일 멱등성]`

### S7. 정산
영업일 단위로 매입사에 지급할 **순액(net)** 을 산출하고 지급 의무를 기표한다. 청산(S6)이 건별인 것과 달리 정산은 **하루치 합산**이다.
`[집계 정합성 / 청산-정산 상태 분리 / 부분 실패 시 재산출]`

### S8. 대사 ★
**승인·홀딩 저장소 ↔ 매입 레코드 ↔ 원장 전표**를 3자 비교한다.

> ⚠️ 원장만 비교하면 안 된다. **매입 전 승인은 원장에 확정 거래가 없으므로**(S9 참조) 미매입을 찾을 수 없다.

`[배치 / 이벤트 유실 탐지 / Outbox가 필요한 진짜 이유]`

### S9. 취소·환불
- **승인취소**: 매입 전. 홀딩 해제. **원장에 확정 거래가 없으므로 역분개도 없다**
- **매입취소/환불**: 매입 후. 역분개 전표 생성, 자금 반환
- **부분취소**: 원거래의 일부 금액만. 누적 취소액이 원거래를 넘을 수 없다

`[보상 트랜잭션 / 원거래 참조 무결성 / 취소-매입 경합]`

### S10. 홀딩 만료
승인 후 기한 내 매입되지 않은 홀딩을 배치가 자동 해제한다.

> ⚠️ **만료는 자금 점유 해제일 뿐 승인 채무를 소멸시키지 않는다.** 만료 이후에도 매입이 도착할 수 있다(지연 매입).

`[시간 기반 전이 / 배치 / 만료 후 도착 처리]`

### S11. 운영자 보류·불일치 처리
운영자가 대사 불일치·미수 거래를 조사하기 위해 **보류(freeze)** 상태로 전환한다. 보류 중인 거래는 만료·자동 정정 대상에서 제외된다.
`[자동 처리 예외 경로 / 상태 우선순위]`

### S12. 조회
고객이 거래 내역과 잔액을 조회한다. **승인만 된 건은 "결제 예정", 매입된 건은 "결제 완료"로 다르게 보인다.**
`[읽기 모델 / 두 개의 잔액을 사용자에게 설명하는 문제]`

## 7. 학습 목표와의 매핑

이 프로젝트의 1차 산출물은 **동작하는 은행이 아니라 이해**다. "더 단순한 방법이 있는데 왜 어렵게 하는가"의 답이 **"그것이 학습 대상이기 때문"** 인 경우를 허용하되, **결정 기록에 그렇게 명시**한다(§2.1이 그 예다).

| 기법 | 요구하는 시나리오 | 없으면 벌어지는 일 |
|---|---|---|
| **멱등성** | S5, S6 | 재시도가 **이중 승인·이중 출금** → 고객 돈이 두 번 빠짐 |
| **망취소·순서 역전 처리** | S5 | 상태불명 승인이 홀딩으로 영구 잔류 → 가용잔액이 잠김 |
| **보상 트랜잭션(Saga)** | S1, S4, S9 | 고아 데이터. 취소했는데 돈이 안 돌아옴 |
| **이벤트 유실 방지(Outbox)** | S6, S8 | 이벤트 유실 → 원장 누락 → **대사에서야 발견** |
| **배치** | S6, S7, S8, S10 | 정산 파일이 본질적으로 일 단위 파일 → 실시간 처리 불가 |
| **동시성 제어** | S4 | 동시 결제로 **한도 초과 승인** |
| **집계 정합성** | S7 | 순액이 개별 거래 합과 어긋나도 모름 |
| **읽기 모델 분리** | S12 | 가용잔액 계산이 승인 SLA를 못 맞춤 |
