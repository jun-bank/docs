## 1. 한 줄 정의

> **jun-bank는 고객에게 계좌와 체크카드를 발급하고, 그 카드로 발생한 결제를 승인·매입·정산하며 그 결과를 원장에 기록하는 카드 발급사(은행)다.**

가장 중요한 단어는 **"발급"** 과 **"승인"** 이다.

- **발급사**이므로 우리는 결제 요청을 **받는** 쪽이다. 만드는 쪽(가맹점·PG)이 아니다.
- **승인**은 "돈을 옮기는 것"이 아니라 "지불 능력을 확인하고 금액을 점유하는 것"이다. 이 구분이 이 시스템 전체 구조를 규정한다.

## 2. 포지션 — 결제 생태계에서 어디에 서 있는가

```
 [카드소지자]                                        [가맹점]
      │ 카드 소지                                        │ 카드 제시
      │                                                  ▼
      │                                          [매입사 / VAN]   ← 모의 서비스로 구축
      │                                                  │
      │                              ① 승인 요청 (실시간, 인바운드)
      │                                                  ▼
      ▼                        ┌───────────────────────────────────┐
 계좌 개설 · 카드 발급 ────────▶│      jun-bank  (발급사 = 우리)      │
 결제 내역 조회        ◀────────│  계좌 · 카드 · 승인 판단 · 원장     │
                               └───────────────────────────────────┘
                                       ▲                    │
                        ② 매입·정산 파일 (D+1, 배치)         │ 승인/거절 응답
                                       │                    ▼
                                 ③ 대사 (우리 원장 ↔ 정산 파일)
```

**이 포지션을 고른 이유**

1. 승인이 **인바운드**여야 타임아웃·상태불명·망취소가 *우리가 처리해야 할 문제*가 된다. 아웃바운드(PG 포지션)면 그건 상대방 문제다.
2. 정산 파일을 **받는** 입장이어야 배치와 대사가 필연이 된다.
3. 기존 계좌·거래 자산이 결제의 **자금원·정산 대상**으로 자연 편입된다.

**이 포지션이 확정하는 경계**

- **가맹점은 우리 고객이 아니다.** 가맹점 계약·가맹점 정산·가맹점 수수료 = 범위 밖
- 우리가 보는 것은 **"매입사가 보내온 승인 요청"까지**다
- 자금 흐름에서 우리 위치: 고객 계좌에서 차감 → 매입사에 지급

> ✅ **확정 (2026-08-03)** — 검토한 대안: ① 발급사+매입사 겸업 ② PG/매입사
> **①을 택하지 않은 이유**: 매입사를 겸하면 승인 요청이 내부 호출이 되어 **타임아웃·상태불명·망취소가 우리 문제가 아니게 된다.** 외부 연동의 긴장이 사라진다.
> **②를 택하지 않은 이유**: 정산 파일을 받는 입장이 아니게 되어 **배치·대사의 필연성이 약해진다.**

## 3. 범위

### 3.1 범위 안 (In Scope)

| 영역 | 내용 |
|---|---|
| 고객·인증 | 회원가입, 로그인, 세션·토큰 |
| 계좌 | 개설, 조회, **입금** (결제 재원 확보 목적) |
| 카드 | **체크카드** 발급, 정지/해지, 한도 관리 |
| **결제 승인** | 인바운드 승인 요청 처리, 카드 유효성·한도·가용잔액 검증, 승인/거절 응답, **홀딩(금액 점유)** |
| **결제 정정** | 승인취소, 부분취소, 환불, **망취소(Reversal)** |
| **매입·정산** | 매입 파일 수신, 확정 반영, 실제 출금, D+n 정산 |
| **대사** | 우리 원장과 매입사 정산 내역 대조, 불일치 분류·적재 |
| **원장** | 복식부기 기록, 잔액 파생, append-only, 감사 로그 |
| 모의 외부 | 매입사/VAN 시뮬레이터 — **지연·타임아웃·중복응답을 의도적으로 주입 가능** |

### 3.2 범위 밖 (Out of Scope)

| 제외 항목 | 왜 안 하는가 |
|---|---|
| **신용카드** (여신·청구·결제일·연체) | 분산처리 학습 목표는 체크카드로 전부 커버된다. 신용카드가 더하는 것은 **회계 복잡도**이지 분산 문제가 아니다 → **후속 단계** |
| **계좌 간 이체** | 이체가 보여주는 Saga·보상은 **결제 승인이 이미 같은 것을 보여준다.** 중복이므로 결제 안정화 후로 미룬다 → **후속 단계** |
| 출금 (ATM·현금) | 결제 흐름 검증에 불필요 |
| 가맹점 관리·가맹점 정산·수수료 | 발급사 포지션이므로 우리 소관이 아님 (§2) |
| 실제 카드 브랜드망 연동, ISO 8583 실규격 | 실 연동 불가. **개념만 차용** |
| 신용평가·여신 심사·추심 | 신용카드가 범위 밖이므로 함께 제외 |
| 모바일/웹 프론트엔드 | API까지가 범위 |
| PCI-DSS 실 준수, 실제 PAN 저장 | 실 인증 대상 아님. **토큰화 개념만 구현** |
| 해외결제·환전·다통화 | 단, **통화 필드는 처음부터 모델에 둔다** (나중에 넣으면 전 테이블 마이그레이션) |

> ⚠️ **"후속 단계"와 "안 함"은 다르다.** 위 표에서 신용카드와 계좌이체는 **나중에 할 것**이고, 나머지는 **하지 않을 것**이다.

## 4. 액터

| 액터 | 유형 | 설명 | 주요 관심사 |
|---|---|---|---|
| **카드소지자** | 사람 | jun-bank 계좌·체크카드 보유 고객 | 잔액이 정확한가 · 결제가 되는가 · 취소가 반영되는가 |
| **가맹점** | 사람/조직 | 카드를 받는 상점. **우리와 직접 계약 없음** | 승인이 떨어지는가 |
| **매입사 / VAN** | **외부 시스템** (모의) | 승인 요청을 중계하고 매입·정산 파일을 보낸다 | 시간 내 응답이 오는가 · 정산이 맞는가 |
| **운영자** | 사람 | jun-bank 내부 운영 | 대사 불일치 · 실패 거래 · 배치 상태 |
| **정산 배치** | **시스템(비인간)** | 마감 시각에 기동해 매입·정산·대사를 수행 | 파일이 전부 처리됐는가 · 원장이 균형인가 |
| **만료 처리 배치** | **시스템(비인간)** | 기한이 지난 홀딩을 해제 | 잔류 홀딩이 없는가 |
| **개발자(본인)** | 사람 | 이 프로젝트의 실행 주체이자 1급 이해관계자 | **실험하고 관찰할 수 있는가** · 로컬에서 전부 도는가 |

> 마지막 행이 이 프로젝트 특유의 액터다. 학습이 목적이므로 개발자 본인이 이해관계자이며, "실험과 관찰이 가능한가"가 실제 품질 요구가 된다.

## 5. 핵심 시나리오

각 시나리오 뒤의 `[ ]` 는 **이 시나리오가 불러오는 기술적 문제**다. Phase 3에서 "아키텍처를 좌우하는 기능"을 고를 때의 근거가 된다.

### S1. 회원가입 · 계좌 개설 · 입금
고객이 가입하고 계좌를 개설한 뒤, 결제 재원을 입금한다. 인증 정보와 프로필이 분리 저장된다.
`[분산 트랜잭션 / 정합성 소유자 정의]`

### S2. 카드 발급
계좌에 연결된 체크카드를 발급받는다. 카드번호는 토큰화되어 저장된다.
`[민감정보 분리 / 계좌-카드 참조 무결성]`

### S3. 결제 승인 ★
가맹점 결제 → 매입사가 승인 요청 → 카드 유효성·한도·**가용잔액** 검증 → 승인/거절 응답 → 승인 시 **홀딩 생성**(실제 출금 아님).
`[동시성 제어 / 응답시간 SLA / 가용잔액 vs 원장잔액]`

### S4. 승인 타임아웃과 망취소 ★
승인 처리 중 응답이 매입사에 도달하지 못한다. 매입사는 **성공인지 실패인지 모른다.** 매입사가 망취소 전문을 보내고, 우리는 해당 승인을 강제 정정한다. **망취소는 중복 전송될 수 있다.**
`[두 장군 문제 / 멱등성 / 상태불명 처리 — 결제 도메인의 심장]`

### S5. 매입 및 정산
D+1에 매입사가 매입 파일을 보낸다. 파일을 읽어 승인건을 **확정 거래로 전환**하고, 계좌에서 실제 출금하며 원장에 기록한다.
`[배치 / 대용량 파일 / 부분 실패와 재처리]`

### S6. 대사 ★
우리 원장과 매입사 정산 내역을 대조한다. 불일치 유형: **미매입**(우리엔 있고 파일엔 없음), **미승인 매입**(파일엔 있고 우리엔 없음), **금액 상이**.
`[배치 / 이벤트 유실 탐지 / Outbox가 필요한 진짜 이유]`

### S7. 취소·환불
- **승인취소**: 매입 전. 홀딩 해제. 원장에 확정 거래가 없으므로 역분개도 없다
- **매입취소/환불**: 매입 후. 역분개 전표 생성, 자금 반환
- **부분취소**: 원거래의 일부 금액만. 누적 취소액이 원거래를 넘을 수 없다

`[보상 트랜잭션 / 원거래 참조 무결성 / 금액 정합성]`

### S8. 홀딩 만료
승인 후 기한 내 매입되지 않은 홀딩을 배치가 자동 해제한다.
`[시간 기반 전이 / 배치 / 잔류 상태 정리]`

### S9. 조회
고객이 거래 내역과 잔액을 조회한다. **승인만 된 건은 "결제 예정", 매입된 건은 "결제 완료"로 다르게 보인다.**
`[읽기 모델 / 두 개의 잔액을 사용자에게 설명하는 문제]`

## 7. 학습 목표와의 매핑

이 프로젝트의 1차 산출물은 **동작하는 은행이 아니라 이해**다. 그래서 "더 단순한 방법이 있는데 왜 어렵게 하는가"의 답이 **"그것이 학습 대상이기 때문"** 인 경우를 허용한다. 단 **결정 기록(ADR)에 그렇게 명시**한다.

각 기법은 아래 시나리오에서 **없으면 실제로 돈이 틀어지는** 형태로 등장한다.

| 기법 | 요구하는 시나리오 | 없으면 벌어지는 일 |
|---|---|---|
| **멱등성** | S4 | 재시도가 **이중 승인** → 고객 돈이 두 번 빠짐 |
| **망취소 처리** | S4 | 상태불명 승인이 홀딩으로 영구 잔류 → 가용잔액이 잠김 |
| **보상 트랜잭션(Saga)** | S1, S3, S7 | 고아 데이터. 취소했는데 돈이 안 돌아옴 |
| **이벤트 유실 방지(Outbox)** | S5, S6 | 이벤트 유실 → 원장 누락 → **D+1 대사에서야 발견** |
| **배치** | S5, S6, S8 | 정산 파일이 본질적으로 일 단위 파일 → 실시간 처리가 불가능 |
| **동시성 제어** | S3 | 동시 결제로 **한도 초과 승인** |
| **읽기 모델 분리** | S9 | 가용잔액 계산이 승인 SLA를 못 맞춤 |

> **이 표가 이 프로젝트의 존재 이유다.** 기법을 써보려고 도메인을 고른 것이 아니라, 도메인이 기법을 요구한다.
