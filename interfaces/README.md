# 외부 인터페이스 규격 — 공통 규약·색인

- 상태: 검토대기 (2026-08-06 신설 — `plans/2026-08-06/interface-specs/`)
- ★ **상위 정본 = UC §7 계약 블록**(의미·오류 코드·멱등 키) — 이 규격은 그 표면의 **물리 표현**이다. 충돌하면 규격이 틀린 것이다.

## 1. 공통 규약 (X-1~11)

| # | 규약 |
|---|---|
| **X-1 인코딩** | ASCII(숫자·영대문자·공백) — 한글·자유 텍스트 필드 없음(사유 등 서술 값은 **코드로만**). 바이트 = 문자 1:1 |
| **X-2 패딩** | 숫자(N) = **좌측 0 패딩** · 문자(AN) = **우측 공백 패딩**. 빈 선택 필드 = 전부 공백 |
| **X-3 금액·통화** | **금액 12N — 통화 최소단위 정수**(BR-07: 부동소수 금지. KRW = 원 단위) + ★ **통화 3AN — 값 `KRW` 고정**(2026-08-06 R-01 개정 — BR-07의 *"통화와 최소단위"* 문면을 **필드로** 충족한다. 단일 통화라도 자리를 비워두지 않으며, 다른 통화 도입은 값이 아니라 **새 전문 버전**의 문제다). **위치 = 본문 선두** — 전문은 공통 헤더(X-5) 다음 첫 필드, 파일은 **H 레코드의 레코드 구분 다음**. ★ 파일의 D·T는 통화를 반복하지 않는다(H가 파일 전체에 대해 1회 선언한다) |
| **X-4 일시** | 전송일시 = 14N `YYYYMMDDHHMMSS`(발신측 시각 — 참고용). ★ **요청 방향에서 귀속 영업일의 판정 입력이 되는 필드는 없다** — 수신 시각 기준 BR-14가 정본(보고 5 정합: **응답에는 판정 결과인 귀속 영업일을 실을 수 있다** — 파일 헤더의 영업일 표기(X-8·BR-14 파일 특칙)와 같은 갈래) |
| **X-5 공통 헤더** (전 전문 선두 50바이트) | ①전문길이 4N(헤더 포함 전체) ②전문구분 10AN — ★ **물리 구분값**(정본 이름 K-2의 매핑 — X-7과 같은 원리): `AUTHREQ`·`AUTHRES`·`CANCELREQ`·`CANCELRES`·`RVSLREQ`·`RVSLRES`·`DEPADV`·`DEPADVRES`(전부 ≤10. 보고 1 해소 — K-2 이름 12자가 10AN을 넘던 충돌은 이름이 아니라 물리 값 층에서 푼다) ③전문버전 2N(`01`) ④상관 식별자 20AN(**멱등 키** — 채널별 의미는 각 규격 §멱등) ⑤전송일시 14N |
| **X-6 기관 코드** | 8AN — 발신 기관(매입사·입금원) 식별. **코드 체계 = [미확정 — 외부 규격 의존]**(자리만 고정). ★ **채널 키의 기관 스코프(R-06)가 가리키는 "기관" = ACL이 인증한 발신 기관**(전문 본문 X-6 기관 코드와 일치 검증 — 불일치 = `ARG_MISMATCH`). 즉 **스코프 축의 값은 인증 결과이고 이 필드는 그 선언**이며, 둘이 갈리면 남의 기관을 사칭한 키 공간에 쓰게 된다 |
| **X-7 응답 코드** | 4N — ★ **정본 코드(신설 코드 대장·SM 응답 열의 문자 상수)의 물리 매핑**. 매핑 표는 각 규격 §응답 코드에 있으며 **숫자 값은 [미확정 — 대외 협의]**, 이 문서 단계의 정본은 문자 상수다. 시스템 채널은 **사유 구분**이 정본 요구(BR-36·15 — L7 비적용, C-2 채널 경계) |
| **X-8 파일 공통** | 고정길이 레코드 + **H/D/T**: 헤더(파일 ID·영업일·건수 예고) / 데이터(레코드 유형 코드로 구분) / 트레일러(**totalRecords·금액 합계** — 배치 INV-3의 입력). 레코드 구분자 없음(고정길이) · 파일 인코딩 X-1. ★ **레코드 유형별 길이는 상이할 수 있다**(2026-08-06 R-12 개정 — H·D·T 동일 길이 강제를 해제한다): 파서는 **선두 1AN 레코드 구분으로 유형을 먼저 판정**한 뒤 **그 유형에 고정된 길이만큼** 읽는다. 구분자 없는 파싱의 전제는 *"모든 레코드가 같은 길이"* 가 아니라 *"유형마다 길이가 하나로 정해져 있다"* 이다 |

> 재수신 = **최초 결과 재반환**(K-1 — 채널 유일 식별자 기준). 각 규격의 §멱등이 키의 정본 소유자를 지목한다.

| # | 규약 (추가) |
|---|---|
| **X-9 요청 지문** | BR-02·29의 `requestFingerprint` = ★ **(전문버전 + 정규화 본문)의 keyed hash**(2026-08-06 R-09 개정 — BR-02 *"요청 내용"* 의 물리 정의). ⑴ **범위**: 본문 전체 + 공통 헤더의 **③전문버전**만 포함하고 **⑤전송일시는 제외**한다 — 전송일시를 넣으면 정상 재전송이 전부 `IDEMPOTENCY_CONFLICT`가 되고(보고 6), 전문버전을 빼면 **같은 바이트열이 버전에 따라 다른 의미인데 같은 지문**이 된다 ⑵ **정규화**: X-2 패딩을 적용한 **수신 바이트열 그대로**를 입력으로 쓴다(재해석·재직렬화하지 않는다 — 파싱 차이가 지문 차이를 만들지 않게) ⑶ **keyed hash(HMAC)** — 발신 기관과 공유하는 키로 계산한다. **알고리즘 선정·키 보관·키 교체는 [구현 검증]**(IV-12) ⑷ 알고리즘·정규화는 **X-9 소관**이며 각 규격이 따로 정하지 않는다 |
| **X-10 판정 순서** (전 전문 공통) | ★ **① 인자 형식 → ② 멱등 단락 → ③ 대상 존재 → ④ 상태**(2026-08-06 R-05 — `AUTH`·`CANCEL`·`REVERSAL`·`DEPOSIT` 공통. 각 규격 §3의 판정 순서 열이 이 순서를 따른다). ⑴ **채널 인가**(경로 식별자 부재·미인가 = `FORBIDDEN_LEVEL` — K-1 ①)는 전문 처리 **이전**의 ACL 판정이라 ① 앞에 선다 ⑵ ★ **② 가 ③ 보다 앞서는 것이 이 순서의 요점**이다 — 재수신은 대상을 다시 조회하지 않고 **최초 결과를 그대로 반환**한다(K-1 시스템 채널). 재조회하면 그 사이의 상태 변화가 같은 요청에 다른 답을 만든다 ⑶ ① 이 ② 앞인 이유 = 형식이 깨진 인자는 멱등 키·지문 판정 자체가 성립하지 않는다 ⑷ 사유를 구분하는 채널(BR-36 계열)에서 ①·② 선행은 **대상 존재 응답이 나올 수 있는 입력 범위를 좁혀** 열거 오라클 노출을 줄인다. 남는 노출은 **채널 속도 제한**이 담당한다(**[구현 검증] IV-11**) |
| **X-11 PAN 취급** | ★ **카드번호(PAN) 평문은 멱등·승인 판정의 메모리 경로에만 존재한다**(2026-08-06 R-08 신설). **남는 표면 — 저장·로그·감사·불일치·DLQ — 에는 마스킹**(BIN 6 + 말미 4, 가운데 마스킹: `123456******7890`)해서 적재한다. 전문 자체는 대외 채널 규격이므로 평문 16N을 싣는다 — 규격 5종의 공통 전제이며, PAN 필드를 **가진 것은 `AUTH-REQ` 하나**이고 나머지는 *"PAN을 싣지 않는다"* 가 X-11의 적용 형태다 |
