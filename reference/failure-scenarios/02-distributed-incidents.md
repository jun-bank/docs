## 2. 사례별 상세 — 우리 자리 지목

### 2.1 재시도 폭풍 / 캐스케이딩

**A2. AWS DynamoDB (2015-09-20)** — https://aws.amazon.com/message/5467D2/
네트워크 순단으로 스토리지 서버들이 메타데이터 서비스에 파티션 멤버십을 재요청했다. GSI 채택이 늘며 멤버십 목록이 조용히 커져 있었고, 처리 시간이 타임아웃에 근접해 **여유가 없었다**. 타임아웃된 서버는 *"재요청하고 스스로를 일시적으로 요청 수신에서 제외"* 하는데, 이 선의의 안전장치가 **재시도가 부하를 유지시키는 자기지속 루프**가 됐다. 오전 5:06에 AWS가 한 일은 용량 추가가 아니라 **메타데이터 요청을 일시 정지**시킨 것이다 — 재시도를 끊어야 회복이 시작됐다.

> ★ **우리 자리: ADR-005 §3 *"재시도가 자연스럽다 — 발행 완료 표시 전까지 계속 남아 있다"*.**
> 그 문장에는 **백오프·지터·상한·독약 격리가 하나도 없다.** QS-05의 *파생 수치*에
> **"Outbox 재시도 간격·상한"** 이 적혀 있지만 **아직 미정**이다. → **뚫림 1**

**A4. Google Cloud (2025-06-12)** — https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW
Spanner에 복제된 잘못된 정책이 Service Control을 전역 크래시 루프에 빠뜨렸다. 흥미로운 것은 **회복 구간**이다. 태스크가 재시작하며 전부 같은 테이블을 동시에 쳤고, 구글은 *"Service Control did not have the appropriate randomized exponential backoff implemented to avoid this"* 라고 명시했다. us-central1 회복이 2시간 40분으로 늘어난 원인이 **백오프 부재 하나**였다.

**A8. Twilio 빌링 (2013-07-18)** — https://www.twilio.com/en-us/blog/company/communications/billing-incident-post-mortem-breakdown-analysis-and-root-cause-html
★★ **이 프로젝트에 가장 가까운 사고다.** 두 층이 겹쳤다.
① redis-slave 전체가 동시에 재접속해 full resync를 요청 = thundering herd → 마스터 과부하 → 오진단 재시작 → 잔액 데이터 전손 + 자기 자신의 슬레이브로 부팅되어 **읽기 전용**.
② 그 위에서 **auto-recharge가 카드를 먼저 긁고 잔액을 나중에 갱신**했다. 잔액을 쓸 수 없으니 *"충전됐다"* 를 영원히 확인 못 하고 **같은 고객 카드를 반복 과금**했다. 고객 1.4%가 피해, 카드 정지·계정 정지까지 갔다.
Twilio가 넣은 방어선 두 개가 정확히 우리 것과 같은 종류다 — *"잔액이 없거나 쓸 수 없으면 계정을 정지하지도, 카드를 긁지도 않는다"* (**fail-closed**) + *"복식부기 DB와 실시간 대조"* (**대사**).

> ★ **우리 자리: HA-3(모든 자금 경로 멱등) · O-2. 그리고 `quality-attributes.md` §3 상충표 1행**
> — *"검증할 수 없으면 개별 요청을 거절한다"*. **Twilio는 그 줄이 없어서 긁었다.**
> 우리 상충표가 옳다는 실증이자, **그 줄이 코드에 실제로 있는지**가 시험 대상이라는 뜻이다.

**A9. 우아한형제들 Hystrix (2017)** — https://techblog.woowahan.com/2542/
Zuul 기본값인 **세마포어 격리**는 호출자 자신의 스레드에서 카운터만 센다 — 하위가 느려지면 호출자 스레드가 그대로 물리고, 임계 초과분은 큐잉도 격리도 없이 즉시 거절(502)된다. 네트워크 호출에는 **벌크헤드가 없다**는 뜻이다. THREAD 격리로 바꿔 해결.

### 2.2 메시지 유실 · 중복

**B1~B3 — 우리가 이미 막은 것.** Jepsen Kafka는 acked 987건 중 **520건(52.7%)** 이 unclean leader election으로 사라졌고(https://aphyr.com/posts/293-jepsen-kafka), Datadog은 같은 일을 프로덕션에서 겪었으며(https://www.datadoghq.com/blog/kafka-at-datadog/), Wix는 *"DB에 쓰고 Kafka에 발행하는 것은 원자적 연산이 아니다"* 를 2,300개 마이크로서비스에서 계통적으로 겪었다(https://medium.com/wix-engineering/event-driven-architecture-5-pitfalls-to-avoid-b3ebf885bdb1).

> ✅ **ADR-005가 안 B(브로커 직접 발행)를 기각한 근거 — *"커밋 후 발행 전 종료 시 유실"* — 가 이 세 건으로 실증된다.**
> ⚠️ 동시에 **되돌리는 조건 R2(→ 안 C, CDC+브로커)를 발동하는 순간 B1·B2·B5가 전부 살아난다.**
> 그때 `unclean.leader.election.enable=false` · `min.insync.replicas` · `acks=all`이 함께 켜져야 한다.
> **R2는 "지연 문제를 푸는 것"이 아니라 "새 실패 목록을 사는 것"이다.**

**B4. 우아한형제들 Outbox (2024)** — https://techblog.woowahan.com/17386/
우리와 같은 문제(*"데이터베이스에는 취소 상태로 저장… 이벤트 발행에 실패하면 컨슈머는 여전히 배달을 진행"*)를 Outbox로 풀었다. **여기서 결정적인 것은 순서 보장 방식이다.**
- *"Debezium에서 메시지 발행에 사용되는 MySQL source connector는 태스크를 하나만 사용하도록 강제"*
- *"같은 키는 같은 테이블에 저장되며, 한 테이블에서는 하나의 커넥터를 사용하기 때문에 같은 키에 대해서는 순서를 보장됩니다"*

> ★ **순서는 선언이 아니라 소유권 구조로 만든다.** 이것이 **뚫림 2**의 근거다.

**C1. Segment (2017)** — https://www.twilio.com/en-us/blog/insights/exactly-once-delivery
at-least-once + 불안정한 모바일망에서 **4주간 수집 이벤트의 약 0.6%가 중복**이었다. 실측치가 있다는 것이 중요하다 — *"중복은 드물다"* 가 아니라 **0.6%는 매일 나온다**. 해법: 모든 메시지에 UUID `messageId`, **그 ID로 Kafka 파티셔닝**해 같은 사본이 항상 같은 워커로 가게 하고, 워커 로컬 RocksDB + Bloom filter로 dedup.

**C2. Airbnb Orpheus (2019)** — https://medium.com/airbnb-engineering/avoiding-double-payments-in-a-distributed-payments-system-2981f6b070bb
★★ 불변식: *"돈을 옮기는 연산이 여러 번 호출돼도 시스템은 **최대 한 번** 옮긴다."* 설계 셋:
1. **Pre-RPC / RPC / Post-RPC** 분리 — *"Pre·Post 단계에 네트워크 호출 없음, RPC 단계에 DB 상호작용 없음"*. 네트워크 호출이 DB 트랜잭션 안에 절대 안 들어간다.
2. *"멱등 라이브러리 커밋과 애플리케이션 계층 DB 커밋이 **같은 코드 블록에서 하나로**"*.
3. ★ **replica lag**: *"응답이 (replica에) '존재하지 않음'이므로 서비스가 결제를 다시 실행해 이중 결제가 난다."* → 멱등 조회는 **마스터에서만**.

| **ADR-011과의 관계** | 두 번째 드레인(**N-2**)은 *"전부 도착"* 만 보장하지 *"순서대로 도착"* 을 보장하지 않는다 |
| **필요한 것** | **파티션 → 릴레이 인스턴스 소유 배정**(ADR-008 B-1과 같은 원자적 할당). 순서는 **소유권이 만든다** |

### 뚫림 3 — 수신측 멱등이 계약이지 제약이 아니다 · 정산은 아예 논증되지 않았다

| | |
|---|---|
| **자리** | **O-2 · O-3 · O-5** · ADR-005 §4 *"원장의 멱등 — 이미 준비돼 있다"* · **R3** |
| **증거** | **A8**(Twilio: 확인 못 하면 무한 재과금) · **C2**(Airbnb: **replica lag가 멱등 검사를 뚫는다**) · **C1**(Segment: 중복률 **0.6% 실측**) · **C5**(카드 이중출금: 반영주기 2일) |
| **결함 ①** | ADR-005는 `JournalEntry`에 `sourceEvent` **필드가 있다**는 사실만으로 *"O-2가 충족된다"* 고 적었다. **유니크 제약 요구가 없다.** 그리고 **R3**은 *"중복 전달이 자금 사고로 이어지면 → 제약조건으로 강제"* 라고 적혀 있다 = **사고 난 뒤에 강제하겠다** |
| **결함 ②** | ★ **정산(C4)의 멱등 키가 어느 문서에도 없다.** O-2의 논증은 **원장만** 다뤘다. 정산이 `Captured`를 두 번 받으면 **그 영업일 순액이 두 번 더해진다** → M15 |
| **결함 ③** | ★ **ADR-005 × ADR-007(읽기·쓰기 분리)의 이음매가 미검토다.** 멱등 조회가 읽기 경로로 가면 **C2가 경고한 이중 결제가 그대로 난다** |
| **결함 ④** | **O-5(outbox 보관 기간)와 수신측 멱등 키 보관 기간이 연결돼 있지 않다.** 수신측 보관 < 릴레이 재시도 상한이면 **중복이 그냥 통과한다**. 이미 리서치가 확보한 기준: Stripe 멱등키 **24시간** · IETF draft *"만료 정책 공표 MUST"* |

### 뚫림 4 — B-3의 lease에 fencing token이 없다 (좀비 파티션이 실제로 쓴다)

| | |
|---|---|
| **자리** | **ADR-008 B-1·B-2·B-3·B-5** · **HA-2** · QS-07 파생 수치(*배치 락 TTL*) |
| **증거** | **F3**(Kleppmann: lease 만료는 **두 소유자를 못 막는다**) · **F5**(토스 21.4억) · **F4**(Santander £130m) · **D1**(GitHub 스플릿브레인) |
| **막는 것** | ⚠️ **절반만.** B-1(원자적 할당)은 **동시 획득**을 막는다. B-3(lease)은 **영구 점유**를 막는다. 그러나 **GC 정지한 좀비가 깨어나 쓰는 것**은 둘 다 안 막는다 |
| **B-2로 안 되는 이유** | B-2(*"재할당돼도 결과가 같다"*)는 **순차 재실행** 가정이다. **좀비 + 신규 소유자의 동시 실행**은 다른 문제 — 두 트랜잭션이 인터리브하면 멱등 검사와 쓰기 사이가 벌어진다 |
| **B-5로 안 되는 이유** | `runId`는 **실행 간** 구분이지 **소유권 세대**가 아니다 |
| **필요한 것** | 파티션 할당마다 **단조 증가 토큰**(할당 세대), 파티션 완료·부분합 기록 시 **토큰 검사 후 낮으면 거부**. `study/10`에 없는 개념이므로 **문서에 신설이 필요** |

### 뚫림 5 — 매입 배치의 파티션이 실질적으로 1개다 (설계된 병렬이 실제로는 직렬)

| | |
|---|---|
| **자리** | **ADR-009 §4**(*"매입 배치는 파일 단위로 파티션한다. 파일이 여럿이면 병렬이 된다"*) · **R3** · **QS-04**(1시간) |
| **증거** | **E5**(AWS: **단일 파티션 키 값은 쪼갤 수 없다** — 자동 분할도 무력) · **E1**(Discord: 굵은 파티션 키 하나가 전부를 먹음) |
| **막는 것** | ★ **없다.** R3(*"파일이 항상 1개면 병렬이 안 된다"*)에 **관찰 후 대응**으로만 등재돼 있다 |
| **왜 지금 문제인가** | 매입 파일은 통상 **일 1회 1개**다. 즉 R3의 조건은 *"관찰될지 모르는 것"* 이 아니라 **기본 상태**다. 파일당 수십만 건(ADR-008 §1)을 **한 인스턴스가 직렬로** 처리하게 된다 |
| **`study/10`을 뒤집는 지점** | §5는 §3(균등 분산 붕괴)을 *"부분 · 치명적이지 않다"* 로 판정했다. 그 판정은 **핫 계좌**만 봤고 **파티션 축 자체가 1개로 붕괴하는 경우**를 안 봤다 |

### 뚫림 6 — 타임아웃 계층이 어느 문서에도 없다 · 고아 트랜잭션이 계좌를 잠근다

| | |
|---|---|
| **자리** | **BR-01**(p99 3초) · **QS-06**(*"대기하지 않음"*) · **E1 락**(BR-04·05) · `study/10` §2 표 마지막 행 |
| **증거** | **G1**(Mux: 계층 역전 · **고아 쿼리가 커넥션 풀 고갈** · 재시도 증폭) · **A9**(우아한형제들: 세마포어 격리에 벌크헤드 없음) · **A2**(타임아웃 여유 없음) |
| **막는 것** | ★ **없다.** BR-01은 **목표값**이고 QS-06은 **요구**다. 둘 다 **장치가 아니다** |
| **연쇄** | 승인이 3초에 포기 → **DB 트랜잭션이 안 죽으면 계좌·카드 로우가 계속 잠김** → 같은 계좌 후속 승인 직렬 지연 → 매입사 타임아웃 → **망취소** → QS-03 경로 폭주. `study/10` §5.1의 예고가 **이 메커니즘으로** 성립한다 |
| **이미 확보된 근거** | 리서치가 Worldpay **25초 권장** · Mastercard 프로세서 **7초** · NICEPAY read **5초** · 토스페이먼츠 **60초**를 모아 뒀다 — **바깥 값은 있는데 안쪽 계층이 없다** |
| **필요한 것** | 요청 타임아웃 > 외부 호출 타임아웃 > DB statement timeout > lock timeout 의 **명시적 예산 식**(G1 형태) + **타임아웃 시 트랜잭션 실제 취소 확인** |

### 뚫림 7 — HA-5 expand-contract는 선언뿐, 절차를 소유한 ADR이 없다

| **이벤트 순서 역전의 기업 포스트모템** | 4대 중 1대가 전담 검색 | ★ **공개 포스트모템이 극히 희소하다는 것 자체가 결론.** 확보한 것은 **D1·D2 둘뿐**이고 둘 다 DB 계층이다. **애플리케이션 이벤트 순서 역전은 아무도 안 쓴다** — 탐지가 어려워 사고로 인지되지 않는 것으로 보인다 |
| Kafka **핫 파티션** 실제 사고 | 검색 다수 | 벤더 마케팅 콘텐츠뿐. **E5**(AWS DynamoDB 공식 문서)로 대체 |
| 롤링 배포 중 **enum·직렬화 버전 스큐** 포스트모템 | 검색 다수 | 못 찾음. Kafka 브로커 업그레이드 사고만 나온다 → **뚫림 7 두 번째 노출은 사례 근거 없이 구조 논증만** |
| 한국 기업의 **스키마 마이그레이션** 1차 사고 기록 | toss.tech · tech.kakao.com · d2.naver.com · woowahan · coupang | **없음.** 일반 해설 블로그만 |
| **토스 자동이체 중복 출금(F5)의 기술적 원인** | 언론·기술블로그 | 회사 발표가 *"전산상의 오류"* 에서 멈춘다. **[2차] 언론 보도만** — 메커니즘은 **추정 금지** |
| 토스 SLASH **재시도 전략** 발표 원본 | 검색 | 제3자 요약 블로그만 확인 → **채택 안 함** |
| Coupang Engineering 이벤트 순서·exactly-once | 검색 | 없음 |

### 5.2 URL은 있으나 본문 확인 실패 — **[미검증] · 설계 근거 금지**

| 항목 | 상태 |
|---|---|
| Honeycomb *"Postmortem: RDS Clogs & Cache-Refresh Crash Loops"* (`honeycomb.io/blog/postmortem-rds-clogs-cache-refresh-crash-loops`) | 3회 페치 모두 **다른 글**이 서빙됨(CMS 슬러그 별칭 추정). 요약된 메커니즘(캐시 소멸 → 전원 미스 → RDS 폭주 → singleflight로 해결)은 **그럴듯하나 확인 실패** |
| 29CM transactional outbox 도입기 (Medium) | 본문 회수 실패 — 내비게이션만 반환 |
| SEC 명령 원문 PDF 직접 페치 | `sec.gov`가 WebFetch에 **403**. **§2.7의 사실은 SEC 보도자료(2013-222)와 검색 스니펫으로 교차 확인**했고 PDF URL은 존재 확인만 |

### 5.3 이 문서가 적극적으로 반증한 것 ★

| 떠도는 판단 | 확인 결과 | 처리 |
|---|---|---|
| *"GitHub 2018-10-21은 스키마 마이그레이션 사고"* | ★ **아니다.** 43초 네트워크 단절 → Orchestrator 스플릿브레인이다. 마이그레이션과 무관 | **D1(순서 역전)로 재분류** |
| *"우리 규모(400 TPS)에서는 핫스팟이 안 해당"* (`study/10` §5) | ⚠️ **부분 오판.** §5는 **핫 계좌**만 봤다. **매입 배치의 파티션 축이 1개로 붕괴하는 것**은 규모가 아니라 **구조** 문제다 | **뚫림 5** 등재 |
| *"O-2는 이미 준비돼 있다"* (ADR-005 §4) | ⚠️ **원장만 논증됐다.** 정산 수신측은 **논증 자체가 없다**. 그리고 `sourceEvent` 필드 존재 ≠ 유니크 제약 | **뚫림 3** 등재 |
| *"ADR-008 B-2·B-3이 배치 중복을 막는다"* | ⚠️ **동시 실행은 못 막는다**(F3). B-2는 **순차 재실행** 가정 | **뚫림 4** 등재 |

> ★ **세 번째·네 번째가 특히 중요하다.** 둘 다 ADR 본문이 *"이미 막고 있다"* 고 **적어 둔** 자리다.
> `reference/research/README.md` §4의 관찰이 여기서 반복된다 —
> **문서 리뷰는 *"다른 문서와 일치하나"* 를 묻지 *"이것이 실제로 막나"* 를 묻지 않는다.**

### 5.4 자료의 성격 ⚠️

- §1 표는 **[1차] 38건 · [2차] 4건**이다. 그중 **2023년 이후가 18건** — 재시도·마이그레이션 영역은 최신 사례가 풍부하다.
- **[2차] 4건**(F4 Santander · F5 토스 · C5 카드 이중출금 · E6 네이버페이)은 **전부 언론 보도**다. 규모·시각은 인용 가능하나 **메커니즘은 근거로 쓸 수 없다.**
- **C5는 2006년 자료**다(20년 경과). 인용한 것은 *"오래된 데이터를 읽고 판단하면 멱등이 뚫린다"* 는 **구조**이며, 이는 C2(2019)가 독립적으로 확인한다.
