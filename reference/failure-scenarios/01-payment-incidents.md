- 방법: WebSearch/WebFetch로 수집. **출처가 확인된 것만 §1~§4에 싣고, 출처를 못 찾은 것은 §6에 격리**한다
- 대조 기준: `domain/aggregates/README.md`(E1~E5·조작 대장) · `product/01-business-rules.md`(BR-01~52·M1~M16) · `architecture/adr/ADR-002·003·005·007·008·009·010·011` · `architecture/quality-scenarios.md`(QS-01~07) · `study/10-failure-at-scale/`

> ⚠️ **한계를 먼저 적는다.**
> ① 기업 포스트모템은 **원인을 공개한 것만** 존재한다. 국내 금융권 사고는 **원인이 "전산 오류"로만 공표**되는 경우가 대부분이라, 구조를 추정할 수 있는 사례가 적다.

#### A1. 토스 자동이체 중복 출금 (2026)

| | |
|---|---|
| **같은 구조인 자리** | **E2 매입 반영** · **E3 미수 회수** — "배치·정기 처리 경로에서 같은 지시가 두 번 자금을 움직인다". 규칙으로는 **BR-23**(파일ID·레코드ID 멱등) · **BR-50**(격리→처리 승격) · **ADR-008 B-2**(각 파티션 처리는 멱등) · **B-5**(runId) |
| **막고 있나** | **막고 있다 (설계상)**. BR-23이 "동일 레코드 재처리는 원장에 아무 변화도 만들지 않는다"를 규칙으로 두었고, `CaptureBatch`의 *격리에 있다 = 미반영 / 처리에 있다 = 반영됨* 집합이 **E2와 같은 커밋**이라 "출금 후 처리 표시 전 종료"가 이중 출금 창구가 되지 않는다 |

| **실험 주입** | ① 가용잔액 100인 계좌에 **동시** 승인 60 × 5건 → 승인 합계 ≤ 100, 초과 승인 0건 (ADR-007 §6 검증 항목) ② 카드 2장으로 각각 카드 한도 내 결제 반복 → **계좌 한도(BR-44)에서 막히는지** ③ ★ **같은 계좌에 400 TPS를 몰아** 낙관적 락 충돌률·재시도 횟수·p99를 측정 — 이것이 QS-01·QS-02의 실제 시험이다 ④ 마감(23:00) 직후 승인이 **같은 달력일 한도**에 누적되는지 (BR-05 · 충돌 C3) |

## 4. ★ 우리가 뚫려 있는 것 — 심각도 순

> 판정 기준: **(자금 오차로 이어지는가) × (지금 발현하는가) × (문서가 스스로 인지하고 있는가)**.
> "문서가 인지하고 미해결로 적어 둔 것"은 **은폐된 결함보다 낫지만 여전히 결함**이다.

### G1. 🔴 **BR-38(입금 정정)의 멱등이 규칙 정본에 없다**

| | |
|---|---|
| **어디** | `product/01-business-rules.md` BR-38 — 규칙 문장·검증 방법 어디에도 멱등 언급이 없다. 멱등 키 `(reversalId, 정정)`과 소유자 `DepositReceipt`는 **`domain/aggregates/README.md` E5 각주에만** 있다 |
| **왜 심각한가** | ① 규칙서 머리말이 *"**이 문서가 규칙의 정본이다.** 다른 문서는 BR-nn으로 참조만 하고 규칙 문장을 복사하지 않는다"* 라고 선언했다. 정본에 없으면 **BR-38만 보고 구현한 사람은 멱등을 만들지 않는다** ② E5 각주가 이미 결과를 계산해 놓았다: *"부족분 미수의 `(origin, sourceRef)` 유일성은 **잔액이 부족할 때만** 작동한다. 잔액 20에 정정 10을 두 번 호출하면 둘 다 미수 없이 성공해 **20이 사라진다**"* ③ **M13**(입금 멱등 충돌)은 `DepositConflict` 이벤트로 적재되는데, **충돌이 안 나면(=키가 없으면) 이벤트 자체가 안 뜬다** |
| **사례 대응** | C3 삼성증권 — *"존재하지 않는 것을 만드는 조작에 검사가 없었다"* |
| **어떻게 닫나** | BR-38 규칙 문장에 *"입금 정정은 `(reversalId, 정정)` 기준으로 멱등이다"* 를 추가하고 검증 방법에 *"같은 정정 지시를 N회 → 잔액 감소 1회분"* 을 넣는다. **L1 변경이므로 별도 게이트가 필요하다** |

### G2. 🔴 **낙관적 락 재시도의 상한이 어디에도 없다 — 재시도 증폭의 입구**

| | |
|---|---|
| **어디** | `account.md` §8 *"계좌 단위 낙관적 락(버전) + **충돌 시 재시도**"*, `card.md` §8 *"카드 단위 낙관적 락"*. **재시도 횟수·백오프·지터·상한이 어느 문서에도 없다.** QS-01 파생 수치의 *"승인 경로 락 보유 시간 상한"* 은 **미확정** |
| **왜 심각한가** | ① `10-failure-at-scale` §5가 **"§2 재시도 증폭은 우리 규모에서도 해당한다"** 고 이미 판정했다 ② 연쇄: 핫 계좌 → 낙관적 락 충돌 → 재시도 → p99 3초 초과(**BR-01**) → 매입사 타임아웃 → **망취소** → 망취소도 E1 락을 잡음 → **더 심한 경합**. 문서 원문: *"우리가 느려서 그 망취소도 느려지면 **망취소 재전송이 겹친다**"* ③ **ISO 8583 0421의 재시도 횟수·간격은 "국내외 어디에도 없다"([미검증])** — 상대의 재시도량을 우리가 통제할 수 없다 |
| **사례 대응** | E6 토스플레이스(내부 데이터 처리 구간 과부하) · E2 Stripe(CPU starvation 연쇄) |
| **어떻게 닫나** | 재시도 상한·백오프를 **설정값으로 명시**하고, QS-01/QS-02 부하 시험에서 **락 충돌률과 재시도 횟수를 1급 측정 항목**으로 둔다. `10-failure-at-scale` §2 표(서킷·백오프·재시도 예산·벌크헤드·타임아웃 계층) 중 **어느 것을 채택/기각하는지 근거와 함께 결정** |

### G3. 🟠 **E2·E4가 계좌 파티션 안에서 닫히지 않는다 — 샤딩 시 이중 출금 방어선이 깨진다**

| **왜 그래도 올리나** | ① ADR-009 **R2**(핫 계좌)나 **ADR-010 R1**(대사가 QS-01 침해) → **ADR-004 R1의 "증설 → 샤딩"** 경로가 트리거되면 **즉시 발현**한다 ② 이때는 이미 부하가 높은 상태라 **가장 나쁜 타이밍**에 발현한다 ③ **문서가 인지하고 있다는 것이 방어는 아니다** |
| **사례 대응** | A1 토스 자동이체(배치 경로 중복) · C4 Knight Capital(환경 간 불일치) |
| **어떻게 닫나** | 지금 고치지 않아도 된다. 다만 **샤딩 도입을 검토하는 순간 이것이 선행 과제**임을 ADR-009 R1/R2의 "그때 할 일"에 못박는다 |

### G4. 🟠 **"대사가 며칠째 안 돌고 있다"를 누가 언제 보는지가 미확정**

| | |
|---|---|
| **어디** | **BR-52** 드레인 대기 상한 **미확정** · **BR-48** 재발견 알림 임계(*"며칠째 미해결이면 통지"*) **미확정** · **BR-37** 미결 정산 허용 시간 **미확정** |
| **왜 심각한가** | 세 미확정이 **한 사슬**이다. 드레인이 안 끝나면 → 대사 미실행 + M16 적재 → **탐지 수단이 정지** → 그 사이 발생한 M1~M15는 **아무도 못 본다**. 그리고 *"M16이 며칠 쌓이면 사람을 부른다"* 가 정해져 있지 않다 |
| **사례 대응** | ★ **B1 Revolut** — 결함이 아니라 **탐지 지연**이 $20M을 만들었다. *"파트너 은행이 알려줬다."* |
| **어떻게 닫나** | 세 값을 **함께** 정한다(따로 정하면 사슬이 안 맞는다). 최소한 *"M16이 2영업일 연속이면 즉시 통지"* 수준의 임계를 BR-48에 넣는다 |

### G5. 🟡 **좀비 파티션에 fencing이 없다**

| | |
|---|---|
| **어디** | **ADR-008 B-1**(원자적 할당) + **B-3**(lease, 만료 시 회수) + **R2**(좀비 회수 오작동) |
| **문제** | B-1이 보장하는 것은 **할당의 원자성**이지 **쓰기의 배타성**이 아니다. lease가 만료돼 재할당된 뒤 원 인스턴스가 GC pause·네트워크 분단에서 돌아와 계속 쓰면 **같은 파티션을 둘이 쓴다** |
| **완화 요인** | 대사·정산은 멱등이라 무해. **매입 재처리(BR-50)** 는 *격리 목록에 있을 때만 반영*하는 승격 구조라 흡수된다. 즉 **도메인 규칙이 인프라 결함을 덮고 있다** |
| **왜 그래도 올리나** | *"도메인이 덮어 준다"* 는 **B-2(파티션 처리 멱등)가 모든 파티션에서 실제로 성립할 때만** 참이다. 새 배치가 하나 추가되고 그것이 멱등이 아니면 즉시 깨진다. fencing token(단조 증가 epoch)은 **인프라 층에서 한 번 막는** 수단이다 |
| **사례 대응** | C4 Knight Capital |

### G6. 🟡 **`markSettled` 수신측 멱등의 근거가 문서에 없다**

| | |
|---|---|
| **어디** | `settlement.md` §5가 스스로 경고한다: *"⚠️ 멱등한 것은 산출뿐이다. **전표 기표와 승인 `markSettled`는 재실행하면 중복된다.** … 그 이벤트를 받는 쪽에 **각자의 멱등**을 둔다"* |
| **문제** | **원장 쪽은 수단이 명시돼 있다** — ADR-005 §4 *"`JournalEntry`는 `sourceEvent` 필드를 이미 갖고 있다"*. **C3의 `markSettled`는 수단이 명시돼 있지 않다.** 상태 전이라서 자연히 멱등일 가능성이 높지만, **"자연히 그럴 것"은 근거가 아니다** — 이 프로젝트가 BR-04 각주에서 이미 같은 판단을 기각했다: *"'승인 상태가 막아준다'는 근거가 아니다. 그렇게 처리했다가 1차 리뷰에서 **이중 해제(치명)** 가 나왔다"* |
| **사례 대응** | B2 발란 · A1 토스 |
| **어떻게 닫나** | `authorization.md`의 `markSettled` 조작에 **멱등 근거 한 줄**을 명시(예: *"`settledBusinessDate`가 이미 채워져 있으면 무변화"*) |

### G7. 🟡 **Outbox 릴레이 자신의 단일 실행 수단이 미정 — "전환 장치가 단일 장애점"**

| | |
|---|---|
| **어디** | **ADR-005 §4** "새로 생기는 일" 칸: *"… **릴레이 자체의 단일 실행 보장**". 수단은 정하지 않았다. §6 검증 표에는 *"릴레이 다중 인스턴스 — 같은 레코드를 둘이 전달하지 않는다 (HA-2)"* 가 **기준으로만** 있다 |
| **완화 요인** | at-least-once(O-1)이므로 **둘이 전달해도 수신측 멱등(O-2)이 흡수**한다. 즉 정합성 사고로는 안 간다 |
| **왜 올리나** | ① O-2가 실제로 구현됐는지는 **ADR-005 R3**(*"중복 전달이 자금 사고로 이어진다 = O-2가 실제로는 없다"*)가 사후 관찰로만 확인된다 ② 반대 방향 — 릴레이가 **하나도 안 돌면** 전표가 안 나가고 M12·M14가 매일 뜨며 **BR-52 드레인이 영원히 안 끝난다**(→ G4와 결합) |
| **사례 대응** | ★ **E7 카카오 판교** — *"이중화는 되어 있었으나 자동 전환 시스템 자체가 한 센터에만"* |

## 5. 실험 시나리오 — 나중에 실제로 주입할 수 있는 형태

> 형식: **주입 지점 · 방법 · 기대 결과 · 실패 판정**. 우선순위는 §4의 심각도를 따른다.
> 전부 **결정론적으로 재현 가능**해야 한다 — 시간 의존 항목은 설정값을 분·초로 축약한다(규칙서 수치 정책).

### X1. 입금 정정 이중 적용 (→ G1) — 최우선

```
준비   계좌 잔액 20 (입금 20, 사용 0)
주입   같은 reversalId 로 reverseDeposit(10) 을 2회 호출 (동시 · 순차 두 경우)
기대   잔액 10, 미수 0, DepositReceipt 기록 1건
실패   잔액 0  ← aggregates/README E5 ③ 이 예고한 "20이 사라진다"
변형   ② 잔액 5에 정정 10 → 잔액 0 + 미수 5, 재호출 시 무변화
       ③ 같은 reversalId 에 다른 금액 → M13(DepositConflict) 적재
```

### X2. 승인 경로 동시성·락 재시도 실측 (→ G2, D1/D3 대응)

```

주입   A) 승인 60 × 5건 동시
       B) 같은 계좌에 400 TPS 지속 60초
       C) B 진행 중 같은 승인들에 대해 망취소 0421 을 반복 전송(횟수 무제한)
측정   승인 합계 · 낙관적 락 충돌률 · 재시도 횟수 분포 · p50/p95/p99 · 락 보유 시간
기대   A) 승인 합계 ≤ 100, 초과 승인 0건        (ADR-007 §6)

실패   C 에서 p99 가 무너지면 → 재시도 증폭이 실재. G2 를 즉시 닫아야 한다

### X3. 프로세스 종료 지점 스윕 (→ QS-05, A1·E4 대응)

### X4. 대사 정지 상태의 지속 (→ G4, B1 Revolut 대응)

       그 사이 M12(잔액-원장) 를 인위적으로 1건 만든다

```

## 6. 출처를 못 찾은 것 — **업계 통념으로 격리**

아래는 **조사했으나 원인이 공개된 1차 사례를 찾지 못했다.** 사례로 인용하지 않는다.

|---|---|---|
| **국내 간편결제 이중 결제 포스트모템** | 토스·카카오페이·네이버페이의 **이중 결제 사고 원인 공개 글** | ❌ **없음.** 카카오페이 기술블로그(A3)는 *가상 시나리오*로 설명하고 실제 사고를 서술하지 않는다. 토스 SLASH 21~24 세션 목록에서도 해당 주제를 못 찾았다 |

| **"이중 환불" 국내 사고** | 원인이 공개된 사례 | ⚠️ 티메프(2024) 관련 *"환불 금액을 세 번 중복해 받았다"* 는 **커뮤니티 게시 기반 보도**뿐. **원인 불명이므로 사례로 쓰지 않았다** |
| **전표 중복 기표 사고** | 회계 원장에서 같은 전표가 두 번 들어간 공개 사례 | ❌ **못 찾음.** C1~C3는 *잘못된 값의 1회 기표*이지 *중복 기표*가 아니다 |
| **동시성으로 인한 한도 초과 승인 실사고** | 실명 금융사의 공개 포스트모템 | ❌ **못 찾음.** D3는 취약점 유형 문헌·버그바운티 사례이고, 실명 은행의 공개 사고 보고서는 확인 못 함 |
| **비씨카드 59시간 장애(E5)의 "프로그램 오류" 내용** | 어떤 프로그램의 어떤 오류인지 | ❌ 공개 안 됨 |
| **우리은행 WINI(E8) 공식 원인** | 은행 공식 발표 | ❌ 없음. 언론의 업계 분석뿐 → **[미검증]** 표기 |

### 출처 없는 업계 통념 (참고용, 근거로 쓰지 말 것)

- *"이중 결제의 대부분은 타임아웃 후 재시도에서 나온다"* — 개별 사례로는 A2·A3가 그 형태이지만, **분포를 주장할 근거는 없다**
- *"대사는 T+1이 표준"* — Uber(A5)가 T+1이라는 사실은 확인했으나 **업계 표준이라는 근거는 없다.** 우리 **QS-04는 마감 후 1시간**으로 더 짧다
- *"장애 시 stand-in(대리승인) 모드가 일반적"* — Mastercard STIP이 존재한다는 것은 BR-01 근거에 이미 [1차]로 인용돼 있으나, **발급사가 자체 stand-in을 두는 것이 일반적인지는 확인 못 함**
