# 대규모에서 달라지는 것 — 처리 효율이 아니라 실패의 양상

> **규모가 커지면 "느려진다"가 아니라 "실패하는 방식이 바뀐다".**
> 원리를 안다고 자동으로 따라오지 않는다 — 겪어야 아는 종류다.
>
> ★ **이 프로젝트의 목표 부하(평시 80 · 피크 400 TPS)에서는 대부분 안 나온다.**
> 그래도 남기는 이유는 §5에 있다.

---

## 1. 부분 실패가 정상 상태가 된다

```
소규모   장애는 사건이다.        "다운 4회를 복구했다"
대규모   장애는 배경이다.        초당 수만 건이면 항상 몇 %는 실패 중이다
```

**다운이 안 난다. 대신 p99가 계속 나쁘다.**

| | 소규모 | 대규모 |
|---|---|---|
| 관제 대상 | **가동 여부** | ★ **분포** (p50/p95/p99) |
| 알림 기준 | 죽었나 | 나빠지는 **추세** |
| 고쳐야 할 것 | 그 장애 | **꼬리(tail)를 만드는 구조** |

> ★ **고칠 대상 자체가 바뀐다.** *"어제 3건 실패"* 를 하나씩 보는 방식이
> *"실패율 0.3%가 0.5%로"* 를 보는 방식으로 바뀐다. **개별 건을 못 쫓는다.**

---

## 2. 재시도가 부하를 증폭시킨다

```
A 느려짐  →  B의 스레드가 A를 기다리며 물림  →  B도 느려짐  →  C까지
                          ↑
                    재시도가 여기에 불을 붙인다
```

**한 번 실패한 요청이 3번 재시도되면 부하가 3배가 된다.** 이미 느린 시스템에 3배가 들어간다.

| 장치 | 무엇을 막나 |
|---|---|
| **서킷 브레이커** | 실패가 임계를 넘으면 **즉시 거절** — 대기 자체를 없앤다 |
| **지수 백오프 + 지터** | 재시도가 **동시에** 몰리는 것을 막는다 |
| **재시도 예산** | 전체 요청 대비 재시도 비율에 상한 |
| **벌크헤드** | 느린 대상 전용 풀 — 다른 경로가 안 물린다 |
| **타임아웃 계층** | 하위 타임아웃 < 상위 타임아웃. **거꾸로면 상위가 먼저 포기하고 하위는 계속 돈다** |

> ★ **"서킷 브레이커를 넣어봤다"와 "재시도 폭풍을 맞고 튜닝했다"는 다르다.**
> 임계값·반열림 시간·지터 폭은 **실측 없이 정할 수 없다.**

---

## 3. 균등 분산 가정이 깨진다

**샤딩·파티셔닝은 "부하가 고르게 들어온다"는 전제 위에 있다.** 실제로는 안 그렇다.

| 편중 원인 | 예 |
|---|---|
| **인기 항목** | 한 상품·한 이벤트가 트래픽 대부분 |
| **큰 테넌트** | 고객 하나가 전체의 절반 |
| **시간 편중** | 특정 시각에 집중 (급여일·정산 시각) |
| **키 설계** | 순차 키 → 마지막 샤드에만 쓰기가 몰린다 |

> ★ **핫스팟은 샤드를 늘려도 안 풀린다.** 한 키에 몰리면 그 키는 여전히 한 샤드다.
> **분할 축을 바꾸거나 그 키만 따로 다뤄야** 한다.

| 대응 | |
|---|---|
| 키에 **엔트로피 추가** | `accountId#bucket` 처럼 쪼갠다 — 단 조회가 복잡해진다 |
| **핫 키 전용 처리** | 상위 N개를 별도 경로로 |
| 읽기 **캐시·복제** | 읽기 편중에만 유효 |

---

## 4. 상태 있는 것은 늘려도 안 된다

**무상태 서버는 스케일아웃하면 된다. 나머지는 아니다.**

| 자원 | 왜 안 늘어나나 |
|---|---|
| **커넥션 풀** | 앱을 2배로 늘리면 DB 커넥션도 2배 — **DB가 먼저 죽는다** |
| **락 경합** | 같은 로우를 노리는 인스턴스가 늘면 **경합이 심해진다** |
| **시퀀스·채번** | 중앙 채번은 인스턴스가 늘수록 병목 |
| **캐시 일관성** | 노드가 늘면 무효화 전파 비용이 **제곱으로** |
| **분산 락** | 늘릴수록 락 서버가 병목 |

> ★ **"증설했는데 더 느려졌다"의 대부분이 여기다.**
> 앞단을 늘렸더니 **뒷단 경합이 심해진** 것이다.

## 5. ★ 우리 규모에서 무엇이 해당하나

목표 부하는 **평시 80 · 피크 400 TPS**(QS-01·QS-02)다. **대규모가 아니다.**

| # | 양상 | 우리에게 | 왜 |
|---|---|---|---|
| §1 | 부분 실패가 정상 상태 | ❌ **안 해당** | 400 TPS에서 실패는 **여전히 사건**이다. 개별 건을 쫓을 수 있다 |
| §3 | 균등 분산 붕괴 | ⚠️ **부분** | 핫 계좌는 가능하나 **치명적이지 않다.** ADR-009 R2에 이미 등재 |
| **§2** | **재시도 증폭** | ★ **해당** | 규모와 무관하다 — §5.1 |
| **§4** | **상태 있는 것의 한계** | ★ **해당** | 규모와 무관하다 — §5.2 |

### 5.1 재시도는 우리 도메인의 **전제**다

```
ISO 8583 0421 (Reversal Advice Repeat)
  종료 조건이 "응답 수신"뿐이고 횟수·간격 규정이 없다
  → 몇 번 오는지 모른다  (quality-scenarios QS-03)
```

**우리는 재시도를 선택한 게 아니라 받는 쪽이다.** 그리고:

| 우리 설계의 재시도 | |
|---|---|
| 매입사 망취소 | at-least-once — **상대가 정한다** |
| **Outbox 릴레이** | ADR-005 O-1 — at-least-once |
| 정산 재시도 | BR-37 — 임계까지 자동 |
| 매입 배치 재처리 | BR-50 — 보류 해제 후 |

> ★ **400 TPS여도 재시도 증폭은 난다.** 매입사가 타임아웃으로 판단해 망취소를 보내는데
> 우리가 느려서 그 망취소도 느려지면, **망취소 재전송이 겹친다.**
> 그래서 **BR-01 p99 3초**가 응답시간 목표가 아니라 **정합성 방어선**인 것이다
> (`quality-attributes.md` §1 주의 ①).

### 5.2 상태 있는 것 — 우리는 이미 걸려 있다

**ADR-010 R1이 정확히 이 문제다.**

```
대사 배치가 실시간 승인과 같은 DB를 친다
  → 앱 인스턴스를 늘려도 DB 경합은 안 줄어든다
  → 되돌리는 조건: "대사 실행 중 QS-01이 침해되면"
```

그리고 **E1이 계좌·카드 로우에 락을 잡는다**(BR-04·05). 같은 계좌 동시 승인은 **직렬화된다** —
그것이 도메인이 요구하는 것이므로 **늘려서 푸는 문제가 아니다.**

> ★ **ADR-004 R1이 "분할이 아니라 증설이 먼저"라고 했는데, 그것도 한계가 있다.**
> 증설이 듣는 것은 **앱 CPU**이고, **DB 쓰기·락 경합에는 안 듣는다.** 그때는 샤딩(ADR-009)이다.

## 6. 왜 그래도 남기나

| 이유 | |
|---|---|
| **§2·§4는 지금 해당한다** | 규모와 무관한 양상이다 |
| **판단 기준을 미리 갖는다** | *"증설했는데 왜 안 빨라지나"* 에 §4가 답한다 |
| ★ **오버엔지니어링을 막는다** | §1·§3이 **우리에게 안 해당한다는 것을 아는 것**이 그것을 안 만드는 근거다 |

> ★ **마지막이 이 문서의 실용적 가치다.** *"대규모니까 서킷 브레이커·백프레셔·핫키 처리를 다 넣자"* 는
> 근거 없는 큰 수와 같다(품질 속성 **D-03**). **어느 양상이 실제로 걸리는지 세는 것**이 먼저다.
