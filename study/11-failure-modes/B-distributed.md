# B. 분산·비동기 실패 (F-09 ~ F-19)

> **프로세스가 갈리는 순간 생기는 문제들.**
> 같은 프로세스에서는 자명하던 것이 **네트워크를 건너면 보장이 사라진다.**

---

## 전제 — 두 장군 문제

이 그룹 전체의 뿌리다.

```
A가 B에게 요청을 보냈는데 응답이 안 온다
  → B가 못 받았나?
  → B가 처리했는데 응답이 유실됐나?
  ★ A는 구분할 수 없다
```

**구분할 방법이 원리적으로 없다.** 그래서 선택지는 둘뿐이다.

| 선택 | 결과 |
|---|---|
| 재시도한다 | **중복** 가능 (at-least-once) |
| 재시도 안 한다 | **유실** 가능 (at-most-once) |

> ★ **"정확히 한 번"(exactly-once)은 전달에서 불가능하다.**
> 가능한 것은 **at-least-once 전달 + 수신측 멱등** = 결과적으로 한 번이다.
>
> **카카오페이가 성공/실패에 "Unknown"을 3번째 상태로 둔 것**이 이 문제를 정면으로 인정한 것이다.

## F-09. 재시도 폭풍 / 캐스케이딩 장애

### 원리 — 부하가 곱해진다

```
정상   요청 100 → 처리 100
느려짐 요청 100 → 30 타임아웃 → 재시도 30 → 실질 130
       더 느려짐 → 60 타임아웃 → 재시도 60 → 실질 160
       → ★ 느려질수록 부하가 는다 (양의 피드백)
```

### 스레드가 물리는 방식

```
서비스 B 가 A 를 동기 호출한다
  A 가 5초 걸리면 B 의 스레드가 5초간 묶인다
  B 의 스레드 풀이 200 개면 → 초당 40 요청만 처리 가능
  → B 도 느려진다 → B 를 부르는 C 도 물린다
  ★ A 하나가 전체를 멈춘다
```

### 장치와 그 원리

| 장치 | 무엇을 하나 | 왜 듣나 |
|---|---|---|
| **서킷 브레이커** | 실패율이 임계를 넘으면 **즉시 거절** | ★ **대기 자체를 없앤다** — 스레드가 안 물린다 |
| **지수 백오프** | 재시도 간격을 1s → 2s → 4s | 회복할 시간을 준다 |
| ★ **지터** | 간격에 난수를 섞는다 | **동시에 몰리는 것**을 막는다 — 백오프만 있으면 전부 같은 시각에 재시도한다 |
| **벌크헤드** | 대상별 전용 풀 | 느린 대상이 **다른 경로를 안 먹는다** |
| **재시도 예산** | 전체 대비 재시도 비율 상한 | 폭주 자체를 막는다 |

> ★ **지터가 없으면 백오프가 오히려 나쁘다.** 100개가 동시에 실패하면
> 1초 뒤에 100개가 **동시에** 재시도한다 — 파도가 된다.

### 사례

**Twilio 빌링 (2013)**: 잔액 갱신 전에 카드를 긁고, 확인이 안 되니 **무한 재과금**.
넣은 방어선이 *"잔액을 쓸 수 없으면 긁지 않는다"*(fail-closed) + *"복식부기 DB와 실시간 대조"*.

> ★ **fail-closed 가 핵심이다.** 확인이 안 되면 **진행하지 않는다.**
> 우리 상충표 *"검증 불가 시 개별 요청 거절"* 이 같은 판단이다.

### 우리 자리 — 규모와 무관하게 해당한다

```
망취소가 at-least-once (ISO 8583 0421은 종료 조건이 "응답 수신"뿐)
  ↓
우리가 느려짐 → 매입사 타임아웃 → 망취소 전송
  ↓
★ 그 망취소도 E1 락을 잡는다 → 더 느려짐 → 망취소 재전송
```

**막는 것**: ADR-012 **W-8~W-11** (락 재시도 상한·백오프·지터·**3초 넘으면 재시도 금지**)
· ⚠️ **Outbox 릴레이 재시도 정책은 아직 없다**

## F-10. 메시지 유실

### 원리 — 커밋과 발행 사이의 틈

```
BEGIN
  UPDATE account ...
COMMIT              ← ① 여기까지 성공
publish(event)      ← ② 여기서 프로세스가 죽으면?
```

**①은 됐고 ②는 안 됐다.** 사실은 바뀌었는데 **아무도 모른다.**

반대로 순서를 바꾸면:

```
publish(event)      ← ① 발행
BEGIN … COMMIT      ← ② 여기서 실패하면?
```

**일어나지 않은 일을 알린 것**이 된다. 더 나쁘다.

> ★ **두 저장소(DB와 브로커)에 원자적으로 쓸 방법이 없다.** 이것이 이 문제의 본질이다.

### 답 — Outbox

```
BEGIN
  UPDATE account ...
  INSERT INTO outbox (event)    ← ★ 같은 트랜잭션
COMMIT

별도 프로세스
  outbox 를 읽어 전달 → 성공 시 완료 표시
```

**사실과 이벤트가 한 커밋**이므로 **둘 다 있거나 둘 다 없다.** 유실이 원천적으로 불가능하다.

### 우리 자리

**막는 것**: ★ **ADR-005** Outbox — 안 B(브로커 직접 발행) 기각이 이 원리에서 나왔다.

## F-11. 메시지 중복

### 원리

Outbox가 유실은 막지만 **중복은 안 막는다.**

```
outbox 읽기 → 전달 성공 → ★ 완료 표시 전에 죽음
재시작 → 아직 미완료로 보임 → 다시 전달
```

**전달과 완료 표시가 원자적일 수 없다** — F-10과 같은 구조가 한 계층 아래에서 반복된다.

### 답 — 수신측 멱등

```
수신측이 "이 이벤트 ID를 이미 처리했나"를 본다
  → 처리했으면 아무 일도 안 한다
```

**핵심은 "본다"가 아니라 "못 넣는다"** 여야 한다는 것이다.

| 방식 | 안전한가 |
|---|---|
| 조회 후 없으면 처리 | ❌ **동시 요청에서 둘 다 "없다"를 본다** |
| ★ **유니크 제약** | ✅ DB가 **두 번째를 거부**한다 |

> ★ **필드가 있는 것과 제약이 있는 것은 다르다.**
> 우리 ADR-005가 *"`JournalEntry`는 `sourceEvent`를 이미 갖고 있어 충족"* 이라고 적었는데
> **유일 제약이 없었다** — 리서치가 그것을 잡았고 **INV-8**로 고쳤다.

### 우리 자리

**막는 것**: **INV-8**(원장) · ⚠️ **정산(C4)의 멱등 키는 아직 없다**

## F-12. 순서 역전

### 원리

```
이벤트 A(입금 100) → B(출금 30) 순으로 발생
전달이 병렬이면 B 가 먼저 도착할 수 있다
  → 잔액이 음수가 되거나, 처리 자체가 거부된다
```

### 왜 "전역 순서"가 답이 아닌가

전역 순서를 보장하려면 **전달을 직렬화**해야 한다 — 처리량이 무너진다.

**답은 "필요한 범위에서만" 순서를 지키는 것**이다.

```
같은 계좌의 이벤트는 순서대로
다른 계좌끼리는 순서 무관
  → 계좌ID 로 파티션 → 파티션 내 단일 소비자
```

> ★ **우아한형제들**이 이것을 **소유권 구조**로 풀었다 —
> *커넥터 단일 태스크 + 키→테이블 고정*. 즉 **한 키는 항상 한 소비자**.

### 우리 자리

ADR-005 **O-4**가 *"순서는 같은 파티션 키 안에서만 보장"* 이라고 **선언**한다.

**막는 것**: ⚠️ **선언뿐 — 장치가 없다.**
릴레이가 2인스턴스면 같은 계좌 레코드를 **병렬로 집을 수 있다.**
그리고 ADR-005 검증표는 **중복만 재고 순서는 안 잰다.**

> ⚠️ **N-2 드레인도 답이 아니다** — 드레인은 *"전부 도착"* 을 보장하지 *"순서대로"* 를 보장하지 않는다.

## F-13. Head-of-line blocking — 독약 메시지

### 원리

```
릴레이가 outbox 를 순서대로 훑는다
  레코드 5 가 영구 실패 (수신측 버그·스키마 불일치 등)
  → 재시도 → 또 실패 → 또 재시도
  → ★ 6 이후가 영원히 안 나간다
```

**한 건이 전체를 막는다.** 그리고 **유실이 아니라 정체**라 대사가 *"아직 안 왔다"* 로만 본다.

### 답

| 장치 | |
|---|---|
| **재시도 상한** | N회 넘으면 포기 |
| ★ **DLQ**(독약 격리) | 실패한 것을 **옆으로 빼고** 다음으로 진행 |
| **격리 알림** | DLQ에 들어간 것을 **사람이 본다** |

> ★ **DLQ 없이 상한만 두면 유실이 된다.** 빼되 **버리지 않는 곳**이 필요하다.

### 우리 자리

**막는 것**: ⚠️ **없다** — ADR-005 §3은 *"재시도가 자연스럽다"* 뿐이다.
순서대로 훑는 구조(O-4)라 **이 문제가 구조적으로 존재한다.**

## F-14. 좀비 — lease 만료로는 못 막는다

### 원리

분산 락·파티션 할당은 보통 **임차(lease)** 로 한다.

```
인스턴스 A 가 파티션 3 을 30초간 임차
  → 30초 안에 갱신하면 유지
  → 갱신 못 하면 만료 → 다른 인스턴스가 가져간다
```

**여기에 구멍이 있다.**

```
시각  A                              B
────────────────────────────────────────────────
 0    파티션 3 임차 (만료 30s)
 5    ★ GC 정지 시작 (40초)
30                                   만료 감지 → 파티션 3 임차
32                                   처리 시작
45    GC 끝. ★ 자기가 아직 소유자인 줄 안다
46    쓰기 실행                       쓰기 실행
      → 둘이 같은 파티션에 쓴다
```

> ★ **A는 자기가 멈춰 있었다는 것을 모른다.** 시계를 봐도 *"방금 갱신했는데"* 로 보인다.
> **lease는 "가져가는 것"을 조정할 뿐 "쓰는 것"을 막지 않는다.**

### 답 — fencing token

```
임차할 때마다 단조 증가하는 번호를 받는다
  A → token 17
  B → token 18

쓰기에 token 을 함께 보낸다
저장소가 "지금까지 본 것보다 작은 token 은 거부"
  A(17) 의 늦은 쓰기 → 거부   ★ 구조적으로 막힌다
```

> **Kleppmann (2016)** 이 이것을 정식화했다.

### 우리 자리

**ADR-008 B-3**이 lease를 두었다.

**막는 것**: ⚠️ **B-1은 *할당*의 원자성**이지 *쓰기*의 배타성이 아니다.
**B-2(멱등)는 순차 재실행 가정**이고 **B-5 runId는 실행 간 구분**이지 소유권 세대가 아니다.
→ **fencing token이 필요하다.**

## F-15. 배치 중복 실행

### 원리

스케줄러를 이중화하면 **가용성은 오르지만 단일 실행이 깨진다.**

```
스케줄러 A, B 를 둘 다 띄움 (A가 죽어도 돌게)
  → 23:00 에 둘 다 트리거
  → 배치가 두 번 돈다
```

**K8s CronJob도 마찬가지다** — 컨트롤러가 재시작하면 중복 생성이 가능하다.

> ★ **Toss Payments (2025)** 원문: *"K8s CronJob은 정확히 한 번을 보장 못 해 배치 중복 실행 문제가 생겼어요."*

### 실제 피해

| 사례 | |
|---|---|
| **토스 자동이체 2026-06** | 38분 · 2.1만 건 · **21.4억 원** |
| **Santander 2021** | 크리스마스 이브 중복 지급 **£130m** |

**우리 도메인·우리 금액대에서 실제로 난다.**

### 답과 그 한계

| 방법 | 단일 실행 | 병렬 |
|---|---|---|
| 리더 선출 | ✅ | ❌ **리더가 전부 처리** |
| 전역 락 | ✅ | ❌ |
| ★ **파티션 할당** | ✅ 파티션당 하나 | ✅ |

### 우리 자리

**막는 것**: **ADR-008 A**(파티션 할당). 안 D(외부 스케줄러 1회 트리거) 기각이
**Toss Payments 사례로 실증됐다.**

⚠️ 단 **F-14(fencing)가 남아 있어** 완전하지 않다.

## F-16. 타임아웃 계층 역전

### 원리

```
정상   상위 5초 > 하위 3초
       → 하위가 먼저 포기 → 상위가 그것을 받아 처리

역전   상위 3초 < 하위 5초
       → 상위가 먼저 포기하고 응답
       → ★ 하위는 계속 돈다. 아무도 안 기다리는 일을
       → 자원(커넥션·락)이 계속 잡혀 있다
```

### 왜 자금 경로에서 치명적인가

```
승인이 3초에 포기하고 거절 응답
  → ★ 그런데 DB 트랜잭션이 안 죽으면 계좌 로우가 계속 잠겨 있다
  → 다음 승인이 그 락을 기다린다
  → 줄줄이 느려진다 → 매입사 타임아웃 → 망취소 폭주
  → 그 망취소도 같은 락을 원한다
```

**F-09(재시도 폭풍)로 이어지는 정확한 경로다.**

### 답

```
바깥에서 안으로 갈수록 타임아웃이 짧아야 한다
  매입사 규약 25초 (Worldpay)
    > 우리 응답 목표 3초 (BR-01)
      > DB 쿼리 타임아웃 1초
        > 락 대기 타임아웃 0.5초
```

**그리고 상위가 포기할 때 하위를 실제로 취소**해야 한다(전파).

### 우리 자리

**막는 것**: ⚠️ **없다.**
BR-01은 목표값, QS-06은 요구일 뿐 **장치가 아니다.**
바깥 값(Worldpay 25초 · Mastercard 7초)은 리서치가 확보했는데 **안쪽 계층이 없다.**

## F-17. 배포 스큐 — 구/신 버전이 동시에 돈다

### 원리

롤링 배포는 **정의상 두 버전이 공존하는 구간**을 만든다.

```
인스턴스 8대
  배포 진행  신 신 신 신 구 구 구 구
             ↑ 같은 요청이 어느 쪽으로 갈지 모른다
```

### 무엇이 깨지나

| 종류 | 예 |
|---|---|
| **스키마** | 신 버전이 새 컬럼을 쓰는데 구 버전이 모른다 (F-06) |
| **이벤트 스키마** | 신 버전이 필드를 추가했는데 구 버전이 파싱 실패 — ★ **유실이 아니라 오해라 대사가 못 잡는다** |
| ★ **동작 규칙** | 구 버전과 신 버전이 **다른 판단**을 한다 |

### 사례

> ★ **Knight Capital (2012)**: 8대 중 **7대만 배포**. 1대의 구 코드가 **재사용된 플래그**를 옛 의미로 해석
> → 45분 만에 **$460M**. 그리고 **롤백이 상황을 악화**시켰다(7대를 구 코드로 되돌리자 문제가 8대로 퍼졌다).

### 우리 자리

★ **ADR-011 lazy close**가 정확히 이 위험을 갖는다.

```
"거래의 귀속 영업일이 lastClosedBusinessDate 보다 크면 확정한다"
  → ★ 어느 버전의 거래가 닫는가?
  → 구 버전은 안 닫고 신 버전은 닫는다
  → 계좌마다 closedBalance 가 있거나 없다
  → ADR-011이 없앴다고 선언한 T2 가 배포 경로로 부활한다
```

**막는 것**: ⚠️ **HA-5 선언뿐**

## F-18. Split-brain

### 원리

```
네트워크가 갈라진다
  → 양쪽이 각각 "상대가 죽었다"고 판단
  → 양쪽 다 리더가 된다
  → 양쪽에 쓰기가 들어간다
  → 합칠 때 충돌
```

### 무엇이 무너지나

★ **유니크 제약이 무력화된다.** 두 DB가 각각 *"이 키는 처음"* 이라고 본다.
**멱등이 유니크 제약에 기대고 있으면 그 순간 멱등이 사라진다.**

### 사례

> **GitHub 2018-10**: 43초 네트워크 단절 → 크로스리전 페일오버 → **24시간 11분** 저하, 954건 미복제.
> 판단 원칙을 명시했다 — *"data integrity over site usability"*.

**우리 상충표 *"정합성 ↔ 가용성 → 정합성"* 과 같은 판단이다.**

### 우리 자리

단일 DB라 **지금은 안 난다.**

**막는 것**: ⚠️ **HA-3 멱등의 근거가 "단일 DB 유니크 제약"이라는 사실이 안 적혀 있다.**
다중화하는 순간 전제가 무너지는데 **그 의존이 문서에 없다.**

## F-19. 핫스팟 — 늘려도 안 풀린다

### 원리

샤딩·파티셔닝은 **부하가 키에 고르게 퍼진다**는 전제 위에 있다.

```
키가 고르면   샤드 4개 → 각 25%
한 키에 몰리면 샤드 4개 → 한 샤드 70%, 나머지 10%씩
  → ★ 샤드를 8개로 늘려도 그 키는 여전히 한 샤드다
```

**분할은 키를 쪼개지 못한다.**

### 편중이 생기는 곳

| 원인 | |
|---|---|
| 인기 항목 | 한 상품·한 이벤트 |
| 큰 테넌트 | 고객 하나가 절반 |
| **시간 편중** | 급여일·정산 시각 |
| **키 설계** | 순차 키 → 마지막 샤드에만 쓰기 |

### 우리 자리 — 규모가 아니라 구조다

```
매입 배치 파티션 = 파일 단위 (ADR-009 §4)
  매입 파일은 통상 일 1회 1개
  → ★ 파티션이 항상 1개
  → 병렬도 1 → QS-04(1시간)가 여기서 깨진다
```

**ADR-009 R3**이 *"파일이 항상 1개면"* 을 되돌리는 조건으로 뒀는데,
**그것이 관찰 대상이 아니라 기본 상태다.**

> ⚠️ **`study/10` §5의 *"핫스팟은 우리에게 안 해당"* 판정을 부분 수정한다** —
> 계좌 핫스팟은 안 해당하지만 **매입 배치는 해당한다.** 규모가 아니라 **구조**다.
