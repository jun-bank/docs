## F-01. Lost update — 커밋된 변경이 조용히 사라진다

### 원리 — MVCC와 스냅샷

MySQL InnoDB는 **MVCC**(다중 버전 동시성 제어)로 동작한다.
읽을 때 락을 잡지 않는 대신, **트랜잭션마다 "그 시점의 사진"** 을 본다.

```
트랜잭션이 시작되면
  → 그 순간의 스냅샷을 만든다
  → 이후 다른 트랜잭션이 뭘 바꾸든 나는 옛 버전을 계속 본다
  → 옛 버전은 undo 로그에 보관돼 있다
```

**격리 수준이 이 스냅샷의 수명을 정한다.**

| 격리 수준 | 스냅샷 |
|---|---|
| **READ COMMITTED (RC)** | **문(statement)마다 새로** 뜬다 — 매번 최신 커밋을 본다 |
| **REPEATABLE READ (RR)** | ★ **트랜잭션 시작 시 한 번** — 끝까지 같은 사진을 본다 |

> **MySQL InnoDB의 기본값은 RR이다** (8.0·8.4·9.x 모두 유지).

### 왜 깨지나

RR의 *"끝까지 같은 사진"* 이 **읽기에는 좋고 쓰기에는 위험하다.**

```
계좌 잔액 100, 홀딩 0

시각  T1 (승인 A: 30 홀딩)          T2 (승인 B: 50 홀딩)
────────────────────────────────────────────────────────
 1    BEGIN
 2    SELECT account
        → balance=100, holdTotal=0
 3                                   BEGIN
 4                                   SELECT account
                                       → balance=100, holdTotal=0   ★ 같은 값
 5    가용잔액 = 100 - 0 = 100
      30 ≤ 100 → 승인
 6    UPDATE holdTotal = 0 + 30
 7    COMMIT                          (T2는 아직 옛 스냅샷을 본다)
 8                                   가용잔액 = 100 - 0 = 100
                                     50 ≤ 100 → 승인
 9                                   UPDATE holdTotal = 0 + 50   ★ 30을 덮어쓴다
10                                   COMMIT

결과  holdTotal = 50   (30 + 50 = 80 이어야 한다)
      가용잔액 = 50    (실제로는 20이어야 한다)
      → 30만큼 초과 승인 가능해진다
```

> ★ **에러가 안 난다.** DB는 *"둘 다 유효한 UPDATE"* 로 본다.
> **숫자만 조용히 틀린다** — 이것이 이 유형이 위험한 이유다.

### 왜 "ORM 패턴"이라 부르나

ORM은 **엔티티를 읽어 객체로 만들고 → 필드를 바꾸고 → 저장**한다.

```java
Account a = repo.findById(id);   // ① load   — 여기서 스냅샷
a.hold(30);                      // ② modify — 메모리에서
repo.save(a);                    // ③ save   — UPDATE ... SET holdTotal = 30
```

**③이 `SET holdTotal = 30`(절대값)이지 `SET holdTotal = holdTotal + 30`(상대값)이 아니다.**
그래서 ①과 ③ 사이에 남이 바꾼 것이 **통째로 사라진다.**

> ★ **Jepsen MySQL 8.0.34 (2023-12)** 가 이것을 측정했다 — **9,048 트랜잭션 중 198건**.
> 원문: *"ORM의 load-modify-save 패턴에서 MySQL이 커밋된 변경을 조용히 버린다."*

### 막는 법 세 가지

| 방법 | 어떻게 | 대가 |
|---|---|---|
| **낙관적 락** | 버전 컬럼을 두고 `UPDATE … WHERE version = ?` — **안 맞으면 0행 갱신 → 예외** | 충돌 시 재시도 필요 |
| **비관적 락** | `SELECT … FOR UPDATE` — 읽는 순간 잠근다 | ★ 락 보유가 **트랜잭션 전체** |
| **상대값 UPDATE** | `SET holdTotal = holdTotal + 30` | 읽은 값으로 **판단**을 못 한다 |

**세 번째가 왜 안 되나**: 우리는 *"가용잔액이 충분한가"* 를 **판단**해야 한다.
상대값 UPDATE는 값을 더할 뿐 조건을 못 본다.

### 우리 자리

**E1 승인**이 정확히 이 패턴이다. 그리고 **ADR-007이 ORM 단일 경로를 의무화**해서 이 패턴이 **강제**된다.

**막는 것**: ADR-012 **W-5**(낙관적 락) + **W-7**(아키텍처 테스트로 버전 필드 존재 강제)

> ⚠️ **W-7이 왜 필요한가**: `@Version` 을 안 붙여도 **컴파일이 되고 테스트도 통과한다.**
> 동시 요청이 없으면 아무 문제가 없기 때문이다. **부하가 걸릴 때만 틀린다.**

## F-02. 데드락 — 서로를 기다린다

### 원리

```
T1: A를 잠금 → B를 원함
T2: B를 잠금 → A를 원함
     → 둘 다 영원히 기다린다
```

InnoDB는 이것을 **자동 탐지**해서 한쪽을 죽인다(`ERROR 1213`).
즉 **데드락 자체는 장애가 아니라 정상 동작**이다 — 문제는 **빈도**다.

### 왜 일어나나 — 세 가지 뿌리

#### (1) 락 순서 불일치

```
T1: 계좌 → 카드
T2: 카드 → 계좌      ★ 순서가 다르면 교차한다
```

**모두가 같은 순서로 잠그면 데드락이 원천적으로 불가능하다.**
그래서 락 순서를 정한다.

#### (2) 중복 키 INSERT의 S락 — 덜 알려진 것

**MySQL 공식 문서 §17.7.3**이 명시한다:

```
같은 유니크 키로 3개 세션이 동시에 INSERT
  세션1  INSERT 성공, X락 보유
  세션2  중복 발견 → ★ S락을 잡고 대기
  세션3  중복 발견 → ★ S락을 잡고 대기
  세션1  ROLLBACK
  세션2·3  둘 다 X락으로 승격하려 함 → 서로의 S락 때문에 대기 → 데드락
```

> ★ **멱등 처리가 정확히 이 패턴이다.** *"같은 키면 무시"* 를 INSERT로 구현하면
> 동시 요청에서 데드락이 난다.

#### (3) 갭 락 vs INSERT

RR에서 범위 조회는 **그 사이의 빈 공간(gap)까지 잠근다** — 팬텀을 막기 위해서다.

```
T1: DELETE FROM x WHERE id BETWEEN 10 AND 20   → 10~20 갭을 잠근다
T2: INSERT INTO x VALUES (15)                   → 대기
```

**ideeli 사례**가 이것이다 — `autoinc_lock_mode`를 바꿔 한 문제를 풀었더니
**갭 락 충돌로 재발**했고, 결국 **RC로 내려서** 해소했다(RC는 갭 락을 거의 안 쓴다).

### 우리 자리

| 뿌리 | 우리 |
|---|---|
| (1) 락 순서 | `aggregates/README.md` 락 순서 ①미수 → ⑤배치 |
| (2) 중복 키 INSERT | ★ **망취소** — BR-01이 정상 경로로 규정했고, 동시 중복이 전제다 |
| (3) 갭 락 | E3·E4가 미수를 **범위로** 고른다 (FIFO) |

**막는 것**: ADR-012 **§2.4**(쓰기 순서) · **W-12**(INSERT 후 중복이면 조회) · **§2.2**(E1·E2는 RC)

## F-03. 커넥션 풀 고갈 — 증설했더니 더 느려진다

### 원리

앱은 DB 커넥션을 **풀에 미리 만들어 두고 빌려 쓴다.**

```
요청 → 풀에서 커넥션 대여 → 쿼리 → 반납
풀이 비면 → 대기 → 타임아웃
```

**총 커넥션 = 앱 인스턴스 수 × 풀 크기.** DB에는 `max_connections` 상한이 있다.

```
인스턴스 4대 × 풀 20 = 80
인스턴스 8대 × 풀 20 = 160   ★ DB 상한이 150이면 여기서 죽는다
```

> ★ **앱을 늘리면 DB가 먼저 죽는다.** `study/10` §4가 말한 *"상태 있는 것은 늘려도 안 된다"* 가 이것이다.

### 더 나쁜 것 — 한 작업이 커넥션을 둘 잡는다

**우아한형제들 사례**:

```
컨슈머 스레드 16개, 풀 크기 10

한 작업이 커넥션을 두 개 잡는다
  ① 비즈니스 트랜잭션용
  ② ★ JPA GenerationType.AUTO 의 채번용 (별도 커넥션)

스레드 10개가 각각 ①을 잡음 → 풀 소진
→ 10개 전부 ②를 기다림 → ②를 줄 커넥션이 없음
→ ★ 데드락. 아무도 반납하지 않는다
```

**풀 크기를 늘려도 안 풀린다** — 스레드가 늘면 같은 일이 반복된다.
**한 작업이 커넥션 하나만 쓰게** 만들어야 한다.

### 우리 자리

배치와 실시간이 **같은 DB**를 친다(ADR-010).

**막는 것**: ★ **ADR-007 W-1** — 자금 경로에 JDBC가 없으므로 **두 번째 커넥션이 생길 수 없다.**

> ★ **이것은 예상 밖의 이득이다.** W-1은 flush 타이밍 때문에 만든 규칙인데
> **커넥션 이중 점유까지 막는다.**
>
> ⚠️ **다만 풀 분리 규칙은 아직 없다** — 대사 배치가 실시간 풀을 먹을 수 있다.

## F-04. 복제 지연 — 방금 쓴 것이 안 보인다

### 원리

```
쓰기 → Primary
읽기 → Replica (복제)

Primary 커밋 → binlog → 네트워크 → Replica 적용
                          ↑
                    이 사이가 "복제 지연"
```

평시 수 ms, 부하가 걸리면 **초 단위**, 대량 DDL 중에는 **시간 단위**가 된다.

### 왜 치명적인가 — 멱등 조회의 경우

```
1회차 요청  → Primary 에 멱등 레코드 INSERT + 결제 처리
2회차 요청  → Replica 에서 멱등 조회
              ★ 아직 복제 안 됨 → "없다" → 다시 결제
              → 이중 결제
```

> ★ **Airbnb Orpheus** 가 이것을 명시했다 — *"replica에서 멱등 조회를 하면 이중 결제가 난다."*
> 그래서 **멱등 조회는 마스터에서만** 한다.

### 같은 뿌리의 다른 얼굴

| 증상 | 실제 |
|---|---|
| *"저장했는데 목록에 없다"* | read-your-writes 위반 |
| *"잔액이 방금 것보다 적다"* | monotonic read 위반 |
| **멱등이 안 먹는다** | ★ 위 두 개보다 훨씬 비싸다 |

### 우리 자리

**막는 것**: ADR-007 **W-2**(자금 판단은 쓰기 데이터소스에서만) · **HA-1**

> ★ **HA-1이 이것까지 덮는다** — *"인스턴스 로컬 상태로 자금 판단 금지"* 에서
> **복제본도 "진짜가 아닌 값"** 이라는 범주가 같다.

## F-05. 롱 트랜잭션 — undo가 쌓여 전체가 느려진다

### 원리 — undo와 purge

MVCC가 옛 버전을 보여주려면 **옛 버전을 어딘가 보관**해야 한다. 그것이 **undo 로그**다.

```
UPDATE 하면
  → 새 값을 쓰고
  → 옛 값을 undo 에 남긴다
  → 아무도 옛 값을 안 보게 되면 purge 스레드가 지운다
```

**"아무도 안 본다"의 판정 기준이 문제다.**

```
오래 열린 읽기 트랜잭션이 하나 있으면
  → 그 트랜잭션이 시작한 시점 이후의 undo 를 전부 남겨야 한다
  → purge 가 멈춘다
  → undo 가 계속 쌓인다  (History List Length)
```

### 왜 전체가 느려지나

```
SELECT 하나가 최신 행을 읽었는데 내 스냅샷보다 새 버전이면
  → undo 를 거슬러 올라가 옛 버전을 재구성한다
  → undo 체인이 길수록 이 작업이 오래 걸린다
  → ★ 쓰기와 무관한 SELECT 도 느려진다
```

> ★ **Percona 사례**: 940개 ACTIVE 트랜잭션 → **History List Length 6,000,000**
> → SELECT 지속 저하. kill 후 793으로 회복.

### 우리 자리

**ADR-011 §1**이 *"M9·M10·M11은 코어 안, 한 읽기 트랜잭션"* 이라고 적었다.
매 영업일 그 트랜잭션이 오래 열리면 **purge가 멈춘다.**

**막는 것**: ADR-012 **§2.2** — 배치는 **RC + 짧은 트랜잭션**

> ⚠️ **RC라도 긴 트랜잭션은 위험하다.** RC는 문마다 스냅샷을 새로 뜨므로
> **문 단위로는** 안전하지만, 트랜잭션이 열려 있는 한 그 트랜잭션 자체의 undo 는 남는다.
> **짧게 끊는 것이 진짜 답이다.**

## F-06. 마이그레이션 — 온라인 DDL이 온라인이 아니다

### 원리 — DDL 알고리즘 세 가지

| 알고리즘 | 무엇 | 제약 |
|---|---|---|
| **INSTANT** | 메타데이터만 바꾼다 | ★ **컬럼 추가(맨 뒤)·기본값 변경 정도.** 인덱스·타입 변경 불가 |
| **INPLACE** | 테이블을 다시 만들되 **원본에서** | 쓰기 대부분 허용. **오래 걸린다** |
| **COPY** | 새 테이블에 복사 | ★ **쓰기 차단** |

### 왜 "온라인인데 장애"가 나나

#### (1) 복제본에서는 논블로킹이 아니다

```
Primary   INPLACE DDL 3시간 실행 (쓰기 계속 받음)
          → binlog 에 DDL 이 하나의 이벤트로 기록
Replica   그 DDL 을 받아서 실행 → ★ 3시간
          그동안 뒤의 이벤트를 못 적용
          → 복제 지연 3시간
```

> **PlanetScale**이 이것을 명시했다. **F-04(복제 지연)가 여기서 발생한다.**

#### (2) 컬럼 드롭이 앱을 깨뜨린다

```
"이 컬럼 안 쓴다" → DROP COLUMN
  → ★ ORM 이 SELECT 에 컬럼 이름을 전부 나열한다
  → 배포 안 된 인스턴스가 그 컬럼을 부른다 → 즉시 실패
```

> ★ **GitHub 2025-08** 이 이것을 **한 달에 두 번** 겪었다.

### 답 — expand-contract

```
① expand    새 컬럼 추가 (구 버전도 동작)
② 배포      앱이 둘 다 다룰 수 있게
③ 이행      데이터 백필
④ 배포      앱이 새 것만 쓰게
⑤ contract  옛 컬럼 제거
```

**각 단계 사이에 "전 인스턴스 배포 완료"를 기다린다.** 그것이 없으면 F-17이 된다.

### 우리 자리

**HA-5**가 *"스키마 변경은 expand-contract"* 라고 선언한다.

**막는 것**: ⚠️ **선언뿐 — 절차를 소유한 ADR이 없다.** DDL 도구·백필 방식·대기 판정이 미정.

## F-07. ORM flush 타이밍 — 같은 트랜잭션인데 옛 값을 읽는다

### 원리 — 영속성 컨텍스트

ORM은 변경을 **바로 DB에 안 보낸다.** 메모리(영속성 컨텍스트)에 모아뒀다가 **flush** 시점에 보낸다.

```
a.hold(30)        → 메모리에만. DB는 아직 모른다
...
flush             → 여기서 UPDATE 가 나간다
commit            → 커밋
```

**flush 시점은 셋이다**: ① 커밋 직전 ② JPQL/Criteria 실행 직전(자동) ③ 명시 호출

### 왜 깨지나

```
a.hold(30);                              // 메모리에만
jdbcTemplate.query("SELECT holdTotal");  // ★ DB 직접 조회 — flush 안 일어남
                                         //   → 옛 값 0 을 읽는다
```

**JPQL이면 ②가 발동해 자동 flush**되지만, **JdbcTemplate은 ORM 흐름 밖**이라 발동하지 않는다.

> ★ **"같은 트랜잭션 안인데 내가 방금 쓴 게 안 보인다"** — 가장 헷갈리는 증상이다.

### 우리 자리

**막는 것**: ★ **ADR-007 W-1** — 자금 경로에서 **ORM 외 접근을 금지**하고,
그것을 **모듈 분리로** 강제한다(JDBC 타입이 그 모듈에 없다).

> ★ *"flush를 꼭 하세요"* 라는 규약이 아니라 **혼용 자체를 불가능하게** 만든 것이 핵심이다.

## F-08. 채번·시퀀스 병목

### 원리

전역 유일 번호(승인번호·전표번호)를 만드는 방법마다 성격이 다르다.

| 방법 | 병목 | 순서 |
|---|---|---|
| **AUTO_INCREMENT** | 테이블 단위 락 (모드에 따라) | 보장 |
| **중앙 시퀀스 테이블** | ★ **한 행에 UPDATE 집중** | 보장 |
| **UUID** | 없음 | ❌ + **인덱스 단편화** |
| **Snowflake류** | 없음 | 시간순 대략 |
| **채번 블록 할당** | 낮음 (N개씩 미리) | 블록 내 보장 |

### 왜 문제가 되나

**중앙 시퀀스는 한 행을 모두가 UPDATE 한다** — 인스턴스를 늘려도 **그 행이 직렬화 지점**이다.
그리고 F-03에서 본 것처럼 **채번용 커넥션을 따로 잡으면** 풀 데드락까지 간다.

**UUID는 병목이 없지만** 랜덤이라 B-tree 인덱스에 **삽입이 흩어져** 페이지 분할이 잦다.

### 우리 자리

승인번호(BR-17)·전표번호. **형식이 아직 미확정**(Phase 4).

**막는 것**: ⚠️ **미정** — Phase 4에서 채번 방식을 정할 때 **이 표를 근거로** 고른다.
