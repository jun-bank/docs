# 05. 아키텍처 스타일과 아키텍처 패턴

> 추상화 레벨: ① 아키텍처 설계
> 책 대응: 2.4.3 아키텍처 스타일과 아키텍처 패턴 (90쪽) · 3.3 시스템 아키텍처 선정 · 3.4 애플리케이션 아키텍처 선정

**이 주제가 jun-bank의 MSA 채택 근거로 직결된다.** 여기를 채우고 나서 `architecture/decisions/`의 ADR 를 확정한다.

---

## 0. 용어 먼저

| 용어 | 뜻 |
|---|---|
| **아키텍처 스타일 (Style)** | 시스템 전체의 **구조적 골격**. "이 시스템은 무슨 모양인가"에 대한 답 |
| **아키텍처 패턴 (Pattern)** | 스타일 안에서 **반복되는 문제의 해법**. 스타일보다 작고 구체적 |
| **디자인 패턴 (Design Pattern)** | 클래스·객체 수준의 해법 (study/04) |
| **배포 단위 (Deployment Unit)** | 독립적으로 배포·기동되는 덩어리. jar 하나, 컨테이너 하나 |
| **결합도 (Coupling)** | 한쪽을 바꿀 때 다른 쪽도 바꿔야 하는 정도 |
| **바운디드 컨텍스트 (Bounded Context)** | 하나의 용어 체계가 일관되게 통하는 경계. DDD 용어 |
| **결과적 일관성 (Eventual Consistency)** | 지금은 다를 수 있으나 **결국** 같아지는 일관성 |
| **강한 일관성 (Strong Consistency)** | 읽으면 **항상** 최신 값이 보이는 일관성 |
| **탄력성 (Elasticity)** | 부하 변화에 맞춰 빠르게 늘리고 줄이는 능력 |
| **장애 격리 (Fault Isolation)** | 한 부분의 장애가 다른 부분으로 번지지 않는 성질 |

### 스타일 vs 패턴의 관계

```
아키텍처 스타일 (마이크로서비스)
    └── 아키텍처 패턴 (Saga, Outbox, API Gateway, Circuit Breaker, CQRS)
            └── 디자인 패턴 (Command, Observer, Strategy)
```

세 층은 **추상화 레벨이 다르다.** 마이크로서비스는 스타일이고, 그 안에서 분산 트랜잭션 문제를 푸는 Saga는 패턴이며, Saga의 보상 단계를 구현하는 Command는 디자인 패턴이다.

### 스타일은 선택하는 것인가 발견하는 것인가

**둘 다다.** 처음에는 선택하지만, 시간이 지나면 시스템이 **실제로 어떤 모양인지**가 드러난다. "우리는 마이크로서비스입니다"라고 선언했지만 실제로는 서비스들이 하나의 DB를 공유하고 함께 배포된다면, 그건 **분산 모놀리스(Distributed Monolith)** 라는 최악의 조합이다 — 분산의 대가는 다 치르면서 이점은 하나도 못 얻는 상태.

# 1. 모놀리식 아키텍처

> **하나의 배포 단위 안에서 구조를 나눈다.** 책 3.4 "애플리케이션 아키텍처" 영역.

⚠️ **"모놀리식 = 나쁘다"는 오해**다. 모놀리식은 **배포 단위가 하나**라는 뜻일 뿐, 내부가 엉망이라는 뜻이 아니다. 잘 나뉜 모놀리식(모듈러 모놀리스)이 엉성한 마이크로서비스보다 훨씬 낫다.

## 1.1 레이어드 아키텍처 (Layered)

### 구조

```
┌─────────────────────────────┐
│  프레젠테이션 (Presentation) │  ← HTTP, 화면
├─────────────────────────────┤
│  비즈니스 (Business)         │  ← 업무 규칙
├─────────────────────────────┤
│  영속화 (Persistence)        │  ← 데이터 접근
├─────────────────────────────┤
│  데이터베이스 (Database)      │
└─────────────────────────────┘
        ↓ 의존 방향은 아래로만
```

가장 흔하고, **아무 결정도 안 하면 자연히 도달하는** 기본형이다.

### 층 간 규칙 — 엄격 vs 완화

| 방식 | 뜻 | 장단 |
|---|---|---|
| **엄격(Closed) 레이어** | 반드시 바로 아래 층만 호출 | 변경 격리는 좋으나 단순 조회도 전 층을 거침 |
| **완화(Open) 레이어** | 층을 건너뛸 수 있음 | 편하지만 층의 의미가 흐려짐 |

### 싱크홀 안티패턴 (Architecture Sinkhole)

요청이 여러 층을 통과하는데 **각 층이 아무 일도 하지 않고 그냥 아래로 넘기기만 하는 것**을 말한다.

```java
// 컨트롤러 → 서비스 → 리포지토리, 각 층이 그냥 전달만 한다
public UserResponse getUser(String id) { return userService.getUser(id); }   // 아무 일도 안 함
public UserResult getUser(String id)   { return userRepository.findById(id); } // 아무 일도 안 함
```

경험칙으로 **전체 요청의 20% 이하**면 정상이다. 80%가 싱크홀이면 층이 과하다는 뜻이다.

### 강점 / 약점

| 강점 | 약점 |
|---|---|
| 이해하기 쉽다 (누구나 안다) | **변경이 수직으로 관통**한다 — 기능 하나 추가에 전 층을 건드림 |
| 관심사 분리가 명확 | 도메인이 아니라 **기술로 나뉜다** — "결제"가 3개 층에 흩어짐 |
| 개발 초기 속도가 빠름 | 배포 단위가 하나라 **부분 확장 불가** |

### 헥사고날·클린 아키텍처와의 관계

레이어드의 **의존 방향 문제**를 고친 것이 헥사고날(포트&어댑터)·클린 아키텍처다.

```
레이어드:  비즈니스 ──의존──▶ 영속화        (비즈니스가 DB를 안다)
헥사고날:  비즈니스 ──소유──▶ 포트 ◀──구현── 영속화   (DB가 비즈니스를 안다)
```

**핵심 차이**: 헥사고날은 **도메인을 중심에 두고 기술을 바깥으로 밀어낸다.** 층이 위아래가 아니라 안팎이 된다. (study/01의 DIP 참조)

**jun-bank**: 현재 모든 서비스가 헥사고날 구조(`domain / application / infrastructure / presentation`)를 쓰고 있다.

## 1.2 파이프라인 아키텍처 (Pipeline / Pipes and Filters)

### 구조

```
[입력] → [필터1] → [파이프] → [필터2] → [파이프] → [필터3] → [출력]
         변환         전달       변환                 변환
```

- **필터(Filter)**: 하나의 변환만 수행하는 독립적 단위. 상태를 갖지 않는다
- **파이프(Pipe)**: 필터 사이의 단방향 통로

### 어떤 문제에 맞는가

**데이터가 일련의 변환을 순서대로 거치는 처리.** 유닉스 파이프(`cat file | grep x | sort | uniq`)가 원형이다.

```java
// 정산 파일 처리 파이프라인
public interface SettlementFilter {
    SettlementBatch apply(SettlementBatch input);
}

public class ParseFilter      implements SettlementFilter { /* 원문 → 레코드 */ }
public class ValidateFilter   implements SettlementFilter { /* 형식·필수값 검증 */ }
public class MatchFilter      implements SettlementFilter { /* 원거래 매칭 */ }
public class LedgerPostFilter implements SettlementFilter { /* 원장 반영 */ }
public class ReportFilter     implements SettlementFilter { /* 결과 집계 */ }

@Service
@RequiredArgsConstructor
public class SettlementPipeline {
    private final List<SettlementFilter> filters;   // 순서대로 주입

    public SettlementBatch run(SettlementBatch input) {
        SettlementBatch current = input;
        for (SettlementFilter filter : filters) {
            current = filter.apply(current);
        }
        return current;
    }
}
```

### 강점 / 약점

| 강점 | 약점 |
|---|---|
| 각 필터가 **독립적으로 테스트** 가능 | 트랜잭션 처리에 부적합 (중간 실패 처리가 까다로움) |
| 필터 **재조합·재사용**이 쉬움 | 필터 간 데이터 형식 합의가 필요 |
| 병렬화하기 좋음 | 흐름 전체를 한눈에 보기 어려움 |

### jun-bank 적용 가능성

**정산·대사 배치에 잘 맞는다.** 파일 파싱 → 검증 → 매칭 → 원장 반영 → 리포트가 정확히 파이프라인 형태다.

단, **부분 실패 시 재처리**(품질 시나리오 QS-09)를 어떻게 할지가 관건이다. 필터마다 처리 지점을 기록해야 재개할 수 있다.

## 1.3 마이크로커널 아키텍처 (Microkernel / Plug-in)

### 구조

```
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ 플러그인 A│  │ 플러그인 B│  │ 플러그인 C│
        └────┬─────┘  └────┬─────┘  └────┬─────┘
             └─────────────┼─────────────┘
                    ┌──────▼──────┐
                    │  코어 시스템  │  ← 최소한의 공통 로직
                    └─────────────┘
```

- **코어(Core)**: 변하지 않는 최소 기능 + 플러그인 등록·실행 메커니즘
- **플러그인(Plug-in)**: 독립적으로 추가·제거되는 기능 단위

### 어떤 문제에 맞는가

**"종류가 계속 늘어나는" 영역.** IDE(IntelliJ 플러그인), 브라우저 확장, 결제 수단이 대표적이다.

```java
// 코어가 정의하는 계약
public interface PaymentMethodPlugin {
    PaymentMethodType type();
    AuthorizationResult authorize(AuthorizeCommand command);
    void cancel(CancelCommand command);
}

// 플러그인들 — 새 결제수단은 클래스 추가만
@Component
public class DebitCardPlugin implements PaymentMethodPlugin {
    public PaymentMethodType type() { return PaymentMethodType.DEBIT_CARD; }
    public AuthorizationResult authorize(AuthorizeCommand c) { /* 즉시 출금 */ }
    public void cancel(CancelCommand c) { /* 즉시 반환 */ }
}

@Component
public class CreditCardPlugin implements PaymentMethodPlugin {
    public PaymentMethodType type() { return PaymentMethodType.CREDIT_CARD; }
    public AuthorizationResult authorize(AuthorizeCommand c) { /* 여신 한도 확인 */ }
    public void cancel(CancelCommand c) { /* 청구 취소 */ }
}

// 코어 — 플러그인이 늘어도 이 코드는 바뀌지 않는다 (OCP)
@Service
@RequiredArgsConstructor
public class PaymentKernel {
    private final List<PaymentMethodPlugin> plugins;

    public AuthorizationResult authorize(AuthorizeCommand command) {
        return plugins.stream()
            .filter(p -> p.type() == command.paymentMethodType())
            .findFirst()
            .orElseThrow(() -> new UnsupportedPaymentMethodException(command.paymentMethodType()))
            .authorize(command);
    }
}
```

### 강점 / 약점

| 강점 | 약점 |
|---|---|
| **확장이 코어를 건드리지 않는다** | 코어의 계약(인터페이스) 설계가 어렵다 |
| 플러그인별 독립 개발·테스트 | 계약을 바꾸면 **모든 플러그인이 깨진다** |
| 필요한 것만 로드 가능 | 플러그인 간 협력이 필요해지면 구조가 무너진다 |

### jun-bank 적용 가능성

**결제 수단(체크/신용/포인트), 인증 방식, 정산 파일 포맷**처럼 종류가 늘어나는 영역에 맞는다. 다만 **코어 계약을 정확히 그을 수 있을 때만** 유효하다 — 체크카드와 신용카드의 승인 흐름이 실제로 같은 계약에 담기는지 먼저 확인해야 한다.

# 2. 분산형 아키텍처

> **여러 배포 단위로 나눈다.** 책 3.3 "시스템 아키텍처" 영역.

⚠️ **공통 대가**: 분산형은 예외 없이 아래를 지불한다.
- 네트워크는 **느리고, 불안정하고, 실패한다**
- 트랜잭션이 **한 번에 끝나지 않는다**
- 디버깅이 **로그 한 곳으로 안 끝난다**
- 배포·운영 대상이 **N배**가 된다

이 대가를 상쇄할 이유가 없으면 분산하지 않는 게 맞다.

## 2.1 서비스 기반 아키텍처 (Service-Based)

### 구조

```
     [API Gateway / UI]
            │
   ┌────────┼────────┐
   ▼        ▼        ▼
[서비스A] [서비스B] [서비스C]     ← 굵직한 4~12개 단위, 독립 배포
   └────────┼────────┘
       ┌────▼────┐
       │  공유 DB │              ← ★ DB는 하나
       └─────────┘
```

### 마이크로서비스와의 결정적 차이

**DB를 공유한다.** 이 한 가지가 모든 것을 바꾼다.

| | 서비스 기반 | 마이크로서비스 |
|---|---|---|
| DB | **공유** | 서비스별 분리 |
| 트랜잭션 | **로컬 ACID로 끝남** | 분산 트랜잭션 |
| 서비스 크기 | 굵다 (도메인 묶음) | 잘다 (바운디드 컨텍스트) |
| 서비스 수 | 4~12 | 수십~수백 |
| 데이터 정합성 | **쉽다** | 어렵다 |

### 강점 / 약점

| 강점 | 약점 |
|---|---|
| **트랜잭션이 여전히 단순** — Saga가 필요 없다 | DB 스키마 변경이 **모든 서비스에 영향** |
| 독립 배포의 이점은 얻는다 | 서비스 간 결합이 DB를 통해 남는다 |
| 운영 부담이 MSA보다 훨씬 작다 | 부분 확장이 DB 병목에 막힌다 |
| **MSA로 가는 중간 단계로 최적** | |

### "MSA로 가기 전 중간 단계"로서의 의미

실무에서 가장 저평가된 스타일이다. 대부분의 팀에게 **마이크로서비스보다 이쪽이 정답**인 경우가 많다. 모놀리식의 배포 문제는 풀면서 분산 트랜잭션의 지옥은 피하기 때문이다.

> **jun-bank 판단 포인트**: 실무 프로젝트라면 이게 최선이다. 다만 **분산 트랜잭션 문제가 발생하지 않으므로 학습 목표의 절반이 사라진다.**

## 2.2 이벤트 기반 아키텍처 (Event-Driven)

### 두 가지 토폴로지

**① 브로커 토폴로지 (Broker Topology)** — 중앙 조율자 없음

```
[결제서비스] ─event─▶ [브로커] ─▶ [원장서비스] ─event─▶ [브로커] ─▶ [알림서비스]
                                                                  └─▶ [정산서비스]
```

각 서비스가 이벤트를 듣고 **스스로 다음 행동을 결정**한다. 전체 흐름이 **어느 코드에도 통째로 적혀 있지 않다.** = **코레오그래피** (→ study/06)

**② 중재자 토폴로지 (Mediator Topology)** — 중앙 조율자 있음

```
                  ┌──────────────┐
[요청] ──────────▶│   중재자      │
                  └───┬───┬───┬──┘
                      ▼   ▼   ▼
                   [A] [B] [C]
```

중재자가 순서를 알고 각 서비스를 호출한다. = **오케스트레이션**

### 강점 / 약점

| 강점 | 약점 |
|---|---|
| **높은 확장성·응답성** — 비동기라 대기하지 않음 | **결과적 일관성**을 감수해야 함 |
| 서비스 간 결합이 매우 낮음 | 전체 흐름 파악이 어렵다 |
| 새 소비자 추가가 기존 코드를 안 건드림 | **디버깅이 극도로 어렵다** |
| 장애 격리가 좋음 | 이벤트 순서·중복 처리 문제 |

### 결과적 일관성을 감수한다는 뜻

```
14:00:00.000  결제 승인 완료 (card-service)
14:00:00.010  이벤트 발행
14:00:00.150  원장 반영 (ledger-service)
              ↑
     이 150ms 동안 "승인은 됐는데 원장엔 없는" 상태가 존재한다
```

**이 중간 상태가 사용자에게 보이면 어떻게 설명할 것인가**가 설계 문제가 된다. 결제 도메인에서는 "결제 예정" vs "결제 완료" 표시로 이걸 다룬다(제품 정의서 S8).

### 디버깅이 왜 어려워지는가

동기 호출은 **스택 트레이스 하나**로 끝난다. 이벤트 기반은 발행 시점과 소비 시점이 **다른 스레드, 다른 프로세스, 다른 시각**이다. 그래서 **분산 추적(distributed tracing)이 선택이 아니라 필수**가 된다. (품질 시나리오 QS-11)

## 2.3 공간 기반 아키텍처 (Space-Based)

### 구조

```
   [요청] ──▶ [메시징 그리드] ──▶ 부하 분산
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   [처리유닛1]  [처리유닛2]  [처리유닛3]      ← 각자 인메모리 데이터 복제본을 가짐
        └───────────┼───────────┘
              [데이터 복제 엔진]
                    │
                    ▼
              [데이터베이스]                 ← 비동기로만 기록. 읽기 경로에 없다
```

**핵심 발상**: **DB를 요청 처리 경로에서 제거한다.** 대부분의 확장성 병목은 DB이므로, 처리 유닛이 인메모리 데이터로 작업하고 DB에는 나중에 비동기로 쓴다.

"공간(Space)"은 튜플 스페이스(tuple space)라는 분산 공유 메모리 개념에서 왔다.

### 어떤 문제에 맞는가

**극단적이고 예측 불가능한 부하.** 콘서트 티켓 오픈, 블랙프라이데이 세일, 실시간 입찰.

### 강점 / 약점

| 강점 | 약점 |
|---|---|
| **극한의 확장성·탄력성** | 구현 복잡도가 매우 높다 |
| DB 병목 제거 | **데이터 정합성 보장이 어렵다** |
| 응답 시간이 매우 빠름 | 인메모리 데이터 유실 위험 |
| | 캐시 일관성 문제 |

### 금융 원장에 쓸 수 있는가

**대체로 아니다.** 이 스타일은 **강한 일관성을 포기하는 대가로 확장성을 얻는다.** 원장은 정확히 그 반대를 요구한다.

> 다만 **조회 경로에는 부분 적용 가능**하다. 잔액 조회 같은 읽기는 캐시 그리드로, 승인·기록 같은 쓰기는 강한 일관성 경로로 나누는 방식(CQRS와 결합).

**jun-bank**: 품질 속성 1위가 기능 정확성이므로 채택하지 않는다. 개념만 안다.

## 2.4 서비스 지향 아키텍처 (SOA)

### 구조

```
   [서비스A]   [서비스B]   [서비스C]
       │           │           │
       └───────────┼───────────┘
            ┌──────▼──────┐
            │     ESB     │   ← Enterprise Service Bus
            │ 라우팅·변환  │      모든 통신이 여기를 지난다
            │ 오케스트레이션│
            └─────────────┘
```

**ESB(엔터프라이즈 서비스 버스)**: 서비스 간 통신을 중개하면서 프로토콜 변환, 메시지 변환, 라우팅, 오케스트레이션까지 담당하는 중앙 미들웨어.

### MSA와 무엇이 같고 다른가

| | SOA | 마이크로서비스 |
|---|---|---|
| 서비스 분리 | ✅ | ✅ |
| 재사용 강조 | **매우 강함** (전사 재사용) | 약함 (**중복 허용**) |
| 통신 | **ESB 경유** (스마트 파이프) | 직접 통신 (**덤 파이프, 스마트 엔드포인트**) |
| 데이터 | 공유 DB 흔함 | 서비스별 분리 |
| 거버넌스 | 중앙집중 | 분산 (팀 자율) |
| 크기 | 크다 (전사 업무 단위) | 작다 (바운디드 컨텍스트) |

### 왜 쇠퇴했다고 평가받는가

1. **ESB가 단일 장애점이자 병목**이 되었다 — 모든 통신이 지나가니까
2. **ESB가 비즈니스 로직을 흡수**했다 — 라우팅 규칙에 업무 규칙이 들어가면서 아무도 이해 못하는 블랙박스가 됨
3. **중앙 거버넌스가 개발 속도를 죽였다** — 서비스 하나 바꾸려면 ESB 팀 승인 필요
4. 벤더 종속 — 상용 ESB 제품에 묶임

> **교훈**: 마이크로서비스의 "덤 파이프, 스마트 엔드포인트" 원칙은 SOA의 실패에서 나왔다. **미들웨어를 똑똑하게 만들지 마라.**

**jun-bank 연결**: API Gateway가 ESB화되지 않도록 주의해야 한다. 게이트웨이는 **라우팅·인증까지만** 하고 업무 로직을 넣지 않는다.

## 2.5 마이크로서비스 아키텍처 (Microservices)

### 구조

```
              [API Gateway]
                    │
       ┌────────┬───┴────┬────────┐
       ▼        ▼        ▼        ▼
   [서비스A] [서비스B] [서비스C] [서비스D]
       │        │        │        │
     [DB A]  [DB B]   [DB C]   [DB D]      ← ★ 서비스마다 자기 DB
       └────────┴───┬────┴────────┘
              [메시지 브로커]              ← 비동기 통신
```

### 핵심 원칙

| 원칙 | 뜻 |
|---|---|
| **서비스별 DB** | 다른 서비스의 DB를 직접 읽지 않는다. **가장 중요하고 가장 자주 어겨지는 원칙** |
| **독립 배포** | 다른 서비스를 기다리지 않고 배포할 수 있다 |
| **바운디드 컨텍스트 정렬** | 서비스 경계 = 도메인 경계. 기술 경계가 아니다 |
| **중복 허용** | 결합을 피하기 위해 코드·데이터 중복을 감수한다 (study/02의 N↔L 충돌) |
| **탈중앙 거버넌스** | 서비스마다 다른 기술 선택 가능 |

### 강점 / 약점

| 강점 | 약점 |
|---|---|
| 서비스별 독립 배포·확장 | **분산 트랜잭션** — Saga·보상 필요 |
| 장애 격리 | 네트워크 실패를 상시 다뤄야 함 |
| 기술 다양성 | 운영 복잡도 폭증 (배포·모니터링·로그) |
| 팀 자율성 | 데이터 정합성 보장이 어렵다 |
| 도메인 경계가 물리적으로 강제됨 | **로컬 개발 환경이 무거워진다** |
| | 통합 테스트가 어렵다 |

### 치르는 대가 목록 (구체적으로)

1. **분산 트랜잭션**: 계좌 차감 + 원장 기록이 다른 서비스면 하나의 트랜잭션으로 못 묶는다 → Saga, 보상, 멱등성
2. **네트워크 실패**: 타임아웃, 부분 실패, "상태 불명" → 재시도, 서킷 브레이커, 망취소
3. **데이터 조회**: "이 사용자의 모든 거래"를 보려면 여러 서비스를 조합해야 한다 → API 조합, CQRS 읽기 모델
4. **운영**: 서비스 11개 = 로그 11곳, 메트릭 11곳, 배포 11번 → 중앙 로깅, 분산 추적 필수
5. **개발 환경**: 로컬에서 전부 띄워야 한다 → Docker Compose, 메모리 요구량 증가 (jun-bank 제약 TC-5)

### 언제 쓰면 안 되는가

- **도메인 경계가 아직 불명확할 때** — 잘못 그은 경계는 모놀리식보다 고치기 훨씬 어렵다. **"모놀리스 우선(Monolith First)"** 이 널리 권장되는 이유
- **팀이 작을 때** — 서비스 수 > 개발자 수면 운영이 불가능
- **강한 일관성이 핵심일 때** — 금융 코어 원장 같은 영역
- **배포 자동화가 없을 때** — 수동 배포로 서비스 11개는 지옥

# 4. 스스로 답할 질문

1. **모놀리식과 분산형은 배타적 선택인가?** 한 시스템 안에서 섞일 수 있는가?
   - 힌트: 분산형은 **시스템 레벨**(①), 레이어드·헥사고날은 **애플리케이션 레벨**(②) 이야기다. 마이크로서비스 각각이 내부적으로 헥사고날일 수 있다 → `project-workflow/phase0/`의 추상화 레벨 규약
2. **"MSA를 쓰는 이유"로 자주 언급되는 것들 중 실제로는 모놀리식으로도 되는 것**은?
   - 후보: 모듈 분리, 팀 분리, 도메인 경계, 코드 재사용, 기술 부채 격리
3. 1인 개발·학습 목적이라는 제약에서 MSA의 대가는 얼마나 큰가?
4. **서비스 기반 아키텍처(DB 공유)가 jun-bank에 더 맞을 가능성은 없는가?**
   - 이 질문에 정직하게 답하는 것이 ADR-0001의 핵심이다
5. 결제 도메인은 강한 일관성을 요구하는데, 이벤트 기반의 결과적 일관성과 어떻게 공존시키는가?
   - 힌트: **모든 것에 결과적 일관성을 쓰지 않는다.** 승인 판단은 강한 일관성, 알림·집계는 결과적 일관성
6. 스타일을 **나중에 바꿀 수 있는가?** 바꾸는 비용은 무엇에 비례하는가?
   - 힌트: 데이터 소유권의 분리 정도
7. **분산 모놀리스**란 무엇이고, 어떻게 알아채는가?
   - 힌트: 서비스를 하나만 배포할 수 없다면 이미 그것이다
