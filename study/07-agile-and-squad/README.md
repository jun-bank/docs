# 07. 애자일과 스쿼드 방식

> 추상화 레벨: 조직·프로세스 (코드 레벨이 아님)
> 책 대응: 2.1 소프트웨어 개발 프로세스 · 4.3 유스케이스 중심의 아키텍처 구현

**왜 아키텍처 문서에 조직 이야기가 들어오는가**: 콘웨이의 법칙 때문이다. 조직 구조와 아키텍처는 서로를 결정한다. 이걸 모르고 아키텍처만 그리면 문서와 현실이 갈라진다.

## 0. 용어 먼저

| 용어 | 뜻 |
|---|---|
| **애자일 (Agile)** | 짧은 주기로 만들고 피드백받아 고쳐가는 개발 방식의 총칭. 특정 방법론 이름이 아니다 |
| **폭포수 (Waterfall)** | 요구분석→설계→구현→테스트를 순서대로 한 번씩 밟는 방식 |
| **이터레이션 (Iteration)** | 반복 주기 하나 |
| **스프린트 (Sprint)** | 스크럼에서 쓰는 이터레이션의 이름. 보통 1~4주 |
| **백로그 (Backlog)** | 해야 할 일의 목록. 우선순위 순으로 정렬됨 |
| **유저 스토리 (User Story)** | 사용자 관점에서 쓴 요구사항 한 줄 |
| **에픽 (Epic)** | 여러 스토리로 쪼개지는 큰 단위 |
| **DoD (Definition of Done)** | "끝났다"의 정의. 팀이 합의한 완료 기준 |
| **속도 (Velocity)** | 한 스프린트에 처리하는 작업량의 실측값 |
| **번다운 차트** | 남은 작업량이 줄어드는 추이 그래프 |
| **회고 (Retrospective)** | 주기 끝에 "무엇을 개선할지" 논의하는 자리 |
| **WIP (Work In Progress)** | 동시에 진행 중인 작업. 칸반에서 이 수를 제한한다 |
| **스쿼드 (Squad)** | 한 제품 영역을 끝까지 책임지는 소규모 교차기능 팀 |
| **교차기능 (Cross-functional)** | 기획·개발·QA 등 필요한 역할이 팀 안에 다 있는 상태 |

## 1. 애자일이란 무엇인가

### 애자일 선언 (2001) — 4가지 가치

> - **개인과 상호작용**을 프로세스와 도구보다
> - **작동하는 소프트웨어**를 포괄적인 문서보다
> - **고객과의 협력**을 계약 협상보다
> - **변화에 대응**을 계획을 따르는 것보다

**가장 흔한 오해**: "문서를 쓰지 말라"가 아니다. 원문은 **"오른쪽도 가치 있지만 왼쪽을 더 중시한다"** 로 끝난다. 문서보다 작동하는 소프트웨어가 우선이라는 뜻이지, 문서가 무가치하다는 뜻이 아니다.

> **jun-bank에 대한 함의**: 지금 설계 문서를 잔뜩 쓰는 것이 애자일에 어긋나는가? **어긋나지 않는다.** 이 문서들은 "포괄적 문서"가 아니라 **판단의 근거**이며, 무엇보다 이 프로젝트의 산출물은 서비스가 아니라 **이해**다.

### 왜 폭포수가 잘 안 되는가

폭포수의 전제는 **"요구사항을 처음에 다 알 수 있다"** 이다. 그런데 실제로는:

- 사용자는 **써보기 전까지 뭘 원하는지 모른다**
- 만들면서 **문제의 진짜 모양이 드러난다**
- 시장·규제·기술이 **개발 중에 바뀐다**

애자일은 이 전제를 뒤집는다: **"모른다는 것을 전제로 설계한다."** 짧게 만들어 보여주고 배운 것을 반영한다.

### 애자일이 아닌 것

| 오해 | 실제 |
|---|---|
| 계획을 안 세운다 | **더 자주** 세운다 (주기마다) |
| 문서를 안 쓴다 | **필요한 만큼만** 쓴다 |
| 설계를 안 한다 | **한 번에 다 하지 않을** 뿐이다 |
| 빠르게 만드는 것 | **빠르게 배우는 것** |
| 매일 야근하는 것 | **지속 가능한 속도**가 원칙 중 하나다 |

## 2. 대표 프레임워크

### 2.1 스크럼 (Scrum)

**시간을 고정하고 범위를 조절**하는 방식이다.

#### 역할 3가지

| 역할 | 책임 |
|---|---|
| **프로덕트 오너 (PO)** | 무엇을 만들지 결정. 백로그 우선순위의 **단독 결정권자** |
| **스크럼 마스터 (SM)** | 프로세스가 굴러가게 함. 장애물 제거. **관리자가 아니다** |
| **개발팀** | 어떻게 만들지 결정. 자기조직화 |

#### 이벤트 5가지

| 이벤트 | 시점 | 목적 |
|---|---|---|
| **스프린트** | 1~4주 | 반복 주기 그 자체 |
| **스프린트 계획** | 시작 시 | 이번에 무엇을 할지 정한다 |
| **데일리 스크럼** | 매일 15분 | 어제/오늘/장애물 공유 |
| **스프린트 리뷰** | 종료 시 | **결과물을 보여주고** 피드백받는다 |
| **회고** | 종료 시 | **프로세스**를 개선한다 |

> ⚠️ 리뷰와 회고는 다르다. **리뷰는 제품**, **회고는 프로세스**를 다룬다. 이걸 합치면 대개 회고가 사라진다.

#### 산출물 3가지

- **제품 백로그**: 전체 할 일 목록
- **스프린트 백로그**: 이번 주기에 할 일
- **증분(Increment)**: 이번 주기의 결과물. **DoD를 만족해야** 증분이다

#### 유저 스토리 형식

```
As a   [누가]
I want [무엇을]
So that [왜]
```

예:
```
As a   카드소지자
I want 결제 취소 내역을 앱에서 확인하고
So that 환불이 정상 처리됐는지 스스로 확인할 수 있다
```

**INVEST 기준** — 좋은 스토리의 조건:

| 글자 | 뜻 |
|---|---|
| **I**ndependent | 다른 스토리와 독립적 |
| **N**egotiable | 세부는 협의 가능 |
| **V**aluable | 사용자에게 가치 있음 |
| **E**stimable | 크기를 가늠할 수 있음 |
| **S**mall | 한 주기에 끝날 만큼 작음 |
| **T**estable | 완료를 검증할 수 있음 |

### 2.2 칸반 (Kanban)

**범위를 고정하지 않고 흐름을 관리**하는 방식이다. 스프린트가 없다.

```
┌─────────┬──────────┬──────────┬─────────┐
│  대기    │  진행중   │  리뷰     │  완료    │
│         │  (WIP≤2) │  (WIP≤1) │         │
├─────────┼──────────┼──────────┼─────────┤
│ 대사 배치│ 승인 API │ 카드 발급 │ 계좌 개설│
│ 정산 파일│          │          │ 회원가입 │
└─────────┴──────────┴──────────┴─────────┘
```

**핵심 원칙**:
1. **현재 작업을 시각화한다**
2. **WIP를 제한한다** ← 가장 중요하고 가장 안 지켜지는 것
3. **흐름을 관리한다** (리드 타임 측정)
4. **정책을 명시한다**
5. **점진적으로 개선한다**

**WIP 제한이 왜 중요한가**: 동시에 5개를 진행하면 5개 모두 **끝나지 않은 상태**로 오래 머문다. 컨텍스트 스위칭 비용이 붙고, 완료된 게 하나도 없어 피드백도 못 받는다. **하나를 끝내고 다음을 시작하는 것**이 총 처리량을 높인다.

### 2.3 스크럼 vs 칸반

| | 스크럼 | 칸반 |
|---|---|---|
| 주기 | 고정 스프린트 | 연속 흐름 |
| 고정하는 것 | **시간** (범위 조절) | **WIP** (시간 조절) |
| 역할 | 정해져 있음 | 없음 |
| 변경 수용 | 스프린트 중엔 지양 | **언제든** |
| 적합한 상황 | 계획 가능한 신규 개발 | 우선순위가 자주 바뀌는 운영·유지보수 |

**1인 개발에는 칸반이 대체로 낫다.** 스프린트 계획·리뷰·데일리의 상당 부분은 **여러 사람의 동기화**를 위한 장치인데, 혼자면 그 비용이 순손실이다.

## 3. 스쿼드 방식 (Spotify Model)

### 구조

스포티파이가 2012년에 소개한 조직 모델이다. **네 가지 단위**로 이루어진다.

```
       트라이브 (Tribe) — 관련된 스쿼드들의 묶음, 100명 이하
   ┌──────────────────────────────────────────┐
   │  ┌────────┐  ┌────────┐  ┌────────┐      │
   │  │ 스쿼드1 │  │ 스쿼드2 │  │ 스쿼드3 │      │  ← 스쿼드: 6~12명 교차기능 팀
   │  │ 결제    │  │ 계좌    │  │ 원장    │      │
   │  └───┬────┘  └───┬────┘  └───┬────┘      │
   │      │           │           │           │
   │  ····┼···········┼···········┼···· 챕터(Chapter): 같은 직군 묶음
   │      백엔드 챕터 / QA 챕터 / 프론트 챕터     │     (스쿼드를 가로지름)
   └──────────────────────────────────────────┘
   ······································· 길드(Guild): 관심사 기반 자발적 모임
                                                (조직 전체를 가로지름)
```

| 단위 | 성격 | 목적 |
|---|---|---|
| **스쿼드 (Squad)** | 6~12명, 교차기능, **자율적** | 한 제품 영역을 **끝까지** 책임 |
| **트라이브 (Tribe)** | 관련 스쿼드 묶음, ~100명 | 스쿼드 간 조율 |
| **챕터 (Chapter)** | 같은 직군의 사람들 (백엔드 챕터 등) | **기술 역량·표준** 유지 |
| **길드 (Guild)** | 관심사 기반 자발적 모임 | 지식 공유 |

**핵심 발상**: 스쿼드는 **세로(제품)**로 나누고, 챕터는 **가로(직군)**로 묶는다. 제품 자율성과 기술 일관성을 동시에 얻으려는 시도다.

### 스쿼드의 조건

- **하나의 미션**을 가진다 ("결제 승인 경험을 책임진다")
- **자율적으로 결정**한다 (무엇을 어떻게 만들지)
- **끝까지 책임진다** — 기획부터 운영까지 (You build it, you run it)
- 다른 스쿼드에 **의존하지 않고 배포**할 수 있다

### 콘웨이의 법칙 (Conway's Law)

> **"시스템을 설계하는 조직은 그 조직의 소통 구조를 그대로 닮은 설계를 만든다."** (1967)

예:
- 프론트팀/백엔드팀/DBA팀으로 나뉜 조직 → **레이어드 아키텍처**가 나온다
- 결제팀/계좌팀/원장팀으로 나뉜 조직 → **도메인별 서비스**가 나온다

**역 콘웨이 전략 (Inverse Conway Maneuver)**: 원하는 아키텍처가 있으면 **조직을 먼저 그 모양으로 바꾼다.** 마이크로서비스를 원하면서 조직은 기술 계층별로 나뉘어 있으면, 결국 분산 모놀리스가 나온다.

> **이것이 스쿼드 모델과 마이크로서비스가 함께 언급되는 이유다.** 스쿼드 하나 = 서비스 몇 개를 소유. 독립 배포가 가능하려면 조직도 독립적이어야 한다.

### 스포티파이 모델의 함정

**스포티파이 자신도 이 모델을 그대로 쓰지 않는다.** 2012년 영상이 널리 퍼지면서 "정답"처럼 받아들여졌지만:

1. **그것은 당시의 스냅샷**이었지 완성된 방법론이 아니었다
2. 스쿼드 간 **의존은 여전히 생겼고**, 조율 비용이 컸다
3. 챕터 리드의 역할이 모호해 **책임 공백**이 발생했다
4. 다른 회사가 형태만 복사하면 **이름만 바뀐 기존 조직**이 된다

> 교훈: **조직 모델은 복사하는 것이 아니라 문제에서 도출하는 것이다.** "우리는 무슨 문제 때문에 이 구조가 필요한가"에 답할 수 없으면 도입하지 않는 게 낫다.

## 4. 1인 개발에 애자일을 어떻게 적용하는가

jun-bank는 1인 프로젝트다. 스크럼 이벤트 대부분이 **여러 사람의 동기화 장치**이므로 그대로 쓰면 형식만 남는다. **살릴 것과 버릴 것**을 가른다.

### 버려도 되는 것

| 항목 | 이유 |
|---|---|
| 데일리 스크럼 | 공유할 상대가 없다 |
| 스토리 포인트·속도 측정 | 상대 추정은 여러 사람의 합의가 있어야 의미가 있다 |
| 역할 분리 (PO/SM/개발) | 전부 한 사람 |
| 스프린트 리뷰 (형식적 발표) | 보여줄 이해관계자가 없다 |

### 반드시 살려야 하는 것

| 항목 | 이유 | jun-bank 적용 |
|---|---|---|
| **작은 증분** | 큰 덩어리는 끝이 안 난다 | **유스케이스 1개 = 1 사이클** (`project-workflow/phase8/`) |
| **DoD** | "끝났다"의 기준이 없으면 영원히 90%다 | 7단계 전부 통과해야 완료 |
| **회고** | **1인 개발에서 가장 중요하다** | 사이클 ⑦단계 |
| **WIP 제한** | 혼자면 동시 작업의 유혹이 더 크다 | **동시 1개** 권장 |
| **백로그 우선순위** | 하고 싶은 것부터 하면 중요한 게 안 끝난다 | 아키텍처 관통도 기준 |
| **작동하는 것 우선** | 완벽한 설계보다 도는 코드 | 얇은 수직 슬라이스 |

### 왜 1인 개발에서 회고가 가장 중요한가

혼자 일하면 **아무도 지적해 주지 않는다.** 잘못된 습관이 그대로 굳는다. 회고는 자기 자신을 상대로 하는 코드 리뷰다.

회고에서 물을 것:
1. **설계와 실제가 갈라진 지점은 어디인가?** → 문서를 고친다
2. **예상보다 오래 걸린 것은 무엇이고, 왜인가?**
3. **다음 사이클에서 하나만 바꾼다면 무엇인가?**
4. **가정 중 틀린 것이 있었나?**

> 1번이 핵심이다. **설계와 구현이 갈라졌는데 문서를 안 고치면, 그때부터 문서는 거짓말이 된다.**

### 1인 스쿼드로 보기

1인 프로젝트를 **"모든 챕터를 겸하는 1인 스쿼드"** 로 보면 유용한 점이 있다. 스쿼드의 조건을 스스로에게 물을 수 있다:

- **하나의 미션이 있는가?** → 결제 도메인 이해
- **끝까지 책임지는가?** → 설계·구현·운영·회고 전부
- **독립적으로 배포 가능한가?** → 로컬 Docker로 전부

챕터가 없다는 것은 **기술 표준을 스스로 세워야 한다**는 뜻이다. 그것이 `conventions/` 디렉토리의 존재 이유다.

## 5. jun-bank의 개발 주기와의 연결

`project-workflow/phase8/`에 정의된 7단계 사이클이 곧 이 프로젝트의 애자일 실천이다.

```
① 유스케이스 선정   ← 백로그 우선순위 (아키텍처 관통도 기준)
② 기능 명세서       ← 유저 스토리 + 수용 기준
③ 설계서 (+ADR)
④ 계약 확정         ← OpenAPI / 이벤트 스키마. 구현보다 먼저
⑤ 구현
⑥ 검증              ← DoD
⑦ 회고·문서 갱신    ← 애자일의 핵심. 여기가 빠지면 폭포수
```

**스프린트 대신 유스케이스를 단위로 삼은 이유**: 결제 도메인에서 "절반 구현된 승인"은 가치가 0이다. 시간을 고정하고 범위를 자르면 **반쪽짜리 결제 흐름**이 남는다. 그래서 시간이 아니라 **완결된 흐름 하나**를 단위로 잡았다. 이건 스크럼보다 **칸반에 가까운 선택**이다.
