# 이벤트 소싱

> **상태를 저장하는 대신, 상태를 바꾼 사건을 저장한다.**
> 이 프로젝트는 **채택하지 않았다**(ADR-003). 그 판단의 근거를 이해하려면 개념부터 필요하다.

---

## 1. 무엇인가

```
상태 저장 (지금)          이벤트 소싱
  Account                   AccountEvents
    balance = 15              Deposited(20)
                              Withdrawn(5)
  UPDATE 로 바꾼다          → balance 는 접어서(fold) 얻는다
                            INSERT 만 있다
```

**저장소에 UPDATE가 없다.** 모든 변경이 사건으로 쌓이고, 현재 상태는 처음부터 재생(replay)한 결과다.

### 재생 비용과 스냅샷

사건이 10만 개면 매번 10만 번 접을 수 없다. 그래서 **스냅샷**을 둔다.

```
Snapshot(v=9000, balance=1,200)  +  Event(9001..9137)  →  현재 상태
```

> ⚠️ **스냅샷은 최적화이지 정본이 아니다.** 스냅샷이 틀리면 **버리고 재생하면 된다** —
> 이 성질이 이벤트 소싱의 가장 큰 장점 중 하나다.

---

## 2. 무엇을 얻나

| 얻는 것 | 왜 |
|---|---|
| **감사가능성이 공짜** | 모든 변경이 **원인과 함께** 남는다. *"왜 이 값이 됐나"* 에 항상 답할 수 있다 |
| **과거 시점 재구성** | *"3월 5일 자정의 잔액"* 을 그 시점까지만 접어서 얻는다 |
| **파생 뷰를 다시 만들 수 있다** | 읽기 모델이 틀렸으면 **지우고 재생**한다. 마이그레이션이 아니라 재구축이다 |
| **시간 여행 디버깅** | 사고 시점의 상태를 그대로 복원해 재현한다 |
| **새 질문에 소급 답변** | *"작년에 부분 환불이 몇 건이었나"* — 사건이 남아 있으면 답할 수 있다 |

> ★ **마지막이 과소평가된다.** 상태만 저장하면 **당시에 묻지 않은 질문은 영원히 답할 수 없다.**

---

## 3. 무엇을 내주나

| 대가 | 왜 |
|---|---|
| **조회가 어렵다** | *"잔액이 100만 이상인 계좌"* 를 사건으로 못 찾는다 → **CQRS가 사실상 필수** |
| ★ **이벤트 스키마를 못 고친다** | **과거 사건을 수정할 수 없다.** 필드를 잘못 설계하면 upcasting(변환 계층)을 영구히 안고 간다 |
| **재생 비용** | 스냅샷 관리가 운영 대상이 된다 |
| **저장량** | 상태 하나 대신 변경 전부를 남긴다 |
| **팀 학습** | 익숙한 CRUD 사고와 다르다. 잘못 배우면 *"이벤트 이름의 CRUD"* 가 된다 |

### 가장 흔한 실패 — 이벤트가 CRUD의 별명이 되는 것

```
나쁨   AccountUpdated(balance=15)        ← 무슨 일이 있었는지 모른다
좋음   Deposited(20) · Withdrawn(5)      ← 원인이 남는다
```

> ★ **`XxxUpdated` 는 거의 항상 신호다.** 도메인 사건이 아니라 **저장 동작에 이름을 붙인 것**이다.

---

## 4. 이 프로젝트는 왜 안 쓰나 (ADR-003)

**기각의 핵심 근거가 성능이나 복잡도가 아니다.**

> **이벤트 소싱의 대가는 "모델을 굳히는 것"이다.**
>
> 우리는 Phase 2에서 도메인 모델을 **열 라운드에 걸쳐** 고쳤고 **환불 모델만 세 번** 바꿨다.
> 그 전에 사건으로 굳혔다면 **전부 마이그레이션 대상**이었다.

| 근거 | |
|---|---|
| 감사가능성은 **이미 확보돼 있다** | BR-10이 원장을 append-only로 뒀다 — **전표가 자금 이동의 이벤트 저장소**다 |
| 승인 경로가 **가용잔액을 매 요청 계산**한다 | QS-02(400 TPS)에서 스냅샷 없이는 못 버틴다 |
| **되돌릴 수 없는 결정**이다 | 스키마가 틀리면 과거를 못 고친다 |

### 우리는 이미 "부분 이벤트 소싱"이다

```
자금 이동   →  사건으로 (원장 전표, append-only)
나머지 상태  →  상태로 (계좌 balance, 승인 상태)
```

**실무에서 가장 흔한 절충이고, BR-40이 그 결정이었다.**

그 대가가 **M12·M14 대사**다 — 잔액과 원장이 어긋날 수 있으므로 그것을 잡는 장치가 필요하다.
**대사를 빼면 이 선택의 근거가 무너진다.**

### 언제 다시 볼 것인가

> **ADR-003 R1**: *M12·M14 불일치가 구조적으로 반복되면* — 잔액을 전표의 파생값으로 돌린다.

---

## 5. 판별 기준 — 언제 쓰나

```
"왜 이 값이 됐나"를 자주 묻는가          → 이벤트 소싱이 답이다
과거 시점 상태가 업무 요구인가            → 그렇다
모델이 아직 흔들리는가                    → ★ 아직 이르다
조회가 복잡한가                          → CQRS를 함께 감당할 수 있는가
```

| 잘 맞는 곳 | 안 맞는 곳 |
|---|---|
| 금융 원장 · 감사 · 규제 대응 | 단순 CRUD · 마스터 데이터 |
| 상태 변화 자체가 업무인 것 (주문·계약) | 현재 값만 중요한 것 (설정·프로필) |
| 사후 분석이 중요한 것 | 조회 패턴이 다양하고 즉시성이 필요한 것 |

> ★ **전부 아니면 전무가 아니다.** 우리처럼 **한 컨텍스트(원장)만** 이벤트 기반으로 두는 것이
> 가장 흔하고, 대개 그것으로 충분하다.

---

## 6. 함께 오는 것들

| 개념 | 관계 |
|---|---|
| **CQRS** | 조회가 어려워지므로 사실상 필수. 단 **CQRS는 이벤트 소싱 없이도 쓴다** |
| **프로젝션** | 사건 → 읽기 모델. 틀리면 **재생**한다 |
| **업캐스팅** | 옛 사건을 새 스키마로 변환. 스키마 변경의 유일한 길 |
| **사가** | 여러 애그리게이트에 걸친 프로세스를 사건으로 조율 |

> ⚠️ **CQRS와 이벤트 소싱을 같은 것으로 오해하는 일이 흔하다.** 별개다.
> 우리는 **CQRS는 일부 쓰고 이벤트 소싱은 안 쓴다**(ADR-007 §3).
