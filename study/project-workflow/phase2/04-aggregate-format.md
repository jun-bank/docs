# 애그리게이트 명세 — 양식과 작성법

---

## 1. 목적

**무엇이 함께 변해야 하고, 무엇이 항상 참이어야 하는지를 고정한다.**

애그리게이트(Aggregate)는 **정합성과 트랜잭션의 단위**다. 이 경계가 곧 "한 번에 원자적으로 바뀌는 범위"이고, 그래서 Phase 3의 트랜잭션 설계가 여기서 직접 파생된다.

> **애그리게이트는 저장 단위가 아니다.**
> 테이블과 1:1로 만들면 저장 구조가 도메인을 지배하게 된다. 판단 기준은 오직 **"이 규칙을 지키려면 무엇이 함께 바뀌어야 하는가"** 다.

## 4. 작성법

### 불변식 찾는 법

**"이 두 값이 동시에 바뀌지 않으면 무엇이 깨지는가?"** 를 물으면 나온다.

| 유형 | 예 |
|---|---|
| **합계 제약** | 누적 취소액 ≤ 원거래 금액 |
| **균형 제약** | 차변 합계 = 대변 합계 |
| **상태 정합** | 상태가 완료면 완료일시가 반드시 있다 |
| **범위 제약** | 잔액은 음수가 될 수 없다 |
| **참조 무결** | 취소는 반드시 원거래를 가리킨다 |

**불변식은 애그리게이트 안에서만 검증 가능해야 한다.** 검증하려고 다른 애그리게이트를 조회해야 한다면:
- 경계가 잘못됐거나
- 그건 불변식이 아니라 **프로세스 규칙**(정책)이다

### 경계 정하는 법

```
① 불변식을 먼저 나열한다
② 각 불변식이 "무엇과 무엇이 동시에 참이어야 하는가"를 본다
③ 그 최소 묶음이 애그리게이트다
```

**크기 판단 기준**:

| 증상 | 진단 | 대응 |
|---|---|---|
| 동시 요청이 자주 충돌한다 | 너무 크다 | 불변식을 다시 보고 쪼갠다 |
| 규칙이 애플리케이션 서비스에 새어 있다 | 너무 작다 | 함께 참이어야 하는 것을 합친다 |
| 한 트랜잭션에서 여러 애그리게이트를 바꾼다 | 경계가 틀렸거나 프로세스가 필요 | 이벤트/Saga로 분리 |

> **원칙: 하나의 트랜잭션은 하나의 애그리게이트만 변경한다.**
> 이걸 지킬 수 없다면 경계를 다시 본다. 정말 필요하면 **의식적으로 예외로 기록**한다.

### 다른 애그리게이트 참조

**반드시 ID로만 참조한다.**

| 나쁜 예 | 좋은 예 |
|---|---|
| `private Account account;` | `private AccountId accountId;` |

객체 참조를 두면:
- 로딩 범위가 애그리게이트를 넘어간다
- 남의 애그리게이트를 바꿀 수 있게 된다
- 트랜잭션 경계가 흐려진다

### 조작(커맨드) 쓰는 법

**사전조건 / 사후조건을 반드시 채운다.** 이게 그대로 테스트가 된다.

```
| 부분취소 | cancelPartially | 상태가 정산완료가 아니다 | 누적취소액이 요청분만큼 증가 | PartiallyCancelled |
```

**조작 이름은 도메인 언어로.** `setStatus`, `update` 같은 이름은 도메인 개념이 아니다.

### 값 객체 판별

| 애그리게이트/엔티티 | 값 객체 |
|---|---|
| **식별자로 구분** | **값으로 구분** |
| 값이 바뀌어도 같은 것 | 값이 바뀌면 다른 것 |
| 생명주기가 있다 | 없다 |
| 계좌, 승인 | 금액, 이메일, 카드번호 |

**값 객체는 불변으로 만든다.** 그러면 공유해도 안전하고 검증을 생성 시점에 한 번만 하면 된다.

### 의문을 닫는 법 — 선택지와 기각 이유를 남긴다

의문이 결정되면 표에서 지우지 말고 **닫힌 의문**으로 옮긴다. 이때 **결론만 적으면 안 된다.**

| 남길 것 | 왜 |
|---|---|
| **검토한 선택지 전부** | 나중에 "이건 왜 안 했나"가 반드시 다시 나온다. 그때 재검토 비용을 없앤다 |
| **기각 이유** | 채택 이유보다 **기각 이유가 더 오래 쓸모 있다.** 상황이 바뀌면 기각 이유가 아직 유효한지만 확인하면 된다 |
| **어떤 규칙·불변식이 됐는가** | 결정이 코드로 강제되는 지점을 가리킨다 |

결정이 **업무 규칙 수준**이면 `01-business-rules.md`에 BR로 승격하고, 애그리게이트 문서에는 **선택지와 이유**를 남긴다. 규칙 본문은 한 곳(BR), 결정 과정은 한 곳(애그리게이트) — 중복하지 않는다.

> **분기를 규칙으로 적기 전에 한 번 의심한다.** "A이면 X, B이면 Y"로 보이는 것이 사실은 **한 문장으로 쓰면 결과로 갈라지는** 경우가 많다. 분기를 규칙에 적으면 A/B 판정 자체가 경합 지점이 된다.

## 5. 흔한 실수

| # | 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|---|
| 1 | **불변식이 없다** | 애그리게이트가 아니라 데이터 묶음이다 | 불변식을 못 찾으면 애그리게이트로 만들지 않는다 |
| 2 | **테이블 = 애그리게이트** | 저장 구조가 도메인을 지배한다 | "함께 변해야 하는가"로만 판단 |
| 3 | **객체로 다른 애그리게이트 참조** | 경계가 무너진다 | ID 참조로 바꾼다 |
| 4 | **너무 크게 잡음** | 락 경합으로 동시성이 죽는다 | 불변식이 요구하는 최소로 |
| 5 | **조작 이름이 CRUD** | 도메인 의도가 사라진다 | 업무 언어로 (`승인한다`, `해제한다`) |
| 6 | **불변식 검증에 외부 조회 필요** | 애그리게이트 안에서 못 지킨다 | 경계를 다시 보거나 정책으로 분리 |
| 7 | **사전/사후조건 빈칸** | 테스트할 것이 불명확 | 반드시 채운다 |
| 8 | **의문을 닫으면서 결론만 남김** | 몇 달 뒤 같은 논의를 처음부터 다시 한다 | 선택지와 **기각 이유**를 함께 남긴다 |

## 6. 완료 기준

- [ ] **불변식이 최소 1개** 있고, 각각 근거 규칙(BR-nn)이 연결돼 있다
- [ ] 모든 불변식이 **이 애그리게이트 안에서 검증 가능**하다
- [ ] 다른 애그리게이트 참조가 **전부 ID**다
- [ ] 모든 조작에 **사전조건·사후조건**이 있다
- [ ] 조작 이름이 **도메인 언어**다 (CRUD 아님)
- [ ] **경계 근거 4문항**(왜 이 범위 / 왜 더 크지 않은가 / 왜 더 작지 않은가 / 트랜잭션 단위인가)이 채워져 있다
- [ ] 값 객체와 엔티티가 구분돼 있다
- [ ] 용어사전의 코드명과 **일치**한다
- [ ] 닫힌 의문에 **선택지와 기각 이유**가 남아 있다 (결론만 있는 것은 미완)
