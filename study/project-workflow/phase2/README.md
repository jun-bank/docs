# Phase 2 — 도메인 정의

> 책 대응: 없음 (DDD 영역. 책 3.3.4 서비스 분할의 **입력**이 되는 단계다)
> 선행 조건: **Phase 1 완료** — 특히 범위와 시나리오

---

## 목적

**개념과 경계를 고정한다.**

이 Phase의 진짜 산출물은 문서가 아니라 **바운디드 컨텍스트**다. 서비스를 어떻게 나눌지(Phase 3)는 여기서 나온 경계를 따라간다. 이 단계를 건너뛰고 서비스를 나누면 **기술적 직관으로 나뉘고, 나중에 못 고친다.**

> 서비스 분할이 잘못됐을 때의 증상:
> - 같은 개념(금액, 사용자)의 정의가 서비스마다 다르다
> - 한 기능을 바꾸는데 서비스 3개를 동시에 배포해야 한다
> - "이 데이터의 주인이 누구인가"에 답할 수 없다
>
> 셋 다 **Phase 2를 건너뛴 결과**다.

## 만드는 문서

**순서가 중요하다.** 앞 문서가 뒤 문서의 입력이다.

| # | 문서 | 양식 | 두는 위치 | 산출 |
|---|---|---|---|---|
| 1 | **용어사전** | [01-glossary-format.md](01-glossary-format.md) | `docs/domain/glossary.md` | 개념의 이름과 정의 |
| 2 | **이벤트 스토밍** | [02-event-storming-format.md](02-event-storming-format.md) | `docs/domain/event-storming.md` | 애그리게이트 후보 · **컨텍스트 후보** |
| 3 | **컨텍스트 맵** | [03-context-map-format.md](03-context-map-format.md) | `docs/domain/context-map.md` | 경계 확정 · **데이터 소유권** |
| 4 | **애그리게이트 명세** | [04-aggregate-format.md](04-aggregate-format.md) | `docs/domain/aggregates/<이름>.md` | 불변식 · 트랜잭션 단위 |
| 5 | **상태 머신** | [05-state-machine-format.md](05-state-machine-format.md) | `docs/domain/state-machines/<이름>.md` | 허용/금지 전이 |

```
① 용어사전        "이걸 뭐라고 부를 것인가"
     ↓
② 이벤트 스토밍    "무슨 일이 일어나는가" → 애그리게이트·컨텍스트 후보
     ↓
③ 컨텍스트 맵      "경계를 어디에 긋고 누가 무엇을 소유하는가"
     ↓
④ 애그리게이트     "무엇이 함께 변하고, 무엇이 항상 참이어야 하는가"
     ↓
⑤ 상태 머신        "어떤 전이가 허용되고 무엇이 금지되는가"
```

**왜 용어사전이 먼저인가**: 이름이 합의되지 않은 상태로 모델을 그리면, 같은 개념에 여러 이름이 붙는다. 그 흔적은 나중에 값 객체 중복·필드명 불일치로 남는다.

## 완료 기준

| # | 기준 | 왜 |
|---|---|---|
| 1 | 용어사전에 **코드에서 쓸 영문명**이 함께 있다 | 한글 개념과 코드 식별자가 1:1로 대응해야 번역 오류가 없다 |
| 2 | 이벤트 스토밍에 **핫스팟(합의 안 된 지점)**이 표시돼 있다 | 애매한 지점을 표시하지 않으면 구현자가 임의로 정한다 |
| 3 | **모든 데이터에 소유 컨텍스트가 하나씩** 정해졌다 | 소유자가 둘이면 반드시 정합성 문제가 생긴다 |
| 4 | 모든 애그리게이트에 **불변식이 최소 1개** 있다 | 불변식 없는 애그리게이트는 그냥 데이터 묶음이다 |
| 5 | 상태 머신에 **허용되지 않는 전이**도 표시돼 있다 | 금지가 명시되지 않으면 코드에서 강제할 수 없다 |
| 6 | 컨텍스트 간 **관계 유형**이 명시돼 있다 | 관계 유형이 통신 방식·의존 방향을 결정한다 |

## 흔한 실패

| 실패 | 증상 | 대응 |
|---|---|---|
| **용어사전을 건너뜀** | 같은 개념에 이름이 여러 개 생긴다 | 모델링 전에 이름부터 합의 |
| **DB 테이블로 모델링** | 애그리게이트가 테이블과 1:1이 된다 | 애그리게이트는 **함께 변하는 단위**지 저장 단위가 아니다 |
| **애그리게이트를 너무 크게** | 락 범위가 커지고 동시성이 죽는다 | 불변식이 요구하는 최소 범위로 줄인다 |
| **애그리게이트를 너무 작게** | 불변식을 지킬 수 없어 서비스로 규칙이 샌다 | 함께 참이어야 하는 것끼리 묶는다 |
| **컨텍스트 경계를 기술로 나눔** | "조회 서비스", "배치 서비스" 같은 이름이 나온다 | 경계는 **용어 체계**로 나눈다 |
| **데이터 소유자 미정** | 같은 데이터가 두 곳에 저장된다 | 소유자를 하나로 정하고 나머지는 복제본으로 명시 |

## 이 Phase가 다음 Phase에 넘기는 것

```
용어사전       ──▶ 전 Phase (모든 문서·코드의 어휘)
이벤트 스토밍   ──▶ Phase 4 유스케이스 도출
컨텍스트 맵     ──▶ Phase 3 서비스 분할 ★ 가장 중요한 입력
애그리게이트    ──▶ Phase 3 트랜잭션 경계 설계
상태 머신       ──▶ Phase 4 유스케이스 대안·예외 흐름
```

**여기서 넘어가지 않는 것**: 서비스 개수, 배포 단위, 기술 선택. 컨텍스트 ≠ 서비스다. 하나의 서비스가 여러 컨텍스트를 담을 수도 있고, 그 판단은 Phase 3의 일이다.
