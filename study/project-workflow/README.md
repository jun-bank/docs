# project-workflow — 문서 작성 순서와 양식

> **무엇을 만드는가가 아니라, 어떤 순서로 어떤 양식으로 만드는가**를 정한다.
> 근거: 『아키텍트 첫걸음』 2~5장 (`reference/architect-textbook-toc.md`)

---

## 이 디렉토리의 성격

**여기에는 특정 프로젝트의 내용이 들어가지 않는다.** 각 Phase에서 만드는 **문서의 양식(템플릿)과 작성법**만 둔다.

| 여기에 두는 것 | 여기에 두지 않는 것 |
|---|---|
| 제품 정의서 **양식**과 작성법 | 이 프로젝트의 제품 정의 **내용** |
| 용어사전 **양식**과 채우는 법 | 이 프로젝트의 실제 용어 |
| ADR **양식**과 판단 기준 | 이 프로젝트의 실제 결정 |

**이유**: 특정 프로젝트에 맞춰 미리 써둔 문서는 대부분 읽히지 않고 낡는다. 재사용되는 것은 **양식과 작성법**이다. 실제 내용은 각 Phase에 도달했을 때 양식을 복사해 채운다.

```
study/project-workflow/          ← 양식과 작성법 (재사용)
        │  복사해서 채운다
        ▼
docs/product/ · docs/domain/ · docs/architecture/ …   ← 실제 내용
```

## 순서를 벗어나는 유일한 경로 — 토대 변경

Phase는 앞에서 뒤로 간다. 그런데 **뒤 Phase를 쓰다가 앞 Phase의 결정이 틀렸음이 드러나는 일**이 실제로 일어난다.

그때 앞 문서를 조용히 고치면 안 된다. 무엇이 왜 실패했는지가 사라지고, **같은 자리가 다시 흔들릴 때 재구성할 수 없다.**

| 경로 | 언제 | 문서 |
|---|---|---|
| **패치** | 리뷰가 지적한 개별 결함 | 각 문서의 변경 이력 |
| **토대 변경** | **같은 자리가 반복해서 깨질 때** | [design-change/](design-change/README.md) → `docs/design-changes/DC-nnn` |
| **검산 기계화** | 결함이 **"목록에서 하나 빠졌다" 계열로 수렴**할 때 | [verification-by-construction.md](verification-by-construction.md) |

> **둘을 구분하지 않으면 패치가 토대 문제를 숨긴다.** 라운드마다 결함 수가 줄어드는 신호가 나오기 때문이다.
>
> ★ **세 번째 경로가 따로 있는 이유**: 토대를 바꿔도 *"목록에서 하나 빠졌다"* 는 사라지지 않는다. 그건 **설계가 아니라 대조의 실패**이고, 리뷰를 한 번 더 도는 것으로는 **다른 항목이 빠질 뿐**이다.

## 전체 순서

```
[1회성 — 처음 한 번만]                          [반복 — 유스케이스마다]

Phase 0  문서 체계 준비          책 —
   │
Phase 1  제품 정의               책 —
   │
Phase 2  도메인 정의             책 —
   │
Phase 3  아키텍처 설계           책 3장
   │
Phase 4  개발 프로세스 표준화     책 4.2
   │
Phase 5  샘플 유스케이스 +
         애플리케이션 기반 구현   책 4.3 전반 + 4.4    ★ 순환을 여기서 끊는다
   │
Phase 6  개발자용 문서 정비       책 4.5
   │
Phase 7  구성 관리 · CI/CD        책 4.6
   │
Phase 8  ───────────────────────▶ 유스케이스 반복      책 4.3 후반
   │                                ① 선정 ② 명세 ③ 설계 ④ 계약
   │                                ⑤ 구현 ⑥ 검증 ⑦ 회고 ─┐
   │                                         ▲            │
   │                                         └────────────┘
Phase 9  품질 보증 체계           책 5장
         └─ 전략은 Phase 8 시작 전에, 실행은 매 사이클 ⑥단계
```

### 핵심 원칙

> **각 Phase는 이전 Phase의 산출물을 입력으로 받는다. 입력이 비어 있으면 그 Phase는 시작할 수 없다.**

"일단 하면서 정하자"는 이 원칙의 반대말이다. 순서를 어기면 이런 일이 벌어진다:

| 순서 오류 | 결과 |
|---|---|
| 용어사전 없이 도메인 모델을 그림 | 같은 개념에 이름이 여러 개 생긴다 |
| 품질 속성 없이 아키텍처를 고름 | 근거가 없어 "좋아 보여서" 고르게 된다 |
| 도메인 경계 없이 서비스를 나눔 | 기술적 직관으로 나뉘고, 나중에 못 고친다 |
| 계약 없이 구현부터 함 | 서비스 간 인터페이스가 구현에 끌려간다 |
| 기반 없이 유스케이스를 구현 | 인증·오류·로깅이 유스케이스마다 달라진다 |
| 테스트 전략 없이 테스트를 씀 | 무엇을 어느 레벨에서 검증할지 매번 다르다 |

**되돌리기 비용이 큰 것부터 결정한다.** 서비스 경계를 나중에 바꾸는 비용은 클래스를 바꾸는 비용의 수백 배다.

### 의존 관계

```
제품 정의 ──▶ 용어사전 ──▶ 도메인 모델 ──▶ 서비스 분할
    │                          │              │
    └──────────▶ 품질 속성 ────┴──────────────┘
                     │
                     ▼
                아키텍처 결정(ADR) ──▶ 계약(API/이벤트) ──▶ 구현
                     │                                        ▲
                     └──────▶ 애플리케이션 기반 ───────────────┘
                                    ▲
                        샘플 유스케이스가 이걸 끌어낸다
```

### 책의 순서와 다른 점 (의도적)

책은 **4.3(유스케이스 중심 구현) → 4.4(애플리케이션 기반 구현)** 순이다. 그런데 기반이 없으면 유스케이스를 구현할 수 없고, 유스케이스가 없으면 어떤 기반이 필요한지 모른다. **순환이다.**

**해결: 샘플 유스케이스.** 아키텍처를 관통하는 유스케이스 하나를 골라 **끝까지 얇게** 구현하면서 기반을 만든다(Walking Skeleton). 그것이 참조 구현이 되고, 이후 실제 유스케이스는 그 위에 얹힌다.

책 4.3.1이 "샘플 유스케이스"와 "실제 유스케이스"를 나눈 이유가 이것이다.

## Phase 색인

각 폴더에 **그 Phase에서 만드는 문서의 양식과 작성법**이 들어 있다.

| Phase | 이름 | 만드는 문서 | 폴더 |
|---|---|---|---|
| 0 | 문서 체계 준비 | 문서 상태 규약 · 추상화 레벨 규약 · ADR 양식 | `phase0/` |
| **1** | **제품 정의** | 제품 정의서 · 비즈니스 규칙서 | **`phase1/`** ✅ |
| **2** | **도메인 정의** | 용어사전 · 이벤트 스토밍 · 컨텍스트 맵 · 애그리게이트 · 상태 머신 | **`phase2/`** ✅ |
| 3 | 아키텍처 설계 | 제약 · 품질 속성 · 품질 시나리오 · ADR · 아키텍처 뷰 · 기술서 | `phase3/` |
| 4 | 개발 프로세스 표준화 | 문서 표준 · 유스케이스 기술서 · 기능 명세서 · 설계서 | `phase4/` |
| 5 | 샘플 유스케이스 + 기반 구현 | 기반 10종 결정서 | `phase5/` |
| 6 | 개발자용 문서 정비 | 코딩·명명 규약 · 절차서 · 구현 가이드 | `phase6/` |
| 7 | 구성 관리 · CI/CD | 구성 관리 대상 · 브랜치 전략 · 파이프라인 정의 | `phase7/` |
| 8 | 유스케이스 반복 | 사이클 체크리스트 · 회고 | `phase8/` |
| 9 | 품질 보증 | 테스트 전략 · 테스트 계획 · 성능 테스트 계획 | `phase9/` |

## 각 Phase 폴더의 공통 구성

```
phaseN/
├── README.md             이 Phase의 목적 · 선행 조건 · 만드는 문서 · 완료 기준 · 흔한 실패
├── 01-<문서>-format.md    양식 + 작성법
├── 02-<문서>-format.md
└── …
```

각 `*-format.md` 는 아래 6개 절을 갖는다:

| 절 | 내용 |
|---|---|
| **1. 목적** | 이 문서가 답하는 질문. 왜 필요한가 |
| **2. 독자** | 누가 읽는가 (**독자가 없으면 그 문서는 쓰지 않는다**) |
| **3. 양식** | **복사해서 쓰는 실제 템플릿** |
| **4. 작성법** | 각 항목을 어떻게 채우는가 |
| **5. 흔한 실수** | 이 문서에서 반복되는 실패 패턴 |
| **6. 완료 기준** | 무엇이 되면 이 문서가 끝난 것인가 |

---

## 사용법

1. 현재 Phase의 `README.md`를 읽고 **선행 조건이 충족됐는지** 확인한다
2. 만들 문서의 `*-format.md`를 연다
3. **§3 양식**을 복사해 실제 문서 위치(`docs/product/`, `docs/domain/` …)에 붙인다
4. **§4 작성법**을 보며 채운다
5. **§6 완료 기준**으로 검증한다
6. Phase의 모든 문서가 끝나면 다음 Phase로

## 각 Phase 완료 기준 요약

| Phase | 완료 기준 (한 문장) |
|---|---|
| 0 | 새 문서를 어디에 어떤 형식으로 쓸지 고민하지 않아도 된다 |
| 1 | **범위 밖**이 명시되어 있고 미확정이 `결정 필요`로 남아 있다 |
| 2 | 모든 애그리게이트에 불변식이 있고 **데이터 소유자가 하나씩** 정해졌다 |
| 3 | 되돌리기 어려운 결정에 **전부 ADR이 있고, 되돌리는 조건이 비어 있지 않다** |
| 4 | 다음 유스케이스를 **템플릿 복사로 시작**할 수 있다 |
| 5 | 샘플 유스케이스가 **E2E로 성공**하고 기반 10종이 참조 구현으로 존재한다 |
| 6 | **초기화된 환경에서 문서만 보고** 따라 하면 동작한다 |
| 7 | 커밋 → 검증 → 배포 가능까지 **사람 손이 안 들어간다** |
| 8 | 각 유스케이스가 **7단계를 전부** 통과했다 |
| 9 | 각 품질 시나리오에 **자동 검증 수단**이 하나씩 붙어 있다 |

## 순서를 지키는 장치

순서를 정해두어도 지켜지지 않으면 의미가 없다.

| 장치 | 내용 |
|---|---|
| **입력 없으면 시작 금지** | 각 Phase README의 "선행 조건"이 비어 있으면 시작하지 않는다 |
| **미확정의 가시화** | 정해지지 않은 것은 문서 안에 `결정 필요 #n`으로 남긴다 |
| **회고에서 점검** | Phase 8 ⑦단계에서 "이번에 순서를 건너뛴 것이 있나" 확인 |
| **되돌리기 어려운 결정은 ADR 필수** | 추상화 레벨 ①(아키텍처)은 예외 없이 |
| **상위 레벨로 올라가기** | 구현 중 아키텍처를 바꾸고 싶어지면 코드로 우회하지 않고 Phase 3으로 올라간다 |
