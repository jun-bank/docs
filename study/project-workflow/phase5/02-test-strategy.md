# 테스트 전략 문서 양식 — 자산을 계층에 배정하는 절차 (워크플로우 정본)

- 상태: 작성중 (2026-08-06 — E2 산출물 ②. 작업 기록 = `plans/2026-08-06/e2-test-strategy/`)
- 목적: 산출물 ②(워크플로우) — **"이미 쌓인 검증 자산을 구현 전에 어떻게 계층에 배정하는가"** 의 재사용 가능한 절차. 교과서 **5장(품질 보증과 테스트)** 대응.
- 이 양식으로 쓰는 문서: `docs/architecture/test-strategy.md`(내용 정본)

## 1. 이 양식이 강제하는 것 (한 문장)

> **테스트 전략은 계층을 나열하는 문서가 아니라, 이미 있는 검증 자산을 하나도 빠뜨리지 않고 계층에 배정하는 문서다.**

계층(피라미드)부터 그리면 *"단위 70% · 통합 20% · E2E 10%"* 같은 **비율 선언**이 나온다. 비율은 검증할 수 없고, 배정 누락은 드러나지 않는다.
자산 대장에서 출발하면 **누락이 산술로 드러난다** — 대장의 원소 수와 배정된 원소 수가 다르면 그것이 결함이다.

> ★ 이 프로젝트에서 이 순서가 성립하는 이유: 구현 전에 이미 **규칙마다 검증 방법 칸**(BR)·**품질 시나리오**(QS)·**실험 시나리오**·**[구현 검증] 대장**(IV)이 있다. 테스트 전략이 만들 것은 **새 검증 항목이 아니라 배정**이다. 자산 대장이 없는 프로젝트라면 이 양식의 §2 ③ 앞에 *"대장부터 만든다"* 가 붙는다.

## 2. 필수 칸 (하나라도 비면 전략이 아니다)

| 칸 | 무엇을 적나 | 비어 있으면 생기는 일 |
|---|---|---|
| **① 계층 정의** | 계층마다 — **판정 대상**(무엇이 틀렸다고 말할 수 있나) · **격리 수준**(무엇을 실물로 쓰나) · **실행 비용·주기** · **실패했을 때 알게 되는 것** | 계층 이름만 있고 경계가 없어, 같은 검증이 세 계층에 중복되거나 아무 계층에도 없다 |
| **② 자산 → 계층 매핑 규칙** | 배정 **판별 질문** 하나 + 예외 처리(둘 이상에 걸칠 때 · 어느 계층으로도 못 갈 때) | 배정이 작성자의 취향이 되고, 다음 사람이 재현하지 못한다 |
| **③ 자산 매핑 표 (전수)** | 자산 대장별 **전 원소**의 배정 — 주 계층 1 + 보조 계층 · 근거 1행. 문서 끝에 **집계**(대장별 원소 수 = 배정 수) | 큰 대장의 뒤쪽이 조용히 빠진다(**silent failure — 이 프로젝트 실측 최다 사고 유형**) |
| **④ 게이트** | **머지 전 최소 안전선**과 계층의 관계 · stakes별 강도 · 계층이 **대체하지 못하는 것** | *"테스트 통과 = 검증 완료"* 로 읽혀, 그린 위장(fail-open 골든·exit 마스킹)이 그대로 통과한다 |
| **⑤ 소유** | 계층별 **테스트 설계 주체** — 생성≠검증 절단선(높음 stakes = 구현 diff 미열람 계약) | 구현자가 자기 diff를 보고 테스트를 쓰면 **테스트가 구현의 사본**이 된다 |
| **⑥ 도구** | 계층이 **요구하는 성질** → 그 성질을 만족하는 **v1 스택** → 후보 도구는 **도입 조건과 함께** 보류 | 요구가 실증되지 않은 스택이 들어오고, 도구가 만든 문제를 도메인 문제로 오인한다(C-08) |
| **⑦ [구현 검증] 연결** | IV 대장의 각 항목이 **어느 계층의 입력**인가 · 이 문서가 **확정하지 않는 수치**의 목록 | 문서가 추측을 정본화한다(검증 정책 v2 §1의 세 번째 유형 — *"판정 = 추측의 정본화, 해롭다"*) |

## 3. 작성 규칙

| # | 규칙 |
|---|---|
| **R1** | ★ **자산 대장이 먼저다.** 계층 정의는 대장을 훑고 나서 쓴다 — 피라미드는 **결과**이지 입력이 아니다 |
| **R2** | ★ **배정은 전수다.** 대장별로 *원소 수 = 배정 수* 를 문서 끝에 집계한다. 불일치 = **결함**이며 "대표 사례"로 대체하지 않는다 |
| **R3** | **배정 판별 질문 하나로 통일한다** — *"이 규칙이 틀렸다는 것을 드러내는 **가장 싼 실행 단위**는 무엇인가?"* 가장 싼 곳이 주 계층이다 |
| **R4** | **주 계층은 하나만 고른다.** 걸치는 것은 보조로 적는다 — 둘 다 주로 두면 **둘 다 안 짜인다** |
| **R5** | ★ **정본을 재해석하지 않는다.** 검증 방법 칸·시나리오 측정 칸은 **인용하고 배정만** 한다. 문면이 틀렸다고 판단되면 배정을 멈추고 **정본 개정을 별도 작업**으로 올린다(스코프 혼합 금지) |
| **R6** | ★ **수치를 확정하지 않는다.** 커버리지 목표·성능 목표는 `[미확정]` 또는 `[구현 검증]`이다. 성능 수치는 **품질 시나리오가 이미 소유**하고 있으므로 테스트 전략이 새로 정하면 정본이 둘이 된다 |
| **R7** | **도구는 마지막 칸이다.** 계층이 요구하는 **성질**을 먼저 적고 도구는 그 성질의 구현체로만 지목한다. 넣지 않기로 한 도구는 ★ **도입 조건**을 함께 적는다(C-08 — *"나중에 필요하면"* 은 판정 불가) |
| **R8** | ★ **게이트는 계층으로 대체되지 않는다.** 머지 전 최소 안전선(스모크·기존 테스트·diff self-review·rollback 판단·public contract 영향·반증 질문)은 **stakes 무관 유지**다 — 검증 정책 v2 **V2-5**가 이것을 명시적 존치 항목으로 둔다 |
| **R9** | **어느 계층으로도 못 가는 자산은 `[구현 검증]`으로 이연하고 중앙 대장에 등재한다**(V2-3). 무음 이연은 금지 — 태그와 대장 등재가 같은 커밋에 있어야 한다 |

## 4. 교과서 5장 대응

| | |
|---|---|
| 대응 장 | **5장 「품질 보증과 테스트」** (`reference/architect-textbook-toc.md` 전체 장 구성 — 본 프로젝트에서의 쓰임 = *"검증 전략(후속)"*) |
| ⚠️ **절 단위 대응** | ★ **[미확인]** — 저장소의 목차 판독본은 **2~4장만** 절·소절을 담고 있고 **5장은 장 제목까지만** 확보돼 있다. 따라서 이 양식은 *"5.x 어느 절에 대응한다"* 를 **주장하지 않는다.** 절 대응이 필요해지면 책 실물에서 5장 목차를 판독해 이 절을 채운다 |
| 대응의 성격 | 교과서가 **개발 주기 뒤에 두는 품질 보증**을, 이 프로젝트는 **구현 전 마지막 문서화 사이클(E2)** 로 당겨 놓는다. 이유는 `01-entry-procedure.md` §1과 같다 — 자산이 이미 쌓여 있어 **배정만 하면 되는 상태**이고, 배정을 구현 뒤로 미루면 **구현 diff가 테스트 설계의 입력**이 되어 절단선(⑤)이 깨진다 |

## 5. 자기 점검 (이 문서가 끝났다고 말할 수 있는 조건)

- [ ] 필수 칸 ①~⑦이 전부 채워졌다 (한 칸이라도 비면 아직 초안)
- [ ] 자산 대장별 **집계표**가 문서 끝에 있고, 원소 수 = 배정 수다
- [ ] 배정 판별 질문(R3)이 **한 개**이고 모든 배정이 그것으로 재현된다
- [ ] 확정한 수치가 **0개**다 (R6 — 성능 수치는 QS 인용, 커버리지는 [미확정])
- [ ] 도입하지 않은 도구마다 **도입 조건**이 적혀 있다 (R7)
- [ ] 어느 계층에도 못 간 자산이 `[구현 검증]` 태그 + 중앙 대장에 있다 (R9)
- [ ] 정본 문서를 **한 줄도 고치지 않았다** (R5)
