# 멀티테넌시 — 그리고 은행에서의 같은 문제

> **한 시스템이 여러 주체의 데이터를 다룰 때, 그것들이 서로 새지 않게 하는 문제.**
>
> ★ **이 프로젝트는 멀티테넌시를 포기했다**(D-04). 그런데 **메커니즘은 필요하다** —
> 은행에서 그것은 **고객 간 격리**와 **운영자 권한 단계**로 나타난다. 같은 문제다.

---

## 0. 왜 이 문서가 필요한가

```
멀티테넌시   테넌트 A가 B의 데이터를 보면 안 된다
은행         고객 A가 B의 계좌를 보면 안 된다
             상담원은 조회만, 관리자는 정정까지, 그 이상은 승인이 필요하다
```

**격리 축의 이름만 다르고 실패 방식은 같다.**
*"쿼리 한 군데에 조건이 빠져서 뚫린다"* 는 테넌트든 고객이든 똑같이 일어난다.

> ★ **은행에서 이것이 특히 중요한 이유**: 새는 것이 **돈과 개인정보**다.
> 조회 한 번 잘못 열리면 그것 자체가 사고이고, 되돌릴 수 없다.

---

## 1. 격리 모델 — 어디서 가르나

| 모델 | 무엇 | 격리 강도 | 대가 |
|---|---|---|---|
| **인스턴스 분리** | 테넌트마다 별도 배포·DB | 최강 | 비용·운영이 테넌트 수만큼 |
| **DB 분리** | 같은 앱, 테넌트마다 DB | 강 | 커넥션 풀 폭증 · 마이그레이션 N회 |
| **스키마 분리** | 같은 DB, 테넌트마다 스키마 | 중 | 마이그레이션 N회 · 스키마 수 한계 |
| **행 단위** (`tenantId` 컬럼) | 한 테이블에 전부 | ★ **약 — 코드가 지킨다** | 누수 위험 · 인덱스 설계 부담 |

### 트레이드오프의 핵심

```
격리를 강하게 할수록
  ✅ 실수로 새지 않는다        (구조가 막는다)
  ❌ 마이그레이션이 N배가 된다
  ❌ 테넌트 간 집계가 어려워진다
  ❌ 소형 테넌트에 과투자
```

> ★ **행 단위가 가장 흔하고 가장 위험하다.** 비용이 싸서 대부분 여기서 시작하는데,
> **격리를 코드가 지킨다** — 이 프로젝트의 실측 결론(*"주의력에 의존하는 규칙은 지켜지지 않는다"*)이
> 정면으로 걸리는 자리다.

### 은행에서는

| 축 | 보통 어떤 모델 |
|---|---|
| **고객 간** | 행 단위 — 계좌·카드에 소유자가 있다 |
| **조직/지점 간** | 행 단위 + 스코프 |
| **운영자 권한 단계** | 행 단위 아님 — **조작 자체를 가른다** |

---

## 2. ★ 권한 누수 — 조건 하나가 빠지는 방식

**가장 많이 일어나는 사고다.** 그리고 **테스트로는 잘 안 잡힌다** — 정상 경로는 다 통과하기 때문이다.

### 새는 경로들

| # | 경로 | 예 |
|---|---|---|
| **L1** | 조회에 조건 누락 | `WHERE id = ?` 만 있고 소유자 조건이 없다 |
| **L2** | **식별자 추측** | `/accounts/12345` 를 다른 값으로 바꿔 호출한다 (IDOR) |
| **L3** | 집계·통계 경로 | 목록은 막았는데 **합계 API**가 안 막혔다 |
| **L4** | 조인의 반대편 | 계좌는 필터했는데 **조인한 거래 테이블**은 안 했다 |
| **L5** | 배치·리포트 | 운영 도구가 **전체를 본다**는 전제로 짜였다 |
| **L6** | 캐시 키 | 캐시 키에 소유자가 빠져 **남의 결과가 반환**된다 |
| **L7** | 에러 메시지 | *"해당 계좌 없음"* vs *"권한 없음"* — 존재 여부가 샌다 |
| **L8** | 이벤트·로그 | 이벤트 payload에 남의 식별자가 실려 하류로 흘러간다 |

> ★ **L6와 L8은 격리를 "저장소 문제"로만 보면 안 보인다.** 캐시와 이벤트에도 같은 축이 필요하다.

### 막는 방법 — 강도 순

| 수단 | 강도 | 무엇을 막나 |
|---|---|---|
| 코드 리뷰 · 규약 | ❌ 약 | 거의 못 막는다 |
| 공통 리포지토리 | ⚠️ 중 | 그 리포지토리를 **안 쓰면** 뚫린다 |
| **DB 행 수준 보안**(RLS) | ✅ 강 | ★ **쿼리를 우회할 수 없다** |
| **타입으로 강제** | ✅ 강 | 소유자 없는 조회를 **컴파일이 거부** |
| 인스턴스/DB 분리 | ✅ 최강 | 구조가 막는다 |

```java
// 조건이 빠질 수 있는 형태
findById(accountId)

// 빠질 수 없는 형태 — 소유자 없이는 호출 자체가 안 된다
findById(accountId, requesterScope)
```

> ★ **이 프로젝트의 ADR-007과 같은 원리다.** *"쓰지 마라"* 가 아니라 **"쓸 수 없게 만든다."**

### 검증은 "정상 경로"가 아니라 "옆집"으로 한다

```
❌ 내 계좌를 조회하면 보인다              ← 통과해도 아무 보장이 없다
✅ 남의 계좌 식별자로 호출하면 거절된다     ← 이것이 검증이다
✅ 모든 조회 API에 대해 위를 반복한다      ← 하나만 빠져도 뚫린다
```

> ★ **"모든 API에 대해"가 핵심이다.** 사람이 세면 빠진다 — **엔드포인트 목록을 생성해서 전수 시험**한다.
> Phase 2에서 조작 대장을 생성한 것과 같은 이유다.

## 3. 리소스 편중 — 큰 고객 하나가 공용 풀을 먹는다

**격리는 데이터만의 문제가 아니다.** 자원도 격리해야 한다.

| 자원 | 편중되면 |
|---|---|
| **커넥션 풀** | 큰 테넌트의 느린 쿼리가 풀을 점유 → 전체 대기 |
| **스레드** | 한 테넌트의 배치가 워커를 다 먹는다 |
| **캐시** | 큰 테넌트의 데이터가 캐시를 밀어낸다 (eviction) |
| **디스크·인덱스** | 한 테넌트가 테이블 대부분을 차지해 통계가 왜곡된다 |
| **락** | 핫 로우가 다른 테넌트까지 대기시킨다 |

### 대응

| 수단 | |
|---|---|
| **테넌트별 쿼터** | 요청 수·동시 실행·데이터량 상한 |
| **풀 분리** | 큰 테넌트를 별도 커넥션 풀·워커로 |
| **우선순위 큐** | 배치를 실시간보다 낮게 |
| **격리 등급** | 큰 테넌트는 **DB 분리로 승격** |

> ★ **은행에서는 "고객"보다 "채널"과 "배치"가 편중을 만든다.**
> 대사·정산 배치가 실시간 승인 경로를 먹는 것이 전형이고,
> 이 프로젝트도 **ADR-010 R1**으로 그것을 되돌리는 조건에 걸어뒀다.

## 4. 스키마 마이그레이션 — 전 테넌트에 적용하는 문제

| 모델 | 마이그레이션 |
|---|---|
| 행 단위 | ✅ **한 번** |
| 스키마 분리 | ❌ **N번** — 하나 실패하면 부분 적용 상태 |
| DB 분리 | ❌ N번 + 순서·롤백 |

### 부분 적용이 진짜 문제다

```
테넌트 1..500  적용 완료
테넌트 501     실패
테넌트 502..   미적용
  → 앱은 어느 스키마를 가정해야 하나?
```

**그래서 `expand-contract`가 필수가 된다** — 이 프로젝트의 `HA-5`와 같은 것.

```
① expand   새 컬럼 추가 (구/신 버전 모두 동작)
② 배포     앱이 둘 다 다룰 수 있게
③ 이행     데이터 이관
④ contract 옛 컬럼 제거
```

> ★ **각 단계 사이에 "전 테넌트 적용 완료"를 기다린다.** 그것이 없으면
> **부분 적용 상태에서 앱이 깨진다.**

## 5. 이 프로젝트에 무엇이 있고 무엇이 없나

### 있는 것

| | |
|---|---|
| **C7 인증** 컨텍스트 | context-map R4 — *"여러 컨텍스트가 같은 요청 주체를 안다"* · **동기** |
| **계좌·카드에 소유자** | 도메인이 소유 축을 갖고 있다 |
| **파티션 키 = 계좌ID** | ADR-009 — 격리 축과 파티션 축이 **일치한다** |

### ★ 없는 것 — 설계 공백

| # | 무엇 | 왜 문제인가 |
|---|---|---|
| **G-1** | **인가(authorization) 모델** | C7은 *인증*이다. **누가 무엇을 할 수 있는지**가 어디에도 없다 |
| **G-2** | **운영자 권한 단계** | BR-28(보류)·BR-37(통지)·BR-42(수동 실행)·BR-45(차단 해제)가 전부 *"운영자"* 라고만 쓴다. **같은 사람인가?** |
| **G-3** | 조회 경로의 소유자 조건 | 조회 API가 아직 없어서 안 드러났을 뿐이다 |
| **G-4** | 감사 로그의 주체 | *"누가 이 조작을 했나"* — 원장은 자금은 남기지만 **행위자를 안 남긴다** |

> ⚠️ **G-2가 특히 큰 구멍이다.** 운영자 조작이 규칙 여럿에 흩어져 있는데
> **권한 단계가 없으면 "운영자면 뭐든 할 수 있다"** 가 된다.
> 은행에서 그것은 **내부 통제 부재**다.
>
> context-map **R10**이 *"운영은 컨텍스트가 아니다 — 자기 모델이 없기 때문"* 이라고 판정했는데,
> **권한 단계는 모델이다.** 그 판정을 다시 볼 필요가 있다.

## 6. 판별 기준

```
지금 안 하면 나중에 못 하는가?
  → tenantId / 소유자 컬럼      ★ 그렇다. 전 테이블 재작성이 된다
  → 권한 단계 모델              ⚠️ 반쯤. 조작 표면이 굳으면 비싸진다
  → 격리 등급 승격 (DB 분리)    ❌ 아니다. 나중에 가능하다
```

> ★ **"멀티테넌시를 안 한다"와 "격리 축이 없다"는 다르다.**
> 테넌트가 하나여도 **고객 간 격리와 권한 단계는 필요하다.**
> 포기 목록에 넣을 때 **무엇을 포기하는지**를 정확히 적어야 한다 — D-04는 그것을 안 했다.
