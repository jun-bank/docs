# HMAC — 공유 비밀 하나로 "이 요청이 진짜 우리 것인가"에 답하기

> 학습 노트다. 결정의 근거가 될 수 없다(이 프로젝트의 배포 인증 결정 정본: [`architecture/adr/ADR-027-deploy-orchestration.md`](../../../architecture/adr/ADR-027-deploy-orchestration.md) — 특히 DO-2·DO-10, 그리고 그것이 인용하는 ADR-024 RL-8).

이 문서는 HMAC(Hash-based Message Authentication Code)을 개념부터 설명하고, 왜 이 프로젝트가 배포 요청 서명에 그것을 쓰는지까지 잇는다. 순서는 하나의 논리를 따른다 — 무엇이 문제였나, 그 문제를 어떤 아이디어로 풀었나, 그 아이디어가 실제로 서려면 무엇을 더 지켜야 하나, 그리고 그것이 못 푸는 문제는 무엇인가. `ipad`/`opad`·상수시간 비교·재전송 같은 이름들은 각각의 기능이 아니라 **"비밀 키 하나로 진위를 증명한다"는 하나의 결정에서 갈라져 나온 결과**로 읽는 것이 이해가 빠르다. 인용한 정의는 RFC 2104와 NIST FIPS 198-1, 구현 문장은 Go 표준 라이브러리 `crypto/hmac` 기준이다.

## 1. 문제 — 배포 API는 인터넷에서 도달 가능한 원격 코드 실행이다

이 프로젝트의 배포 경로는 CI가 인터넷을 건너 엣지를 거쳐 허브의 배포 에이전트에 요청을 보내는 형태다(정본: ADR-027 DO-1). 그 요청 한 건이 하는 일은 컨테이너를 갈아 끼우는 것 — 즉 **배포 요청을 받아들인다는 것은 남이 보낸 명령을 우리 서버에서 실행한다는 것**이다. 그러면 에이전트가 반드시 답해야 하는 질문이 둘 생긴다.

- **위조**: 이 요청을 정말 우리 CI가 보냈나, 아니면 아무나 엔드포인트에 POST한 것인가.
- **변조**: 우리 CI가 보낸 요청이 맞다 해도, 중간에서 대상 호스트나 이미지 digest가 바뀌지 않았나.

TLS(HTTPS)는 이 둘을 대신 풀어 주지 못한다. TLS는 전송 구간의 도청과 변조를 막고 상대 서버의 신원을 확인해 주지만, **"이 HTTP 요청의 발신자가 누구인가"를 애플리케이션에게 증명해 주지는 않는다** — 엣지에서 TLS가 종단되고 나면 그 뒤로 흐르는 것은 그냥 평문 요청이고, 엣지는 인증하지 않고 전달만 한다(ADR-027 DO-1). 그래서 요청 자체에 "이건 비밀 키를 아는 쪽이 만들었다"는 증거를 실어야 한다. 그 증거를 만드는 표준적인 방법이 MAC(메시지 인증 코드)이고, 그중 해시 함수로 만드는 것이 HMAC이다.

## 2. 아이디어 — 공유 비밀 키와 해시로 인증 태그를 만든다

MAC의 발상은 단순하다. 보내는 쪽과 받는 쪽만 아는 비밀 키 `K`가 있으면, 메시지 `text`에 대해 `K`가 없으면 계산할 수 없는 짧은 태그를 붙여 함께 보낸다. 받는 쪽은 같은 `K`로 같은 태그를 다시 계산해 첨부된 값과 맞춰 본다. 맞으면 두 가지가 한꺼번에 증명된다 — **키를 아는 누군가가 만들었고(진위), 그 뒤로 메시지가 바뀌지 않았다(무결성)**. FIPS 198-1은 HMAC을 "암호학적 해시 함수와 공유 비밀 키를 결합해 메시지를 인증하는 메커니즘"으로 규정한다([NIST FIPS 198-1](https://csrc.nist.gov/pubs/fips/198-1/final)).

여기서 "해시 함수로 만든다"가 HMAC의 정체다. SHA-256 같은 잘 검증된 해시가 이미 있으니, 그것을 부품으로 재활용해 MAC을 만들자는 것이다. RFC 2104는 그 조립법을 다음 한 줄로 정의한다([RFC 2104](https://www.rfc-editor.org/rfc/rfc2104)):

```
HMAC(K, text) = H( (K ⊕ opad) ‖ H( (K ⊕ ipad) ‖ text ) )
```

`H`는 해시 함수(예: SHA-256), `‖`는 이어 붙이기, `⊕`는 XOR다. `ipad`는 "바이트 `0x36`을 블록 크기 `B`만큼 반복한 것", `opad`는 "바이트 `0x5C`를 `B`만큼 반복한 것"이고, i·o는 각각 inner·outer의 mnemonic이다(RFC 2104 원문). 키가 블록 크기보다 길면 먼저 해시해 줄인다. 눈여겨볼 점은 **해시가 두 번 겹쳐 있다는 것** — 안쪽에서 키를 섞어 메시지를 해시하고, 그 결과를 다시 키를 섞어 한 번 더 해시한다. 왜 하필 이 모양인지가 다음 절이다.

## 3. 왜 두 번 해시하나 — 단순 `hash(key‖msg)`의 함정

가장 순진한 MAC은 "키와 메시지를 이어 붙여 한 번 해시한다", 즉 `H(K ‖ text)`다. 이건 **깨진다**. SHA-256을 포함한 Merkle-Damgård 계열 해시는 메시지를 블록 단위로 순차 처리하며 내부 상태를 이어 가는 구조인데, 이 구조에는 **길이 확장 공격(length extension attack)**이라는 약점이 있다. 해시 출력값 자체가 사실상 "여기까지 처리한 내부 상태"이기 때문에, 공격자가 `H(K ‖ text)` 값과 메시지 길이만 알면 **키를 몰라도** 그 상태에서 이어서 데이터를 덧붙여 `H(K ‖ text ‖ 임의데이터)`의 유효한 태그를 만들 수 있다([Length extension attack, Wikipedia](https://en.wikipedia.org/wiki/Length_extension_attack)). 배포 요청으로 치면, 유효한 요청 하나를 관찰한 공격자가 뒤에 무언가를 덧붙인 새 요청을 통과시킬 수 있다는 뜻이다.

HMAC의 이중 해시가 정확히 이 구멍을 막는다. 안쪽 해시의 결과를 바깥 해시가 한 번 더 감싸 버리므로, 최종 값은 더 이상 "이어서 처리 가능한 내부 상태"가 아니다 — 바깥 해시가 안쪽의 상태를 가려 확장을 불가능하게 만든다. RFC 2104 본문은 이 중첩 구조의 수학적 정당화를 저자들의 분석 논문[BCK1]에 미루지만, 실무에서 HMAC을 "그냥 `hash(key‖msg)` 하지 말고 반드시 써야 하는 것"으로 만드는 이유가 이 길이 확장 방어다. `ipad`와 `opad`가 서로 다른 상수인 것도, 안쪽과 바깥쪽에서 키를 **다른 방식으로** 섞어 두 해시가 서로 다른 키로 동작하는 효과를 내기 위해서다.

## 4. 대칭 키 — 서명자와 검증자가 같은 열쇠를 쥔다

HMAC은 **대칭 키** 방식이다. 태그를 만드는 쪽(CI)과 검증하는 쪽(배포 에이전트)이 **똑같은 비밀 키**를 갖는다. 이 점이 흔히 "서명"이라 부르는 공개 키 방식(RSA·ECDSA 등)과 갈리는 지점이다. 공개 키 서명은 개인 키로 서명하고 누구나 아는 공개 키로 검증하므로, **검증자가 서명을 위조할 수 없다** — 검증 능력과 서명 능력이 분리된다. HMAC은 그렇지 않다. 검증할 수 있는 쪽은 곧 태그를 만들 수도 있다. 같은 키를 쥐고 있기 때문이다.

무엇을 언제 쓰나의 판단은 여기서 나온다.

- **HMAC(대칭)**: 양쪽이 서로를 신뢰하고 안전하게 키를 공유할 수 있는 **닫힌 두 당사자** 사이. 빠르고 단순하며 키 관리가 열쇠 하나로 끝난다. 대신 그 키가 새면 **양쪽 능력이 모두 무너진다**.
- **공개 키 서명(비대칭)**: 검증자가 여럿이거나(누구나 검증), 검증자를 신뢰할 수 없어 "검증은 시키되 위조는 막아야" 하는 경우, 혹은 제3자에게 부인 방지를 증명해야 하는 경우.

이 프로젝트의 배포 경로는 정확히 전자다 — 당사자가 CI와 에이전트 **둘뿐**이고, 서로 신뢰하며, 키를 CI 시크릿 저장소에 안전히 둘 수 있다. 검증자가 태그를 만들 수 있다는 HMAC의 성질이 여기서는 문제가 되지 않는다(에이전트가 우리 것이므로). 그래서 무거운 공개 키 기반 없이 대칭 키 하나로 충분하다. [실무 의견]

## 5. 검증의 함정 — 태그 비교는 상수시간이어야 한다

태그를 다시 계산했으면 첨부된 태그와 "같은가"를 봐야 한다. 그런데 이 비교를 **평범한 바이트 비교(`==`)로 하면 새 구멍이 뚫린다**. 보통의 비교 함수는 첫 번째로 다른 바이트를 만나면 즉시 멈추므로, **앞쪽 바이트가 많이 맞을수록 비교에 걸리는 시간이 미세하게 길어진다**. 공격자는 태그를 바꿔 가며 응답 시간을 재서, "지금 이 후보가 앞 몇 바이트까지 맞았는지"를 시간으로 읽어낼 수 있다 — 이것이 타이밍 공격이고, 이 방식으로 태그를 앞에서부터 한 바이트씩 맞춰 나가면 결국 유효한 태그를 통째로 복원할 수 있다.

방어는 **상수시간 비교**다. 두 태그가 어디서 갈리든 **항상 전체를 끝까지 비교해 걸리는 시간이 입력 내용과 무관**하게 만든다. Go의 `crypto/hmac`은 이걸 위해 별도 함수를 제공하고 문서에 못박는다: "Equal은 두 MAC을 타이밍 정보를 흘리지 않고 비교한다(Equal compares two MACs for equality without leaking timing information)" 그리고 "수신자는 타이밍 부채널을 피하기 위해 반드시 Equal로 MAC을 비교해야 한다"([Go crypto/hmac](https://pkg.go.dev/crypto/hmac)). 즉 HMAC을 쓴다는 것은 태그 계산뿐 아니라 **태그 비교까지 상수시간으로 한다**는 뜻이며, 이 둘 중 하나만 빠뜨려도 인증이 새어 나간다.

## 6. 표준과 구현 — Go `crypto/hmac`이 제공하는 것

HMAC은 RFC 2104가 정의하고 NIST FIPS 198-1이 미국 연방 표준으로 채택한, 20년 넘게 검증된 구성이다. 그래서 직접 `ipad`/`opad`를 조립할 일은 없다 — 표준 라이브러리를 쓴다. Go에서는 `hmac.New`에 해시 생성자와 키를 넘겨 계산기를 만들고, 검증은 `hmac.Equal`로 한다. 공식 문서의 표준 사용 패턴이 그대로 검증 함수다([Go crypto/hmac](https://pkg.go.dev/crypto/hmac)):

```go
// messageMAC 이 message 에 대한 유효한 HMAC 태그인지 검사한다.
func ValidMAC(message, messageMAC, key []byte) bool {
	mac := hmac.New(sha256.New, key)
	mac.Write(message)
	expectedMAC := mac.Sum(nil)
	return hmac.Equal(messageMAC, expectedMAC)   // == 가 아니라 상수시간 비교 (§5)
}
```

핵심은 두 줄로 요약된다 — `hmac.New(sha256.New, key)`로 키를 섞은 계산기를 만들고, 마지막을 `hmac.Equal`로 닫는다. 여기서 `==`를 쓰면 §5의 타이밍 구멍이 그대로 열린다.

## 7. 우리 프로젝트 — 무엇에 서명하고 키는 누가 쥐나

개념을 배포 경로에 얹으면 두 가지 설계 결정이 남는다 — **서명 범위**와 **키 보유**. 둘 다 ADR-027이 정본이고, 여기서는 왜 그렇게 잡았는지만 읽는다(재판정은 그 문서에서 한다).

**서명 범위 = 정규화된 method + path + body digest + `requestId` + `issuedAt`/`expiresAt`**(정본: ADR-027 DO-10 ⑴). 왜 이 여섯인가는 §1의 "변조" 질문에서 나온다 — 요청의 **의미를 결정하는 모든 축**이 태그 안에 들어가야, 그중 하나라도 바뀌면 검증이 깨진다. method·path는 "무엇을 하는 요청인가", body digest는 "본문 전체"(digest만 서명하면 본문을 통째로 다시 해시하지 않고도 본문 변조를 잡는다), `requestId`는 요청의 신원, `issuedAt`/`expiresAt`는 유효 시간 창이다. 그리고 DO-10은 한 가지를 더 못박는다 — **"서명 밖의 값은 판정에 쓰지 않는다."** 태그로 보호되지 않는 필드로 결정을 내리면, 그 필드는 공격자가 자유롭게 바꿀 수 있는 입력이기 때문이다.

**키는 CI 플랫폼의 시크릿 저장소가 단독 보유한다**(정본: ADR-027 DO-2). 서명 검증에 실패하면 **적용하지 않고 거절을 기록한다 — 예외 없음**(DO-2가 인용하는 ADR-024 RL-8). §4에서 봤듯 HMAC은 대칭 키라 **키를 쥔 쪽이 곧 배포를 명령할 수 있는 쪽**이므로, 이 키는 host-root 장악과 같은 강도의 비밀이다. 그래서 키를 사람이 만지거나 이미지에 넣지 않고 CI 시크릿에 가두며, 발급·보관·교체를 별도 축이 소유한다(ADR-027 DO-2). 그리고 §1에서 TLS가 인증을 대신하지 못한다고 했듯, 여기서도 **SSH는 인증 수단이 아니라 서명 검증을 통과한 뒤에 열리는 전송**일 뿐이다(DO-2) — 관문의 순서가 고정이라는 것이 이 구조의 안전 성질이다.

## 8. 한계 — HMAC은 재전송을 막지 못한다

HMAC이 증명하는 것은 딱 두 가지, **진위와 무결성**이다. 그런데 유효한 요청을 **그대로 복사해 다시 보내면**, 그 복사본도 진짜 키로 만들어진 진짜 태그를 달고 있으므로 검증을 **당연히 통과한다**. HMAC은 "이 태그가 유효한가"에 답할 뿐 "이 요청을 전에 본 적 있는가"에는 답하지 못한다 — 즉 **freshness(신선함)를 보장하지 않는다**. ADR-027 DO-10이 이 지점을 정확히 짚는다: *"HMAC은 진위를 증명할 뿐 freshness를 보장하지 않는다 — 유효 요청 한 건을 탈취하면 같은 배포를 언제든 다시 실행할 수 있고, 프록시·CI의 타임아웃 재시도와 응답 유실도 같은 결과를 만든다."*

배포에서 이건 특히 위험하다 — 지나간 배포를 재실행하면 되돌린 버전이 조용히 되살아날 수 있고, 그 재실행이 성공처럼 보인다. 그래서 재전송은 **HMAC 밖의 별도 방어선**이 맡는다. 그것이 §7에서 서명 범위에 `requestId`·`issuedAt`/`expiresAt`를 넣은 이유다(정본: ADR-027 DO-10).

- **시간 창**: `expiresAt`이 지났거나 `issuedAt`이 허용 skew 밖이면 거절·기록한다(DO-10 ⑵). 오래된 요청의 재사용 창을 좁힌다.
- **멱등 원장**: 부작용을 내기 전에 `requestId`를 내구적으로 선점하고(DO-10 ⑶), **같은 `requestId` + 같은 body digest면 재실행하지 않고 그 요청의 현재 상태를 반환**한다(DO-10 ⑷). 같은 요청이 두 번 와도 배포는 한 번만 일어난다.

정리하면, **HMAC은 "누가·무엇을"에 답하고, `requestId` 멱등은 "몇 번"에 답한다**. 두 축은 겹치지 않으므로 어느 하나로 다른 하나를 대신할 수 없다 — 이 프로젝트가 서명과 멱등 원장을 함께 두는 이유가 여기 있다.
