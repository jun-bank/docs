# JWKS — 발급자의 공개키를 어디서 얻고 키 회전을 어떻게 따라가나

> 학습 노트다. 결정의 근거가 될 수 없다(이 프로젝트의 배포 신원 검증 정본: [`architecture/adr/ADR-027-deploy-orchestration.md`](../../../architecture/adr/ADR-027-deploy-orchestration.md) DO-11 · 게이트 2 코드 `infra/internal/auth/oidc.go`). 마지막 두 절의 우리 적용은 그 정본을 **인용**할 뿐 여기서 재판정하지 않는다.

JWKS(JSON Web Key Set)는 토큰 발급자가 자신의 **공개키 집합을 JSON으로 게시하는 표준 엔드포인트**다. 이 문서는 그것이 무엇이고 왜 필요하며 어떻게 동작하는지를 개념부터 설명한다. 형제 문서 [`oidc.md`](oidc.md)가 *"서명이 발급자의 공개 키로 검증되지 않으면 payload의 어떤 값도 신뢰할 수 없다"* 에서 멈춘 바로 그 자리 — 검증자는 그 공개키를 대체 어디서, 어떻게 얻는가 — 를 이 글이 잇는다. RS256 같은 비대칭 서명 검증은 발급자의 공개키를 손에 쥐어야 시작되는데, 그 키를 코드에 박아 두면 발급자가 키를 바꾸는 순간 검증이 통째로 깨진다. JWKS는 그 "어디서·어떻게"를 표준화해, 검증자가 키를 미리 심어 두지 않고도 발급자에게서 **그때그때 가져와 회전을 따라가게** 한다. 인용한 스펙 문장은 RFC 7515·7517·7518·7519(JOSE 제품군)와 OpenID Connect Discovery 1.0 기준이다.

## 1. 왜 필요한가 — 공개키를 하드코딩하면 회전에서 조용히 깨진다

비대칭 서명의 성질부터 짚어야 이 문제가 보인다. RS256에서 발급자는 **개인키로 서명**하고 검증자는 그에 짝지는 **공개키로 검증**한다. 공개키는 이름 그대로 비밀이 아니라서 아무에게나 내줘도 안전하다 — 그것으로는 서명을 위조할 수 없기 때문이다. 그래서 여기서 어려운 문제는 기밀성이 아니라 **전달과 회전**이다: 그 공개키를 검증자에게 어떻게 넘겨주고, 발급자가 키를 바꿀 때 어떻게 따라가게 하느냐다.

가장 순진한 답은 검증자 설정에 발급자의 공개키를 **한 번 박아 두는 것**이다. 이건 발급자가 키를 바꾸는 순간 무너진다. 발급자가 서명키를 교체하는 것(키 회전)은 사고가 아니라 정기적인 보안 위생이다 — 주기적으로, 혹은 유출이 의심되면 즉시 새 키로 갈아탄다. 회전 뒤 발급되는 토큰은 새 개인키로 서명되므로, 박아 둔 옛 공개키로는 **하나도 검증되지 않는다.** 검증자는 진짜 토큰을 전부 거절하기 시작하고(가용성 사고), 그걸 피하려면 회전 때마다 검증자를 다시 배포해 키를 손으로 맞춰야 한다.

JWKS는 이 결박을 끊는다. 발급자가 자신의 현재 공개키들을 **정해진 엔드포인트에 게시**하고 검증자가 그것을 가져오면, 회전은 발급자 쪽에서 일어나되 검증자 코드를 건드리지 않고 전파된다. 검증자가 쥐는 것은 특정 키가 아니라 "발급자의 키 목록을 어디서 가져오는가"라는 **위치**이고, 키 자체는 그 위치에서 그때그때 온다.

## 2. JWK과 JWKS — 공개키 하나, 그리고 그 집합

먼저 낱개 단위인 JWK를 본다. **JWK(JSON Web Key)는 암호 키 하나를 표현한 JSON 객체**다(RFC 7517). 키의 메타데이터를 이름 붙은 필드로 담는데, 판정에 자주 쓰이는 넷은 이렇다.

- **`kty`** — 키 종류(key type). `"RSA"`·`"EC"` 같은 알고리즘 계열을 가리킨다.
- **`use`** — 용도. `"sig"`(서명 검증용)냐 `"enc"`(암호화용)냐다. 우리가 쓰는 것은 `"sig"`다.
- **`alg`** — 이 키로 쓰도록 의도된 알고리즘(예: `"RS256"`).
- **`kid`** — 키 식별자(key ID). 여러 키 중 하나를 지목하는 이름표이며, 회전 때 옛 키와 새 키를 구분하는 핵심이다(§3).

RSA 공개키의 **실제 키 재료**는 두 수 — 모듈러스 `n`과 지수 `e` — 이고, 이 필드들은 RFC 7517이 아니라 그것이 위임하는 알고리즘 스펙 RFC 7518(JWA) §6.3.1이 정의한다(둘 다 Base64urlUInt 인코딩, `e`는 흔히 65537 = `"AQAB"`). 즉 JWK 하나를 받으면 검증자는 `n`·`e`로 RSA 공개키를 복원해 서명 검증에 쓴다.

여기서 집합 단위가 **JWKS(JWK Set)**다. RFC 7517은 이를 "`keys` 멤버를 가진 JSON 객체이며, `keys`는 JWK들의 배열"로 규정한다. 발급자가 키를 **여러 개 한꺼번에** 게시할 수 있다는 이 점이 회전을 매끄럽게 만든다 — 옛 키와 새 키가 배열 안에 잠시 공존하기 때문이다(§3).

```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "a1b2c3d4...",
      "n": "0vx7agoebGcQ...",   // 모듈러스 (Base64urlUInt · RFC 7518 §6.3.1)
      "e": "AQAB"               // 지수 65537
    }
  ]
}
```

## 3. 동작 — discovery로 위치를 찾고, kid로 키를 고른다

검증자가 발급자 URL 하나에서 출발해 검증된 서명에 닿기까지는 네 걸음이다. 순서가 곧 신뢰의 사슬이다.

첫째, **위치 찾기(discovery)**다. OIDC 발급자는 발급자 URL 뒤에 `/.well-known/openid-configuration`을 붙인 자리에 설정 문서를 게시하고(OIDC Discovery 1.0), 그 문서 안의 **`jwks_uri`** 필드가 JWK Set 문서의 URL을 담는다. 스펙은 이 URL이 반드시 `https`여야 한다고 못박는다(그 이유는 §5). 그래서 경로는 *발급자 URL → discovery 문서 → `jwks_uri` → JWK Set*으로 이어진다.

둘째, **키 고르기**다. 검증할 JWT의 헤더에는 `kid`가 실려 있다(RFC 7515의 JOSE 헤더 파라미터 — "이 서명을 만든 키가 무엇인지 알려 주는 힌트"). 검증자는 그 `kid`를 읽어, 가져온 JWK Set에서 **같은 `kid`를 가진 키**를 고른다. `kid`가 없으면 집합의 키를 하나씩 다 시도해야 하므로, `kid`는 "어느 키인가"를 한 번에 지목하는 장치다.

셋째, **서명 검증**이다. 고른 JWK의 공개키(`n`·`e`로 복원한 RSA 공개키)로 서명을 확인한다. 이 검증이 통과한 다음에야 payload의 claim들을 신뢰할 수 있다(oidc.md §3) — JWKS는 이 첫 관문에 넣을 열쇠를 조달하는 일을 한다.

넷째, **회전 따라가기**다. 발급자는 JWK Set에 **새 `kid`를 추가**하고 옛 키는 이미 발급된 토큰이 검증되도록 얼마간 유예로 남겨 회전한다. 검증자는 매 요청마다 페치하면 발급자를 두드리게 되므로 JWK Set을 **캐시**하되, **모르는 `kid`를 만나면 다시 페치**한다. "캐시하되 미지 `kid`면 재페치"라는 이 한 줄이 회전 계약의 전부다 — 새 키가 검증자 재배포 없이 스스로 전파되는 통로다.

## 4. 우리 맥락 — 게이트 2가 아직 채우지 못한 페치

이 개념이 이 프로젝트의 배포 인증에서 서는 자리는 게이트 2다. 배포 게이트 1(HMAC + 신선도)이 "요청이 위조되지 않았고 신선한가"를 판정한 뒤, 게이트 2는 GitHub Actions가 발급한 **OIDC ID 토큰(RS256)**을 agent가 검증해 "이 요청이 정말 우리 파이프라인에서 왔는가"를 본다(정본: ADR-027 DO-11). 코드(`infra/internal/auth/oidc.go`)는 이 일을 둘로 나눈다 — **서명 검증**(`TokenVerifier`가 `KeySet`으로 발급자 공개키를 얻어 확인)과 **claim 행렬**(`checkClaims`)이다. JWKS 페치가 사는 곳이 바로 그 `KeySet.VerificationKey(kid)`다.

문제는 지금 그 페치가 **비어 있다**는 것이다. `infra/cmd/agent/main.go`의 `jwksScaffold`는 자리만 잡은 스캐폴드이고, `VerificationKey`는 값을 돌려주는 대신 `"JWKS 공개키 페치 미구현 (다음 마일스톤 — 발급자 JWKS HTTPS 페치)"` 오류를 낸다. 그래서 게이트 2는 지금 **어떤 키도 얻지 못하며**, fail-closed 설계상 이는 OIDC 토큰을 통과시키는 것이 아니라 **전부 거절**하는 것으로 귀결된다. 이슈 #11("JWKS 실 공개키 페치")이 이 자리를 채운다 — 발급자의 `jwks_uri`에서 GitHub의 공개키를 페치·캐시하고 회전을 추적해, 그때 비로소 실제 서명 검증이 선다.

그때까지 기계가 보증하는 경계는 HMAC + 신선도까지이고, OIDC 서명 검증은 막혀 있다. DO-11이 요구하는 것 — `iss` 하나로 고정, **RS256 고정**, `none`·HS256 방어(§5) — 중에서 서명 검증 자체를 실제로 세우는 조각이 JWKS다. 검증된 서명이 신뢰할 수 있는 claim을 내주기 전까지 claim 행렬은 대조할 대상이 없기 때문이다. (발급자 URL·회전·캐시가 플랫폼에서 실제로 서는 형태는 코드 주석이 `[구현 검증]`으로 표시해 둔 이연 항목이다.)

## 5. 보안 고려 — 신뢰의 뿌리가 페치와 알고리즘 고정에 있다

JWKS 검증이 새는 곳은 대개 몇 군데로 정해져 있다. 각각이 하나의 침입 경로를 연다.

**HTTPS로만 페치한다.** `jwks_uri`가 `https`여야 한다는 규정(OIDC Discovery)은 장식이 아니다. 평문 HTTP로 키를 가져오면 중간자(MITM)가 응답을 가로채 **가짜 공개키를 주입**할 수 있고, 그러면 공격자가 그 짝 개인키로 서명한 토큰이 버젓이 "검증"된다. 페치 채널의 무결성이 이후 모든 서명 검증의 신뢰 뿌리이므로, 여기가 뚫리면 아래가 전부 무의미해진다.

**알고리즘 혼동 공격(alg confusion)을 막는다.** 고전적 공격은 토큰이 헤더에 `"alg":"none"`(서명 없음)이나 `"alg":"HS256"`(대칭 HMAC)을 선언하는 것이다. 검증자가 토큰 자신의 `alg`를 믿으면, 공격자는 **공개된** 발급자 공개키를 HMAC 비밀키로 삼아 HS256 토큰을 위조하거나 `none`으로 서명을 통째로 없앨 수 있다. 방어는 **알고리즘을 토큰이 아니라 서버가 고정**하는 것이다. 우리 코드가 정확히 그렇게 한다 — `keyFunc` 진입에서 RSA가 아닌 서명 방식을 거절하고 `jwt.WithValidMethods([]string{"RS256"})`로 못박아, 공개키가 대칭 비밀로 오용될 여지를 닫는다(`oidc.go`).

**`kid`는 신뢰 경계 밖의 힌트다.** `kid`는 서명이 검증되기 전의 토큰, 즉 공격자가 만질 수 있는 값이다. 그래서 `kid`는 "가져온 JWK Set **안에서** 어느 키를 시도할지"를 좁히는 데만 쓰고, 그 이상을 시켜서는 안 된다 — 예컨대 `kid`가 파일 경로나 URL이라고 해서 검증자가 임의의 출처에서 키를 로드하게 두면 안 된다. `kid`는 선택지를 좁힐 뿐 새 출처를 인가하지 않는다.

**캐시 TTL과 회전 지연은 맞바꿈이다.** 캐시는 필요하지만 창을 하나 연다. 너무 오래 캐시하면 발급자가 **유출로 폐기한 키**가 은퇴 뒤에도 신뢰되고, 너무 짧으면 배포마다 발급자를 두드리다 잠깐의 불통에도 실패한다. 새 키는 §3의 "미지 `kid` 재페치"가, 폐기된 키는 유한한 TTL이 각각 맡는 축이다.

**페치 실패는 fail-closed다.** JWK Set을 못 가져오거나 `kid`에 맞는 키가 없으면 검증자는 통과가 아니라 **거절**해야 한다. 우리 `KeySet` 계약이 그대로 이 규칙이다 — 알 수 없는 `kid`·페치 실패는 오류이고 거절로 이어진다(`oidc.go`). 현재 스캐폴드가 무조건 오류를 내는 것은 이 규칙의 극단적 형태일 뿐이다.

## 6. 표준과 역사 — JOSE 제품군이 2015년 5월에 한꺼번에 나왔다

JWKS는 홀로 선 규격이 아니라 **JOSE**(JSON Object Signing and Encryption) 제품군의 한 조각이고, 이 계열은 2015년 5월에 함께 표준화됐다.

- **RFC 7519 — JWT**(JSON Web Token): 토큰 자체(header.payload.signature).
- **RFC 7515 — JWS**(JSON Web Signature): 서명, 그리고 어느 키로 서명했는지를 가리키는 `kid` JOSE 헤더 파라미터.
- **RFC 7517 — JWK**(JSON Web Key): 키 하나(JWK)와 키 집합(JWK Set — `keys` 배열).
- **RFC 7518 — JWA**(JSON Web Algorithms): 알고리즘과 키 재료, RSA의 `n`·`e`(§6.3.1)와 RS256.

그 위에서 **OpenID Connect Discovery 1.0**이 `/.well-known/openid-configuration` 설정 문서와 `jwks_uri` 필드를 정의해, 발급자를 그 JWK Set에 묶는다. 이 규격들이 함께 있어 검증자는 발급자 URL 하나에서 출발해 검증된 서명까지 도달한다 — 이 문서가 §3에서 따라간 그 경로다.
