# 01. LSM 계열 저장 구조의 병합 모델

> 교정 대상: "저장 후 재정렬한다" → **정렬은 쓰기 시점에 이미 끝나 있고, 백그라운드 작업은 재정렬이 아니라 머지 소트다.**

---

## 1. 쓰기 경로: 어디서 정렬이 끝나는가

```
write
  ├─▶ WAL (append-only, 내구성 확보)
  └─▶ memtable (인메모리 정렬 구조: skiplist / red-black tree)
            │  임계치 도달
            ▼
     immutable memtable ──flush──▶ SSTable (디스크, 정렬 완료, 불변)
                                        │
                                   compaction (여러 SSTable의 k-way merge)
                                        ▼
                                   새 SSTable
```

핵심:

1. **정렬은 memtable에서 이미 일어난다.** 인메모리 정렬 자료구조에 넣는 순간 순서가 잡힌다.
2. **디스크로 내려간 세그먼트는 불변(immutable)이다.** 수정도 삭제도 제자리에서 하지 않는다.
   - update = 새 버전 append
   - delete = tombstone 마커 append
3. **compaction은 재정렬이 아니다.** 이미 각각 정렬된 파일 N개를 읽어 하나의 정렬된 스트림으로 합치는 **머지 소트**다. 비교 정렬(O(n log n))이 아니라 N-way merge(O(n log N), N = 파일 수)다.

---

## 2. 그래서 병합 비용의 본질은 무엇인가

**틀린 직관**: 병합이 느린 건 락 경합/데드락 때문이다.
**실제**: 병합 대상 파일은 불변이라 **락 자체가 거의 필요 없다.** 비용은 전부 자원 경쟁이다.

| 비용 항목 | 내용 |
|---|---|
| **병합 I/O** | 같은 데이터를 레벨을 내려가며 여러 번 다시 쓴다 → **쓰기 증폭(write amplification)** |
| **CPU** | 머지, 압축(compression), 체크섬 |
| **페이지 캐시 오염** | 병합이 캐시를 밀어내 조회 성능이 같이 떨어진다 |
| **디스크 대역폭 경쟁** | 조회의 랜덤 읽기와 병합의 순차 읽기/쓰기가 같은 디바이스를 놓고 싸운다 |
| **공간 증폭** | 병합 중에는 원본과 결과물이 동시에 존재 |

> 정리 문장: **"병합은 정렬 비용이 아니라, 조회와 자원을 나눠 쓰는 백그라운드 재작성 비용이다."**

### 세 가지 증폭의 트레이드오프

병합 전략은 결국 셋 중 무엇을 포기할지의 선택이다.

| 전략 | 쓰기 증폭 | 읽기 증폭 | 공간 증폭 |
|---|---|---|---|
| **Leveled** (RocksDB 기본) | 높음 | 낮음 (레벨당 파일 1개만 확인) | 낮음 |
| **Tiered / Size-tiered** (Cassandra) | 낮음 | 높음 (같은 레벨에 겹치는 파일 다수) | 높음 |

읽기 증폭을 줄이는 보조 장치: **블룸 필터**(이 SSTable에 이 키가 없음을 싸게 확인), **스파스 인덱스**(파일 내 블록 위치).

---

## 3. 파생 교정: "프라이머리가 정렬하고 레플리카가 서빙" 모델은 없다

이 모델은 **Elasticsearch에도 ClickHouse에도 존재하지 않는다.** 둘 다 다르게 동작한다.

### Elasticsearch (Lucene 세그먼트)
- 프라이머리 샤드가 색인 → **레플리카 샤드에는 병합된 결과가 아니라 원본 연산이 복제**된다 (문서 단위 복제, 최신 버전에서는 시퀀스 번호 기반 복구).
- 따라서 **레플리카는 자기 자신의 세그먼트를 스스로 만들고 스스로 병합한다.**
- 결과: 프라이머리와 레플리카의 세그먼트 구성은 **같지 않다.** 병합 시점도 다르다.
- 실무 함의: 병합 부하는 레플리카에서도 똑같이 발생한다. "레플리카는 읽기만 하니 가볍다"가 성립하지 않는다.
- 관련 개념: `refresh`(새 세그먼트 생성 → 검색 가능) / `flush`(translog 비우고 Lucene commit) / `force_merge`(수동 병합, 쓰기 끝난 인덱스에만)

### ClickHouse (ReplicatedMergeTree)
- 레플리카끼리 Keeper(ZooKeeper)의 **복제 로그를 통해 조율**한다.
- 기본 동작은 각 레플리카가 같은 병합을 각자 수행하는 것이지만, **병합 결과 파트를 다른 레플리카에서 가져오는(fetch) 경로가 별도로 존재한다.**
  - `execute_merges_on_single_replica_time_threshold` — 한 레플리카만 병합하고 나머지는 받아오게
  - `prefer_fetch_merged_part_time_threshold` / `prefer_fetch_merged_part_size_threshold` — 큰/오래 걸리는 병합은 받아오는 쪽 선택
  - `always_fetch_merged_part` — 항상 받아오기
- 즉 "누가 병합하느냐"는 **아키텍처가 고정한 것이 아니라 설정으로 고르는 트레이드오프**다: CPU/IO를 아끼는 대신 네트워크를 쓴다.

> 한 줄로: **ES는 각자 병합, ClickHouse는 각자 병합이 기본이되 결과를 받아오는 옵션이 있다.**

## 4. 공부법: db-engine-lab에 LSM 붙이기

이미 B-Tree가 있으므로, 같은 인터페이스로 LSM 엔진을 하나 더 구현하면 두 구조의 차이가 **코드로 남는다.**

### 구현 순서 (각 단계마다 동작하는 상태 유지)

| 단계 | 만드는 것 | 확인할 것 |
|---|---|---|
| 1 | memtable (정렬 맵) + WAL append | 재시작 후 WAL 재생으로 복구되는가 |
| 2 | flush → SSTable 파일 (정렬된 KV + 스파스 인덱스 + footer) | 파일이 정렬되어 있는가 |
| 3 | 조회 경로: memtable → 최신 SSTable → 과거 순 | 최신 버전이 이기는가 |
| 4 | tombstone 삭제 | 삭제 후 조회가 없음을 반환하는가 |
| 5 | size-tiered compaction | 파일 수가 수렴하는가 |
| 6 | 블룸 필터 | 없는 키 조회의 디스크 접근 횟수 감소 측정 |
| 7 | leveled compaction | 쓰기 증폭 vs 읽기 증폭 수치 비교 |

### 반드시 계측할 것 (이게 실측 경험이 된다)
- **쓰기 증폭**: (실제 디스크에 쓴 바이트) / (유저가 쓴 바이트)
- **읽기 증폭**: 키 하나 조회에 접근한 SSTable 수 (블룸 필터 적용 전후)
- **공간 증폭**: 디스크 사용량 / 논리 데이터 크기
- **병합 중 조회 p99**: 병합 스레드를 켠 상태와 끈 상태의 조회 레이턴시 차이 ← **3번 항목(자원 경쟁)을 몸으로 증명하는 실험**

마지막 항목이 핵심이다. 이게 "병합 비용의 본질은 자원 경쟁"이라는 문장에 **본인 측정치를 붙여주는** 실험이다.

---

## 5. 면접용 한 문단 요약

> LSM은 쓰기를 인메모리 정렬 구조에 받고, 임계치에서 이미 정렬된 불변 세그먼트로 디스크에 떨군다. 그래서 백그라운드 컴팩션은 재정렬이 아니라 정렬된 파일들의 머지 소트고, 비용의 본질은 락이 아니라 쓰기 증폭과 조회와의 I/O·CPU 경쟁이다. Leveled는 쓰기 증폭을 대가로 읽기 증폭을 줄이고, tiered는 반대다. 복제 관점에서도 "한 노드가 병합하고 나머지는 서빙"이 기본은 아니다. ES는 레플리카가 각자 색인하고 각자 병합하며, ClickHouse는 각자 병합이 기본이되 병합 결과 파트를 fetch하도록 설정으로 바꿀 수 있다.
