# 00. 개발 분야별 평가 축 정리

> 백엔드 고유(Concurrency / Scalability / HA), 프론트 고유(UX), 공통(Performance / System Design / Maintainability)

---

## 1. 백엔드 고유 축

### Concurrency (동시성)
**정의**: 여러 실행 흐름이 같은 자원을 동시에 건드릴 때 **정확성**을 지키는 것.
성능(빠른가)이 아니라 정합성(틀리지 않는가)이 1차 관심사다.

**대표 실패**
- 재고 1개인데 동시에 2건 주문 → 재고 -1 (lost update)
- 중복 결제 요청 → 2회 승인
- 카운터 증가 누락 (read-modify-write 경쟁)

**도구**
| 도구 | 쓰는 자리 |
|---|---|
| 낙관적 락 (version 컬럼) | 충돌 빈도 낮음, 재시도 가능 |
| 비관적 락 (`SELECT ... FOR UPDATE`) | 충돌 잦음, 재시도 비용 큼 |
| 트랜잭션 격리 수준 | phantom / non-repeatable read 방어 |
| 멱등성 키 | 클라이언트 재시도가 중복이 되지 않게 |
| DB 유니크 제약 | 최후의 방어선. 애플리케이션 락보다 강함 |
| 커넥션 풀 사이징 | 동시성의 상한을 정하는 물리적 제약 |

**면접 포인트**: "락을 걸었습니다"가 아니라 **"어떤 실패를 막기 위해 어느 수준의 락을 골랐고, 그 대가는 무엇이었나"**.

---

### Scalability (확장성)
**정의**: 트래픽/데이터가 10배가 되면 **무엇이 먼저 터지는가**를 알고 그 지점을 옮기는 것.

**핵심 질문**: 수직 확장으로 못 가는 지점이 어디인가?

- **무상태화**: 세션을 서버 메모리에 두면 수평 확장 불가 → 외부 저장소로
- **읽기 확장**: 리드 레플리카, 캐시 (단, 복제 지연 = 읽기 정합성 문제)
- **쓰기 확장**: 샤딩 (샤드 키 선택이 사실상 되돌릴 수 없는 결정)
- **부하 평탄화**: 큐로 피크를 흡수, 동기 처리를 비동기로
- **병목 이동**: 앱 서버를 늘리면 DB 커넥션이 병목이 된다. 확장은 병목을 없애는 게 아니라 옮기는 것

---

### High Availability (고가용성)
**정의**: 일부 구성 요소가 죽어도 서비스 전체는 산다.

- **SPOF 제거**: 단일 인스턴스, 단일 AZ, 단일 리더
- **Failover**: 자동 승격, 헬스체크, 리더 선출
- **장애 전파 차단**: 서킷 브레이커, 타임아웃(가장 자주 빠뜨림), 벌크헤드
- **재시도 + 지수 백오프 + 지터**: 재시도는 잘못하면 장애를 증폭시킨다 (retry storm)
- **Graceful degradation**: 추천 기능이 죽어도 상품 상세는 뜬다

**측정**: 가용성은 "죽었냐"가 아니라 SLO(예: 99.9% 성공률) + 에러 버짓으로 말한다.

## 2. 프론트 고유 축

### UX (개발자 관점)
디자인 심미성이 아니라 **인터랙션이 답답하지 않은가**.

- **상태를 다 만들었는가**: loading / empty / error / partial — 성공 경로만 만든 화면은 미완성
- **낙관적 업데이트**: 서버 응답을 기다리지 않고 UI 먼저 반영, 실패 시 롤백
- **레이아웃 시프트**: 이미지/광고가 뒤늦게 들어와 클릭을 어긋나게 하지 않는가 (CLS)
- **입력 반응성**: 타이핑/클릭 후 100ms 안에 반응이 있는가 (INP)
- **접근성**: 키보드 탐색, 포커스 관리, 스크린리더 — 법적 요구사항인 경우도 많음

## 3. 공통 축 (분야마다 의미가 다름)

### Performance
| | 백엔드 | 프론트 |
|---|---|---|
| 지표 | p95/p99 레이턴시, 처리량(RPS) | LCP, INP, CLS, TTFB |
| 흔한 병목 | N+1 쿼리, 인덱스 미사용, 락 대기 | 번들 크기, 불필요한 리렌더 |
| 주요 수단 | 인덱스, 캐시, 배치, 커넥션 풀 | 코드 스플리팅, 메모이제이션, 이미지 최적화 |

> **평균이 아니라 꼬리(p99)를 본다.** 평균 응답 200ms에 p99가 5초면 사용자 1%는 서비스를 못 쓰는 것이다.

---

### System Design
**한 줄 정의**: 어떻게 쪼개고 **경계를 어디에 긋는가**.

- 백엔드: 서비스 분리 기준, 데이터 모델링, API 계약, 동기 vs 비동기, 저장소 선택(OLTP/OLAP/캐시/큐)
- 프론트: 컴포넌트 계층, **서버 상태와 클라이언트 상태의 분리**, 라우팅, 디자인 시스템

경계를 잘못 그으면 나중에 바꾸는 비용이 가장 큰 축이다. 되돌리기 쉬운 결정과 어려운 결정을 구분해서 말할 수 있어야 한다.

---

### Maintainability
**한 줄 정의**: 6개월 뒤의 내가 (또는 남이) 안전하게 고칠 수 있는가.

- 결합도↓ 응집도↑
- **테스트 가능한 구조** (테스트를 짰냐보다, 짤 수 있는 구조냐)
- 일관된 컨벤션, 타입 안정성
- 관측 가능성: 로그/메트릭/트레이스가 없으면 유지보수가 불가능하다
- 백엔드: 계층 분리, 비즈니스 로직을 프레임워크에서 떼어내기
- 프론트: 컴포넌트 재사용, prop drilling 회피, 상태 위치의 일관성

---

## 4. 이 구분은 완전히 깔끔하지 않다

의도적으로 기억해둘 교차점:

- **프론트에도 concurrency가 있다**: 늦게 도착한 옛날 응답이 최신 데이터를 덮어쓰는 race condition (요청 취소, 시퀀스 번호, `AbortController`)
- **프론트에도 HA가 있다**: CDN, 오프라인 캐시, API 실패 시 fallback UI
- **백엔드 레이턴시는 그대로 UX가 된다**: p99가 UX 지표다

> 면접에서 "이건 백엔드 영역이라"로 선을 긋기보다, **각 축을 자기 도메인 언어로 번역해서 말할 수 있으면** 훨씬 강하다.
