# 06. 트랜잭셔널 아웃박스 vs 발송 로그 패턴

> 핵심 명제: **저장 시점이 어떤 실패 계열을 닫는지 결정한다.**
> 두 패턴은 코드가 비슷해 보이지만 **닫는 실패가 다르다.**

---

## 1. 원인: 이중 쓰기(dual write) 문제

```java
@Transactional
public void createOrder(...) {
    orderRepo.save(order);           // ① DB
    kafkaTemplate.send("orders", e); // ② 브로커  ← 다른 시스템
}
```

①과 ②는 **서로 다른 시스템**이라 원자적으로 묶이지 않는다. (분산 트랜잭션/2PC는 성능·운영 비용 때문에 사실상 안 씀)

| 실패 지점 | 결과 |
|---|---|
| ① 성공, ② 실패 | 주문은 있는데 이벤트가 없음 → **다운스트림 미반영 (유실)** |
| ② 성공, ① 롤백 | 이벤트는 나갔는데 주문이 없음 → **유령 이벤트** |

> `@Transactional` 안에서 `send()`를 호출해도 **Kafka 전송은 롤백되지 않는다.** 이걸 모르고 짜는 코드가 가장 흔하다.

---

## 2. 두 패턴의 결정적 차이 = 저장 시점

### A. 트랜잭셔널 아웃박스 — **비즈니스 트랜잭션과 같이 저장**

```java
@Transactional
public void createOrder(...) {
    orderRepo.save(order);
    outboxRepo.save(new OutboxEvent(...));   // 같은 DB, 같은 트랜잭션
}   // 커밋: 둘 다 저장되거나 둘 다 안 되거나
```
```
[릴레이] outbox에서 미발행 행 폴링 (또는 CDC) → 브로커 발행 → ack 후 완료 표시
```

- **닫는 실패**: 발행 유실. 비즈니스 변경이 커밋됐다면 이벤트 행도 반드시 존재한다
- **남는 성질**: 중복 발행 (릴레이가 발행 후 완료 표시 전에 죽으면 재발행) → **소비 측 멱등성이 짝으로 필요** (05번 문서)
- **보장 등급**: at-least-once, 유실 없음

### B. 발송 로그(dispatch log) — **내보낼 때 저장**

```java
public void publish(Event e) {
    kafkaTemplate.send(...);          // 먼저 보내고
    dispatchLogRepo.save(...);        // 보낸 기록을 남김
}
```

- **기록의 목적**: 사후 추적/대조. 발행을 보장하는 장치가 아니다
- **남는 실패**: 비즈니스 트랜잭션은 커밋됐는데 발행 시도 자체가 없었던 구간 → **유실 창(window)이 남는다**
- **보장 등급**: best-effort

### 비교표

| | 트랜잭셔널 아웃박스 | 발송 로그 |
|---|---|---|
| 저장 시점 | 비즈니스 TX와 **함께** | 발행 **시점에** |
| 원자성 | ✅ 같은 DB 트랜잭션 | ❌ 없음 |
| 발행 유실 | 없음 | **가능** |
| 중복 | 있음 (멱등 소비 필요) | 있음 |
| 지연 | 릴레이 폴링 주기만큼 | 거의 없음 |
| 복잡도 | 릴레이/CDC 필요 | 낮음 |
| 순서 | 아웃박스 ID 순으로 보존 가능 | 보장 어려움 |

## 3. 본인 설계의 언어화

> **구조**: 발송 로그 + **원천 전량 대조 배치**가 유실 창을 메우는 형태

즉, 발행 경로에서는 유실을 막지 못하지만, **주기적으로 원천 데이터를 통째로 훑어 "이벤트가 나갔어야 하는데 안 나간 것"을 찾아 재발행**한다. 실시간 보장을 배치 정합성으로 대체한 설계다.

```
실시간 경로: 원천 변경 → 발행 시도 → 발송 로그 기록  (유실 가능)
           ─────────────────────────────────────
보정 경로:  배치 → 원천 전량 스캔 → 발송 로그와 대조 → 누락분 재발행
```

이건 **틀린 설계가 아니라, 성립 조건이 붙은 설계**다. 면접에서 이렇게 말하면 된다.

### 성립 조건 (둘 다 만족해야 함)

1. **이벤트가 원천 상태에서 재도출 가능해야 한다**
   현재 상태를 보고 "이 이벤트가 나갔어야 했다"를 판정할 수 있어야 배치가 누락을 찾는다.
2. **지연을 허용해야 한다**
   유실분은 다음 배치 주기까지 반영되지 않는다. 배치 주기 = **최대 복구 지연 시간(RTO)**.

### 성립하지 않는 경우 → 정식 아웃박스 필수

| 이벤트 성격 | 예시 | 재도출 가능? |
|---|---|---|
| **상태형** | "주문 상태 = 배송중", "재고 = 5" | ✅ 현재 상태를 보면 알 수 있음 |
| **사건형** | "주문이 승인됨", "쿠폰이 사용됨", "잔액이 100 차감됨" | ❌ **일어났다는 사실 자체가 소실되면 복구 불가** |

**결정적 구분**: **중간 상태 전이는 원천에 남지 않는다.**
`PENDING → APPROVED → SHIPPED`가 짧은 시간에 일어났다면, 배치가 나중에 봤을 때는 `SHIPPED`만 보인다. `APPROVED` 이벤트가 나갔어야 했다는 사실을 **알 방법이 없다.** 다운스트림이 그 전이에 반응해야 한다면 유실이 확정된다.

또한 **감사(audit)나 정산처럼 "발생 순간"이 의미를 갖는 이벤트**도 재도출로 대체할 수 없다.

> 정리 문장: **"상태를 동기화하는 파이프라인이면 대조 배치로 충분하고, 사건을 전달하는 파이프라인이면 아웃박스가 필수다."**

---

## 4. 제약: Redis에 아웃박스를 두면 안 되는 이유

아웃박스의 **유일한 존재 이유는 비즈니스 데이터와 같은 트랜잭션에 묶이는 것**이다.

```java
@Transactional
public void createOrder(...) {
    orderRepo.save(order);          // PostgreSQL
    redisTemplate.opsForList()...   // Redis ← 다른 시스템
}   // 롤백해도 Redis는 안 돌아옴
```

**Redis 아웃박스 = 이중 쓰기 문제를 그대로 한 칸 옮긴 것.** 아무것도 해결하지 못한다.

- Redis 트랜잭션(`MULTI/EXEC`)은 Redis 내부의 원자성일 뿐, RDBMS와는 무관하다
- Redis는 기본 구성에서 비동기 복제 + 주기적 영속화라 **장애 시 유실 자체가 정상 동작**이다
- 결론: **아웃박스는 비즈니스 데이터와 같은 DB, 같은 트랜잭션에 있어야만 아웃박스다.** 다른 저장소에 두면 이름만 아웃박스다.

(Redis Stream을 **큐**로 쓰는 건 별개 문제고 가능하다. 문제는 **아웃박스**로 쓰는 것.)

## 5. 릴레이 구현: 폴링 vs CDC

| | 폴링 릴레이 | CDC (Debezium 등) |
|---|---|---|
| 방식 | `SELECT ... WHERE published = false` 주기 조회 | WAL/binlog를 tail |
| 지연 | 폴링 주기 | 거의 실시간 |
| DB 부하 | 폴링 쿼리 부하 | 낮음 (로그만 읽음) |
| 인프라 | 없음 | Kafka Connect 등 추가 |
| 다중 인스턴스 | `SELECT ... FOR UPDATE SKIP LOCKED` 필요 | 커넥터가 관리 |

폴링 릴레이 핵심 쿼리:
```sql
SELECT * FROM outbox
WHERE published_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;   -- 여러 릴레이 인스턴스가 같은 행을 잡지 않도록
```

**공통 운영 포인트**
- 발행 후 완료 표시 사이의 크래시 → 재발행 → **소비 측 멱등성으로 흡수** (05번)
- 완료된 아웃박스 행은 주기적으로 정리(파티션 드롭 또는 아카이브). 안 그러면 테이블이 무한 증가
- 아웃박스 적체량에 알림을 건다 (릴레이 정지 감지)


## 7. 면접용 한 문단 요약

> 이중 쓰기 문제 때문에 DB 커밋과 브로커 발행은 원자적으로 묶이지 않는다. 트랜잭셔널 아웃박스는 이벤트를 비즈니스 트랜잭션과 **같은 트랜잭션**에 저장해서 발행 유실 계열을 닫고, 릴레이가 재발행하므로 중복은 남아 소비 측 멱등성이 짝으로 필요하다. 반면 발송 로그는 내보낼 때 기록하는 거라 사후 추적은 되지만 유실 창이 남는다. 제가 한 설계는 후자에 원천 전량 대조 배치를 붙여 그 창을 메우는 구조였는데, 성립 조건이 두 개다 — 이벤트가 원천 상태에서 재도출 가능할 것, 그리고 배치 주기만큼의 복구 지연을 허용할 것. "주문 승인됨" 같은 사건형 이벤트는 중간 상태 전이가 원천에 남지 않아 재도출이 불가능하므로 정식 아웃박스가 필수다. 그리고 아웃박스는 비즈니스 DB 안에 있어야만 의미가 있어서, Redis에 두면 원자성 자체가 성립하지 않는다.
