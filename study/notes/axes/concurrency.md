# Concurrency (동시성)

> **지키는 것: 정확성**
> "빠른가"가 아니라 **"틀리지 않는가"**의 축이다.

---

## 1. 왜 별도의 축인가

동시성은 성능과 자주 혼동되지만 방향이 반대다.
- **락을 걸면 느려진다.** 성능을 위해 락을 푸는 게 아니라, **정확성을 위해 성능을 내주는** 것
- 그래서 동시성 설계는 "얼마나 내줄 것인가"의 문제다

### 왜 어려운가
| 성질 | 결과 |
|---|---|
| **실패가 조용하다** | 예외도 로그도 없다. 며칠 뒤 정산이 안 맞아서 발견 |
| **재현이 안 된다** | 단일 스레드 테스트는 항상 통과 |
| **부하가 올라야 나타난다** | 개발·스테이징에서는 안 보인다 |
| **인스턴스가 늘면 방어가 무효화된다** | 로컬 락은 1대에서만 동작 |

---

## 2. 실패 유형 카탈로그

| 유형 | 시나리오 | 결과 |
|---|---|---|
| **Lost Update** | 둘이 같은 행을 읽고 각자 계산해서 씀 | 나중 쓰기가 앞 쓰기를 덮어씀 (재고, 잔액, 카운터) |
| **Write Skew** | 각자 조건 확인하고 각자 통과 | 둘 다 통과하면 안 되는데 통과 (당직 최소 1명인데 둘 다 퇴근) |
| **Phantom Read** | 범위 검사 중 새 행이 끼어듦 | "중복 없음" 확인 후 중복 삽입 |
| **Read Skew** | 여러 행을 읽는 중에 데이터가 바뀜 | 계좌 A는 이체 전, B는 이체 후 값을 읽음 |
| **중복 실행** | 클라이언트 재시도, 더블 클릭 | 결제 2회 |
| **데드락** | 서로의 락을 기다림 | 둘 다 멈춤 (DB가 하나를 죽여줌 — 그나마 다행) |
| **분산 중복** | 인스턴스 N대에서 스케줄러 N번 실행 | 정산 N배 |

---

## 3. 도구와 선택 기준

| 도구 | 쓰는 자리 | 대가 |
|---|---|---|
| **조건부 업데이트** | `UPDATE ... WHERE qty >= 1` → 영향 행 0이면 실패 | **가장 저렴하고 강력.** 먼저 검토할 것 |
| **낙관적 락** (version) | 충돌이 드물고 재시도 가능 | 충돌 잦으면 재시도 폭증 |
| **비관적 락** (`FOR UPDATE`) | 충돌 잦고 재시도 비용 큼 | 처리량 저하, 데드락 |
| **DB 유니크 제약** | 중복 삽입 방지 | **최후의 방어선.** 앱 로직보다 강함 |
| **CHECK 제약** | `qty >= 0` 등 불변식 | 마지막 안전망 |
| **트랜잭션 격리 수준** | phantom/read skew 방어 | 높일수록 느려짐. **격리 수준만으로 lost update는 안 막힌다** |
| **멱등성 키** | 클라이언트 재시도 흡수 | 키 저장소 필요 |
| **인박스 테이블** | 메시지 중복 소비 흡수 | 테이블·정리 필요 |
| **파티션 직렬화** | Kafka 키, actor 모델 | 애초에 동시 접근을 없앰. **확장성과 상성 좋음** |
| **분산 락** (Redis 등) | 여러 인스턴스 조율 | ⚠️ **정확성 보장이 아니다** (아래 참고) |

### 선택 순서 (실무)
```
1. 애초에 경합을 없앨 수 있나?      → 파티셔닝, 키 분산
2. 조건부 업데이트로 되나?          → 가장 저렴
3. 낙관적 락으로 되나?              → 충돌 빈도 확인
4. 비관적 락이 필요한가?            → 처리량 대가 감수
5. 그리고 항상: DB 제약을 최후 방어선으로
```

## 4. 분산 락에 대한 경고

**분산 락은 정확성 보장 수단이 아니다.**

```
프로세스 A: 락 획득 (TTL 10초)
프로세스 A: GC 일시정지 15초 ← 락이 만료됨
프로세스 B: 락 획득 (A가 죽은 줄 알고)
프로세스 A: 깨어나서 자기가 락을 가졌다고 믿고 작업 수행
→ 둘이 동시에 임계 구역에 있다
```

- TTL 만료, GC 정지, 네트워크 지연으로 **두 프로세스가 동시에 락을 가졌다고 믿을 수 있다**
- **분산 락은 "중복 작업을 줄이는 최적화"로만 쓴다**
- 정확성이 필요하면 **저장소 레벨의 조건부 쓰기나 펜싱 토큰**으로

---

## 5. 규모별 방어 범위

**같은 방어가 규모가 바뀌면 무효가 된다.**

| 범위 | 유효한 수단 | 무효해지는 것 |
|---|---|---|
| 단일 프로세스 | `synchronized`, `ReentrantLock`, `AtomicLong` | — |
| 다중 인스턴스 | DB 락, 조건부 업데이트, 유니크 제약 | **로컬 락 전부 무효** |
| 다중 리전 | 리전별 소유권 분할, CRDT | DB 락도 지연 문제 |

> **가장 흔한 사고: 단일 인스턴스에서 잘 동작하던 `synchronized`가, 인스턴스를 2대로 늘리는 순간 조용히 무효가 된다.** 코드는 그대로라 아무도 눈치채지 못한다.

## 6. 프론트엔드에도 동시성이 있다

| 문제 | 시나리오 | 해법 |
|---|---|---|
| **응답 경쟁 상태** | 빠르게 타이핑 → 늦게 온 옛 응답이 최신 결과를 덮어씀 | `AbortController`로 취소, 요청 시퀀스 번호 |
| **중복 제출** | 더블 클릭 | 제출 중 버튼 비활성화 + **서버 멱등성 키** (프론트만으로는 부족) |
| **낙관적 업데이트 충돌** | 여러 업데이트가 겹침 | 순서 보장, 실패 시 롤백 |

---

## 7. 자문 체크리스트

- [ ] 이 API가 **동시에 2번** 호출되면 어떻게 되는가
- [ ] 클라이언트가 재시도하면 중복이 생기는가
- [ ] 애플리케이션 로직이 뚫려도 **DB 제약이 막아주는가**
- [ ] 인스턴스가 2대가 되어도 이 방어가 유효한가
- [ ] 스케줄러·배치가 중복 실행되지 않는가
- [ ] 분산 락에 정확성을 의존하고 있지 않은가
- [ ] 트랜잭션 범위 안에 외부 API 호출이 있지 않은가 (락 유지 시간 폭증)

---

## 8. 면접에서 말하는 방식

**나쁜 답변**: "동시성 문제가 있어서 락을 걸었습니다."

**좋은 답변의 형태**
> "재고 차감에서 lost update가 발생할 수 있었습니다. 충돌 빈도가 낮아서 처음엔 낙관적 락을 검토했는데, 인기 상품은 충돌이 잦아 재시도가 폭증했습니다. 그래서 조건부 업데이트(`WHERE qty >= 1`)로 바꿔서 한 번의 쿼리로 확인과 차감을 원자적으로 처리했고, 최후 방어선으로 `CHECK (qty >= 0)` 제약을 걸었습니다."

**포함해야 할 요소**: 어떤 실패 유형인지 → 어떤 수단을 왜 골랐는지 → 무엇을 대가로 냈는지 → 최후 방어선이 무엇인지
