# Performance (성능)

> **지키는 것: 속도**
> 같은 일을 더 적은 시간·자원으로. (Scalability는 "더 많은 일을 감당", Performance는 "일 하나를 빨리")

---

## 1. 대원칙 3개

### ① 평균이 아니라 꼬리(tail)를 본다
```
평균 200ms, p99 5초
→ 사용자 100명 중 1명은 서비스를 못 쓴다
```
게다가 한 페이지가 API를 10개 호출하면, **그중 하나라도 느릴 확률**은 훨씬 높다.
→ **p99가 사실상의 체감 성능이다.**

**추가 규칙**: **성공과 실패를 분리해서 측정한다.** 빠르게 실패하는 요청이 많으면 평균 지연이 오히려 좋아 보인다.

### ② 측정 없이 최적화하지 않는다
병목은 직관과 거의 항상 다르다. 프로파일링 → 실행 계획 → 트레이스.

### ③ 가장 큰 병목부터 (암달의 법칙)
전체의 5%인 구간을 2배 빠르게 해도 전체는 2.5% 빨라진다.

## 2. 지표

| 분야 | 지표 | 기준 |
|---|---|---|
| **백엔드** | p50 / p95 / **p99** 지연 | 서비스마다 |
| | 처리량 (RPS) | |
| | 에러율 | |
| | 자원 포화도 (CPU, 스레드풀, 커넥션) | |
| **프론트** | **LCP** (주요 콘텐츠 표시) | 2.5초 이하 |
| | **INP** (입력 반응) | 200ms 이하 |
| | **CLS** (레이아웃 밀림) | 0.1 이하 |
| | TTFB | |

**체감 규칙**: 100ms 안에 반응이 있으면 즉각적으로 느끼고, 1초를 넘으면 흐름이 끊긴다.
→ 결과를 못 주더라도 **반응은 즉시 줘야 한다** (버튼 비활성화, 스피너).

---

## 3. 백엔드 병목 카탈로그

| 병목 | 진단 | 처방 |
|---|---|---|
| **N+1 쿼리** | 요청당 쿼리 수, 같은 형태 반복 | fetch join, batch size, DataLoader |
| **인덱스 미사용** | `EXPLAIN`에 Seq Scan | 복합 인덱스 (선택도 높은 컬럼 선두), 커버링 인덱스 |
| **잘못된 실행 계획** | 통계 낡음, 데이터 분포 변화 | `ANALYZE`, 힌트, 쿼리 재작성 |
| **락 대기** | 락 대기 시간, 스레드 덤프 | 트랜잭션 범위 축소, 락 순서 통일 |
| **커넥션 풀 대기** | 풀 대기 시간 지표 | **트랜잭션에서 외부 호출 제거**, 풀 재산정 |
| **직렬 호출** | 트레이스의 순차 구간 | 병렬화, 배치 API |
| **과도한 데이터** | 응답 크기, 전송 시간 | `SELECT *` 제거, 페이지네이션, 필요한 필드만 |
| **직렬화 비용** | CPU 프로파일 | 응답 축소, 포맷 변경 |
| **GC** | GC 로그, stop-the-world | 할당량 감소, 힙 조정 |

### 순서
```
1. N+1 제거          ← 효과가 가장 큼
2. 인덱스
3. 쿼리 재작성
4. 캐시              ← 여기서부터 복잡도가 는다
5. 비동기화 / 사전 계산
```

## 4. 프론트 병목 카탈로그

| 병목 | 처방 |
|---|---|
| **번들 크기** | 코드 스플리팅, 트리 셰이킹, 무거운 라이브러리 대체 |
| **불필요한 리렌더** | 메모이제이션, 상태를 필요한 곳으로 내리기, 리스트 key |
| **이미지** | 적절한 포맷/크기, lazy loading, 반응형 이미지 |
| **폭포수 요청** | 병렬 요청, 프리페치, SSR |
| **긴 메인 스레드 작업** | 가상 스크롤, 청크 분할, 웹 워커 |
| **폰트** | `font-display`, 프리로드 |

## 5. 캐시에 대한 균형 잡힌 시각

캐시는 성능 개선의 대표 수단이지만:

| 조건 | 결과 |
|---|---|
| 히트율 낮음 | 오버헤드만 증가 |
| 캐시 미스 경로가 느림 | **그게 그대로 p99가 된다** |
| 무효화 로직 복잡 | 새로운 버그 원천 |
| 캐시 의존도 높음 | **캐시가 죽으면 시스템이 죽는다** |

> **원칙: 먼저 쿼리를 고치고, 그 다음 캐시.**
> 순서를 바꾸면 근본 문제가 덮여서 나중에 캐시를 걷어낼 수 없게 된다.

---

## 6. 백엔드와 프론트의 접점

**백엔드 p99는 그대로 프론트 LCP가 된다.**

"백엔드는 빠른데 화면이 느리다"는 대부분 **측정 구간이 다른 것**이다.
- 백엔드: 앱 진입~응답 (예: 50ms)
- 실제 사용자: DNS + TLS + 네트워크 + 서버 + 다운로드 + 렌더 (예: 2초)

> **종단(end-to-end) 측정, 특히 RUM(실사용자 모니터링)이 있어야 대화가 된다.**
> 서버 로그의 응답 시간만 보면 영원히 "우리는 빠른데요"가 된다.

## 7. 성능 작업의 함정

| 함정 | 설명 |
|---|---|
| **조기 최적화** | 병목이 아닌 곳을 최적화하며 코드를 망가뜨림 |
| **마이크로 벤치마크 맹신** | JIT 워밍업, 캐시 효과로 실제와 다름 |
| **빈 DB에서 테스트** | 데이터가 쌓이면 완전히 다른 결과 |
| **평균만 보기** | p99를 놓침 |
| **가독성 희생** | 측정된 효과 없이 복잡도만 증가 |
| **로컬에서만 측정** | 네트워크 지연·동시성이 빠져 있음 |

---

## 8. 체크리스트

- [ ] p99를 측정하고 있는가 (평균만 보고 있지 않은가)
- [ ] 성공/실패 지연을 분리해서 보는가
- [ ] 요청당 쿼리 수를 아는가 (N+1 탐지)
- [ ] 느린 쿼리 상위 항목을 정기적으로 보는가
- [ ] 캐시 히트율을 측정하고, **미스 경로의 지연**을 아는가
- [ ] 프로덕션 규모 데이터로 테스트했는가
- [ ] 실사용자 관점(RUM) 지표가 있는가
- [ ] 최적화 전후를 **숫자로** 비교했는가

---

## 9. 면접에서 말하는 방식

**나쁜 답변**: "쿼리를 최적화해서 성능을 개선했습니다."

**좋은 답변의 형태**
> "목록 API의 p99가 3초였습니다. APM으로 보니 요청당 쿼리가 200개 넘게 나가는 N+1이었고, fetch join으로 3개로 줄여서 p99가 300ms가 됐습니다. 캐시도 검토했지만 데이터 변경이 잦아 히트율이 낮을 것 같아서, 쿼리를 먼저 고치는 쪽을 택했습니다."

**포함해야 할 요소**: 어떤 지표가 → 얼마였고 → 원인이 무엇이었고 → 어떻게 확인했고 → 얼마가 됐는가
