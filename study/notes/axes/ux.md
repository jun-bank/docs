# UX (개발자 관점)

> **지키는 것: 사용 가능성**
> 디자인이 예쁜가가 아니라 **인터랙션이 답답하지 않은가.**
> 디자이너가 아니라 **개발자가 책임지는 영역**이 분명히 있다.

---

## 1. 개발자가 책임지는 UX

디자인 시안에는 없지만 개발자가 결정하는 것들:

| 영역 | 개발자의 결정 |
|---|---|
| **상태 처리** | 로딩·빈·에러·부분 실패 화면을 만들었는가 |
| **반응 속도** | API 병렬화, 캐싱, 낙관적 업데이트 |
| **에러 메시지** | 사용자가 다음에 뭘 해야 할지 알 수 있는가 |
| **레이아웃 안정성** | 뒤늦게 들어온 콘텐츠가 화면을 밀어내지 않는가 |
| **접근성** | 키보드, 포커스, 스크린리더 |
| **재시도 안전성** | 더블 클릭이 중복 주문이 되지 않는가 |

---

## 2. 상태를 다 만들었는가

**성공 경로만 만든 화면은 미완성이다.**

| 상태 | 빠뜨리면 |
|---|---|
| **Loading** | 화면이 멈춘 것처럼 보임 → **사용자가 버튼을 다시 누름** (동시성 문제로 이어짐) |
| **Empty** | "데이터가 없음"과 "로딩 실패"를 구분 못 함 |
| **Error** | 무슨 일이 났는지 모름. **복구 수단(재시도 버튼)까지** 있어야 완성 |
| **Partial** | 일부만 실패했는데 전체를 못 쓰게 만듦 |
| **Stale** | 오래된 데이터를 최신인 것처럼 보여줌 |
| **Offline** | 네트워크 없는 상태에서 무한 로딩 |

> **스켈레톤 UI가 스피너보다 나은 이유**: 레이아웃을 미리 확보해서 로딩 후 화면이 튀지 않는다. 즉 CLS까지 같이 해결한다.

### 에러 메시지 원칙
| 나쁨 | 좋음 |
|---|---|
| "오류가 발생했습니다" | "일시적인 문제입니다. 다시 시도해 주세요" + 재시도 버튼 |
| "500 Internal Server Error" | (사용자에게 내부 코드를 노출하지 않되, **추적용 ID는 보여준다**) |
| 무엇을 해야 할지 없음 | **다음 행동**을 제시 |

---

## 3. 반응성

| 지표 | 의미 | 기준 |
|---|---|---|
| **LCP** | 주요 콘텐츠 표시 | 2.5초 이하 |
| **INP** | 입력 반응 지연 | 200ms 이하 |
| **CLS** | 레이아웃 밀림 | 0.1 이하 |

### 체감 규칙
- **100ms 이내**: 즉각적으로 느낀다
- **1초 이내**: 흐름이 유지된다
- **10초 이상**: 다른 일을 하러 간다

> **결과를 못 주더라도 "반응"은 즉시 줘야 한다.**
> 버튼 비활성화, 스피너, 낙관적 업데이트 — 무엇이든 100ms 안에 화면이 바뀌어야 한다.

### 레이아웃 시프트 (CLS)
이미지·광고·폰트가 뒤늦게 들어와 콘텐츠를 밀어내면, **누르려던 걸 못 누르고 엉뚱한 걸 누른다.** (결제 버튼 옆에 광고가 뜨는 케이스)
- 이미지에 `width`/`height` 또는 `aspect-ratio` 명시
- 폰트 로딩 전략(`font-display`)
- 동적 삽입 영역은 미리 공간 확보

---

## 4. 낙관적 업데이트

서버 응답을 기다리지 않고 UI를 먼저 바꾸고, 실패하면 되돌린다.

| 적합 | 부적합 |
|---|---|
| 좋아요, 북마크 | **결제** |
| 체크박스, 토글 | **삭제** (되돌리면 더 혼란) |
| 정렬·필터 | 잔액 변동 |
| 목록에 항목 추가 | 재고 확정 |

**기준: 실패했을 때 되돌리는 게 사용자에게 자연스러운가?**
- 좋아요가 잠깐 켜졌다 꺼지는 건 괜찮다
- "결제 완료"가 떴다가 취소되는 건 사고다

---

## 5. 프론트에도 있는 동시성 문제

| 문제 | 시나리오 | 해법 |
|---|---|---|
| **응답 경쟁 상태** | 빠르게 타이핑 → **늦게 온 옛 응답이 최신 결과를 덮어씀** | `AbortController` 취소, 요청 시퀀스 번호 |
| **중복 제출** | 더블 클릭 | 제출 중 비활성화 + **서버 멱등성 키** |
| **탭 간 상태 불일치** | 여러 탭에서 다른 상태 | `BroadcastChannel`, 포커스 시 재검증 |

> **프론트만으로는 중복 제출을 막을 수 없다.** 네트워크 재시도, 새로고침, 뒤로가기가 있다. **서버 멱등성이 있어야 완성이다.** → `./concurrency.md`

---

## 6. 접근성

**많은 나라에서 법적 요구사항이다.** 선택 사항이 아닌 경우가 있다.

- [ ] 키보드만으로 모든 기능에 도달 가능한가
- [ ] 포커스 표시가 보이는가 (`outline: none`만 하고 대체 스타일이 없는 경우가 흔함)
- [ ] **모달을 열면 포커스가 안으로 들어가고, 닫으면 원래 자리로 돌아오는가**
- [ ] 이미지 대체 텍스트, 폼 레이블이 있는가
- [ ] 색 대비가 충분한가 (색만으로 정보를 전달하지 않는가)
- [ ] 동적 변경이 스크린리더에 알려지는가 (`aria-live`)

## 7. 백엔드 개발자도 UX 지표를 갖는다

**백엔드 p99는 그대로 UX다.**

| 백엔드의 결정 | UX 결과 |
|---|---|
| p99 지연 | 사용자 1%의 체감 속도 |
| 에러 응답 형식 | 프론트가 좋은 에러 메시지를 만들 수 있는가 |
| 부분 실패 지원 | 일부 실패 시 나머지라도 보여줄 수 있는가 |
| 멱등성 제공 | 재시도가 안전한가 |
| 페이지네이션 방식 | 무한 스크롤이 가능한가 |
| 폴백 가능한 응답 | 추천 실패 시 인기 목록이라도 |

> 면접에서 "백엔드라 UX는 잘 모릅니다"보다, **"p99와 에러 응답 설계가 UX에 직결된다"**고 말하는 게 훨씬 강하다.

---

## 8. 체크리스트

- [ ] 모든 비동기 화면에 로딩·빈·에러 상태가 있는가
- [ ] 에러 화면에 **다음 행동**(재시도 등)이 있는가
- [ ] 버튼 클릭 후 100ms 안에 화면이 반응하는가
- [ ] 중복 제출이 막히는가 (프론트 + **서버 멱등성**)
- [ ] 늦게 온 응답이 최신 데이터를 덮어쓰지 않는가
- [ ] 이미지·동적 콘텐츠로 레이아웃이 밀리지 않는가
- [ ] 키보드만으로 사용 가능한가
- [ ] 실사용자 지표(RUM)를 측정하고 있는가

---

## 9. 면접에서 말하는 방식

**나쁜 답변**: "UX는 디자이너 영역이라서요."

**좋은 답변의 형태**
> "목록 화면에서 로딩 중에 사용자가 버튼을 여러 번 누르는 문제가 있었습니다. 프론트에서 제출 중 비활성화를 하고, 근본적으로는 서버에 멱등성 키를 도입해서 중복 요청이 같은 결과를 반환하게 했습니다. 그리고 스켈레톤 UI로 바꿔서 로딩 후 레이아웃이 튀는 것도 같이 해결했습니다."
