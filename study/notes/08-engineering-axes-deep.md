# 개발 분야별 평가 축 (확장판)

> 백엔드 고유: Concurrency / Scalability / High Availability
> 프론트 고유: UX
> 공통: Performance / System Design / Maintainability
>
> 이 문서의 목적은 **각 축을 "무엇을 지키는 활동인가"로 정의하고, 자신의 경험을 그 언어로 번역할 수 있게 하는 것**이다.

---

## 0. 왜 이렇게 나누는가

이 7개 축은 임의의 분류가 아니라 **서로 다른 실패를 막는 활동**이다. 헷갈리기 쉬운 지점부터 정리한다.

| 축 | 지키는 것 | 실패했을 때 |
|---|---|---|
| Concurrency | **정확성** | 데이터가 틀린다 (조용히) |
| Scalability | **성장 여력** | 트래픽이 늘면 못 버틴다 |
| Availability | **연속성** | 일부 고장이 전체 중단이 된다 |
| Performance | **속도** | 느리다 (동작은 한다) |
| System Design | **변경 비용** | 기능 추가가 갈수록 비싸진다 |
| Maintainability | **인수인계 가능성** | 아무도 못 고친다 |
| UX | **사용 가능성** | 동작은 하는데 쓰기 싫다 |

**가장 흔한 혼동 3가지**

1. **Concurrency ≠ Performance**
   동시성은 "빠른가"가 아니라 **"틀리지 않는가"**다. 락을 걸면 오히려 느려진다. 성능을 위해 락을 푸는 게 아니라, **정확성을 위해 성능을 내주는** 것이다.
2. **Scalability ≠ Performance**
   요청 1건이 10ms인 건 성능. 요청이 10배 와도 여전히 10ms인 건 확장성. **단일 요청이 아무리 빨라도 수평 확장이 막혀 있으면 확장성은 0이다.** (반대로 느려도 확장 가능한 시스템은 서버를 더 넣으면 된다)
3. **Availability ≠ Scalability**
   레플리카를 3대 두는 건 둘 다에 기여하지만 목적이 다르다. 확장성은 **부하 분산**, 가용성은 **대체 가능성**. 부하가 없어도 가용성을 위해 레플리카가 필요하다.

## 1. Concurrency (동시성)

### 정의
여러 실행 흐름이 **같은 자원을 동시에** 건드릴 때 정확성을 지키는 것.

### 왜 어려운가
**실패가 조용하다.** 예외도 안 나고 로그도 안 남는다. 재고가 -1이 된 걸 며칠 뒤에 발견한다. 게다가 **테스트에서 재현되지 않는다** — 단일 스레드 테스트는 항상 통과한다.

### 대표 실패 유형

| 유형 | 시나리오 | 결과 |
|---|---|---|
| **Lost update** | 두 요청이 같은 행을 읽고 각자 계산해서 쓴다 | 나중 쓰기가 앞 쓰기를 덮어씀 |
| **Write skew** | 각자 조건을 확인하고 각자 통과 | 둘 다 통과하면 안 되는데 통과 (예: 당직자 최소 1명 규칙에서 둘 다 퇴근) |
| **Phantom read** | 범위 조건 검사 중에 새 행이 끼어듦 | "중복 없음" 확인 후 중복 삽입 |
| **중복 실행** | 클라이언트 재시도, 더블 클릭 | 결제 2회 |
| **데드락** | 두 트랜잭션이 서로의 락을 기다림 | 둘 다 멈춤 (다행히 DB가 감지해서 하나를 죽임) |

### 도구와 선택 기준

| 도구 | 쓰는 자리 | 대가 |
|---|---|---|
| **낙관적 락** (version 컬럼) | 충돌이 드물고, 실패 시 재시도 가능 | 충돌 잦으면 재시도 폭증 |
| **비관적 락** (`SELECT ... FOR UPDATE`) | 충돌이 잦고, 재시도 비용이 큼 | 처리량 저하, 데드락 위험 |
| **트랜잭션 격리 수준** | phantom / non-repeatable read 방어 | 높일수록 느려짐. 그리고 **격리 수준만으로는 lost update가 안 막힌다** |
| **DB 유니크 제약** | 중복 삽입 방지 | 최후의 방어선. 앱 락보다 강함 |
| **멱등성 키** | 클라이언트 재시도가 중복이 되지 않게 | 키 저장소 필요 |
| **분산 락** (Redis 등) | 여러 인스턴스 간 조율 | **정확성 보장이 아니다** (TTL 만료, GC pause). 최적화 수단으로만 |
| **단일 파티션 직렬화** | Kafka 키 파티셔닝, actor 모델 | 애초에 동시 접근을 없앰 |
| **커넥션 풀 사이징** | 동시성의 물리적 상한 | 크면 DB가, 작으면 앱이 대기 |

### 사고의 순서 (실무에서 실제로 밟는 절차)
1. **경합하는 자원이 무엇인가** — 행 하나? 집계값? 외부 API 호출 횟수?
2. **경합 범위가 어디까지인가** — 단일 프로세스 / 인스턴스 간 / DB 레벨
3. **틀렸을 때 비용이 얼마인가** — 조회수 카운터가 몇 개 틀리는 것과 잔액이 틀리는 것은 다르다
4. **그제야 도구를 고른다**

> 순서를 거꾸로 밟으면(도구부터 고르면) "일단 락 걸었습니다"가 된다.

### 자문 체크리스트
- [ ] 이 API가 동시에 2번 호출되면 어떻게 되는가?
- [ ] 클라이언트가 재시도하면 중복이 생기는가?
- [ ] 애플리케이션 락이 뚫려도 DB 제약이 막아주는가?
- [ ] 인스턴스가 2대로 늘어나도 이 방어가 유효한가? (JVM 레벨 `synchronized`는 무효)

## 2. Scalability (확장성)

### 정의
트래픽·데이터가 10배가 되면 **무엇이 먼저 터지는지 알고, 그 지점을 옮길 수 있는가.**

### 핵심 통찰
**확장은 병목을 없애는 게 아니라 옮기는 것이다.**
앱 서버를 늘리면 → DB 커넥션이 병목이 되고 → 커넥션 풀을 늘리면 → DB CPU가 병목이 되고 → 읽기 복제본을 붙이면 → 쓰기가 병목이 된다.
**"지금 병목이 어디인지" 말할 수 있는 게 확장성 이해의 척도다.**

### 두 종류의 확장

| | 수직 확장 (scale up) | 수평 확장 (scale out) |
|---|---|---|
| 방법 | 더 큰 장비 | 더 많은 장비 |
| 난이도 | 쉬움 (코드 변경 없음) | 어려움 (상태 처리 필요) |
| 한계 | **물리적 상한 존재** | 이론상 무제한 |
| 가용성 | 기여 없음 (여전히 SPOF) | 기여함 |

> 실무 순서는 **수직 확장이 먼저다.** 장비 하나로 버틸 수 있으면 그게 훨씬 싸고 단순하다. 수평 확장은 못 버틸 때 지불하는 복잡도다.

### 수평 확장을 막는 것들

**1) 서버에 남는 상태**
- 세션을 서버 메모리에 두면 → 다른 서버로 요청이 가면 로그아웃됨
- 해법: 외부 세션 저장소, 또는 토큰(JWT)
- 같은 문제: 로컬 파일 업로드, 인메모리 캐시(불일치), 인메모리 스케줄러(중복 실행), 로컬 락

**2) 공유 자원의 단일 지점**
- 단일 DB 마스터, 단일 캐시 노드, 단일 큐 파티션

### 확장 수단별 정리

| 수단 | 해결하는 것 | 새로 생기는 문제 |
|---|---|---|
| **무상태화** | 앱 서버 수평 확장 | 세션 저장소가 새 의존성 |
| **읽기 복제본** | 읽기 부하 | **복제 지연** — 쓰고 바로 읽으면 없다 |
| **캐시** | 반복 조회 | 무효화, 스탬피드, 정합성 |
| **샤딩** | 쓰기·데이터 크기 | **샤드 키가 사실상 되돌릴 수 없는 결정.** 크로스 샤드 조인/트랜잭션 불가 |
| **큐** | 피크 흡수, 응답 분리 | 순서, 중복, 지연, 백프레셔 |
| **CQRS / 읽기 모델 분리** | 조회 최적화 | 최종적 일관성 |

### 확장성을 말하는 방식
"트래픽이 늘어도 괜찮게 설계했습니다"는 아무 정보가 없다. 대신:

> "현재 구조에서 가장 먼저 터지는 건 X입니다. 지금은 Y까지 버티고, 그 이상은 Z를 해야 합니다. 아직 안 한 이유는 (복잡도 / 아직 그 규모가 아님)입니다."

**"안 한 이유를 말할 수 있는 것"이 중요하다.** 모든 걸 다 한 시스템은 오버엔지니어링이다.

## 3. High Availability (고가용성)

### 정의
일부 구성 요소가 죽어도 **서비스 전체는 산다.**

### 측정부터 정의한다
가용성은 "죽었냐/살았냐"의 이분법이 아니라 **비율**이다.

| 가용성 | 연간 다운타임 | 월 다운타임 |
|---|---|---|
| 99% | 3.65일 | 7.3시간 |
| 99.9% | 8.8시간 | 43분 |
| 99.99% | 53분 | 4.3분 |
| 99.999% | 5.3분 | 26초 |

**9가 하나 늘 때마다 비용은 대략 한 자릿수씩 는다.** 그래서 "가용성 목표가 몇 9인가"를 먼저 정하고 거기에 맞는 투자를 한다. 무조건 높이는 게 정답이 아니다.

**SLI / SLO / 에러 버짓**
- SLI: 측정 지표 (예: 성공 응답 비율)
- SLO: 목표 (예: 99.9%)
- **에러 버짓**: 허용된 실패량 (99.9% 목표면 0.1%는 써도 되는 예산) → 이게 남아 있으면 배포·실험을 공격적으로, 소진했으면 안정화에 집중

### 장애를 다루는 4단계

**① 예방 — SPOF 제거**
- 단일 인스턴스, 단일 AZ, 단일 리더, 단일 커넥션
- 체크 방법: **구성 요소 하나씩 짚으며 "이게 죽으면?"을 물어본다**

**② 격리 — 장애 전파 차단**
| 도구 | 막는 것 |
|---|---|
| **타임아웃** | 무한 대기로 스레드가 고갈되는 것 — **가장 자주 빠뜨리는 것** |
| **서킷 브레이커** | 죽은 의존성을 계속 때려서 자원 낭비 + 복구 방해 |
| **벌크헤드** | 한 기능의 장애가 다른 기능의 스레드까지 먹는 것 |
| **레이트 리밋 / 로드 셰딩** | 과부하로 전체가 같이 죽는 것 (일부를 버려서 나머지를 살림) |

> **타임아웃이 없으면 서킷 브레이커도 의미가 없다.** 응답이 안 오는 걸 감지할 방법이 없기 때문.

**③ 복구 — Failover**
- 헬스체크(liveness vs readiness 구분), 자동 승격, 리더 선출
- **재시도는 양날의 검**: 지수 백오프 + **지터(jitter)** 없이 재시도하면 모든 클라이언트가 동시에 재시도해서 복구 중인 시스템을 다시 죽인다 (retry storm / thundering herd)

**④ 완화 — Graceful degradation**
- 추천 기능이 죽어도 상품 상세는 뜬다
- 실시간 재고가 안 오면 "재고 확인 중"으로 표시하고 주문은 받는다
- **핵심 기능과 부가 기능을 미리 나눠 두는 게 설계다.** 장애 났을 때 나누면 늦다

### 흔한 착각
- "이중화했으니 가용성이 확보됐다" → **failover가 실제로 동작하는지 테스트했는가?** 안 해본 failover는 없는 것과 같다
- "레플리카가 있으니 백업은 필요 없다" → **복제는 백업이 아니다.** 실수로 `DELETE`한 것도 그대로 복제된다

## 4. UX (프론트 고유, 개발자 관점)

### 정의
디자인 심미성이 아니라 **인터랙션이 답답하지 않은가.** 개발자가 책임지는 영역이 분명히 있다.

### ① 상태를 다 만들었는가
성공 경로만 만든 화면은 **미완성**이다.

| 상태 | 빠뜨리면 |
|---|---|
| **Loading** | 화면이 멈춘 것처럼 보임 → 사용자가 버튼 재클릭 (동시성 문제로 이어짐) |
| **Empty** | "데이터가 없음"과 "로딩 실패"를 구분 못 함 |
| **Error** | 무슨 일이 났는지 모름. **복구 수단(재시도 버튼)까지** 있어야 함 |
| **Partial** | 일부만 실패했을 때 전체를 못 쓰게 만듦 |
| **Stale** | 오래된 데이터를 최신인 것처럼 보여줌 |

> 스켈레톤 UI가 스피너보다 나은 이유: 레이아웃을 미리 확보해서 **로딩 후 화면이 튀지 않는다.**

### ② 낙관적 업데이트
서버 응답을 기다리지 않고 UI를 먼저 바꾸고, 실패하면 되돌린다.
- 적합: 좋아요, 체크박스, 정렬 — 실패해도 되돌리기 쉽고 피해가 작음
- 부적합: 결제, 삭제 — 되돌리기가 사용자를 더 혼란스럽게 함

### ③ 레이아웃 시프트 (CLS)
이미지/광고/폰트가 뒤늦게 들어와 콘텐츠를 밀어내면, **사용자가 누르려던 걸 못 누르고 엉뚱한 걸 누른다.**
- 이미지에 `width`/`height` 또는 `aspect-ratio` 명시
- 폰트 로딩 전략(`font-display`)
- 동적 삽입 영역은 미리 공간 확보

### ④ 반응성
| 지표 | 의미 | 기준 |
|---|---|---|
| **LCP** | 주요 콘텐츠가 그려지는 시점 | 2.5초 이하 |
| **INP** | 입력에 대한 반응 지연 | 200ms 이하 |
| **CLS** | 레이아웃 밀림 정도 | 0.1 이하 |

**체감 규칙**: 100ms 안에 반응이 있으면 즉각적으로 느끼고, 1초를 넘으면 흐름이 끊긴다.
→ **당장 결과를 못 주더라도 "반응"은 즉시 줘야 한다.** (버튼 비활성화, 스피너)

### ⑤ 접근성
- 키보드만으로 모든 기능에 도달 가능한가, 포커스가 보이는가
- 모달을 열면 포커스가 안으로 들어가고, 닫으면 원래 자리로 돌아오는가
- 이미지 대체 텍스트, 폼 레이블, 색 대비
- **많은 나라에서 법적 요구사항이다.** 선택 사항이 아닌 경우가 있다

### ⑥ 프론트에도 있는 concurrency
검색어를 빠르게 타이핑하면 요청이 여러 개 나가고, **늦게 도착한 옛날 응답이 최신 결과를 덮어쓴다.**
- 해법: `AbortController`로 이전 요청 취소, 요청 시퀀스 번호로 최신 응답만 반영, 디바운스

## 5. Performance

### 정의
**같은 일을 더 적은 시간·자원으로.** (Scalability는 "더 많은 일을 감당", Performance는 "일 하나를 빨리")

### 대원칙 3개

**① 평균이 아니라 꼬리를 본다**
평균 200ms에 p99가 5초면 **사용자 100명 중 1명은 서비스를 못 쓰는 것**이다. 그리고 한 페이지가 API를 10개 호출하면, 그중 하나라도 느릴 확률은 훨씬 높아진다 → **p99가 사실상의 체감 성능**이 된다.

**② 측정 없이 최적화하지 않는다**
병목은 직관과 거의 항상 다르다. 프로파일링/APM/실행 계획을 먼저 본다.

**③ 가장 큰 병목부터 (암달의 법칙)**
전체의 5%를 차지하는 코드를 2배 빠르게 해도 전체는 2.5% 빨라진다.

### 백엔드

| 병목 | 진단 | 처방 |
|---|---|---|
| **N+1 쿼리** | 쿼리 로그에 같은 형태 반복 | fetch join, batch size, DataLoader |
| **인덱스 미사용** | `EXPLAIN`에 Seq Scan | 복합 인덱스 (선택도 높은 순, 선두 컬럼 규칙) |
| **락 대기** | `pg_stat_activity`, 락 대기 시간 | 트랜잭션 범위 축소, 순서 통일 |
| **커넥션 고갈** | 풀 대기 시간 증가 | 트랜잭션 내 외부 API 호출 제거 |
| **직렬 호출** | 트레이스에 순차 구간 | 병렬화, 배치 API |
| **불필요한 데이터** | 응답 크기 | `SELECT *` 제거, 페이지네이션 |

**캐시는 만능이 아니다**: 히트율이 낮으면 오버헤드만 늘고, 무효화 로직이 새로운 버그 원천이 된다. **먼저 쿼리를 고치고, 그래도 안 되면 캐시.**

### 프론트

| 병목 | 처방 |
|---|---|
| **번들 크기** | 코드 스플리팅, 트리 셰이킹, 무거운 라이브러리 대체 |
| **불필요한 리렌더** | 메모이제이션, 상태를 필요한 곳으로 내리기 |
| **이미지** | 적절한 포맷/크기, lazy loading, 반응형 이미지 |
| **폭포수 요청** | 병렬 요청, 프리페치, SSR |
| **긴 작업** | 가상 스크롤, 청크 분할, 웹 워커 |

### 백/프론트 공통 함정
**백엔드 p99는 그대로 프론트 LCP가 된다.** "백엔드는 빠른데 화면이 느리다"는 대부분 측정 구간이 다른 것이다. **종단(end-to-end) 측정**이 있어야 대화가 된다.

## 6. System Design

### 정의
**어떻게 쪼개고, 경계를 어디에 긋는가.**

### 왜 가장 중요한가
**되돌리는 비용이 가장 큰 축**이기 때문이다. 코드는 리팩터링하면 되지만, 잘못 그은 서비스 경계나 샤드 키는 되돌리는 데 몇 달이 걸린다.

> 그래서 설계 논의의 핵심 질문은 **"이 결정은 되돌릴 수 있는가?"**다.
> 되돌리기 쉬운 결정은 빨리 정하고, 어려운 결정은 오래 고민한다.

| 되돌리기 쉬움 | 되돌리기 어려움 |
|---|---|
| 라이브러리 선택 | 데이터 모델 |
| 내부 클래스 구조 | 서비스 경계 |
| 캐시 도입 | 샤드 키 |
| 배포 방식 | 공개 API 계약 |
| | 동기 → 비동기 전환 |

### 백엔드 설계의 결정 지점

**1) 경계를 어디에 긋나**
- 기준은 **함께 변하는 것끼리 묶는다**(응집도). 기술 계층이 아니라 **비즈니스 능력** 단위
- 판별법: **"이 기능을 바꾸려면 몇 개 서비스를 동시에 배포해야 하나?"** 2개 이상이면 경계가 틀렸다
- **모놀리스가 기본값이다.** 경계가 확실해지기 전에 쪼개면 분산 모놀리스가 된다 (분산의 비용은 다 내고 이점은 없는 상태)

**2) 동기 vs 비동기**
| | 동기 (HTTP) | 비동기 (메시지) |
|---|---|---|
| 언제 | 즉시 응답 필요, 결과에 따라 분기 | 결과를 기다릴 필요 없음, 부하 평탄화 |
| 결합 | 강함 (상대가 죽으면 나도 영향) | 약함 |
| 비용 | 단순 | 순서·중복·지연·모니터링 복잡도 |

**3) 저장소 선택**
| 성격 | 선택 |
|---|---|
| 트랜잭션·정합성 | RDBMS |
| 대량 집계·분석 | 컬럼 지향 (ClickHouse) |
| 전문 검색 | Elasticsearch |
| 저지연 조회·휘발성 | Redis |
| 이벤트 스트림 | Kafka |

> **저장소를 늘릴 때마다 정합성 문제가 하나씩 생긴다.** RDBMS 하나로 될 일을 셋으로 나누면, 그 셋을 맞추는 게 새로운 일이 된다.

**4) API 계약**
- 버저닝, 하위 호환, 에러 형식 통일
- **소비자가 있는 API는 사실상 되돌릴 수 없다**

### 프론트 설계의 결정 지점

**1) 서버 상태 vs 클라이언트 상태 분리** — 가장 중요
| | 서버 상태 | 클라이언트 상태 |
|---|---|---|
| 예 | API로 받은 목록, 상세 | 모달 열림, 폼 입력, 필터 선택 |
| 성질 | 내가 소유하지 않음, 언제든 낡음 | 내가 소유함 |
| 도구 | 데이터 페칭 라이브러리 (캐시·재검증·무효화) | 로컬 state / 상태 관리 |

**서버 데이터를 전역 상태에 통째로 넣는 것이 가장 흔한 설계 실수다.** 캐싱·무효화·로딩·에러를 전부 직접 만들게 된다.

**2) 상태의 위치** — 필요한 가장 가까운 곳에 둔다. 전역은 최후의 수단
**3) 컴포넌트 경계** — 재사용 단위 vs 도메인 단위 구분
**4) 라우팅 / 코드 스플리팅 경계**

## 7. Maintainability

### 정의
**6개월 뒤의 내가(또는 남이) 안전하게 고칠 수 있는가.**

### 핵심 전환
"코드가 깨끗한가"가 아니라 **"변경이 안전한가"**로 질문을 바꾼다. 예쁜데 못 고치는 코드가 있고, 투박한데 안전하게 고칠 수 있는 코드가 있다.

### 구성 요소

**① 결합도↓ 응집도↑**
- 한 곳을 고치면 몇 곳이 따라 바뀌는가 = 결합도
- 관련된 코드가 한 곳에 모여 있는가 = 응집도
- **판별법**: 기능 하나를 바꿀 때 열어야 하는 파일 수

**② 테스트 가능한 구조** ← 가장 중요
> 질문은 "테스트를 짰는가"가 아니라 **"테스트를 짤 수 있는 구조인가"**다.

테스트가 안 짜지는 코드는 대개 **의존성이 안에 하드코딩되어 있고, 부수효과와 로직이 섞여 있다.** 즉 **테스트 용이성은 설계 품질의 지표**다.
- 비즈니스 로직이 프레임워크·DB·시간(`now()`)·랜덤에 직접 묶여 있지 않은가
- 테스트가 느리면(전부 통합 테스트) 아무도 안 돌린다

**③ 관측 가능성 (Observability)**
운영 중인 시스템은 **못 보면 못 고친다.**
| 축 | 답하는 질문 |
|---|---|
| **로그** | 무슨 일이 있었나 (구조화, 상관관계 ID 필수) |
| **메트릭** | 얼마나 자주, 얼마나 오래 |
| **트레이스** | 어디서 시간을 썼나 (분산 시스템에선 필수) |

**④ 일관성**
- 같은 문제를 같은 방식으로 푼다. **일관되게 평범한 것이 군데군데 뛰어난 것보다 낫다** — 읽는 사람이 예측할 수 있기 때문
- 컨벤션은 문서가 아니라 **자동화(린터·포매터·CI)로 강제**한다. 사람이 지키게 하면 안 지켜진다

**⑤ 타입 안정성** — 컴파일 타임에 잡히는 버그는 런타임 버그보다 100배 싸다

**⑥ 문서화 — 무엇을 남기나**
- 코드를 읽으면 아는 것(**무엇을** 한다)은 안 적는다
- 코드를 읽어도 모르는 것(**왜** 이렇게 했나, 어떤 대안을 왜 버렸나)을 적는다
- **ADR(Architecture Decision Record)**: 결정·맥락·대안·결과를 짧게 남김. 6개월 뒤의 "이거 왜 이렇게 돼 있지?"를 막는다

### 분야별
- **백엔드**: 계층 분리, 비즈니스 로직을 프레임워크에서 떼어내기, 트랜잭션 경계 명시, 마이그레이션 관리
- **프론트**: 컴포넌트 재사용, prop drilling 회피, 디자인 토큰, 스타일 격리

## 8. 축들 사이의 트레이드오프

**축은 독립적이지 않다. 하나를 올리면 다른 게 내려간다.** 이걸 말할 수 있으면 이해도가 드러난다.

| 충돌 | 내용 |
|---|---|
| **Concurrency ↔ Performance** | 락은 정확성을 사고 처리량을 판다 |
| **Consistency ↔ Availability** | CAP. 분단 시 정합성을 지키면 일부 요청을 거절해야 한다 |
| **Scalability ↔ Consistency** | 복제·샤딩은 최종적 일관성을 부른다 |
| **Performance ↔ Maintainability** | 캐시·비정규화·수동 튜닝은 복잡도를 늘린다 |
| **Availability ↔ 비용** | 9 하나에 비용 한 자릿수 |
| **System Design ↔ 속도** | 미리 쪼개면 오버엔지니어링, 안 쪼개면 나중에 비쌈 |
| **UX ↔ Consistency** | 낙관적 업데이트는 잠깐 거짓말을 한다 |

> 좋은 답변의 형태: **"A를 위해 B를 얼마만큼 내줬고, 그 판단의 근거는 C였습니다."**
> 나쁜 답변: "성능도 좋고 확장성도 좋고 유지보수도 좋게 만들었습니다."

## 9. 경계는 깔끔하지 않다 (교차 번역)

면접에서 **"그건 제 영역이 아니라서요"**로 선을 긋는 것보다, 각 축을 자기 도메인 언어로 번역하는 게 훨씬 강하다.

| 축 | 백엔드 버전 | 프론트 버전 |
|---|---|---|
| **Concurrency** | 행 락, 격리 수준 | 응답 경쟁 상태, 요청 취소, 낙관적 업데이트 롤백 |
| **Availability** | 이중화, failover | CDN, 오프라인 캐시, API 실패 시 fallback UI |
| **Scalability** | 샤딩, 복제 | 가상 스크롤, 페이지네이션, 점진적 로딩 |
| **UX** | **p99 레이턴시, 에러 메시지 품질, 멱등성(재시도 안전)** | 인터랙션 반응성 |
| **Maintainability** | 계층 분리 | 컴포넌트 경계 |

**특히 기억할 두 가지**
- **백엔드 p99는 그대로 UX다.** 백엔드 개발자도 UX 지표를 갖는다
- **프론트에도 동시성이 있다.** 늦게 온 옛 응답이 최신 데이터를 덮어쓰는 문제

## 10. 자기 경험을 이 축으로 번역하기

### 번역 템플릿
> **[상황]** 어떤 규모/제약에서
> **[축]** 어떤 축의 문제였고
> **[선택]** 무엇을 골랐고
> **[대가]** 무엇을 내줬고
> **[측정]** 어떻게 확인했는가

**예시**
> "일 500만 건 이벤트 파이프라인에서(상황) 발행 유실을 막는 게 문제였는데(Concurrency/신뢰성), 정식 아웃박스 대신 발송 로그 + 대조 배치를 택했습니다(선택). 실시간 보장을 배치 주기만큼의 복구 지연으로 바꾼 것이고(대가), 이게 성립한 건 이벤트가 원천 상태에서 재도출 가능했기 때문입니다. 대조 배치의 누락 검출 건수를 지표로 봤습니다(측정)."

### 자기 점검 매트릭스
프로젝트별로 채워보고, **빈칸이 곧 다음 공부 주제이자 예상 질문**이다.

| 축 | 내 사례 | 측정한 수치 | 내준 대가 |
|---|---|---|---|
| Concurrency | | | |
| Scalability | | | |
| Availability | | | |
| Performance | | | |
| System Design | | | |
| Maintainability | | | |
| UX | | | |

> **모든 칸을 채운 시스템은 없다.** 안 한 것을 "안 했다"가 아니라 **"이런 이유로 안 했다"**로 말할 수 있으면 그게 더 좋은 답이다.

## 11. 한 문단 요약

> 백엔드 고유 축은 동시성(정확성), 확장성(성장 여력), 가용성(연속성)이고, 프론트 고유 축은 UX(사용 가능성)다. 성능·시스템 설계·유지보수는 공통이지만 분야마다 지표와 수단이 다르다. 이 축들은 독립적이지 않아서 하나를 올리면 다른 게 내려가고, 그래서 좋은 설계 설명은 "다 좋게 만들었다"가 아니라 "무엇을 위해 무엇을 얼마만큼 내줬는가"의 형태를 띤다. 그리고 경계도 깔끔하지 않다. 프론트에도 응답 경쟁 상태라는 동시성 문제가 있고, 백엔드 p99는 그대로 UX 지표가 된다. 그래서 각 축을 자기 도메인 언어로 번역해서 말할 수 있는 게 실제 실력에 가깝다.
