# 02. 요청 경로 계층별 설계

> 사용자의 요청이 지나가는 길을 순서대로 따라가며, **각 지점에서 무엇을 결정해야 하는가**를 정리한다.

```
사용자
 │
 ├─ DNS / GSLB          ← 어느 리전으로?
 ├─ CDN / 엣지           ← 여기서 끝낼 수 있나?
 ├─ L4 로드밸런서        ← 어느 존으로?
 ├─ L7 로드밸런서/게이트웨이 ← 어느 서비스로? 통과시킬까?
 ├─ 앱 서버 (무상태)
 ├─ 캐시
 └─ DB
```

**원칙: 가능한 한 앞에서 끝낸다.** 뒤로 갈수록 비싸고, 뒤로 갈수록 확장이 어렵다.

---

## 1. DNS / GSLB — 리전 라우팅

| 방식 | 특징 |
|---|---|
| **DNS 라운드로빈** | 가장 단순. **장애 감지 못 함** (죽은 IP도 계속 응답) |
| **가중 라우팅** | 리전별 트래픽 비율 조정, 점진적 전환에 유용 |
| **지연 기반 라우팅** | 가장 가까운 리전으로 |
| **헬스체크 기반 failover** | 죽은 리전을 레코드에서 제외 |
| **Anycast** | 같은 IP를 여러 위치에 광고, 네트워크가 가까운 곳으로 |

### 함정: TTL
DNS 레코드를 바꿔도 **캐시된 TTL만큼은 옛 주소로 간다.** 클라이언트/중간 리졸버가 TTL을 무시하기도 한다.
→ **DNS는 failover 수단으로는 느리다.** 초 단위 전환이 필요하면 Anycast나 LB 레벨 전환을 쓴다.
→ 전환 예정이면 미리 TTL을 낮춰둔다 (예: 하루 전 60초로).

---

## 2. CDN / 엣지

**가장 효과 대비 비용이 좋은 확장 수단.** 오리진에 오지 않는 요청이 최고의 최적화다.

| 대상 | 캐시 가능성 |
|---|---|
| 정적 자산 (JS/CSS/이미지) | 즉시 가능. 파일명 해싱 + 긴 TTL |
| 공개 API 응답 | 가능 (`Cache-Control: s-maxage`) |
| 개인화 응답 | 어려움. 공통 부분만 분리하거나 엣지 컴퓨팅 |

### 핵심 헤더
```
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=86400
```
- `max-age` 브라우저 / `s-maxage` CDN
- **`stale-while-revalidate`**: 만료돼도 일단 옛 것을 주고 뒤에서 갱신 → **오리진 부하 급감 + 응답 지연 제거**. 가용성에도 기여(오리진이 죽어도 옛 응답 제공)
- `stale-if-error`: 오리진 에러 시 옛 응답 사용

### 캐시 키 설계
쿼리 파라미터 순서, 추적용 파라미터(`utm_*`), 쿠키가 캐시 키에 들어가면 **히트율이 0에 수렴한다.** 캐시 키에서 제외할 것을 명시한다.

## 3. 로드밸런서

### L4 vs L7
| | L4 (TCP) | L7 (HTTP) |
|---|---|---|
| 판단 근거 | IP/포트 | 경로, 헤더, 쿠키 |
| 성능 | 빠름 | 상대적으로 느림 |
| 기능 | 단순 분배 | 경로 라우팅, 리트라이, 헤더 조작, TLS 종료 |

보통 **L4 → L7 2단 구성**을 쓴다.

### 분배 알고리즘
| 알고리즘 | 적합한 상황 | 함정 |
|---|---|---|
| **Round Robin** | 요청 비용이 균일 | 무거운 요청이 한 서버에 몰릴 수 있음 |
| **Least Connections** | 요청 처리 시간이 제각각 | **일반적으로 가장 무난한 기본값** |
| **EWMA / 최소 응답시간** | 인스턴스 성능 편차 | 느려진 인스턴스를 자동 회피 |
| **Consistent Hashing** | 캐시 지역성 필요 | 노드 변동 시 일부만 재배치 |
| **Random 2-choice** | 대규모 | 2개 뽑아 덜 바쁜 쪽 — 단순한데 효과 좋음 |

> **Least Connections의 함정**: 방금 재시작해서 커넥션이 0인 서버로 트래픽이 한꺼번에 몰린다(콜드 스타트 폭탄). → **슬로우 스타트(ramp-up)** 설정 필요.

### 헬스체크 — 3종 구분
| 종류 | 질문 | 실패 시 |
|---|---|---|
| **Liveness** | 프로세스가 살아 있나 | 재시작 |
| **Readiness** | 트래픽을 받을 준비가 됐나 | **트래픽에서 제외 (재시작 아님)** |
| **Startup** | 부팅이 끝났나 | 초기화 오래 걸리는 앱의 오탐 방지 |

**설계 함정 — 깊은 헬스체크(deep health check)의 연쇄 실패**
헬스체크가 DB까지 확인하도록 만들면, **DB가 잠깐 느려질 때 모든 인스턴스가 동시에 unhealthy가 되어 서비스 전체가 내려간다.**

> 원칙: **liveness는 얕게(프로세스 자체만), readiness는 필요한 만큼만.** 의존성 상태는 헬스체크가 아니라 서킷 브레이커로 다룬다.

## 4. API 게이트웨이

앱에 도달하기 전에 처리하면 좋은 것들을 모은다.

| 기능 | 이유 |
|---|---|
| 인증/인가 (1차) | 모든 서비스가 중복 구현할 필요 없음 |
| **레이트 리밋** | 앱 자원을 쓰기 전에 차단 — **가용성의 1차 방어선** |
| 라우팅 / 버저닝 | 클라이언트에 내부 구조를 노출하지 않음 |
| 요청 크기 제한 | 대용량 요청으로 인한 메모리 고갈 방지 |
| 관측 (trace id 주입) | 종단 추적의 시작점 |

### 레이트 리밋 알고리즘
| 알고리즘 | 특징 |
|---|---|
| **Fixed Window** | 단순. 경계에서 2배 버스트 허용되는 문제 |
| **Sliding Window Log** | 정확. 메모리 많이 씀 |
| **Sliding Window Counter** | 절충안. 실무 기본값 |
| **Token Bucket** | 버스트 허용하면서 평균 제한 — **가장 널리 쓰임** |
| **Leaky Bucket** | 출력 속도를 일정하게 (하위 시스템 보호) |

**설계 포인트**: 무엇을 기준으로 제한하나 — IP / 사용자 / API 키 / 엔드포인트별. 그리고 **429 응답에 `Retry-After`를 반드시 넣는다.** 안 넣으면 클라이언트가 즉시 재시도해서 상황을 악화시킨다.

## 5. 앱 계층

### 세션 처리 — 스티키 세션은 최후 수단
| 방식 | 문제 |
|---|---|
| **스티키 세션** | 서버 죽으면 그 세션 전부 유실. **배포 시 문제. 부하 불균형.** 오토스케일과 상성 나쁨 |
| **외부 세션 저장소** | Redis 등. 네트워크 홉 추가되지만 표준 해법 |
| **토큰 (JWT)** | 서버 상태 없음. 대신 **즉시 무효화가 어렵고** 크기가 큼 |

> 실무 절충: **짧은 수명 액세스 토큰 + 서버측 리프레시 토큰.** 무상태성과 무효화 가능성을 절충.

### 연결 관리
- **Keep-Alive**: 커넥션 재사용. 없으면 TCP+TLS 핸드셰이크 비용이 매 요청마다
- **HTTP/2**: 멀티플렉싱. 단, **L7 LB 뒤에서 커넥션이 한 서버에 고정되어 부하가 쏠릴 수 있다** → LB에서 요청 단위 분배 설정 확인
- **커넥션 풀**: 앱 → DB/외부 API. Little's Law로 크기 산정 (01번 문서)
- **파일 디스크립터 한계** (`ulimit -n`): 고동시성에서 자주 막히는 지점

### Graceful Shutdown — 무중단 배포의 핵심
종료 신호를 받았을 때의 순서:

```
1. readiness를 false로 (LB가 새 트래픽을 안 보내게)
2. LB가 인지할 때까지 대기  ← 이 단계를 빠뜨리는 경우가 대부분
3. 진행 중인 요청 처리 완료 대기 (드레이닝, 타임아웃 설정)
4. 커넥션 풀·큐 컨슈머 정리
5. 종료
```

**2번을 빼면 무중단 배포가 아니다.** readiness를 false로 바꿔도 LB의 헬스체크 주기(예: 5초 × 3회)만큼은 트래픽이 계속 온다. 그 사이에 프로세스를 죽이면 **502가 발생한다.**

```yaml
# Kubernetes 예
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 15"]   # LB 전파 대기
terminationGracePeriodSeconds: 60
```

## 6. 계층별 체크리스트

- [ ] CDN에서 끝낼 수 있는 요청이 오리진까지 오고 있지 않은가
- [ ] 캐시 키에 불필요한 파라미터가 들어가 히트율을 깎고 있지 않은가
- [ ] 헬스체크가 의존성까지 확인해서 연쇄 실패를 만들 위험이 있는가
- [ ] LB에 슬로우 스타트가 설정되어 있는가
- [ ] 레이트 리밋 응답에 `Retry-After`가 있는가
- [ ] 앱이 무상태인가 (01번 체크리스트)
- [ ] Graceful shutdown에 LB 전파 대기 단계가 있는가
- [ ] 파일 디스크립터·포트 한계에 여유가 있는가
