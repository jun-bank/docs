# 01. 확장의 기본 원리

> 개별 기법을 외우기 전에, **왜 그 기법이 필요한가**를 만드는 원리 4개.

---

## 1. 확장은 병목을 없애는 게 아니라 옮기는 것이다

```
앱 서버 증설 → 병목이 DB 커넥션으로 이동
커넥션 풀 확대 → 병목이 DB CPU로 이동
읽기 복제본 추가 → 병목이 쓰기(마스터)로 이동
샤딩 → 병목이 크로스 샤드 쿼리로 이동
```

**따라서 확장성 이해의 척도는 "지금 병목이 어디인지 말할 수 있는가"다.**
병목이 어딘지 모른 채 서버를 늘리면, 돈만 쓰고 아무것도 안 빨라진다.

### 병목 후보를 훑는 순서
1. **포화된 자원**: CPU / 메모리 / 디스크 IOPS / 네트워크 대역폭
2. **한정된 슬롯**: 스레드 풀, 커넥션 풀, 파일 디스크립터, 포트
3. **직렬 구간**: 락, 단일 리더, 단일 파티션, 전역 카운터
4. **외부 의존**: 서드파티 API의 레이트 리밋

> 병목이 3번(직렬 구간)이면 **장비를 아무리 늘려도 소용없다.** 1·2번은 돈으로 해결되지만 3번은 설계로만 해결된다.

---

## 2. Little's Law — 용량 산정의 기본 공식

```
L (동시 처리 건수) = λ (도착률, RPS) × W (평균 처리 시간)
```

### 왜 중요한가
**스레드 풀·커넥션 풀 크기를 감으로 정하지 않게 해준다.**

예시: 목표 1,000 RPS, 평균 응답 200ms
```
L = 1000 × 0.2 = 200
→ 동시에 200건이 처리 중이어야 함
→ 워커 스레드가 200개 필요 (또는 비동기로 200건 동시 진행)
```

응답 시간을 100ms로 줄이면 필요 스레드는 100개로 준다.
**성능 개선은 그대로 용량 확보가 된다.**

### 역방향 활용 — 이게 더 자주 쓴다
큐 대기가 쌓이면: `대기 시간 = 큐 길이 / 처리율`
- 큐에 10,000건, 처리율 100/s → 지금 넣은 건 100초 뒤에 처리됨
- **큐 길이만 보지 말고 "지금 넣으면 언제 나오나"를 지표로 만든다**

---

## 3. Universal Scalability Law — 노드를 늘려도 안 빨라지는 이유

이상적으로는 서버 2배 → 처리량 2배여야 하지만 실제로는:

```
            N
C(N) = ─────────────────────────
       1 + α(N−1) + βN(N−1)
```
- **α (경합, contention)**: 직렬 구간. 락, 단일 DB — 증가분을 깎는다
- **β (일관성 비용, coherence)**: 노드끼리 상태를 맞추는 비용 — **노드 수의 제곱으로 는다**

### 실무적 결론
| | 증상 | 원인 | 처방 |
|---|---|---|---|
| α만 있음 | 늘려도 점점 덜 빨라짐 (수렴) | 직렬 구간 | 락 범위 축소, 샤딩 |
| β가 있음 | **늘리면 오히려 느려짐** | 노드 간 조율 | 조율 자체를 줄임 (파티셔닝, 비동기, 최종적 일관성) |

> **"서버를 늘렸는데 더 느려졌다"는 β 때문이다.** 분산 락, 분산 트랜잭션, 전체 노드 브로드캐스트, 캐시 동기화가 대표적. 그래서 **조율이 필요 없게 데이터를 나누는 것(파티셔닝)이 확장의 본질**이다.

## 4. 상태가 확장을 막는다

### 무상태화 체크리스트
아래가 하나라도 있으면 수평 확장이 막히거나 버그가 난다.

| 상태 | 증상 | 해법 |
|---|---|---|
| **세션을 서버 메모리에** | 다른 서버로 가면 로그아웃 | 외부 세션 저장소 / 토큰 |
| **로컬 파일 업로드** | 다른 서버에서 파일 못 찾음 | 오브젝트 스토리지 |
| **인메모리 캐시** | 인스턴스마다 값이 다름 | 분산 캐시, 또는 짧은 TTL 감수 |
| **인메모리 스케줄러** | **N대면 N번 실행** | 분산 스케줄러, 리더 선출, DB 락 |
| **`synchronized` / 로컬 락** | 인스턴스 간에는 무효 | DB 락, 또는 파티셔닝으로 직렬화 |
| **인메모리 카운터/집계** | 합계가 틀림 | 중앙 집계, 또는 주기적 병합 |
| **로컬 임시 파일 기반 작업** | 재시도가 다른 서버로 가면 실패 | 공유 스토리지 |

### 상태를 "없애는" 게 아니라 "밀어내는" 것
상태는 사라지지 않는다. **앱 계층에서 빼서 전용 저장소로 옮기는 것**이다.
그래서 앱은 쉽게 늘어나고, 어려운 문제(상태 관리)는 그걸 잘하는 시스템(DB, Redis)에 몰아넣는다.

**→ 그래서 확장의 최종 난이도는 항상 데이터 계층에 있다.**

### 계층별 확장 난이도
```
쉬움  앱 서버 (무상태면 그냥 늘림)
  │   캐시 (샤딩 가능, 유실 허용)
  │   DB 읽기 (복제본 추가, 지연 감수)
어려움 DB 쓰기 (샤딩 — 되돌리기 어려움)
```

## 5. 확장하기 전에 먼저 할 것

**"서버를 늘리자"는 대개 세 번째 선택지다.**

### ① 측정
어디가 느린지 모르고 늘리면 병목이 아닌 곳을 늘린다. APM, 프로파일링, DB 실행 계획.

### ② 낭비 제거 (가장 저렴)
| 낭비 | 효과 |
|---|---|
| N+1 쿼리 제거 | 쿼리 수 100분의 1 |
| 인덱스 추가 | 응답 시간 자릿수 개선 |
| 불필요한 데이터 전송 제거 | 네트워크·직렬화 비용 |
| 중복 호출 제거 | 그대로 처리량 |

**낭비 제거는 성능과 확장성을 동시에 개선하면서 복잡도를 늘리지 않는다.** 유일하게 공짜에 가까운 수단.

### ③ 수직 확장
장비 하나로 버틸 수 있으면 그게 훨씬 싸고 단순하다. **수평 확장은 못 버틸 때 지불하는 복잡도**다.
- 현대 서버 1대의 성능은 직관보다 훨씬 높다 (수십 코어, 수백 GB RAM, NVMe)
- 많은 서비스가 "제대로 튜닝한 DB 한 대"로 충분하다

## 6. 확장성을 말하는 방식

**나쁜 답변**
> "트래픽이 늘어도 괜찮게 설계했습니다."

**좋은 답변의 형태**
> "현재 병목은 X입니다. 지금 구조로 Y까지 버팁니다. 그 이상은 Z를 해야 하고, 아직 안 한 이유는 (복잡도 대비 필요성 / 아직 그 규모가 아님)입니다."

**"안 한 이유를 말할 수 있는 것"이 핵심이다.** 모든 확장 기법을 다 적용한 시스템은 오버엔지니어링이고, 그 자체가 유지보수 부채다.
