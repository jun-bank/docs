## 01~07 — 학습 노트

> **설계 문서가 아니다.** 여기 있는 내용은 결정의 근거가 될 수 없다. 결정은 ADR에만 남긴다.
> 나중에 별도 저장소로 옮길 수 있다.

### 사용법

각 주제 폴더의 `README.md`에 **개념 설명 + 코드 예제 + 스스로 답할 질문**이 들어 있다. 읽고 직접 따라 치면서 정리하는 용도다.

문서 끝의 **"jun-bank 적용 검토"** 표는 **의도적으로 비어 있다.** 공부한 뒤 우리 코드에 적용해 판단을 채우는 칸이며, **여기가 채워져야 그 주제가 끝난 것**이다.

각 노트에 아래 셋이 확보되면 완료로 본다:

1. **정의** — 한 문장으로 설명할 수 있는가
2. **판단 기준** — 언제 쓰고 언제 쓰지 않는가
3. **jun-bank 연결점** — 우리 코드/설계의 어디에 해당하는가 (이게 없으면 남의 지식이다)

> "설계 레벨"은 책 2.2의 네 단계(**아키텍처 / 모듈 / 컴포넌트 / 클래스 설계**)를 가리킨다.
> 어느 레벨의 이야기인지 의식하면서 공부하면 나중에 설계 논의가 흔들리지 않는다.
> (이 4단계의 규약 문서는 Phase 0에서 만든다 — 아직 미착수)

### 학습 순서 (권고)

```
04 GoF ──┐
         ├─▶ 02 CLEAN ──▶ 03 도메인/애플리케이션 ──▶ 05 아키텍처 스타일 ──▶ 06 오케/코레오
01 SOLID ┘   (컴포넌트)         (모듈)                  (아키텍처)           (아키텍처)

07 애자일·스쿼드 — 언제든. 다만 05를 읽은 뒤가 콘웨이의 법칙이 와닿는다
```

**아래 레벨부터 올라간다.** 05·06을 먼저 하면 용어는 늘지만 판단 근거가 없어서 "MSA가 좋대"류의 결론에 도달하기 쉽다.

### 이 노트들이 향하는 곳

공부가 공부로 끝나지 않게, 각 주제를 **특정 Phase의 결정**에 연결해 둔다.

| 주제 | 연결되는 결정 | 언제 |
|---|---|---|
| 02 CLEAN (비중복 ↔ 느슨한 결합 충돌) | 공용 값 객체를 공유할 것인가 | Phase 3 |
| 03 도메인/애플리케이션 로직 | 계층 규약 | Phase 6 |
| 05 아키텍처 스타일 | 시스템·애플리케이션 아키텍처 선정 | Phase 3 |
| 06 오케/코레오 | 트랜잭션 흐름 설계 | Phase 3 |
| 07 애자일·스쿼드 | 개발 주기 | Phase 8 |
| 01 SOLID · 04 GoF | 코딩 규약 | Phase 6 |
