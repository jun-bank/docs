# study — 학습 노트

> **이 디렉토리는 설계 문서가 아니다.** 공부하며 익히는 개인 학습 노트이며, 나중에 별도 저장소로 옮길 수 있다.
> 여기 있는 내용은 **결정의 근거가 될 수 없다.** 결정은 `architecture/decisions/`(ADR)에만 남긴다.

## 사용법

각 주제 폴더의 `README.md`에는 **개념 설명 + 코드 예제 + 스스로 답할 질문**이 들어 있다. 읽고 직접 따라 치면서 정리하는 용도다.

문서 끝의 **"jun-bank 적용 검토"** 표는 **비어 있다.** 이건 의도된 것이다 — 공부한 뒤 우리 코드에 직접 적용해 판단을 채워 넣는 칸이며, **여기가 채워져야 그 주제가 끝난 것**이다.

각 노트에 아래 세 가지가 확보되면 완료로 본다:

1. **정의** — 한 문장으로 설명할 수 있는가
2. **판단 기준** — 언제 쓰고 언제 쓰지 않는가
3. **jun-bank 연결점** — 우리 코드/설계의 어디에 해당하는가 (이게 없으면 남의 지식이다)

## 학습 순서 (권고)

```
04 GoF ──┐
         ├─▶ 02 CLEAN ──▶ 03 도메인/애플리케이션 ──▶ 05 아키텍처 스타일 ──▶ 06 오케/코레오
01 SOLID ┘      (③④)            (②)                     (①)                  (①)

07 애자일·스쿼드 — 언제든. 다만 05를 읽은 뒤가 콘웨이의 법칙이 와닿는다
```

**아래 레벨부터 올라간다.** 05·06을 먼저 하면 용어는 늘지만 판단 근거가 없어서 "MSA가 좋대"류의 결론에 도달하기 쉽다.

## 이 노트들이 향하는 곳

각 주제는 최종적으로 **특정 ADR의 입력**이 된다. 공부가 공부로 끝나지 않게 하는 장치다.

| 주제 | 연결되는 결정 |
|---|---|
| 02 CLEAN (N↔L 충돌) | `Money` 6벌을 공유할 것인가 → ADR-0005 (예정) |
| 03 도메인/애플리케이션 | 계층 규약 → `conventions/coding-convention.md` (예정) |
| 05 아키텍처 스타일 | 시스템·애플리케이션 아키텍처 선정 → **ADR-0001**(제안됨) · ADR-0002 (예정) |
| 06 오케/코레오 | 트랜잭션 흐름 설계 → `drafts/03-transaction-design.md` · ADR-0004 (예정) |
| 07 애자일·스쿼드 | 개발 주기 → `drafts/development-cycle.md` |
