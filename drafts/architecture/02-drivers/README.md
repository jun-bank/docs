# 02. 아키텍처 드라이버

> 추상화 레벨: ① 아키텍처 설계
> 책 대응: 3.2 아키텍처 드라이버의 핵심 사항 (100쪽)

**아키텍처 드라이버**란 아키텍처를 실제로 결정짓는 입력이다. 기능 목록이 아키텍처를 정하는 것이 아니라, **제약 · 품질 속성 · 영향력 있는 기능 요구사항**이 정한다.

## 구성

| 문서 | 책 대응 | 내용 |
|---|---|---|
| [01-constraints.md](01-constraints.md) | 3.2.2 제약 | 비즈니스 제약 · 기술 제약 — **협상 불가능한 전제** |
| [02-quality-attributes.md](02-quality-attributes.md) | 3.2.3~3.2.4 품질 속성 | ISO/IEC 25010 기반 선정과 **우선순위** |
| [03-quality-scenarios.md](03-quality-scenarios.md) | 3.2.5 품질 속성 시나리오 | 측정 가능한 형태로 구체화 |
| (아래 §영향력 있는 기능 요구사항) | 3.2.6 | 아키텍처를 좌우하는 소수의 기능 |

## 왜 이 순서인가

```
제약(고정)  →  품질 속성(선택)  →  품질 시나리오(측정 가능)  →  아키텍처 결정(ADR)
바꿀 수 없음    무엇을 우선할지     "빠르게"가 아니라 "3초 내"     비로소 판단 가능
```

제약을 먼저 적는 이유는, **제약을 모르고 고른 품질 속성은 지킬 수 없기 때문**이다. 예를 들어 "고가용성"을 목표로 삼아도 1인 개발·무예산 제약 아래에서는 다중 리전이 불가능하다.

---

## 영향력 있는 기능 요구사항 (3.2.6)

전체 기능 중 **아키텍처를 좌우하는 소수**만 여기에 적는다. 나머지 기능은 아키텍처를 바꾸지 않는다.

| # | 기능 | 왜 아키텍처를 좌우하는가 |
|---|---|---|
| **S3** | **결제 승인** | 응답 시간 SLA + 동시성 제어 + 가용잔액 계산이 동시에 걸린다. **읽기 경로와 쓰기 경로, 캐시 전략, 락 전략을 전부 규정**한다 |
| **S4** | **승인 타임아웃·망취소** | 외부와의 통신이 "상태 불명"으로 끝날 수 있음을 전제해야 한다. **멱등성 설계와 재시도 정책이 시스템 전역 규약**이 된다 |
| **S5** | **매입·정산 (배치)** | 실시간 경로와 **완전히 다른 처리 모델**이 필요하다. 배치 실행 주체·재처리 단위·부분 실패 처리를 아키텍처가 수용해야 한다 |
| **S6** | **대사** | 두 개의 독립된 기록을 대조한다. **이벤트 유실을 탐지할 수 있는 구조**(Outbox 등)를 강제한다 |
| **S7** | **취소·환불** | 원거래 참조 무결성과 역분개가 필요하다. **원장을 append-only로 강제**한다 |

> 나머지 기능(회원가입·조회·카드 발급 등)은 위 5개가 정한 아키텍처 안에서 구현된다. **아키텍처를 이 5개 기준으로 설계하고, 나머지가 그 위에 얹히는지 검증**하는 순서다.

---

## 그 외 영향을 미치는 요소 (3.2.7)

- **학습 목적**: 이 프로젝트의 1차 목표는 동작하는 서비스가 아니라 **결제 도메인과 분산 처리에 대한 이해**다. 따라서 "더 단순한 방법이 있는데 왜 어렵게 하는가"에 대한 답이 **"그것이 학습 대상이기 때문"** 인 경우가 있다. 그럴 때는 ADR에 그렇게 적는다.
- **기존 자산**: 15개 저장소, Java 21 / Spring Boot 4.0.0 기반 골격이 이미 존재한다. 백지에서 시작하지 않는다.
- **1인 개발**: 팀 간 커뮤니케이션 비용이 0인 대신, **운영 부담이 전부 한 사람에게 온다.** 서비스를 늘리는 결정의 대가가 크다.
