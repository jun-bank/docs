# 02-3. 품질 속성 시나리오

> 추상화 레벨: ① 아키텍처 설계
> 책 대응: 3.2.5 품질 속성 시나리오 (108쪽)
> 상태: **초안 v0.1 — 수치 확정 필요**

---

## 왜 시나리오로 바꾸는가

"신뢰성이 높아야 한다"는 **검증할 수 없다.** 아키텍처를 판단하려면 측정 가능한 형태여야 한다.

품질 속성 시나리오는 6요소로 구성한다:

| 요소 | 뜻 |
|---|---|
| **자극원** | 누가/무엇이 유발하는가 |
| **자극** | 무슨 일이 일어나는가 |
| **환경** | 어떤 상태에서 |
| **대상** | 시스템의 어느 부분이 |
| **응답** | 어떻게 반응해야 하는가 |
| **응답 측정** | **무엇으로 성공을 판정하는가** ← 이게 없으면 시나리오가 아니다 |

각 시나리오는 **검증 방법**까지 적는다. 검증할 수 없는 시나리오는 채택하지 않는다.

---

## QS-01. 승인 응답 시간 — 시간 반응성

| 요소 | 내용 |
|---|---|
| 자극원 | 매입사(모의) |
| 자극 | 결제 승인 요청 1건 |
| 환경 | 정상 운영 상태 |
| 대상 | 승인 처리 경로 (게이트웨이 → 카드 → 계좌 → 원장) |
| 응답 | 승인 또는 거절을 응답한다 |
| **응답 측정** | **p99 ≤ 3초** (매입사 타임아웃 5초보다 여유 확보) |

- 검증: 부하 테스트 + 응답 시간 분포 측정
- 관련 품질 속성: 시간 반응성(5위)
- ⚠️ **1위(기능 정확성)와 충돌 시 정확성이 이긴다** — 3초를 못 지키면 캐시가 아니라 구조를 본다

---

## QS-02. 동시 결제 시 한도 초과 방지 — 기능 정확성

| 요소 | 내용 |
|---|---|
| 자극원 | 서로 다른 가맹점 |
| 자극 | **같은 카드로 동시에** 승인 요청 N건 |
| 환경 | 가용잔액이 요청 합계보다 작은 상태 |
| 대상 | 승인 판단 + 홀딩 생성 |
| 응답 | 가용잔액 범위 내 건만 승인하고 나머지는 거절 |
| **응답 측정** | **승인된 건의 금액 합계 ≤ 가용잔액. 초과 승인 0건.** 반복 실행에도 재현 |

- 검증: 동시 요청 부하 테스트 + 사후 잔액 검산
- 관련 품질 속성: 기능 정확성(1위)
- **아키텍처에 강제하는 것**: 계좌 단위 동시성 제어(락 또는 직렬화)

---

## QS-03. 승인 타임아웃 후 망취소 — 결함 허용성 + 멱등성

| 요소 | 내용 |
|---|---|
| 자극원 | 매입사(모의) |
| 자극 | 승인 요청 후 응답을 받지 못해 **망취소 전문 전송**. 망취소도 **중복 전송**될 수 있음 |
| 환경 | 승인은 실제로 성공했거나 실패했음 — **어느 쪽인지 알 수 없음** |
| 대상 | 승인·홀딩·원장 |
| 응답 | 성공했다면 취소하고, 실패했다면 아무 변화도 만들지 않는다 |
| **응답 측정** | **망취소를 1회 보내든 5회 보내든 최종 상태가 동일하다.** 홀딩 잔류 0건, 원장 중복 0건 |

- 검증: 응답 유실을 주입한 시나리오 테스트 + 망취소 N회 반복 후 상태 비교
- 관련 품질 속성: 결함 허용성·복구성(2위)
- **아키텍처에 강제하는 것**: 멱등키 기반 요청 처리, 승인 상태의 명시적 "불명" 처리

---

## QS-04. 하위 서비스 장애 — 안전한 실패

| 요소 | 내용 |
|---|---|
| 자극원 | 인프라 |
| 자극 | 원장 서비스 또는 계좌 서비스가 응답하지 않음 |
| 환경 | 승인 요청이 들어오는 중 |
| 대상 | 승인 처리 경로 |
| 응답 | **승인하지 않고 거절**한다. 확정되지 않은 상태를 남기지 않는다 |
| **응답 측정** | **잘못 승인된 건 0건.** 장애 구간 이후 잔액·원장 정합성 유지 |

- 검증: 서비스 강제 종료 후 승인 요청, 복구 후 정합성 검산
- 관련 품질 속성: 결함 허용성(2위) > 가용성(8위)
- **판단 근거**: 틀린 승인보다 거절이 낫다 (`02-quality-attributes.md` §2)

---

## QS-05. 이벤트 유실 없음 — 무결성

| 요소 | 내용 |
|---|---|
| 자극원 | 인프라 |
| 자극 | DB 커밋 직후 Kafka 발행 실패 (브로커 다운) |
| 환경 | 결제/이체 처리 중 |
| 대상 | 이벤트 발행 경로 |
| 응답 | 이벤트가 유실되지 않고 **브로커 복구 후 반드시 발행**된다 |
| **응답 측정** | **커밋된 상태 변경 건수 = 최종 발행된 이벤트 건수.** 유실 0건 |

- 검증: 브로커 중단 → 처리 → 복구 → 건수 대조
- 관련 품질 속성: 무결성(3위)
- **아키텍처에 강제하는 것**: Outbox 패턴(또는 동등 보장). **현재 `user-service`는 try-catch 삼킴 + 자체 재시도 → 이 시나리오를 통과하지 못한다**

---

## QS-06. 대사 불일치 탐지 — 기능 정확성 + 분석성

| 요소 | 내용 |
|---|---|
| 자극원 | 정산 배치 |
| 자극 | 매입사 정산 파일과 우리 원장을 대조 |
| 환경 | D+1 정산 시각. 일부 건이 의도적으로 어긋나 있음 |
| 대상 | 대사 배치 |
| 응답 | 불일치를 **유형별로 분류해 적재**한다 (미매입 / 미승인 매입 / 금액 상이) |
| **응답 측정** | **주입한 불일치 건을 100% 탐지.** 자동 정정은 0건 (운영자 확인 대상으로만 적재) |

- 검증: 불일치를 인위적으로 주입한 정산 파일로 배치 실행
- 관련 품질 속성: 기능 정확성(1위), 분석성(4위)

---

## QS-07. 원장 무결성 — 무결성

| 요소 | 내용 |
|---|---|
| 자극원 | 임의의 자금 이동 |
| 자극 | 전표 생성 |
| 환경 | 상시 |
| 대상 | 원장 |
| 응답 | 모든 전표가 차변=대변 균형을 만족하며, 기존 전표는 **수정·삭제되지 않는다** |
| **응답 측정** | **시산 결과 차변 합 = 대변 합.** 기존 전표 UPDATE/DELETE 발생 0건 |

- 검증: 시산 검증 쿼리 + 원장 테이블 변경 이력 점검
- 관련 품질 속성: 무결성(3위)

---

## QS-08. 부분취소 누적 초과 방지 — 기능 정확성

| 요소 | 내용 |
|---|---|
| 자극원 | 가맹점 |
| 자극 | 같은 원거래에 대해 부분취소를 **동시에/반복** 요청 |
| 환경 | 누적 취소액이 원거래 금액에 근접 |
| 대상 | 취소 처리 |
| 응답 | 누적 취소액이 원거래 금액을 초과하는 요청은 거절 |
| **응답 측정** | **누적 취소액 ≤ 원거래 금액. 초과 0건** (동시 요청에서도) |

- 검증: 동시 부분취소 부하 테스트
- 관련 품질 속성: 기능 정확성(1위)

---

## QS-09. 배치 부분 실패 재처리 — 복구성

| 요소 | 내용 |
|---|---|
| 자극원 | 정산 배치 |
| 자극 | 파일 처리 도중 중단 (예: 10,000건 중 6,400건 처리 후 실패) |
| 환경 | D+1 정산 |
| 대상 | 매입 반영 배치 |
| 응답 | 재실행 시 **이미 처리된 건을 중복 반영하지 않고**, 남은 건만 처리한다 |
| **응답 측정** | **재실행 후 총 반영 건수 = 파일 건수.** 중복 반영 0건. "에러 없이 끝남"이 아니라 **건수로 판정** |

- 검증: 중단 주입 후 재실행, 건수·금액 대조
- 관련 품질 속성: 복구성(2위)
- ⚠️ **"에러 없이 돌았다"는 완료가 아니다.** 부분 실패의 조용한 성공 위장이 가장 흔한 사고 유형이다

---

## QS-10. 로컬 전체 기동 — 설치 용이성

| 요소 | 내용 |
|---|---|
| 자극원 | 개발자(본인) |
| 자극 | 초기화된 환경에서 전체 시스템 기동 |
| 환경 | 로컬 단일 머신, Docker |
| 대상 | 전체 시스템 |
| 응답 | 모든 서비스가 정상 기동하고 헬스체크를 통과한다 |
| **응답 측정** | **단일 명령 + 수동 조작 0회.** 기동 완료까지 걸린 시간을 기록 |

- 검증: 클린 환경에서 실행
- 관련 품질 속성: 설치 용이성(7위)
- 제약 BC-3 / TC-5와 직결

## QS-11. 장애 추적 — 분석성

| 요소 | 내용 |
|---|---|
| 자극원 | 개발자 |
| 자극 | 실패한 결제 1건의 원인 조사 |
| 환경 | 여러 서비스를 거친 요청 |
| 대상 | 로그·추적 |
| 응답 | 하나의 추적 ID로 전 구간 흐름을 재구성할 수 있다 |
| **응답 측정** | **추적 ID 1개로 관련 로그 전부 조회 가능.** 끊긴 구간 0개 |

- 검증: 실패 주입 후 추적 재구성
- 관련 품질 속성: 분석성(4위)

## 확정 필요한 수치

아래는 임시값이다. `product/00-product-definition.md` §6 비즈니스 규칙과 함께 확정한다.

| 시나리오 | 항목 | 임시값 |
|---|---|---|
| QS-01 | 승인 응답 p99 | 3초 (매입사 타임아웃 5초 가정) |
| QS-02 | 동시 요청 수 N | 미정 |
| QS-06 | 정산 파일 규모 | 미정 |
| QS-09 | 배치 처리 건수 | 미정 |
| QS-10 | 기동 시간 상한 | 미정 |

> **결정 필요 #S1**: 위 수치들. 학습 목적상 **작게 잡되 구조가 드러날 만큼**은 되어야 한다 (예: 정산 파일 1만 건이면 배치 재처리 설계가 의미를 갖는다).
