# 02-1. 제약 (Constraints)

> 추상화 레벨: ① 아키텍처 설계
> 책 대응: 3.2.2 제약 (101쪽)
> 상태: **초안 v0.1 — 사용자 검토 대기**

**제약은 협상 대상이 아니다.** 품질 속성은 "무엇을 더 중시할까"의 선택이지만, 제약은 "그럴 수 없다"는 사실이다. 제약을 무시한 아키텍처는 문서상으로만 존재한다.

---

## 1. 비즈니스 제약

| # | 제약 | 아키텍처에 미치는 영향 |
|---|---|---|
| **BC-1** | **실 고객·실 자금이 없는 학습 프로젝트다** | 가용성·재해복구에 실제 비용을 쓸 이유가 없다. 반면 **정합성 오류는 학습 목적상 반드시 잡아야** 한다 (틀린 채로 굴러가면 배우는 게 없다) |
| **BC-2** | **1인 개발** | 서비스를 하나 늘릴 때마다 운영·빌드·배포 부담이 전부 한 사람에게 온다. **서비스 수를 늘리는 결정의 대가가 크다** |
| **BC-3** | **무예산** | 유료 클라우드·관리형 서비스 사용 불가. **로컬 Docker 기반**으로 전부 재현 가능해야 한다 |
| **BC-4** | **실제 금융망·카드사와 연동 불가** | 외부 연동은 **모의 서비스(매입사/VAN)로 대체**한다. 대신 지연·타임아웃·중복응답을 **의도적으로 주입 가능**해야 한다 |
| **BC-5** | **규제 실 준수 대상 아님** (전자금융거래법·PCI-DSS 등) | 실 인증을 받지 않는다. 다만 **카드번호 토큰화·감사 로그·append-only 원장 같은 개념은 반영**한다 (그것이 학습 대상이므로) |
| **BC-6** | **명시적 마감이 없다** | 일정 압박은 없으나, **학습 사이클이 멈추면 실패**다. 완성도보다 "한 바퀴를 끝까지 도는 것"을 우선한다 |
| **BC-7** | **1차 목표는 동작하는 서비스가 아니라 이해다** | "더 단순한 방법이 있는데 왜 어렵게 하는가"의 답이 **"그것이 학습 대상이라서"** 인 경우를 허용한다. 단 **ADR에 그렇게 명시**한다 |

> **BC-2와 BC-7은 서로 당긴다.** 학습을 위해 분산 구조를 택하면(BC-7) 1인 운영 부담이 커진다(BC-2). 이 긴장은 없앨 수 없고, **서비스 개수를 정할 때 명시적으로 저울질**해야 한다. → `decisions/0001-*`

## 2. 기술 제약

### 2.1 확정된 것 (이미 채택되어 되돌리는 비용이 큼)

실제 `build.gradle` 확인 결과, 11개 서비스 전부 아래로 통일되어 있다.

| 항목 | 버전 | 비고 |
|---|---|---|
| Java | **21** (toolchain) | 전 서비스 동일 |
| Spring Boot | **4.0.0** | 전 서비스 동일 |
| Spring Cloud | **2025.1.0** | Config / Eureka / Gateway / OpenFeign / LoadBalancer / Resilience4j |
| 데이터베이스 | **PostgreSQL** | 서비스별 분리 DB |
| 메시징 | **Apache Kafka** (spring-kafka) | |
| 영속화 | **Spring Data JPA + QueryDSL 5.1.0** | |
| 관측 | Micrometer Tracing + Zipkin(Brave), Prometheus, logstash-logback-encoder | |
| API 문서 | springdoc-openapi 2.8.4 | |
| 공용 라이브러리 | `io.github.jun-bank:common-lib:0.0.1` | 외부 Maven 저장소로 배포 중 |
| 실행 환경 | Docker Compose (`infrastructure` 저장소) | |

### 2.2 제약으로 작용하는 사실

| # | 제약 | 아키텍처에 미치는 영향 |
|---|---|---|
| **TC-1** | 서비스 간 **동기 통신은 OpenFeign**, 비동기는 **Kafka** 로 이미 고정 | 통신 방식 선택지가 사실상 둘이다. **어떤 흐름에 어느 쪽을 쓸지**가 결정 대상 |
| **TC-2** | **서비스별 DB 분리** 구조 | 서비스 경계를 넘는 트랜잭션은 **분산 트랜잭션**이 된다. 2PC 미사용 → 보상 기반 |
| **TC-3** | `common-lib` 이 **외부 Maven 저장소로 배포**된다 | 공용 코드 변경 시 **배포 → 버전 올림 → 각 서비스 반영**의 사이클이 필요. 공유를 늘릴수록 배포 결합이 커진다 |
| **TC-4** | 서비스 디스커버리 = **Eureka**, 진입점 = **Gateway** | 클라이언트는 게이트웨이만 안다. 인증 헤더 전파가 게이트웨이 책임 |
| **TC-5** | **단일 머신(로컬 Docker)에서 전부 구동**되어야 한다 (BC-3) | 서비스가 늘수록 메모리·기동 시간이 선형 증가. **서비스 개수의 실질 상한이 존재** |
| **TC-6** | 스키마 관리가 **`ddl-auto: update`** 상태 (`config-repo/configs/common/application.yml:61`) | **결함으로 식별됨.** 마이그레이션 도구 도입이 필요 → ADR 대상 |

### 2.3 되돌릴 수 있는 것 / 없는 것

| 되돌리기 어려움 | 항목 |
|---|---|
| **매우 어려움** | 서비스별 DB 분리(TC-2), 서비스 분할 경계 |
| **어려움** | Kafka 채택, Eureka/Gateway 구성, `common-lib` 외부 배포 방식 |
| **보통** | Java·Spring Boot 버전, QueryDSL |
| **쉬움** | 관측 도구, API 문서 도구, `ddl-auto` → 마이그레이션 도구 전환 |

> 이 표가 **ADR을 어디에 써야 하는지**를 알려준다. "매우 어려움"과 "어려움"에 해당하는 결정은 전부 ADR이 있어야 한다. 현재 **하나도 없다.**

## 3. 제약이 아닌 것 (혼동 주의)

아래는 제약처럼 보이지만 **선택**이다. 즉 바꿀 수 있고, 따라서 근거가 필요하다.

- "MSA로 간다" → **선택**이다. 제약이 아니다. → `decisions/0001-*`
- "헥사고날 아키텍처를 쓴다" → **선택**이다. → `decisions/0002-*` (예정)
- "이벤트는 Kafka로 보낸다" → 도구는 제약(TC-1)이지만, **어떤 흐름을 이벤트로 할지는 선택**이다
