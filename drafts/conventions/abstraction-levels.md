# 설계의 추상화 레벨 — 4단계

- 작성일: 2026-08-03
- 근거: 『아키텍트 첫걸음』 2.2 소프트웨어 설계의 추상화 레벨 (57쪽)
- 상태: **적용 중 — 모든 설계 문서·논의에 이 표기를 의무화한다**

---

## 왜 이 문서가 다른 설계 문서보다 먼저인가

현재 코드베이스의 혼란(`Money` 값 객체가 6개 서비스에 복붙, 서비스 경계 근거 불명, 신뢰성 전략이 서비스마다 다름)은 **서로 다른 추상화 레벨의 이야기를 같은 자리에서 한 결과**다.

> "Money를 공유할까?" 는 **모듈 레벨** 질문이고,
> "결제와 원장을 나눌까?" 는 **아키텍처 레벨** 질문이며,
> "값 객체로 만들까 원시타입으로 둘까?" 는 **클래스 레벨** 질문이다.

이 셋을 한 대화에서 섞으면 결론이 나지 않는다. **레벨이 다르면 판단 기준도, 되돌리는 비용도 다르기 때문이다.**

---

## 네 가지 레벨

| 레벨 | 다루는 것 | 되돌리는 비용 | 결정 기록 위치 |
|---|---|---|---|
| **① 아키텍처 설계** | 시스템을 어떤 단위로 나누고 어떻게 통신하는가 | **매우 높음** — 배포 단위·DB·계약이 함께 움직임 | **ADR 필수** |
| **② 모듈 설계** | 하나의 단위 안에서 책임을 어떻게 묶는가 | 높음 — 패키지 구조·의존 방향 | ADR 또는 설계서 |
| **③ 컴포넌트 설계** | 협력하는 객체 묶음의 역할과 인터페이스 | 중간 | 설계서 |
| **④ 클래스 설계** | 개별 타입의 책임·상태·메서드 | 낮음 — 리팩토링으로 흡수 | 코드 + 리뷰 |

### ① 아키텍처 설계

**jun-bank에서 다루는 것**: 서비스 분할(account / card / ledger / …), 동기·비동기 통신 선택, 데이터 소유권, 트랜잭션 경계, 배포 단위.

- 예: "결제 승인과 원장 기록을 같은 서비스에 둘 것인가"
- 예: "서비스 간 통신을 Feign(동기)으로 할 것인가 이벤트로 할 것인가"
- 판단 기준: 품질 속성 (`drafts/architecture/02-drivers/`)
- **되돌리기 어렵다 → 반드시 ADR을 남긴다**

### ② 모듈 설계

**jun-bank에서 다루는 것**: 한 서비스 내부의 패키지 구조, 계층 간 의존 방향, 공용 라이브러리 경계.

- 예: "헥사고날의 domain / application / infrastructure / presentation 경계를 어디에 그을 것인가"
- 예: "`Money`를 common-lib에 둘 것인가, 각 서비스가 자기 것을 가질 것인가" ← **현재 미해결**
- 판단 기준: 의존 방향, 변경의 파급 범위

### ③ 컴포넌트 설계

**jun-bank에서 다루는 것**: 유스케이스를 수행하는 객체 묶음의 협력 구조, 포트/어댑터 인터페이스.

- 예: "승인 처리에서 한도 검증을 별도 컴포넌트로 뺄 것인가, 애그리게이트 안에 둘 것인가"
- 예: "`AuthServicePort`가 무엇을 노출해야 하는가"
- 판단 기준: 응집도, 인터페이스의 안정성

### ④ 클래스 설계

**jun-bank에서 다루는 것**: 개별 클래스의 책임, 값 객체 여부, 불변식 위치.

- 예: "`Money`를 값 객체로 만들 것인가"
- 예: "`User.previousStatus` 같은 롤백용 필드를 도메인 모델에 둘 것이 맞는가" ← **현재 결함으로 식별됨**
- 판단 기준: SOLID, 응집도, 불변식이 지켜지는 위치

## 적용 규칙

1. **모든 설계 문서 머리에 레벨을 표기한다.**
   예: `> 추상화 레벨: ① 아키텍처 설계`
2. **한 문서에서 두 레벨 이상을 다루지 않는다.** 필요하면 문서를 나누고 링크한다.
3. **논의 중 레벨이 섞이면 멈춘다.** "지금 이건 어느 레벨 얘기인가?"를 먼저 정리한다.
4. **레벨이 올라갈수록 기록 의무가 강해진다.** ①은 ADR 필수, ④는 코드가 곧 기록이다.
5. **하위 레벨에서 상위 레벨 결정을 뒤집지 않는다.** 클래스 설계를 하다가 서비스 경계를 바꾸고 싶어지면, 그건 클래스 문제가 아니라 **아키텍처 결정이 틀렸다는 신호**다. 멈추고 ①로 올라간다.

> 규칙 5가 이 문서의 실질이다. 구현하다가 "이러면 저 서비스랑 합치는 게 낫겠는데" 싶을 때, 그 자리에서 코드로 우회하면 경계가 조용히 무너진다. **올라가서 다시 결정하고 ADR을 남긴다.**

## 현재 식별된 문제의 레벨 분류

앞서 코드 분석에서 찾은 결함을 레벨별로 나누면, **어느 것을 먼저 결정해야 하는지**가 드러난다.

| 결함 | 레벨 | 순서 |
|---|---|---|
| 서비스 경계가 기술 직관으로 결정됨 | ① 아키텍처 | **1순위** |
| 회원가입이 분산 트랜잭션인데 보상 없음 | ① 아키텍처 | **1순위** |
| 신뢰성 전략(Outbox/Saga)이 서비스마다 다름 | ① 아키텍처 | **1순위** |
| email 이중 저장 — 정합성 소유자 불명 | ① 아키텍처 | **1순위** |
| `Money` 6벌 중복 | ② 모듈 | 2순위 |
| 스키마 마이그레이션 도구 부재 | ② 모듈 | 2순위 |
| `User.previousStatus` 롤백 필드 누수 | ④ 클래스 | 3순위 (①이 정해지면 자동 해소) |

> 마지막 행이 규칙 5의 실례다. `previousStatus`는 클래스 레벨 문제로 보이지만, **원인은 ① 레벨의 분산 트랜잭션 설계 부재**다. 클래스만 고치면 다시 생긴다.
