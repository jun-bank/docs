## 1. 목적

### 1.1 이 시스템은 무엇인가

> **jun-bank는 고객에게 계좌와 카드를 발급하고, 그 카드로 발생한 결제를 승인·정산·기록하는 리테일 은행이다.**

결제 요청을 만드는 쪽(가맹점·PG)이 아니라, **결제 요청을 받아 판단하고 돈을 움직이는 쪽** — 즉 **발급사(Issuer)** 다.

→ 상세: [`product/00-product-definition.md`](../product/00-product-definition.md)

### 1.2 이 프로젝트의 진짜 목표

**1차 산출물은 동작하는 은행이 아니라 이해다.**

결제 도메인은 분산 시스템 기법이 "있으면 좋은 것"이 아니라 **없으면 실제로 돈이 틀어지는** 몇 안 되는 영역이다. 멱등성이 없으면 이중 승인이 나고, Outbox가 없으면 D+1 대사에서야 원장 누락이 발견된다.

따라서 이 시스템의 설계 판단에는 다음 원칙이 적용된다:

> **"더 단순한 방법이 있는데 왜 어렵게 하는가"의 답이 "그것이 학습 대상이기 때문"인 경우를 허용한다. 단, ADR에 그렇게 명시한다.**

이 원칙이 가장 크게 작용한 결정이 [ADR-0001](decisions/0001-system-architecture-selection.md)이다.

## 2. 사용자(업무 주체)와 이해관계

### 2.1 액터

| 액터 | 유형 | 시스템과의 관계 |
|---|---|---|
| **카드소지자** | 사람 | jun-bank 계좌·카드 보유. 결제·조회·이체의 주체 |
| **가맹점** | 사람/조직 | 카드를 받는 상점. **우리와 직접 계약 없음** (매입사와 계약) |
| **매입사 / VAN** | 외부 시스템 (모의) | 승인 요청 중계, 매입·정산 파일 송부 |
| **운영자** | 사람 | 대사 불일치·실패 거래·배치 상태 처리 |
| **정산 배치** | 시스템 | 사람이 아닌 액터. 마감 시각에 기동 |

### 2.2 이해관계 (Concerns)

각 액터가 이 시스템에 대해 **무엇을 걱정하는가**. 이것이 곧 품질 속성의 출처다.

| 액터 | 이해관계 | 대응하는 품질 속성 | 검증 |
|---|---|---|---|
| 카드소지자 | 내 잔액이 정확한가 | **기능 정확성 (1위)** | QS-02, QS-07 |
| 카드소지자 | 결제가 제때 되는가 | 시간 반응성 (5위) | QS-01 |
| 카드소지자 | 취소가 제대로 반영되는가 | 복구성 (2위) | QS-08 |
| 카드소지자 | 승인만 된 건과 완료된 건을 구분할 수 있는가 | 사용성 (8위, 예외적으로 중요) | 제품 정의서 S8 |
| 매입사 | 시간 내 응답이 오는가 | 시간 반응성 | QS-01 |
| 매입사 | 망취소가 정확히 처리되는가 | **결함 허용성 (2위)** | QS-03 |
| 매입사 | 정산이 맞는가 | 기능 정확성 | QS-06 |
| 운영자 | 불일치를 발견할 수 있는가 | 분석성 (4위) | QS-06 |
| 운영자 | 장애 원인을 추적할 수 있는가 | 분석성 | QS-11 |
| **개발자(본인)** | **실험하고 관찰할 수 있는가** | **시험성 (4위)** | — |
| 개발자(본인) | 로컬에서 전부 돌아가는가 | 설치 용이성 (7위) | QS-10 |

> **마지막 두 행이 이 프로젝트 특유의 이해관계다.** 학습이 목적이므로 개발자 본인이 1급 이해관계자이며, "실험과 관찰이 가능한가"가 실제 품질 요구가 된다.

## 3. 아키텍처 드라이버

아키텍처를 결정한 것은 기능 목록이 아니라 **제약 · 품질 속성 · 영향력 있는 기능 요구사항**이다.

→ 상세: [`02-drivers/`](02-drivers/)

### 3.1 제약 (요약)

**협상 불가능한 전제.**

| 구분 | 핵심 |
|---|---|
| 비즈니스 | 실 고객·실 자금 없음 · **1인 개발** · 무예산 · 실 금융망 연동 불가 · **학습이 1차 목표** |
| 기술 | Java 21 / Spring Boot 4.0.0 / Spring Cloud 2025.1.0 · PostgreSQL(서비스별) · Kafka · **로컬 단일 머신 구동** |

> **가장 큰 긴장**: 1인 운영 부담(BC-2) ↔ 학습 목적(BC-7). 학습을 위해 분산 구조를 택하면 운영 부담이 커진다. 이 긴장은 없앨 수 없고 **서비스 개수를 정할 때 명시적으로 저울질**해야 한다.

→ 상세: [`02-drivers/01-constraints.md`](02-drivers/01-constraints.md)

### 3.2 품질 속성 우선순위

**충돌 시 위가 아래를 이긴다.**

| 순위 | 품질 속성 | 근거 |
|---|---|---|
| 1 | **기능 정확성** | 금액이 틀리면 이 시스템은 존재 의미가 없다 |
| 2 | **결함 허용성 · 복구성** | 분산 환경에서 부분 실패는 정상 상태다 |
| 3 | **무결성 · 책임 추적성** | 원장은 append-only. 무슨 일이 있었는지 항상 설명 가능 |
| 4 | **시험성 · 분석성** | 학습 프로젝트의 실질 = 실험과 관찰 |
| 5 | **시간 반응성** | 단, **승인 경로 한정** |
| 6 | 상호운용성 | 계약이 명확해야 모의 카드사와 맞물린다 |
| 7 | 설치 용이성 | 로컬에서 전부 떠야 한다 |
| 8 | **가용성 · 사용성** | **의도적으로 버린다** |

**이 순위가 내리는 대표적 판단**:
- 승인 속도를 위해 잔액을 캐시할까? → **안 된다** (1 > 5)
- 서비스 하나 죽었을 때 계속 받을까? → **거절한다** (2 > 8). **틀린 승인보다 거절이 낫다**
- 로그를 줄여 성능을 높일까? → **안 된다** (3·4 > 5)

→ 상세: [`02-drivers/02-quality-attributes.md`](02-drivers/02-quality-attributes.md)

### 3.3 영향력 있는 기능 요구사항

전체 기능 중 **아키텍처를 좌우하는 5개.** 나머지는 이들이 정한 아키텍처 위에 얹힌다.

| # | 기능 | 아키텍처에 강제하는 것 |
|---|---|---|
| **S3** | 결제 승인 | 동시성 제어, 가용잔액 계산, 응답 SLA |
| **S4** | 승인 타임아웃·망취소 | **멱등성이 시스템 전역 규약**이 됨 |
| **S5** | 매입·정산 (배치) | 실시간과 **다른 처리 모델**, 재처리 단위 |
| **S6** | 대사 | **이벤트 유실을 탐지 가능한 구조**(Outbox) |
| **S7** | 취소·환불 | 원거래 참조 무결성, **원장 append-only** |

### 3.4 품질 속성 시나리오

측정 가능한 형태로 구체화한 11개 시나리오. **검증 방법이 없는 시나리오는 채택하지 않는다.**

대표 3개:

| # | 시나리오 | 응답 측정 |
|---|---|---|
| QS-02 | 같은 카드로 동시 결제 N건 | **승인 합계 ≤ 가용잔액. 초과 승인 0건** |
| QS-03 | 승인 응답 유실 후 망취소 중복 전송 | **1회든 5회든 최종 상태 동일.** 홀딩 잔류 0건 |
| QS-09 | 정산 배치 중단 후 재실행 | **총 반영 건수 = 파일 건수.** 중복 0건. "에러 없이 끝남"이 아니라 **건수로 판정** |

→ 상세: [`02-drivers/03-quality-scenarios.md`](02-drivers/03-quality-scenarios.md)

## 4. 아키텍처 모델

**아키텍처는 하나의 그림으로 표현할 수 없다.** 보는 사람마다 알고 싶은 것이 다르다.

이 프로젝트는 두 모델을 병용한다:

| 모델 | 축 | 문서 |
|---|---|---|
| **4+1 뷰** | **어떤 관점**으로 볼 것인가 (논리·개발·프로세스·물리 + 시나리오) | [`models/4plus1-views.md`](models/4plus1-views.md) |
| **C4 모델** | **어떤 배율**로 볼 것인가 (컨텍스트·컨테이너·컴포넌트·코드) | [`models/c4-model.md`](../drafts/c4-model.md) |

### 그리는 순서

```
① 시나리오 뷰 (S3 결제 승인)   ← 먼저. 나머지 뷰에 무엇이 필요한지 드러난다
② 프로세스 뷰                  ← 트랜잭션 경계·타임아웃·피벗 표기
③ 물리 뷰 / C4 컨테이너        ← infrastructure 저장소로 즉시 가능
④ 논리 뷰                      ← 도메인 모델 확정 후
⑤ 개발 뷰 / C4 컴포넌트        ← 서비스 분할 재검토(ADR-0003) 후
```

일반적으로는 논리 뷰부터 그리지만, **jun-bank는 이미 코드가 있고 도메인 모델이 재검토 대상**이므로 확정된 것부터 그린다.

→ 상세: [`models/`](models/)

## 5. 전체 시스템 구성

### 5.1 시스템 아키텍처

**마이크로서비스** — 서비스별 DB 분리, 동기는 OpenFeign, 비동기는 Kafka.

**채택 근거는 품질이 아니라 목적이다.** 품질 속성만으로 비교하면 모놀리식 또는 서비스 기반 아키텍처가 이긴다 (기능 정확성 1위는 단일 트랜잭션이 압도적으로 유리하고, 1인 운영 부담도 그쪽이 낫다). 그럼에도 마이크로서비스를 택한 것은 **분산 환경에서 정합성을 지키는 방법을 익히는 것이 이 프로젝트의 목적**이기 때문이다.

→ [ADR-0001: 시스템 아키텍처로 마이크로서비스를 채택한다](decisions/0001-system-architecture-selection.md) **(제안됨 — 확정 대기)**

### 5.2 애플리케이션 아키텍처

현재 모든 서비스가 **헥사고날(포트&어댑터)** 구조를 쓰고 있다. 다만 **이 선택에 대한 기록이 없다.** → ADR-0002 (예정)

```
domain/          인프라 의존 0 — 순수 자바
application/     유스케이스, 포트(DIP), 트랜잭션 경계
infrastructure/  JPA·Feign·Kafka 어댑터 (의존 방향이 안쪽을 향한다)
presentation/    컨트롤러
```

### 5.3 트랜잭션 전략

- **2PC 미사용, Saga(보상 기반)** 채택
- 오케스트레이션/코레오그래피는 **흐름마다 다르게** 선택 — 하나로 통일하지 않는다
- 결제 승인·망취소·이체·회원가입 = 오케스트레이션 / 알림·집계·탈퇴 정리 = 코레오그래피

**시스템 전역 규약**: 멱등성(ID-1~7) · Outbox(EV-1~6) · 재시도·타임아웃(RT-1~5) · Saga 상태(SG-1~5)

→ 상세: [`drafts/03-transaction-design.md`](03-transaction-design.md)

### 5.4 현재 구성 (재검토 대상)

11개 서비스가 존재하나 **경계 근거가 기록되어 있지 않다.** 서비스 분할은 재검토 대상이다(ADR-0003 예정).

| 구분 | 저장소 |
|---|---|
| 진입·인프라 | gateway-server, eureka-server, config-server, config-repo, infrastructure |
| 공용 | common-lib |
| 도메인 | auth-server, user-service, account-service, transaction-service, transfer-service, card-service, ledger-service |

**확인된 문제** (`conventions/abstraction-levels.md` §현재 식별된 문제의 레벨 분류):

| 결함 | 레벨 | 처리 |
|---|---|---|
| 서비스 경계가 기술 직관으로 결정됨 | ① 아키텍처 | ADR-0003 |
| 회원가입이 분산 트랜잭션인데 보상 없음 | ① 아키텍처 | `drafts/03-transaction-design.md` |
| 신뢰성 전략(Outbox/Saga)이 서비스마다 다름 | ① 아키텍처 | `drafts/03-transaction-design.md` |
| email 이중 저장 — 정합성 소유자 불명 | ① 아키텍처 | ADR-0003 |
| `Money` 6벌 중복 | ② 모듈 | ADR-0005 |
| 스키마 마이그레이션 도구 부재 (`ddl-auto: update`) | ② 모듈 | ADR (예정) |
| `User.previousStatus` 롤백 필드 누수 | ④ 클래스 | ①이 정해지면 자동 해소 |
